今日のテーマ：リレーショナルデータベースとSQLの基本（SELECT と JOIN）

① まず結論

リレーショナルデータベースは「二次元の表（テーブル）」を組み合わせてデータを管理する仕組みで、その操作言語が SQL（エスキューエル）です。[web:7][web:2]

SELECT と JOIN を理解すると、応用情報のデータベース問題だけでなく、実務での検索ロジックや画面一覧・集計処理の考え方を自分で設計できるようになります。[web:2][web:5]

② 仕組み：リレーショナルDBと SQL

リレーショナルデータベースは、行 × 列の表を複数用意し、それらを「キー（ID）」で関連付けて管理する方式です。[web:7] 例えば「社員テーブル」と「部署テーブル」を分けて、社員テーブルに部署ID（外部キー）を持たせて紐づけます。[web:7]

SQL はこのリレーショナルデータベースを操作するための共通言語で、SELECT（検索）、INSERT（追加）、UPDATE（更新）、DELETE（削除）などを使ってデータを扱います。[web:5][web:11] 試験・実務ともに、最も頻出で重要なのが SELECT 文と、複数テーブルを結合する JOIN です。[web:2][web:8]

SELECT 文の基本構造

SELECT 列名1, 列名2, ...
FROM テーブル名
WHERE 条件
ORDER BY 並び替え対象列;

「どのテーブルから（FROM）」「どんな条件で（WHERE）」「どの列を取得するか（SELECT）」「どう並べるか（ORDER BY）」という部品に分けて考えるのがポイントです。[web:2][web:5]

JOIN の基本構造（内部結合）

SELECT 列名
FROM テーブルA
INNER JOIN テーブルB
  ON テーブルA.キー列 = テーブルB.キー列
WHERE 条件;

INNER JOIN は、両方のテーブルに共通して存在するキーの組合せだけを取り出す結合で、社員と部署、注文と顧客のような「親子関係」をまとめて表示する時に使います。[web:2][web:7]

③ 身近な例：Webサービスや業務システム

EC サイトを例にすると、「顧客テーブル」「注文テーブル」「商品テーブル」があり、注文テーブルは顧客ID・商品IDを持っています。[web:7] 顧客一覧画面で「直近の注文日」や「購入金額合計」を表示するために、顧客テーブルと注文テーブルを JOIN して集計します。[web:7][web:2]

社内の勤怠システムでも、「社員」「所属」「勤怠記録」を別テーブルにし、画面表示時に JOIN して「社員名＋所属名＋当日の出退勤時刻」を一覧に出します。[web:7] このときの SQL の考え方は、そのまま応用情報午後のデータベース問題の ER 図やテーブル定義・SQL読解に対応します。[web:9][web:12]

④ 応用情報ではどう問われる？

応用情報の午前試験では、リレーショナルデータベースの構造、正規化、主キー・外部キー、SQL 文の結果を選ばせる 4 択問題が毎回複数出題されます。[web:1][web:4]

午後試験では「仕様 → ER 図 → テーブル定義 → SQL 記述・読解」という流れで 1題分まとめて問われることが多く、正しい JOIN 条件や WHERE 条件を考えさせる設問が頻出です。[web:4][web:9][web:12][web:13]

このテーマを理解していると、仕様からテーブル設計を考える問題や、複数テーブルを結合した SQL の出力結果を読み解く問題が解けるようになります。[web:9][web:12]

⑤ 試験で覚えるポイント（3〜5個）

  • リレーショナルデータベース＝二次元の表をキーで結びつける方式だと理解する。[web:7]
  • SELECT 文は「SELECT／FROM／WHERE／ORDER BY」の4つに分解して読む（書く）。[web:2][web:5]
  • INNER JOIN は「両テーブルに共通して存在するキーの組合せ」だけを取り出す結合である。[web:2][web:7]
  • 主キーは行を一意に識別する列、外部キーは他テーブルの主キーを参照して関連付ける列である。[web:7]
  • 午前は結果の読み取り中心、午後は仕様を踏まえた SQL 記述・テーブル設計まで問われることを意識する。[web:4][web:9][web:12]

🔗 基本情報とのつながり

FEではここまで： 基本情報では、SELECT・WHERE・ORDER BY・JOIN などの基本構文と、単純なテーブル結合や正規化の概念が 4択・科目B問題として出題されます。[web:2][web:11][web:14] SQL の文法を覚え、与えられたクエリの結果を表形式でイメージできることがゴールです。[web:2][web:5]

APではここまで理解する： 応用情報では、FE で学んだ SQL・正規化を前提に、業務仕様から ER 図やテーブル設計を自分で組み立て、その上で SQL を設計・修正する応用力が問われます。[web:3][web:15][web:9] また、午後試験で記述式の SQL を書かせたり、誤った結合条件による不整合や性能問題への気付きも評価されます。[web:12][web:13]

💻 実務とのつながり（ITエンジニア視点）

Web 開発や業務システム開発では、画面の一覧表示・検索機能・帳票出力など、多くの処理が「SELECT ＋ JOIN ＋ 集計」で成り立っています。[web:7][web:8] フレームワークや ORマッパーを使っていても、裏側では SQL が生成されているため、SELECT・JOIN の考え方を理解していると、遅いクエリの原因調査や N+1 問題の改善に役立ちます。[web:7]

また、GitHub Pages＋Supabase のような BaaS を使う場合も、管理画面でクエリを書く・確認する場面があり、DB 設計と SQL の基本が分かっていると「テーブルの切り方」「インデックスの張り方」「集計ロジックの実装方針」を自信を持って決められるようになります。[web:7][web:8]

🧠 1問だけ確認問題（AP 午前レベル＋午後意識）

ある EC システムには、次の2つのテーブルがあります。

顧客テーブル(customer)
  customer_id   主キー
  name          顧客名

注文テーブル(order)
  order_id      主キー
  customer_id   顧客ID（外部キー）
  order_date    注文日

「2024年1月1日以降に注文した顧客の顧客IDと顧客名、直近の注文日を一覧で取得したい」とき、最も適切な SQL として正しいものはどれでしょうか。

  1. SELECT customer_id, name, MAX(order_date) FROM customer WHERE order_date >= '2024-01-01';
  2. SELECT c.customer_id, c.name, MAX(o.order_date) FROM customer c INNER JOIN order o ON c.customer_id = o.customer_id WHERE o.order_date >= '2024-01-01' GROUP BY c.customer_id, c.name;
  3. SELECT c.customer_id, c.name, o.order_date FROM customer c, order o WHERE o.order_date >= '2024-01-01';
  4. SELECT c.customer_id, c.name FROM customer c WHERE EXISTS ( SELECT * FROM order o WHERE o.order_date >= '2024-01-01' );

正解

② が正解です。

解説

「顧客ごとに直近の注文日」を出したいので、顧客と注文を JOIN し、注文日で絞り込んだ上で、顧客単位に GROUP BY して MAX(order_date) を求める必要があります。[web:2][web:7] 選択肢②は INNER JOIN で customer と order をキー列 customer_id で結合し、WHERE で日付条件を絞り、GROUP BY で顧客ごとに集約しているため、要件に合致します。[web:2]

他の選択肢が違う理由

  • ①：FROM 句が customer のみで order テーブルを参照しておらず、order_date 列も存在しないため、表構造に合いません。[web:2]
  • ③：顧客と注文の結合条件（customer_id の等値結合）が書かれていないため、全組合せの直積（不正な結合）になり、顧客ごとの正しい注文日が得られません。[web:2][web:7]
  • ④：EXISTS 句で「条件を満たす注文が存在する顧客」を絞ることはできますが、直近注文日を SELECT していないため要件を満たしません。[web:2]
