CloudFront のしくみとキャッシュ

リクエストの流れ：キャッシュの 3 つの層

キャッシュミスのとき：オリジンから最初のバイトが届いたらすぐ利用者へ送り始め（全部を待たない）、次のリクエストに備えてキャッシュにも入れる。
ひっかけ：キャッシュできない動的なコンテンツにも CloudFront は効く。リクエストが AWS のバックボーンネットワークを通るから。
出典：CloudFront がコンテンツを配信する方法（「オリジンから最初のバイトが到着した直後に、CloudFront はそのオブジェクトをユーザーに転送し始めます。」「リクエスト時に決定される動的リクエストは、リージョン別エッジキャッシュを通過せず、直接オリジンに送信されます。」）／Amazon CloudFront とは何ですか?（「CloudFront は、コンテンツを最良の方法で供給できるエッジロケーションに各ユーザーリクエストを AWS バックボーンネットワーク経由でルーティングすることで、コンテンツの配信を高速化します。」）

Origin Shield：オリジンへのリクエストを 1 つにまとめる

項目内容
効果ヒット率が上がる。同時リクエストがまとまり、オリジンの負荷が下がる
置く場所オリジンへのレイテンシーが最も低いリージョン
料金追加料金がかかる
似たものリージョン別エッジキャッシュは自動で使われ、設定はいらない
見分け方：「オリジンの負荷を下げたい」「複数のリージョンの利用者が同じものを取りに来る」→ Origin Shield。無効化や TTL を短くすると、オリジンへのリクエストはかえって増える。
出典：Amazon CloudFront Origin Shield の使用（「Origin Shield を使用すると、CloudFront のすべてのキャッシュレイヤーからオリジンへのすべてのリクエストが Origin Shield を通過し、キャッシュヒットの可能性が高くなります。」「オリジンに対するレイテンシーが最も低い AWS リージョンを選択するようにしてください。」）

TTL：どれだけキャッシュに持つか

決める場所やり方効く範囲
キャッシュ動作最小・最大・デフォルトの TTL を設定する（キャッシュポリシー）同じパスパターンのすべてのファイル
オリジンのヘッダーCache-Control の max-age・s-maxage、または Expires を返すそのファイルだけ
何も設定しないキャッシュポリシーを使わないときの既定は 24 時間すべて
s-maxage の使いどころ：max-age と併用すると、ブラウザのキャッシュと CloudFront のエッジキャッシュで、保持する期間を変えられる。
出典：コンテンツをキャッシュに保持する期間 (有効期限) を管理する（「キャッシュポリシーの使用をオプトアウトした場合、デフォルトの TTL (有効期限) は 24 時間ですが、次の設定を更新してデフォルトを上書きできます。」「CloudFront キャッシュに最新バージョンがすでにある場合、オリジンはステータスコード `304 Not Modified` を返します。」）

キャッシュキーとキャッシュヒット率

ヒット率を上げる方法説明
キーを絞るオリジンが一意のオブジェクトを返すクエリ文字列・ヘッダー・Cookie だけをキャッシュポリシーで含める
そろえるパラメータの大文字と小文字、並べる順序を統一する
長く持つmax-age を実用的な範囲で長くする。Origin Shield を使う
出典：ポリシーを使用してキャッシュキーを制御する（「キャッシュキーに含まれる値が少なくなると、キャッシュヒットの可能性が高まります。」）／CloudFront キャッシュから直接提供するリクエストの割合 (キャッシュヒット率) を増やす（「オリジンが一意のオブジェクトを返すクエリ文字列パラメータのみを転送するように CloudFront を設定する。」）

古いファイルを消す：無効化 と バージョン付きファイル名

無効化（Invalidation）バージョン付きファイル名
やることエッジキャッシュのファイルを有効期限の前に消す（POP とリージョン別エッジキャッシュの両方）style_v2.css のように名前を変え、HTML の参照も変える
次のリクエストCloudFront がオリジンから最新版を取る新しい名前なので、最初から新しいファイル
ブラウザ・プロキシ古い版が残って見えることがある確実に新しい版になる
コスト無効化の料金がかかりうるこちらのほうが安い
向く場面誤って公開したファイルをすぐ消す頻繁に更新するファイル。ロールバックも簡単
見分け方：「すぐに配信を止めたい」→ 無効化。「頻繁に更新」「確実に新しい版」「コストを抑える」→ バージョン付きファイル名。
ひっかけ：TTL を短くしても、すでにキャッシュされたファイルはすぐには消えない。
出典：ファイルを無効化してコンテンツを削除する（「ファイルを無効にした場合、キャッシュ内でオブジェクトが有効期限切れになるまで、ユーザーに旧バージョンが引き続き表示されることがあります。」「バージョニングのほうが、コストが安くなります。」）／CloudFront がコンテンツを配信する方法（「たとえば、キャッシュ無効化リクエストでは、有効期限が切れる前に、POP とリージョン別エッジキャッシュの両方からオブジェクトが削除されます。」）

Global Accelerator

2 つの静的なエニーキャスト IP、リスナーとエンドポイントグループ、標準とカスタムルーティングのアクセラレーター、トラフィックダイヤルとエンドポイントの重み、クライアントアフィニティ、クライアント IP の保存、ヘルスチェック。

Global Accelerator の部品

静的 IP の良さ：取引先のファイアウォールや DNS に 1 回だけ登録すれば、後ろのエンドポイントやリージョンを変えても IP は変わらない。オリジンを 2 つの入口の後ろに隠すので、攻撃のリスクも減る。
ひっかけ：IP はアクセラレーターを無効にしても割り当てられたまま。削除すると失う。リージョンごとに IP が付くのではない。重みとリージョンの組み合わせは Claude が作った例。
出典：AWS Global Accelerator コンポーネント（「静的 IP アドレスは、アクセラレーターを無効にし、トラフィックを受け入れたりルーティングしたりしなくなった場合でも、存在する限り、アクセラレーターに割り当てられたままになります。」「各リスナーには 1 つ以上のエンドポイントグループが関連付けられ、トラフィックはいずれかのグループのエンドポイントに転送されます。」）／AWS Global Accelerator ユースケースについて（「Global Accelerator は、2 つの静的エントリポイントの背後にあるオリジンをマスキングすることで、攻撃のリスクを減らします。」）

標準アクセラレーターカスタムルーティングアクセラレーター
送り先の決め方ユーザーの場所・エンドポイントのヘルス・重みなどで最適なものへ外部の静的 IP とリスナーポートで、特定の EC2 とポートに決まった形で
エンドポイントALB（内部向けも可）・NLB・EC2・Elastic IPVPC のサブネット（中の EC2 のプライベート IP）
クライアント IPALB・EC2・セキュリティグループ付き NLB で保存できる常に保存される
使う場面世界の利用者を最も近い正常なリージョンへ。素早い切り替えVoIP やオンラインゲームで、複数の利用者を同じセッションのサーバーに集める

クライアント IP の保存とヘルスチェック

エンドポイント（標準アクセラレーター）クライアント IP の保存
Application Load Balancerできる
EC2 インスタンスできる
NLB（セキュリティグループあり）できる
NLB（セキュリティグループなし）できない
Elastic IP アドレスできない
ヘルスチェック：定期的にすべてのエンドポイントを確かめ、正常なものだけに送る。異常になると、新しい接続を瞬時にほかの正常なエンドポイントへ。正常なものが 1 つもないときは、グループのすべてのエンドポイントに送る。
ひっかけ：全部が異常でも「503 を返す」「捨てる」ではない。Global Accelerator が CloudFront に送るしくみもない。
出典：AWS Global Accelerator でクライアント IP アドレスを保存する（「Global Accelerator は、カスタムルーティングアクセラレーター上のエンドポイントのクライアント IP アドレスを常に保存します。」）／アクセラレーターのヘルスチェックアクセスを確保する（「トラフィックをルーティングする正常なエンドポイントがない場合、Global Accelerator は受信クライアントリクエストをエンドポイントグループ内のすべてのエンドポイントにルーティングします。」）

まとめ
