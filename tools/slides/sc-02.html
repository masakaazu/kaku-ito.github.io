第2章

パスワードと資格情報への攻撃

「何を固定して、何を変えるか」で見分ける。ハッシュ値は解読しなくても使われることがある。

支援士 #02 攻撃の流れと認証への攻撃23-2

パスワードを当てる攻撃：何を固定し、何を変えるか

攻撃固定変えて試すロックは効く？
ブルートフォース1つの IDすべての文字の組合せ効く
辞書攻撃1つの ID辞書の単語・人名・その組合せ効く
リバースブルートフォース1つのパスワード多数の ID効かない（各 ID は1回）
パスワードスプレーよく使われるパスワード多数の ID に、時刻と接続元 IP を変えて少しずつ回避される
クレデンシャルスタッフィング漏れた ID とパスワードの組別のサイトで試す失敗が少なく気付きにくい
R4春 問4文字の種類 M、文字数 n のパスワードの総数は Mⁿ（同じ文字を何度使ってもよく、順番も区別する）。
M!/(M−n)! は「同じ文字を使わない並べ方」、M!/(n!(M−n)!) は「組合せ」なので誤り。
共通の切り札は MFA。加えて、スプレーやリバースは「1つの ID の失敗回数」では見えないので、組織全体のログイン失敗の傾向や接続元を監視する。スタッフィングは使い回しの禁止と、漏えいしたパスワードの利用の拒否。
出典：IPA 午前Ⅱ 令和4年度秋期 問6（パスワードスプレー）・令和4年度春期 問4（総数の式）／IPA「支援士試験 シラバス（案）」用語例「ブルートフォース攻撃，リバースブルートフォース攻撃，クレデンシャルスタッフィング」

ハッシュ値をねらう攻撃：解読するか、そのまま使うか

レインボーテーブル攻撃（解読する）
Pass the Hash（解読しない）
R7秋 問2（R5春・R3秋と同じ）「ハッシュ値から導出された平文パスワードを使う」は解読してから使うので Pass the Hash ではない。正解は「パスワードのハッシュ値だけでログインできる仕組みを悪用してログインする」。
Pass the Hash の対策：管理者アカウントを端末ごとに分ける（同じパスワードの使い回しをしない）、特権アカウントの利用を絞る（PAM）、メモリからの認証情報の窃取を防ぐ OS の機能、NTLM より強い認証方式に移す。
出典：IPA 午前Ⅱ 令和7年度秋期 問2／IPA「支援士試験 シラバス（案）」用語例「レインボーテーブル攻撃」、中分類26「パスワードクラック対策（ソルト，ストレッチング など）」

多要素認証をすり抜ける攻撃

MFA 疲労攻撃（プッシュ通知爆撃）
  1. 攻撃者は ID とパスワードをすでに持っている
  2. ログインを何度も試し、承認の通知を大量に送る
  3. 利用者が根負けや誤操作で「承認」を押す
対策：番号照合（ログイン画面の数字を入力させる）、通知に地域やアプリ名を表示、短時間の繰り返しを制限、パスキーへの移行。
AiTM フィッシング（中継型）
ワンタイムコードは中継されると防げない。パスキー（FIDO2）はブラウザが接続先のオリジンを確かめて署名するので、偽ドメインでは成り立たない＝フィッシング耐性（#10）。
ひっかけ：「パスワードを長くする」「有効期限を短くする」は、攻撃者がすでにパスワードを持っている／その場で中継している攻撃には効かない。
出典：IPA「支援士試験 シラバス（案）」用語例「MFA 疲労攻撃（…プッシュ通知爆撃（Push Bombing））」、中分類25「フィッシング耐性のある認証」「FIDO（FIDO2，WebAuthn，CTAP，パスキー）」
第3章

セッションと通信への攻撃

ログインのあとは「セッション ID」が本人の証明になる。そこと、通信の途中が狙われる。

支援士 #02 攻撃の流れと認証への攻撃23-2

セッションハイジャックとセッション固定化

セッションハイジャック（あとから盗む）
盗まれ方対策
推測（連番・時刻）暗号論的な乱数で十分長い ID
盗聴HTTPS、cookie の Secure 属性
XSS で cookie を読むXSS 対策、HttpOnly 属性
URL に埋め込んだ ID の漏えいID は cookie で受け渡す
セッション固定化（先に渡しておく）
  1. 攻撃者がサイトから正規のセッション ID を手に入れる
  2. その ID を利用者に使わせる（細工したリンクなど）
  3. 利用者がその ID のままログインする
  4. 攻撃者が同じ ID で、ログイン済みとして入る
対策：ログインに成功したら新しい ID を発行し、古い ID を無効にする。ID を URL で受け渡さない。
出典：IPA「安全なウェブサイトの作り方」（セッション管理の不備）／IPA「支援士試験 シラバス（案）」用語例「セッションハイジャック，セッション固定化攻撃（Session Fixation），リプレイ攻撃」

リプレイ攻撃と中間者攻撃

リプレイ攻撃：盗聴したものを再送する
対策：毎回変わる値を混ぜる。チャレンジレスポンス、ナンス、タイムスタンプ、シーケンス番号、ワンタイムパスワード。「毎回同じハッシュ値を送る」は再送されれば通る。
中間者攻撃（MITM）：間に入り込む
入り込み方防ぎ方
偽の Wi-Fi アクセスポイントTLS とサーバ証明書の検証
ARP スプーフィングDHCP スヌーピング・動的 ARP 検査（#13）
DNS の偽の応答DNSSEC（#14）
HTTPS を HTTP に下げるHSTS（#17）
証明書の警告を無視して接続すると、TLS を使っていても中間者攻撃は防げない。
出典：IPA「支援士試験 シラバス（案）」用語例「リプレイ攻撃」／中分類25「TLS」「DHCP スヌーピング」、中分類26「HSTS」

MITB 攻撃：ブラウザの中で取引を書き換える

対策（R4春 問11 の選択肢）効く？理由
EV SSL サーバ証明書で接続先を確認✕接続先は本物の銀行
ログインのワンタイムパスワード✕ログインは本人が正しく行う。書き換えはログイン後
SSL ではなく TLS で暗号化✕書き換えは暗号化の前（ブラウザの中）
トランザクション署名○取引内容そのものを、PC と別の機器で検証する
出典：IPA 午前Ⅱ 令和4年度春期 問11（令和2年度10月 問10）。図の口座や金額は Claude が作った例

トランザクション署名のしくみ

  1. 別の機器で計算：ハードウェアトークン（またはスマホ）に振込先口座番号と金額を入力し、MAC を作る
  2. 送る：振込画面に振込先・金額・MAC を入力して銀行に送る
  3. 銀行で計算：受け取った振込先・金額から、同じ手順で MAC を作る
  4. 照合：②の MAC と③の MAC が一致すれば、振込先と金額は改ざんされていない
H31春 問8④でできるのは「振込先口座番号と振込金額が改ざんされていないことを確認できる」。
盗聴されていないこと・盗聴者の特定・改ざん箇所の訂正は、MAC ではできない。
R5秋 問7トランザクション署名＝「送金操作を行う PC とは別のデバイスに振込先口座番号などの取引情報を入力して表示された値」を送る。
取引内容に結び付かないワンタイムパスワード（メール・ログイン用）は誤り。
2つの条件：①PC とは別の機器で計算する（PC のマルウェアが触れない）、②取引の内容（振込先・金額）を入力して計算する。どちらが欠けても MITB は防げない。MAC のしくみは #16。
出典：IPA 午前Ⅱ 平成31年度春期 問8・令和5年度秋期 問7

比べるもの見分けるポイント
