RDS の可用性とスケーリング

3 つの構成：スタンバイは読めない

いちばんのひっかけ：「読み取りの負荷を下げたい」にマルチ AZ DB インスタンスを答えさせる選択肢。そのスタンバイは読み取りを処理できない。読み取りを逃がすのはリードレプリカかマルチ AZ DB クラスター（Aurora なら Aurora レプリカ）。
出典：Amazon RDS のマルチ AZ DB インスタンスデプロイ（「高可用性のオプションは、読み取り専用シナリオ向けのスケーリングソリューションではありません。」「スタンバイレプリカを使用してリードトラフィックを処理することはできません。」）／Amazon RDS のマルチ AZ DB クラスターデプロイ（「マルチ AZ DB クラスター配置では、準同期レプリケーションを使用します。」）／DB インスタンスのリードレプリカの操作（「RDS は、リードレプリカの自動スケーリングをサポートしていません。」）

比べて選ぶ

構成複製読める選ぶ合図
マルチ AZ DB インスタンス別の AZ のスタンバイ 1 台へ同期読めない「AZ の障害でも自動で復旧」「読み取りの分散は不要」
マルチ AZ DB クラスター3 つの AZ のリーダー 2 台へ準同期読める「高可用性と読み取りの拡張を 1 つで」「書き込みレイテンシーを低く」
リードレプリカ非同期（最大 15 台）読める「レポートのクエリを本番から分ける」「数秒遅れのデータでよい」
クロスリージョンリードレプリカ別のリージョンへ非同期読める「リージョンの災害対策」「遠くの利用者の近くで読む」「リージョンの移行」
同期と非同期：同期（マルチ AZ DB インスタンス）はコミットの時点でスタンバイにも書かれるのでデータを失いにくいが、書き込みのレイテンシーが長くなることがある。非同期（リードレプリカ）はプライマリを待たせないが、少し遅れる。
組み合わせられる：マルチ AZ の DB インスタンスにリードレプリカを付けられる。スタンバイへは同期、リードレプリカへは非同期で複製され、読み取りはリードレプリカだけが受ける。
出典：Amazon RDS のマルチ AZ DB クラスターデプロイ（「マルチ AZ DB クラスターは、マルチ AZ DB インスタンスの配置と比較して、高可用性、読み取りワークロードの容量の増加、および書き込みレイテンシーの低減を提供します。」）／DB インスタンスのリードレプリカの操作（「スタンバイレプリカとのレプリケーションは同期的です。」「リードレプリカとは異なり、スタンバイレプリカは読み取りトラフィックを処理できません。」）／Amazon RDS のクォータと制約

クロスリージョンリードレプリカと昇格

使い道は 3 つ：災害対策、利用者に近いリージョンでの読み取り、リージョン間の移行。昇格すると再起動し、ソースとの複製は止まる。昇格には数分以上かかることがある。
読まないなら：別のリージョンで復元できればよく、ふだんの読み取りに使わないなら、DB を動かし続けない「自動バックアップのクロスリージョンレプリケーション」のほうが安い（次の章）。
出典：別の AWS リージョン でのリードレプリカの作成（「Amazon RDS では、リードレプリカをソース DB インスタンスとは異なる AWS リージョン に作成できます。」「クロスリージョンレプリケーションから転送されたデータには、Amazon RDS のデータ転送料金が発生します。」）／リードレプリカをスタンドアロン DB インスタンスに昇格させる（「リードレプリカを昇格させると、RDS によって DB インスタンスが使用可能になる前に DB インスタンスが再起動されます。」）

RDS Proxy・ストレージの自動スケーリング・RDS Custom

RDS Proxy（接続をプールする）
接続の急増から DB を守る。フェイルオーバーでもアプリの接続を保つ。IAM 認証を強制でき、ほとんどのアプリはコードを変えずに使える。
ストレージの自動スケーリングと RDS Custom
機能内容
ストレージの自動スケーリング空き領域が 10% 未満の状態が 5 分以上続くと、ストレージを自動で増やす。増えるのはストレージだけ（CPU・メモリ・台数は変わらない）
RDS CustomDB と OS の管理者権限が要るアプリ向け。OS とデータベース環境をカスタマイズでき、管理作業は自動化される
ふつうの RDS基盤のホストにアクセスできず、一部の特権も制限される。すべて AWS に任せたいとき
出典：Amazon RDS Proxy（「Amazon RDS Proxy を使用すると、アプリケーションでデータベース接続をプールおよび共有して、アプリケーションのスケーリング能力を向上させることができます。」）／Amazon RDS ストレージの自動スケーリングによる容量の自動管理（「使用可能な空き領域は、割り当てられたストレージの 10% 未満です。」「低ストレージ状態は 5 分以上続きます。」）／Amazon RDS Custom（「マネージドサービスエクスペリエンスを提供するために、Amazon RDS では基盤となるホストにアクセスできません。」）

バックアップと特定時点への復元（PITR）

バックアップ特徴選ぶ合図
自動バックアップDB インスタンス全体。保持期間は 0〜35 日（0 で無効）。DB を消すとき「保持」を選ばないと一緒に消える「数分前・数日前に戻す」
DB スナップショット（手動）保持期間で消えず、DB を消しても残る。コピー（別リージョン・暗号化）と共有ができる「35 日より長く残す」「変更の前に」
クロスリージョンの自動バックアップスナップショットとログを別のリージョンにも複製。マルチ AZ DB クラスターは不可「別のリージョンで PITR」「読み取りは不要」
出典：Amazon RDS の DB インスタンスを特定の時点に復元する（「DB インスタンスを特定の時点に復元し、ソース DB インスタンスを変更せずに新しい DB インスタンスを作成できます。」「RDS は、DB インスタンスのトランザクションログを 5 分ごとに Amazon S3 にアップロードします。」）／バックアップの保存期間（「DB インスタンスのバックアップ保持期間は、0 ～ 35 日間で設定できます。」）／別の AWS リージョン への自動バックアップのレプリケーション（「自動バックアップレプリケーションは、マルチ AZ DB クラスターではサポートされていません。」）

暗号化と、パスワードの扱い

暗号化していない DB を暗号化する
機能内容ひっかけ
RDS の暗号化（KMS）ストレージ・ログ・自動バックアップ・リードレプリカ・スナップショットを AES-256 で。アプリの変更は不要作成後に KMS キーは変えられない。暗号化なしの DB の暗号化レプリカは作れない
IAM データベース認証パスワードの代わりに認証トークン（有効期間 15 分）。MariaDB・MySQL・PostgreSQLパスワードを「管理」するのではなく「使わない」
Secrets Manager との統合マスターユーザーのパスワードを RDS が Secrets Manager で管理し、既定で 7 日ごとにローテーションパスワード自体はある。自動で変えるのが目的
出典：Amazon RDS リソースの暗号化（「ただし、暗号化されていないスナップショットのコピーは暗号化できるので、暗号化されていない DB インスタンスに効果的に暗号化を追加できます。」）／MariaDB、MySQL、および PostgreSQL の IAM データベース認証（「この認証方法では、DB インスタンスに接続するときにパスワードを使用する必要はありません。」）／Amazon RDS および AWS Secrets Manager によるパスワード管理（「RDS はシークレットの設定を管理し、デフォルトで 7 日ごとにシークレットをローテーションします。」）

ブルー/グリーンデプロイとメンテナンス

ブルー/グリーンデプロイ
エンジンのバージョンアップやパラメータの変更を、本番に影響なく試す。データは失われず、アプリの変更も不要。RDS では MariaDB・MySQL・PostgreSQL。
マルチ AZ のメンテナンスの順番
順すること
1スタンバイにメンテナンスを行う
2スタンバイをプライマリに昇格させる
3旧プライマリにメンテナンスを行い、新しいスタンバイにする
メンテナンスウィンドウは DB インスタンスごとの週単位の 30 分。必須として自動で入るのは、セキュリティと信頼性に関わるパッチだけ。
出典：Amazon RDS ブルー/グリーンデプロイの概要（「切り替えには通常 1 分もかからず、データが失われることはなく、アプリケーションを変更する必要もありません。」）／DB インスタンスのメンテナンス（「旧プライマリでメンテナンスを実行し、その旧プライマリが新しいスタンバイになる。」「セキュリティやインスタンスの信頼性に関連するパッチのみ、必須のパッチ適用として自動的にスケジューリングされます。」）。バージョンの番号は Claude が作った例

Amazon Aurora

3 つの AZ に 6 つのコピーを持つクラスターボリューム、Aurora レプリカと 3 種類のエンドポイント、Auto Scaling と Serverless v2、Global Database、バックトラックとクローン、I/O-Optimized。

AWS SAA #15 RDS と Auroraタスク 3.3

Aurora のしくみ：ストレージを共有するクラスター

6 つのコピー：書き込みは 3 つの AZ の 6 つのストレージノードに同期で複製される。リーダーがいてもいなくても、ライター 1 台だけでもストレージは 3 AZ。インスタンスはストレージを共有するので、レプリカのラグは通常 100 ミリ秒未満で、追加もすぐ。
インスタンスの可用性は別：ライター 1 台だけだと、障害のときに引き継ぐインスタンスがない。別の AZ に Aurora レプリカを足すと、その 1 台がプライマリを引き継ぐ（マルチ AZ になる）。
出典：Amazon Aurora の高可用性（「データがプライマリ DB インスタンスに書き込まれると、Aurora によりアベイラビリティーゾーン全体で、クラスターボリュームに関連付けられた 6 つのストレージノードにデータが同期的に複製されます。」「問題がプライマリインスタンスに影響する場合、これらのリーダーインスタンスの 1 つがプライマリインスタンスとして引き継ぎます。」）／Amazon Aurora でのレプリケーション（「このラグは、通常はプライマリインスタンスが更新を書き込んだ後、100 ミリ秒未満です。」）

エンドポイントとストレージ設定

エンドポイントつながる先使う場面
クラスターエンドポイントいまのプライマリ（ライター）。フェイルオーバーしても同じ接続文字列書き込み（INSERT・DDL・DML）
リーダーエンドポイントすべての Aurora レプリカに接続を自動で分散ふつうの読み取り
カスタムエンドポイント選んだインスタンスの組だけ大きさの違うインスタンスを分析用に分ける
インスタンスエンドポイント特定の 1 台診断・チューニング
ストレージ設定I/O の料金向く場合
Aurora Standard100 万リクエストごとに課金I/O が総支出の 25% 未満
Aurora I/O-Optimized追加料金なしI/O が総支出の 25% 以上

Aurora Auto Scaling と Aurora Serverless v2

Aurora Auto Scaling（リーダーの台数を増減）
Aurora Serverless v2（容量そのものを伸縮）
Auto Scaling：Aurora レプリカの数を CloudWatch のメトリクスとターゲット値で調整する。ライターの負荷には効かない。
Serverless v2：1 ACU は約 2 GiB のメモリと CPU・ネットワーク。0〜256 ACU。最小を 0 ACU にすると、使わないときに一時停止して料金を抑える。グラフの形は Claude が描いた模式図。
出典：Aurora レプリカでの Amazon Aurora Auto Scaling（「Aurora Auto Scaling は、ライター DB インスタンスのワークロードには適用されません。」）／Aurora serverless の仕組み（「各 ACU では、約 2 ギビバイト (GiB) のメモリと、対応する CPU、ネットワークが組み合わせられています。」「最小容量が 0 ACU の場合、ワークロードが実行されていないときは、クラスターは 0 にスケールされます。」）

Aurora Global Database

選ぶ合図：「世界中の利用者が近くで読む」「書き込みは 1 リージョン」「リージョン全体の障害に分単位で切り替える」。計画的な切り替えはスイッチオーバー、障害のときはフェイルオーバー。
RDS との違い：RDS ではクロスリージョンリードレプリカ（非同期・昇格は手動）。Aurora の Global Database は専用のインフラで複製し、セカンダリはそれぞれクラスターとして読み取りを拡張できる。
出典：Amazon Aurora Global Database の使用（「Aurora Global Database は、データが書き込まれる 1 つのプライマリ AWS リージョンと、最大 10 の読み取り専用セカンダリ AWS リージョンで構成されます。」）／Amazon Aurora Global Database でのスイッチオーバーまたはフェイルオーバーの使用（「Aurora Global Database の場合、RTO は分単位になります。」「Aurora Global Database の場合、RPO (目標復旧時点) は通常、秒単位で測定されます。」）。リージョンの組み合わせは Claude が作った例

戻す・複製する：PITR・バックトラック・クローン

機能何が起きる対象選ぶ合図
特定時点への復元保持期間（1〜35 日）の任意の時点で、新しいクラスターを作るAurora 全般「新しい DB でよい」「数日前に戻す」
バックトラック新しいクラスターを作らず、同じクラスターを巻き戻す（最大 72 時間）。前後に何度も動かせるAurora MySQL「WHERE 句のない DELETE を数分で戻す」
