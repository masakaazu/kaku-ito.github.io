デジタル署名と MAC の違い（R4秋・R6春）

デジタル署名
送信者ハッシュ値を自分の秘密鍵で署名
→
誰でも送信者の公開鍵で検証
MAC
送信者メッセージ＋共通鍵
→
受信者同じ共通鍵で計算し照合
MAC署名
完全性受信者が確認誰でも確認
第三者への証明できないできる
否認防止できないできる
MAC は受信者も同じ値を作れる → 第三者には「送信者が作った」と証明できない。MAC は公開鍵では作らない。
HMAC：鍵を内外2回使う構造で伸長攻撃を防ぐ（RFC 2104）。
出典：IPA 午前Ⅱ 令和4年度秋期 問1・令和6年度春期 問2／NIST FIPS 186-5／RFC 2104

XML 署名とコードサイニング

XML 署名の3つの形（R1秋・R5秋・R7秋）
形位置関係
エンベロープ署名署名を対象の中に入れる
エンベローピング署名署名の中に対象を包む
デタッチ署名別々に置く。同じ XML 文書の別エレメントにもできる
CMS（S/MIME の構文）や ASN.1（X.509 の記述）は XML 署名では使わない。署名も XML で書く。
コードサイニング
配布者がプログラムに署名コードサイニング証明書＋タイムスタンプ
利用者が検証配布者は誰か・改ざんがないか
安全なプログラムであることは保証しない。署名鍵を盗まれるとマルウェアにも正規の署名が付く。
出典：W3C「XML Signature Syntax and Processing Version 1.1」／IPA 午前Ⅱ 令和7年度秋期 問6

証明書パス検証と失効の確認

ルート CA 証明書（自己署名）OS・ブラウザに組み込み＝信頼の起点
中間 CA 証明書ルートの秘密鍵で署名
サーバ証明書 www.example.jp中間 CA の秘密鍵で署名
下から順に、署名・期限・失効・用途を確かめる（RFC 5280 6章）。
方法しくみ

証明書の発行を管理する：CA/B・ACME・CAA・CT

仕組み何をするかいつ効く
CA/Browser Forum発行基準（Baseline Requirements）。最大有効期間 398 日 → 2029年に 47 日へ短縮が決定業界のルール
ACMEHTTP-01・DNS-01 のチャレンジでドメイン管理を確かめ、発行・更新を自動化（Let's Encrypt）発行・更新のとき
CAA レコード発行してよい CA を DNS で指定。CA は発行前に確認発行の前に防ぐ
CT発行した証明書を公開ログに登録。所有者が監視発行の後に見つける

まとめ：本番での問われ方

MAC：共通鍵で作る → 受信者が完全性を確認。第三者には証明できない。署名：送信者の秘密鍵で作り、公開鍵で誰でも検証。
XML 署名：デタッチ署名は同じ文書の別エレメントにも。CMS・ASN.1 は使わない。
役割：RA＝本人確認と承認、CA＝署名と発行、VA＝失効の問合せに応答、CPS＝運用の詳細の文書。
CRL：期限内に失効した証明書のシリアル番号。OCSP：失効情報の問合せ。
証明書：規格は X.509。CA は公開鍵を含む情報に、CA の秘密鍵で署名。CAA：不正な発行を防ぐ。
応用：秘密分散・準同型・ゼロ知識証明・TEE・ML-KEM/ML-DSA・暗号アジリティ。
