最小ストレージ期間と最小サイズを計算する

Standard-IA に入れて 10 日で消すと（Claude の例）
期間の前に削除・上書き・別のクラスへの移行をすると、残りの日数分が日割りでかかる。Deep Archive は 180 日、Glacier Flexible Retrieval と Instant Retrieval は 90 日。
10 KB のオブジェクトを Standard-IA に置くと
Intelligent-Tiering は 128 KB 未満を見張らず、自動の階層化の対象にしない。
選び方：128 KB 以上で、30 日以上置き、月に 1 回くらいしか読まない → Standard-IA。四半期に 1 回くらいでミリ秒で読みたい → Glacier Instant Retrieval。読み方が読めない → Intelligent-Tiering。
出典：Amazon S3 ストレージクラスの理解と管理（「30 日前に削除、上書き、または別のストレージクラスに移行されたオブジェクトは、通常のストレージ使用料に加えて、最低 30 日間の残りの期間分の日割り料金が発生します。」「オブジェクトが 128 KB 以下の場合、Amazon S3 は 128 KB に相当する料金を請求します。」）

S3 のコストを下げる設定

ライフサイクルの移行と 128 KB移行のリクエストはオブジェクトごとに課金。2024 年 9 月から 128 KB 未満はデフォルトで移行しない。Glacier Flexible・Deep Archive へはオブジェクトごとに 40 KB のオーバーヘッド
不完全なマルチパートアップロードの中止途中の部品にも保存の料金。AbortIncompleteMultipartUpload のルールがベストプラクティス。早期削除の料金はかからない
リクエスタ支払いリクエストとダウンロードの料金をリクエストした人が払う。保存は所有者。匿名のアクセスは不可
S3 Storage Lens組織・アカウント・バケットのメトリクスを集め、コスト最適化とデータ保護の推奨を示す
アーカイブの取り出し速さ料金
高速すばやい（プロビジョンドキャパシティで容量を保証）プレミアム機能（緊急の料金）
標準（デフォルト）Flexible はふつう 3〜5 時間、Deep Archive は 12 時間以内大容量より高い
大容量最も遅い最も安い。大量のデータ向け
出典：Amazon S3 ライフサイクルを使用したオブジェクトの移行（「オブジェクトごとに移行リクエストが課金されるためです。」）／不完全なマルチパートアップロードを削除するためのバケットライフサイクル設定の設定（「ベストプラクティスとして、ストレージコストを最小限に抑えるため、AbortIncompleteMultipartUpload アクションを使用してライフサイクルルールを設定することをお勧めします。」）／アーカイブ取得オプションを理解する（「大容量取り出しでは、大量のデータを安価に取得できます。」）

リクエスタ支払い：だれが何を払うか

使いどころ：郵便番号のリスト・参照データ・地理空間の情報・ウェブクロールのデータなど、大きなデータセットを共有したいが、アクセスの費用は負担したくないとき。
ひっかけ：リクエスタ支払いにしても、保存の料金は所有者。誰が払うかわからない匿名のアクセスはできなくなる。署名付き URL や CloudFront は、料金を払う人を変えない。
出典：ストレージの転送と使用にリクエスタ支払い汎用バケットを使用する（「リクエスタ支払いバケットの場合、リクエストおよびバケットからのデータのダウンロードにかかるコストは、所有者でなくリクエストを実行したリクエスタが支払います。」「データの保管にかかるコストは常にバケット所有者が支払います。」「汎用バケットでリクエスタ支払いを有効にすると、そのバケットへの匿名アクセスは許可されなくなります。」）

データ転送の料金マップ

考え方：データ転送の料金は、送信元・送信先・量で決まる。高い可用性のための AZ 間の転送は必要なコストとして受け入れ、大量の往復やリージョンをまたぐ転送は設計で減らす。どこに料金がかかっているかは CUR の使用タイプや Cost Explorer で見る。
出典：データ転送料金について（「特定のリソースについては、 AWS リージョン内のデータ転送におけるインバウンドトラフィックとアウトバウンドトラフィックの両方に対して課金されます。」「転送先のリージョンに転送されたデータには料金はかかりません。」「インターネットからへのデータ転送には料金はかかりません AWS。」）

NAT ゲートウェイの料金と減らし方

NAT ゲートウェイの料金減らし方
使える時間 1 時間ごと大量に送るリソースと同じ AZ に置く。または、リソースがある各 AZ に NAT ゲートウェイを作る
処理したデータ 1 GB ごとAWS のサービス宛てのトラフィックは、ゲートウェイエンドポイントやインターフェイスエンドポイントで NAT を通さない
出典：NAT ゲートウェイの料金（「NAT ゲートウェイをプロビジョンすると、NAT ゲートウェイが使用可能な時間 1 時間ごと、およびゲートウェイが処理するデータ 1 GB ごとに課金されます。」「または、リソースがある各アベイラビリティーゾーンに NAT ゲートウェイを作成します。」）

エンドポイントと NAT インスタンス

ゲートウェイエンドポイントインターフェイスエンドポイント
対象S3 と DynamoDB多くの AWS のサービス（S3・DynamoDB も）
料金追加料金なし追加料金がかかる
しくみルートテーブルに経路を足すVPC の中にプライベート IP のネットワークインターフェイス

選び方：VPC の中から同じリージョンの S3・DynamoDB へ → ゲートウェイエンドポイント（無料）。オンプレミスから Direct Connect や VPN で S3 へプライベートに → インターフェイスエンドポイント。
NAT インスタンス：NAT AMI のもとの Amazon Linux AMI はメンテナンスサポートが 2023 年 12 月 31 日に終わった。AWS は NAT ゲートウェイへの移行を勧めている（可用性と帯域幅に優れ、運用の手間が少ない）。

CloudFront・Direct Connect・スロットリング

何を減らすか料金・しくみ
CloudFrontオリジンの負荷とデータ転送（エッジでキャッシュ）使用タイプ・地域・選んだ機能で変わる
Direct Connect大量のデータをインターネット経由で送るコストポート時間料金（容量と専用・ホスト型で決まる）＋データ転送出力
API Gateway のスロットリング呼び出しすぎによるバックエンドの負荷とコストトークンバケット。超えると 429 Too Many Requests
スロットリングがかかる順（API Gateway）
1. 使用量プランのクライアント・メソッドごとAPI キーで顧客を見分け、レートとクォータを決める
2. ステージのメソッドごとメソッドごとに違う設定もできる
3. アカウント（リージョンごと）申請で引き上げられる
4. AWS のリージョン全体すべてのアカウントに効く
決め手：「世界中に静的なファイルを配り、送信の料金を減らす」→ CloudFront。「毎月何十 TB もオンプレミスとやり取り」→ Direct Connect（インターネット経由よりコスト効率がよく確実）。「特定の顧客の呼び出しすぎ」→ 使用量プランと API キー。
出典：COST08-BP02 データ転送コストを最適化するコンポーネントを選択する（「インターネットを介して大量のデータを転送するよりも、この方が高コスト効率で確実です。」）／Direct Connect とは（「ポート時間料金は容量および接続のタイプ (専用接続あるいはホスト型接続) によって決定されます。」）／API Gateway のスループットを向上させるために REST API へのリクエストをスロットリングする（「API Gateway は、トークンバケットアルゴリズムを使用してトークンでリクエストをカウントし、API へのリクエストを調整します。」）
