第1章

ストレージクラス

アクセスの多さ・取り出しの速さ・AZ の数・最小ストレージ期間で選ぶ。自動で選ぶ Intelligent-Tiering、アーカイブの復元、1 つの AZ の 2 つのクラス。

AWS SAA #13 Amazon S3タスク 3.1

ストレージクラスの地図

選び方の順：①どれくらい読むか（頻度）②読むときの速さ（ミリ秒か、数分〜数時間待てるか）③ AZ を失ってもよいか（作り直せるか）④どれくらい残すか（最小ストレージ期間）。頻度が分からないなら Intelligent-Tiering。
出典：Amazon S3 ストレージクラスの理解と管理（「デフォルトでは、S3 のオブジェクトは S3 Standard ストレージクラスに保存されますが、Amazon S3 は、保存するオブジェクトに対して、広範なストレージクラスを提供します。」「S3 One Zone-IA (ONEZONE_IA) と S3 Express One Zone (EXPRESS_ONEZONE) を除くすべてのストレージクラスは、災害によるアベイラビリティーゾーンの物理的な損失に対して回復力を持つように設計されていることに注意します。」）

S3 Intelligent-Tiering：自動で階層を移る

選ぶ合図：「アクセスのパターンが分からない・変わる」「運用の手間なく自動で」なら Intelligent-Tiering。決まった日数で動かすならライフサイクル。小さなファイルばかりなら効果が出ない。
出典：Amazon S3 ストレージクラスの理解と管理（「低頻度アクセス – S3 Intelligent-Tiering では、30 日間連続してアクセスされなかったオブジェクトは低頻度アクセス階層に移動されます。」「オブジェクトのサイズが 128 KB 未満の場合は、モニタリングされず、自動階層化に適していません。」）／S3 Intelligent-Tiering の仕組み（「低頻度アクセス階層またはアーカイブインスタントアクセス階層にあるオブジェクトに後からアクセスすると、自動的に高頻度アクセス階層に戻されます。」）

本番の場面：「急ぎで数個を数分で」→ 迅速。「大量を安く、半日待てる」→ 大容量。「いつでもミリ秒で、でもめったに読まない」→ Instant Retrieval。「年 1 回未満、2 日待てる、最も安く」→ Deep Archive。
迅速を確実に：需要が高いときは迅速取り出しが使えないことがある。確実にしたいならプロビジョンドキャパシティーを買う。もっと予測どおりに速く読みたいなら Instant Retrieval を検討する。
出典：アーカイブ取得オプションを理解する（「3 つの取り出しアクセスオプション (高速、標準、大容量) から選択して、希望する取り出し速度に基づいてアーカイブされたオブジェクトを復元できます。」「プロビジョンドキャパシティーがなくても、需要が異常に高い期間は、迅速取り出しを使用できない可能性があります。」）／長期データストレージとしての S3 Glacier ストレージクラスを理解する（「一括取り出しは無料です。」）

1 つの AZ のクラス：One Zone-IA と Express One Zone

S3 One Zone-IA（安く置く）
Standard-IA より安い。CRR のコピー先のレプリカや、元から作り直せるデータに。作り直せないデータは Standard-IA。
S3 Express One Zone（速く読む）
レイテンシーが最も低いクラス。コンピューティングと同じ AZ に置ける。AZ の損失には耐えられない。
出典：Amazon S3 ストレージクラスの理解と管理（「Amazon S3 はオブジェクトデータを 1 つのアベイラビリティーゾーンでのみ保存するため、S3 Standard-IA よりも安価になります。」「S3 Express One Zone は、現在入手可能なレイテンシーが最も低いクラウドオブジェクトストレージクラスで、データアクセス速度は最大 10 倍速く、リクエストコストは S3 スタンダードよりも 50% 低減されます。」）／ディレクトリバケットの使用
第2章

データの管理と保護

日数で自動に移す・消す（ライフサイクル）、誤りから戻す（バージョニングと MFA 削除）、だれにも消させない（Object Lock）、別の場所にコピーする（レプリケーション）。

AWS SAA #13 Amazon S3タスク 3.1

S3 ライフサイクル：上から下へ移して、最後に消す

移行アクションと失効アクション：移行＝別のクラスへ移すタイミング。失効＝削除するタイミング。ルールは既存のオブジェクトにも、あとから追加されたものにも効く。
注意：128 KB 未満は既定で移行されない（1 件ごとの移行の料金が割高になるため）。最小ストレージ期間の前に移すと、その分の料金がかかる。
出典：オブジェクトのライフサイクルの管理（「S3 ライフサイクルは、オブジェクトを低コストのストレージクラスに移行するか、ユーザーに代わって期限切れのオブジェクトを削除することで、ライフサイクル全体でコスト効率の高い方法でオブジェクトを保存するのに役立ちます。」）／Amazon S3 ライフサイクルを使用したオブジェクトの移行（「Amazon S3 は、以下の図のようにストレージクラス間の移行のためのウォーターフォールモデルをサポートします。」「2024 年 9 月以降、デフォルトの動作により、128 KB 未満のオブジェクトが任意のストレージクラスに移行されることを回避します。」）

バージョニングと MFA 削除

状態：無効（既定）→ 有効 → 停止。一度有効にすると無効には戻せない（停止はできる）。各バージョンはオブジェクト全体として料金がかかるので、古いバージョンはライフサイクルで整理する。
前提になる機能：レプリケーションと Object Lock は、バージョニングが有効なバケットでしか使えない。
出典：S3 バージョニングによる複数のバージョンのオブジェクトの保持（「例えば、オブジェクトを削除した場合、Amazon S3 は、オブジェクトを完全に削除する代わりに削除マーカーを挿入します。」「一度バケットのバージョニングを有効にすると、バージョニング無効の状態に戻すことはできません。」）／MFA 削除の設定（「ただし、MFA Delete を有効化できるのは、バケット所有者 (ルートアカウント) のみです。」）

S3 Object Lock：WORM で消させない

コンプライアンスモードガバナンスモードリーガルホールド
期間保持期間を決める保持期間を決める期限なし（外すまで）
だれが消せるだれも（ルートユーザーも）s3:BypassGovernanceRetention の許可を持ち、ヘッダーを付けた人明示的に外すまでだれも消せない
モードの変更できない（期間の延長だけ）特別な許可があればできる—
使う場面規制で、決まった期間だれにも変えさせないほとんどの人から守る・本番の前の試し訴訟などで、終わりが決まっていない
前提：Object Lock はバージョニングが有効なバケットでだけ動く。ロックはオブジェクトのバージョンごとに付き、同じ名前で上書きすると新しいバージョンができ、古いバージョンはロックされたまま残る。
最も強い保護：コンプライアンスモードのオブジェクトを期限の前に消す唯一の方法は、AWS アカウントを削除すること。「ルートユーザーも含めて」とあればコンプライアンスモード。
出典：S3 Object Lock を使用したオブジェクトのロック（「オブジェクトロックは、write-once-read-many (WORM) モデルを使用してオブジェクトを保存します。」「オブジェクトロックは S3 バージョニングが有効になっているバケットでのみ機能します。」「保持期限が切れる前にコンプライアンスモードのオブジェクトを削除する唯一の方法は、関連する AWS アカウント を削除することです。」）

性能と使い方

プレフィックスで広げる、大きなファイルは分けて送る・分けて読む、遠くからは Transfer Acceleration。イベント通知・署名付き URL・バッチオペレーション・アクセスポイント。

AWS SAA #13 Amazon S3タスク 3.1

プレフィックスとリクエストレート

数字：パーティショニングされたプレフィックスごとに、毎秒 3,500 以上の書き込み系（PUT/COPY/POST/DELETE）と 5,500 以上の読み取り系（GET/HEAD）。図の件数は Claude が作った例。
ほかの手：同じオブジェクトが何度も読まれるなら、CloudFront や ElastiCache でキャッシュして S3 へのリクエスト自体を減らす。503 の数は CloudWatch のリクエストメトリクスで監視できる。
出典：設計パターンのベストプラクティス: Amazon S3 のパフォーマンスの最適化（「例えば、アプリケーションは、パーティショニングされた Amazon S3 プレフィックスごとに毎秒 3,500 回以上の PUT/COPY/POST/DELETE リクエストまたは 5,500 回以上の GET/HEAD リクエストを達成できます。」「バケット内のプレフィックスの数に制限はありません。」）／Amazon S3 のパフォーマンスの設計パターン（「スケーリングプロセス中に、HTTP 503 (Slow Down) レスポンスを受け取る場合があります。」）

マルチパートアップロードとバイト範囲のフェッチ

マルチパートアップロード：100 MB 以上で勧められている。パート番号は 1〜10,000。順番はばらばらでよく、失敗したパートだけ送り直す。サイズが分からないうちから送り始められる。
残ったパートは有料：完了も停止もしないと、パートの料金がかかり続ける。ライフサイクルの AbortIncompleteMultipartUpload で、日数がたったら消す。
出典：Amazon S3 でのマルチパートアップロードを使用したオブジェクトのアップロードとコピー（「100 MB 以上のオブジェクトは、単一のオペレーションでアップロードするのではなく、マルチパートアップロードを使用するのがベストプラクティスです。」「1～10,000 の範囲で任意のパート番号を選択できます。」）／Amazon S3 のパフォーマンスのガイドライン（「Amazon S3 への同時接続を使用して、同じオブジェクトのさまざまなバイト範囲をフェッチできます。」）

まとめて扱う・分けて渡す

機能何をする選ぶ合図
S3 バッチオペレーションマニフェスト（S3 インベントリのレポートなど）に並べたオブジェクトに、1 種類の操作を一括で。コピー・タグ・ACL・復元・暗号化の更新「数十億のオブジェクトに一括で」「既存のオブジェクトをまとめて」
S3 アクセスポイント共有のデータセットに、それぞれ別の許可とネットワークの制御を持つ入口を作る。VPC からだけに限れる「チームごとに許可を分けたい」「バケットポリシーが巨大」
静的ウェブサイトホスティングHTML・画像・クライアント側のスクリプトなど静的なコンテンツを配信「サーバーなしで静的なサイト」。HTTPS で配るなら CloudFront（Amplify ホスティング）
強い整合性PUT・DELETE のあと、すぐに読むと最新の結果が返る（すべてのリージョン）「書いた直後に読むと古い？」→ 古くならない
アクセスポイントの範囲：アクセスポイントで行えるのはオブジェクトの操作だけ。バケットの削除やレプリケーションの設定などはできない。
出典：バッチオペレーションでオブジェクトオペレーションを一括で実行する（「S3 バッチオペレーションを使用して、オブジェクトのコピー、オブジェクトのサーバー側の暗号化の更新、オブジェクトのタグやアクセスコントロールリスト (ACL) の設定を行います。」）／アクセスポイントを使用した共有データセットへのアクセスの管理（「仮想プライベートクラウド (VPC) からのリクエストのみを受け付けるようにアクセスポイントを設定することで、プライベートネットワークへの Amazon S3 データアクセスを制限できます。」）／Amazon S3 を使用して静的ウェブサイトをホスティングする／Amazon S3 とは（「Amazon S3 には、すべての AWS リージョン にある Amazon S3 バケットの、オブジェクトの PUT と DELETE に関する、書き込み後読み取りの強力な整合性があります。」）
