シングルサインオンと認証基盤

どこで認証して、何を持ち回るか。

支援士 #11 ID連携とシングルサインオン25-4

SSO の3つの古典的な方式

リバースプロキシ方式
利用者
リバースプロキシここで認証・中継
Web サーバ群改修不要
全通信が集中 → 単一障害点（R4秋・R6秋の正解）
エージェント方式
利用者
Web サーバ＋エージェント認証サーバと連携
認証サーバ成功後は cookie
エージェントは Web サーバに入れる。
代理認証方式
利用者の PC＋代行ソフトログイン画面を検知
ID・パスワードを代行入力
既存システム改修不要
クライアント側で動く。サーバの改修は不要。
R6秋 問8 の誤りの選択肢は「エージェントがクライアント PC でログイン画面を監視」（＝代理認証の説明）、「代理認証は対象サーバの改修が必要」（逆）。
出典：IPA 午前Ⅱ 令和4年度秋期 問7・令和6年度秋期 問8

Kerberos：パスワードを流さずにチケットで

① 利用者 → AS：ログインパスワードから作った鍵で応答を復号できるか
② AS → 利用者：TGTチケットをもらうためのチケット
③ 利用者 → TGS：TGT を示す「ファイルサーバを使いたい」
④ TGS → 利用者：サービスチケット
⑤ 利用者 → ファイルサーバ：サービスチケットを示す
AS と TGS をまとめて KDC（AD ではドメインコントローラ）。
時刻のずれに弱い。チケットにタイムスタンプが入り、既定で5分程度を超えると失敗。
KDC の鍵（krbtgt）が盗まれると TGT を偽造できる＝ゴールデンチケット（#02）。
SSO の問題で「チケット」が出たら Kerberos、「アサーション」なら SAML。
出典：RFC 4120 The Kerberos Network Authentication Service (V5)／Microsoft Learn「Kerberos 認証の概要」

LDAP・IDaaS・SCIM：ID を管理する仕組み

LDAP（ディレクトリへの問い合わせ）
dn: uid=tanaka,ou=sales,dc=example,dc=jp cn: 田中 一郎 mail: tanaka@example.jp memberOf: cn=eigyo,ou=groups,...
LDAPTCP 389。平文のバインドは盗聴される
LDAPSTCP 636。TLS で保護（StartTLS も）
入力をフィルタに直結 → LDAP インジェクション（#03）。認証は「バインドできるか」で。
IDaaS を中心にした連携
IDaaS（Entra ID・Okta など）認証・MFA・SSO・ログ
ログインのとき：SAML・OpenID Connect
アカウントの作成・削除：SCIMREST＋JSON（RFC 7643・7644）
退職者を IDaaS で止めれば、SCIM で各 SaaS のアカウントも消える（デプロビジョニング）。
出典：RFC 4511・RFC 4513（LDAP）／RFC 7643・RFC 7644（SCIM 2.0）／IPA「支援士試験 シラバス（案）」用語例「LDAP サーバでの認証，IDaaS」

第3章

OAuth 2.0 と OpenID Connect

OAuth は「認可」。認証は OpenID Connect。

支援士 #11 ID連携とシングルサインオン25-4

OAuth 2.0 の4つの役割（R6秋 問16）

リソースオーナー：利用者 A「D に写真の読取りだけ許す」と同意
認可サーバ：Web サービス Cアクセストークンを発行
リソースサーバ：Web サービス Cリソース B を保管、トークンを確かめる
クライアント：Web サービス Dトークンを受け取り、B にアクセス
選択肢判定
C がアクセストークンを発行正解
D がアクセストークンを発行D は受け取る側
A のデジタル証明書を送るOAuth にない
R5秋・R7春：OAuth 2.0 は認可。認可サーバが、利用者の許可を得て、クライアントに権限を付与する。「本人であるかを確認する」は認証の説明で誤り。
出典：RFC 6749 The OAuth 2.0 Authorization Framework 1.1 Roles／IPA 午前Ⅱ 令和6年度秋期 問16・令和7年度春期 問16

認可コードグラントと PKCE

① クライアントが code_verifier を作りS256 ハッシュ＝code_challenge
→
② 認可要求に code_challenge を付ける利用者が認可サーバで同意
→
③ 認可コードがリダイレクトで返るここで横取りされても…
→
④ コード＋code_verifierでトークンと交換ハッシュが一致しなければ拒否
グラントRFC 9700（2025）
認可コード＋PKCE推奨（全クライアントで PKCE）
インプリシット（URL でトークン）使うべきでない
パスワードをクライアントに渡す方式使ってはならない
クライアントクレデンシャルサーバ同士（利用者なし）
PKCE はもともと、秘密の鍵を安全にもてないスマホアプリなどのパブリッククライアントのために作られた（RFC 7636）。
出典：RFC 7636 Proof Key for Code Exchange／RFC 9700 OAuth 2.0 Security Best Current Practice 2.1.1・2.1.2・2.4

4つのトークンを見分ける

トークン規格だれがだれに見せる何を表す・注意
認可コードOAuth 2.0クライアント → 認可サーバ一回限りの引換券。PKCE で守る
アクセストークンOAuth 2.0クライアント → リソースサーバスコープと期限付きの許可。Bearer なので盗まれたら使われる → 短い期限
リフレッシュトークンOAuth 2.0クライアント → 認可サーバ新しいアクセストークンをもらう。寿命が長い → ローテーション
ID トークンOpenID ConnectOP（IdP） → RPだれが・いつ・どう認証されたか。署名付き JWT
OpenID Connect ＝ OAuth 2.0 ＋ 認証の層。アクセストークンだけでログインさせると、別アプリ用のトークンで他人になりすませる。
出典：RFC 6749 1.4・1.5／RFC 6750 Bearer Token Usage／OpenID Connect Core 1.0 2 ID Token

ID トークンと JWT の検証

JWT ＝ ヘッダ．ペイロード．署名（Base64URL）
{"alg":"RS256","kid":"k1"} . {"iss":"https://idp.example.jp", "sub":"u12345", "aud":"rp-app-01", "exp":1793500000, "iat":1793499700, "nonce":"n-0S6_WzA2Mj"} . （IdP の秘密鍵による署名）
JWS は改ざん検出、中身は誰でも読める。隠すなら JWE。
確かめる確かめないと
署名と algalg "none" の偽トークンが通る
iss別の発行者のトークンを信じる
aud他の RP 宛てを使い回される
exp期限切れが使える
nonceリプレイ・トークンの差し込み
受け入れるアルゴリズムはサーバ側で固定（RFC 8725）。
出典：RFC 7519（JWT）・RFC 7515（JWS）・RFC 7516（JWE）・RFC 8725（JWT BCP）／OpenID Connect Core 1.0 3.1.3.7。JWT の例は Claude が作った

まとめ：本番での問われ方

SSO の方式：リバースプロキシ＝集中・単一障害点、エージェント＝Web サーバに導入、代理認証＝クライアントで代行入力・改修不要。
持ち回るもの：Kerberos＝チケット、SAML＝アサーション、OAuth＝アクセストークン、OIDC＝ID トークン。
SAML の目印：OASIS・異なるドメイン・XML・認証/属性/認可。認証は IdP、検証は SP。
OAuth 2.0 は認可：利用者の許可のもと、認可サーバがクライアントにアクセストークンを発行。本人確認は OpenID Connect。
守り方：PKCE（コードの横取り）、短いアクセストークン、リフレッシュトークンのローテーション、aud・alg の検証。
IDaaS＋SCIM で、アカウントの削除まで一元化。
出典：IPA 午前Ⅱ（このPDFの問題演習）／IPA「支援士試験 シラバス（案）Ver.0.1」
