第1章

ECS と ECR の部品

設計図（タスク定義）から製品（タスク）を作り、係（サービス）が数を保つ。イメージは ECR に置く。

AWS SAA #08 コンテナタスク 2.1

ECS の部品のつながり

サービス＝数を保つ係：決めた数のタスクを動かし続け、失敗・停止したら置き換える。ロードバランサーの後ろに置ける。Web・API など長く動くものはサービス。
REPLICA と DAEMON：レプリカ（デフォルト）は全体で数を保つ。デーモンはコンテナインスタンス（EC2）ごとに 1 つずつ（ログやモニタリングのエージェント）。
出典：Amazon ECSの タスク定義（「タスク定義はアプリケーションのブループリントです。」）／Amazon ECS サービス（「タスクの 1 つが失敗または停止した場合、Amazon ECS サービススケジューラはタスク定義の別のインスタンスを起動してそれを置き換えます。」）／Amazon ECS クラスター（「クラスターは AWS リージョン 固有です。」）

ECR：イメージの倉庫を守り、片付け、配る

機能何をする本番の言い回し
プライベートリポジトリIAM のリソースベースの権限で守る。Docker・OCI のイメージを置く「社外に公開せずイメージを保存」
基本スキャンAWS ネイティブの技術と CVE のデータベースで、OS の脆弱性を調べる「プッシュ時に OS の脆弱性を」
拡張スキャンAmazon Inspector と連携し、自動で継続的に。OS とプログラミング言語のパッケージ「言語のライブラリも継続的に」
ライフサイクルポリシールールに合う古いイメージをアーカイブ・期限切れにする「古いイメージのストレージ料金」
レプリケーション別のリージョン・別のアカウントへ自動でコピー「災害対策で別リージョンにも」
だれがプルする：ECS のタスクを起動するときは、ECS（Fargate）のエージェントがタスク実行ロールで ECR からプルする（第2章）。
ひっかけ：イメージの脆弱性は GuardDuty ではなく ECR のスキャン（拡張なら Inspector）。S3 や EFS はレジストリの代わりにならない。
出典：Amazon Elastic Container Registry とは（「Amazon ECR は、IAM AWS を使用したリソースベースのアクセス許可を持つプライベートリポジトリをサポートします。」）／Amazon ECR でイメージをスキャンしてソフトウェア脆弱性がないか調べる（「拡張スキャン – Amazon ECR は Amazon Inspector と統合され、リポジトリの自動継続的なスキャンを提供します。」）／Amazon ECR でのプライベートイメージレプリケーション（「Amazon ECR は、クロスリージョンレプリケーションおよびクロスアカウントレプリケーションの両方をサポートしています。」）
第2章

キャパシティ・権限・ネットワーク

どこで動かすか、だれの権限で何を呼ぶか、タスクにどんな IP とディスクを持たせるか。

AWS SAA #08 コンテナタスク 2.1

どこで動かす：起動タイプとキャパシティプロバイダー

動かす場所サーバーの管理向く場面
Fargate不要まず考える
Fargate Spot不要・中断あり（2 分前に警告）止まってよい処理を安く
EC2（ASG）自分で細かい制御・リザーブドで安く
マネージドインスタンスAWS がパッチ・スケールGPU・特定のインスタンス
External自分で（オンプレ）ECS Anywhere
起動タイプは EC2・Fargate・External の 3 つ。今はキャパシティプロバイダーで指定するのが勧められている。
キャパシティプロバイダー戦略で混ぜる（例）
ひっかけ：「Fargate Spot という起動タイプ」はない。Fargate Spot はキャパシティプロバイダー（FARGATE_SPOT）で使う。
出典：Amazon ECS の起動タイプとキャパシティプロバイダー（「起動タイプには、EC2、Fargate、External があります。」「Amazon ECS でサポートされているキャパシティプロバイダーは、Fargate および FARGATE_SPOT、セルフマネージド EC2 インスタンス用の Auto Scaling グループ、Amazon ECS マネージドインスタンスです。」）／Amazon ECS マネージドインスタンスの設計／外部インスタンスの Amazon ECS クラスター

EC2 のどこに置く：タスク配置戦略

戦略置き方使いどころ
binpack未使用の CPU・メモリが最小になるよう詰めるインスタンス数を減らしてコスト削減
spread指定した値（AZ・インスタンス）に均等に。サービスのデフォルトは AZ に spread可用性を上げる
randomランダム特にこだわらない
出典：戦略を使用して Amazon ECS タスク配置を定義する（「binpack タスクはコンテナインスタンスに配置され、未使用の CPU またはメモリを最小にします。」「spreadタスクは指定された値に基づいて均等に配置されます。」）

2つのロール：タスクロールとタスク実行ロール

症状で見分ける：「イメージがプルできない」「ログが出ない」「シークレットが取れない」→ 実行ロール。「アプリが S3 で AccessDenied」→ タスクロール。
やってはいけない：EC2 のインスタンスロールにアプリの権限を付ける（全タスクが同じ権限に）・アクセスキーを環境変数に書く。DB のパスワードは Secrets Manager に置き、タスク定義の secrets で渡す。
出典：Amazon ECS タスクの IAM ロール（「タスクロールは、アプリケーションが Amazon S3 などの他の AWS サービスにアクセスするときに必要です。」）／Amazon ECS タスク実行IAM ロール（「タスク実行ロールは、ユーザーに代わって AWS API コールを実行するためのアクセス許可を Amazon ECS コンテナと Fargate エージェントに付与します。」）／Amazon ECS コンテナに機密データを渡す

ネットワークとストレージ

モードしくみ
awsvpcタスクごとに専用の ENI とプライベート IP。タスクごとにセキュリティグループ。Fargate はこれ。ターゲットタイプは ip
bridgeEC2 の中の Docker の仮想ネットワーク。動的ホストポートマッピングで ALB に登録
hostホストの ENI のポートをそのまま使う。同じポートのタスクは 1 台に 1 つ
AWS のおすすめ：特別な理由がなければ awsvpc。ECS Anywhere の外部インスタンスでは awsvpc は使えない。
ストレージ特徴
Fargate のエフェメラル最低 20 GiB、最大 200 GiB。タスクが終われば消える・共有しない
EFS ボリューム永続・複数のタスクで共有。Fargate でも使える
EBS ボリューム高性能なブロック。データの多い処理に
共有して残すなら EFS：アップロードされたファイルをどのタスクでも読むなら EFS。一時ファイルならエフェメラルを増やす。
出典：EC2 の Amazon ECS タスクネットワークオプション（「Amazon ECS では、別のネットワークモードを使用する特別の必要性がある場合を除き、awsvpc ネットワークモードの使用を推奨します。」）／Amazon ECS 向けの Fargate タスクエフェメラルストレージ（「エフェメラルストレージの総量は、最大 200 GiB まで増やすことができます。」）／Amazon ECS での Amazon EFS ボリュームの使用（「これにより、タスクは、配置されているインスタンスにかかわらず、同じ永続的ストレージにアクセスできます。」）
第3章

スケーリングとデプロイ

タスクを増やし、ALB でつなぎ、止めずに入れ替える。バッチはスケジュールで起動。

AWS SAA #08 コンテナタスク 2.1

タスクを増やす・インスタンスを増やす

スケーリングの種類決め方例
ターゲット追跡メトリクスと目標値を決めるだけ（CPU・メモリ・ALB のリクエスト数）CPU の平均を 60% に保つ
ステップしきい値ごとに増減する数を決める80% 超で +2、90% 超で +4
スケジュール日時で数を変える毎朝 8 時に 10 にする
予測過去の日次・週次のパターンから前もって増やす毎週月曜の朝の山
出典：ターゲットメトリクスを使用して Amazon ECS サービスをスケールする（「ターゲット追跡スケーリングポリシーで、メトリクスを選択してターゲット値を設定します。」）／EC2 ワークロード用の Amazon ECS キャパシティプロバイダー（「マネージドスケーリング機能を使用して、Auto Scaling グループのスケールインおよびスケールアウトアクションを Amazon ECS に管理させることも、自分自身でスケーリングアクションを管理することもできます。」）

ALB でつなぐ：パスで分ける・ポートを動的に

ロードバランサーの選び方：HTTP/HTTPS で URL やホストで分けるなら ALB。TCP・UDP（レイヤー 4）なら NLB。Fargate では ALB・NLB・GWLB が使える。
ターゲットタイプ：awsvpc（Fargate）のタスクは ENI に結び付くので、ターゲットグループのターゲットタイプは instance ではなく ip。
出典：Amazon ECS 用の Application Load Balancer を使用する（「Application Load Balancer では、アプリケーションレイヤー (HTTP/HTTPS) でルーティング決定を行い、パスベースのルーティングをサポートします。」「Application Load Balancer では、動的ホストポートマッピングをサポートしています。」）／Amazon ECS の AWS Fargate 用のアーキテクト（「また、このようなサービスのターゲットグループを作成する場合は、ターゲットタイプとして instance ではなく、ip を選択する必要があります。」）

止めずに入れ替える：ローリングとブルー/グリーン

ローリング更新（desiredCount 4・最小 100%・最大 200%）
minimumHealthyPercent＝正常でなければならない数の下限、maximumPercent＝動かしてよい数の上限（どちらも desiredCount に対する ％）。
ローリングブルー/グリーン
入れ替え方少しずつ置き換え新旧を両方用意して切り替え
事前の検証しにくいテストのトラフィックで確かめる
戻し方もう一度デプロイベイク時間中は旧版が残り、すぐ戻せる
バッチは EventBridge スケジューラ：毎日 2 時に 1 回、などはサービスにせず、スケジュールで Fargate のタスクを起動する。15 分を超えるので Lambda では無理な処理の定番。
出典：タスクを置き換えて Amazon ECS サービスをデプロイする（「maximumPercent 設定で許可されている場合、スケジューラは異常な状態のタスクを停止する前に代替タスクを起動します。」）／Amazon ECS ブルー/グリーンデプロイ（「Amazon ECS ブルー/グリーンデプロイを使用すると、本番トラフィックをルーティングする前に、新しいサービスリビジョンを検証できます。」）／Amazon EventBridge スケジューラを使用して Amazon ECS タスクをスケジュールする

Amazon EKS

Kubernetes をそのまま使いたいなら EKS。コントロールプレーンは AWS、ノードの面倒をどこまで任せるかを選ぶ。

AWS SAA #08 コンテナタスク 2.1

EKS：ノードの面倒をどこまで任せるか

オンプレミスでしくみ
EKS Hybrid Nodes自社のサーバーを、リージョンの EKS クラスターのノードにする（リージョンへの安定した接続が要る）
EKS on Outpostsデータセンターに置いた AWS 管理のハードウェア（Outposts）の上で EKS
EKS Anywhereインターネットから切り離した自己完結の環境で、Kubernetes クラスターを自分で動かす
出典：マネージドノードグループを使用してノードライフサイクルを簡素化する（「Amazon EKS マネージド型ノードグループは、Amazon EKS Kubernetes クラスターのノード (Amazon EC2 インスタンス) のプロビジョニングとライフサイクル管理を自動化します。」）／AWS Fargate を使用してコンピューティング管理を簡素化する（「デーモンセットは Fargate ではサポートされていません。」）／クラウド環境とオンプレミス環境に Amazon EKS クラスターをデプロイする（「Amazon EKS on AWS Outposts と Amazon EKS Hybrid Nodes には、オンプレミス環境から AWS リージョンへの信頼性の高い接続が必要です。」）

EKS のスケーリングと権限

2 段階のスケーリング
権限の渡し方しくみ
EKS Pod IdentityPod（サービスアカウント）ごとに IAM ロールの認証情報を渡す
IRSAIAM ロールを Kubernetes のサービスアカウントに関連付ける
ノードのロール全 Pod が同じ権限になる（最小権限にならない）
ECS との対応：ECS のタスクロール ≒ EKS の Pod Identity・IRSA。ECS のサービスの自動スケーリング ≒ HPA。ECS のキャパシティのスケール ≒ Karpenter。
出典：Horizontal Pod Autoscaler を使用してポッドデプロイをスケールする（「ターゲットの CPU 使用率を設定すると、Horizontal Pod Autoscaler はターゲットを満たすようにアプリケーションをスケールインまたはスケールアウトします。」）／Karpenter と Cluster Autoscaler を使用したクラスターコンピューティングのスケーリング（「EKS Auto Mode は Karpenter に基づいて構築されます。」）／EKS Pod Identity が Pod に AWS サービスへのアクセス権を付与する仕組みを学ぶ（「AWS 認証情報を作成してコンテナに配布したり、Amazon EC2 インスタンスのロールを使用したりする必要はありません。」）
