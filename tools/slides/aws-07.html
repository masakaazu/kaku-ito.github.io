第1章

Lambda のしくみと設定

関数は実行環境の中で動く。メモリ・時間・ディスク・依存関係・つなぎ方を決める。

AWS SAA #07 サーバーレスタスク 2.1

実行環境のライフサイクルとコールドスタート

コールドスタートは少ない：AWS によると呼び出しの 1% 未満。それでも困るなら、プロビジョニングされた同時実行か SnapStart（第2章）。
使い回しは保証されない：次の呼び出しが同じ環境に来るとは限らない。ログインの状態などは関数の中に持たない（ステートレス）。
出典：Lambda 実行環境のライフサイクルの概要（「Init フェーズは 10 秒に制限されています。」「通常、コールドスタートは呼び出しの 1% 未満で発生します。」）／AWS Lambda 関数を使用するためのベストプラクティス（「関数ハンドラー外で SDK クライアントとデータベース接続を初期化し、静的なアセットを /tmp ディレクトリにローカルにキャッシュします。」）

Lambda の数字：これだけは覚える

項目値
メモリ128 MB〜10,240 MB（1 MB 単位）
タイムアウトデフォルト 3 秒・最大 900 秒（15 分）
/tmp512 MB〜10,240 MB（一時・共有しない）
ペイロード同期 6 MB／非同期 1 MB
.zip圧縮 50 MB・解凍後 250 MB（レイヤー込み）
コンテナイメージ10 GB（非圧縮）
レイヤー1 関数に 5 つまで

CPU はメモリについてくる
CPU は直接決められない：CPU が足りない（遅い）ならメモリを増やす。vCPU 数の設定はない。
15 分を超える処理：Lambda は無理。Fargate・EC2・AWS Batch に移すか、小さく分けて Step Functions でつなぐ。
出典：Lambda クォータ／Lambda 関数のメモリを設定（「Lambda は、設定されたメモリの量に比例して CPU パワーを割り当てます。」）／Lambda 関数のタイムアウトを設定する（「この設定のデフォルト値は 3 秒ですが、最大値の 900 秒 (15 分) まで 1 秒単位で調整できます。」）

レイヤー・コンテナイメージ・バージョンとエイリアス

しくみ何のため
レイヤー共通ライブラリを .zip にまとめ、多くの関数で使い回す。コードと別に更新できる
コンテナイメージ250 MB に入らない大きな依存関係（ECR に置く、最大 10 GB）。動きは Lambda のまま（15 分）
バージョン発行した時点で固める（変更不可）。編集中は $LATEST
エイリアスバージョンを指す名前。付け替え・2 つのバージョンへの振り分け
関数 URL関数専用の HTTPS の入口。認証は IAM かなし。API キーやキャッシュは API Gateway
エイリアスで新しいバージョンを少しだけ試す
出典：レイヤーによる Lambda 依存関係の管理（「Lambda レイヤーは、補助的なコードやデータを含む .zip ファイルアーカイブです。」）／Lambda 関数のバージョンを管理する（「関数のバージョンを公開すると、そのコード、ランタイム、アーキテクチャ、メモリ、レイヤー、その他のほとんどの設定はイミュータブルになります。」）／Lambda 関数のエイリアスの作成（「Lambda のエイリアスとは、更新可能な関数のバージョンへのポインタです。」）

VPC の中のリソースを使う Lambda

ひっかけ：関数をパブリックサブネットに接続しても、パブリック IP は付かず、インターネットにも出られない。Lambda に Elastic IP は付けられない。
正しい形：関数はプライベートサブネット（2 つ以上の AZ）。インターネットへは NAT ゲートウェイ経由。AWS のサービスだけなら VPC エンドポイントでもよい。
出典：Lambda 関数に Amazon VPC 内のリソースへのアクセスを許可する（「関数をパブリックサブネットに接続しても、インターネットアクセスやパブリック IP アドレスは提供されません。」）／VPC に接続された Lambda 関数にインターネットアクセスを有効にする（「プライベートサブネットは、NAT ゲートウェイ経由でインターネットにアクセスできます。」）
第2章

呼び出しとスケーリング

待つのか、任せるのか、取りに行くのか。失敗したときの動きと、同時に動く数の決め方。

AWS SAA #07 サーバーレスタスク 2.1

3つの呼び出し方

見分け方：呼び出し元が結果を必要とする（API の応答）→ 同期。「置かれたら」「通知が来たら」→ 非同期。キューやストリーム → イベントソースマッピング。
SQS は押してこない：Lambda のポーラーがキューをポーリングする。関数の中で ReceiveMessage を回し続ける必要はない。
出典：Lambda 関数を同期的に呼び出す（「関数を同期的に呼び出すと、Lambda は関数を実行し、レスポンスを待ちます。」）／Lambda 関数を非同期的に呼び出す（「非同期呼び出しの場合、Lambda はリクエストをキューに入れ、追加情報のない成功のレスポンスを返します。」）／Lambda がストリームおよびキューベースのイベントソースからのレコードを処理する方法（「イベントソースマッピング内では、イベントポーラーと呼ばれるリソースが新しいメッセージをアクティブにポーリングし、関数を呼び出します。」）

非同期呼び出しが失敗したら

送信先（Destinations）デッドレターキュー（DLQ）
送るとき成功時・失敗時を別々に設定できる失敗して捨てられるときだけ
中身呼び出しの詳細（レスポンス・エラー）を含む JSON の記録イベントの中身だけ
送り先標準 SQS・標準 SNS・Lambda・EventBridge・S3（失敗時のみ）標準 SQS・標準 SNS
出典：Lambda がエラーを処理し、非同期呼び出しで再試行する方法（「その際、最初の 2 回の試行の間に 1 分間、2 回目と 3 回目の間に 2 分間の待機時間があります。」）／Lambda 非同期呼び出しのレコードのキャプチャ（「デッドレターキューの場合、Lambda はイベントのコンテンツのみを送信し、レスポンスの詳細は送信しません。」）

同時実行：取り合い・確保・温めておく

リージョンの同時実行 1,000 を全関数で分け合う（例）
上限にもなる：予約済み同時実行は下限であり上限。古い DB に同時に 50 本までしかつなげないなら 50 に絞る。
何をする料金
予約済み同時実行枠を確保し、上限にもする追加なし
プロビジョニングされた同時実行初期化済みの環境を前もって用意（数十ミリ秒で応答）。バージョン・エイリアスに設定追加あり
SnapStart初期化済みのスナップショットから再開。用意は不要（Java・Python・.NET）Java は追加なし。ほかはスナップショットの料金
1 つの関数は 10 秒ごとに最大 1,000 の実行環境ずつ増やせる。1,000 は引き上げを申請できる。
出典：Lambda 関数のスケーリングについて（「デフォルトで、アカウントの同時実行はリージョン内のすべての関数全体で 1,000 に制限されています。」）／関数に対する予約済み同時実行数の設定（「予約済同時実行数は、下限と上限の両方の役割を果たします。」）／Lambda SnapStart による起動パフォーマンスの向上（「アプリケーションに SnapStart で適切に対処できない厳格なコールドスタートレイテンシー要件がある場合は、プロビジョニングされた同時実行を使用します。」）
