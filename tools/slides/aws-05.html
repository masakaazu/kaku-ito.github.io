第1章

だれが何をしたか（CloudTrail）

操作はすべてイベントになる。90 日はタダで見られる。長く残す・まとめる・改ざんを確かめる方法を押さえる。

CloudTrail の3つの記録のしかた

イベント履歴証跡CloudTrail Lake
中身そのリージョンの管理イベント選んだイベント（管理・データ・Insights）選んだイベントをイベントデータストアに
期間過去 90 日S3 に置くかぎり料金オプションで最長約 10 年など
料金なし管理イベントの1コピーは無料（S3 の保存料は別）取り込み・保存・クエリに料金
使いどころ最近の操作をすぐ調べる長期保存・通知・ほかのツールで分析SQL で長期の監査・分析
出典：とは AWS CloudTrail（「イベント履歴 の閲覧には CloudTrail の料金はかかりません。」「証跡を作成すると、進行中の管理イベントのコピーを 1 つ無料で CloudTrail から S3 バケットに配信できますが、Amazon S3 ストレージには料金がかかります。」）

管理イベント・データイベント・Insights イベント

管理イベントデータイベントInsights イベント
何の記録リソースに対する管理の操作（コントロールプレーン）リソースの上や中での操作API の呼び出しの率・エラーの率の異常
例AttachRolePolicy・CreateSubnet・CreateTrail・EC2 の起動S3 の GetObject・PutObject・DeleteObject、Lambda の実行ふだんより急に RunInstances が増えた
デフォルトで記録されるされない（量が多い）されない
本番のひっかけ：「S3 のオブジェクトをだれが読んだか」は、証跡を作っただけでは残らない。データイベントを有効にする。
アラームにつなぐ：証跡を CloudWatch Logs や EventBridge に送ると、「IAM のポリシーが変わったら SNS で通知」のような仕組みが作れる。
出典：CloudTrail のコンセプト（「デフォルトでは、証跡とイベントデータストアは管理イベントをログ記録しますが、データイベントまたは Insights イベントは記録しません。」「データイベントは、多くの場合、高ボリュームのアクティビティです。」）／CloudTrail Insights の使用

もれなく・改ざんなく残す

組織の証跡 × マルチリージョン
組織の証跡は管理アカウント（または委任された管理者）が作る。メンバーアカウントのユーザーは、消す・止める・変えるができない。図は Claude が作った模式図。
守りたいこと使うもの
全アカウントの記録を1か所に組織の証跡
使っていないリージョンの操作も残すマルチリージョン証跡
届いたあとに書き換えられていない証明ログファイルの整合性の検証
90 日より長く、SQL で分析CloudTrail Lake
整合性の検証のしくみ：SHA-256 のハッシュと、RSA のデジタル署名。気づかれずに変更・削除・偽造することが計算上できなくなる。セキュリティやフォレンシックの調査で重要。
出典：組織の証跡の作成（「組織の証跡では、組織内の管理アカウントとすべてのメンバーアカウントのイベントが記録されます。」）／CloudTrail ログファイルの整合性の検証（「検証されたログファイルは、セキュリティおよびフォレンシック調査で非常に重要です。」）
第2章

設定とネットワークの記録

Config は「リソースの今と昔の姿」。フローログは「流れた通信」。CloudWatch Logs は「アプリが書いたログ」。

AWS SAA #05 ログ・監査と脅威の検出タスク 1.3

同じ出来事を CloudTrail と Config で見る

Config の動き：リソースの作成・変更・削除を続けて記録し、設定のスナップショットと履歴を S3 に届ける。変化を SNS で知らせることもできる。
どちらでも止めない：CloudTrail も Config も「記録・評価」のサービス。危ない操作を事前に止めるのは SCP や IAM のポリシー（#01・#02）。
出典：AWS Config とは?（「AWS Config は、AWS アカウントにある AWS リソースに関する設定の詳細ビューを提供します。」「また、AWS Config はリソースの作成、変更、または削除を継続的に評価します。」）

Config ルール → 修復 → まとめて配る・まとめて見る

しくみ何をする本番の言い回し
Config ルールあるべき設定を決めて評価。AWS のマネージドルールと、自分で書くカスタムルール「基準に合わないリソースを続けて見つける」
修復非準拠のリソースを Systems Manager の自動化ドキュメントで直す「見つけたら自動で直す」
コンフォーマンスパックルールと修復の一式を、アカウント・リージョン・組織にまとめて配る（YAML）「PCI DSS 向けのルール一式を全社に」
アグリゲータ複数アカウント・複数リージョンの設定と準拠のデータを1か所に集める「全社の準拠状況を1画面で」
出典：AWS Config による非準拠リソースの是正（「AWS Config では、AWS Config ルール で評価されている非準拠のリソースを修復できます。」）／コンフォーマンスパック／マルチアカウントマルチリージョンのデータ集約

VPC フローログと CloudWatch Logs

VPC フローログ
項目中身
記録するものネットワークインターフェイスに出入りする IP の通信の情報（送信元・送信先・ポート・許可か拒否か など）
記録しないものパケットの中身
送り先CloudWatch Logs・S3・Data Firehose
性能への影響なし（通信の経路の外で集める）
使いどころ厳しすぎる SG のルールの診断、インスタンスに届く通信の監視
CloudWatch Logs
項目中身
集めるものEC2・CloudTrail・Route 53 など、システム・アプリ・AWS のサービスのログ
できることクエリで検索、フィルターでログからメトリクスを作る、機密データのマスキング
ログクラス標準と、取り込みが安い低頻度アクセス
アラームの作り方：ログ →（フィルター）→ メトリクス → CloudWatch アラーム → SNS。「ERROR が 1 分に 10 回で通知」など。
出典：VPC フローログを使用した IP トラフィックのログ記録（「フローログデータはネットワークトラフィックのパスの外で収集されるため、ネットワークのスループットやレイテンシーには影響しません。」）／Amazon CloudWatch Logs とは（「CloudWatch Logs を使用すると、使用するすべてのシステム、アプリケーション、 AWS サービスからのログを 1 つの非常にスケーラブルなサービスに一元化できます。」）

GuardDuty：有効にするだけで見張る

基本データソース見えること（例）
CloudTrail 管理イベントふだんと違う場所からの API の呼び出し、ログの停止
VPC フローログ悪いと知られた IP との通信
Route 53 Resolver の DNS クエリログ悪いドメインの名前解決（マイニングなど）
見えることの例は Claude がまとめたもの。GuardDuty は独立した複製のストリームでログを読むので、証跡やフローログを自分で有効にしなくてよく、既存の設定にも影響しない。初めてのリージョンは 30 日間の無料トライアル。
見つけて知らせる：GuardDuty は検出結果を出す。止める・隔離するのは EventBridge から呼ぶ Lambda などで自分で組む。
自動対応の例
出典：GuardDuty 基本データソース（「GuardDuty は CloudTrail イベントを管理したり、既存の CloudTrail 設定に影響を与えたりすることはありません。」）／EventBridge を使用した GuardDuty 検出結果の処理（「検出結果をイベントとして自動的に公開 (送信) します。」）
