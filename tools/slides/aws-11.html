Route 53

名前を IP に変える DNS を、AWS ではどう作るか。ホストゾーンとレコード、8 つのルーティングポリシー、ヘルスチェックでのフェイルオーバー、オンプレミスとの名前解決

各ページの下に、根拠にした AWS の公式ドキュメント（Amazon Route 53 デベロッパーガイド・Amazon VPC ユーザーガイド）を書いた（青い文字を押すと開く）。「」の中はドキュメントの原文どおり（日本語版は機械翻訳のため、語順が不自然なところもそのまま）。ドメイン名・IP アドレス・構成は Claude が作った例

キャッシュ：リゾルバーは答えを TTL のあいだキャッシュする。ネームサーバーの情報はふつう 2 日間キャッシュされる。だから DNS の切り替えは「すぐには全員に効かない」。

第1章

DNS とホストゾーン

名前の入れ物（ホストゾーン）と中身（レコード）。インターネット向けと VPC の中向け、エイリアスと CNAME、TTL と DNSSEC。

AWS SAA #11 Route 53タスク 2.2・3.4

パブリックホストゾーンとプライベートホストゾーン

スプリットビュー DNS：同じ名前（example.com）でパブリックとプライベートの両方を作ると、VPC の中からはプライベートの答え、外からはパブリックの答えが返る。社内用と公開用を同じドメインで分けられる。
引けないとき：プライベートホストゾーンの名前が VPC の中で引けないなら、VPC の DNS 属性（enableDnsHostnames・enableDnsSupport）を確かめる。インターネットゲートウェイは関係ない。
出典：ホストゾーンの使用（「ホストゾーンは、レコードのコンテナです。」）／プライベートホストゾーンの使用（「スプリットビュー DNS では、内部使用 (accounting.example.com) とパブリックウェブサイト (www.example.com) などの外部使用で同じドメイン名 (example.com) を使用します。」）／VPC の DNS 属性

CNAME名前 → 別のドメイン名サブドメインだけ。ゾーンの頂点には作れない。クエリは有料

TTL：リゾルバーがキャッシュする秒数。長いとクエリが減って料金が下がるが、変更の反映が遅れる。短いと変更やフェイルオーバーが早く効く。ヘルスチェックと組み合わせるレコードは 60 秒以下が勧められている。
出典：サポートされる DNS レコードタイプ（「CAA レコードを作成すると、間違った CA がドメインの証明書を発行することを防止できます。」）／Amazon Route 53 の概念（「Route 53 の料金は Route 53 が応答する DNS クエリの数に一部基づいているため、TTL を長くすると料金を減らすことができます。」「このレコードをヘルスチェックに関連付ける場合は、クライアントがヘルスステータスの変化に迅速に応答するように、TTL を 60 秒以下に指定することをお勧めします。」）

第2章

ルーティングポリシー

同じ名前に、どの答えを返すか。割合・速さ・障害・場所・距離・正常な複数の値・利用者の IP の 8 つの決め方。

AWS SAA #11 Route 53タスク 2.2・3.4

8 つのルーティングポリシー

ポリシー何で答えを選ぶ本番の言い回し
シンプル1 つのリソース（1 つのレコードに複数の値も書ける）「1 台の Web サーバー」
加重重みの割合（重み ÷ 合計）「5% だけ新バージョン」「少しずつ移行」
レイテンシー利用者から最もレイテンシーが低いリージョン「世界中の利用者に最も速く」
フェイルオーバープライマリが正常ならプライマリ、異常ならセカンダリ「アクティブ/パッシブ」「障害時だけ予備へ」
位置情報利用者のいる場所（大陸・国・米国の州）「国ごとに言語」「配信の権利がある国だけ」
地理的近接性利用者とリソースの距離＋バイアス「あるリージョンに送る範囲を広げる」
複数値回答正常なレコードからランダムに最大 8 つ「DNS で複数の IP、故障したものは返さない」
IP ベース利用者の IP の CIDR と送り先の対応（自分で登録）「特定の ISP の利用者を特定のエンドポイントへ」
まぎらわしい組：「速さ」＝レイテンシー（ネットワークの測定）。「場所の区切り」＝位置情報（国・大陸）。「距離と範囲の調整」＝地理的近接性（バイアス）。「利用者の IP」＝IP ベース。
出典：ルーティングポリシーの選択（「フェイルオーバールーティングポリシー – アクティブ/パッシブフェイルオーバーを構成する場合に使用します。」「複数値回答ルーティングポリシー – ランダムに選ばれた最大 8 つの正常なレコードを使用して Route 53 が DNS クエリに応答する場合に使用します。」）

加重・レイテンシー・フェイルオーバー

レイテンシーは測定で決まる：利用者と AWS のデータセンターのあいだのレイテンシーのデータで選ぶ。地図の上で近いリージョンが選ばれるとは限らない。
加重 vs フェイルオーバー：加重は常に割合で両方に送る。重み 100：0 にしても、異常時の自動の切り替えのための仕組みではない。アクティブ/パッシブはフェイルオーバー。
出典：加重ルーティング（「リソースへのトラフィックの送信を停止する場合は、そのレコードの重みを 0 に変更します。」）／レイテンシーに基づくルーティング／フェイルオーバールーティング（「フェイルオーバールーティングを使用すると、トラフィックが正常であればリソースに、最初のリソースが異常であれば別のリソースにルーティングできます。」）

位置情報・地理的近接性・IP ベース

位置情報の使い道：利用者の言語で見せる・配信の権利がある場所だけに制限する。重なるときは小さい地域（例：北米よりカナダ）が優先。
違いの決め手：「国の境目どおり」なら位置情報。「範囲を少しずつ広げたい」なら地理的近接性。「特定の ISP・特定の CIDR」なら IP ベース。
出典：位置情報ルーティング（「デフォルトレコードを作成しない場合、Route 53 はそのような場所からのクエリに対して "応答なし" という応答を返します。」）／地理的近接性ルーティング（「バイアスは、トラフィックがリソースに移動する地理的リージョンを拡大または縮小します。」）／IP ベースルーティング

複数値回答とシンプルの違い

シンプル（1 つのレコードに 4 つの IP）
複数値回答（値ごとのレコード＋ヘルスチェック）
ロードバランサーとの違い：DNS は IP を返すだけで、リクエストを中継しない。リゾルバーが答えをキャッシュしたあとにサーバーが使えなくなったら、クライアントのソフトが答えの中の別の IP を試せる。複数値回答は「ロードバランサーの代わりではない」。
本番の言い回し：「ロードバランサーを使わず、DNS で複数の正常な IP を返したい」→ 複数値回答。「ヘルスチェック付きで負荷を分けたい（リクエストごと）」→ ALB・NLB（#09）。
出典：複数値回答ルーティング（「これはロードバランサーに代わるものではありませんが、複数のヘルスチェックされた IP アドレスを返すことは、DNS を使用して稼働時間とロード共有を向上させる方法です。」「すべてのレコードが異常である場合、Route 53 は DNS クエリに最大 8 つの異常なレコードを返します。」）／シンプルルーティング
第3章

ヘルスチェックとハイブリッド DNS

何をどこから確かめるか。VPC の中は届かない。オンプレミスと名前を引き合う向き、出ていく名前解決の絞り方。

AWS SAA #11 Route 53タスク 2.2

ヘルスチェックの種類

種類何を見るこんなとき
エンドポイント世界各地のヘルスチェッカーから、IP かドメイン名にインターネット経由でリクエスト。間隔は 30 秒か 10 秒。18% を超えるチェッカーが正常なら正常公開している Web サーバー・ALB
算出したほかの複数のヘルスチェックの結果をまとめる「5 台中 3 台以上が正常なら正常」
CloudWatch アラームアラームと同じデータストリームで判断（ALARM になるのを待たない）VPC の中のプライベートなリソース・DynamoDB のスロットリングなど任意のメトリクス
Evaluate Target Healthエイリアスレコードの向け先（ALB など）の正常性を評価（ヘルスチェックを別に作らなくてよい）ALB へのエイリアスを組み合わせたフェイルオーバー・レイテンシー
VPC の中は届かない：Route 53 のヘルスチェッカーは VPC の外にある。プライベート IP だけのリソースは、CloudWatch のメトリクスにアラームを付け、そのアラームを見るヘルスチェックにする。
18% の理由：1 つの地域のネットワークの問題だけで異常と判断しないよう、複数のリージョンのチェッカーが正常と見ていることを確かめるための値。
出典：Amazon Route 53 ヘルスチェックの種類／Amazon Route 53 でヘルスチェックの正常性を判断する方法（「18% を超えるヘルスチェッカーがエンドポイントを正常であるとレポートした場合、Route 53 はそのエンドポイントを正常と見なします。」）／プライベートホストゾーンのフェイルオーバーの設定（「Route 53 ヘルスチェッカーは VPC の外にあります。」）

レコードのツリー：レイテンシー × フェイルオーバー

構成は Claude が作った例。どちらかのリージョンが異常ならレイテンシーの中で外れ、両方が異常ならフェイルオーバーでセカンダリへ。
ターゲットの正常性の評価：エイリアスレコードで Yes にすると、向け先の正常性を Route 53 が確かめる。ヘルスチェックを関連付ける代わりに、または一緒に使える。
TTL も合わせて：切り替えを早く効かせたいなら、TTL を 60 秒以下に。エイリアスで AWS リソースに向けるときはリソースの既定の TTL になる。
出典：Amazon Route 53 の複雑な構成でのヘルスチェックの動作（「[Evaluate Target Health] の値を [Yes] に設定する代わりに (または設定したうえで)、エイリアスレコードにヘルスチェックを関連付けることができます。」）

オンプレミスと名前を引き合う：Resolver エンドポイント

向きで覚える：インバウンド＝オンプレミス（や別の VPC）から VPC へ入るクエリの入口。アウトバウンド＝VPC からオンプレミスへ出るクエリの出口で、どのドメインをどこに送るかのルールを作る。
ひっかけ：プライベートホストゾーンに関連付けられるのは VPC で、オンプレミスの DNS サーバーは関連付けられない。オンプレミスから引くならインバウンドエンドポイント経由。
出典：Route 53 VPC Resolver とは（「インバウンド Resolver エンドポイントを使用すると、VPC に、オンプレミスネットワークまたは別の VPC から DNS クエリが可能になります。」「アウトバウンド Resolver エンドポイントを使用すると、VPC から、オンプレミスネットワークまたは別の VPC に DNS クエリが可能になります。」）／ネットワークへのアウトバウンド DNS クエリの転送

DNS ファイアウォール

何を防ぐ：主な用途は「DNS 漏洩」。侵入した攻撃者が、DNS のルックアップを使って VPC のデータを自分のドメインに送るのを、名前の解決の段階で止める。
似た名前の区別：DNS ファイアウォール＝出ていく名前の解決。Network Firewall＝通信そのもの。AWS WAF＝HTTP のリクエスト。DNSSEC＝自分のゾーンの応答への署名。
出典：DNS ファイアウォールを使用してアウトバウンド DNS トラフィックをフィルタリングする（「Resolver DNS Firewall を使用すると、仮想プライベートクラウド (VPC) のアウトバウンド DNS トラフィックをフィルタリングおよび規制できます。」「DNS Firewall による保護の主な用途は、データの DNS 漏洩を防ぐことです。」）
