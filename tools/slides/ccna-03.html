3 ウェイハンドシェイクと終わり方

フラグ意味使う場面
SYN番号を合わせる始めるとき
ACK確認応答の欄が有効接続後はいつも
FINもう送るデータはないふつうの終わり
RSTコネクションをリセット打ち切り・異常
ふつうの終わり方：片方が FIN →相手が ACK。相手も送り終えたら FIN →ACK。閉じるのは片方向ずつで、FIN を送った側も相手が閉じるまで受け取れる。
UDP にはこの手順がない。いきなりデータを送る。
出典：RFC 9293 3.5（The "three-way handshake" is the procedure used to establish a connection／Figure 6: Basic Three-Way Handshake）・3.6（We have chosen to treat CLOSE in a simplex fashion. The user who CLOSEs may continue to RECEIVE until … the remote peer has CLOSED also）・3.1（ACK: Acknowledgment field is significant／RST: Reset the connection／SYN: Synchronize sequence numbers／FIN: No more data from sender）

シーケンス番号と確認応答の計算

次の SEQ ＝ 今の SEQ ＋ データのバイト数
ACK ＝ 受け取った最後のバイト ＋ 1
  1. A が SEQ=101 で 500 バイト送る（101〜600 番）
  2. B は 600 番まで受けたので ACK=601（次は 601 がほしい）
  3. A は次に SEQ=601 から送る
  4. 601 のセグメントが失われると、B は ACK=601 のまま → A は時間切れ（RTO）で再送
数字は計算の例として Claude が作った。
番号はバイトの数：セグメントの数ではなく、送ったバイトの位置を表す。だから受け手は抜け・重複・順番の入れ替わりが分かる。
落とし穴：ACK は「受け取った最後の番号」ではなくその次。600 ではなく 601。
出典：RFC 9293 3.1（Sequence Number: The sequence number of the first data octet in this segment … If SYN is set, the sequence number is the initial sequence number (ISN) and the first data octet is ISN+1／Acknowledgment Number: … the value of the next sequence number the sender of the segment is expecting to receive）・3.8.1（the retransmission timeout (RTO) must be dynamically determined）

ウィンドウと輻輳制御

ウィンドウ ＝ 受け手が今受け取れる量（Claude が作成）
フロー制御輻輳制御
合わせる相手受け手のバッファーネットワークの混み具合
しくみウィンドウの欄（16 ビット）スロースタート・輻輳回避・高速再送・高速回復
決まりRFC 9293RFC 5681
UDPなしなし
なぜ速い？1 つ送るたびに ACK を待つと遅い。ウィンドウの範囲までは続けて送り、まとめて ACK を受ける。
UDP は輻輳制御を持たないので、アプリが線の速さで送り続けると経路を混ませる（RFC 8085）。
出典：RFC 9293 3.8.6（The window sent in each segment indicates the range of sequence numbers the sender of the window (the data receiver) is currently prepared to accept … related to the data buffer space）・3.1（Window: 16 bits）／RFC 5681（slow start, congestion avoidance, fast retransmit, and fast recovery）／RFC 8085（UDP … provides no inherent congestion control mechanisms）

UDP の性質と使いどころ

UDP がしないことだから…
接続をつくるつなぐ・切る手間がない、覚える状態が少ない
再送失ったら失ったまま。遅れが増えない
重複・順番の処理必要ならアプリが自分で作る
輻輳制御送る量はアプリしだい
RFC 8085：確実な配達がいるアプリは、その仕組みを自分で作らなければならない（MUST）。順番がいるなら自分で並べ直す。
音声・動画（RTP）遅れて届いた音は役に立たない。再送して待つより、次を流す。RTP はふつう UDP の上で動き、UDP のポート番号とチェックサムを使う。
1 往復で済むやりとりDNS の問い合わせ、DHCP、TFTP、SNMP、syslog、NTP。接続をつくる手間のほうが大きい。
落とし穴：「UDP は信頼性がない＝役に立たない」ではない。軽さ・速さのために選ぶ。
出典：RFC 8085 1（they do not establish end-to-end connections … does not incur connection establishment and teardown overheads）・3.3（UDP does not provide any reliability … Applications that do require reliable message delivery MUST implement an appropriate mechanism themselves／does not protect against datagram duplication／Applications that require ordered delivery MUST reestablish datagram ordering themselves）／RFC 3550（Applications typically run RTP on top of UDP to make use of its multiplexing and checksum services）

4 つの設定と「同じネットワーク？」の判断

設定役割例

送る前の判断（RFC 1122 3.3.1.1）
  1. 自分のアドレスと宛先を、同じマスクでネットワークの部分だけ取り出す
  2. 同じ → 同じネットワーク：宛先へ直接送る
  3. 違う → ゲートウェイへ送る
192.168.10.25／24 → 192.168.10.0

症状から、まちがった設定を当てる

症状疑う設定理由
同じ LAN とは通じるが、外と通じないデフォルトゲートウェイ外あての通信は出口へ送る。出口がまちがっていると届かない
IP アドレスなら通じるが、名前では通じないDNS サーバー経路は正しい。名前を IP に変えられていない
IPv4 アドレスが 169.254.x.xDHCP（届いていない）ほかに設定の方法がないときに付くリンクローカルのアドレス
同じ LAN の一部の相手と通じないサブネットマスク同じネットワークの相手を外だと思い（またはその逆）、送り先をまちがえる
ゲートウェイが別のネットワークの番号ゲートウェイの値ゲートウェイは自分と同じネットワークの中になければならない

まとめ

TCP（1.5）コネクション型。SYN→SYN＋ACK→ACK。番号はバイト単位、ACK は次にほしい番号。ウィンドウ＝受け手、輻輳制御＝ネットワーク
UDP（1.5）コネクションレス・8 バイト・再送なし。音声（RTP）・DHCP・TFTP・SNMP・DNS の問い合わせ
ポート（1.5）0〜1023 System、1024〜49151 User、49152〜65535 Dynamic。サーバーは決まった番号で待つ
端末の設定（1.10）IP・マスク・ゲートウェイ・DNS。ipconfig（/all）、ip address・ip route・resolv.conf、macOS の TCP/IP 画面
数字中身
TCP／UDP ヘッダー20 B〜／8 B
DNS の UDP512 バイトまで
DHCP67（サーバー）・68（クライアント）
FTP／TFTPTCP 20・21／UDP 69
