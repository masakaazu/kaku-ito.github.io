Site-to-Site VPN の部品

しくみ決まり本番で狙われる点
VPN トンネル1 つの VPN 接続に 2 本。それぞれ固有のパブリック IP両方を設定しておく（冗長性）
仮想プライベート GW1 つの VPC にアタッチ。既定の ASN は 64512VPN の IPv6・高速 VPN・広帯域幅トンネルは使えない
Transit Gateway複数の VPC とオンプレミスをつなぐハブとして VPN を終端IPv6・高速 VPN・広帯域幅トンネル（5 Gbps）が使える
出典：AWS Site-to-Site VPN 接続用のトンネルオプション（「冗長性を確保するために両方のトンネルを設定することが重要です。」）／AWS Site-to-Site VPN の仕組み（「VPN 接続は、仮想プライベートゲートウェイまたは AWS 側のトランジットゲートウェイと、オンプレミス側のカスタマーゲートウェイの間に 2 つの VPN トンネルを提供します。」「仮想プライベートゲートウェイは Site-to-Site VPN 接続で IPv6 をサポートしません。」）

VPN の冗長化・帯域・高速化

困りごとやり方ひっかけ
AWS 側の故障1 つの VPN 接続の 2 本のトンネルを両方設定（別々の AZ で終わる）トンネル 2 本ではオンプレミスのルーターの故障は防げない
自社ルーターの故障・保守2 台目のカスタマーゲートウェイデバイスで、同じ VGW へ 2 つ目の VPN 接続。BGP で切り替え両方のデバイスが同じ IP 範囲を広告する
トンネルの帯域スタンダード 1.25 Gbps → 広帯域幅トンネル 5 Gbps（Transit Gateway か Cloud WAN）VGW には「大きなサイズ」はない
さらに帯域複数の VPN 接続で ECMP。広帯域幅の VPN 接続 2 つ（4 トンネル）で 20 GbpsECMP は Transit Gateway の VPN アタッチメントで有効にする
経路が不安定高速 VPN 接続：Global Accelerator で最寄りのエッジから AWS のネットワークへTGW だけ。VGW 不可・既存の接続で有効化不可・DX パブリック VIF 不可
出典：フェイルオーバー用の冗長 AWS Site-to-Site VPN 接続（「冗長な VPN 接続とカスタマーゲートウェイデバイスを使用すれば、1 つのデバイスでメンテナンスを実行しながら、2 番目の VPN 接続を通してトラフィックの送信を継続することができます。」）／AWS Site-to-Site VPN 接続用のトンネルオプション（「トンネルあたり 5 Gbps を超える帯域幅が必要な場合は、複数の VPN 接続にまたがって ECMP を使用できます。」）／高速 AWS Site-to-Site VPN 接続（「仮想プライベートゲートウェイは、高速化 VPN 接続をサポートしません。」）

VPN のルーティングと優先順位

静的ルーティングオンプレミスの IP プレフィックスを手で指定する
動的ルーティング（BGP）カスタマーゲートウェイと経路を自動で交換。冗長な VPN 接続や VPN CloudHub で使う
ルート伝達VPN 接続が UP のとき、VPN のルートを VPC のルートテーブルに自動で入れる。これを忘れると、トンネルが UP でも届かない
ローカルルートが最優先VPN や Direct Connect から伝わったルートがより具体的でも、VPC のローカルルートと重なればローカルが勝つ
出典：ルートテーブルと AWS Site-to-Site VPN ルーティングの優先度（「Site-to-Site VPN 接続または Direct Connect 接続から伝達されるルートが VPC のローカルルートと重複する場合は、伝達されたルートがより詳細であっても、ローカルルートが最優先されます。」「Direct Connect 接続から BGP で伝播されたルート」）／AWS Site-to-Site VPN の開始方法（「ルートテーブルのルート伝播を有効にして、Site-to-Site VPN ルートを自動的に伝播することができます。」）

VPN CloudHub と Client VPN

各拠点は一意の ASN で、動的ルーティングの VPN 接続を作る。拠点の IP 範囲は重ねない。
Client VPN内容
何か個人の端末からの、マネージドのリモートアクセス VPN（OpenVPN ベース・TLS）
認証Active Directory・フェデレーション・証明書
規模利用者の数に合わせて自動でスケール
既定フルトンネル：端末のすべての通信が VPN を通る
分割トンネルエンドポイントのルートに合う通信だけ VPN へ。AWS からの送信が減り、データ転送のコストが下がる
出典：VPN CloudHub を使用した AWS Site-to-Site VPN 接続間の安全な通信（「サイト間で IP 範囲が重複することは許可されません。」）／AWS Client VPN とは（「AWS Client VPN は、オンプレミスネットワーク内の AWS リソースに安全にアクセスできるようにする、クライアントベースのマネージド VPN サービスです。」）／AWS Client VPN エンドポイントの分割トンネル（「AWSからの送信トラフィックの量を減らして、データ転送コストを削減できます。」）。拠点名と ASN は Claude が作った例

Direct Connect のしくみと接続の種類

接続速度だれが作る向く場面
専用接続1・10・100・400 GbpsAWS に申し込み、ロケーションで物理ポートを使う大きな帯域・LAG で束ねる
ホスト接続50 Mbps 〜 25 GbpsDirect Connect パートナーが作り、利用者が受け入れる1 Gbps 未満の小さな拠点
LAG100 Gbps 未満は 4 本まで、100・400 Gbps は 2 本まで同じエンドポイントの同じ速度の専用接続を束ねる帯域を増やし 1 つとして管理
出典：Direct Connect とは（「この接続を使用すると、パブリック AWS サービス (Amazon S3 など) または Amazon VPC への仮想インターフェイスを直接作成し、ネットワークパス内のインターネットサービスプロバイダーをバイパスできます。」）／専用 Direct Connect 接続（「指定できる値は 1 Gbps、10 Gbps、100 Gbps、および 400 Gbps です。」）／Direct Connect リンク集約グループ (LAGs)（「LAG のすべての接続では、同じ帯域幅を使用する必要があります。」）

仮想インターフェイスと Direct Connect ゲートウェイ

選び方：VPC へ → プライベート VIF（VGW か Direct Connect ゲートウェイ）。S3 などのパブリックなエンドポイントへ → パブリック VIF。Transit Gateway の先の多くの VPC へ → トランジット VIF。
Direct Connect ゲートウェイ：グローバルなリソースで、1 本の接続から世界のリージョンの VPC に届く。ただし、同じ Direct Connect ゲートウェイにつながった VPC どうしは、ここを通って通信できない。
出典：Direct Connect 仮想インターフェイスとホスト仮想インターフェイス（「プライベート仮想インターフェイス: プライベート IP アドレスを使って Amazon VPC にアクセスするには、プライベート仮想インターフェイスを使用する必要があります。」）／Direct Connect ゲートウェイ（「Direct Connect ゲートウェイはグローバルに利用可能なリソースです。」）

Direct Connect の回復性モデル

ひっかけ：LAG は帯域を増やすもので、同じ機器・同じロケーションで終わる接続を束ねる。ロケーションの障害への備えにはならない。「ロケーション全体の障害にも耐える・最も高い可用性」→ 最大回復性。
出典：AWS Direct Connect レジリエンシーツールキット（「最大回復性: このモデルは、99.99％ の SLA を達成するための専用接続をリクエストする方法を提供します。」「高い回復性: このモデルは、99.9％ の SLA を達成するための専用接続をリクエストする方法を提供します。」「開発とテスト: このモデルでは、1 つの場所にある個別のデバイスを終端とする別々の接続を使用して、クリティカルでないワークロードの開発とテストの回復性を実現できます。」）

Direct Connect の暗号化と予備の経路

方法しくみ使いどころ
何もしないDirect Connect は既定で転送中の通信を暗号化しないアプリ側で TLS などを使う前提
Direct Connect＋Site-to-Site VPN専用接続の上に VPN を張り、IPsec で暗号化したプライベートな接続にする「VPC までを IPsec で暗号化」
MACsecIEEE の標準。ルーターと Direct Connect ロケーションの間を、レイヤー 2 のポイントツーポイントで暗号化回線の区間の暗号化。エンドツーエンドではない
VPN を予備に同じ VGW に、インターネット経由の VPN 接続を作る。DX のルートが優先され、止まると VPN へ「専用線の予備をコストを抑えて」
出典：AWS Direct Connect での暗号化（「AWS Direct Connect は、デフォルトで転送中のトラフィックを暗号化しません。」「この組み合わせにより、IPsec で暗号化されたプライベート接続が提供されます。」）／Direct Connect での MAC セキュリティ（「MACsec は、イーサネットリンク上でポイントツーポイントのセキュリティを提供します。」）

Transit Gateway のルートテーブルで分ける

関連付けと伝達：各アタッチメントは、ちょうど 1 つのルートテーブルに関連付ける（どの表を見て送るか）。アタッチメントのルートは 1 つ以上の表に伝達する（どの表に自分を載せるか）。ブラックホールルートで通信を捨てることもできる。
忘れやすい設定：VPC 側のサブネットのルートテーブルにも、Transit Gateway へのルートを書く。TGW の表だけでは、VPC から出ていかない。
出典：AWS Transit Gateway の仕組み（「アタッチメントごとに 1 つのルートテーブルに関連付けることができます。アタッチメントでそのルートを 1 つ以上のルートテーブルに伝播できます。」「ルートに一致するトラフィックを破棄する Transit Gateway ルートテーブルでは、ブラックホールルートを作成できます。」）。ルートテーブルの名前は Claude が作った例

Transit Gateway ピアリングと一元的な発信

ピアリングとの違い：VPC ピアリングでは相手の VPC の NAT デバイスを使えない（#17）。Transit Gateway なら、出口の VPC に通信を中継できる。Transit Gateway ピアリングの経路は、伝達ではなく静的ルートで作る。
出典：AWS Transit Gateway の Transit Gateway ピアリングアタッチメント（「Transit Gateway 間でトラフィックをルーティングするには、Transit Gateway のピアリングアタッチメントをポイントする静的ルートをTransit Gateway のルートテーブルに追加します。」）／AWS Transit Gateway の仕組み（「インターネットゲートウェイがない VPC からのアウトバウンドインターネットトラフィックを、NAT ゲートウェイとインターネットゲートウェイを含む VPC にルーティングするように、トランジットゲートウェイを設定できます。」）。VPC の数は Claude が作った例

ハイブリッド DNS：Resolver エンドポイント

向きで選ぶ：社内から VPC の名前（プライベートホストゾーン）を引く → インバウンド。VPC の EC2 から社内の名前を引く → アウトバウンドと転送ルール（ドメインごとに 1 つ、VPC に関連付ける）。
ひっかけ：社内の DNS から VPC の「CIDR＋2」に直接転送する方法はサポートされず、結果が不安定になる。インバウンドエンドポイントを使う。
出典：Route 53 VPC Resolver とは（「インバウンド Resolver エンドポイントを使用すると、VPC に、オンプレミスネットワークまたは別の VPC から DNS クエリが可能になります。」「アウトバウンド Resolver エンドポイントを使用すると、VPC から、オンプレミスネットワークまたは別の VPC に DNS クエリが可能になります。」）／VPC とネットワークの間における DNS クエリの解決（「代わりに、Resolver のインバウンドエンドポイントの使用をお勧めします。」）
