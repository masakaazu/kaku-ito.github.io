ロードバランサーと Auto Scaling

リクエストを複数のサーバーに分け（ELB）、サーバーの台数を負荷に合わせて増減し、壊れたら置き換える（EC2 Auto Scaling）。種類の選び方と設定の決め方

各ページの下に、根拠にした AWS の公式ドキュメント（Elastic Load Balancing・Application／Network／Gateway Load Balancer・Amazon EC2 Auto Scaling）を書いた（青い文字を押すと開く）。「」の中はドキュメントの原文どおり（日本語版は機械翻訳のため、語順が不自然なところもそのまま）。会社名や構成の例は Claude が作った例

全体像試験ガイド タスク 2.1・2.2・3.2

ELB の役目：複数の AZ のターゲットに分け、ヘルスチェックで正常なものにだけ送る。ロードバランサー自体もトラフィックに合わせて自動でスケールする。
Auto Scaling の役目：負荷に合わせて台数を増減する（弾力性）＋故障したインスタンスを置き換えて希望の数を保つ（耐障害性）。ELB に自動で登録・登録解除する。
出典：Elastic Load Balancing とは?／Amazon EC2 Auto Scaling とは（「Amazon EC2 Auto Scaling は、EC2 ヘルスチェックを使用してインスタンスのヘルスと可用性を自動的にモニタリングし、終了したインスタンスまたは障害が発生したインスタンスを置き換えて、希望するキャパシティを維持します。」）

スキーム：インターネット向けと内部向け

作るときに決める：インターネット向けはノードにパブリック IP があり、DNS 名がパブリックに解決される。内部向けはプライベート IP だけで、VPC の中（や VPN・Direct Connect でつながった先）から使う。
本番の言い回し：「アプリ層は Web 層からだけ受ける」→ 内部向けのロードバランサー。インターネット向けにしてセキュリティグループで絞るより筋がよい。
出典：Elastic Load Balancing の仕組み（「ロードバランサーを作成するとき、ロードバランサーを内部向けにするかインターネット向けにするか選択する必要があります。」「インターネット向けロードバランサーのノードにはパブリック IP アドレスが必要です。」）

クロスゾーン負荷分散：AZ ごとの台数の差

2 つの AZ のノードにトラフィックが半分ずつ来るとした計算（Claude が作った例）。無効だと各ノードは自分の AZ のターゲットにだけ送るので、台数の少ない AZ a の 1 台が 25% を受け持つ。
答え方：「NLB の後ろで一部の AZ のインスタンスだけ負荷が高い」→ クロスゾーン負荷分散を有効にする（または AZ ごとの台数をそろえる）。
AZ の数：ALB は少なくとも 2 つの AZ を有効にする必要がある。1 つの AZ だけのロードバランサーは作れない。
出典：Elastic Load Balancing の仕組み（「Network Load Balancer と Gateway Load Balancer では、クロスゾーン負荷分散はデフォルトで無効になっています。」「Application Load Balancer では、クロスゾーン負荷分散がロードバランサーレベルで常に有効になっています。」「ただし、Application Load Balancer では、少なくとも 2 つ以上のアベイラビリティーゾーンを有効にする必要があります。」）

GWLB：検査装置を透過的に挟む

何をする：ファイアウォール・侵入検知と防止・ディープパケットインスペクションなどの仮想アプライアンスをまとめて置き、台数を増減し、正常なものにだけ通す。通信は検査して元の流れに戻る（透過的）。
ほかとの違い：AWS WAF は ALB・CloudFront などの HTTP のリクエストを調べる。Network Firewall は AWS のマネージドのファイアウォール。「サードパーティのアプライアンス」なら GWLB。
出典：Gateway Load Balancer とは？（「ゲートウェイロードバランサ― を使用すると、ファイアウォール、侵入検知および防止システム、ディープパケットインスペクションシステムなどの仮想アプライアンスをデプロイ、スケーリング、管理できます。」「Gateway Load Balancer エンドポイントとの間で送受信されるトラフィックは、ルートテーブルを使用して設定されます。」）

ヘルスチェックと登録解除の遅延

ヘルスチェックの状態
状態意味
initial登録中か、最初のヘルスチェック中。1 回合格すると正常になる
healthy正常。リクエストを送る
unhealthy応答しないか不合格。送らない
draining登録解除中。新しいリクエストは送らず、処理中のものが終わるのを待つ
フェイルオープン：全ターゲットが異常になったら、ALB は状態にかかわらず全ターゲットに送る。設定ミスで全滅してもサービス全体は止めないため。
登録解除の遅延（デフォルト 300 秒）
処理中のリクエストもつながった接続もなくなれば、遅延の終わりを待たずにすぐ外れる。
答え方：「スケールインやデプロイで処理中のリクエストがエラーになる」→ 登録解除の遅延を処理時間より長く。逆に「外れるのが遅くデプロイに時間がかかる」→ 短く。
出典：Application Load Balancer ターゲットグループのヘルスチェック（「ターゲットは、登録後に正常と見なされるためには、1 つのヘルスチェックに合格する必要があります。」「ターゲットグループに異常な登録済みターゲットのみが含まれている場合、そのヘルスステータスにかかわらず、ロードバランサーはそれらすべてのターゲットにリクエストをルーティングします。」）／Application Load Balancer のターゲットグループ属性を編集する（「デフォルトでは、Elastic Load Balancing 登録解除プロセスを完了する前に 300 秒待って、ターゲットへ処理中のリクエストが完了するのを助けることができます。」）

NLB の固定 IP と「NLB の後ろに ALB」

NLB の IP：AZ ごとのノードが固定の IP アドレスを持つ。インターネット向けなら、サブネットごとに Elastic IP を 1 つ付けられる。ALB の IP は変わるので、IP を登録してもらう相手には向かない。
世界中から固定 IP：複数のリージョンをまたいで固定の IP で入り口を作るなら Global Accelerator（#19 で学ぶ）。1 つのリージョンなら NLB で足りる。
出典：Network Load Balancer とは?（「インターネット向けのロードバランサーを作成する場合は、必要に応じて 1 つの Elastic IP アドレスをサブネットごとに関連付けることができます。」「1 秒あたり数百万のリクエストを処理できます。」）／Network Load Balancers のターゲットグループ

起動テンプレート・ヘルスチェック・猶予期間

設定要点本番の言い回し → 答え
起動テンプレートAMI・インスタンスタイプ・セキュリティグループ・ユーザーデータなど。起動設定と違い、複数のバージョンを持てる。複数のタイプやスポットの組み合わせもこちら「AMI を新しくしたい」→ 新しいバージョン＋インスタンスの更新
EC2 のヘルスチェックデフォルト。インスタンスが動いているか（ステータスチェック）だけを見る「アプリが固まっても置き換わらない」→ これだけでは足りない
ELB のヘルスチェック有効にすると、ロードバランサーが異常と報告したインスタンスも置き換える「ALB では異常なのに置き換わらない」→ 有効にする
猶予期間起動直後、異常でも終了しない最小の時間。コンソールのデフォルト 300 秒「準備中に終了と起動をくり返す」→ 準備時間より長く
くり返しのわな：猶予期間が短いと、起動 → 準備中にヘルスチェック不合格 → 終了 → また起動、がずっと続く。ELB のヘルスチェックを外すのは答えにならない（固まったときに置き換わらなくなる）。
デフォルトのインスタンスウォームアップ：新しいインスタンスのメトリクスが落ち着くまで集計に入れない時間。ターゲット追跡・ステップでの増やしすぎを防ぐ。
出典：Auto Scaling 起動テンプレート（「ただし、起動設定の代わりに起動テンプレートを定義すると、複数のバージョンの起動テンプレートを使用することができます。」）／Auto Scaling グループのヘルスチェックについて／Auto Scaling グループにヘルスチェックの猶予期間を設定する（「コンソールでは、Auto Scaling グループを作成するときのヘルスチェックの猶予期間がデフォルトで 300 秒になっています。」）

スケーリングポリシーを選ぶ

方法決め方本番の言い回し
ターゲット追跡メトリクスと目標値だけ。サーモスタットのように保つ。アラームは自動で作られる「CPU を 50% くらいに保つ」「最も簡単に」
ステップアラームのしきい値をどれだけ超えたかで、増減する数を段階的に「大きく超えたら一気に増やす」
シンプルアラーム 1 つで決めた数。1 回動くとクールダウンが終わるまで待つAWS は使わないことを勧める
スケジュール日時（cron とタイムゾーン）で最小・希望・最大を設定「毎週月曜の朝」「年度末」「セールの前」
予測過去の負荷から日次・週次のパターンを見つけ、前もって増やす「毎日くり返す山」「起動が遅く、山の前に準備」
反応か予定か：ターゲット追跡・ステップ・シンプルは「負荷が来てから」の動的スケーリング。スケジュールは人が日時を決める。予測は AWS が過去から学ぶ。
ひっかけ：年に 1 回の決まった日の山は、予測（日次・週次のくり返し）よりスケジュール。「希望を最大にしておく」は常に最大でコストのむだ。
出典：Amazon EC2 Auto Scaling のターゲットトラッキングスケーリングポリシー（「例として、これはサーモスタットがターゲット温度を維持する仕組みと似ています。」）／Amazon EC2 Auto Scaling のステップおよび簡易スケーリングポリシー（「ベストプラクティスとして、シンプルスケーリングポリシーとスケーリングクールダウンを使用しないことをお勧めします。」）／スケジュールされたスケーリング／予測スケーリング（「予測スケーリングは、負荷の履歴データを分析して、トラフィックフローの日ごとまたは週ごとのパターンを検出することで機能します。」）

ターゲット追跡の動き（CPU 50% を目標にした例）

数値は Claude が作った例。台数は目標に近づくよう AWS が計算する。
使えるメトリクス：CPU の平均使用率・ネットワークの入出力・ALB のターゲットあたりのリクエスト数など。メトリクスの値は、台数に比例して増減するものを選ぶ。
メッセージの数で：SQS のキューの深さで増減するなら、「インスタンスあたりのバックログ」を自分で計算したメトリクスを目標にする（#06）。

ライフサイクルフックとウォームプール

ライフサイクルフック：次の状態に移る前に待たせる。待つ時間のデフォルトは 1 時間。EventBridge で通知し、Lambda を呼んだり、インスタンスに入って作業したりする。「終了前にログを S3 へ」「準備が終わってからトラフィックを受ける」。
ウォームプール：大量のデータを書き込むなど起動が非常に遅いアプリ向け。いつも余分に動かしておく（過剰なプロビジョニング）より安い。起動が速いアプリでは要らない。
出典：Amazon EC2 Auto Scaling のライフサイクルフック（「ライフサイクルフックのデフォルトタイムアウトは 1 時間です (ハートビートタイムアウト)。」「スケールイン イベントが発生すると、ライフサイクルフックによってインスタンスが終了される前に一時停止され、Amazon EventBridge を使用して通知が送信されます。」）／ウォームプールを使用してブート時間が長いアプリケーションのレイテンシーを低減する（「ウォームプールを使用すると、インスタンスが大量のデータをディスクに書き込む必要があるなど、起動時間が非常に長いアプリケーションのレイテンシーを低減できます。」）

どれを終了するか・何で動かすか・どう入れ替えるか

機能要点本番の言い回し
終了ポリシースケールインでどれを先に終了するか。まず AZ のあいだのバランスを保つ（多い AZ から減らす）。デフォルトは古い設定（古い起動設定・古いテンプレートのバージョン）のものから「どのインスタンスが終了されるか」
複数のインスタンスタイプと購入オプション1 つのグループでオンデマンドとスポット、複数のタイプを組み合わせる。キャパシティの再調整で、中断されそうなスポットを前もって置き換える「最低限はオンデマンド、増える分はスポット」
インスタンスの更新新しい起動テンプレートのバージョンで、最小正常率と最大正常率に基づき、バッチごとに順に置き換える「新しい AMI に、止めずに全台入れ替え」
オンデマンドとスポットの組み合わせ（例）：オンデマンドの基本の台数 2・それを超える分はオンデマンド 30%・スポット 70%、タイプは m7i・m6i・m7a から（Claude が作った例）。タイプを増やすほどスポットを確保しやすい。
ひっかけ：「希望を 0 にしてから戻す」「全台を手で終了」はサービスが止まる。「リザーブドをスポットに変換」という機能はない。
出典：Amazon EC2 Auto Scaling の終了ポリシーを設定する（「デフォルトでは、Amazon EC2 Auto Scaling は、古い設定を使用しているインスタンスを最初に終了するように設計された終了ポリシーを使用します。」）／複数のインスタンスタイプと購入オプションを使用する Auto Scaling グループ（「1 つの Auto Scaling グループ内で、オンデマンドインスタンスとスポットインスタンスのフリートを起動してオートスケールできます。」）／Auto Scaling グループでのインスタンスの更新の仕組み（「最小正常率および最大正常率に基づいて、バッチ内のインスタンスを置き換えます。」）
