バーストパフォーマンス（T）と CPU クレジット

向く用途：多くの汎用のワークロードは、ふだんはビジーではない。小さな Web サーバー・開発環境・マイクロサービスなど、平均は低く、ときどき跳ねる処理に合う。グラフの数字は Claude が作った例。
向かない用途：CPU をずっと高く使う処理。クレジットを使い続けることになるので、M や C などの固定パフォーマンスのインスタンスにする。
出典：バーストパフォーマンスインスタンス（「多くの汎用ワークロードでは、平均的な状態はビジーではないので、持続的で高いレベルの CPU パフォーマンスを必要としません。」）／Amazon EC2 インスタンスタイプ（「各バーストパフォーマンスインスタンスは、CPU 使用率がベースラインを下回っている間は継続的にクレジットを獲得し、ベースラインを上回っている間は継続的にクレジットを消費します。」）

無制限モードとスタンダードモード

無制限モード（unlimited）スタンダードモード（standard）
クレジットが尽きたら必要なだけベースラインを超えて使い続けられるベースラインの性能まで下がる
追加の料金24 時間の平均の CPU 使用率がベースラインを超えると、超えた分にかかるかからない
既定T4g・T3a・T3 は、デフォルトで無制限モードで起動する設定で選ぶ
合うときときどき長めに跳ねても、性能を落としたくない料金を確実に固定したい
本番の場面：「T3 のインスタンスで追加料金が増えている」「CPU がいつも高い」→ 無制限モードで超えた分を払い続けている。固定パフォーマンスの M・C に変えるのが答えになりやすい。
ひっかけ：サイズを小さくすると、ベースラインも下がるので、超える分がかえって増える。スタンダードに変えると料金は止まるが、性能が下がる。
出典：バーストインスタンスの無制限モードの概念（「24 時間の平均 CPU 使用率がベースラインを超えたインスタンスには、vCPU 時間あたりの超過の使用量に対して、[均一追加料金]が発生します。」）／バーストパフォーマンスインスタンス（「T4g、T3a、および T3 インスタンスは、デフォルトで無制限モードで起動するため、起動クレジットを受け取ることはありません。」）

AMI と EC2 Image Builder

ゴールデンイメージ：設定を済ませた AMI から起動すると、起動のたびに長いインストールをしなくてよい。スケールアウトが速くなる（ユーザーデータで毎回入れるより速い）。
手作業をなくす：「毎月パッチを当てた AMI を自動で作り直す」なら EC2 Image Builder のパイプライン。AWS Backup はデータを守るもので、パッチを当てたイメージは作らない。
出典：Amazon EC2 の Amazon マシンイメージ（「AMI を別の AWS リージョンにコピーし、そのリージョンでインスタンスを起動するために使用できます。」）／Image Builder とは（「EC2 Image Builder は、カスタマイズされ、安全で、up-to-dateサーバーイメージの作成、管理、デプロイを自動化 AWS のサービス するフルマネージド型です。」「パイプラインを設定して、所有しているイメージの更新とシステムパッチを自動化できます。」）

ユーザーデータとキーペア

ユーザーデータ（起動時のスクリプト）
#!/bin/bash
dnf -y install httpd
systemctl enable --now httpd
aws s3 cp s3://example-bucket/site/ \
  /var/www/html/ --recursive
Claude が作った例（Amazon Linux の Web サーバー）。Linux ではシェルスクリプトか cloud-init のディレクティブ。Windows では起動エージェントが処理する
いつ動く：デフォルトでは最初の起動のときだけ。再起動では動かない。
秘密は書かない：インスタンスの中から読めるが、認証や暗号化で守られていない。パスワードは Secrets Manager などに。
キーペア（接続の鍵）
OSプライベートキーの使い道
LinuxSSH で接続する
Windows管理者パスワードを復号する
鍵を配らずに入る：キーペアの代わりに、Systems Manager Session Manager でブラウザや CLI から接続できる。SSH のポートを開けずに済む。
取り違え：IAM ユーザーのアクセスキーは AWS の API を呼ぶためのもので、SSH には使わない。
出典：ユーザーデータ入力を使用して EC2 インスタンスを起動するときにコマンドを実行する（「デフォルトでは、ユーザーデータスクリプトと cloud-init ディレクティブは、インスタンスの最初の起動サイクル中にのみ実行されます。」）／Amazon EC2 のキーペアと Amazon EC2 インスタンス（「Windows インスタンスの場合、管理者パスワードを復号化するにはプライベートキーが必要です。」）

インスタンスメタデータと IMDSv2

本番の場面：「メタデータの読み方をトークン方式だけにしたい」「SSRF でロールの認証情報を盗まれるのを防ぎたい」→ IMDSv2 を必須にする。ユーザーデータもメタデータと同じ場所から読めるので、秘密は置かない。
出典：インスタンスメタデータサービスを使用してインスタンスメタデータにアクセスする（「IMDSv2 呼び出しのみを受け入れるように各インスタンスでインスタンスメタデータサービス (IMDS) を設定できます。」）／EC2 インスタンスのインスタンスメタデータにアクセスする（「IMDSv2 が必要な場合はIMDSv1 は動作しません。」）／インスタンスメタデータを使用して EC2 インスタンスを管理する（「インスタンスメタデータおよびユーザーデータにはそのインスタンス自体内からのみアクセスできるものの、データは認証または暗号化手法によって保護されていません。」）

インスタンスストア：何をすると消えるか

向く用途：バッファ・キャッシュ・スクラッチデータなど、頻繁に変わる一時的なデータ。インスタンスの料金に含まれる。
起きることインスタンスストアのデータメモリの内容
再起動残る消える
停止 → 開始消える消える
休止 → 開始消えるルートの EBS に保存して戻る
終了消える消える
残したいデータ：EBS・S3・EFS に置くか、複数のインスタンスに複製する。止めて開始すると、ふつうは新しいホストに移るので、前のディスクには戻れない。
出典：Amazon EC2 インスタンスストアボリュームのデータの永続性（「インスタンスストアボリューム上のデータはインスタンスが再起動しても保持されます。」「ただし、インスタンスが停止、休止、終了するとデータは消滅します。」）／EC2 インスタンス用のインスタンスストアの一時ブロックストレージ（「インスタンスストアはバッファ、キャッシュ、スクラッチデータ、その他の一時的データのように頻繁に変化する情報の一時的なストレージに最適です。」）

休止：メモリの状態のまま止める

使う場面：起動してメモリにデータを読み込むまでに長い時間がかかるサーバーを、夜は止めて、翌朝その状態から再開したいとき。使うには、休止を有効にして起動し、休止の前提条件を満たす必要がある。
停止との違い：停止ではメモリの内容は消え、開始するとアプリを最初から立ち上げ直す。インスタンスストアのデータは、休止でも停止でも消える。
出典：Amazon EC2 インスタンスの休止（「休止状態に入ると、インスタンスメモリ (RAM) に置かれていた内容が、Amazon Elastic Block Store (Amazon EBS) のルートボリュームに保存されます。」「EBS ボリュームのストレージに対しては、RAM の内容のストレージも含めて、料金が発生します。」）

インスタンスの自動復旧

何のため：1 台のインスタンスの可用性を戻す。インスタンス ID や IP が変わらないので、取引先や DNS の設定を変えずに済む。復旧が失敗したら、手動で停止して開始する。
ほかとの違い：Auto Scaling は異常なインスタンスを捨てて新しい（別の ID の）インスタンスを起動する。ELB のヘルスチェックは送り先から外すだけで、インスタンスは直さない。
出典：インスタンスの自動復旧（「これらの復旧メカニズムは がシステムステータスチェックが失敗する原因となる基盤となるハードウェアまたはソフトウェアの問題AWSを検出したときに、インスタンスの可用性を復元するように設計されています。」「復元されたインスタンスは失われた要素を除いて、元のインスタンスと同じです。」「サポート対象のインスタンスを起動すると、簡易自動復旧がデフォルトで有効になります。」）

拡張ネットワーキング（ENA）と EFA

問題文の言葉答え
ネットワークを多く使う一般のサーバー・PPS を上げたいENA（拡張ネットワーキング）
MPI・密結合の HPC・分散学習のノード間通信EFA＋クラスタープレイスメントグループ
固定のパブリック IPElastic IP（性能は変わらない）
ENA の範囲：Nitro ベースのインスタンスは、すべて ENA を使って拡張ネットワーキングをしている。SR-IOV は、従来の仮想化したネットワークインターフェイスより I/O の性能が高く、CPU の使用率が低い。

プレイスメントグループの 3 つの戦略

覚え方：速さ＝クラスター（まとめる）。多数を壊れにくく＝パーティション（組ごとに分ける）。少数を確実に分ける＝スプレッド（1 台ずつ分ける）。
台数で見分ける：100 台の分散システムをラックで分けたいならパーティション。スプレッドは AZ ごとに 7 台までなので足りない。
出典：プレイスメントグループのプレイスメント戦略（「低いネットワークレイテンシー、高いネットワークスループット、またはその両方からメリットを受けるアプリケーションの場合は、クラスタープレイスメントグループの使用をお勧めします。」「パーティションプレイスメントグループは、アベイラビリティーゾーンごとに最大 7 つのパーティションを持つことができます。」「スプレッドプレイスメントグループは、それぞれ異なるハードウェアに配置されるインスタンスのグループです。」）

パーティションとスプレッドをくわしく

パーティションスプレッド（ラックレベル）
分ける単位インスタンスの組（パーティション）ごとに別のラックインスタンス 1 台ずつ別のハードウェア
上限AZ ごとに最大 7 パーティション（台数は多くてよい）AZ ごとに実行中のインスタンスは最大 7 台
障害の影響1 つのハードウェアの障害は、そのパーティションの中だけ1 台のハードウェアの障害は、その 1 台だけ
アプリへの情報どのパーティションかを、トポロジー対応のアプリと共有できる—
合う用途HDFS・HBase・Cassandra などの大規模な分散・複製互いに分けておきたい少数の重要なインスタンス
計算の例（AWS のドキュメントの例）：3 つの AZ があるリージョンでは、AZ ごとに 7 台 × 3 ＝ 合計 21 台までスプレッドプレイスメントグループで動かせる。
出典：プレイスメントグループのプレイスメント戦略（「各パーティション内のインスタンスは、他のパーティション内のラックを共有しないため、単一のハードウェア障害の影響は関連付けられたパーティションのみに留まります。」「この情報は、HDFS、HBase、Cassandra などトポロジー対応アプリケーションと共有できます。」「例えば、3 つのアベイラビリティーゾーンがあるリージョンでは、アベイラビリティーゾーンごとにインスタンス 7 個として、合計 21 個のインスタンスをスプレッドプレイスメントグループ内で実行できます。」）
