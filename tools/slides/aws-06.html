SQS のメッセージの一生

SQS は「取りに行く」：受け手が ReceiveMessage で取りに行く（ポーリング）。押し出してくれる SNS とはここが違う。
消すまでが仕事：処理が終わったら DeleteMessage で消す。消さなければ、また誰かに配られる。
出典：Amazon SQS とは（「メッセージの安全性のため、Amazon SQS は複数のサーバーにメッセージを保存します。」）／Amazon SQS の可視性タイムアウト（「タイムアウトが期限切れになるメッセージを削除しなかった場合、メッセージはキューに再表示されて、別のコンシューマーが取得できるようになります。」）

標準キューと FIFO キュー

標準キューFIFO キュー
スループットほぼ無制限300 API コール/秒（バッチで 3,000 件/秒）。高スループットモードで最大 30,000 TPS
配信少なくとも 1 回（重複あり）1 回のみの処理
順序ベストエフォートメッセージグループの中で送った順
重複排除なし（受け手をべき等に）5 分間の重複排除の間隔
選び方：「順序が大事」「二重処理は困る」→ FIFO。「とにかく大量・速く」「順序は気にしない」→ 標準（重複はべき等で吸収）。
メッセージグループで並列にする
出典：Amazon SQS キュータイプ（「つまり、すべてのメッセージは少なくとも 1 回配信されますが、再試行やネットワーク遅延が原因で 2 回以上配信される場合もあります。」「FIFO キューでは、各メッセージグループ内のメッセージを送信した順序どおりに取り出します。」）／Amazon SQS の 1 回のみ処理

可視性タイムアウトとデッドレターキュー

可視性タイムアウトデッドレターキュー
値デフォルト 30 秒・0 秒～12 時間。ChangeMessageVisibility で途中で延ばせる再処理ポリシーの maxReceiveCount で、何回受け取られたら移すかを決める
決まり処理と削除にかかる時間に合わせるソースキューと同じアカウント・同じリージョン。保持期間は元のキューより長く
出典：Amazon SQS の可視性タイムアウト（「キューのデフォルトの可視性タイムアウトは 30 秒ですが、アプリケーションがメッセージを処理および削除するために必要な時間に合わせて調整できます。」）／Amazon SQS でのデッドレターキューの使用（「デッドレターキューは、ソースキューと同じ AWS アカウント およびリージョンにある必要があります。」）

待つ・遅らせる・残す

つまみ何をする値本番の言い回し
ロングポーリングすべてのサーバーを調べ、メッセージが来るか待ち時間が切れるまで待って応答（WaitTimeSeconds）。デフォルトはショートポーリング待ち時間を設定「空の応答が多くコストがかさむ」
遅延キュー送ったメッセージを、決めた時間だけ受け手から見えなくする0 秒～15 分「送ってから数分は処理させない」
保持期間消えるまでの時間デフォルト 4 日・1 分～14 日「受け手が数日止まってもなくさない」
可視性タイムアウト受け取ったあと、ほかの受け手から隠す時間30 秒・0 秒～12 時間「二重に処理される」
遅延と可視性の違い：遅延キューは「受け取る前」、可視性タイムアウトは「受け取った後」に見えなくする。
15 分より先の予定：SQS の遅延は最大 15 分。何時間・何日も先の実行は EventBridge スケジューラ（第3章）。
出典：Amazon SQSショートポーリングとロングポーリング（「このオプションを使用すると、空のレスポンスの数が減少し、コストが削減される可能性があります。」）／Amazon SQS のメッセージキュー（クォータ）（「デフォルトでは、メッセージは4日間保持されます。最小の期間は60秒(1分) です。最大は1,209,600秒(14日)です。」）

受け手を増やす：キューの長さで Auto Scaling

用語決め方
インスタンスあたりのバックログApproximateNumberOfMessages ÷ 動いているインスタンス数（カスタムメトリクスにする）
許容できるバックログ（目標値）許容できる待ち時間 ÷ 1 件の平均処理時間
なぜ CPU ではなく：キューにたまった仕事の量に比例して増減できる。CPU が低くても仕事がたまっていることがある。
サーバーを持たずに処理するなら Lambda のイベントソースマッピング（Lambda がキューをポーリングし、バッチで関数に渡す）。一部だけ失敗したら、部分的なバッチレスポンスで失敗分だけ再試行させる（#07）。
出典：Amazon SQS に基づくスケーリングポリシー（「ターゲット値を、維持する*インスタンスごとに許容されるバックログ*に設定します。」）／Amazon SQS での Lambda の使用

4つのサービスの使い分け

SQSSNSEventBridgeAmazon MQ
形キュートピック（パブリッシュ/サブスクライブ）イベントバス＋ルールActiveMQ・RabbitMQ のブローカー
届け方受け手が取りに行く（ポーリング）押し出す（プッシュ）ルールに合えばターゲットへ業界標準のプロトコル
受け手1つのメッセージは1つの受け手登録したすべての受け手条件に合うターゲットブローカーの使い方しだい
ためる最大 14 日ためない（受け手に SQS を付ける）ためるより振り分けブローカーがためる
選ぶ決め手受け手の都合で処理・負荷の平準化同じ通知を多くの受け手にAWS・SaaS のイベントを条件で既存のブローカーからコードを変えずに
本番のひっかけ：「オンプレミスの ActiveMQ / RabbitMQ をコードを変えずに移したい」で SQS を選ばない。SQS・SNS は新しく作るときの第一候補、移行なら Amazon MQ。
出典：Amazon MQ とは（「既存のメッセージブローカーからメッセージングコードを書き換えずに Amazon MQ に移行することもできます。」）／Amazon SNS 通知の Amazon SQS キューへのファンアウトと非同期処理（「Amazon SQS は、分散アプリケーションがポーリングモデルを介してメッセージを交換するために使用するメッセージキューサービスです。」）

選び分け：この要件ならこれ

要件答え
受け側が止まっても受付を止めないSQS で切り離す
順序どおりに1回だけ処理FIFO キュー（グループで並列）
同じメッセージが2回処理される（処理が長い）可視性タイムアウトを延ばす
何度も失敗するメッセージを分けるデッドレターキュー
空の受信が多くて高いロングポーリング
1 MiB を超えるデータを渡すS3 に置いて参照を送る（拡張クライアント）
たまった仕事に合わせて EC2 を増減インスタンスあたりのバックログで Auto Scaling
同じ通知を複数のシステムに確実にSNS → 複数の SQS（ファンアウト）
受け手ごとに欲しいメッセージだけSNS のフィルターポリシー
AWS や SaaS のイベントを条件で振り分けEventBridge
既存の RabbitMQ をコードを変えずに移すAmazon MQ
