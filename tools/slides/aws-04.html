エンベロープ暗号化

なぜ封筒にする：大きなデータを毎回 KMS に送らずにすむ。KMS には小さなデータキーの暗号化・復号だけを頼む。S3・EBS・RDS の暗号化もこの考え方。
KMS はデータキーを保存しない：暗号化データキーはデータと一緒に自分で保存する。KMS キーそのものはダウンロードできない。
出典：AWS KMS 暗号化の必須事項（「データキーでプレーンテキストデータを暗号化してから、そのデータキーを別のキーで暗号化する手法です。」）／データキーを生成する（「ダウンロードできない対称 KMS キーとは異なり、データキーは AWS KMSの外部での使用のためにユーザーに返されます。」）

S3 の暗号化の選び方

方式キーを管理するのは特徴合う要件
SSE-S3S3全バケットのデフォルト。2023 年 1 月 5 日から新しいオブジェクトは自動で暗号化。追加費用なしとくに要件がない
SSE-KMSKMS（aws/s3 かカスタマーマネージド）キーの権限で復号できる人を分ける。CloudTrail で監査。KMS の料金がかかる監査・権限の分離・アカウント間の共有（カスタマーマネージド）
DSSE-KMSKMS独立した2つの AES-256 の層「2層の暗号化」が必要
SSE-Cお客様（リクエストごとに渡す）S3 はキーを保存しない。キーをなくすとデータも失う。HTTPS 必須。新しいバケットではデフォルトで無効（2026 年 4 月から）キーを AWS に預けたくないが、暗号化処理は S3 に任せたい
クライアント側お客様S3 に送る前に暗号化。S3 は中身を知らないAWS をふくむ第三者に中身を見せない
S3 バケットキー：SSE-KMS で KMS への呼び出しを減らし、KMS のリクエストコストを最大 99% 削減。「SSE-KMS の KMS の料金が高い」→ これ。
ひっかけ：「SSE-S3 でキーの使用を CloudTrail で監査」はできない。キーの監査が要るなら SSE-KMS。
出典：サーバー側の暗号化によるデータの保護（「Amazon S3 マネージドキーによるサーバー側の暗号化 (SSE-S3) は、Amazon S3 のすべてのバケットでのデフォルトの暗号化設定です。」）／SSE−C（「これは、暗号化キーを紛失した場合、オブジェクトも失われることを意味します。」）／S3 バケットキー／クライアント側の暗号化（「Amazon S3 は、すでに暗号化されているオブジェクトを受け取るだけで、オブジェクトの暗号化または復号には関与しません。」）

転送中の暗号化：HTTPS を強制する

S3：HTTP のリクエストを拒否するバケットポリシー
{
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": [
    "arn:aws:s3:::example-bucket",
    "arn:aws:s3:::example-bucket/*"
  ],
  "Condition": {
    "Bool": { "aws:SecureTransport": "false" }
  }
}
ステートメントは Claude が書いた例（バケット名は例）。HTTPS でないリクエストを明示的に拒否する。
場所転送中の暗号化
S3バケットポリシーで aws:SecureTransport を使い HTTPS だけを許可
ALB・CloudFrontACM の証明書で HTTPS のリスナー
RDSSSL/TLS で接続。サーバー証明書を検証すれば相手も確かめられる
EBS暗号化ボリュームなら、ボリュームとインスタンスの間も暗号化
保存時と混同しない：デフォルトの暗号化を SSE-KMS にしても、HTTP の接続は止まらない。
出典：Amazon S3 のセキュリティのベストプラクティス（「HTTPS (TLS) を使用すると、潜在的な攻撃者が中間者攻撃または同様の攻撃を使用してネットワークトラフィックを盗聴または操作することを防止できます。」）／SSL/TLS を使用した接続の暗号化（「SSL/TLS 接続は、クライアントと DB インスタンスまたはクラスターの間を移動するデータを暗号化することによって、1 つのセキュリティ層を提供します。」）

EBS の暗号化

暗号化したボリュームで暗号化されるもの
1ボリューム内の保存データ
2ボリュームとインスタンスの間で移動するデータ
