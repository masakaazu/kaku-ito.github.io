ブロックとファイルのストレージ

EBS ボリュームは AZ に属する

本番の場面：「別の AZ のインスタンスに、このボリュームのデータを移したい」→ スナップショットを取り、その AZ でボリュームを作る。ボリュームを直接ほかの AZ のインスタンスにはアタッチできない。
自動では守られない：AWS は EBS のデータを自動でバックアップしない。スナップショットを定期的に取るか、Data Lifecycle Manager や AWS Backup で自動化する。
出典：Amazon Elastic Block Store とは？（「さらに、ボリュームのデータは、1 つのアベイラビリティーゾーンの複数サーバー間で自動的にレプリケートされ、1 つのコンポーネントに障害が発生したときにデータが失われることを防ぎます。」）／Amazon EBS スナップショット（「スナップショットデータは、リージョン内のすべてのアベイラビリティーゾーンで自動的にレプリケートされます。」「AWS は、EBS ボリュームに保存されているデータを自動的にバックアップしません。」）

ボリュームタイプ：SSD は IOPS、HDD はスループット

タイプ種類向く用途最大 IOPS最大スループットブート
gp3汎用 SSDほとんどの用途・ブート・開発・中規模の DB80,0002,000 MiB/秒できる
gp2汎用 SSD（前の世代）同上。容量でベースラインが決まる16,000250 MiB/秒できる
io2 Block Expressプロビジョンド IOPS SSD重要な DB・1 ミリ秒未満・耐久性 99.999%256,0004,000 MiB/秒できる
st1スループット最適化 HDDEMR・ETL・DWH・ログ処理（大きな順次）500500 MiB/秒できない
sc1Cold HDDアクセスの少ないデータを最も安く250250 MiB/秒できない
読み方：小さな I/O をたくさん（DB・トランザクション）→ SSD。大きなファイルを順に読む（ログ・ETL）→ HDD。HDD はブートボリュームにできない。耐久性は io2 Block Express が 99.999%、ほかは 99.8〜99.9%。
インスタンス側の上限：st1・sc1 のスループットは、ボリュームとインスタンスの上限の小さいほうで決まる。EBS 最適化インスタンスを選ぶのが勧められている。
出典：Amazon EBS ボリュームの種類（「SSD-backed のボリュームは、主要なパフォーマンス属性は IOPS である I/O サイズの小さい頻繁な読み取り/書き込み操作を伴うトランザクションワークロード用に最適化されています。」「HDD-backed のボリュームはパフォーマンスの主要な属性がスループットである大規模なストリーミングワークロード用に最適化されています。」）／Amazon EBS スループット最適化 HDD ボリュームと Cold HDD ボリューム（「ネットワークボトルネックを回避するには、すべての Amazon EBS ボリュームで、EBS 最適化 EC2 インスタンスを選択することをお勧めします。」）

gp3 と gp2：IOPS を容量と切り離す

本番の場面：「IOPS のためだけに gp2 を大きくしている」→ gp3 に変えて、容量は必要な分だけ、IOPS は別に買う。変更は Elastic Volumes で、インスタンスを止めずにできる。グラフの線の形は Claude が描いた模式図。
出典：Amazon EBS 汎用 SSD ボリューム（「gp3 ボリュームは、ストレージの料金に含まれている 3,000 IOPS の一貫したベースライン IOPS パフォーマンスを提供します。」「gp3 ボリュームはバーストパフォーマンスを使用しません。」「ベースライン IOPS パフォーマンスは、最小 100 から最大 16,000 の間で、ボリュームサイズの GiB あたり 3 IOPS のレートで直線的にスケールします。」）

io2 Block Express とマルチアタッチ

io2 Block Express（最高性能）
項目値
最大 IOPS256,000（Nitro）
最大スループット4,000 MiB/秒
最大サイズ64 TiB
レイテンシー16 KiB で平均 500 マイクロ秒未満

ミッションクリティカルな DB など、IOPS・スループット・低レイテンシーのすべてが要るときに選ぶ。
マルチアタッチ（io1・io2 だけ）
同時の書き込みを整えるクラスター対応のファイルシステムやアプリが要る。gp3・gp2・HDD はマルチアタッチできない。
出典：Amazon EBS プロビジョンド IOPS SSD ボリューム（「これらは、IOPS が高く、スループットが大量で、低レイテンシーを必要とする、重要なワークロード向けに設計された、最高パフォーマンスの Amazon EBS ストレージボリュームです。」）／マルチアタッチを使用して EBS ボリュームを複数の EC2 インスタンスへアタッチ（「マルチアタッチが有効なボリュームは、同じアベイラビリティーゾーンにある「Nitro System」に構築された最大 16 のインスタンスにアタッチできます。」）

Elastic Volumes と EBS 暗号化

Elastic Volumes（止めずに変える）
次の変更は、前の変更が終わるまで待つ（ローリング 24 時間で最大 4 回など）。変更は数分〜数時間かかる。
EBS 暗号化（KMS キー）
項目内容
どこで暗号化インスタンスのホストのサーバー
守るもの保存時のデータと、インスタンスとの間の転送中のデータ
自動にするデフォルトでの暗号化を有効にする
キーの変更既存は変えられない。スナップショットのコピーで別のキーにできる
暗号化されていないボリュームを暗号化したい：スナップショットを取り、暗号化を指定してコピーし、そこから新しいボリュームを作る。既存のボリュームをその場で暗号化するのではない。
出典：Elastic Volumes オペレーションを使用して Amazon EBS ボリュームを変更する（「Amazon EBS Elastic Volumes では、EBS ボリュームのボリュームサイズの増加、ボリュームタイプの変更、パフォーマンスの調整を行うことができます。」）／Amazon EBS 暗号化（「既存のスナップショットまたはボリュームに関連付けられている KMS キー を変更することはできません。」「ただし、スナップショットコピーオペレーション中に別の KMS キー を関連付けて、コピーしたスナップショットを新しい KMS キー で暗号化できます。」）

Amazon EFS

Linux 向けのサーバーレスな共有ファイルシステム。マウントターゲット、リージョンと 1 ゾーン、ストレージクラスとライフサイクル、スループットモードとパフォーマンスモード、アクセスポイントとレプリケーション。

AWS SAA #14 ブロックとファイルのストレージタスク 3.1

EFS のしくみ：AZ ごとのマウントターゲット

マウントターゲット：NFSv4 のエンドポイントの IP アドレス。AZ ごとに 1 つ作れ、インスタンスは同じ AZ のマウントターゲットにつながる。EC2・ECS・EKS・Lambda・Fargate から使える。
Windows は不可：Windows の EC2 での EFS の利用はサポートされない。Windows の共有なら FSx for Windows File Server。
出典：Amazon EFS の仕組み（「マウントターゲットは、EFS ファイルシステムをマウントできる NFSv4 エンドポイントの IP アドレスを提供します。」「AWS リージョンのアベイラビリティーゾーンごとに 1 つのマウントターゲットを作成できます。」「Microsoft Windows ベースの Amazon EFS インスタンスでの Amazon EC2 の使用はサポートされていません。」）

EFS の 4 つの設定

設定選べるもの選ぶ合図
ファイルシステムタイプリージョン（推奨・複数の AZ に冗長に保存）／1 ゾーン（1 つの AZ・AWS Backup で自動バックアップ）本番はリージョン。AZ の障害で失ってもよい開発用なら 1 ゾーンで安く
ストレージクラスEFS 標準（SSD）／EFS 低頻度アクセス（四半期に数回）／EFS アーカイブ（年に数回）ライフサイクル管理で、アクセスのない日数に応じて自動で移す
スループットモードエラスティック（推奨・既定）／プロビジョニング／バースト（容量に比例・クレジット）予測できない → エラスティック。容量は小さいが決まった高いスループット → プロビジョニング
パフォーマンスモード汎用（推奨・低レイテンシー）／最大 I/O（前の世代・高い並列性、レイテンシーは高い）ふつうは汎用。最大 I/O は 1 ゾーン・エラスティックでは使えない
ひっかけ：「スループットが足りない」にパフォーマンスモードを答えさせる、「レイテンシーを下げたい」に最大 I/O を答えさせる選択肢に注意。スループット＝スループットモード、レイテンシー＝汎用モード。
出典：Amazon EFS の機能（「新しいファイルシステムデータは、最初に EFS 標準ストレージクラスに書き込まれ、次にライフサイクル管理を使用して EFS 低頻度アクセスストレージクラスおよび EFS アーカイブストレージクラスに階層化できます。」）／Amazon EFS のパフォーマンス仕様（「Amazon EFS には、エラスティック、プロビジョニングされた、バーストの 3 つのスループットモードがあります。」「最大 I/O パフォーマンスモードは、汎用パフォーマンスモードよりもオペレーションごとのレイテンシーが高くなります。」）

EFS のアクセスポイントとレプリケーション

EFS アクセスポイント（アプリごとの入口）
決まった POSIX のユーザーと、別のルートディレクトリを当てはめる。IAM ポリシーで、アプリに決まったアクセスポイントを使わせる。
EFS レプリケーション（別の場所に同期）
レプリケーション設定を作れば、同期は自動で保たれる。災害のときはコピー先に切り替える。
出典：アクセスポイントの使用（「EFS アクセスポイントは、EFS ファイルシステムへのアプリケーション固有のエントリポイントです。」「また、ファイルシステムに対して別のルートディレクトリを適用し、このディレクトリまたはそのサブディレクトリ内のデータに対してのみ、クライアントにアクセスを許可することもできます。」）／EFS ファイルシステムのレプリケート（「レプリケーション設定を作成した後は、Amazon EFS により、ソースファイルシステムとデスティネーションファイルシステムの同期が自動的に維持されます。」）

Amazon FSx

よく使われるファイルシステムを、そのままフルマネージドで。Windows File Server・Lustre・NetApp ONTAP・OpenZFS の 4 つを、プロトコルと用途で見分ける。

FSx の 4 つの種類を見分ける

サービスプロトコル中身と特徴選ぶ合図
FSx for Windows File ServerSMBネイティブの Windows ファイルシステム。Active Directory と連携。シングル AZ／マルチ AZWindows・AD・SMB・NTFS の権限
FSx for LustreLustre（POSIX・Linux）ML・HPC・動画処理など速さが重要な処理。S3 にリンクしてファイルとして見せ、書き戻せる。スクラッチ／永続HPC・機械学習・S3 のデータを高速に

EFS との違い：EFS は AWS 独自のサーバーレスな NFS。FSx は「Windows」「Lustre」「ONTAP」「ZFS」というよく知られたファイルシステムを、その機能のまま使う。問題文にこれらの名前や SMB・iSCSI が出たら FSx。

FSx for Windows File Server とマルチ AZ

移しやすさ：Windows の開発者や管理者が使っているコード・アプリ・ツールを変えずに使える。Windows ソフトウェアの更新、ハードウェアの障害の対応、バックアップは AWS が行う。
マルチ AZ：WSFC で 2 つの AZ に置き、障害やメンテナンスで自動でフェイルオーバーする。本番のほとんどに勧められる。SQL Server の高可用性にはマルチ AZ の CA 共有が要る。
出典：FSx for Windows ファイルサーバーとは？（「Amazon FSx のファイルストレージを使用すると、Windows のデベロッパーや管理者が今日使用しているコード、アプリケーション、およびツールを変更することなく引き続き使用できます。」）／可用性および耐久性:　シングル AZ およびマルチ AZ のファイルシステム（「高い可用性と耐久性モデルを備えたマルチ AZ ファイルシステムは、ほとんどのプロダクションワークロードで使用することをお勧めします。」）

FSx for Lustre：S3 とつないで高速に処理

デプロイデータ向く使い方
スクラッチ複製されない。ファイルサーバーの障害でデータは残らない一時的な保存・短期の処理（結果は S3 へ）
永続複製され、障害のときはファイルサーバーが置き換えられる長期の保存・スループット重視の処理
出典：Amazon FSx for Lustre とは何ですか？（「Simple Storage Service (Amazon S3) バケットにリンクすると、FSx for Lustre ファイルシステムは S3 オブジェクトをファイルとして透過的に表示します。」「スクラッチファイルシステムは、テンポラリストレージと短期間のデータ処理に最適です。」「データはレプリケーションされず、ファイルサーバに障害が発生しても保持されません。」「永続ファイルシステムでは、データがレプリケーションされ、障害が発生した場合はファイルサーバーが置き換えられます。」）

FSx for NetApp ONTAP と FSx for OpenZFS

FSx for NetApp ONTAP（マルチプロトコル）
オンプレミスで ONTAP を使っている会社が、アプリやデータの管理方法を変えずに移す・バックアップする・バーストするのに向く。
FSx for OpenZFS（ZFS・Linux のファイルサーバーから）
アプリのコードやデータの管理方法を変えずに、オンプレミスの ZFS や Linux のファイルサーバーから移すのに向く（英語版のドキュメントによる）。
出典：Amazon FSx for NetApp ONTAP とは何ですか?（「さらに FSx for ONTAP では、データを低コストで伸縮性のあるストレージに自動的に階層化することで、容量のプロビジョニングや管理の必要性を軽減します。」）／What is Amazon FSx for OpenZFS?（「Amazon FSx for OpenZFS is a fully managed file storage service that makes it easy to move data to AWS from on-premises ZFS or other Linux-based file servers.」）
