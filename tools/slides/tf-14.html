import ブロックの手順

# imports.tf import { to = aws_s3_bucket.this # 取りこみ先のアドレス id = "example-bucket" # プロバイダーでの ID } # main.tf resource "aws_s3_bucket" "this" { bucket = "example-bucket" }
id は plan のときに分かる文字列。identity（属性の組）とは同時に書けない。for_each・provider も書ける。
1. 取りこみ先の resource を書く
↓
2. import ブロックを書く
↓
3. terraform plan「1 to import」を確かめる
↓
4. terraform applyステートに入る。import ブロックは履歴として残してよい
resource がないと、次の計画で消そうとする。
出典：Import existing resources／import block reference

terraform state のサブコマンド

コマンド何をするかステート
state listリソースのアドレスを一覧変えない
state show ADDRESS1 つのリソースの属性変えない

state replace-providerプロバイダーのソースを付けかえ変える
ステートを変えるものは必ずバックアップを書き、止められない：『backups for state modification can not be disabled』

mv・rm・push の注意点

$ terraform state mv -dry-run aws_instance.a aws_instance.b $ terraform state mv aws_instance.a aws_instance.b $ terraform state rm aws_instance.web $ terraform state push ./fixed.tfstate $ terraform state replace-provider \ hashicorp/aws registry.acme.corp/acme/aws
-dry-run（mv・rm）：変えずに対象だけ表示。
state mv型は変えられない。チームでは設定の変更との間にだれも変更しないよう連絡
state rm設定が残っていれば次の plan で「新しく作る」
state pushリモートを手で直すときだけ。lineage がちがう・serial が小さいと拒否（-force は危険）
リモートステートでも同じように使える（毎回ネットワークの往復）。
出典：Command: state mv／state rm／state push／state replace-provider

TF_LOG とその仲間

$ export TF_LOG=TRACE $ export TF_LOG_PATH=./terraform.log # 追記 $ terraform apply $ export TF_LOG_PROVIDER=DEBUG # プロバイダーだけ $ unset TF_LOG # または TF_LOG=off
くわしい ← TRACE・DEBUG・INFO・WARN・ERROR → くわしくないJSON：TRACE 以上を JSON で（安定した形式ではない）
変数役割
TF_LOG有効にする。出力は stderr。どんな値でも有効
TF_LOG_PATHファイルに追記（TF_LOG も必要）
TF_LOG_CORETerraform 本体だけ
TF_LOG_PROVIDERプロバイダーのプラグインだけ
『even when TF_LOG_PATH is set, TF_LOG must be set』
使う場面：予期しない動きのデバッグ、バグ報告。ログに機密が入りうる。
