ポリシーの書き方

どこに付けるか（ID か、リソースか）と、許可を与えるか（上限だけか）で種類を分ける。

AWS SAA #01 IAMとポリシータスク 1.1

ポリシーの種類：許可を「与える」ものと「上限を決める」もの

種類付ける先許可を与えるかポイント
ID ベースのポリシーユーザー・グループ・ロール与える管理ポリシー（AWS 管理・カスタマー管理）とインライン。Principal は書かない
リソースベースのポリシーS3 バケット・SQS キュー・KMS キー・ロール（信頼ポリシー）など与えるインラインだけ。Principal に相手を書く。別アカウントも指定できる
VPC エンドポイントポリシーVPC エンドポイント追加の境界付けないと、フルアクセスを許すデフォルトのポリシーが付く
アクセス許可の境界ユーザー・ロール与えないID ベースのポリシーの上限。リソースベースのポリシーの許可は絞らない
SCP（#02）組織・OU・アカウント与えないアカウントの中のユーザーとロールの上限（メンバーのルートも）
RCP（#02）組織・OU・アカウント与えないアカウントの中のリソースの上限
ACLS3・VPC など与えるJSON でない唯一の種類。別アカウントにだけ使える

ポリシーの JSON を読む

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadOwnFolder",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::example-bucket/home/${aws:username}/*",
      "Condition": {
        "Bool": { "aws:SecureTransport": "true" }
      }
    }
  ]
}
Claude が作った例。ユーザーが自分のフォルダだけを、HTTPS のときだけ読み書きできる。
要素意味
Version2012-10-17 を使う（変数もこの版から）
Statement1つ以上。複数あれば OR でまとめて評価
EffectAllow か Deny
Action操作。NotAction は「これ以外すべて」（拒否ではない）
Resource対象の ARN。ID ベースでは必須
Principal相手。リソースベースで使う。ID ベースには書けない
Condition効く条件。true のときだけそのステートメントが効く
ARN の形：arn:aws:サービス:リージョン:アカウント:リソース。IAM はリージョンが空、S3 バケットはリージョンもアカウントも空。
出典：ポリシーとアクセス許可（JSON ポリシードキュメント構造）／NotAction／ポリシー変数／ARN

Condition でよく使う条件キー

条件キー比べるもの本番での使いどころ
aws:SourceIpリクエスト元の IP アドレス（パブリック IP だけ）社内の IP からだけ許可。VPC エンドポイント経由のリクエストには含まれない
aws:SourceVpceリクエストが通った VPC エンドポイントの IDS3 バケットを「この VPC エンドポイント経由だけ」にする
aws:RequestedRegion呼び出されたリージョン使えるリージョンを限る
aws:MultiFactorAuthPresent一時的な認証情報を MFA で確かめたか大事な操作は MFA のときだけ。アクセスキーで署名したリクエストには含まれない
aws:SecureTransportTLS で送られたか（true／false）false を Deny して HTTPS を強制
aws:PrincipalOrgIDプリンシパルが属する組織の IDバケットを自分の組織のアカウントだけに開く（#02）
sts:ExternalIdロールを引き受けるときに渡された外部 ID第三者に委任するロールの信頼ポリシー（第3章）
キーの名前は大文字・小文字を区別しない（aws:SourceIP と AWS:SourceIp は同じ）。aws: で始まるのがどのサービスでも使えるグローバル条件キー。
出典：AWS グローバル条件コンテキストキー（各キーの説明と「可用性」）／IAM JSON ポリシー要素Condition
第3章

許可の決まり方と絞り込み

最初はすべて拒否。Allow で開き、明示的な Deny はどこにあっても勝つ。

AWS SAA #01 IAMとポリシータスク 1.1

1つのアカウントの中での判定の流れ

暗黙的な拒否：ルートユーザー以外のリクエストは、最初はすべて拒否されている。Allow があって初めて開く。
明示的な拒否：どの種類のポリシーにあっても、ほかの Allow より強い。ポリシーの順番や範囲の広さは関係ない。
出典：エンフォースメントコードロジックがリクエストを評価してアクセスを許可または拒否する方法（「明示的な拒否は明示的な許可をオーバーライドします。」）

アクセス許可の境界：共通部分だけが使える

ポイント中身
付ける先ユーザーかロール（グループには付かない）
何で設定するか管理ポリシー（AWS 管理かカスタマー管理）
権限を与えるか与えない（上限だけ）
リソースベースのポリシーの許可境界では絞られない
代表的な使い方＝管理の委任：開発者に「ロールを作ってよい。ただし、この境界を付けたものだけ」と任せる。開発者が強いポリシーを付けても、境界を超えられない。
似たもの：SCP はアカウント全体の上限（#02）、セッションポリシーはそのセッションだけの上限。
出典：IAM エンティティのアクセス許可境界（「アイデンティティベースのポリシーとそのアクセス許可の境界の両方で許可されているアクションのみを実行できます。」）／ベストプラクティス（アクセス許可の境界を使用して、アカウント内のアクセス許可の管理を委任する）

別のアカウントのリソースを使わせる2つの方法

方法しくみちがい
① ロールB にロールを作り、信頼ポリシーで A を許可。A 側では sts:AssumeRole を許可引き受けている間は、元の権限は使えない（ロールの権限になる）
② リソースベースS3・SNS・SQS などのリソースのポリシーで A を許可。A 側では ID ベースのポリシーでそのリソースを許可元の権限のまま使える。対応しているサービスだけ
どちらも「両側の許可」が要る。リソース側のポリシーに相手を書くだけでは信頼関係の半分。
出典：クロスアカウントポリシーの評価論理／ポリシーとアクセス許可（「信頼関係は半分しか確立されない」）／IAM ロール（委任・クロスアカウントアクセスのロール）

委任の落とし穴をふさぐ：外部 ID と PassRole

外部 ID（混乱した代理問題の対策）
外部の会社が顧客ごとに一意の値を決め、顧客は信頼ポリシーの条件 sts:ExternalId でその値を要求する。値は Claude が作った例。
iam:PassRole
場面要る許可
EC2 を起動して既存のロールを付けるec2:RunInstances ＋ そのロールへの iam:PassRole
Lambda 関数に実行ロールを設定するそのロールへの iam:PassRole
自分でロールを引き受けるsts:AssumeRole（PassRole とは別）
なぜ要るか：自分の権限は弱くても、強いロールをサービスに付ければ、そのサービス経由で強い操作ができてしまう。渡してよいロールを PassRole で限る。
PassRole で渡せるのは同じアカウントのサービスだけ。
出典：混乱する代理問題（「ロールの信頼ポリシーに `ExternalId` の条件の確認を含めることを必須とする」）／AWS サービスにロールを渡すアクセス許可をユーザーに付与する

最小権限と点検の道具

道具分かること・できることこう聞かれたら
IAM Access Analyzer（外部アクセス）リソースベースのポリシーを分析し、外部（別アカウント・組織の外）と共有されている S3 バケットや IAM ロールを見つける「意図せず公開・共有されたリソースを探す」
IAM Access Analyzer（未使用のアクセス）使われていない権限を見つける「余分な権限を洗い出す」
IAM Access Analyzer（ポリシーの生成・検証）CloudTrail のアクセスの記録から、実際に使った操作だけのポリシーを作る／ポリシーを文法とベストプラクティスで確かめる「実際の利用に合わせて最小権限のポリシーを作る」
最終アクセス情報ユーザー・グループ・ロール・ポリシーが、各サービスに最後にアクセスした日時（アクセスアドバイザー）「使っていないサービスの権限を外す」
認証情報レポート全ユーザーのパスワード・アクセスキー・MFA 機器などの状態の一覧「MFA なしのユーザー、古いアクセスキーを一覧に」
最小権限：タスクに必要な権限だけを、決まったリソースと条件で与える。広めに始めて、使われ方を見て絞るのが AWS の進め方。
出典：IAM Access Analyzer の使用／認証情報レポート／ベストプラクティス（最小特権アクセス許可を適用する・未使用の…を定期的に確認して削除する）
