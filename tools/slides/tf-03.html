第1章

ステートの役割

設定と現実をつなぐ台帳。

Terraform #03 ステートのしくみ目標 2d

ステートは設定と実物の対応表『a necessary requirement for Terraform to function』

設定（.tf）resource "aws_instance" "foo"
↕ ステート（terraform.tfstate）が対応づける
実物（AWS）インスタンス ID i-abcd1234
『The primary purpose of Terraform state is to store bindings between objects in a remote system and resource instances declared in your configuration.』
なぜタグではだめ？答え
初期の試作ステートなしで AWS のタグを使っていた
問題タグに対応しないリソース・クラウドがある
結論Terraform 独自のステートで対応づける
1 つの実物は 1 つのリソースインスタンスだけに。import で 2 か所に取りこむと、対応があいまいになる。
出典：State／Purpose of Terraform State（Mapping to the Real World）

ステートの 4 つの目的

目的中身ないとどうなるか
対応づけ設定のインスタンス ⇔ 実物の IDどれを変える・消すのか分からない
メタデータ最新の依存関係・最後に使ったプロバイダー設定（alias）設定から消したリソースを消す順番が分からない
性能全リソースの属性のキャッシュ（『the most optional feature』）大きな環境で -refresh=false が使えない
同期チームで同じステート → リモートステート＋ロック各自が別のステートで、同時に実行してしまう
大きな環境：API は 1 件ずつで数百ミリ秒・回数制限もある → 『-refresh=false … -target』を使い、キャッシュしたステートを正とみなす。
出典：Purpose of Terraform State（Metadata／Performance／Syncing）

refresh：ステートを実物に合わせる

実物を読むプロバイダーが API で今の設定を取る
↓
ステートを更新実物は変えない。ステートだけを変える
↓
設定と比べて計画作る・変える・消す
『Prior to any operation, Terraform does a refresh to update the state with the real infrastructure.』
書き方扱い
plan・apply自動で refresh する（ふつうはこれで足りる）
terraform refresh非推奨。確認なしでステートを書きかえる
apply -refresh-only変化を見てから承認できる（#13）
出典：State／Command: refresh
第2章

ステートの中身と見方

JSON だけど、手では書かない。

Terraform #03 ステートのしくみ目標 2d

ステートファイルの中身

{ "version": 4, "terraform_version": "1.12.0", "serial": 7, # 書くたびに増える "lineage": "3f1c…", # 作ったときの一意な ID "outputs": { … }, "resources": [{ "type": "aws_instance", "name": "foo", "provider": "provider[\"registry.terraform.io/hashicorp/aws\"]", "instances": [{ "attributes": { "id": "i-abcd1234", … }, "dependencies": [ "aws_subnet.a" ] }] }] }
『direct file editing of the state is discouraged』→ terraform state コマンドで。
形式は版で変わりうる。外部のソフトには show -json・output -json の出力を渡す。
state push は、lineage がちがう・行き先の serial が大きいと止まる（-force で押し切る前に state pull でバックアップ）。
出典：State（Inspection and Modification／Format）／State Storage and Locking（Manual State Pull/Push）

ステートを読むコマンド

コマンド何が出るか注意
terraform show最新のステート（プランファイルを渡せばその計画）を人向けに-json では sensitive も平文
terraform state listリソースのアドレスの一覧（ルート → モジュールの順）パターンで絞りこめる
terraform state show ADDR1 つのリソースのくわしい属性アドレスは state list で調べる
terraform output -jsonルートモジュールの出力値自動化で apply の直後に保存
terraform state pullステートをそのまま標準出力に（jq と組み合わせ）反対の push はとても危険
plan・apply 以外でステートを変えると『lose track of managed resources』。変える前にバックアップ。
出典：Command: show／Command: state list／Inspect Terraform State／Command: state pull／Update Terraform state manually overview
第3章

守る・共有する

秘密が入る。だからリモートとロック。

Terraform #03 ステートのしくみ目標 2d

ステートには秘密が入る

variable "db_password" { type = string sensitive = true # 表示は隠れる } resource "aws_db_instance" "main" { password = var.db_password } # → ステートには平文で残る
sensitive は『redacts those values from CLI output』だけ。ステートに残さないのは ephemeral・write-only（#10）。
Store your state remotelyリモートに置く
Encrypt your state at restHCP Terraform・S3（encrypt）・GCS
Use access controls見られる人を限る
Use audit logsだれが見たかを残す
ローカルでは平文のファイル → Git に入れない。
出典：Manage sensitive data（Background／State security best practices）

リモートステートとロック

ローカル（既定）リモート
terraform.tfstate（local バックエンド）HCP Terraform・S3・Azure Blob・GCS・Consul …
最新か・同時に動かしていないかを各自が確認全員で共有。出力値をほかの設定へ読み取り専用で
ディスクに残る失敗したとき以外ディスクに残さない
リモートでも console・state・taint などはローカルと同じように動く。
ステートのロック書きこむおそれのある操作で自動。メッセージは出ない
ロックに失敗したら『Terraform does not continue』。対応しないバックエンドもある。
HCP Terraform は操作を中央のキューに並べ、承認待ちの計画があるのに新しい計画を作ろうとしたことも見つける。
local バックエンドも、システムの API でロックする。
出典：Remote State／State Storage and Locking／State Locking／Backend Type: local
