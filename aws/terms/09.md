## 09-1 ロードバランサーの種類

### まとめ表

| 項目 | ALB | NLB | GWLB |
| :-: | :-: | :-: | :-: |
| 層 | 第 7 層（HTTP/HTTPS） | 第 4 層（TCP・UDP・TLS） | 第 3 層（GENEVE、ポート 6081） |
| 振り分けの決め手 | パス・ホスト・ヘッダー・メソッド・クエリ・送信元 IP | フローハッシュ（接続ごと） | 仮想アプライアンスへ透過的に |
| 固定の IP | なし（DNS 名で使う） | AZ ごとに 1 つ。Elastic IP を付けられる | — |
| クロスゾーン負荷分散 | 常に有効 | デフォルトで無効 | デフォルトで無効 |
| 向く場面 | Web・API・マイクロサービス・コンテナ | 超大量・低レイテンシー・固定 IP・TCP/UDP | ファイアウォールや IDS/IPS を挟む |

### ELB の種類

#### Elastic Load Balancing（いらすてぃっくろーどばらんしんぐ / ELB）

- 意味：受け取ったトラフィックを、複数の AZ の複数のターゲット（EC2・コンテナ・IP アドレスなど）に自動で分けるサービス
- ポイント：ヘルスチェックで正常なターゲットにだけ送る。トラフィックに合わせてロードバランサー自体も自動でスケールする。種類は ALB・NLB・GWLB・CLB（前世代）
- 語の意味：Elastic＝伸び縮みする、Load＝負荷、Balancing＝釣り合わせること

#### Application Load Balancer（あぷりけーしょんろーどばらんさー / ALB）

- 意味：OSI の第 7 層（アプリケーション層、HTTP/HTTPS）で動き、リクエストの中身でターゲットグループを選ぶロードバランサー
- ポイント：パス・ホスト・HTTP ヘッダー・メソッド・クエリ・送信元 IP で振り分けられる。ターゲットは EC2・IP・Lambda。AWS WAF・ユーザー認証（Cognito・OIDC）・リダイレクト・固定レスポンスも使える。少なくとも 2 つの AZ が要る
- 例：`/api/*` を API のターゲットグループ、`/*` を Web のターゲットグループへ

#### Network Load Balancer（ねっとわーくろーどばらんさー / NLB）

- 意味：OSI の第 4 層（TCP・UDP・TLS）で動き、1 秒あたり数百万のリクエストを処理できるロードバランサー
- ポイント：AZ ごとに固定の IP アドレスを 1 つ持ち、インターネット向けならサブネットごとに Elastic IP を付けられる。「固定 IP」「UDP」「超低レイテンシー」「HTTP 以外のプロトコル」なら NLB。ALB をターゲットにして（ターゲットタイプ alb）、固定 IP と ALB の機能を組み合わせることもできる
- 例：取引先がファイアウォールで許可する固定 IP を NLB の Elastic IP で用意する

#### Gateway Load Balancer（げーとうぇいろーどばらんさー / GWLB）

- 意味：ファイアウォール・侵入検知と防止（IDS/IPS）・ディープパケットインスペクションなどの仮想アプライアンスを、透過的に挟み込み、スケールさせるロードバランサー
- ポイント：第 3 層で動き、アプライアンスとは GENEVE（ポート 6081）でやりとりする。利用する側の VPC には Gateway Load Balancer エンドポイントを置き、ルートテーブルでトラフィックを通す。「サードパーティのファイアウォールをまとめて通す」なら GWLB
- 例：全 VPC の出入りの通信を、セキュリティ VPC のファイアウォール群に通す

#### Classic Load Balancer（くらしっくろーどばらんさー / CLB）

- 意味：Elastic Load Balancing の前世代のロードバランサー
- ポイント：新しく作るなら ALB か NLB。パスやホストでの振り分けなどの新しい機能はない。古い構成の移行先を問われたら、HTTP なら ALB、TCP なら NLB
- 例：EC2-Classic 時代からの CLB を ALB に移す

#### ロードバランサーのスキーム（すきーむ / scheme）

- 意味：ロードバランサーをインターネット向けにするか、内部向けにするかの選択。作るときに決める
- ポイント：インターネット向けはノードにパブリック IP があり、DNS 名がパブリックに解決される。内部向けはプライベート IP だけで、VPC の中（やつながったネットワーク）からだけ使える。多層アーキテクチャでは、Web 層の前はインターネット向け、アプリ層の前は内部向け
- 例：インターネット向け ALB → Web 層 → 内部 ALB → アプリ層

#### クロスゾーン負荷分散（くろすぞーんふかぶんさん / cross-zone load balancing）

- 意味：各 AZ のロードバランサーのノードが、有効なすべての AZ のターゲットに分けること。無効だと、自分の AZ のターゲットにだけ分ける
- ポイント：ALB は常に有効。NLB と GWLB はデフォルトで無効なので、AZ ごとのターゲット数がばらつくと、少ない AZ のターゲットに負荷が偏る。有効にすれば全ターゲットに均等
- 例：AZ a に 2 台、AZ b に 8 台。無効なら a の 2 台が全体の半分を受け持つ（Claude が作った例）

## 09-2 ALB と NLB の設定

### まとめ表

| 困りごと | 設定 |
| :-: | :-: |
| ホスト名やパスで別のアプリへ | リスナールール（ホスト・パスの条件） |
| 縮小時に処理中のリクエストが切れる | 登録解除の遅延（デフォルト 300 秒） |
| サーバーのメモリにセッションを持つ古いアプリ | スティッキーセッション（Cookie） |
| 処理時間がまちまちで一部に偏る | 最小の未処理のリクエスト |
| 追加したばかりのサーバーに一気に来る | スロースタートモード |
| アプリのログにクライアントの IP が出ない | X-Forwarded-For ヘッダー |
| アプリを変えずにログイン画面を付ける | ALB のユーザー認証（Cognito・OIDC） |

### 振り分けとターゲット

#### リスナー（りすなー / listener）

- 意味：決めたプロトコルとポートで接続を待ち受け、ルールに従ってターゲットグループに送る、ロードバランサーの入口
- ポイント：ALB は HTTP・HTTPS、NLB は TCP・UDP・TLS など。HTTPS のリスナーには証明書が要る。HTTP（80）のリスナーで HTTPS（443）へのリダイレクトを返すのが定番
- 例：443 の HTTPS リスナーと、80 → 443 にリダイレクトする HTTP リスナー

#### リスナールール（りすなーるーる / listener rules）

- 意味：ALB のリスナーで、条件（パス・ホスト・HTTP ヘッダー・メソッド・クエリ・送信元 IP）に合ったリクエストに、どのアクションを取るか決めるルール
- ポイント：アクションは転送（forward）・リダイレクト・固定レスポンス・ユーザー認証（authenticate-cognito・authenticate-oidc）。優先順位の高いルールから順に評価する。1 つの ALB で複数のサービスを振り分けられる
- 例：ホストが `api.example.com` なら API のターゲットグループへ

#### ターゲットグループ（たーげっとぐるーぷ / target group）

- 意味：ロードバランサーが送る先（ターゲット）をまとめたもの。ヘルスチェックや振り分けの設定もここで決める
- ポイント：ターゲットタイプは instance・ip・lambda（ALB）、alb（NLB）。作ったあとで変えられない。ip なら、ピアリングした VPC や、Direct Connect・Site-to-Site VPN でつながったオンプレミスのサーバーもターゲットにできる。Fargate のタスクは ip
- 例：オンプレミスの 10.10.0.0/16 のサーバーを ip ターゲットとして ALB の後ろに置く

#### ヘルスチェック（ELB）（へるすちぇっく / health checks）

- 意味：ロードバランサーがターゲットに定期的にリクエストを送り、正常なターゲットにだけトラフィックを送るための確認
- ポイント：プロトコル・ポート・パス・間隔・しきい値を決める。登録後は 1 回のヘルスチェックに合格すると正常になる。全ターゲットが異常になると、ロードバランサーは全ターゲットに送る（フェイルオープン）
- 例：`/health` に HTTP で 30 秒ごとに確認する

#### 登録解除の遅延（とうろくかいじょのちえん / deregistration delay）

- 意味：ターゲットを外すとき、処理中のリクエストが終わるのを待つ時間。デフォルト 300 秒
- ポイント：この間は新しいリクエストを送らず、状態は draining になる。処理中のリクエストやつながっている接続がなければすぐに外れる。スケールインやデプロイで処理中のリクエストが切れるなら、処理時間に合わせて調整する。昔の CLB の Connection Draining にあたる
- 例：最長 2 分かかる処理があるので 150 秒にする

#### スティッキーセッション（すてぃっきーせっしょん / sticky sessions）

- 意味：同じクライアントからのリクエストを、Cookie を使って同じターゲットに送り続ける設定
- ポイント：期間ベース（ロードバランサーが作る Cookie）とアプリケーションベース（アプリの Cookie に合わせる）がある。クライアントが Cookie に対応している必要がある。負荷が偏り、そのターゲットが落ちるとセッションが消えるので、本来はセッションを DynamoDB・ElastiCache に置いてステートレスにするのがよい
- 例：コードを変えられない古いアプリで、ログイン状態を保つ

#### ルーティングアルゴリズム（るーてぃんぐあるごりずむ / routing algorithm）

- 意味：ALB のターゲットグループで、どのターゲットに次のリクエストを送るかの決め方。ラウンドロビン（デフォルト）・最小の未処理のリクエスト・加重ランダム
- ポイント：ラウンドロビン＝順番に均等。最小の未処理のリクエスト＝処理中のリクエストが最も少ないターゲットへ（処理時間がまちまちなとき）。加重ランダム＝ランダムな順で均等に。スロースタートモードは、追加したターゲットへのリクエストを直線的に増やす（最小の未処理のリクエスト・加重ランダムとは一緒に使えない）
- 例：重いレポートと軽い参照が混ざる API で、最小の未処理のリクエストにする

### HTTPS・ヘッダー・認証

#### HTTPS リスナーと TLS 終端（てぃーえるえすしゅうたん / HTTPS listener and TLS termination）

- 意味：ロードバランサーがサーバー証明書でクライアントとの TLS を終わらせ、復号してからターゲットに送ること
- ポイント：証明書は ACM で無料で用意でき、自動更新される。暗号化・復号の負荷をターゲットから外せる（オフロード）。複数の証明書を付けて、SNI でドメインごとに使い分けられる。ターゲットまで暗号化が要るなら、ターゲットへも HTTPS で送る
- 例：`www.example.com` と `shop.example.com` の証明書を 1 つの ALB に付ける

#### X-Forwarded-For（えっくすふぉわーでっどふぉー / X-Forwarded-For）

- 意味：HTTP/HTTPS のロードバランサーが、元のクライアントの IP アドレスを入れてターゲットに渡すリクエストヘッダー
- ポイント：ALB を通すと、ターゲットから見た送信元はロードバランサーの IP になる。アプリのアクセスログでクライアントの IP を知りたいならこのヘッダーを見る。ほかに X-Forwarded-Proto（元のプロトコル）・X-Forwarded-Port（元のポート）もある
- 例：Web サーバーのログの形式に X-Forwarded-For を足す

#### ALB のユーザー認証（ゆーざーにんしょう / authenticate users）

- 意味：ALB のリスナールールで、ターゲットに送る前にユーザーをログインさせる機能（authenticate-oidc・authenticate-cognito）
- ポイント：OIDC に準拠した IdP や、Cognito のユーザープール（Google などのソーシャル、SAML の企業の ID）で認証できる。アプリのコードを変えずにログインを付けられる
- 例：社内ツールの前で、社員の IdP のログインを求める

#### NLB の固定 IP（こていあいぴー / static IP and Elastic IP）

- 意味：NLB が AZ ごとに持つ固定の IP アドレス。インターネット向けなら、サブネットごとに Elastic IP を付けられる
- ポイント：ALB の IP は変わるので、相手のファイアウォールに IP を登録してもらう必要があるなら NLB。HTTP の振り分けもしたいなら、NLB のターゲットに ALB を登録する。世界中から固定の IP で入るなら Global Accelerator（#19）
- 例：2 つの AZ の NLB に Elastic IP を 2 つ付け、取引先に伝える

## 09-3 EC2 Auto Scaling

### まとめ表

| スケーリングの方法 | 決め方 | 向く場面 |
| :-: | :-: | :-: |
| ターゲット追跡 | メトリクスと目標値だけ（サーモスタットのように） | ふつうはまずこれ（CPU 50% を保つ） |
| ステップ | CloudWatch アラームのしきい値ごとに増減する数 | 超えた量に応じて大きく動かしたい |
| シンプル | アラーム 1 つで決めた数。クールダウンを待つ | AWS はステップか追跡を勧める |
| スケジュール | 日時（cron）で最小・希望・最大を変える | 予定が分かっている山（年度末・セール） |
| 予測 | 過去の日次・週次のパターンから前もって増やす | 毎日・毎週くり返す山 |

### グループと起動

#### 水平スケーリングと垂直スケーリング（すいへい・すいちょくすけーりんぐ / horizontal and vertical scaling）

- 意味：水平＝台数を増減する（スケールアウト・スケールイン）。垂直＝1 台を大きく・小さくする（スケールアップ・スケールダウン）
- ポイント：水平は上限が高く、1 台が落ちても残りで続けられ、自動で増減しやすい（Auto Scaling）。垂直は手軽だが、大きさに上限があり、変えるときに止まることが多い。水平にするにはステートレスに作る
- 例：EC2 を 2 台 → 10 台にする（水平）／m7i.large → m7i.4xlarge にする（垂直）

#### Amazon EC2 Auto Scaling（おーとすけーりんぐ / Amazon EC2 Auto Scaling）

- 意味：EC2 インスタンスの数を、決めた条件に合わせて自動で増減し、異常なインスタンスを置き換えるサービス
- ポイント：負荷に合わせて増減（弾力性）するだけでなく、台数を固定にしていても、落ちたインスタンスを置き換えて数を保つ（耐障害性）。ELB と組み合わせると、増えたインスタンスは自動でターゲットに登録され、減らしたものは外される
- 例：最小 2・最大 10 で、2 つの AZ に分けて Web サーバーを動かす

#### Auto Scaling グループ（おーとすけーりんぐぐるーぷ / Auto Scaling group）

- 意味：同じ設定の EC2 インスタンスをまとめて、数を管理する単位。最小・希望するキャパシティ・最大を決める
- ポイント：最小より減らず、最大より増えない。スケーリングポリシーは最小と最大のあいだで希望するキャパシティを変える。複数の AZ のサブネットを指定すると、AZ のあいだでバランスを保つ
- 例：最小 4・希望 6・最大 12

#### 起動テンプレート（きどうてんぷれーと / launch template）

- 意味：Auto Scaling グループが起動するインスタンスの設定（AMI・インスタンスタイプ・キーペア・セキュリティグループ・ユーザーデータなど）
- ポイント：起動設定と似ているが、複数のバージョンを持てる。複数のインスタンスタイプやスポットの組み合わせなどの新しい機能は起動テンプレートで使う。AMI を変えるなら新しいバージョンを作り、インスタンスの更新で入れ替える
- 例：`web-template` のバージョン 7 で新しい AMI を指定する

#### ヘルスチェックと猶予期間（Auto Scaling）（へるすちぇっくとゆうよきかん / health checks and grace period）

- 意味：Auto Scaling グループが、インスタンスが正常かを確かめ、異常なら置き換えるしくみ。猶予期間は、起動直後の確認を待つ時間
- ポイント：デフォルトは EC2 のステータスチェック（インスタンスが動いているか）だけ。アプリが固まっても気付けないので、ELB のヘルスチェックを有効にすると、ロードバランサーが異常と判断したインスタンスも置き換える。起動に時間がかかると、準備中に異常とされて終了されるので、猶予期間を延ばす（コンソールのデフォルト 300 秒）
- 例：ELB のヘルスチェックを有効にし、猶予期間を 600 秒にする

### スケーリングポリシー

#### ターゲット追跡スケーリング（たーげっとついせきすけーりんぐ / target tracking scaling）

- 意味：メトリクスと目標値を決めると、その値に近づくようにインスタンス数を自動で増減するスケーリングポリシー
- ポイント：サーモスタットが温度を保つのと同じ考え方。CloudWatch アラームは自動で作られる。CPU の平均使用率・ネットワーク・ALB のターゲットあたりのリクエスト数などを使う。まず考えるべき方法
- 例：CPU の平均使用率 50% を目標にする

#### ステップスケーリングとシンプルスケーリング（すてっぷ・しんぷるすけーりんぐ / step and simple scaling）

- 意味：CloudWatch アラームのしきい値を超えたときに、決めた数だけ増減するスケーリングポリシー。ステップはしきい値の超え方に応じて段階的に、シンプルは 1 つの調整だけ
- ポイント：シンプルスケーリングは、1 回動くとクールダウンの期間が終わるまで次の調整を待つ。AWS はシンプルスケーリングとクールダウンを使わないことを勧めている（ターゲット追跡かステップ）
- 例：CPU 60〜80% で +1、80% 以上で +3（ステップ）

#### スケジュールされたスケーリング（すけじゅーるされたすけーりんぐ / scheduled scaling）

- 意味：決めた日時に、グループの希望するキャパシティ・最小・最大を設定するスケーリング
- ポイント：負荷の変化が予測できる（日時が分かっている）ときに使う。くり返しは cron 式とタイムゾーンで書く。毎朝の始業や、決まった日のセールの前に増やす
- 例：毎週月曜 8:30 に最小を 10 にし、19:00 に 2 に戻す

#### 予測スケーリング（よそくすけーりんぐ / predictive scaling）

- 意味：過去の負荷のデータから日次・週次のパターンを見つけ、将来の需要を予測して前もってキャパシティを増やすスケーリング
- ポイント：営業時間は高く夜や週末は低い、など周期のある負荷に向く。起動に時間がかかるアプリでも、山の前に準備できる。負荷に反応してから増やす動的スケーリング（ターゲット追跡など）より早く動ける。スケジュールは人が日時を決め、予測は AWS が過去から学ぶ
- 例：毎朝 9 時の山の 10 分前に自動で台数を増やす

#### ウォームアップとクールダウン（うぉーむあっぷ・くーるだうん / instance warmup and cooldown）

- 意味：ウォームアップ＝新しいインスタンスが使えるようになり、メトリクスに反映されるまで待つ時間。クールダウン＝シンプルスケーリングで、1 回の調整のあと次の調整を待つ時間
- ポイント：起動したばかりのインスタンスの値で判断すると、増やしすぎたり減らしすぎたりする。ターゲット追跡とステップではデフォルトのインスタンスウォームアップを設定する
- 例：アプリの起動に 3 分かかるので、ウォームアップを 180 秒にする

### 運用

#### ライフサイクルフック（らいふさいくるふっく / lifecycle hooks）

- 意味：インスタンスの起動時や終了時に、次の状態に移る前に待機させ、そのあいだに処理をはさむしくみ。待つ時間のデフォルトは 1 時間
- ポイント：起動時＝ソフトのインストールや設定を終えてからトラフィックを受ける。終了時＝ログやデータを退避してから終わる。EventBridge で通知し、Lambda を呼んだり、インスタンスに入って作業したりできる
- 例：スケールインのとき、終了前にアプリのログを S3 に送る

#### ウォームプール（うぉーむぷーる / warm pools）

- 意味：前もって初期化（起動とセットアップ）を済ませたインスタンスを、停止などの状態で待たせておき、スケールアウトのときにすぐ使うしくみ
- ポイント：大量のデータを書き込むなど、起動に非常に時間がかかるアプリのレイテンシーを下げる。常に余分に動かしておく（過剰なプロビジョニング）必要がなくなる。要らないときに作るとコストがかかる
- 例：起動に 20 分かかるアプリのインスタンスを、停止状態で 5 台待たせる

#### 終了ポリシー（しゅうりょうぽりしー / termination policies）

- 意味：スケールインのとき、どのインスタンスを先に終了するかの決め方
- ポイント：まず AZ のあいだのバランスを保つことが優先で、多い AZ から減らす。デフォルトは、古い設定（起動設定・古い起動テンプレートのバージョン）のインスタンスを先に終了するように作られている
- 例：AZ a に 3 台、AZ b に 2 台なら、a から 1 台減らす

#### 複数のインスタンスタイプと購入オプション（ふくすうのいんすたんすたいぷ / mixed instances groups）

- 意味：1 つの Auto Scaling グループで、複数のインスタンスタイプと、オンデマンドとスポットを組み合わせて起動する設定
- ポイント：スポットで安くしつつ、最低限の台数はオンデマンドで確保する。複数のタイプを指定すると、スポットのキャパシティを確保しやすい。キャパシティのリバランスで、中断されそうなスポットを前もって置き換えられる
- 例：オンデマンドを最低 2 台、それ以上は 70% をスポットにし、m7i・m6i・m7a から選ぶ

#### インスタンスの更新（いんすたんすのこうしん / instance refresh）

- 意味：Auto Scaling グループのインスタンスを、新しい起動テンプレートのバージョン（新しい AMI など）で順に置き換える機能
- ポイント：インスタンスやルートボリュームを置き換える必要がある設定変更で、特にインスタンスが多いときに便利。最小正常率と最大正常率に基づき、バッチごとに少しずつ入れ替える
- 例：パッチを当てた新しい AMI に、全 20 台を順に入れ替える

#### 問 aws-09-o11

- 問：ALB のターゲットグループのすべてのターゲットが、同時にヘルスチェックに失敗した。このとき ALB はどう動くか。
- ア：どのターゲットにもリクエストを送らず、すべて 503 を返す
- イ：別のリージョンのロードバランサーに自動で切り替える
- ウ：ターゲットを自動で再起動する
- エ：ヘルスステータスにかかわらず、すべてのターゲットにリクエストを送る
- 正解：エ
- 解説：ターゲットグループに異常なターゲットしかない場合、ロードバランサーは全ターゲットにリクエストを送る（フェイルオープン）。ヘルスチェックの設定ミスで全滅したときに、サービス全体が止まらないためのしくみ。
- アの意味：全ターゲットが異常のときは送らないのではなく、全ターゲットに送る。
- イの意味：ALB はリージョンの中のサービスで、別のリージョンへの切り替えは Route 53 などで行う。
- ウの意味：ALB はターゲットを再起動しない。置き換えるのは Auto Scaling。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「Application Load Balancer ターゲットグループのヘルスチェック」（『ターゲットグループに異常な登録済みターゲットのみが含まれている場合、そのヘルスステータスにかかわらず、ロードバランサーはそれらすべてのターゲットにリクエストをルーティングします。』『つまり、有効なすべてのアベイラビリティーゾーン内で、すべてのターゲットが同時にヘルスチェックに失敗すると、ロードバランサーはオープンに失敗します。』））
