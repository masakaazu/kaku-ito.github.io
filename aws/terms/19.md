## 19-1 CloudFront のしくみとキャッシュ

### まとめ表

| 項目 | CloudFront | Global Accelerator |
| :-: | :-: | :-: |
| 何をするか | エッジロケーションでウェブコンテンツをキャッシュして配信 | エッジから AWS のネットワークで最適なエンドポイントに通信を送る |
| 受けるもの | ウェブのリクエスト（静的・動的） | TCP・UDP のリスナー |
| 入口 | ディストリビューションのドメイン名 | 2 つの静的なエニーキャスト IP アドレス |
| 向く場面 | 画像・動画・サイトの高速化 | ゲーム・VoIP・固定 IP・リージョン間の素早い切り替え |

数字や条件は AWS「Amazon CloudFront とは何ですか?」「AWS Global Accelerator コンポーネント」による

### 配信のしくみ

#### Amazon CloudFront（くらうどふろんと / Amazon CloudFront）

- 意味：エッジロケーションという世界のデータセンターのネットワークで、静的と動的なウェブコンテンツの配信を速くするサービス
- ポイント：リクエストは DNS で、ふつうレイテンシーが最も低いエッジロケーションに送られる。キャッシュにあればすぐ返し、なければオリジンから取る。AWS のバックボーンネットワークを通るので、キャッシュできない動的なリクエストも速くなる。コピーが多くのエッジにあるので、信頼性と可用性も上がる
- 例：S3 に置いた画像を、世界の利用者に CloudFront で配る
- 語の意味：CDN＝Content Delivery Network（コンテンツ配信網）

#### ディストリビューション（でぃすとりびゅーしょん / Distribution）

- 意味：どのオリジンのコンテンツを、どのように配信するかを CloudFront に指示する設定のまとまり
- ポイント：オリジン・キャッシュ動作（パスごとのキャッシュや関数の設定）・証明書・地理的制限・WAF などをまとめる。キャッシュ動作はパスのパターンごとに分けられ、それぞれにキャッシュポリシーや署名者を付けられる
- 例：/images/* は S3、/api/* は ALB をオリジンにする

#### エッジロケーション（POP）（えっじろけーしょん / Edge location, Point of presence）

- 意味：ビューワー（利用者）に直接コンテンツを返す、世界各地の CloudFront の拠点
- ポイント：人気のあるコンテンツをすばやく返す。あまりリクエストされないファイルは、有効期限の前でも消して場所を空けることがある
- 例：東京の利用者は、東京のエッジロケーションから画像を受け取る

#### リージョン別エッジキャッシュ（りーじょんべつえっじきゃっしゅ / Regional edge cache）

- 意味：オリジンとエッジロケーション（POP）の間にある、POP より大きなキャッシュを持つ CloudFront の拠点
- ポイント：POP で消えた人気の下がったオブジェクトも、ここに長く残るので、オリジンに戻る回数が減る。PUT・POST などのメソッドや、リクエスト時に決まる動的なリクエストは、ここを通らずオリジンへ直接行く。オリジンが同じリージョンの S3 なら、ここを飛ばす
- 例：少し前に流行った商品の写真が、リージョン別エッジキャッシュから返る

#### オリジン（おりじん / Origin）

- 意味：CloudFront が配信するコンテンツの元の置き場所
- ポイント：S3 バケット、ALB・EC2 などの HTTP サーバー、MediaPackage などを指定できる。S3 の静的ウェブサイトエンドポイントは、カスタムオリジンとして設定する
- 例：S3 バケットと ALB の 2 つのオリジンを持つディストリビューション

#### Origin Shield（おりじんしーるど / CloudFront Origin Shield）

- 意味：オリジンの前に置く、CloudFront のキャッシュの追加の層
- ポイント：すべてのキャッシュ層からオリジンへのリクエストが Origin Shield を通るので、キャッシュヒット率が上がり、同じオブジェクトへの同時リクエストも減ってオリジンの負荷が下がる。オリジンへのレイテンシーが最も低いリージョンで有効にする。追加料金がかかる
- 例：世界中から同じ動画が一斉に要求されても、オリジンへのリクエストを 1 回にまとめる

### キャッシュの制御

#### キャッシュキーとキャッシュポリシー（きゃっしゅきー / Cache key, Cache policy）

- 意味：キャッシュの中のオブジェクトを見分ける一意の識別子と、それに含めるヘッダー・Cookie・クエリ文字列や TTL を決める設定
- ポイント：キャッシュキーに含める値が少ないほど、キャッシュヒットしやすい。オリジンが内容を変えるクエリ文字列だけを含め、大文字小文字や順序をそろえる。キャッシュポリシーはキャッシュ動作にアタッチする
- 例：言語で内容が変わるので、lang のクエリ文字列だけをキャッシュキーに入れる

#### TTL（てぃーてぃーえる / Minimum TTL, Default TTL, Maximum TTL）

- 意味：CloudFront がファイルをキャッシュに持ち、オリジンに問い合わせるまでの期間
- ポイント：短くすると動的なコンテンツに合い、長くすると利用者の性能が上がる。キャッシュポリシーを使わないときの既定は 24 時間。ファイルごとには、オリジンが Cache-Control の max-age・s-maxage や Expires ヘッダーを返して決める。期限が切れても、オリジンが 304 Not Modified を返せば同じファイルを使い続ける
- 例：ほとんど変わらないロゴ画像に、オリジンで長い max-age を付ける

#### キャッシュヒット率（きゃっしゅひっとりつ / Cache hit ratio）

- 意味：オリジンに行かず、CloudFront のキャッシュから直接返したリクエストの割合
- ポイント：上げる方法は、max-age を実用的な範囲で長くする、Origin Shield を使う、キャッシュキーに入れる値を必要なものだけにする、など。上がるとオリジンの負荷と利用者のレイテンシーが下がる
- 例：CloudFront のログで、オリジンに転送されたクエリ文字列を調べて減らす

#### 無効化（むこうか / Invalidation）

- 意味：有効期限の前に、CloudFront のエッジキャッシュからファイルを消すこと
- ポイント：次のリクエストで、CloudFront はオリジンから最新版を取る。リージョン別エッジキャッシュからも消える。ただし、ブラウザや企業のプロキシのキャッシュには古い版が残ることがある。頻繁に更新するファイルなら、バージョン付きファイル名のほうが安い
- 例：誤って公開したファイルを、すぐに配信から消す

#### バージョン付きファイル名（ばーじょんつきふぁいるめい / Versioned file names）

- 意味：ファイルを更新するとき、style_v2.css のように名前を変えて別のファイルとして配信するやり方
- ポイント：頻繁に更新するファイルでは、無効化より勧められる。ブラウザやプロキシのキャッシュがあっても返すファイルを確実に変えられ、ロールバックも簡単。無効化の料金がかからないので安い
- 例：デプロイのたびに、JavaScript のファイル名にハッシュを付ける

## 19-2 CloudFront のセキュリティと高可用性

### まとめ表

| 守りたいもの | 使うもの |
| :-: | :-: |
| S3 バケットへの直接アクセスを防ぐ | オリジンアクセスコントロール（OAC）＋バケットポリシー |
| ALB への直接アクセスを防ぐ | カスタムヘッダー＋ALB のルール、または VPC オリジン |
| 有料の 1 つのファイル | 署名付き URL |
| 有料の多くのファイル・URL を変えない | 署名付き Cookie |
| 特定の国からのアクセス | 地理的制限 |
| フォームの特定の項目（カード番号など） | フィールドレベル暗号化 |
| SQL インジェクションなどの攻撃 | AWS WAF |

数字や条件は AWS「Amazon S3 オリジンへのアクセスを制限する」「署名付き URL を使用するか、署名付き Cookie を使用するかを決定する」による

### オリジンを守る

#### オリジンアクセスコントロール（おりじんあくせすこんとろーる / Origin access control, OAC）

- 意味：CloudFront から S3 オリジンに、認証したリクエストを送るしくみ。バケットポリシーで CloudFront からのアクセスだけを許す
- ポイント：古いオリジンアクセスアイデンティティ（OAI）より勧められる。すべてのリージョンの S3（新しいオプトインリージョンも）と、PUT・DELETE などの動的なリクエストに対応する。S3 の静的ウェブサイトエンドポイントはカスタムオリジンなので、OAC も OAI も使えない
- 例：S3 バケットを非公開のまま、CloudFront の URL からだけ画像を見せる

#### カスタムヘッダーによる ALB の保護（かすたむへっだー / Custom origin header）

- 意味：CloudFront が ALB に送るリクエストに秘密のカスタムヘッダーを付け、ALB はそのヘッダーがあるリクエストだけを転送する構成
- ポイント：インターネット向けの ALB に、利用者が直接アクセスするのを防ぐ。安全性を上げるには HTTPS も使う。CloudFront はレイテンシーを下げ、DDoS 攻撃の吸収にも役立つ
- 例：X-Origin-Verify という名前のヘッダーに長いランダムな値を入れる

#### VPC オリジン（ぶいぴーしーおりじん / VPC origins）

- 意味：プライベートサブネットにある ALB・NLB・EC2 を、CloudFront のオリジンにする機能
- ポイント：オリジンにパブリックなアクセスを持たせず、CloudFront を唯一の入口にする。アクセスを制限するための ACL などの手間が減る。AWS RAM でほかのアカウントと共有できる
- 例：内部向けの ALB をプライベートサブネットに置いたまま、CloudFront で公開する

### 閲覧者を制限する

#### 署名付き URL（しょめいつきゆーあーるえる / Signed URL）

- 意味：有効期限などを含み、署名者の秘密鍵で署名した URL。持っている人だけがプライベートなコンテンツにアクセスできる
- ポイント：個別のファイル（インストーラーなど）を制限するとき、Cookie に対応しないクライアントのときに使う。署名者には信頼されたキーグループ（推奨）か AWS アカウントを使う。署名者をキャッシュ動作に付けると、そのファイルには署名が必須になる。S3 の署名付き URL（#13）とは別もの
- 例：購入した人にだけ、24 時間有効なダウンロードリンクを送る

#### 署名付き Cookie（しょめいつきくっきー / Signed cookies）

- 意味：署名した Cookie で、複数の制限されたファイルへのアクセスを許すしくみ
- ポイント：HLS の動画のすべてのファイルや、会員エリアのすべてのファイルなど、多くのファイルに使う。今の URL を変えたくないときにも使う。基本の機能は署名付き URL と同じ
- 例：有料会員がログインしたら署名付き Cookie を発行し、会員ページの動画をすべて見せる

#### 地理的制限（ちりてきせいげん / Geographic restrictions）

- 意味：特定の国のユーザーが、ディストリビューションのコンテンツにアクセスできないようにする機能
- ポイント：許可する国のリストか、拒否する国のリストを作る。ディストリビューションのすべてのファイルを国の単位で制限する。ファイルの一部だけや、国より細かい単位なら、サードパーティーの位置情報サービスを使う
- 例：配信の権利がある日本だけに、動画を見せる

#### フィールドレベル暗号化（ふぃーるどれべるあんごうか / Field-level encryption）

- 意味：POST リクエストの特定のフィールドを、ユーザーの近くのエッジで公開鍵で暗号化する機能
- ポイント：HTTPS に加えるセキュリティの層。暗号化されたデータは、アプリケーションスタック全体で暗号化されたままで、秘密鍵を持つ特定のアプリだけが読める。1 つのリクエストで 10 個までのフィールドを暗号化できる
- 例：カード番号のフィールドを、決済システムだけが復号できるように暗号化する

#### HTTPS と証明書（えいちてぃーてぃーぴーえす / HTTPS, ACM certificate）

- 意味：ビューワーと CloudFront の間、CloudFront とオリジンの間で HTTPS を必須にして通信を暗号化する設定
- ポイント：ACM のパブリック証明書が勧められる。独自のドメイン名でビューワーとの HTTPS に ACM の証明書を使うときは、米国東部（バージニア北部）リージョン（us-east-1）でリクエストかインポートする
- 例：www.example.com の証明書を us-east-1 の ACM で発行し、ディストリビューションに付ける

#### AWS WAF との統合（ぶいぶいえーえふ / AWS WAF）

- 意味：リクエストがサーバーに届く前にブロックして、ウェブアプリと API を守るウェブアプリケーションファイアウォールを、ディストリビューションに付けること
- ポイント：CloudFront のコンソールの 1 回の選択でウェブ ACL を作れる。作っておいたウェブ ACL も付けられる。オリジンに届く前のエッジで攻撃を止める
- 例：SQL インジェクションを防ぐマネージドルールを、ディストリビューションに付ける

### 可用性とエッジの処理

#### オリジンフェイルオーバー（おりじんふぇいるおーばー / Origin failover, Origin group）

- 意味：プライマリとセカンダリの 2 つのオリジンでオリジングループを作り、プライマリが失敗したらセカンダリに切り替える機能
- ポイント：キャッシュミスのとき、まずプライマリに送る。フェイルオーバー用に設定したステータスコード（400・403・404・416・429・500・502・503・504 から選ぶ）が返ると、そのリクエストをセカンダリに送る。既定では、プライマリへの接続を 30 秒（10 秒を 3 回）試してから切り替える。前のリクエストをセカンダリに切り替えたあとも、次のリクエストはまずプライマリに送る
- 例：東京の S3 をプライマリ、大阪の S3（レプリケーション先）をセカンダリにする

#### CloudFront Functions（くらうどふろんとふぁんくしょんず / CloudFront Functions）

- 意味：ビューワーの近くで動く、JavaScript の軽量で短い関数
- ポイント：起動は 1 ミリ秒未満で、毎秒数百万のリクエストに対応する。イベントはビューワーリクエストとビューワーレスポンスだけ。ネットワーク・ファイルシステム・リクエストの本文には触れない。キャッシュキーの正規化、ヘッダーの操作、URL のリダイレクトや書き換え、トークンの検証に向く
- 例：すべてのリクエストにセキュリティヘッダーを足す

#### Lambda@Edge（らむだあっとえっじ / Lambda@Edge）

- 意味：Node.js や Python のコードをビューワーの近くで動かす、AWS Lambda の拡張機能
- ポイント：イベントはビューワーリクエスト・ビューワーレスポンス・オリジンリクエスト・オリジンレスポンスの 4 つ。最大 30 秒動き、ネットワーク・ファイルシステム・リクエストの本文にアクセスできる。外部のサービスを呼ぶ処理、数ミリ秒以上かかる処理、サードパーティのライブラリが要る処理に向く
- 例：オリジンリクエストのときに、外部の認証サービスを呼ぶ

## 19-3 Global Accelerator

### まとめ表

| 調整の単位 | 使うもの | 例 |
| :-: | :-: | :-: |
| リージョン（エンドポイントグループ） | トラフィックダイヤル（0〜100%） | 新しいリージョンに少しずつ流す |
| リージョンの中のエンドポイント | エンドポイントの重み | 2 つの ALB に 8 対 2 で分ける |
| 利用者ごと | クライアントアフィニティ | 同じ送信元 IP は同じエンドポイントへ |
| 利用者を特定の EC2 とポートへ | カスタムルーティングアクセラレーター | ゲームのセッションに割り当てる |

数字や条件は AWS「AWS Global Accelerator コンポーネント」「トラフィックダイヤルを使用してリージョンへ送信するトラフィックフローを調整する」による

### しくみ

#### AWS Global Accelerator（ぐろーばるあくせられーたー / AWS Global Accelerator）

- 意味：アクセラレーターを作り、利用者の通信を最も近いエッジから AWS のグローバルネットワークで最適なエンドポイントに送って、アプリの性能と可用性を上げるサービス
- ポイント：複数のリージョンのエンドポイントに対応するグローバルなサービス。ヘルスや設定の変更にすぐ反応し、正常なエンドポイントに送る。オリジンを 2 つの静的な入口の後ろに隠すので、攻撃のリスクも減る。ゲーム・メディア・モバイルアプリ・広告技術・財務など、とても低いレイテンシーが要るアプリに向く
- 例：東京とオレゴンの ALB の前に置き、障害のときは数秒で反対のリージョンへ送る

#### 静的 IP アドレス（せいてきあいぴーあどれす / Static IP addresses）

- 意味：アクセラレーターに付く、AWS のエッジネットワークからのエニーキャストの固定 IP アドレス（IPv4 なら 2 つ）
- ポイント：クライアントの単一の固定の入口になる。アクセラレーターを無効にしても割り当てられたままで、削除すると失う。独自の IP アドレス範囲（BYOIP）も使える。後ろのエンドポイントを変えても、利用者や取引先の許可リストは変えなくてよい
- 例：取引先のファイアウォールに 2 つの IP だけを登録してもらう
- 語の意味：エニーキャスト＝同じアドレスを多くの場所で広告し、最も近い場所が受ける方式

#### 標準アクセラレーター（ひょうじゅんあくせられーたー / Standard accelerator）

- 意味：ユーザーの場所、エンドポイントのヘルス、設定した重みなどから、最適なエンドポイントに通信を送るアクセラレーター
- ポイント：エンドポイントは NLB・ALB（内部向けも可）・EC2・Elastic IP。正常なエンドポイントだけに送る。正常なエンドポイントが 1 つもないときは、エンドポイントグループのすべてのエンドポイントに送る
- 例：世界の利用者を、最も近い正常なリージョンの ALB に送る

#### カスタムルーティングアクセラレーター（かすたむるーてぃんぐ / Custom routing accelerator）

- 意味：利用者を、アクセラレーターの後ろの特定の EC2 インスタンスとポートに決まった形で送るアクセラレーター
- ポイント：エンドポイントは VPC のサブネットだけで、そのプライベート IP に送る。外部の静的 IP とリスナーポートから、送信先が決まる。クライアント IP は常に保存される。VoIP やオンラインゲームで、複数の利用者を同じセッションのサーバーに集めるのに使う
- 例：マッチングしたプレイヤーを、同じゲームサーバーの同じポートに送る

#### リスナー（りすなー / Listener）

- 意味：設定したポートとプロトコルで、クライアントからアクセラレーターへの接続を受けるもの
- ポイント：TCP・UDP・その両方で設定できる。各リスナーは 1 つ以上のエンドポイントグループに関連付ける。クライアントアフィニティを設定すると、同じ送信元 IP の利用者を同じエンドポイントに送る（状態を持つアプリ向け）
- 例：UDP 3000 番のリスナーで、ゲームの通信を受ける

#### エンドポイントグループとトラフィックダイヤル（えんどぽいんとぐるーぷ / Endpoint group, Traffic dial）

- 意味：1 つのリージョンのエンドポイントのまとまりと、そこへ送る通信の割合を決める設定
- ポイント：トラフィックダイヤルは既定で 100%。下げると、そのリージョン向けの通信の一部をほかのリージョンに回す。新しい接続だけに効く。リージョンごとの性能テストやブルー/グリーンデプロイに使う。ヘルスチェックの設定もエンドポイントグループごと
- 例：新しいリージョンのダイヤルを 10% から始め、問題がなければ 100% にする

#### エンドポイントの重み（えんどぽいんとのおもみ / Endpoint weights）

- 意味：エンドポイントグループの中の各エンドポイントに送る通信の割合を決める値
- ポイント：同じリージョンの中での分散や、新しい版のテストに使う。トラフィックダイヤル（リージョン単位）と組み合わせる。可用性を守るため、限られた場面では Global Accelerator が重みを上書きする
- 例：同じリージョンの古い ALB に 200、新しい ALB に 50 の重みを付ける

#### クライアント IP アドレスの保存（くらいあんとあいぴーのほぞん / Client IP address preservation）

- 意味：エンドポイントに届くパケットに、元のクライアントの送信元 IP アドレスを残す機能
- ポイント：標準アクセラレーターでは、ALB・EC2・セキュリティグループ付きの NLB で使える。セキュリティグループのない NLB と Elastic IP のエンドポイントでは使えない。カスタムルーティングでは常に保存される
- 例：アプリのログに、利用者の本当の IP アドレスを記録する

### 19-1 CloudFront のしくみとキャッシュ

#### 問 aws-19-o01

- 問：東京リージョンの S3 に置いた商品の画像を、世界中の利用者が見る。海外の利用者の表示が遅い。オリジンの構成を大きく変えずに、表示を速くしたい。最も適したものはどれか。
- ア：S3 のクロスリージョンレプリケーションで、世界の全リージョンにコピーする
- イ：S3 の前に、より大きな EC2 インスタンスを置く
- ウ：S3 をオリジンにした CloudFront のディストリビューションを作る
- エ：S3 の前に Global Accelerator を置く
- 正解：ウ
- 解説：CloudFront は、世界のエッジロケーションにコンテンツをキャッシュし、利用者に近いエッジから返す。S3 をオリジンにするだけで、静的なコンテンツの配信が速くなる。
- アの意味：コピーは増えるが、利用者を最寄りのコピーに向けるしくみがなく、管理とストレージのコストも増える。
- イの意味：1 つのリージョンから返すことは変わらず、海外までの距離は縮まらない。
- ウの意味：正しい。
- エの意味：エンドポイントは ALB・NLB・EC2・Elastic IP で、S3 の画像をエッジでキャッシュするものではない。
- 出典：オリジナル問題（根拠：AWS「Amazon CloudFront とは何ですか?」（『CloudFront では、エッジロケーションというデータセンターの世界的ネットワークを経由してコンテンツを配信します。』）／AWS「AWS Global Accelerator コンポーネント」（『標準アクセラレーターのエンドポイントは、Network Load Balancer、Application Load Balancer、EC2 インスタンス、または Elastic IP アドレスです。』））

#### 問 aws-19-o02

- 問：利用者が要求したオブジェクトが、エッジロケーションのキャッシュになかった。CloudFront の動きとして正しいものはどれか。
- ア：利用者に 404 を返し、次のリクエストまでにオリジンから取っておく
- イ：オリジンに転送し、最初のバイトが届いたらすぐ利用者に送り始め、キャッシュにも入れる
- ウ：利用者をオリジンの URL にリダイレクトする
- エ：オブジェクト全体をキャッシュに入れ終わってから、利用者に送る
- 正解：イ
- 解説：キャッシュにないとき、CloudFront はディストリビューションの設定に従ってリクエストをオリジンに転送する。オリジンから最初のバイトが届いた直後に利用者へ送り始め、次のリクエストに備えてキャッシュにも追加する。
- アの意味：キャッシュにないときもオリジンから取って返すので、404 にはならない。
- イの意味：正しい。
- ウの意味：CloudFront が代わりにオリジンから取るので、利用者をオリジンに向けることはない。
- エの意味：全体を待たずに、最初のバイトから送り始める。
- 出典：オリジナル問題（根拠：AWS「CloudFront がコンテンツを配信する方法」（『オリジンから最初のバイトが到着した直後に、CloudFront はそのオブジェクトをユーザーに転送し始めます。また、CloudFront は、そのオブジェクトに対する次回のリクエストに備えて、キャッシュにそのオブジェクトを追加します。』））

#### 問 aws-19-o03

- 問：CloudFront のリージョン別エッジキャッシュについて、正しいものはどれか。
- ア：オリジンと POP の間にあり、POP から消えた人気の下がったオブジェクトも長く残す
- イ：リクエスト時に決まる動的なリクエストも、必ずリージョン別エッジキャッシュを通る
- ウ：PUT や POST のリクエストは、リージョン別エッジキャッシュに保存される
- エ：オリジンが同じリージョンの S3 でも、必ずリージョン別エッジキャッシュを通る
- 正解：ア
- 解説：リージョン別エッジキャッシュは、オリジンと POP の間にあり、POP より大きなキャッシュを持つ。人気が下がって POP から消えたオブジェクトも長く残るので、オリジンに戻る回数が減る。
- アの意味：正しい。
- イの意味：動的なリクエストは、リージョン別エッジキャッシュを通らずにオリジンへ直接送られる。
- ウの意味：PUT や POST などは、POP からオリジンへ直接送られる。
- エの意味：オリジンが同じリージョンの S3 なら、POP は S3 へ直接行く。
- 出典：オリジナル問題（根拠：AWS「CloudFront がコンテンツを配信する方法」（『リージョン別エッジキャッシュのキャッシュは個別の POP よりも大きいため、オブジェクトは最も近いリージョン別エッジキャッシュロケーションでより長くキャッシュに残ります。』『リクエスト時に決定される動的リクエストは、リージョン別エッジキャッシュを通過せず、直接オリジンに送信されます。』））

#### 問 aws-19-o04

- 問：新作の動画が公開されると、世界中のキャッシュ層から同じオブジェクトへのリクエストが一斉にオリジンに届き、オリジンの負荷が高くなる。オリジンへのリクエストを減らしたい。最も適したものはどれか。

- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「Amazon CloudFront Origin Shield の使用」（『Origin Shield を使用すると、CloudFront のすべてのキャッシュレイヤーからオリジンへのすべてのリクエストが Origin Shield を通過し、キャッシュヒットの可能性が高くなります。』））

- 問：あるディストリビューションは、キャッシュポリシーを使わない設定で、オリジンも Cache-Control や Expires のヘッダーを返さない。CloudFront がファイルをキャッシュする既定の期間はどれか。

#### 問 aws-19-o10

- 問：キャッシュキーに含める値と、キャッシュヒット率の関係として正しいものはどれか。

### 19-2 CloudFront のセキュリティと高可用性

#### 問 aws-19-o11

- 問：S3 バケットの画像を CloudFront で配信している。利用者が S3 の URL で直接アクセスするのを防ぎ、CloudFront 経由だけにしたい。新しく設定するときに AWS が勧めるものはどれか。
- ア：オリジンアクセスコントロール（OAC）を作り、バケットポリシーで CloudFront からのアクセスだけを許可する
- イ：オリジンアクセスアイデンティティ（OAI）を作る
- ウ：バケットを公開し、CloudFront の署名付き URL を使う
- エ：S3 の静的ウェブサイトエンドポイントをオリジンにして、OAC を付ける
- 正解：ア
- 解説：CloudFront から S3 に認証したリクエストを送る方法には OAC と OAI があり、OAC が勧められる。すべてのリージョンの S3 と、PUT・DELETE などの動的なリクエストに対応する。
- アの意味：正しい。
- イの意味：古い方法で、新しいリージョンや動的なリクエストに対応しないことがある。
- ウの意味：バケットを公開すると、S3 の URL から直接見られてしまう。
- エの意味：ウェブサイトエンドポイントはカスタムオリジンとして設定するので、OAC は使えない。

#### 問 aws-19-o30

- 問：Global Accelerator のあるエンドポイントグループで、すべてのエンドポイントがヘルスチェックに失敗した。このとき Global Accelerator はどうするか。
- ア：エンドポイントグループのすべてのエンドポイントにリクエストを送る
- イ：すべてのリクエストを捨てる
- ウ：クライアントに 503 を返す
- エ：CloudFront のディストリビューションにリクエストを送る
- 正解：ア
- 解説：ふだんは正常なエンドポイントだけに送るが、正常なエンドポイントが 1 つもないときは、エンドポイントグループのすべてのエンドポイントにリクエストを送る。
- アの意味：正しい。
- イの意味：捨てずに、すべてのエンドポイントに送る。
- ウの意味：Global Accelerator が自分でエラーを返すのではなく、エンドポイントに送る。
- エの意味：Global Accelerator が CloudFront に送るしくみはない。
- 出典：オリジナル問題（根拠：AWS「アクセラレーターのヘルスチェックアクセスを確保する」（『トラフィックをルーティングする正常なエンドポイントがない場合、Global Accelerator は受信クライアントリクエストをエンドポイントグループ内のすべてのエンドポイントにルーティングします。』））
