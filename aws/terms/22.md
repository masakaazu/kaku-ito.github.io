## 22-1 EC2 の購入オプション

### まとめ表

| 購入オプション | 何に払うか・何を約束するか | 選ぶ決め手 |
| :-: | :-: | :-: |
| オンデマンド | 起動したインスタンスに秒単位で払う。約束なし | 短期・予測できない・止められない |
| Savings Plans | 1〜3 年、1 時間あたり USD の使用額を約束 | 使う額は読めるが、タイプやリージョンは変えたい |
| リザーブドインスタンス | 1〜3 年、インスタンスの設定（タイプ・リージョンなど）を約束 | 同じ設定で長く動かす |
| スポット | 使われていない EC2 キャパシティを大幅割引で使う | 中断されてもよい・時間に柔軟 |
| 専有ホスト | 物理サーバー 1 台ごとに払う | ソケット・コア単位のライセンスを持ち込む（BYOL） |
| ハードウェア専有インスタンス | 1 つのアカウント専用のハードウェアで、インスタンスごとに払う | ハードウェアを共有したくないが、配置の制御はいらない |
| キャパシティ予約 | 特定の AZ のキャパシティを、オンデマンドと同じ料金で押さえる | 期間の約束なしで、確実に起動できるようにする |

数字や条件は AWS「Amazon EC2 の請求および購入オプション」「Savings Plans のタイプ」による

### 購入オプションの種類

#### オンデマンドインスタンス（おんでまんどいんすたんす / On-Demand Instances）

- 意味：長期の約束をせず、起動したインスタンスの分だけ秒単位で払う、EC2 の基本の買い方
- ポイント：割引はないが、いつ止めてもよい。短期間のテスト、使う量が読めないとき、中断できない処理に向く。長く動かすことが決まったら Savings Plans や RI に切り替えると安くなる
- 例：新しいサービスの最初の 1 か月、負荷が読めないのでオンデマンドで動かす

#### Savings Plans（せーびんぐすぷらんず / Savings Plans）

- 意味：1 年または 3 年の期間、1 時間あたり何 USD 分を使うかを約束する代わりに、料金が割り引かれるしくみ
- ポイント：AWS のコンピューティングの料金を最大 72% 減らせる。インスタンスの設定ではなく「使う額」を約束するので、RI より柔軟。支払いは全額前払い・一部前払い・前払いなしから選ぶ。約束の条件は購入後に変えられない。キャパシティは予約しない
- 例：毎時 10 USD 分のコンピューティングを 3 年使うと約束する

#### リザーブドインスタンス（りざーぶどいんすたんす / Reserved Instances, RI）

- 意味：1 年または 3 年の期間、インスタンスタイプやリージョンなどの設定を約束する代わりに、オンデマンドの料金が割り引かれるしくみ
- ポイント：物理的なインスタンスではなく、条件が合うオンデマンドの使用に請求の割引が付く。一部前払いや前払いなしでも、期間中は使ったかどうかにかかわらず請求される
- 例：本番の m5.large を 3 年動かすので、同じ設定の RI を買う
- 語の意味：Reserved＝予約された

#### スポットインスタンス（すぽっといんすたんす / Spot Instances）

- 意味：使われていない EC2 のキャパシティを、オンデマンドより大幅に安く使うインスタンス
- ポイント：AWS がキャパシティを取り戻すときは中断される。時間に柔軟な処理や、中断してよい処理（データ分析・バッチ・バックグラウンド処理）に向く。料金は需要と供給の長い傾向で変わる
- 例：夜の画像変換のバッチを、スポットインスタンスで安く回す
- 語の意味：Spot＝その場の（現物取引の）

### 専有と予約

#### 専有ホスト（せんゆうほすと / Dedicated Hosts）

- 意味：インスタンスを動かすためだけに、自分専用に使う物理サーバー
- ポイント：ソケットと物理コアの数が見え、インスタンスをどのホストに置くかを制御できる（ホストアフィニティ）。ソケット・コア・VM 単位のライセンスを持ち込める（BYOL）。請求はホストごと。インスタンス容量をほかのアカウントと共有することもできる
- 例：物理コア数で課金されるデータベースのライセンスを、そのまま AWS に持ち込む
- 語の意味：BYOL＝Bring Your Own License（自分のライセンスを持ち込む）

#### ハードウェア専有インスタンス（はーどうぇあせんゆういんすたんす / Dedicated Instances）

- 意味：1 つの AWS アカウント専用のハードウェアの上で動く EC2 インスタンス
- ポイント：ほかのアカウントとハードウェアを共有しないが、どのホストに置くかは見えず、制御もできない。停止して起動すると、同じホストで動くとは限らない。請求はインスタンスごと。配置の制御や BYOL が要るなら専有ホスト
- 例：規程で「ほかの会社とサーバーを共有しない」と決まっているが、ライセンスの持ち込みはない
- 語の意味：Dedicated＝専用の。ふつう（デフォルト）は「共有テナンシー」で、複数のアカウントが同じ物理ハードウェアを使うことがある

#### オンデマンドキャパシティ予約（きゃぱしてぃよやく / On-Demand Capacity Reservations, ODCR）

- 意味：特定の AZ に、EC2 のコンピューティングキャパシティを好きな期間だけ予約するしくみ
- ポイント：すぐに使える予約は期間の約束がなく、いつでも取り消せる。インスタンスを動かしているかどうかにかかわらず、オンデマンドと同じ料金がかかる。割引そのものはないが、Savings Plans とリージョン RI の割引は乗る（ゾーン RI の割引は乗らない）
- 例：年に一度の大型セールの日、確実に 100 台起動できるように前日から予約する
- 語の意味：ODCR＝On-Demand Capacity Reservation

### Savings Plans の種類

#### Compute Savings Plans（こんぴゅーとせーびんぐすぷらんず / Compute Savings Plans）

- 意味：最も柔軟な Savings Plans。オンデマンドの料金から最大 66% 割り引かれる
- ポイント：インスタンスファミリー・サイズ・リージョン・OS・テナンシーに関係なく、EC2 の使用に自動で適用される。Fargate と Lambda の使用にも適用される。c5 から m5 への移行、リージョンの移動、EC2 から Fargate への移行をしても割引が続く
- 例：来年 EC2 の一部を Fargate に移す予定があるので、Compute Savings Plans を選ぶ

#### EC2 Instance Savings Plans（いーしーついんすたんすせーびんぐすぷらんず / EC2 Instance Savings Plans）

- 意味：選んだリージョンの特定のインスタンスファミリーに約束する代わりに、オンデマンドから最大 72% 割り引かれる Savings Plans
- ポイント：そのファミリーの中なら、サイズ・OS・テナンシーを変えても適用される。ファミリーやリージョンを変えると適用されない。割引の大きさはスタンダード RI と同じくらい、Compute Savings Plans はコンバーティブル RI と同じくらい
- 例：東京リージョンの m5 を 3 年使い続けると決まっているので、EC2 Instance Savings Plans を選ぶ

#### Database Savings Plans（でーたべーすせーびんぐすぷらんず / Database Savings Plans）

- 意味：Aurora・RDS・DynamoDB・ElastiCache などのデータベースサービスのコストを、最大 35% 減らす Savings Plans
- ポイント：エンジン・インスタンスファミリー・サイズ・AZ・リージョンに関係なく適用される。RDS for Oracle から Aurora PostgreSQL 互換エディションに移すような変更をしても割引が続く
- 例：RDS と DynamoDB をまとめて 1 つの約束で割り引く

#### 支払いオプション（しはらいおぷしょん / All Upfront, Partial Upfront, No Upfront）

- 意味：Savings Plans や RI の約束の料金を、全額前払い・一部前払い・前払いなしのどれで払うかの選び方
- ポイント：前払いなしでも約束は約束で、期間中は使わなくても請求される。RI では一般に前払いを多くするほど節約できる（RI のドキュメントでは「すべて前払い」と書く）。Savings Plans のおすすめの約束額は Cost Explorer で見られる
- 例：手元の資金に余裕がないので、前払いなしで 1 年の Savings Plans を買う
- 語の意味：Upfront＝前払いの

### リザーブドインスタンスの種類

#### スタンダード RI（すたんだーど / Standard Reserved Instances）

- 意味：コンバーティブル RI より大きく割り引かれるが、ほかの RI に交換できない RI
- ポイント：Reserved Instance Marketplace で売ったり買ったりできる。変更（一部の属性の変更）はできるが、交換はできない
- 例：3 年間まったく同じ構成で動かす基幹システムに買う

#### コンバーティブル RI（こんばーてぃぶる / Convertible Reserved Instances）

- 意味：期間の途中で、インスタンスファミリー・タイプ・プラットフォーム・スコープ・テナンシーの違う別のコンバーティブル RI に交換できる RI
- ポイント：交換できる代わりに、割引はスタンダード RI より小さい。Reserved Instance Marketplace では売れない
- 例：2 年目に新しい世代のインスタンスファミリーへ移る予定があるので、コンバーティブル RI を選ぶ
- 語の意味：Convertible＝交換できる

#### リージョン RI（りーじょん / Regional Reserved Instances）

- 意味：リージョンを範囲（スコープ）にした RI。キャパシティは予約しない
- ポイント：そのリージョンのどの AZ の使用にも割引が付く（AZ の柔軟性）。Linux／Unix・デフォルトのテナンシーなら、同じファミリーの中でサイズを問わず割引が付く（サイズの柔軟性）。購入をキューに入れられる。スコープで料金は変わらない
- 例：AZ をまたいで台数が変わる Web サーバーに、リージョン RI を使う

#### ゾーン RI（ぞーん / Zonal Reserved Instances）

- 意味：特定の AZ を範囲にした RI。その AZ のキャパシティも予約する
- ポイント：割引は指定した AZ の使用にだけ付く。AZ の柔軟性もサイズの柔軟性もない。購入をキューに入れられない。キャパシティ予約にはゾーン RI の割引は付かない
- 例：障害のときでも 1a で確実に起動したいので、1a のゾーン RI を買う

#### Reserved Instance Marketplace（りざーぶどいんすたんすまーけっとぷれいす / Reserved Instance Marketplace）

- 意味：使わなくなったスタンダード RI を、ほかの AWS のお客様に売ったり、ほかのお客様から買ったりできる場
- ポイント：売れるのはスタンダード RI だけで、コンバーティブル RI は売れない
- 例：サービスを終えて残り 1 年の RI が余ったので、Marketplace に出す

## 22-2 スポットインスタンスと組み合わせ

### まとめ表

| しくみ | いつ・何をするか | 使い方 |
| :-: | :-: | :-: |
| 再調整に関する推奨事項 | 中断のリスクが高まったとき、早めに知らせる | 2 分前の通知より前に、別のインスタンスへ移す |
| 中断通知 | 停止・終了の 2 分前に知らせる | 処理の途中経過を保存し、片付ける |
| 混合インスタンスグループ | 1 つの Auto Scaling グループでオンデマンドとスポットを混ぜる | ベースはオンデマンド、増えた分はスポット |
| price-capacity-optimized | 中断されにくく、できるだけ安いプールを選ぶ | 使い始めにおすすめの配分戦略 |
| Fargate Spot | 予備のキャパシティで ECS タスクを安く動かす | 中断してよいタスク |

数字や条件は AWS「スポットインスタンスの中断通知」「複数のインスタンスタイプの配分戦略」による

### スポットの中断

#### スポットインスタンスの中断（ちゅうだん / Spot Instance interruption）

- 意味：AWS がキャパシティを取り戻すときなどに、スポットインスタンスを終了・停止・休止させること
- ポイント：主な理由はキャパシティの回収だが、ホストのメンテナンスやハードウェアの使用停止でも起きる。上限料金を決めると、決めないときより中断が増える。向くのはステートレスで、障害に強く、柔軟なアプリケーション
- 例：バッチの途中で中断されても、続きから再開できるように作っておく

#### スポットインスタンスの中断通知（ちゅうだんつうち / Spot Instance interruption notice）

- 意味：EC2 がスポットインスタンスを停止または終了する 2 分前に出す警告
- ポイント：中断動作を「休止」にしたときは、通知は出るがすぐに休止が始まるので、2 分の猶予はない。EventBridge のルールで受け取り、途中経過の保存などにつなげられる
- 例：通知を受けたら、処理中のジョブを S3 に書き出してキューに戻す

#### EC2 インスタンスの再調整に関する推奨事項（さいちょうせい / EC2 instance rebalance recommendation）

- 意味：スポットインスタンスで中断のリスクが高まったことを知らせるシグナル
- ポイント：2 分前の中断通知が届く前の段階で、中断のリスクが高くない新しいインスタンスなどにワークロードを移せる
- 例：シグナルを受けたら、別のインスタンスタイプのスポットを先に起動して処理を移す

#### 中断動作（ちゅうだんどうさ / Interruption behavior）

- 意味：スポットインスタンスが中断されるとき、終了・停止・休止のどれにするかの設定
- ポイント：何も決めないと（デフォルト）終了する。時間に柔軟なワークロードなら、終了ではなく停止や休止にしておくと、あとで続きから動かせる
- 例：メモリの中身を残したいので、中断動作を休止にする

### 組み合わせ

#### 混合インスタンスグループ（こんごういんすたんすぐるーぷ / Mixed instances group）

- 意味：1 つの Auto Scaling グループの中で、複数のインスタンスタイプと、オンデマンドとスポットの両方を使うグループ
- ポイント：スポットの割引に加えて、オンデマンドの部分には RI や Savings Plans の割引も付く。スポットはインスタンスタイプと AZ を広く選べるほど確保しやすい（ワークロードごとに少なくとも 10 種類のタイプが目安）
- 例：c5・c6i・m5・m6i など 10 種類以上のタイプを並べ、スポットを主に使う

#### オンデマンドのベースキャパシティと割合（べーすきゃぱしてぃ / On-Demand base capacity, percentage above base）

- 意味：混合インスタンスグループで、最初に必ずオンデマンドで起動する台数（ベース）と、それを超えた分のうちオンデマンドにする割合
- ポイント：スケールアウトのときは、ベースのオンデマンドが起動してからスポットが起動する。ベースを超えた分は、割合でオンデマンドとスポットに分ける
- 例：ベース 2 台、超えた分のオンデマンドの割合 20%。10 台のときは 2 台＋残り 8 台の 20% がオンデマンド

#### price-capacity-optimized（ぷらいすきゃぱしてぃおぷてぃまいずど / price-capacity-optimized allocation strategy）

- 意味：価格とキャパシティの両方を見て、中断されにくく、価格ができるだけ低いスポットのプールを選ぶ配分戦略
- ポイント：Auto Scaling で使い始めるときのおすすめ。capacity-optimized はキャパシティだけを見る。lowest-price は中断のリスクが非常に高いので勧められていない
- 例：混合インスタンスグループのスポットの配分戦略を price-capacity-optimized にする
- 語の意味：スポットキャパシティプール＝同じインスタンスタイプと AZ の、使われていない EC2 インスタンスのまとまり

#### Fargate Spot（ふぁーげーとすぽっと / AWS Fargate Spot）

- 意味：予備のコンピューティングキャパシティで、中断してよい ECS タスクを Fargate の料金より安く動かすしくみ
- ポイント：AWS がキャパシティを取り戻すときは、2 分の警告のあとにタスクが止まる。Fargate と Fargate Spot のキャパシティプロバイダーを、キャパシティプロバイダー戦略で混ぜられる
- 例：ECS のバッチ処理のタスクを、Fargate Spot で動かす

## 22-3 適切なサイズとサーバーレス・データベースのコスト

### まとめ表

| 手段 | 何を安くするか | 選ぶ決め手 |
| :-: | :-: | :-: |
| Compute Optimizer | 大きすぎる・使っていないリソース | 使用率のメトリクスから適切なサイズを推奨 |
| T インスタンス | ふだん CPU をあまり使わないサーバー | 平均は低く、ときどき高くなる |
| arm64（Graviton）の Lambda | Lambda の料金とパフォーマンス | コードが arm64 で動く |
| リザーブド DB インスタンス | 長く動かす RDS の DB インスタンス | 1 年・3 年、同じエンジンとクラスで使う |
| Aurora serverless | 負荷の差が大きい Aurora | 使わないときは 0 ACU まで下げる |

数字や条件は AWS「AWS Compute Optimizer とは」「Aurora serverless の仕組み」による

### 適切なサイズ

#### AWS Compute Optimizer（こんぴゅーとおぷてぃまいざー / AWS Compute Optimizer）

- 意味：リソースの設定と使用率のメトリクスを分析して、適切なサイズを推奨し、アイドル状態のリソースを見つけるサービス
- ポイント：対象は EC2 インスタンス・Auto Scaling グループ・EBS ボリューム・Lambda 関数・Fargate の ECS サービス・商用ソフトウェアのライセンス・Aurora と RDS。使うにはオプトインが要る。組織の管理アカウントでオプトインすると、複数のアカウントの結果も見られる
- 例：CPU 使用率がずっと 5% の m5.2xlarge に、小さいサイズへの変更を推奨される

#### バーストパフォーマンスインスタンス（ばーすと / Burstable performance instances, T instances）

- 意味：ベースラインの CPU 性能を持ち、必要なときだけベースラインを超えて CPU を使える（バーストできる）低コストの T 系のインスタンス
- ポイント：T4g・T3a・T3（旧世代の T2）がある。CPU の使用率がふだん低〜中程度の汎用ワークロードで、固定性能のインスタンスより安くできる。ずっと高い CPU を使うなら固定性能のほうが安い
- 例：ふだんの CPU は 10% で、朝だけ高くなる社内向けの Web サーバー

#### CPU クレジット（しーぴーゆーくれじっと / CPU credits, standard mode, unlimited mode）

- 意味：T インスタンスが、ベースラインより下のときに貯め、上のときに使う CPU の使用権
- ポイント：スタンダードモードは貯めたクレジットがなくなると、CPU がベースラインまで下がる。Unlimited モードは余剰クレジットでバーストを続けられ、24 時間の平均がベースラインを超えた分は vCPU 時間あたりの追加料金になる。T3 が 100% で動き続けると、同じサイズの M5 の約 1.5 倍の料金になる
- 例：t3.large のベースラインは 30%。24 時間の平均が 40% なら、超えた 10% 分に追加料金がかかる

#### Lambda の arm64 アーキテクチャ（あーむ / arm64 architecture, AWS Graviton2）

- 意味：Lambda 関数を、AWS Graviton2 プロセッサ用の 64 ビット ARM アーキテクチャで動かす設定
- ポイント：x86_64 で動く同じ関数より、料金とパフォーマンスが大幅によい。ほとんどのリージョンで使える。コードや依存ライブラリが arm64 で動く必要がある
- 例：Python の関数のアーキテクチャを x86_64 から arm64 に変えて、コストを下げる
- 語の意味：Graviton＝AWS が設計した ARM ベースのプロセッサ

### データベースのコスト

#### リザーブド DB インスタンス（りざーぶどでぃーびー / Reserved DB instances）

- 意味：RDS の DB インスタンスを 1 年または 3 年予約して、オンデマンドより大幅に割り引いてもらうしくみ
- ポイント：割引が付くのは、リージョン・DB エンジン・DB インスタンスのタイプなどが同じ DB インスタンス（エンジンのバージョンは同じでなくてよい）。マルチ AZ とシングル AZ のどちらにも適用される
- 例：本番の RDS for MySQL を 3 年使うので、同じクラスのリザーブド DB インスタンスを買う

#### サイズ柔軟なリザーブド DB インスタンス（さいずじゅうなん / Size-flexible reserved DB instances）

- 意味：同じインスタンスクラスタイプの中なら、サイズが違う DB インスタンスにも割引が付くリザーブド DB インスタンス
- ポイント：サイズの違いは「1 時間あたりの正規化された単位」で比べる。RDS for Db2・MariaDB・MySQL・Oracle（BYOL）・PostgreSQL で使え、SQL Server と Oracle のライセンス込みには適用されない。クラスタイプをまたいでは使えない
- 例：ラージ 1 台（単位 4）の予約が、ミディアム 2 台（単位 2＋2）にもそのまま効く

#### Aurora serverless（おーろらさーばーれす / Amazon Aurora Serverless）

- 意味：負荷に合わせて Aurora のデータベースの容量を自動で増減させる、オンデマンドのオートスケーリングの設定
- ポイント：容量は ACU（Aurora 容量単位）で表し、最小と最大を決める。0 ACU から 256 ACU まで使え、0.5 ACU 単位で細かく増減する。最小を 0 ACU にすると、ワークロードがないときは 0 まで下がる。負荷の差が大きい・読めない・開発やテストの環境に向き、安定した負荷はプロビジョン済みのクラスターに向く
- 例：夜と週末は使わない開発用の Aurora を、最小 0 ACU にする
- 語の意味：ACU＝Aurora Capacity Unit（Aurora 容量単位）
