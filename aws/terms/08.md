## 08-1 ECS と ECR の部品

### まとめ表

| 部品 | ひとことで | たとえると（Claude が作ったたとえ） |
| :-: | :-: | :-: |
| クラスター | タスクやサービスをまとめる論理的なグループ（リージョンごと） | 工場 |
| タスク定義 | イメージ・CPU とメモリ・ポート・ロールなどを書いた JSON の設計図 | 設計図 |
| タスク | タスク定義から起動した、動いているコンテナの組 | 設計図から作った製品 1 つ |
| サービス | 決めた数のタスクを動かし続け、落ちたら置き換える | 在庫を一定に保つ係 |
| ECR | コンテナイメージを置くレジストリ | 部品の倉庫 |

### ECS の部品

#### コンテナ（こんてな / container）

- 意味：アプリケーションと、動かすのに必要なライブラリや設定を 1 つにまとめ、どこでも同じように動かせるようにしたもの。元になるファイル一式をコンテナイメージと呼ぶ
- ポイント：仮想マシンより軽く、すぐ起動する。「開発環境では動くのに本番で動かない」を減らせる。マイクロサービスに分けて、部品ごとに別々にデプロイ・スケールしやすい
- 例：Web アプリを Docker イメージにして、ECS で 4 つ動かす

#### Amazon ECS（いーしーえす / Amazon Elastic Container Service）

- 意味：コンテナを動かし、スケールさせるための AWS のフルマネージドのコンテナオーケストレーションサービス
- ポイント：コントロールプレーン（どこで何を動かすか決める部分）は AWS が管理する。動かす場所（キャパシティ）は Fargate・EC2・ECS マネージドインスタンス・オンプレミス（ECS Anywhere）から選ぶ。Kubernetes を使いたいなら EKS
- 語の意味：Elastic＝伸び縮みする、Container＝コンテナ、Service＝サービス

#### クラスター（くらすたー / cluster）

- 意味：タスクやサービスをまとめる論理的なグループ。動かすためのキャパシティもここに結び付ける
- ポイント：クラスターはリージョンごと。1 つのクラスターに、Fargate のタスクと EC2 のタスクを混ぜることもできる
- 例：本番用と検証用でクラスターを分ける

#### タスク定義（たすくていぎ / task definition）

- 意味：アプリケーションの設計図。使うイメージ・CPU とメモリ・ポート・ネットワークモード・IAM ロール・ログの出し先などを JSON で書いたもの
- ポイント：タスク定義そのものは動かない。これを元にタスクを起動する。変更すると新しいリビジョン（版）になる。`requiresCompatibilities` で、Fargate・EC2 など、どこで動かせるかを決める
- 例：`web:12`（タスク定義 web のリビジョン 12）

#### タスク（たすく / task）

- 意味：タスク定義から起動した、実際に動いているコンテナの組
- ポイント：1 回だけ動かすバッチなら、タスクを直接起動する（スタンドアロンタスク、RunTask）か、スケジュールで起動する。ずっと動かし続けるならサービスにする
- 例：夜間の集計を 1 回だけタスクとして動かす

#### ECS サービス（いーしーえすさーびす / service）

- 意味：決めた数（desiredCount）のタスクを動かし続ける仕組み。タスクが止まったり、ヘルスチェックに失敗したりすると、新しいタスクに置き換える
- ポイント：ロードバランサーの後ろに置け、タスクを自動でターゲットに登録する。長く動き続けるステートレスな Web アプリや API 向き。デプロイ（ローリング・ブルー/グリーン）や Auto Scaling もサービスの単位で行う
- 例：Web のタスクを常に 4 つ、ALB の後ろで動かす

#### レプリカ戦略とデーモン戦略（れぷりかせんりゃく・でーもんせんりゃく / REPLICA and DAEMON）

- 意味：サービスのタスクの配り方。レプリカはクラスター全体で必要な数を保つ。デーモンはコンテナインスタンス（EC2）ごとに 1 つずつ置く
- ポイント：指定しなければレプリカ。ログの収集やモニタリングのエージェントのように「各サーバーに 1 つ」が要るものはデーモン
- 例：全 EC2 インスタンスにログ転送のエージェントを 1 つずつ置く

### ECR の機能

#### Amazon ECR（いーしーあーる / Amazon Elastic Container Registry）

- 意味：コンテナイメージを保存・管理する AWS のマネージドのレジストリ
- ポイント：プライベートリポジトリは IAM のリソースベースの権限で守れる。Docker イメージや OCI イメージを置ける。パブリックのリポジトリもある。ECS・EKS・Lambda（コンテナイメージの関数）がここからイメージを取り出す（プル）
- 語の意味：Registry＝登録所（イメージの置き場）

#### イメージスキャン（いめーじすきゃん / image scanning）

- 意味：コンテナイメージの中のソフトウェアの脆弱性を見つける ECR の機能
- ポイント：基本スキャン＝AWS ネイティブの技術と CVE のデータベースで OS の脆弱性を調べる。拡張スキャン＝Amazon Inspector と連携し、リポジトリを自動で継続的にスキャンし、OS とプログラミング言語のパッケージの両方を調べる
- 例：プッシュされたイメージを拡張スキャンで調べ続け、重大な脆弱性を通知する

#### ライフサイクルポリシー（ECR）（らいふさいくるぽりしー / lifecycle policy）

- 意味：ルールに合った古いイメージを、自動でアーカイブしたり期限切れ（削除）にしたりする設定
- ポイント：イメージがたまり続けるとストレージの料金がかかる。「タグなしで 14 日たったもの」「最新の 30 個より古いもの」などで片付ける
- 例：開発用リポジトリでは、タグなしのイメージを 7 日で消す

#### レプリケーション（ECR）（れぷりけーしょん / replication）

- 意味：プライベートレジストリのイメージを、別のリージョンや別のアカウントへ自動でコピーする設定
- ポイント：クロスリージョンとクロスアカウントの両方に対応。別アカウントへコピーするには、コピー先のレジストリのアクセス許可ポリシーで許可が要る。災害対策や、近いリージョンからのプルに使う
- 例：東京のイメージを大阪のレジストリにもコピーしておく

## 08-2 キャパシティ・権限・ネットワーク

### まとめ表

| 動かす場所 | サーバーの管理 | 向いているもの |
| :-: | :-: | :-: |
| Fargate | 不要（CPU とメモリを決めるだけ） | ふつうの Web・API・バッチ。まず考える |
| Fargate Spot | 不要（中断あり） | 止まってもよい処理を安く |
| EC2（Auto Scaling グループ） | 自分で（インスタンスの種類・AMI・パッチ） | 特定のインスタンスタイプ・細かい制御・リザーブドで安く |
| ECS マネージドインスタンス | AWS が（割り当て・パッチ・スケール） | GPU や特定のインスタンスタイプを使いたいが管理はしたくない |
| External（ECS Anywhere） | 自分で（オンプレミス） | オンプレミスのサーバーや VM を ECS でまとめて管理 |

### どこで動かす

#### 起動タイプ（きどうたいぷ / launch type）

- 意味：タスクやサービスを動かすインフラの種類。EC2・Fargate・External の 3 つ
- ポイント：Fargate＝サーバーレス。EC2＝自分の EC2 インスタンス（コンテナインスタンス）の上。External＝ECS Anywhere で登録したオンプレミスのサーバー。今はキャパシティプロバイダーで指定するのが勧められている
- 例：タスク定義の `requiresCompatibilities` に `FARGATE` を入れる

#### キャパシティプロバイダー（きゃぱしてぃぷろばいだー / capacity provider）

- 意味：タスクを動かすキャパシティの供給元。FARGATE・FARGATE_SPOT・EC2 の Auto Scaling グループ・ECS マネージドインスタンスがある
- ポイント：キャパシティプロバイダー戦略で、複数を割合（重み）で組み合わせられる。EC2 の Auto Scaling グループでは、マネージドスケーリングにすると、タスクの数に合わせて ECS がインスタンスを増減する
- 例：FARGATE を最低 2 つ、それ以上は FARGATE_SPOT に 3:1 で配る

#### ECS マネージドインスタンス（まねーじどいんすたんす / Amazon ECS Managed Instances）

- 意味：EC2 インスタンスの上でタスクを動かしつつ、インスタンスの割り当て・スケーリング・パッチ適用・保守を AWS に任せるキャパシティ
- ポイント：Fargate では選べない GPU・特定の CPU アーキテクチャ・高いネットワーク性能などのインスタンスを使える。AWS が要件を満たす低コストの汎用インスタンスタイプを選ぶ
- 例：GPU で推論するコンテナを、インスタンスの管理なしで動かす

#### ECS Anywhere（えにうぇあ / Amazon ECS Anywhere）

- 意味：オンプレミスのサーバーや VM を「外部インスタンス」として ECS クラスターに登録し、EXTERNAL 起動タイプでタスクを動かす機能
- ポイント：AWS のコンソールや API で、クラウドと同じ形でオンプレミスのコンテナを管理できる。外部インスタンスでは awsvpc ネットワークモードは使えない（bridge・host・none）
- 例：工場のサーバーで動くデータ収集のコンテナを、ECS からまとめて管理する

#### タスク配置戦略（たすくはいちせんりゃく / task placement strategy）

- 意味：EC2 起動タイプで、どのコンテナインスタンスにタスクを置くかの決め方。binpack・spread・random
- ポイント：binpack＝空いている CPU・メモリが最小になるよう詰める（インスタンス数を減らしてコスト削減）。spread＝AZ やインスタンスに均等に散らす（可用性）。random＝ランダム。サービスのタスクはデフォルトで AZ に spread される
- 例：AZ に spread し、その中で binpack する

### 権限とネットワーク

#### タスクロール（たすくろーる / task IAM role）

- 意味：タスクの中のコンテナで動くアプリケーションが、S3 や DynamoDB など他の AWS のサービスを呼ぶときに使う IAM ロール
- ポイント：アプリの権限はタスクロール。EC2 インスタンスのロールに付けると、そのインスタンスで動く全タスクが同じ権限を持ってしまう。アクセスキーをイメージや環境変数に入れない。CloudTrail にどのタスクが使ったかが残る
- 例：画像処理のタスクに、特定の S3 バケットへの読み書きだけを許す

#### タスク実行ロール（たすくじっこうろーる / task execution IAM role）

- 意味：ECS のエージェント（Fargate のエージェント）が、タスクを起動するために AWS の API を呼ぶときの IAM ロール
- ポイント：ECR からイメージをプルする・CloudWatch Logs にログを送る（awslogs）・Secrets Manager や Parameter Store から機密データを取り出す、に使う。コンテナの中のアプリからは使えない。「イメージがプルできない」「ログが出ない」なら実行ロールを疑う
- 例：`AmazonECSTaskExecutionRolePolicy` を付けたロールを、タスク定義の実行ロールに指定する

#### awsvpc ネットワークモード（えーだぶりゅーえすぶいぴーしー / awsvpc network mode）

- 意味：タスクごとに専用の ENI（Elastic Network Interface）とプライベート IP アドレスを割り当てるネットワークモード
- ポイント：タスクごとにセキュリティグループを付けられる。Fargate では awsvpc を使う。AWS は特別な理由がなければ awsvpc を勧めている。ロードバランサーのターゲットグループは、インスタンスではなく IP をターゲットタイプにする。ほかに bridge（Docker の仮想ネットワーク）・host（ホストのポートをそのまま使う）がある
- 例：決済のタスクだけ、DB のセキュリティグループから許可する

#### シークレットの受け渡し（しーくれっとのうけわたし / passing sensitive data）

- 意味：DB のパスワードや API キーを Secrets Manager か Parameter Store に置き、タスク定義の `secrets` で参照して、環境変数としてコンテナに渡す方法
- ポイント：タスク定義やイメージに平文で書かない。取り出すのはタスク実行ロールなので、実行ロールに読み取りの権限を付ける。自動ローテーションが要るなら Secrets Manager
- 例：`secrets` に `DB_PASSWORD` と Secrets Manager の ARN を書く

#### コンテナのストレージ（こんてなのすとれーじ / storage for tasks）

- 意味：タスクが使うディスク。Fargate のエフェメラルストレージ・EFS ボリューム・EBS ボリュームなど
- ポイント：Fargate のエフェメラルストレージはデフォルトで最低 20 GiB、最大 200 GiB まで増やせる（タスクが終わると消える）。複数のタスクで同じファイルを共有し、ずっと残すなら EFS（Fargate でも使える）
- 例：複数の Web タスクが、アップロードされた画像を EFS で共有する

## 08-3 スケーリングとデプロイ

### まとめ表

| やりたいこと | 使うもの |
| :-: | :-: |
| CPU の平均を 60% に保つようタスク数を増減 | サービスの自動スケーリング（ターゲット追跡） |
| 毎朝 8 時にタスクを増やす | スケジュールされたアクション |
| 1 つの ALB で /api と /web を別サービスへ | ALB のパスベースのルーティング |
| 1 台の EC2 に同じサービスのタスクを複数 | ALB の動的ホストポートマッピング |
| タスク数を減らさずに順に入れ替える | ローリング更新（minimumHealthyPercent 100・maximumPercent 200） |
| 本番に流す前に新版を確かめ、すぐ戻す | ブルー/グリーンデプロイ |
| 毎晩 2 時にバッチを 1 回動かす | EventBridge スケジューラで ECS のタスクを起動 |

### ふやす・つなぐ・入れ替える

#### サービスの自動スケーリング（さーびすのじどうすけーりんぐ / service auto scaling）

- 意味：Application Auto Scaling で、ECS サービスのタスク数（desiredCount）を自動で増減する機能
- ポイント：ターゲット追跡（CPU の平均・メモリ・ALB のターゲットあたりのリクエスト数を目標値に保つ）・ステップ（しきい値ごとに決めた数を増減）・スケジュール（日時で）・予測（過去のパターンから）がある。タスクを増やしても EC2 のキャパシティが足りないときは、キャパシティプロバイダーのマネージドスケーリングでインスタンスも増やす
- 例：CPU の平均使用率を 60% に保つ

#### ALB との統合（えーえるびーとのとうごう / Application Load Balancer）

- 意味：ECS サービスを Application Load Balancer の後ろに置き、タスク間にリクエストを分ける構成
- ポイント：ALB は HTTP/HTTPS（レイヤー 7）でパスベースのルーティングができ、1 つの ALB で複数のサービスを振り分けられる。EC2 起動タイプでは動的ホストポートマッピング（ホストポート 0）で、1 台のインスタンスに同じサービスのタスクを複数置ける。TCP/UDP なら NLB
- 例：`/api/*` は API サービス、`/*` は Web サービスへ

#### ローリング更新（ろーりんぐこうしん / rolling update）

- 意味：動いているタスクを、新しいタスク定義のタスクに少しずつ置き換えるデプロイ方法（デプロイタイプ ECS）
- ポイント：minimumHealthyPercent＝デプロイ中に正常に動いていなければならないタスク数の下限（％）。maximumPercent＝同時に動かしてよいタスク数の上限（％）。100 と 200 なら、先に新しいタスクを立ててから古いものを止めるので、処理能力が落ちない
- 例：desiredCount 4、minimumHealthyPercent 100、maximumPercent 200

#### ブルー/グリーンデプロイ（ぶるーぐりーんでぷろい / blue/green deployment）

- 意味：今の本番（ブルー）と新しい版（グリーン）を同時に用意し、テストのトラフィックで確かめてから本番のトラフィックを切り替えるデプロイ方法
- ポイント：切り替えたあともベイク時間のあいだはブルーが残るので、問題があればすぐ戻せる（ロールバック）。ロードバランサーか Service Connect を使うサービスでは、ECS がトラフィックの切り替えを管理する
- 例：グリーンをテスト用のリスナーで確かめ、問題なければ本番のリスナーを切り替える

#### スケジュールされたタスク（すけじゅーるされたたすく / scheduled tasks）

- 意味：決めた日時やくり返しで、ECS のタスクを起動する方法。EventBridge スケジューラ（cron・rate・1 回だけ）を使う
- ポイント：ずっと動かす必要のないバッチは、サービスにせずスケジュールで起動すれば、動いている間だけ料金がかかる。15 分を超えるバッチを Lambda の代わりに動かすときの定番
- 例：毎日 2 時に、集計のタスクを Fargate で 1 回動かす

## 08-4 Amazon EKS

### まとめ表

| 選び方 | ECS | EKS |
| :-: | :-: | :-: |
| ひとことで | AWS 独自のシンプルなオーケストレーション | Kubernetes をマネージドで |
| 向いている | AWS だけで動かす・学ぶことを少なく | 既存の Kubernetes のマニフェスト・ツール・ノウハウを使う／複数の環境で同じ Kubernetes |
| サーバーレス | Fargate | Fargate（Fargate プロファイル）・EKS Auto Mode |
| アプリの権限 | タスクロール | EKS Pod Identity・IRSA |
| オンプレミス | ECS Anywhere | EKS Hybrid Nodes・EKS Anywhere・Outposts |

### EKS の部品

#### Amazon EKS（いーけーえす / Amazon Elastic Kubernetes Service）

- 意味：Kubernetes のクラスターを動かすための、AWS のフルマネージドの Kubernetes サービス
- ポイント：Kubernetes のコントロールプレーンは AWS が管理する。Kubernetes そのものなので、既存のマニフェスト・Helm・kubectl などをそのまま使える。AWS とオンプレミスの両方で同じ Kubernetes を使いたいときにも向く
- 語の意味：Kubernetes＝コンテナを自動で配置・管理するオープンソースのしくみ（「操舵手」の意味のギリシャ語）

#### マネージド型ノードグループ（まねーじどがたのーどぐるーぷ / managed node group）

- 意味：EKS のノード（Pod を動かす EC2 インスタンス）のプロビジョニングとライフサイクル管理を自動化する機能
- ポイント：ノードは EKS が管理する EC2 Auto Scaling グループの一部として作られ、複数の AZ にまたがれる。更新や終了のときはノードのドレイン（Pod の退避）も自動で行う。インスタンスやグループは自分のアカウントにある
- 例：m7g.large のノードを 3〜10 台で動かすノードグループ

#### EKS の Fargate（ふぁーげーと / AWS Fargate for EKS）

- 意味：ノードを持たずに、Pod を Fargate で動かす方法。Fargate プロファイルに一致した Pod が Fargate で動く
- ポイント：Fargate プロファイル（名前空間とラベル）に一致しない Pod は Pending のままになることがある。DaemonSet は使えない。Pod はプライベートサブネットだけ。各 Pod は VM で分離される
- 例：名前空間 `batch` の Pod だけ Fargate で動かす

#### EKS Auto Mode（おーともーど / EKS Auto Mode）

- 意味：コントロールプレーンだけでなく、ノード（データプレーン）の管理まで AWS が行う EKS の動かし方
- ポイント：インスタンスの自動プロビジョニング・最適なインスタンスの選択・スケーリング・OS のパッチ適用までを AWS が行う。Karpenter をもとに作られている。マネージド型ノードグループより、さらに手間を減らしたいとき
- 例：ノードの面倒を見る人がいないチームで EKS を使う

#### Horizontal Pod Autoscaler（ほりぞんたるぽっどおーとすけーらー / Horizontal Pod Autoscaler, HPA）

- 意味：CPU 使用率などに応じて、Pod の数を自動で増減する Kubernetes の機能
- ポイント：増減するのは Pod の数。Pod が増えてノードに入りきらないとき、ノード（EC2）を増やすのは Karpenter や Cluster Autoscaler。役割を混同しない
- 例：Web の Pod の CPU を 50% に保つよう 2〜20 個で増減する

#### Karpenter と Cluster Autoscaler（かーぺんたー / Karpenter and Cluster Autoscaler）

- 意味：Pod が動けないとき（Pending）にノードを増やし、空いたら減らす、Kubernetes のクラスターのオートスケーラー
- ポイント：Karpenter は、負荷に合った適切なサイズの EC2 インスタンスを 1 分未満で起動する、柔軟で速いオートスケーラー。Cluster Autoscaler は Auto Scaling グループの台数を増減する昔からの方法。EKS Auto Mode は Karpenter をもとにしている
- 例：GPU が要る Pod が来たら、Karpenter が GPU インスタンスを 1 台足す

#### EKS Pod Identity と IRSA（ぽっどあいでんてぃてぃ / EKS Pod Identity and IAM roles for service accounts）

- 意味：Pod の中のアプリに、Pod（Kubernetes のサービスアカウント）ごとの IAM ロールの一時的な認証情報を渡すしくみ
- ポイント：EC2 のインスタンスプロファイルと同じように、アプリに認証情報を配る。ノードのロールを使うと全 Pod が同じ権限になり、最小権限にならない。IRSA（サービスアカウントの IAM ロール）は、IAM ロールを Kubernetes のサービスアカウントに関連付ける方法。EKS Pod Identity も同じ目的のしくみ
- 例：注文の Pod には DynamoDB の権限だけ、画像の Pod には S3 の権限だけ

#### EKS Hybrid Nodes と EKS Anywhere（はいぶりっどのーど・えにうぇあ / Amazon EKS Hybrid Nodes and EKS Anywhere）

- 意味：オンプレミスで EKS を使う方法。Hybrid Nodes は自社のサーバーを AWS リージョンの EKS クラスターのノードにする。EKS Anywhere は自己完結（エアギャップ）の環境で Kubernetes クラスターを自分で動かす
- ポイント：Hybrid Nodes と EKS on Outposts は、AWS リージョンへの信頼できる接続が要る（コントロールプレーンはリージョン）。インターネットから切り離された環境なら EKS Anywhere。ECS で同じことをするなら ECS Anywhere
- 例：工場のサーバーを、東京リージョンの EKS クラスターのノードとして使う
