## 10-1 高可用性の基本

### まとめ表

| 守りたい障害 | 範囲 | 基本の対策 |
| :-: | :-: | :-: |
| 1 台のインスタンス・1 つのディスク | コンポーネント | 複数台＋ロードバランサー・Auto Scaling で置き換え |
| 1 つのデータセンター・1 つの AZ | AZ | 1 つのリージョンの中の複数の AZ（マルチ AZ） |
| リージョン全体の大規模な災害・規制の要件 | リージョン | 別のリージョンへの DR（10-2 の 4 つの戦略） |
| 誤った削除・データの破損・ランサムウェア | データ | ポイントインタイムのバックアップ（レプリケーションだけでは守れない） |

### リージョンと AZ

#### リージョン（りーじょん / Region）

- 意味：AWS のデータセンターが集まった、別々の地理的なエリア。東京（ap-northeast-1）・大阪（ap-northeast-3）など
- ポイント：各リージョンは他のリージョンから完全に分離されるように作られていて、リソースはリージョン間で自動ではレプリケートされない。別のリージョンにも置きたいなら、自分でコピーやレプリケーションを設定する
- 例：東京で本番、大阪を DR 用にする

#### アベイラビリティーゾーン（あべいらびりてぃーぞーん / Availability Zone, AZ）

- 意味：1 つのリージョンの中にある、複数の独立した場所。各リージョンに少なくとも 3 つある
- ポイント：AZ どうしは、同時に壊れないように意味のある距離（最大でおよそ 100 km）離れているが、1 桁ミリ秒のレイテンシーで同期レプリケーションできるほど近い。1 つの AZ だけに置いたワークロードは高可用性がない
- 例：ap-northeast-1a・1c・1d に EC2 を分けて置く

#### マルチ AZ と単一障害点（たんいつしょうがいてん / Multi-AZ and single point of failure）

- 意味：単一障害点（SPOF）＝そこが 1 つ壊れるとシステム全体が止まる部分。マルチ AZ＝複数の AZ に分けて置き、1 つの AZ が落ちても続けられるようにすること
- ポイント：1 つの AZ の 1 台の EC2・1 つの NAT ゲートウェイ・シングル AZ の DB は SPOF。データセンター 1 つの障害までなら、1 つのリージョンの中のマルチ AZ で守れる
- 例：EC2 を 2 つの AZ に分け、ALB の後ろに置き、RDS をマルチ AZ にする

#### 高可用性とディザスタリカバリ（こうかようせい・でぃざすたりかばり / high availability and disaster recovery）

- 意味：高可用性＝ワークロードの部品（コンポーネント）が壊れてもサービスを続けること。ディザスタリカバリ（DR）＝大規模な災害のあと、ワークロード全体の別のコピーで復旧すること
- ポイント：どちらも監視・複数の場所・自動フェイルオーバーを使うが、目的が違う。高可用性のための継続的なレプリケーションは、誤った削除や破損もそのままコピーしてしまう。DR にはポイントインタイムのバックアップも要る
- 例：マルチ AZ の RDS（高可用性）に加え、別リージョンにスナップショットをコピーする（DR）

#### 静的安定性（せいてきあんていせい / static stability）

- 意味：障害が起きても、新しいリソースの起動や設定の変更に頼らずに、そのまま動き続けられるように、前もって十分なキャパシティを置いておく設計
- ポイント：障害時に新しいインスタンスを起動する設計は安いが、大規模な障害のときは起動の仕組みや残りの AZ のキャパシティに頼るので、確実ではない。1 つの AZ が落ちても残りで全負荷を受けられる台数を、前もって各 AZ に置く
- 例：必要な 6 台を 3 つの AZ に 3 台ずつ（計 9 台）置き、1 つの AZ が落ちても 6 台残るようにする（Claude が作った例）

#### コントロールプレーンとデータプレーン（こんとろーるぷれーん・でーたぷれーん / control plane and data plane）

- 意味：コントロールプレーン＝リソースを作る・変える・消すための仕組み（API での起動や設定）。データプレーン＝動いているリソースがサービスを提供する部分
- ポイント：データプレーンのほうが、ふつうは可用性の設計目標が高い。回復性を最大にするには、フェイルオーバーの操作をデータプレーンの操作だけで済むように設計する。Auto Scaling で台数を増やすのはコントロールプレーンの操作
- 例：障害時にインスタンスを起動する（コントロールプレーン）より、前から動いているインスタンスにトラフィックを向ける（データプレーン）

### 自動化と見える化

#### Infrastructure as Code と StackSets（いんふらすとらくちゃあずこーど / Infrastructure as Code, CloudFormation StackSets）

- 意味：インフラの構成をコード（CloudFormation のテンプレートなど）で書き、同じ環境をくり返し作れるようにすること。StackSets は、複数のアカウントとリージョンにスタックを 1 回の操作で作る・更新する・消す機能
- ポイント：DR リージョンにインフラを作り直すとき、手作業ではなくテンプレートから確実にデプロイできる。AWS CDK ならふつうのプログラミング言語で書け、CloudFormation に変換される
- 例：本番と同じ VPC・ALB・Auto Scaling グループのテンプレートを、StackSets で東京と大阪に配る

#### AMI のコピー（えーえむあいのこぴー / copy an AMI）

- 意味：AMI（EC2 の起動に使うイメージ）を、別のリージョンや別のアカウントにコピーすること
- ポイント：AMI はリージョン固有のリソースなので、別のリージョンで同じ AMI からインスタンスを起動するには、そのリージョンにコピーしておく必要がある。DR リージョンの AMI を最新に保つ
- 例：本番の AMI を作るたびに大阪にもコピーする

#### Service Quotas（さーびすくぉーた / Service Quotas）

- 意味：AWS のサービスごとのリソース・操作・項目の最大値（クォータ、制限とも呼ぶ）を見て管理するサービス。必要なら引き上げを申請する
- ポイント：DR リージョンのクォータが本番より低いままだと、災害時に本番と同じ規模まで増やせない。DR リージョンのクォータも前もって本番と同じくらいに引き上げておく
- 例：大阪の EC2 の vCPU のクォータを、東京と同じに引き上げておく

#### Amazon RDS Proxy（あーるでぃーえすぷろきし / Amazon RDS Proxy）

- 意味：アプリと RDS・Aurora のあいだに入り、データベースへの接続をプールして共有するマネージドのプロキシ
- ポイント：Lambda のように接続を大量に作るアプリで、DB の接続数があふれるのを防ぐ。DB のフェイルオーバーのとき、アプリの接続を保ったままスタンバイに自動でつなぎ、障害への耐性を高める。IAM 認証や Secrets Manager の認証情報も使える
- 例：数千の Lambda から Aurora に接続するので RDS Proxy を挟む

#### AWS X-Ray（えっくすれい / AWS X-Ray）

- 意味：アプリが処理するリクエストのデータ（トレース）を集め、どこで遅れたりエラーになったりしているかを見せるサービス
- ポイント：複数のサービス（API Gateway・Lambda・DynamoDB など）をまたぐリクエストの流れを追い、ボトルネックを見つける。CloudWatch はメトリクスとログ、X-Ray はリクエストの経路
- 例：注文 API のどのサービスで時間がかかっているかを調べる

#### AWS Fault Injection Service と Resilience Hub（えふあいえす・れじりえんすはぶ / AWS FIS and AWS Resilience Hub）

- 意味：AWS FIS＝わざと障害を起こす実験（フォールトインジェクション）を行うマネージドサービス。Resilience Hub＝アプリのレジリエンスの目標（RTO・RPO）を決め、それを満たせそうかを評価して改善を勧めるサービス
- ポイント：FIS は条件を満たしたら実験を自動で止めるなどの安全装置を持つ。Resilience Hub は Well-Architected フレームワークに基づいて推奨する。「障害を実際に起こして確かめる」なら FIS、「目標を満たせるか評価する」なら Resilience Hub
- 例：FIS で 1 つの AZ のインスタンスを止め、サービスが続くかを確かめる

## 10-2 DR の目標と 4 つの戦略

### まとめ表

| 戦略 | DR リージョンに常にあるもの | 復旧時間 | コスト |
| :-: | :-: | :-: | :-: |
| バックアップと復元 | バックアップだけ | 最も長い | 最も低い |
| パイロットライト | データ（常にレプリケーション）＋止めたインフラ | バックアップより短い | 低い |
| ウォームスタンバイ | 縮小した、すぐ動く本番のコピー | パイロットライトより短い | 中 |
| マルチサイトアクティブ/アクティブ | 全部（全リージョンでトラフィックを処理） | ほぼゼロ | 最も高い |

### 目標

#### 事業継続計画（じぎょうけいぞくけいかく / business continuity plan, BCP）

- 意味：災害などで業務が止まったときに、事業を続けたり早く戻したりするための計画。DR 計画はその一部
- ポイント：ビジネスへの影響分析とリスク評価で、止まったときの損失を数字にし、RTO と RPO を決める。復旧の仕組みのコストが、障害や損失のコストより高いなら（規制などの理由がない限り）作らない
- 例：注文システムが 1 時間止まると 500 万円の損失なので、RTO を 30 分にする（Claude が作った例）

#### 目標復旧時間（もくひょうふっきゅうじかん / Recovery Time Objective, RTO）

- 意味：サービスが止まってから、復旧するまでに許される最大の時間
- ポイント：「どれだけ早く戻すか」。RTO を短くするほど、DR リージョンに前もって動かしておくものが増え、コストが上がる
- 例：RTO 15 分＝止まってから 15 分以内にサービスを戻す
- 語の意味：Recovery＝回復、Time＝時間、Objective＝目標

#### 目標復旧時点（もくひょうふっきゅうじてん / Recovery Point Objective, RPO）

- 意味：最後にデータを戻せる時点から、障害が起きるまでに許される最大の時間。どこまでのデータの損失を許すか
- ポイント：「どれだけ前のデータに戻るか」。バックアップの頻度が RPO を決める。1 日 1 回のバックアップなら最大 1 日分を失う。RPO をほぼゼロにするには継続的なレプリケーション
- 例：RPO 5 分＝失ってよいデータは最大 5 分ぶん
- 語の意味：Recovery＝回復、Point＝時点、Objective＝目標

### 4 つの戦略

#### バックアップと復元（ばっくあっぷとふくげん / backup and restore）

- 意味：データのバックアップを DR リージョンなどに保存しておき、災害のときにインフラ・設定・アプリを作り直してデータを復元する戦略
- ポイント：4 つの中で最もコストが低く、RPO と RTO は最も長い。データだけでなく、インフラ（CloudFormation のテンプレート）や AMI もバックアップしておく。データの損失や破損への対策としても使う
- 例：AWS Backup で毎日のスナップショットを大阪にコピーし、災害時に CloudFormation で環境を作って復元する

#### パイロットライト（ぱいろっとらいと / pilot light）

- 意味：データベースなどのデータは DR リージョンに常にレプリケートしておき、アプリのサーバーなどはコードと設定を用意したうえで「スイッチオフ」にしておく戦略
- ポイント：ガスのコンロの種火のように、核の部分だけを常に点けておく。そのままではリクエストを処理できず、災害時にサーバーを「オン」にして増やす必要がある。ウォームスタンバイより安く、時間がかかる
- 例：Aurora のデータは大阪に常にレプリケートし、アプリの Auto Scaling グループは 0 台にしておく

#### ウォームスタンバイ（うぉーむすたんばい / warm standby）

- 意味：本番の環境を小さくしたコピーを、DR リージョンで常に動かしておく戦略
- ポイント：パイロットライトとの違いは、小さい規模ながらすぐにトラフィックを処理できること。災害時はスケールアップ（増やす）だけでよい。常に動いているので、テストもしやすい
- 例：大阪で本番の 1/4 の台数を動かしておき、災害時に Auto Scaling で本番の規模まで増やす

#### マルチサイトアクティブ/アクティブ（まるちさいとあくてぃぶあくてぃぶ / multi-site active/active）

- 意味：複数のリージョンでワークロードを同時に動かし、すべてのリージョンで本番のトラフィックを処理する戦略
- ポイント：最も複雑でコストが高いが、ほとんどの災害で復旧時間をほぼゼロにできる。フェイルオーバーという操作はなく、壊れたリージョンからトラフィックを外すだけ。データの破損への備えとしてバックアップは要る
- 例：東京と大阪の両方でユーザーを受け、DynamoDB グローバルテーブルで書き込みを両方に

#### ホットスタンバイ（ほっとすたんばい / hot standby）

- 意味：DR リージョンに本番の全負荷を処理できるキャパシティを用意しておき、ふだんは 1 つのリージョンだけがトラフィックを処理するアクティブ/パッシブの形
- ポイント：災害時に Auto Scaling（コントロールプレーン）で増やすのを待たなくてよい、静的に安定した形。ウォームスタンバイ（縮小版）とマルチサイト（全リージョンで処理）のあいだ
- 例：大阪にも東京と同じ台数を置き、ふだんはトラフィックを送らない

#### フェイルオーバーとフェイルバック（ふぇいるおーばー・ふぇいるばっく / failover and failback）

- 意味：フェイルオーバー＝障害のときに、トラフィックをプライマリから DR 側に切り替えること。フェイルバック＝復旧したあとで、プライマリに戻すこと
- ポイント：アクティブ/パッシブ（パイロットライト・ウォームスタンバイ・ホットスタンバイ）では、ふだんは全トラフィックがプライマリへ行き、障害時に DR リージョンに切り替える。誤ったアラームで切り替えると損失が出るので、自動ではなく手動で始めることも多い
- 例：Route 53 のヘルスチェックで東京の異常を検知し、大阪に切り替える

#### DR のテスト（でぃーあーるのてすと / testing disaster recovery）

- 意味：DR リージョンへのフェイルオーバーを定期的に実際に行い、RTO と RPO を満たせるかを確かめること
- ポイント：くり返しテストしている経路しか、いざというときにうまく動かない。テストしないと、DR リージョンのキャパシティやサービスクォータが足りない・AMI が古い、などに気付けない
- 例：半年に 1 回、大阪への切り替え訓練をする

## 10-3 データの保護と複製・切り替え

### まとめ表

| 手段 | 何を守る | RPO の目安 |
| :-: | :-: | :-: |
| スナップショット（AWS Backup） | 誤った削除・破損・災害 | バックアップの間隔 |
| 継続的バックアップ（PITR） | 秒単位で戻したい | 最大 35 日の範囲で 1 秒単位 |
| 継続的なレプリケーション（S3 CRR・Aurora グローバル・DynamoDB グローバルテーブル） | リージョンの災害 | ほぼゼロ（ただし削除や破損もコピーされる） |
| Vault Lock・論理エアギャップボールト | 悪意のある削除・ランサムウェア | — |

### バックアップ

#### AWS Backup（えーだぶりゅーえすばっくあっぷ / AWS Backup）

- 意味：EBS・EC2・RDS・Aurora・DynamoDB・EFS・FSx・Storage Gateway などのバックアップを、1 か所でまとめて設定・自動化・監視できるフルマネージドサービス
- ポイント：サービスごとにバラバラにスナップショットを取るのではなく、バックアッププランで一元管理する。リージョン間・アカウント間のコピーもできる
- 例：全部の本番リソースをタグで選び、1 つのバックアッププランで守る

#### バックアッププラン（ばっくあっぷぷらん / backup plan）

- 意味：AWS Backup で、どのリソースを、いつ・どのくらいの頻度でバックアップし、どれだけ保持するかを決めるポリシー
- ポイント：リソースを割り当てると、プランに従って自動でバックアップと保持をする。バックアップの頻度が RPO を決める。コピー先のリージョンやアカウントもプランに書ける
- 例：毎日 1 回、35 日保持し、大阪のボールトにもコピーする

#### バックアップボールトと Vault Lock（ばっくあっぷぼーると・ぼーるとろっく / backup vault and AWS Backup Vault Lock）

- 意味：バックアップボールト＝バックアップを保存し整理する入れ物。Vault Lock＝ボールトのバックアップを、保持期間が終わるまで削除できないようにするオプション機能
- ポイント：ガバナンスモードは十分な IAM 権限を持つユーザーなら解除できる。コンプライアンスモードは、猶予期間が過ぎると、ルートユーザーも AWS も、ボールトの設定の変更や削除ができない。ランサムウェアや内部の不正からバックアップを守る
- 例：規制で 7 年の保存が要るバックアップを、コンプライアンスモードのボールトに入れる

#### 論理エアギャップボールト（ろんりえあぎゃっぷぼーると / logically air-gapped vault）

- 意味：AWS Backup の、ふつうのボールトより保護を強めた特別なボールト。Vault Lock のコンプライアンスモードが備わり、他のアカウントと共有してすばやく復旧できる
- ポイント：ボールトを持つアカウントにアクセスできなくなっても（乗っ取り・閉鎖など）、マルチパーティー承認（MPA）を通じて別のアカウントから復元できるようにする。耐障害性を高めるには、別のリージョンのこのボールトにもコピーする
- 例：本番アカウントが侵害されたとき、セキュリティ用のアカウントから復元する

#### クロスリージョンとクロスアカウントのコピー（こぴー / cross-Region and cross-account backup copy）

- 意味：バックアップを別のリージョンや、組織の中の別のアカウントにコピーすること
- ポイント：リージョン間＝本番から離れた場所に保存する事業継続や規制の要件に。アカウント間＝本番アカウントが侵害されてもバックアップを守る。KMS で暗号化したものはキーの扱いに注意する
- 例：東京の本番アカウントのバックアップを、大阪のバックアップ専用アカウントにコピーする

#### 継続的バックアップとポイントインタイムリカバリ（けいぞくてきばっくあっぷ / continuous backup and point-in-time recovery, PITR）

- 意味：最初にフルバックアップを取り、そのあとトランザクションログを定期的にバックアップして、指定した時刻に 1 秒単位で戻せるようにするバックアップ
- ポイント：最大 35 日前まで戻せる。スナップショットのバックアップと両方で守ることが勧められている。「誤って消す直前の時刻に戻したい」なら PITR
- 例：午後 3 時 12 分に誤って更新したので、3 時 11 分の状態に戻す

### 複製と切り替え

#### クロスリージョンの継続的なレプリケーション（れぷりけーしょん / continuous cross-Region replication）

- 意味：データを別のリージョンに、継続的に非同期でコピーし続けること。S3 のレプリケーション・RDS のクロスリージョンリードレプリカ・Aurora グローバルデータベース・DynamoDB グローバルテーブルなど
- ポイント：パイロットライト以上の戦略で RPO を小さくする基本。ただし削除や破損もそのままコピーされるので、バックアップ（ポイントインタイム）と組み合わせる。RDS のリードレプリカは、切り替えのときに昇格させる（数分かかる）
- 例：S3 のバケットを大阪のバケットにレプリケートし、バージョニングも有効にしておく

#### Aurora グローバルデータベース（おーろらぐろーばるでーたべーす / Amazon Aurora Global Database）

- 意味：1 つの Aurora データベースを、複数のリージョンにまたがって動かす機能。書き込みはプライマリリージョン、ほかのリージョンは読み取り
- ポイント：ふつう 1 秒未満のレイテンシーで、最大 5 つのセカンダリリージョンにレプリケートする。プライマリが落ちたら、セカンダリのリージョンを昇格させて、1 分以内に読み書きを引き受けられる。書き込みを 1 つのリージョンに集める「書き込みグローバル」に向く
- 例：東京がプライマリ、大阪がセカンダリの Aurora

#### DynamoDB グローバルテーブル（だいなもでぃーびーぐろーばるてーぶる / Amazon DynamoDB global tables）

- 意味：DynamoDB のテーブルを複数のリージョンに置き、どのリージョンでも読み書きできるようにする機能
- ポイント：書き込みを近いリージョンで受ける「書き込みローカル」ができ、マルチサイトアクティブ/アクティブに向く。同時に更新されたときは、最後に書いたものが勝つ
- 例：東京と大阪の両方でユーザーのカートを更新する

#### AWS Elastic Disaster Recovery（いらすてぃっくでぃざすたりかばり / AWS Elastic Disaster Recovery, AWS DRS）

- 意味：サーバーのブロックレベルのレプリケーションで、オンプレミスや別のクラウド、EC2 のサーバー（アプリやサーバー上の DB）を AWS に継続的にレプリケートし、災害時にすぐ起動できるようにするサービス
- ポイント：データは安いストレージと最小限のコンピューティングのステージングエリアに置き、サーバーは「スイッチオフ」にしておく（パイロットライト）。アプリを作り変えずに DR を用意できる。RDS は対象外
- 例：オンプレミスの業務サーバー 30 台の DR 先を AWS にする

#### トラフィックの切り替え（とらふぃっくのきりかえ / traffic management for failover）

- 意味：DR のとき、利用者のトラフィックを DR リージョンに向ける方法。Route 53・Global Accelerator・CloudFront
- ポイント：Route 53＝ヘルスチェックで DNS のフェイルオーバー。Global Accelerator＝エニーキャストの同じ静的 IP のまま、正常なリージョンに送る（トラフィックダイヤルで割合も変えられる）。CloudFront のオリジンフェイルオーバー＝リクエストごとに、失敗したらセカンダリのオリジンへ
- 例：Route 53 のフェイルオーバールーティングで、東京の ALB が異常なら大阪の ALB へ

- 問：Web アプリが 1 つの AZ の 1 台の EC2 と、シングル AZ の RDS で動いている。データセンター 1 つの障害でサービスが止まらないようにしたい。最もコストを抑えた対策はどれか。
- ア：別のリージョンに同じ構成を作り、マルチサイトアクティブ/アクティブにする
- イ：EC2 のインスタンスタイプを大きくする
- ウ：EC2 の EBS スナップショットを毎日取る
- エ：EC2 を複数の AZ に分けて ALB の後ろに置き、RDS をマルチ AZ にする
- 正解：エ

- イの意味：1 台のまま（単一障害点）で、AZ が落ちると止まる。
- ウの意味：データは戻せるが、復旧まで止まる。サービスを止めない対策ではない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS ホワイトペーパー「クラウド内の災害対策は異なる」（『単一の AWS リージョン内の複数のアベイラビリティーゾーンにデプロイすることで、ワークロードを単一の (または複数の) データセンターの障害から保護できます。』））

- アの意味：マルチ AZ は AZ の障害のときにスタンバイへフェイルオーバーする。
- イの意味：正しい。
- ウの意味：マルチ AZ のスタンバイは同じリージョンの別の AZ にある。
- エの意味：そのような制限はない。
- 出典：オリジナル問題（根拠：AWS ホワイトペーパー「高可用性はディザスタリカバリではありません」（『プライマリストレージデバイスでファイルを削除または破損した場合、それらの破壊的な変更はセカンダリストレージデバイスにレプリケートできます。』『代わりに、DR 戦略の一部としてpoint-in-timeバックアップも必要です。』））

### 10-2 DR の目標と 4 つの戦略

#### 問 aws-10-o11

- 問：「障害が起きても、失ってよいデータは最大 15 分ぶん。サービスは 2 時間以内に戻す」という要件がある。RPO と RTO の組み合わせとして正しいものはどれか。
- ア：RPO 15 分、RTO 2 時間
- イ：RPO 2 時間、RTO 15 分
- ウ：RPO 15 分、RTO 15 分
- エ：RPO 2 時間、RTO 2 時間
- 正解：ア
- 解説：RPO は最後の復旧時点から許されるデータの損失の時間、RTO はサービスが止まってから復旧までに許される時間。
- アの意味：正しい。
- イの意味：RPO と RTO が逆。
- ウの意味：RTO が要件より厳しく、コストが上がる。
- エの意味：RPO が要件より緩く、2 時間ぶんのデータを失う。
- 出典：オリジナル問題（根拠：AWS ホワイトペーパー「事業継続計画 (BCP)」（『**目標復旧時間 (RTO)** は、サービスの中断からサービスの復旧までの最大許容遅延時間です。』『**目標復旧時点 (RPO)** は、最後のデータ復旧時点からの最大許容時間です。』））

#### 問 aws-10-o12

- 問：社内の資料管理システムの DR を用意したい。RPO・RTO は 24 時間でよく、DR のためのコストはできるだけ低くしたい。最も適した戦略はどれか。

- 正解：エ
- 解説：バックアップと復元は 4 つの戦略のうち最もコストと複雑さが低い。RPO・RTO が長くてよいなら十分。

- イの意味：縮小版の本番を常に動かすので、さらに高い。
- ウの意味：最も複雑でコストが高い。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS ホワイトペーパー「クラウド内での災害対策オプション」（『AWS 内で利用できるディザスタリカバリ戦略は、低コストと複雑さの低いバックアップから、複数のアクティブなリージョンを使用したより複雑な戦略まで、4 つのアプローチに広く分類できます。』））

- 問：パイロットライトとウォームスタンバイの違いとして正しいものはどれか。
