## 02-1 組織とアカウント

### まとめ表

| 部品 | 中身 | 覚えること |
| :-: | :-: | :-: |
| 組織 | アカウントの集まり（木の形） | 管理アカウント1つ＋メンバーアカウント |
| ルート（管理ルート） | 木のいちばん上の入れ物 | 組織に1つだけ。自動でできる |
| OU（組織単位） | アカウントのグループ | 入れ子にできる。ポリシーをまとめて付ける |
| 管理アカウント | 組織を作ったアカウント | 全員分の料金を払う。SCP が効かない |
| メンバーアカウント | それ以外のアカウント | 一度に1つの組織にだけ入れる |

### 組織のしくみ

#### AWS Organizations（えーだぶりゅーえすおーがないぜーしょんず / AWS Organizations）

- 意味：複数の AWS アカウントを1つの組織にまとめ、作成・グループ分け・ポリシーの適用・請求を一元的に管理するサービス
- ポイント：AWS は、アカウントを「アクセス許可・セキュリティ・コスト・ワークロードの自然な境界」とし、環境を広げるときは複数のアカウントに分けるのをベストプラクティスとしている。ほかのサービス（GuardDuty・CloudTrail・Backup など）と統合すると、組織の全アカウントで使える
- 例：本番・開発・セキュリティ・ログ保管をそれぞれ別のアカウントにして、1つの組織にまとめる

#### 管理アカウント（かんりあかうんと / management account）

- 意味：組織を作ったアカウント。アカウントの作成・招待・削除、ポリシーの付け外しなどを行い、組織全体の料金を払う（支払者アカウント）
- ポイント：SCP は管理アカウントのユーザーやロールには効かない。そのため、管理アカウントには作業用のリソースを置かず、組織の管理に必要な作業だけに使うのが AWS のおすすめ。管理アカウントをほかのアカウントに変えることはできない
- 例：日々のワークロードはメンバーアカウントで動かす

#### メンバーアカウント（めんばーあかうんと / member account）

- 意味：組織に入っている、管理アカウント以外のアカウント
- ポイント：一度に入れる組織は1つだけ。管理アカウントで新しく作るか、既存のアカウントを招待して入れる。SCP の制限を受ける（そのアカウントのルートユーザーも）

#### 組織単位（そしきたんい / organizational unit, OU）

- 意味：組織の中のアカウントのグループ。OU の中に OU を入れて階層にできる
- ポイント：同じルールを当てたいアカウントをまとめ、OU にポリシーを付けると、その下のアカウントすべてに効く
- 例：「本番 OU」「開発 OU」「セキュリティ OU」に分ける
- 語の意味：Organizational＝組織の、Unit＝単位

#### 管理ルート（かんりるーと / root）

- 意味：組織の階層のいちばん上の入れ物。組織を作ると自動でできる、組織に1つだけのもの
- ポイント：ルートユーザー（#01）とは別物。ルートに SCP を付けると、すべての OU とメンバーアカウントに効く（管理アカウントには効かない）

#### すべての機能と一括請求（すべてのきのうといっかつせいきゅう / all features, consolidated billing）

- 意味：組織の機能のセット。「すべての機能」は既定でおすすめのもので、SCP などのポリシーやサービスの統合も使える。「一括請求（コンソリデーティッドビリング）」は請求をまとめる機能だけ
- ポイント：SCP を使うには「すべての機能」が必要。一括請求だけの組織から「すべての機能」に変えるときは、招待で入ったメンバーアカウントすべての承認が要る

#### 委任管理者（いにんかんりしゃ / delegated administrator）

- 意味：管理アカウントの代わりに、組織のポリシーや、組織と統合した AWS のサービスを管理するよう指定されたメンバーアカウント
- ポイント：管理アカウントで行う作業を減らすためのしくみ。委任管理者はメンバーアカウントなので SCP の制限を受ける
- 例：セキュリティ用のアカウントを GuardDuty の委任管理者にする

#### タグポリシー（たぐぽりしー / tag policy）

- 意味：組織のアカウントのリソースに付けるタグを標準化するポリシー
- ポイント：タグのキーや値の大文字・小文字などをそろえる。コスト配分タグ（#23）の表記ゆれを防ぐのに使う。SCP のように操作を止めるためのものではない

#### AWS RAM（えーだぶりゅーえすらむ / AWS Resource Access Manager）

- 意味：作ったリソースを、別のアカウント・OU・組織全体と安全に共有するサービス
- ポイント：リソースごとにリソースベースのポリシーを書かなくても共有できる。共有できる代表例は VPC のサブネット、Transit Gateway、Route 53 Resolver のルール
- 例：ネットワーク用アカウントの VPC のサブネットを、アプリ用のアカウントに共有する
- 語の意味：Resource＝リソース、Access＝アクセス、Manager＝管理するもの

## 02-2 ガードレール（SCP と Control Tower）

### まとめ表

| しくみ | 付ける先 | 何を制限するか |
| :-: | :-: | :-: |
| SCP | ルート・OU・アカウント | メンバーアカウントの IAM ユーザーとロールの上限（ルートユーザーも） |
| RCP | ルート・OU・アカウント | メンバーアカウントのリソースの上限（組織の外の人からのアクセスも） |
| Control Tower の予防コントロール | OU | ルール違反になる操作をさせない（SCP・RCP などで実装） |
| Control Tower の検出コントロール | OU | ルール違反のリソースを見つけて知らせる（Config ルールで実装） |
| Control Tower のプロアクティブコントロール | OU | 作る前に調べ、違反なら作らせない（CloudFormation フックで実装） |

### SCP と RCP

#### SCP（えすしーぴー / service control policy）

- 意味：組織のメンバーアカウントの IAM ユーザーと IAM ロールが使える権限の上限を、一元的に決めるポリシー
- ポイント：SCP は権限を与えない（IAM のポリシーでの許可が別に要る）。メンバーアカウントのルートユーザーにも効く。管理アカウントには効かない。サービスにリンクされたロールにも効かない。リソースベースのポリシーには直接影響しない
- 例：開発 OU に「東京とバージニア北部以外のリージョンでの操作を Deny」する SCP を付ける
- 語の意味：Service＝サービス、Control＝制御、Policy＝ポリシー

#### FullAWSAccess（ふるえーだぶりゅーえすあくせす / FullAWSAccess）

- 意味：組織の作成時に、すべてのルート・OU・アカウントに自動で付く、AWS 管理の SCP。すべてのサービスとアクションを許可する
- ポイント：SCP は「許可されていないものは拒否」のしくみなので、これを外して代わりの許可を付けないと、メンバーアカウントのすべての操作が失敗する。「Deny を足す」使い方（拒否リスト）なら、これを残したまま Deny の SCP を足す

#### SCP の評価（えすしーぴーのひょうか / SCP evaluation）

- 意味：複数の階層に付いた SCP から、アカウントで使える上限を決めるルール
- ポイント：許可されるには、ルートからそのアカウントまでの「すべての階層」で Allow が要る（どこか1つでも欠ければ拒否）。拒否は、途中の「どこか1つ」の SCP の Deny で決まる。実際にできるのは、SCP（と RCP）が許す範囲と、ID ベース・リソースベースのポリシーが許す範囲の共通部分
- 例：ルートとアカウントに FullAWSAccess があっても、間の OU に Allow がなければ使えない

#### RCP（あーるしーぴー / resource control policy）

- 意味：組織のメンバーアカウントのリソースに対して使える権限の上限を、一元的に決めるポリシー
- ポイント：SCP は「自分の組織のプリンシパルが何をできるか」、RCP は「自分の組織のリソースに、だれが何をできるか」を絞る。組織の外のプリンシパルからのアクセスを絞りたいときは RCP。RCP も権限を与えず、管理アカウントのリソースには効かない

### Control Tower

#### AWS Control Tower（えーだぶりゅーえすこんとろーるたわー / AWS Control Tower）

- 意味：ベストプラクティスに沿ったマルチアカウント環境を、簡単に作って管理するサービス。Organizations・Service Catalog・IAM Identity Center などを組み合わせて動かす
- ポイント：「複数アカウントの環境を、すぐに、決まった安全な形で用意したい」ならこれ。Organizations だけで自分で組み立てるより手間が少ない
- 例：新しい部署のアカウントを、ログ設定やガードレールが済んだ状態で払い出す

#### ランディングゾーン（らんでぃんぐぞーん / landing zone）

- 意味：セキュリティとコンプライアンスのベストプラクティスに沿って設計された、複数アカウントの環境。Control Tower が作る
- ポイント：OU・アカウント・ユーザーなどを含む。ランディングゾーンのバージョン 3.3 以前では、セキュリティ用の OU にログアーカイブアカウントと監査アカウント（共有アカウント）が作られる

#### コントロール（ガードレール）（こんとろーる / control, guardrail）

- 意味：環境全体を継続的に統制する、わかりやすい言葉で書かれたルール。OU 単位で適用し、その OU のすべてのアカウントに効く
- ポイント：ふるまいは3種類。予防（違反になる操作を許さない。SCP・RCP などで実装）、検出（違反を見つけてダッシュボードで知らせる。AWS Config ルールで実装）、プロアクティブ（作る前に調べ、違反のリソースは作らせない。CloudFormation フックで実装）。指針として必須・強く推奨・選択の3つがある
- 例：検出コントロール「S3 バケットのパブリック読み取りが許されていないか」

#### Account Factory（あかうんとふぁくとりー / Account Factory）

- 意味：事前に承認した設定で、新しいアカウントを作るためのテンプレート。Control Tower に組み込まれている
- ポイント：Service Catalog の上に作られている。部署の担当者がセルフサービスでアカウントを作っても、会社のルールに合った形になる

#### 責任共有モデル（せきにんきょうゆうもでる / shared responsibility model）

- 意味：セキュリティとコンプライアンスを、AWS と利用者で分担するという考え方
- ポイント：AWS はホスト OS・仮想化レイヤー・施設の物理的なセキュリティなどを担当。利用者はゲスト OS（更新やパッチ）、アプリ、セキュリティグループの設定などを担当。利用者の範囲は使うサービスによって変わる（マネージドサービスほど AWS の範囲が広い）
- 例：EC2 のゲスト OS のパッチは利用者の責任。施設やハードウェアは AWS の責任

## 02-3 ID の連携（フェデレーション）

### まとめ表

**どれを使うか（IAM ユーザーガイドの表を簡単にしたもの）**

| 場面 | 使うもの | ID ソース |
| :-: | :-: | :-: |
| 社員が組織の複数のアカウントを使う | IAM Identity Center | Identity Center ディレクトリ・Active Directory・外部 IdP（SAML 2.0） |
| 1つのアカウントだけ・短期間の小さな利用・マシン | IAM のフェデレーション | SAML 2.0・OIDC |
| Web・モバイルアプリの利用者 | Amazon Cognito | ソーシャル・SAML・OIDC など |

### 社員の ID

#### ID フェデレーション（あいでぃーふぇでれーしょん / identity federation）

- 意味：AWS の外にある ID（会社のディレクトリなど）でサインインした人に、AWS のリソースを使わせること。AWS 側に IAM ユーザーを作らない
- ポイント：AWS は、人間のユーザーには IAM ユーザーを個別に作らず、ID プロバイダーとのフェデレーションを使うよう勧めている。フェデレーションした人は、ロールの一時的な認証情報で操作する

#### ID プロバイダー（あいでぃーぷろばいだー / identity provider, IdP）

- 意味：利用者の ID を管理し、サインインを確かめて、その結果を AWS などに伝える仕組みやサービス
- 例：Okta、Microsoft Entra ID、社内の Active Directory、Google
- 語の意味：Identity＝ID（本人であること）、Provider＝提供するもの

#### SAML 2.0（さむるにーてんぜろ / Security Assertion Markup Language 2.0）

- 意味：IdP でサインインした結果（アサーション）を、ほかのサービスに渡すための標準
- ポイント：社内の IdP（AD FS など）と AWS をつなぐ代表的な方法。IAM では `AssumeRoleWithSAML` でロールを引き受ける。IAM Identity Center も SAML 2.0 の IdP と連携できる
- 語の意味：Security＝安全、Assertion＝表明（この人は確かに本人です）、Markup Language＝記述言語

#### OIDC（おーあいでぃーしー / OpenID Connect）

- 意味：OAuth 2.0 の上に作られた、ID を確かめる標準。トークン（JWT）で本人の情報を渡す
- ポイント：IAM では `AssumeRoleWithWebIdentity` でロールを引き受ける。GitHub Actions など AWS の外で動くアプリに、アクセスキーなしで AWS を使わせるのに向く
- 語の意味：Open＝公開の、ID＝本人確認、Connect＝つなぐ

#### IAM Identity Center（あいえむあいでんてぃてぃせんたー / AWS IAM Identity Center）

- 意味：社員（ワークフォース）のユーザーを、組織の複数の AWS アカウントや AWS のアプリにつなぐサービス。1か所からシングルサインオンでき、短期の認証情報が渡される
- ポイント：組織で人間のユーザーのアクセスを一元管理するなら、AWS がまず勧めるのはこれ。ユーザーは AWS アクセスポータルからアカウントとロールを選んでサインインする
- 例：社員が会社の IdP でサインインし、本番アカウントでは読み取りだけ、開発アカウントでは管理者として使う

#### 権限セット（けんげんせっと / permission set）

- 意味：IAM Identity Center で、1つ以上の IAM ポリシーをまとめたテンプレート。ユーザーやグループと AWS アカウントの組み合わせに割り当てる
- ポイント：割り当てると、Identity Center がそれぞれのアカウントに対応する IAM ロールを自動で作る。AWS 管理・カスタマー管理・インライン・職務機能のポリシーを入れられ、アクセス許可の境界も付けられる。1人に複数の権限セットを割り当てられる
- 例：権限セット「ReadOnly」を、監査チームと全アカウントの組み合わせに割り当てる

#### ID ソース（あいでぃーそーす / identity source）

- 意味：IAM Identity Center で、ユーザーとグループをどこで管理するかの設定
- ポイント：組織に1つだけ。選べるのは3つ：Identity Center ディレクトリ（既定。Identity Center の中で作る）、Active Directory（オンプレミスか AWS Managed Microsoft AD）、外部 ID プロバイダー（Okta や Entra ID など）。Simple AD は ID ソースにできない

### ディレクトリとアプリの利用者

#### AWS Managed Microsoft AD（えーだぶりゅーえすまねーじどまいくろそふとえーでぃー / AWS Directory Service for Microsoft Active Directory）

- 意味：AWS が管理する本物の Microsoft Active Directory。VPC の中の複数のアベイラビリティーゾーンに、ドメインコントローラーのペアを作る
- ポイント：AD 対応のアプリ（SharePoint、.NET や SQL Server のアプリなど）を AWS で動かせる。オンプレミスの AD と信頼関係を結べる。ほかのアカウントと共有できる
- 例：AWS 上の Windows サーバーをドメインに参加させ、社内の AD とも信頼関係を結ぶ

#### AD Connector（えーでぃーこねくたー / AD Connector）

- 意味：ディレクトリへの問い合わせを、クラウドにキャッシュせず、オンプレミスの Microsoft AD に転送するゲートウェイ
- ポイント：ユーザー情報は AWS に置かず、オンプレミスの AD をそのまま使いたいときに選ぶ。オンプレミスのドメインと1対1で、ほかのアカウントとは共有できない
- 例：社員が今の AD のアカウントのまま、AWS のサービスにサインインする

#### Simple AD（しんぷるえーでぃー / Simple AD）

- 意味：Samba 4 を使った、Active Directory 互換の単体のマネージドディレクトリ
- ポイント：新しい顧客には提供されなくなった（似た機能は AWS Managed Microsoft AD か AD Connector）。IAM Identity Center の ID ソースにはできない

#### Amazon Cognito ユーザープール（あまぞんこぐにーとゆーざーぷーる / Amazon Cognito user pool）

- 意味：Web・モバイルアプリのためのユーザーディレクトリ。サインアップ・サインインを受け持ち、アプリや API に JWT を発行する
- ポイント：「このユーザーはだれか（認証）」に答える部品。Google や Apple などのソーシャル、SAML や OIDC の IdP でのサインインもまとめられる。アプリから見ると OIDC の IdP
- 例：スマホアプリの会員登録とログインをユーザープールで作り、API Gateway でトークンを確かめる

#### Amazon Cognito ID プール（あまぞんこぐにーとあいでぃーぷーる / Amazon Cognito identity pool）

- 意味：信頼できるトークンを、一時的で権限を絞った AWS の認証情報と交換する仕組み
- ポイント：「このユーザーはどの AWS リソースを使えるか（認可）」に答える部品。サインインしていないゲストにも一時的な認証情報を出せる。アプリが利用者の代わりに S3 や DynamoDB を直接呼ぶときに使う
- 例：アプリの利用者が自分の写真を S3 に直接アップロードする

## 問題演習

- 書式：「#### 問 問題ID」の下に、問・ア〜エ・正解・解説・選択肢ごとの意味・出典を書く。「###」は小分類（クイズの範囲に使う）
- 全問オリジナル問題（AWS は本番の問題を公開していない）。会社名や場面は Claude が作った例。出典には、答えの根拠にした AWS のドキュメントを書いた

### 02-1 組織とアカウント

#### 問 aws-02-o01

- 問：ある会社は 40 個の AWS アカウントを部署ごとにばらばらに持っている。請求をまとめ、部署ごとにアカウントをグループ分けし、まとめてルールを当てたい。最も適したサービスはどれか。
- ア：AWS Organizations
- イ：AWS RAM
- ウ：IAM Identity Center
- エ：AWS Directory Service
- 正解：ア
- 解説：複数のアカウントを1つの組織にまとめ、OU でグループ分けし、ポリシーを当て、請求を一元化するのは Organizations。
- アの意味：正しい。
- イの意味：リソースをアカウント間で共有するサービスで、アカウントをまとめて管理するものではない。
- ウの意味：社員のサインインと、アカウントへのアクセスを一元管理するサービス。請求やアカウントのグループ分けは行わない。
- エの意味：Active Directory を AWS で使うためのサービス。
- 出典：オリジナル問題（根拠：AWS「AWS Organizations とは」（『AWS Organizations は、AWS リソースの成長や拡張に伴い、環境の一元管理およびガバナンスを支援します。』）／AWS Organizations の概念と用語（組織『上部に[ルート]があり、ルートの下にネストされた[組織単位]を持つ階層的な木のような構造に整理できる』））

#### 問 aws-02-o02

- 問：Organizations の組織で、組織全体の料金を支払うアカウントはどれか。
- ア：委任管理者に指定したメンバーアカウント
- イ：それぞれのメンバーアカウントが自分の分を払う
- ウ：ルート（管理ルート）
- エ：管理アカウント
- 正解：エ
- 解説：管理アカウントは支払者アカウントの役割を持ち、組織内のアカウントで発生したすべての料金を支払う。
- アの意味：委任管理者はポリシーやサービスの管理を任されたメンバーアカウントで、支払いはしない。
- イの意味：組織に入ると請求は管理アカウントにまとめられる。
- ウの意味：ルートは階層のいちばん上の入れ物で、アカウントではない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS Organizations の概念と用語（『このアカウントには支払者アカウントの役割があり、組織内のアカウントによって発生したすべての料金を支払う責任があります。』））

#### 問 aws-02-o03

- 問：セキュリティ担当は「管理アカウントでは日々のワークロードを動かさない」ルールを決めた。AWS のおすすめに沿った理由として最も適切なものはどれか。
- ア：管理アカウントでは EC2 を起動できないため
- イ：管理アカウントのリソースは料金が2倍になるため
- ウ：SCP が管理アカウントのユーザーやロールには効かず、ガードレールで守れないため
- エ：管理アカウントは一度に1つのリージョンしか使えないため
- 正解：ウ
- 解説：SCP はメンバーアカウントにだけ効き、管理アカウントには効かない。そのため管理アカウントは組織の管理に必要な作業だけに使い、リソースはメンバーアカウントに置くのがおすすめ。
- アの意味：起動はできる。問題は SCP で縛れないこと。
- イの意味：料金が変わるという決まりはない。
- ウの意味：正しい。
- エの意味：そのような制限はない。
- 出典：オリジナル問題（根拠：AWS「サービスコントロールポリシー (SCP)」（『SCP は、管理アカウントのユーザーやロールには影響を与えません。SCP は、組織内のメンバーアカウントにのみ影響を与えます。』）／AWS Organizations の概念と用語（『AWS リソースを組織内の他のメンバーアカウントに保存し、管理アカウントからは切り離すことをおすすめします。』））

#### 問 aws-02-o04

- 問：本番用のアカウント 15 個に同じ SCP を付けたい。今後も本番用のアカウントは増える。最も手間の少ない方法はどれか。
- ア：アカウントを増やすたびに、そのアカウントに SCP を付ける
- イ：本番用のアカウントを1つの OU に入れ、その OU に SCP を付ける
- ウ：管理アカウントに SCP を付ける
- エ：各アカウントの IAM ロールにアクセス許可の境界を付ける
- 正解：イ
- 解説：OU に付けたポリシーは、その下のすべてのアカウントに効く。新しいアカウントも OU に入れるだけでよい。
- アの意味：動くが、付け忘れのおそれがあり手間が多い。
- イの意味：正しい。
- ウの意味：SCP は管理アカウントには効かない。また付けた先の下にしか効かない。
- エの意味：アカウントの中の個々のロールの上限で、アカウント全体をまとめて縛るしくみではない。
- 出典：オリジナル問題（根拠：AWS Organizations の概念と用語（組織単位『OU は、組織内のアカウントのサブセットに同じコントロールを適用する必要がある場合に役立ちます。』））

#### 問 aws-02-o05

- 問：今の組織は「一括請求」の機能だけで作られている。SCP を使えるようにするために必要なことはどれか。
- ア：管理アカウントにアクセス許可の境界を付ける
- イ：「すべての機能」を有効にする（招待で入ったメンバーアカウントの承認が要る）
- ウ：AWS RAM で SCP を共有する
- エ：何もしなくてよい。一括請求の組織でも SCP は使える
- 正解：イ
- 解説：一括請求だけの組織では、ポリシーでユーザーやロールの操作を制限することはできない。「すべての機能」に変えると SCP が使える。
- アの意味：境界は IAM の機能で、SCP を使えるようにすることとは関係ない。
- イの意味：正しい。
- ウの意味：RAM はリソースを共有するサービスで、ポリシーの機能を有効にするものではない。
- エの意味：一括請求の機能セットには SCP などの高度な機能は含まれない。
- 出典：オリジナル問題（根拠：AWS Organizations の概念と用語（一括請求『共有課金機能を提供する機能セットではありますが、AWS Organizations のより高度な機能は含まれません。』…『すべての機能を有効にするには、招待済みのすべてのメンバーアカウントを使用して、管理アカウントでプロセスを開始する際に送信される招待を承認し、変更を承認する必要があります。』））

#### 問 aws-02-o09

- 問：AWS のマルチアカウントの考え方として正しいものはどれか。
- ア：管理を楽にするため、すべてのワークロードを1つのアカウントに集める方がよい

- 出典：オリジナル問題（根拠：AWS「AWS Organizations とは」（『AWS アカウントは、アクセス許可、セキュリティ、コスト、ワークロードの自然境界です。マルチアカウント環境は、クラウド環境をスケーリングするときに推奨されるベストプラクティスです。』）／概念と用語（『AWS アカウントはユーザーとは異なります。』））

### 02-2 ガードレール（SCP と Control Tower）

#### 問 aws-02-o11

- 問：開発 OU のアカウントでは、EC2 の大きなインスタンスタイプを起動させたくない。開発者の IAM ポリシーは各アカウントの管理者が自由に変えられる。最も確実な方法はどれか。
- ア：開発 OU に、該当するインスタンスタイプの起動を Deny する SCP を付ける
- イ：各アカウントの IAM ポリシーで Deny を書き、変更されないことを祈る
- ウ：開発 OU にタグポリシーを付ける
- エ：管理アカウントの IAM ユーザーに Deny を書く
- 正解：ア
- 解説：SCP はアカウントの管理者（ルートユーザーも含む）でも外せない上限になる。アカウントの中の IAM ポリシーをどう変えても、SCP で拒否された操作はできない。
- アの意味：正しい。
- イの意味：アカウントの管理者が消せてしまう。
- ウの意味：タグの表記をそろえるもので、起動を止めるしくみではない。
- エの意味：管理アカウントのユーザーへの設定は、メンバーアカウントの開発者に効かない。
- 出典：オリジナル問題（根拠：AWS「サービスコントロールポリシー (SCP)」（『SCP は、メンバーアカウントのルートユーザーを含む、メンバーアカウントの IAM ユーザーとロールのアクセス許可を制限します。』））

#### 問 aws-02-o12

- 問：新しいメンバーアカウントで、IAM ユーザーに何のポリシーも付けていない。アカウントには FullAWSAccess の SCP だけが付いている。このユーザーが S3 のバケット一覧を見るとどうなるか。
- ア：許可される。FullAWSAccess がすべてを許可するため
- イ：許可される。読み取りの操作は SCP の対象外のため
- ウ：管理アカウントの権限で実行される
- エ：拒否される。SCP は権限を与えず、IAM のポリシーでの許可が別に要る
- 正解：エ
- 解説：SCP は上限を決めるだけで、権限を与えない。IAM のポリシーが付いていないユーザーは、SCP がすべてを許していても何もできない。
- アの意味：FullAWSAccess は「上限を全開にする」だけで、ユーザーに権限を与えるものではない。
- イの意味：読み取りも許可が必要。
- ウの意味：そのような引き継ぎはない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「サービスコントロールポリシー (SCP)」（『IAM アクセス許可ポリシーがアタッチされていないユーザーは、たとえ適用される SCP によりすべてのサービスとアクションが許可されても、いずれのサービスもアクセスも許可されません。』））

#### 問 aws-02-o13

- 問：組織の構造は「ルート → 本番 OU → アカウントB」。ルートとアカウントB には FullAWSAccess が付いているが、本番 OU からは FullAWSAccess を外し、S3 だけを許可する SCP を付けた。アカウントB の管理者ができることはどれか（IAM の権限は十分にあるとする）。
- ア：すべての操作（アカウントに FullAWSAccess があるため）
- イ：何もできない
- ウ：S3 以外のすべての操作
- エ：S3 の操作だけ
- 正解：エ
- 解説：SCP で許可されるには、ルートからアカウントまでのすべての階層で Allow が要る。本番 OU が S3 しか許していないので、アカウントB の上限は S3 だけになる。
- アの意味：アカウントに直接付いた Allow だけでは足りない。途中の OU で欠けたものは拒否される。
- イの意味：S3 はすべての階層で許可されているので使える。
- ウの意味：逆。S3 だけが残る。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「SCP 評価」（『特定のアカウントに対してアクセス許可を**許可する**には、アカウント (ターゲット アカウント自体を含む) への直接パスのルートから各 OU までのすべてのレベルで**明示的な `Allow` ステートメント**が必要です。』））

#### 問 aws-02-o14

- 問：ルートとアカウントC に「EC2 をすべて許可」の SCP、その間の開発 OU に「ec2:TerminateInstances を Deny」の SCP が付いている。アカウントC で TerminateInstances はどうなるか（IAM の権限は十分にあるとする）。
- ア：許可される。アカウントに直接付いた SCP が優先される
- イ：許可される。ルートの SCP が最も強い
- ウ：拒否される。途中のどの階層の Deny でも拒否される
- エ：管理アカウントの承認があれば許可される
- 正解：ウ
- 解説：SCP の拒否は、ルートからアカウントまでの経路の、どれか1つの SCP の Deny で決まる。
- アの意味：直接付いたものが優先されるルールはない。Deny が勝つ。
- イの意味：階層の上下で強さは決まらない。
- ウの意味：正しい。
- エの意味：そのような承認のしくみはない。
- 出典：オリジナル問題（根拠：AWS「SCP 評価」（『特定のアカウントに対するアクセス許可が**拒否される**場合、ルートからアカウント (ターゲット アカウント自体を含む) への直接パス内の各 OU を経由する**すべての SCP**がそのアクセス許可を拒否できます。』））

#### 問 aws-02-o15

- 問：管理者がルートから FullAWSAccess を外したが、代わりの許可の SCP を付けなかった。何が起きるか。
- ア：何も変わらない。SCP は拒否だけを書くものだから
- イ：管理アカウントの操作だけが失敗する
- ウ：メンバーアカウントのすべての AWS の操作が失敗する
- エ：メンバーアカウントのルートユーザーだけは操作できる
- 正解：ウ
- 解説：SCP は「許可されていないものは拒否」のしくみ。FullAWSAccess を外して代わりの許可を付けないと、メンバーアカウントのすべての操作が失敗する。
- アの意味：SCP の Allow がなくなるので、すべてが拒否される。
- イの意味：SCP は管理アカウントには効かない。影響を受けるのはメンバーアカウント。
- ウの意味：正しい。
- エの意味：SCP はメンバーアカウントのルートユーザーにも効く。
- 出典：オリジナル問題（根拠：AWS「サービスコントロールポリシー (SCP)」（『FullAWSAccess ポリシーを削除しないでください。そうしないと、メンバーアカウントからのすべての AWS アクションが失敗します。』））

#### 問 aws-02-o16

- 問：SCP で制限できないものはどれか。
- ア：メンバーアカウントのルートユーザーの操作
- イ：サービスにリンクされたロールの権限で行われる操作
- ウ：委任管理者に指定したメンバーアカウントの操作
