## 12-1 インスタンスタイプの選び方

### まとめ表

| ワークロード | ファミリー（シリーズの文字） |
| :-: | :-: |
| Web サーバー・コードリポジトリなど、バランスよく使う | 汎用（M、バースト可能は T） |
| バッチ処理・動画の変換・ゲームサーバー・科学モデリング | コンピューティング最適化（C） |
| メモリ内の大きなデータセット（インメモリ DB・キャッシュ） | メモリ最適化（R・X・U・Z） |
| ローカルの大量のデータへの高い I/O | ストレージ最適化（I・D・H） |
| GPU・機械学習・グラフィックス・FPGA | 高速コンピューティング（P・G・Inf・Trn・F） |
| 大規模な HPC | ハイパフォーマンスコンピューティング（Hpc） |

### タイプとファミリー

#### インスタンスタイプ（いんすたんすたいぷ / instance type）

- 意味：EC2 インスタンスのハードウェア（vCPU・メモリ・ストレージ・ネットワークの性能）の組み合わせ。用途ごとにインスタンスファミリーにまとめられている
- ポイント：起動するときに選ぶ。止めてから別のタイプに変えられる（垂直スケーリング）。新しく起動するなら、性能のよい現行世代が勧められている
- 例：m7i.large・c7g.xlarge・r7i.2xlarge

#### インスタンスタイプの命名規則（めいめいきそく / instance type naming conventions）

- 意味：インスタンスタイプの名前は「ファミリー（シリーズ＋世代＋追加の機能）」と「サイズ」でできている
- ポイント：最初の文字がシリーズ（例：c）、次の数字が世代（例：7）、そのあとの文字が追加の機能（g＝Graviton、a＝AMD、i＝インテル、d＝インスタンスストア、n＝ネットワークと EBS の最適化など）。ピリオドの後がサイズ（large・4xlarge・metal など）
- 例：c7gd.4xlarge ＝ コンピューティング最適化・第 7 世代・Graviton・インスタンスストア付き・4xlarge（Claude が読み解いた例）

#### 汎用インスタンス（はんよう / general purpose instances）

- 意味：コンピューティング・メモリ・ネットワークのリソースをバランスよく持つインスタンス（M・T など）
- ポイント：Web サーバーやコードリポジトリなど、リソースを均等に使うアプリに向く。どれに偏るか分からないなら、まずここから
- 例：社内の Web アプリを m7i.large で動かす

#### コンピューティング最適化インスタンス（こんぴゅーてぃんぐさいてきか / compute optimized instances）

- 意味：高性能なプロセッサが生きる、計算の多い処理のためのインスタンス（C）
- ポイント：バッチ処理・メディアのトランスコーディング・高性能な Web サーバー・HPC・科学モデリング・専用のゲームサーバー・広告サーバー・機械学習の推論に向く。メモリあたりの vCPU が多い
- 例：動画の変換のバッチを c7i で動かす

#### メモリ最適化インスタンス（めもりさいてきか / memory optimized instances）

- 意味：メモリの中の大きなデータセットを速く処理するためのインスタンス（R・X・U・Z など）
- ポイント：インメモリのデータベース・大きなキャッシュ・リアルタイムのビッグデータ分析に向く。「メモリ不足で遅い」「大きなデータをメモリに載せる」なら R
- 例：大きな Redis のキャッシュを r7g で動かす

#### ストレージ最適化インスタンス（すとれーじさいてきか / storage optimized instances）

- 意味：ローカルストレージの大規模なデータセットに、高い順次の読み書きと、低レイテンシーで毎秒数万のランダムな I/O を出すためのインスタンス（I・D・H）
- ポイント：インスタンスストア（ローカルの NVMe など）を使う NoSQL データベース・データウェアハウス・分散ファイルシステムに向く。インスタンスストアのデータは停止で消えるので、複製する前提で使う
- 例：Cassandra のノードを i4i で動かす

#### 高速コンピューティングインスタンス（こうそくこんぴゅーてぃんぐ / accelerated computing instances）

- 意味：GPU・FPGA・専用チップなどのハードウェアアクセラレーターで、浮動小数点の計算・グラフィックス・データのパターンマッチングを CPU のソフトより効率よく行うインスタンス
- ポイント：P＝GPU（機械学習の学習など）、G＝グラフィックス、Inf＝AWS Inferentia（推論）、Trn＝AWS Trainium（学習）、F＝FPGA。「GPU が要る」「機械学習」ならここ
- 例：深層学習のモデルの学習を p5 で行う

#### ハイパフォーマンスコンピューティングインスタンス（はいぱふぉーまんすこんぴゅーてぃんぐ / high performance computing instances）

- 意味：大規模な HPC のワークロードを、最高の価格パフォーマンスで動かすためのインスタンス（Hpc）
- ポイント：大規模で複雑なシミュレーションや深層学習など、高性能なプロセッサが生きるアプリに向く。EFA やクラスタープレイスメントグループと組み合わせることが多い
- 例：流体のシミュレーションを hpc7a で動かす

#### AWS Graviton（ぐらびとん / AWS Graviton）

- 意味：AWS が設計した Arm ベースのプロセッサ。EC2 のワークロードに最高のコストパフォーマンスを出すように作られている
- ポイント：インスタンスタイプの名前の「g」（m7g・c7g・r7g・t4g など）が目印。Arm ベースなので、アプリ・ライブラリ・コンテナのイメージが Arm に対応している必要がある
- 例：Java の Web アプリを m7i から m7g に移してコストを下げる

#### バーストパフォーマンスインスタンスと CPU クレジット（ばーすとぱふぉーまんす / burstable performance instances and CPU credits）

- 意味：ふだんはベースラインの CPU 性能で動き、必要なときにベースラインを超えてバーストできるインスタンス（T）。バーストは CPU クレジットで管理する
- ポイント：CPU 使用率がベースラインより低いあいだはクレジットがたまり、超えているあいだは使われる。ふだんは暇で、ときどき忙しい小さな Web サーバー・開発環境・マイクロサービスに向く。常に CPU を高く使うなら固定パフォーマンスのインスタンス（M・C など）
- 例：開発用の Web サーバーを t3.small で動かす

#### 無制限モード（むせいげんもーど / unlimited mode）

- 意味：バーストパフォーマンスインスタンスで、クレジットが足りなくても、必要なだけベースラインを超えて CPU を使えるモード
- ポイント：T4g・T3a・T3 はデフォルトで無制限モードで起動する。24 時間の平均の CPU 使用率がベースラインを超えると、超えた分に追加料金がかかる。スタンダードモードは、クレジットを使い切るとベースラインまで下がる
- 例：t3 のインスタンスの CPU がずっと高く、追加料金が増えている → m 系に変える

#### AWS Compute Optimizer（こんぴゅーとおぷてぃまいざー / AWS Compute Optimizer）

- 意味：リソースの設定と使用率のメトリクスを分析し、適切なサイズ（ライトサイジング）を勧め、アイドルのリソースを見つけるサービス
- ポイント：EC2 のインスタンスが大きすぎる（過剰）か小さすぎる（不足）かを判断し、コストの削減と性能の改善の両方を勧める。「どのインスタンスタイプにすべきか分からない」なら Compute Optimizer
- 例：CPU が 5% しか使われていない m7i.4xlarge に、m7i.xlarge を勧められる

## 12-2 起動と構成

### まとめ表

| 起きること | インスタンスストアのデータ | メモリ（RAM）の内容 |
| :-: | :-: | :-: |
| 再起動 | 残る | 消える |
| 停止 → 開始 | 消える | 消える |
| 休止 → 開始 | 消える | ルートの EBS に保存して戻る |
| 終了 | 消える | 消える |

停止して開始すると、ふつうは新しいホストに移り、Elastic IP がなければ新しいパブリック IPv4 アドレスになる（AWS「インスタンスの自動復旧」）

### イメージと起動時の設定

#### Amazon マシンイメージ（あみ / Amazon Machine Image, AMI）

- 意味：EC2 インスタンスを起動するのに必要なソフトウェア（OS・アプリなど）を持つイメージ。ブロックデバイスマッピングも含む
- ポイント：インスタンスを起動するときは必ず AMI を指定する。設定済みのインスタンスから自分の AMI（ゴールデンイメージ）を作ると、起動が速くなる。リージョン固有なので、別のリージョンで使うならコピーする（#10）
- 例：パッチとアプリを入れた自社の AMI から Auto Scaling で起動する

#### EC2 Image Builder（いめーじびるだー / EC2 Image Builder）

- 意味：カスタマイズされ、安全で最新のサーバーイメージ（AMI やコンテナのイメージ）の作成・管理・配布を自動化するフルマネージドサービス
- ポイント：パイプラインで、イメージの更新とシステムのパッチを自動化できる。手作業で AMI を作り直す手間をなくす
- 例：毎月、最新のパッチを当てた AMI を自動で作り、各リージョンに配る

#### ユーザーデータ（ゆーざーでーた / user data）

- 意味：インスタンスの起動時に渡し、起動後の自動の設定やスクリプトを実行させるデータ。Linux ではシェルスクリプトか cloud-init のディレクティブ
- ポイント：デフォルトでは、最初の起動のときにだけ実行される（再起動では動かない）。インスタンスの中からはメタデータとして読めるが、暗号化されないので、パスワードなどの秘密は書かない（Secrets Manager などを使う）
- 例：起動時に Web サーバーをインストールして、S3 からコンテンツを取る

#### インスタンスメタデータと IMDSv2（いんすたんすめたでーた / instance metadata and IMDSv2）

- 意味：インスタンスメタデータ＝インスタンスの中から読める、そのインスタンスに関するデータ（ホスト名・セキュリティグループ・IAM ロールの一時的な認証情報など）。IMDSv2＝トークンを使う新しい読み方
- ポイント：インスタンスの中からだけ読めるが、データは認証や暗号化で守られていない。IMDSv2 を必須にすると IMDSv1 は動かなくなる（まず PUT でトークンを取り、それを付けて GET する）。オープンなファイアウォールやリバースプロキシ、SSRF の弱さへの多層防御になる
- 例：全インスタンスで IMDSv2 を「必須」にする

#### キーペア（きーぺあ / key pair）

- 意味：プライベートキーと公開キーの組。EC2 インスタンスに接続するときの身元の証明に使う
- ポイント：Linux ではプライベートキーで SSH 接続する。Windows では管理者パスワードの復号にプライベートキーが要る。プライベートキーは自分で安全に保管する。キーを配らずに入りたいなら Systems Manager Session Manager
- 例：運用担当者だけがプライベートキーを持ち、踏み台なしで入るなら Session Manager を使う

### ストレージと止め方

#### インスタンスストア（いんすたんすすとあ / instance store）

- 意味：インスタンスのホストのディスクにある、一時的なブロックレベルのストレージ
- ポイント：バッファ・キャッシュ・スクラッチデータなど、頻繁に変わる一時的なデータに最適。再起動では残るが、停止・休止・終了で消える。残したいデータは EBS・S3・EFS にコピーする。大きさはインスタンスタイプで決まる
- 例：動画の変換の作業用の一時ファイルをインスタンスストアに置く

#### 休止（きゅうし / hibernation）

- 意味：インスタンスを止めるとき、メモリ（RAM）の内容をルートの EBS ボリュームに保存し、開始したときにメモリの内容を戻す止め方
- ポイント：起動に時間がかかるアプリ（メモリにデータを載せるのに時間がかかるなど）を、止めたところから素早く再開できる。前もって休止を有効にして起動し、休止の前提条件を満たす必要がある。休止して止めているあいだ、インスタンスの料金はかからないが、RAM の内容を含む EBS のストレージには料金がかかる
- 例：大きなキャッシュを温めるのに 20 分かかる開発サーバーを、夜は休止する

#### インスタンスの自動復旧（じどうふっきゅう / instance auto-recovery）

- 意味：ハードウェアなどの基盤の問題でシステムステータスチェックが失敗したとき、インスタンスを別のハードウェアで復旧させるしくみ（簡易自動復旧と CloudWatch アクションベースの復旧）
- ポイント：簡易自動復旧は、対応するインスタンスでは起動したときから有効。復旧したインスタンスは、失われた要素を除いて元と同じ（インスタンス ID・プライベート IP・Elastic IP など）。1 台のインスタンスの可用性を上げるもので、複数台の Auto Scaling とは別
- 例：1 台だけの業務サーバーで、CloudWatch のアラームで復旧のアクションを設定する

## 12-3 ネットワークと配置

### まとめ表

| プレイスメントグループ | 置き方 | 向く用途 |
| :-: | :-: | :-: |
| クラスター | 1 つの AZ の中で近くにまとめる | HPC など、低レイテンシー・高スループットの通信 |
| パーティション | パーティションごとに別のラック（AZ ごとに最大 7 パーティション） | Hadoop・HDFS・HBase・Cassandra・Kafka などの大規模な分散・複製 |
| スプレッド | 1 台ずつ別のラック（AZ ごとに最大 7 台） | 少数の重要なインスタンスを互いに分ける |

### ネットワーク

#### Elastic Network Interface（えにー / Elastic Network Interface, ENI）

- 意味：VPC の中の、仮想のネットワークカードにあたる部品。プライベート IP・Elastic IP・セキュリティグループ・MAC アドレスなどを持つ
- ポイント：同じ AZ のインスタンスにアタッチできる。外して別のインスタンスに付け替えると、属性（IP など）もついていく。各インスタンスのプライマリのネットワークインターフェイスは外せない。管理用のネットワークを分ける、IP に紐づくライセンスを移す、などに使う
- 例：IP にライセンスが紐づくソフトのため、セカンダリの ENI を予備のインスタンスに付け替える

#### Elastic IP アドレス（いらすてぃっくあいぴー / Elastic IP address）

- 意味：アカウントに割り当てられる、静的なパブリック IPv4 アドレス。解放するまで自分のもの
- ポイント：別のインスタンスにすばやく付け替えて、障害を隠せる。使っているかどうかにかかわらず、すべての Elastic IP に料金がかかる。止めて開始してもパブリック IP を変えたくないなら Elastic IP
- 例：取引先に許可してもらう固定の IP として、Web サーバーに Elastic IP を付ける

#### 拡張ネットワーキング（かくちょうねっとわーきんぐ / enhanced networking, ENA）

- 意味：SR-IOV（シングルルート I/O 仮想化）で、対応するインスタンスタイプに高い帯域・高い PPS・低いインスタンス間のレイテンシーを出すネットワーク。Elastic Network Adapter（ENA）を使う
- ポイント：Nitro ベースのインスタンスはすべて ENA を使う。追加料金はない。SR-IOV は、従来の仮想化したネットワークインターフェイスより I/O の性能が高く、CPU の使用率が低い。OS を通さずに通信する（OS バイパス）のは EFA
- 例：ネットワークを多く使う Web サーバーで、ENA が有効なタイプを選ぶ

#### Elastic Fabric Adapter（いーえふえー / Elastic Fabric Adapter, EFA）

- 意味：AI・機械学習・HPC のアプリを速くするために EC2 インスタンスにアタッチするネットワークデバイス
- ポイント：OS バイパスの機能（SRD プロトコル）で、ノードのあいだの通信を速くする。HPC の MPI や、機械学習の NCCL に対応する。「密に結びついたノード間の通信」「MPI」なら EFA。ENA は一般の高速なネットワーク
- 例：数百台で MPI の流体シミュレーションを、EFA とクラスタープレイスメントグループで動かす
- 語の意味：Elastic＝伸び縮みする、Fabric＝（ノードを結ぶ）網、Adapter＝接続装置

### プレイスメントグループ

#### クラスタープレイスメントグループ（くらすたー / cluster placement group）

- 意味：1 つの AZ の中で、インスタンスを近くにまとめて置くプレイスメントグループ
- ポイント：ネットワークの低いレイテンシー・高いスループットが要るアプリ（HPC の密結合のノード間通信）に勧められる。同じグループの中では、フローあたりのスループットの上限も高い。1 つの AZ なので、AZ の障害には弱い
- 例：HPC のジョブの 32 台をクラスタープレイスメントグループで起動する

#### パーティションプレイスメントグループ（ぱーてぃしょん / partition placement group）

- 意味：インスタンスを論理的なパーティションに分け、パーティションどうしが同じラック（ネットワークと電源）を共有しないように置くプレイスメントグループ
- ポイント：1 つのハードウェアの障害の影響は、そのパーティションの中だけに留まる。AZ ごとに最大 7 パーティション。どのインスタンスがどのパーティションかを、HDFS・HBase・Cassandra などのトポロジーを意識するアプリに伝えられる。大規模な分散・複製のワークロード向け
- 例：100 台の Hadoop クラスターを 3 つのパーティションに分ける

#### スプレッドプレイスメントグループ（すぷれっど / spread placement group）

- 意味：インスタンスを 1 台ずつ別々のハードウェア（ラック）に置くプレイスメントグループ
- ポイント：少数の重要なインスタンスを互いに分けて、同時に壊れるリスクを減らす。ラックレベルでは AZ ごとに実行中のインスタンスは最大 7 台（3 つの AZ なら合計 21 台）。台数が多いならパーティション
- 例：3 台のデータベースのプライマリ候補を、スプレッドプレイスメントグループで起動する
