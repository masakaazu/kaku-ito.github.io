## 01-1 だれがアクセスするか（ID）

### まとめ表

| ID | 認証情報 | 向いている使い方 |
| :-: | :-: | :-: |
| ルートユーザー | メールアドレスとパスワード（＋MFA） | ルートでしかできない作業だけ |
| IAM ユーザー | パスワード・アクセスキー（長期） | フェデレーションが使えない場合や緊急用 |
| IAM ユーザーグループ | なし（ユーザーの入れ物） | 複数のユーザーにまとめて許可を付ける |
| IAM ロール | 引き受けたときだけの一時的な認証情報 | EC2・Lambda のアプリ、別アカウント、外部 ID の人 |

### アカウントとユーザー

#### ルートユーザー（るーとゆーざー / AWS account root user）

- 意味：AWS アカウントを作ったときの最初のサインイン ID。アカウントのすべてのサービスとリソースに完全なアクセス権を持つ
- ポリシーとの関係：ID ベースのポリシーもアクセス許可の境界も付けられない。ただし、アカウントが AWS Organizations に入っていれば SCP の制限を受ける
- 使い方：AWS は日常の作業に使わないよう強く勧めている。使うのは、ルートでしかできない作業のときだけにする
- 例：アカウントの閉鎖（Organizations に入っていない単独のアカウントの場合）、ただ1人の IAM 管理者が自分の権限を消してしまったときの復旧、S3 の MFA 削除の設定、すべてのプリンシパルを拒否してしまったバケットポリシーの削除

#### IAM ユーザー（あいえむゆーざー / IAM user）

- 意味：アカウントの中に作る、1人の人または1つのアプリを表す ID。パスワードやアクセスキーなどの長期の認証情報を持つ
- ポイント：AWS は、ID フェデレーションでまかなえない場合にだけ使うよう勧めている。例として、ロールを使えないワークロード、Identity Center に対応していないサードパーティーのツール、ID プロバイダーが止まったときの緊急アクセスが挙がっている
- 例：オンプレミスの古いツールが使う、アクセスキーを持つユーザー

#### IAM ユーザーグループ（あいえむゆーざーぐるーぷ / IAM user group）

- 意味：IAM ユーザーの集まり。グループにポリシーを付けると、所属する全員がその許可を受け取る
- ポイント：グループの中にグループは入れられない（入れ子にできない）。1人のユーザーは複数のグループに入れる。グループはサインインする主体ではないので、リソースベースのポリシーの Principal には書けない。全ユーザーが自動で入るグループもない
- 例：Developers グループに開発用のポリシーを付け、新しく入った開発者をグループに追加するだけで権限がそろう

#### アクセスキー（あくせすきー / access key）

- 意味：IAM ユーザー（またはルートユーザー）の長期の認証情報。アクセスキー ID とシークレットアクセスキーの組で、CLI・SDK・API のリクエストに署名する
- ポイント：1ユーザーにつき最大2つ（2つあるので、入れ替えのときに新旧を並べて使える）。シークレットは作ったときしか見られない。なくしたら削除して作り直す。ルートユーザーのアクセスキーは作らないのが原則。アプリのファイルに書き込まない
- 例：`AKIAIOSFODNN7EXAMPLE`（アクセスキー ID の書式の例。AWS ドキュメントの例）

#### MFA（えむえふえー / multi-factor authentication）

- 意味：パスワードに加えて、もう1つの要素（手元の機器のコードなど）でも本人確認する多要素認証
- ポイント：ルートユーザーと IAM ユーザーに設定でき、1人につき最大8台の MFA 機器を登録できる。種類はパスキー・セキュリティキー、仮想認証アプリ、ハードウェア TOTP トークン。ポリシーの条件 `aws:MultiFactorAuthPresent` で「MFA を使ったときだけ許可」もできる
- 語の意味：Multi＝複数の、Factor＝要素、Authentication＝認証

### ロール

#### IAM ロール（あいえむろーる / IAM role）

- 意味：アクセス許可ポリシーを持つ ID で、特定の人ではなく「必要な人やサービスが引き受ける」もの。引き受けると、そのセッション用の一時的な認証情報が渡される
- ポイント：ロールにはパスワードやアクセスキーのような長期の認証情報がない。引き受けられるのは、同じまたは別のアカウントの IAM ユーザー、同じアカウントのロール、AWS のサービス、SAML 2.0 や OpenID Connect の外部 ID プロバイダーで認証された人
- 例：EC2 上のアプリが S3 を読むためのロール、別アカウントの監査担当が引き受けるロール

#### 信頼ポリシー（しんらいぽりしー / trust policy）

- 意味：ロールに付ける、だれがそのロールを引き受けられるか（プリンシパル）を決めるポリシー。ロールに必ず付く、リソースベースのポリシーの一種
- ポイント：ロールには「信頼ポリシー（だれが引き受けられるか）」と「アクセス許可ポリシー（引き受けたら何ができるか）」の2つが付く。信頼ポリシーの Principal にはワイルドカード（*）を書けない
- 例：`"Principal": {"Service": "ec2.amazonaws.com"}`（EC2 が引き受けられる）

#### サービスロール（さーびすろーる / service role）

- 意味：AWS のサービスが、利用者の代わりに操作するために引き受ける IAM ロール。管理者が作成・変更・削除できる
- ポイント：サービスにリンクされたロールとの違いは「だれが持ち主か」。サービスロールは利用者が自由に編集できる

#### サービスにリンクされたロール（さーびすにりんくされたろーる / service-linked role）

- 意味：特定の AWS のサービスに結びついたサービスロール。サービスが持ち主で、多くはサービスを使い始めたときに自動で作られる
- ポイント：IAM 管理者は中身を見られるが、編集はできない。消すには先に関連するリソースを消す必要がある（使っているリソースが権限を失わないため）

#### インスタンスプロファイル（いんすたんすぷろふぁいる / instance profile）

- 意味：IAM ロールを EC2 インスタンスに渡すための入れ物
- ポイント：コンソールで EC2 用のロールを作ると、同じ名前のインスタンスプロファイルが自動で作られる。1つのインスタンスプロファイルに入るロールは1つだけ（この上限は上げられない）。1台のインスタンスに同時に付けられるロールも1つだけで、そのインスタンス上のアプリはみな同じ権限を共有する
- 例：起動中のインスタンスにも、あとからロールを付けられる

#### 一時的な認証情報（いちじてきなにんしょうじょうほう / temporary security credentials）

- 意味：AWS STS が発行する、有効期限つきの認証情報。期限は数分から数時間に設定できる
- ポイント：ユーザーといっしょに保存されず、求められるたびに作られる。期限が切れたら使えないので、取り消しや入れ替えの手間がない。ロールと ID フェデレーションの土台
- 例：EC2 のロールの認証情報は自動で更新されるので、アプリにアクセスキーを書く必要がない

#### AWS STS（えーだぶりゅーえすえすてぃーえす / AWS Security Token Service）

- 意味：一時的な認証情報を発行するサービス
- ポイント：主な API は、ロールを引き受ける `AssumeRole`、SAML の IdP で認証した人用の `AssumeRoleWithSAML`、OIDC の IdP（JWT）用の `AssumeRoleWithWebIdentity`、IAM ユーザーからフェデレーション用のセッションを作る `GetFederationToken`。AssumeRole のセッションの長さは `DurationSeconds` で、ロールの最大セッション時間（最大 12 時間＝43200 秒）まで指定できる
- 語の意味：Security＝安全、Token＝しるし（認証情報）、Service＝サービス

#### ロールの連鎖（ろーるのれんさ / role chaining）

- 意味：ロールの一時的な認証情報を使って、さらに別のロールを引き受けること
- ポイント：連鎖したセッションは最長1時間。ロール自体の最大セッション時間を長くしても、1時間を超える `DurationSeconds` を指定すると失敗する

## 01-2 ポリシーの書き方

### まとめ表

| 種類 | 付ける先 | 許可を与えるか |
| :-: | :-: | :-: |
| ID ベースのポリシー（管理・インライン） | ユーザー・グループ・ロール | 与える |
| リソースベースのポリシー | S3 バケット・SQS キュー・KMS キー・ロール（信頼ポリシー）など | 与える（Principal に書いた相手に） |
| アクセス許可の境界 | ユーザー・ロール | 与えない（上限だけ） |
| SCP（#02） | 組織・OU・アカウント | 与えない（上限だけ） |
| セッションポリシー | ロールを引き受けるときに渡す | 与えない（上限だけ） |

### ポリシーの種類

#### ID ベースのポリシー（あいでぃーべーすのぽりしー / identity-based policy）

- 意味：IAM のユーザー・グループ・ロールに付けて、その ID が何をできるかを決めるポリシー
- ポイント：管理ポリシー（AWS 管理・カスタマー管理）とインラインポリシーに分かれる。Principal 要素は書かない（付けた相手がプリンシパルになる）
- 例：ユーザー John に EC2 の `RunInstances` を許可する

#### リソースベースのポリシー（りそーすべーすのぽりしー / resource-based policy）

- 意味：S3 バケット・SQS キュー・KMS キー・VPC エンドポイントなどのリソースに付けて、だれがそのリソースに何をできるかを決めるポリシー
- ポイント：インラインだけで、管理ポリシーの形はない。Principal 要素で相手（別のアカウントでもよい）を指定する。代表例は S3 のバケットポリシーとロールの信頼ポリシー
- 例：バケットポリシーで、別のアカウント 111122223333 に GetObject を許可する

#### AWS 管理ポリシー（えーだぶりゅーえすかんりぽりしー / AWS managed policy）

- 意味：AWS が作って管理する、独立したポリシー（自分の ARN を持つ）
- ポイント：中身は利用者が変えられない。AWS が新サービスなどに合わせてときどき更新し、付けている全員に反映される。最初はこれで始め、最小権限のカスタマー管理ポリシーへ移るのが AWS のおすすめ
- 例：`arn:aws:iam::aws:policy/IAMReadOnlyAccess`

#### カスタマー管理ポリシー（かすたまーかんりぽりしー / customer managed policy）

- 意味：利用者が自分のアカウントで作って管理する、独立したポリシー
- ポイント：何度でも変更でき、複数のユーザー・グループ・ロールに付けられる。AWS 管理ポリシーより細かく、必要な分だけに絞れる

#### インラインポリシー（いんらいんぽりしー / inline policy）

- 意味：1つのユーザー・グループ・ロールに直接埋め込むポリシー
- ポイント：ポリシーと ID が厳密に1対1。ID を消すとポリシーもいっしょに消える。ほかの ID に使い回せない
- 例：あるロールだけに、ほかに流用されたくない特別な許可を付ける

### ポリシーの要素

#### Effect（えふぇくと / Effect）

- 意味：そのステートメントが許可（`Allow`）か拒否（`Deny`）かを決める要素
- ポイント：ポリシーは1つ以上のステートメントからなり、各ステートメントに Effect・Action・Resource などを書く。最初に書く `Version` は `2012-10-17` を使う（ポリシー変数もこのバージョンから）

#### Action と NotAction（あくしょんとのっとあくしょん / Action, NotAction）

- 意味：Action は許可・拒否する操作の一覧。NotAction は「書いた操作以外のすべて」に当てはまる
- ポイント：`"Effect": "Allow", "NotAction": "s3:DeleteBucket"` と Resource を S3 にすると、バケット削除以外の S3 操作だけを許可する（ほかのサービスの操作は許可されない）。NotAction は「拒否」ではない点に注意
- 例：`"Action": ["s3:GetObject", "s3:PutObject"]`

#### Resource（りそーす / Resource）

- 意味：操作の対象となるリソースを ARN で指定する要素
- ポイント：ID ベースのポリシーでは必ず書く。`*` はすべてのリソース

#### Principal（ぷりんしぱる / Principal）

- 意味：リソースベースのポリシーで、許可・拒否する相手（アカウント・ユーザー・ロール・サービスなど）を指定する要素
- ポイント：リソースベースのポリシーでは必要、ID ベースのポリシーには書けない。グループは書けない
- 例：`"Principal": {"AWS": "arn:aws:iam::111122223333:root"}`（そのアカウント全体）

#### Condition（こんでぃしょん / Condition）

- 意味：ポリシーが効く条件を書く要素。条件演算子（等しい・より小さい など）で、リクエストの情報（コンテキストキー）と値を比べる
- ポイント：`aws:` で始まるのが全サービス共通のグローバル条件キー。条件が true のときだけそのステートメントが効く
- 例：`"Condition": {"Bool": {"aws:MultiFactorAuthPresent": "true"}}`

#### グローバル条件キー（ぐろーばるじょうけんきー / global condition context keys）

- 意味：どのサービスのポリシーでも使える、`aws:` で始まる条件キー
- ポイント：試験でよく出るもの → `aws:SourceIp`（リクエスト元の IP。パブリック IP だけに使える。VPC エンドポイント経由のリクエストには含まれない）、`aws:RequestedRegion`（呼び出されたリージョン）、`aws:MultiFactorAuthPresent`（MFA を使ったか）、`aws:SecureTransport`（TLS で送られたか）、`aws:PrincipalOrgID`（プリンシパルが属する組織）
- 例：`aws:SecureTransport` が false のリクエストを Deny して、HTTPS を強制する

#### ポリシー変数（ぽりしーへんすう / policy variables）

- 意味：ポリシーを書くときに値が決まっていない部分に置く `${...}` の変数。リクエストのときの値に置き換わる
- ポイント：`Version` が `2012-10-17` のポリシーでだけ使える
- 例：`"Resource": "arn:aws:s3:::bucket/home/${aws:username}/*"` で、各ユーザーが自分のフォルダだけを使える

#### ARN（えーあーるえぬ / Amazon Resource Name）

- 意味：AWS のリソースを一意に表す名前
- ポイント：形は `arn:パーティション:サービス:リージョン:アカウントID:リソース`。パーティションは通常 `aws`。IAM や S3 のバケットのように、リージョンやアカウントを書かない ARN もある
- 例：`arn:aws:iam::123456789012:role/examplerole`
- 語の意味：Amazon Resource Name＝Amazon のリソースの名前

## 01-3 許可の決まり方と絞り込み

### まとめ表

**1つのアカウントの中での判定（ドキュメントの評価の流れを簡単にしたもの）**

| 順 | 調べること | 結果 |
| :-: | :-: | :-: |
| 1 | どこかのポリシーに当てはまる明示的な Deny があるか | あれば拒否（ほかの Allow より強い） |
| 2 | SCP・RCP で許可されているか | なければ拒否 |
| 3 | リソースベースか ID ベースのポリシーに Allow があるか | どこにもなければ拒否（暗黙の拒否） |
| 4 | アクセス許可の境界・セッションポリシーの範囲内か | 外なら拒否 |
| 5 | ここまで通った | 許可 |

**別のアカウントのリソースを使うとき**

| 置き場所 | 必要なもの |
| :-: | :-: |
| リソースのあるアカウント（信頼する側） | リソースベースのポリシー（またはロールの信頼ポリシー）で相手を許可 |
| 使う人のアカウント（信頼される側） | ID ベースのポリシーでそのリソース（またはロールの引き受け）を許可 |

### 判定のしくみ

#### 暗黙的な拒否（あんもくてきなきょひ / implicit deny）

- 意味：どのポリシーにも Allow がないために、何も書いていなくても拒否されること
- ポイント：ルートユーザー以外のリクエストは、最初はすべて暗黙的に拒否されている。Allow があれば暗黙の拒否は上書きされる

#### 明示的な拒否（めいじてきなきょひ / explicit deny）

- 意味：ポリシーに `"Effect": "Deny"` と書いて拒否すること
- ポイント：明示的な拒否は、ほかのどのポリシーの Allow よりも強い。ポリシーの種類を問わず、1か所でも当てはまる Deny があれば拒否

#### アクセス許可の境界（あくせすきょかのきょうかい / permissions boundary）

- 意味：ユーザーやロールに設定する、ID ベースのポリシーで与えられる権限の上限
- ポイント：境界そのものは権限を与えない。実際にできるのは「ID ベースのポリシー」と「境界」の両方で許可された操作だけ。管理ポリシー（AWS 管理かカスタマー管理）を使って設定する。リソースベースのポリシーが与える権限の上限は決めない。開発者に「ロールを作ってよいが、この境界を付けたものだけ」と任せる使い方が代表例
- 例：境界で S3・CloudWatch・EC2 だけを許可すると、ID ベースのポリシーで IAM を許可しても IAM は使えない

#### セッションポリシー（せっしょんぽりしー / session policy）

- 意味：ロールを引き受けるとき（AssumeRole など）に渡して、そのセッションの権限をさらに絞るポリシー
- ポイント：権限は与えない。セッションの権限は、ロールの ID ベースのポリシーとセッションポリシーの共通部分になる

#### クロスアカウントアクセス（くろすあかうんとあくせす / cross-account access）

- 意味：あるアカウントのプリンシパルに、別のアカウントのリソースを使わせること
- ポイント：リソースのあるアカウントを「信頼する」アカウント、使う人のアカウントを「信頼される」アカウントと呼ぶ。リソースベースのポリシーに相手を書くだけでは半分で、使う人の側の ID ベースのポリシーでも許可が要る。方法は2つ：①ロールを作って引き受けてもらう（元の権限は一時的に使えなくなる）、②S3・SNS・SQS などではリソースベースのポリシーで直接許可する
- 例：本番アカウントに監査用ロールを作り、信頼ポリシーで監査アカウントを許可する

#### 外部 ID（がいぶあいでぃー / external ID）

- 意味：第三者の会社に自分のアカウントのロールを引き受けさせるとき、信頼ポリシーの条件 `sts:ExternalId` で確かめる、顧客ごとに違う値
- ポイント：「混乱した代理」問題を防ぐためのもの。第三者がほかの顧客から聞いたロールの ARN を使って、別の顧客のアカウントに入れないようにする

#### 混乱した代理問題（こんらんしただいりもんだい / confused deputy problem）

- 意味：操作の権限を持たない者が、権限を持つ別の者（代理）に操作をさせてしまうセキュリティの問題
- ポイント：第三者への委任（クロスアカウント）では外部 ID、AWS のサービスどうし（クロスサービス）では条件キー `aws:SourceArn`・`aws:SourceAccount` などで防ぐ

#### iam:PassRole（あいえむぱすろーる / iam:PassRole）

- 意味：EC2 や Lambda などの AWS のサービスに IAM ロールを渡す（設定する）ための許可
- ポイント：ユーザーが自分より強いロールをサービスに付けて権限を広げるのを防ぐしくみ。同じアカウントのサービスにだけ渡せる
- 例：EC2 を起動してロールを付けるには、`ec2:RunInstances` に加えて、そのロールへの `iam:PassRole` が要る

### 最小権限と点検

#### 最小権限（さいしょうけんげん / least privilege）

- 意味：タスクに必要な権限だけを与えること。どの条件で、どのリソースに、どの操作ができるかを決めて付ける
- ポイント：AWS のベストプラクティスの1つ。広めの AWS 管理ポリシーから始めて、使われた操作を見ながら絞っていく

#### IAM Access Analyzer（あいえむあくせすあならいざー / IAM Access Analyzer）

- 意味：アクセス権の点検をする IAM の機能
- ポイント：①外部と共有されているリソース（S3 バケットや IAM ロールなど）を見つける、②使われていない権限を見つける、③ポリシーを文法とベストプラクティスで検証する、④CloudTrail の記録から実際に使った操作だけのポリシーを作る
- 例：「別アカウントに公開されてしまったバケットを探したい」→ Access Analyzer の外部アクセスの検出

#### 最終アクセス情報（さいしゅうあくせすじょうほう / last accessed information）

- 意味：ユーザー・グループ・ロール・ポリシーが、各サービスに最後にアクセスした日時の情報。IAM コンソールのアクセスアドバイザーで見る
- ポイント：使われていないサービスの権限を見つけて外すのに使う

#### 認証情報レポート（にんしょうじょうほうれぽーと / credential report）

- 意味：アカウントの全ユーザーと、その認証情報（パスワード・アクセスキー・MFA 機器など）の状態を一覧にしたレポート
- ポイント：ダウンロードして、MFA を設定していないユーザーや古いアクセスキーを見つける監査に使う。Access Analyzer（権限の点検）との違いに注意

- 問：ユーザーが EC2 インスタンスを起動するときに、既存の IAM ロールをインスタンスに付けようとしたら拒否された。ec2:RunInstances は許可されている。足りない権限はどれか。

- イ：sts:AssumeRole
- ウ：iam:CreateRole
- エ：iam:AttachRolePolicy
- 正解：ア
- 解説：AWS のサービスにロールを渡す（設定する）には、そのロールへの iam:PassRole の許可が要る。自分より強いロールをサービスに付けて権限を広げることを防ぐしくみ。
- アの意味：正しい。
- イの意味：ユーザー自身がロールを引き受けるための許可。サービスに渡す場合とは別。
- ウの意味：ロールを新しく作る許可。既存のロールを付けるだけなら要らない。
- エの意味：ロールにポリシーを付ける許可で、ロールを渡す許可ではない。
- 出典：オリジナル問題（根拠：AWS「AWS サービスにロールを渡すアクセス許可をユーザーに付与する」（『ユーザーがロール (とそのアクセス許可) を AWS サービスに渡すには、そのサービスにロールを渡すアクセス許可が必要になります。』））

#### 問 aws-01-o30
