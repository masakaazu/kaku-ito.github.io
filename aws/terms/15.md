## 15-1 RDS の可用性とスケーリング

### まとめ表

| しくみ | 複製のしかた | 読み取りに使える | 主な目的 |
| :-: | :-: | :-: | :-: |
| マルチ AZ DB インスタンス | 別の AZ のスタンバイ 1 台に同期 | 使えない | 高可用性（自動フェイルオーバー） |
| マルチ AZ DB クラスター | 3 つの AZ のリーダー 2 台に準同期 | 使える | 高可用性＋読み取りの拡張 |
| リードレプリカ | 非同期（最大 15 台） | 使える | 読み取りの拡張・昇格して DR |
| クロスリージョンリードレプリカ | 別のリージョンへ非同期 | 使える | DR・ユーザーの近くで読む・移行 |

数字は AWS「Amazon RDS のクォータと制約」などによる

### 高可用性と読み取りの拡張

#### Amazon RDS（あーるでぃーえす / Amazon Relational Database Service）

- 意味：クラウドでリレーショナルデータベースを作り、動かし、スケールするためのマネージドサービス
- ポイント：エンジンは IBM Db2・MariaDB・Microsoft SQL Server・MySQL・Oracle Database・PostgreSQL（Aurora は Aurora ユーザーガイド）。パッチ・バックアップ・障害検出は AWS が行い、利用者は基盤のホストにはアクセスできない。OS まで触りたいなら RDS Custom か EC2 に自分で入れる
- 例：EC2 に自分で MySQL を入れていたのを RDS for MySQL に移し、バックアップとパッチの手間を減らす
- 語の意味：Relational＝表どうしを関係でつなぐ、Database＝データベース、Service＝サービス

#### マルチ AZ DB インスタンス（まるちえーぜっと / Multi-AZ DB instance deployment）

- 意味：別の AZ に同期スタンバイを 1 台自動で作って保つ、RDS の高可用性の構成
- ポイント：プライマリからスタンバイへは同期で複製する。障害やメンテナンスのときは自動でスタンバイに切り替わる。スタンバイは読み取りに使えない（読み取りの拡張にはならない）。同期の分、シングル AZ より書き込みのレイテンシーが長くなることがある。既存の DB インスタンスを変更してマルチ AZ にできる
- 例：本番の RDS for PostgreSQL をマルチ AZ にして、AZ の障害でも自動で復旧させる

#### マルチ AZ DB クラスター（まるちえーぜっとくらすたー / Multi-AZ DB cluster deployment）

- 意味：3 つの AZ に 1 台のライターと 2 台の読み取り可能なリーダーを置く、RDS の準同期の高可用性の構成
- ポイント：変更のコミットには少なくとも 1 台のリーダーの承認が要る（準同期）。リーダーはフェイルオーバー先になり、読み取りも処理する。マルチ AZ DB インスタンスより高可用性・読み取りの容量・書き込みレイテンシーの点で優れる。Aurora DB クラスターとは別のもの
- 例：RDS for MySQL で、高可用性と読み取りの分散を 1 つの構成で満たす

#### リードレプリカ（りーどれぷりか / Read replica）

- 意味：DB インスタンスの読み取り専用のコピー。プライマリの更新が非同期でコピーされる
- ポイント：読み取りのクエリをレプリカに向けて、プライマリの負荷を下げる。プライマリあたり最大 15 台（クォータ）。RDS はリードレプリカの自動スケーリングをサポートしないので、手動で作る（自動で増減したいなら Aurora Auto Scaling）。同じリージョンの中の複製のデータ転送には料金がかからない
- 例：業務レポートのクエリを本番ではなくリードレプリカで実行する

#### クロスリージョンリードレプリカ（くろすりーじょん / Cross-Region read replica）

- 意味：ソースの DB インスタンスと別のリージョンに作るリードレプリカ
- ポイント：使い道は 3 つ。災害対策（障害のときに昇格させる）、ユーザーに近いリージョンでの読み取り、リージョン間の移行。RDS が安全な通信路を設定する。リージョンをまたぐデータ転送には料金がかかる
- 例：東京の RDS for MySQL の、大阪のリードレプリカ

#### リードレプリカの昇格（しょうかく / Promote a read replica）

- 意味：リードレプリカを、書き込みもできる独立した DB インスタンスにすること
- ポイント：昇格すると再起動し、数分以上かかることがある。昇格したあとはソースとの複製が止まる。ほかのリードレプリカには影響しない。災害復旧や、データを分けて別の DB にするときに使う
- 例：東京のリージョンが使えなくなったので、大阪のリードレプリカを昇格して本番にする

### 接続・容量・カスタマイズ

#### ストレージの自動スケーリング（すとれーじのじどうすけーりんぐ / Storage autoscaling）

- 意味：空き領域が少なくなったときに、RDS が DB インスタンスのストレージを自動で増やす機能
- ポイント：空き領域が割り当ての 10% 未満の状態が 5 分以上続くと増やす（前の変更から一定の条件を満たすとき）。増えるのはストレージで、インスタンスクラス（CPU・メモリ）や読み取りの台数ではない。ワークロードが予測できないときに使う
- 例：利用者が急に増えている新しいモバイルゲームの DB

#### RDS Proxy（あーるでぃーえすぷろきし / Amazon RDS Proxy）

- 意味：アプリと DB の間に置き、データベース接続をプールして共有するマネージドなプロキシ
- ポイント：接続を毎回開くオーバーヘッドを減らし、急な接続の増加から DB を守る。フェイルオーバーのとき、アプリの接続を保ったままスタンバイにつなぎ直す。IAM 認証を強制でき、認証情報は Secrets Manager に置ける。ほとんどのアプリはコードを変えずに使える
- 例：Lambda 関数が同時にたくさん動いて DB の接続数があふれるのを防ぐ

#### RDS Custom（あーるでぃーえすかすたむ / Amazon RDS Custom）

- 意味：データベースの環境と OS へのアクセスとカスタマイズを許す、RDS の形態
- ポイント：ふつうの RDS は基盤のホストにアクセスできず、一部の特権も制限される。依存するアプリのために DB と OS の管理者権限が要るなら RDS Custom。すべてを AWS に任せたいならふつうの RDS
- 例：特定の OS の設定が必要なパッケージアプリの Oracle を、マネージドの利点を残して動かす

#### メンテナンスウィンドウ（めんてなんすうぃんどう / Maintenance window）

- 意味：パッチ適用などのメンテナンスを行う、DB インスタンスごとの週単位の 30 分の時間帯
- ポイント：セキュリティと信頼性に関わるパッチだけが必須として自動でスケジュールされ、まれ（通常は数か月に一度）。マルチ AZ なら、スタンバイをメンテナンスして昇格させ、旧プライマリをメンテナンスして新しいスタンバイにするので、止まる時間を短くできる
- 例：メンテナンスウィンドウを、利用の少ない日曜の深夜にする

## 15-2 RDS の保護と運用

### まとめ表

| したいこと | 使う機能 |
| :-: | :-: |
| 数分前の状態に戻す | 特定時点への復元（PITR）＝新しい DB インスタンスができる |
| 35 日より長く残す | 手動の DB スナップショット（または AWS Backup） |
| 別のリージョンにバックアップ | 自動バックアップのクロスリージョンレプリケーション |
| 暗号化していない DB を暗号化 | スナップショットを暗号化してコピーし、復元する |
| パスワードなしで接続 | IAM データベース認証（MariaDB・MySQL・PostgreSQL） |
| マスターパスワードを自動で変える | Secrets Manager との統合（既定で 7 日ごと） |
| 本番に影響なく更新を試す | ブルー/グリーンデプロイ |

### バックアップと復元

#### 自動バックアップ（じどうばっくあっぷ / Automated backups）

- 意味：バックアップウィンドウの間に RDS が自動で取る、DB インスタンス全体のバックアップ
- ポイント：ストレージボリュームのスナップショットとトランザクションログで、保持期間の任意の時点に戻せる。保持期間は DB インスタンスで 0〜35 日（0 で無効）、マルチ AZ DB クラスターで 1〜35 日。バックアップは S3 に保存される。DB を削除するとき「自動バックアップの保持」を選ばないと、自動バックアップも一緒に消える
- 例：保持期間を 7 日にして、1 週間以内の任意の時点に戻せるようにする

#### 特定時点への復元（とくていじてんへのふくげん / Point-in-time recovery, PITR）

- 意味：バックアップ保持期間の中の任意の時点の状態で、新しい DB インスタンスを作る復元
- ポイント：元の DB インスタンスは変わらず、新しいインスタンスができる（接続先が変わる）。トランザクションログは 5 分ごとに S3 にアップロードされるので、戻せる最新の時刻（LatestRestorableTime）は通常、現在の数分前。Aurora MySQL のバックトラックとの違いは、新しい DB を作るかどうか
- 例：誤って表を消したので、消す 1 分前の時点で新しい DB インスタンスを作り、データを取り出す

#### DB スナップショット（でぃーびーすなっぷしょっと / DB snapshot）

- 意味：利用者が手動で取る DB インスタンスのバックアップ
- ポイント：最初は全体、以後は増分。自動バックアップと違って保持期間で消えず、DB インスタンスを削除しても残る。コピー（別のリージョン・暗号化）と共有（別のアカウント）ができる。35 日を超えて残したいときに使う
- 例：大きな変更の前に手動スナップショットを取っておく

#### 自動バックアップのクロスリージョンレプリケーション（じどうばっくあっぷのれぷりけーしょん / Cross-Region automated backups）

- 意味：スナップショットとトランザクションログを、別のリージョンにも複製する設定
- ポイント：別のリージョンで特定時点への復元ができ、災害対策になる。リードレプリカと違い、別のリージョンで DB インスタンスを動かし続けないので、読み取りには使えない。マルチ AZ DB クラスターではサポートされない（マルチ AZ DB インスタンスはできる）
- 例：東京の RDS for Oracle のバックアップを大阪にも複製する

### セキュリティと更新

#### RDS の暗号化（あんごうか / Amazon RDS encryption）

- 意味：KMS キーで、DB インスタンスのストレージ・ログ・自動バックアップ・リードレプリカ・スナップショットを保管時に暗号化する機能
- ポイント：AES-256 で、アプリの変更は要らない。作成後に KMS キーは変えられない。暗号化していない DB インスタンスの暗号化されたリードレプリカは作れない。暗号化していない DB を暗号化するには、スナップショットを暗号化してコピーし、そこから復元する（ブルー/グリーンデプロイでもできる）
- 例：既存の暗号化していない DB を、暗号化したスナップショットのコピーから作り直す

#### IAM データベース認証（あいえーえむでーたべーすにんしょう / IAM database authentication）

- 意味：パスワードの代わりに、IAM で作る認証トークンで DB に接続するしくみ
- ポイント：MariaDB・MySQL・PostgreSQL で使える。トークンは署名バージョン 4 で作られ、有効期間は 15 分。DB にユーザーの認証情報を保存せず、IAM でアクセスを一元管理できる。通信は SSL/TLS で暗号化される
- 例：EC2 のロールに DB への接続を許可する IAM ポリシーを付け、アプリはトークンで接続する

#### Secrets Manager との統合（しーくれっつまねーじゃー / Password management with Secrets Manager）

- 意味：RDS のマスターユーザーのパスワードを、Secrets Manager で管理させる機能
- ポイント：RDS がシークレットを作って管理し、既定で 7 日ごとにローテーションする（スケジュールは変えられる）。パスワードをコードや設定ファイルに書かなくてよい。IAM データベース認証との違いは、パスワード自体はあり、それを自動で管理すること
- 例：マスターパスワードを人が知らないままにし、アプリは Secrets Manager から読む

#### ブルー/グリーンデプロイ（ぶるーぐりーん / Blue/Green Deployments）

- 意味：本番（ブルー）をコピーして同期し続けるステージング環境（グリーン）を作り、変更を試してから切り替える機能
- ポイント：エンジンのバージョンアップやパラメータの変更をグリーンで試せる。切り替え（スイッチオーバー）は通常 1 分もかからず、データは失われず、アプリの変更も要らない。RDS では MariaDB・MySQL・PostgreSQL でサポート
- 例：MySQL のメジャーバージョンアップを、グリーンで確かめてから短時間で切り替える

## 15-3 Amazon Aurora

### まとめ表

| 機能 | 何をする | 選ぶ合図 |
| :-: | :-: | :-: |
| Aurora レプリカ | 最大 15 台・ラグは通常 100 ミリ秒未満・フェイルオーバー先 | 読み取りの拡張と高可用性 |
| Aurora Auto Scaling | Aurora レプリカの数を自動で増減 | 読み取りの負荷が変わる |
| Aurora Serverless v2 | ACU で容量を自動調整（0〜256 ACU） | 予測できない・使わない時間がある |
| Global Database | 最大 10 のセカンダリリージョンに通常 1 秒未満で複製 | 世界で読む・リージョンの災害対策 |
| バックトラック | 新しいクラスターを作らずに巻き戻す（最大 72 時間） | Aurora MySQL で誤操作を戻す |
| クローン | コピーオンライトで速く安く複製 | 本番データでテスト環境 |

### Aurora のしくみ

#### Amazon Aurora（おーろら / Amazon Aurora）

- 意味：MySQL・PostgreSQL と互換性がある、フルマネージドのリレーショナルデータベースエンジン
- ポイント：RDS の一部で、高速な分散ストレージを使う。ストレージは自動で伸び、クラスターボリュームは最大 256 TiB。DB インスタンスの集まり（クラスター）とストレージが分かれている。RDS for MySQL・PostgreSQL からはスナップショットの復元などで移せる
- 例：RDS for MySQL を Aurora MySQL に移して、読み取りの台数と可用性を上げる

#### クラスターボリューム（くらすたーぼりゅーむ / Cluster volume）

- 意味：Aurora のデータを保存する、SSD の単一の仮想ボリューム
- ポイント：3 つの AZ にデータの 6 つのコピーを持つ。リーダーがいてもいなくても複製される（ライター 1 台だけでもストレージは 3 AZ）。インスタンスを足してもデータをコピーしないので、すぐに追加できる。データを消すと領域が解放される
- 例：ライター 1 台だけのクラスターでも、ストレージは AZ の障害でデータを失いにくい

#### Aurora レプリカ（おーろられぷりか / Aurora Replica）

- 意味：Aurora DB クラスターの中の、読み取り専用の DB インスタンス（リーダーインスタンス）
- ポイント：最大 15 台。ストレージを共有するので、レプリカラグは通常 100 ミリ秒未満。プライマリに問題があると、レプリカの 1 台がプライマリを引き継ぐ（フェイルオーバー）。可用性のため、プライマリとリーダーを複数の AZ に分けるのが勧められる
- 例：ライター 1 台だけのクラスターに、別の AZ のリーダーを足してマルチ AZ にする

#### Aurora I/O-Optimized と Aurora Standard（あいおーおぷてぃまいずど / Aurora I/O-Optimized, Aurora Standard）

- 意味：Aurora の 2 つのストレージ設定。I/O-Optimized は読み書きの I/O に追加料金がなく、Standard は I/O のリクエストごとに料金がかかる
- ポイント：I/O の支出が Aurora の総支出の 25% 以上なら I/O-Optimized、25% 未満なら Standard が向く。I/O-Optimized から Standard へはいつでも、Standard から I/O-Optimized へは 30 日に 1 回切り替えられる
- 例：I/O の料金が全体の 40% を占める注文処理の DB を I/O-Optimized にする

### エンドポイント

#### クラスターエンドポイント（くらすたーえんどぽいんと / Cluster endpoint）

- 意味：Aurora DB クラスターの、いまのプライマリ（ライター）インスタンスにつながる接続先
- ポイント：INSERT・DDL・DML など書き込みに使う。フェイルオーバーで別のインスタンスが昇格しても、同じ接続文字列のままでよい
- 例：アプリの書き込み用の接続先をクラスターエンドポイントにする

#### リーダーエンドポイント（りーだーえんどぽいんと / Reader endpoint）

- 意味：Aurora レプリカ全体に、読み取りの接続を自動で分散する接続先
- ポイント：クエリ（読み取り）に使う。接続のバランシングは Aurora が行う。書き込みはできない
- 例：アプリの読み取り用の接続先をリーダーエンドポイントにする

#### カスタムエンドポイント（かすたむえんどぽいんと / Custom endpoint）

- 意味：クラスターの中の、選んだ DB インスタンスの組だけにつながる接続先
- ポイント：インスタンスの大きさや設定が違うものが混ざっているときに便利。リーダーエンドポイントは全レプリカ、カスタムエンドポイントは選んだインスタンスだけ。インスタンスエンドポイントは特定の 1 台（診断やチューニング用）
- 例：大きなインスタンスのレプリカ 2 台だけを、分析用のカスタムエンドポイントにまとめる

### スケーリングとグローバル

#### Aurora Auto Scaling（おーろらおーとすけーりんぐ / Aurora Auto Scaling）

- 意味：Aurora レプリカの数を、ワークロードに合わせて自動で増減する機能
- ポイント：スケーリングポリシーで最小と最大の台数を決め、CloudWatch のメトリクス（平均 CPU 使用率など）とターゲット値で調整する。ライターには効かず、リーダーの負荷にだけ役立つ。RDS のリードレプリカには自動スケーリングがない
- 例：リーダーの平均 CPU 使用率 60% を保つように、レプリカを 1〜5 台で増減する

#### Aurora Serverless v2（おーろらさーばーれす / Aurora Serverless v2、ドキュメントでは Aurora serverless）

- 意味：Aurora の容量を需要に合わせて自動で調整する、オンデマンドのオートスケーリング設定
- ポイント：容量の単位は ACU（約 2 GiB のメモリと CPU・ネットワーク）。0〜256 ACU の範囲を決める。最小を 0 ACU にすると、使われていないときに一時停止（自動一時停止）できる。使った分だけの料金。ACU を半分ずつ細かく足せる。負荷が大きく変わる・予測できない・開発やテストに向く
- 例：夜は使わない社内システムの DB を、最小 0 ACU の Serverless v2 にする

#### Aurora Global Database（おーろらぐろーばるでーたべーす / Amazon Aurora Global Database）

- 意味：1 つのプライマリリージョンと最大 10 の読み取り専用のセカンダリリージョンにまたがる、1 つの Aurora データベース
- ポイント：書き込みはプライマリリージョンだけ。専用のインフラで通常 1 秒未満のレイテンシーで複製する。RPO は通常秒単位、RTO は分単位。計画的な切り替え（スイッチオーバー、データ損失なし）と、障害時のフェイルオーバーがある。書き込み転送で、セカンダリからの書き込みをプライマリに送れる
- 例：東京をプライマリ、バージニア北部とフランクフルトをセカンダリにして、各地のユーザーが近くで読む

### 戻す・複製する

#### バックトラック（ばっくとらっく / Backtrack）

- 意味：バックアップから復元せずに、Aurora MySQL の DB クラスターを指定した時刻まで巻き戻す機能
- ポイント：Aurora MySQL だけ。新しいクラスターを作らないので速い。バックトラックウィンドウの上限は 72 時間。前後に何度も動かして、変更がいつ起きたかを調べられる。バックアップと復元の代わりではない
- 例：WHERE 句を付け忘れた DELETE を、実行の直前まで巻き戻す

#### Aurora クローン（くろーん / Aurora cloning）

- 意味：元のクラスターと同じデータページを共有する、独立したボリュームを持つ新しいクラスターを作る機能
- ポイント：コピーオンライトなので、最初はほとんど追加の領域が要らず、変更したページの分だけストレージが増える。高速で費用効果が高いように設計されている。本番データを壊さずにテストや分析ができる
- 例：本番の Aurora をクローンして、スキーマ変更の影響を試す

#### Aurora の自動バックアップ（おーろらのじどうばっくあっぷ / Aurora backups）

- 意味：Aurora がクラスターボリュームを連続的・増分的にバックアップし、保持期間の間残すしくみ
- ポイント：保持期間の任意の時点に復元できる（新しいクラスターができる）。保持期間は 1〜35 日で、既定は 1 日。保持期間を超えて残すならクラスタースナップショット（期限切れにならない）。バックアップの書き込みで性能に影響したり中断したりしない
- 例：保持期間を 14 日にし、月末の状態はクラスタースナップショットで残す
