## 11-1 DNS とホストゾーン

### まとめ表

| やりたいこと | 使うもの |
| :-: | :-: |
| ドメイン名を取る・他社から移す | Route 53 のドメイン登録 |
| インターネットに名前を公開する | パブリックホストゾーン |
| VPC の中だけで名前を引く | プライベートホストゾーン（VPC の DNS 属性を 2 つとも true） |
| example.com（ゾーンの頂点）を ALB・CloudFront に向ける | エイリアスレコード（CNAME は作れない） |
| 別の名前に向ける（サブドメイン） | CNAME またはエイリアス |
| 応答の改ざんを防ぐ | DNSSEC 署名 |

### Route 53 とゾーン

#### Amazon Route 53（るーとごじゅうさん / Amazon Route 53）

- 意味：ドメイン登録・DNS ルーティング・ヘルスチェックの 3 つの機能を持つ、AWS の DNS サービス
- ポイント：3 つを好きな組み合わせで使える（ドメインは他社で登録し、DNS だけ Route 53 にする、など）
- 例：example.com を Route 53 で登録し、ホストゾーンでレコードを管理し、ヘルスチェックでフェイルオーバーする

#### ドメインの登録（とうろく / domain registration）

- 意味：新しいドメイン名（example.com など）を取得すること。Route 53 はドメインのレジストラとして登録できる
- ポイント：ほかのレジストラから Route 53 に移管することも、逆に Route 53 から別のレジストラに移管することもできる
- 例：他社で取った example.com を Route 53 に移管する

#### パブリックホストゾーン（ぱぶりっくほすとぞーん / public hosted zone）

- 意味：インターネットでのトラフィックのルーティングの仕方を決めるレコードを入れる入れ物。ホストゾーンの名前はドメインと同じ
- ポイント：ホストゾーンを作ると、Route 53 のネームサーバー（4 つ）が割り当てられる。他社で登録したドメインなら、レジストラ側のネームサーバーを Route 53 のものに変える
- 例：example.com のパブリックホストゾーンに www の A レコードを作る

#### プライベートホストゾーン（ぷらいべーとほすとぞーん / private hosted zone）

- 意味：関連付けた 1 つ以上の VPC の中からの DNS クエリにだけ応える、ホストゾーン
- ポイント：インターネットからは引けない。VPC の enableDnsHostnames と enableDnsSupport の両方を true にする必要がある。同じドメイン名で、外向き（パブリック）と内向き（プライベート）を分けるスプリットビュー DNS もできる
- 例：db.corp.example.com を VPC の中だけで引けるようにする

#### A レコードと AAAA レコード（えーれこーど / A and AAAA records）

- 意味：名前を IP アドレスに対応させるレコード。A は IPv4、AAAA は IPv6
- ポイント：最も基本のレコード。エイリアスレコードも、種類としては A や AAAA で作る
- 例：www.example.com → 192.0.2.10（A）

#### CNAME レコード（しーねーむれこーど / CNAME record）

- 意味：ある名前へのクエリを、別のドメイン名に対応させるレコード
- ポイント：ゾーンの頂点（example.com そのもの）には作れない。サブドメインには作れる。CNAME のクエリには料金がかかる。AWS のリソースに向けるならエイリアスレコードがよい
- 例：shop.example.com → shop.example.net（CNAME）
- 語の意味：Canonical＝正式の、Name＝名前

#### その他のレコード（MX・TXT・NS・SOA・CAA）（そのほかのれこーど / other record types）

- 意味：MX＝メールサーバーの名前と優先順位。TXT＝文字列（SPF の値など）。NS＝ホストゾーンのネームサーバー。SOA＝ドメインとホストゾーンの情報。CAA＝そのドメインの証明書を発行してよい認証局
- ポイント：NS と SOA はホストゾーンを作ると自動で作られる。SPF は SPF タイプではなく TXT レコードで書くのが勧められている。CAA で、許していない認証局が証明書を出すのを防ぐ
- 例：example.com の CAA に amazon.com を書き、ACM だけに発行を許す（Claude が作った例）

#### TTL（てぃーてぃーえる / time to live）

- 意味：DNS リゾルバーがレコードの値をキャッシュしておく秒数
- ポイント：長いと、Route 53 へのクエリが減って料金が下がるが、値を変えたときに反映が遅れる。短いと、変更やフェイルオーバーが早く効く。ヘルスチェックと組み合わせるレコードは 60 秒以下が勧められている。エイリアスレコードでは TTL を自分で決められない
- 例：移行の前日に TTL を 300 秒から 60 秒に下げておく
- 語の意味：Time＝時間、To＝〜まで、Live＝生きている

#### エイリアスレコード（えいりあすれこーど / alias record）

- 意味：ALB・CloudFront・S3 の静的ウェブサイト・API Gateway などの AWS リソースや、同じホストゾーンの別のレコードに向ける、Route 53 独自の DNS の拡張
- ポイント：CNAME と違い、ゾーンの頂点（example.com）にも作れる。AWS リソースへのエイリアスのクエリは無料（CNAME は有料）。リソースの IP が変わっても自動で追従する。TTL はリソース側のものが使われる
- 例：example.com（頂点）を ALB に向けるエイリアスの A レコード

#### DNSSEC 署名（でぃーえぬえすせっく / DNSSEC signing）

- 意味：ホストゾーンのすべての応答に公開鍵暗号で署名し、DNS リゾルバーが「Route 53 から送られ、改ざんされていない」ことを確かめられるようにする機能
- ポイント：DNS の応答のなりすましや改ざんを見抜ける。キー署名キー（KSK）を使い、親のゾーンに DS レコードを置いて信頼の連鎖を作る。有効にすると、レコードの TTL は 1 週間までに制限される
- 例：金融サービスのドメインで DNSSEC 署名を有効にする

## 11-2 ルーティングポリシー

### まとめ表

| ポリシー | 何で選ぶ | 本番の言い回し |
| :-: | :-: | :-: |
| シンプル | 1 つのリソース（値を複数書くとランダムな順） | 「1 台の Web サーバー」 |
| 加重 | 決めた比率 | 「新バージョンに 10% だけ」「カナリア」 |
| レイテンシー | 利用者から最もレイテンシーが低いリージョン | 「世界中の利用者に最も速いリージョン」 |
| フェイルオーバー | プライマリが正常ならプライマリ、異常ならセカンダリ | 「アクティブ/パッシブ」「障害時だけ予備へ」 |
| 位置情報 | 利用者のいる場所（大陸・国・米国の州） | 「国ごとに別のサイト」「配信を国で制限」 |
| 地理的近接性 | 利用者とリソースの距離＋バイアス | 「範囲を広げて、あるリージョンに多く送る」 |
| 複数値回答 | ヘルスチェックに合格した最大 8 つをランダムに | 「DNS で複数の IP、異常なものは返さない」 |
| IP ベース | 利用者の IP の CIDR | 「特定の ISP の利用者を特定のエンドポイントへ」 |

### ルーティングポリシー

#### シンプルルーティング（しんぷるるーてぃんぐ / simple routing）

- 意味：特別なルーティングをせず、ふつうの DNS レコードとして 1 つのリソースに向けるポリシー
- ポイント：同じ名前とタイプのレコードは 1 つだけだが、1 つのレコードに複数の IP を書ける（値ごとの正常性は確かめない）。エイリアスならリソースを 1 つだけ指定する
- 例：www.example.com を 1 台の Web サーバーに向ける

#### 加重ルーティング（かじゅうるーてぃんぐ / weighted routing）

- 意味：同じ名前とタイプのレコードを複数作り、それぞれの重みの割合でトラフィックを分けるポリシー
- ポイント：新しいバージョンに少しだけ流すテスト（カナリア）や、少しずつの移行に使う。割合＝そのレコードの重み ÷ 全体の重みの合計。重みを 0 にすると、そのリソースへ送るのを止められる
- 例：旧環境 90・新環境 10 の重みで、新環境に 10% を送る

#### レイテンシールーティング（れいてんしーるーてぃんぐ / latency-based routing）

- 意味：複数の AWS リージョンにリソースがあるとき、利用者から最もレイテンシーが低いリージョンのレコードを返すポリシー
- ポイント：レイテンシーのデータは、利用者と AWS のデータセンターのあいだの測定に基づく。地図の上の距離ではなく、ネットワークの速さで選ぶ。地理的に近くても、遅ければ選ばれない
- 例：オレゴンとシンガポールの ALB。ロンドンの利用者には、レイテンシーが低いほうを返す

#### フェイルオーバールーティング（ふぇいるおーばーるーてぃんぐ / failover routing）

- 意味：プライマリが正常ならプライマリに、異常ならセカンダリに送るポリシー
- ポイント：アクティブ/パッシブのフェイルオーバーを作る。プライマリにはヘルスチェック（またはエイリアスのターゲットの正常性の評価）が要る。セカンダリに S3 の静的ウェブサイトの「メンテナンス中」ページを置くのが定番
- 例：プライマリ＝東京の ALB、セカンダリ＝大阪の ALB

#### 位置情報ルーティング（いちじょうほうるーてぃんぐ / geolocation routing）

- 意味：利用者のいる場所（DNS クエリの送信元の場所）で、どのリソースに送るかを決めるポリシー。大陸・国・米国の州で指定する
- ポイント：利用者の言語でコンテンツを見せる、配信の権利がある国だけに制限する、などに使う。重なるときは小さい地域が優先。どの場所にも当たらないクエリのための「デフォルト」レコードを作らないと、そのクエリには「応答なし」になる
- 例：日本からは日本語のサイト、それ以外はデフォルトの英語のサイトへ

#### 地理的近接性ルーティング（ちりてききんせつせいるーてぃんぐ / geoproximity routing）

- 意味：利用者とリソースの場所（AWS のリージョン、または緯度と経度）の距離で、最も近いリソースに送るポリシー
- ポイント：バイアスの値で、あるリソースに送る地理的な範囲を広げたり狭めたりできる。位置情報が「場所の区切り（国など）」で決めるのに対し、地理的近接性は「距離＋バイアス」で決める
- 例：東京のリージョンのバイアスを上げ、東南アジアの一部の利用者も東京に送る

#### 複数値回答ルーティング（ふくすうちかいとうるーてぃんぐ / multivalue answer routing）

- 意味：ヘルスチェックに合格したレコードの中から、ランダムに最大 8 つの値を返すポリシー
- ポイント：シンプルに複数の IP を書くのと違い、各値にヘルスチェックを付け、異常なものは返さない。ロードバランサーの代わりではないが、DNS で可用性と負荷の分散を高める方法。全部が異常なら、最大 8 つの異常なものを返す
- 例：4 台の Web サーバーの IP を、ヘルスチェック付きで返す

#### IP ベースルーティング（あいぴーべーするーてぃんぐ / IP-based routing）

- 意味：利用者の IP アドレスの範囲（CIDR のコレクション）と、送り先のエンドポイントの対応を自分で登録して、ルーティングを決めるポリシー
- ポイント：位置情報やレイテンシーは Route 53 が集めたデータを使うが、IP ベースは自分が知っている利用者の情報で細かく決める。特定の ISP の利用者を、伝送のコストや性能が良いエンドポイントに送る
- 例：ある ISP の IP の範囲からのクエリを、その ISP と直接つながったエンドポイントへ

## 11-3 ヘルスチェックとハイブリッド DNS

### まとめ表

| 調べたいもの | ヘルスチェックの種類 |
| :-: | :-: |
| インターネットから届く Web サーバー・ALB | エンドポイントのヘルスチェック（世界各地のヘルスチェッカーから） |
| 複数のヘルスチェックをまとめて（何台以上が正常か） | 算出したヘルスチェック |
| VPC の中のプライベートなリソース・任意のメトリクス | CloudWatch アラームのヘルスチェック |
| エイリアスの先（ALB など）の正常性 | ターゲットの正常性の評価（Evaluate Target Health） |

### ヘルスチェック

#### エンドポイントのヘルスチェック（えんどぽいんとのへるすちぇっく / health checks that monitor an endpoint）

- 意味：IP アドレスかドメイン名で指定したエンドポイントに、世界各地のヘルスチェッカーからインターネット経由で定期的にリクエストを送り、正常かを確かめるヘルスチェック
- ポイント：間隔は 30 秒か 10 秒。HTTP・HTTPS・TCP。18% を超えるヘルスチェッカーが正常と報告すれば正常。ヘルスチェッカーは VPC の外にあるので、プライベートな IP には届かない
- 例：www.example.com の /health を 30 秒ごとに HTTPS で確かめる

#### 算出したヘルスチェック（さんしゅつしたへるすちぇっく / calculated health checks）

- 意味：ほかの複数のヘルスチェックの結果をまとめて、正常か異常かを決めるヘルスチェック
- ポイント：同じ役割のリソースが複数あるとき、「最低何台が正常か」で判断する。1 台が落ちただけではフェイルオーバーしない、などができる
- 例：5 台の Web サーバーのヘルスチェックのうち、3 台以上が正常なら正常とする

#### CloudWatch アラームのヘルスチェック（くらうどうぉっちあらーむのへるすちぇっく / health checks that monitor CloudWatch alarms）

- 意味：CloudWatch アラームと同じデータストリームを見て、正常か異常かを決めるヘルスチェック
- ポイント：インターネットから届かない VPC の中のリソースの正常性を見るのに使う（例：EC2 の StatusCheckFailed のアラーム）。DynamoDB の読み込みのスロットリングの数など、任意のメトリクスでも判断できる。アラームが ALARM になるのを待たずに判断する
- 例：プライベートホストゾーンのフェイルオーバーで、プライマリの DB サーバーの状態をアラームで見る

#### ターゲットの正常性の評価（たーげっとのせいじょうせいのひょうか / Evaluate Target Health）

- 意味：エイリアスレコードで、向け先（ALB や別のレコードなど）の正常性を Route 53 が評価する設定
- ポイント：Yes にすると、ヘルスチェックを別に作らなくても、向け先の正常性に応じて、そのレコードを正常・異常として扱う。ヘルスチェックを関連付ける代わりに、または一緒に使える。フェイルオーバーやレイテンシーのエイリアスレコードを組み合わせた、複雑な構成（レコードのツリー）で使う
- 例：東京と大阪の ALB へのレイテンシーのエイリアスで、Evaluate Target Health を Yes にする

### ハイブリッド DNS とフィルタリング

#### Route 53 VPC Resolver（りぞるばー / Amazon Route 53 VPC Resolver）

- 意味：すべての VPC で最初から使える DNS サーバー。パブリックなレコード・VPC 固有の DNS 名・プライベートホストゾーンへのクエリに、再帰的に答える
- ポイント：以前の名前は Route 53 Resolver。オンプレミスと VPC のあいだで名前を引き合うには、Resolver エンドポイントと条件付き転送ルールを使い、VPN か Direct Connect でつなぐ
- 例：VPC の EC2 が、プライベートホストゾーンの名前もインターネットの名前も引ける

#### インバウンドエンドポイント（いんばうんどえんどぽいんと / inbound endpoint）

- 意味：オンプレミスのネットワーク（や別の VPC）から、VPC の中の名前を引くための入口。VPC の中の IP アドレスを持つ
- ポイント：オンプレミスの DNS サーバーで、例えば aws.corp.example.com のクエリをインバウンドエンドポイントの IP に転送するよう設定する。向きを覚える：外から VPC へ入る＝インバウンド
- 例：社内の PC から、プライベートホストゾーンの db.aws.corp.example.com を引く

#### アウトバウンドエンドポイントと転送ルール（あうとばうんどえんどぽいんと / outbound endpoint and forwarding rules）

- 意味：VPC の中から、オンプレミスのネットワーク（や別の VPC）の名前を引くための出口と、どのドメインをどこに転送するかのルール
- ポイント：アウトバウンドエンドポイントと 1 つ以上のルールを作る。ルールで、どのドメインのクエリをどこに転送するかを決める。VPC から外へ出る＝アウトバウンド
- 例：corp.example.com のクエリを、オンプレミスの DNS サーバー 10.1.0.53 に転送するルール

#### DNS ファイアウォール（でぃーえぬえすふぁいあうぉーる / Route 53 Resolver DNS Firewall）

- 意味：VPC から外へ出る DNS のクエリを、ドメインのリストのルールで許可・ブロックする機能
- ポイント：ルールグループを作って VPC に関連付ける。主な用途は、侵入した攻撃者が DNS のルックアップを使って VPC のデータを外のドメインに送る「DNS 漏洩」を防ぐこと。Network Firewall は通信そのもの、DNS ファイアウォールは名前の解決を見る
- 例：既知の悪性ドメインへの名前の解決をブロックする

### 11-1 DNS とホストゾーン

#### 問 aws-11-o01

- 問：ドメイン example.com（ゾーンの頂点）を、Application Load Balancer に向けたい。最も適したレコードはどれか。
- ア：ALB を向け先にしたエイリアスレコード（A）
- イ：ALB の DNS 名を値にした CNAME レコード
- ウ：ALB の今の IP アドレスを値にした A レコード
- エ：ALB の DNS 名を値にした NS レコード
- 正解：ア
- 解説：CNAME はゾーンの頂点には作れないが、エイリアスレコードは作れる。ALB へのエイリアスのクエリは無料で、IP が変わっても追従する。
- アの意味：正しい。
- イの意味：ゾーンの頂点に CNAME は作れない。
- ウの意味：ALB の IP は変わるので、いずれ届かなくなる。
- エの意味：NS はネームサーバーを示すもので、ALB に向けるものではない。
- 出典：オリジナル問題（根拠：AWS「エイリアスレコードと非エイリアスレコードの選択」（『CNAME レコードとは異なり、DNS 名前空間の最上位ノード (*Zone Apex* とも呼ばれる) にエイリアスレコードを作成できます。』『example.com の CNAME レコードを作成することはできませんが、トラフィックを example.com にルーティングする www.example.com のエイリアスレコードを作成できます (www.example.com のレコードタイプが CNAME でない限り）。』））

#### 問 aws-11-o02

- 問：CloudFront のディストリビューションに向けるレコードで、DNS のクエリの料金をできるだけ抑えたい。最も適したものはどれか。
- ア：エイリアスレコードを使う
- イ：CNAME レコードを使う
- ウ：TTL を 0 にする
- エ：プライベートホストゾーンにレコードを作る
- 正解：ア
- 解説：Route 53 では、AWS リソースへのエイリアスのクエリは課金されない。CNAME のクエリには課金される。
- アの意味：正しい。
- イの意味：CNAME のクエリには料金がかかる。
- ウの意味：キャッシュされず、クエリが増えて料金が上がる。
- エの意味：VPC の中からしか引けず、インターネットの利用者は使えない。
- 出典：オリジナル問題（根拠：AWS「エイリアスレコードと非エイリアスレコードの選択」（『Route 53 では、 AWS リソースへのエイリアスクエリには課金されません。』『Route 53 では、CNAME クエリに対して課金されます。』））

#### 問 aws-11-o03

- 問：社内システムの名前（app.corp.example.com）を、VPC の中の EC2 からだけ引けるようにしたい。インターネットには公開しない。最も適したものはどれか。
- ア：プライベートホストゾーンを作り、VPC に関連付ける
- イ：パブリックホストゾーンを作り、セキュリティグループで制限する
- ウ：各 EC2 の hosts ファイルに書く
- エ：インバウンドエンドポイントを作る
- 正解：ア
- 解説：プライベートホストゾーンは、関連付けた VPC の中からの DNS クエリに Route 53 がどう答えるかを決める入れ物。インターネットからは引けない。
- アの意味：正しい。
- イの意味：パブリックホストゾーンはインターネットから引ける。セキュリティグループは DNS の公開範囲を決めない。
- ウの意味：台数が増えると管理できない。
- エの意味：オンプレミスから VPC の名前を引くための入口で、名前を定義するものではない。
- 出典：オリジナル問題（根拠：AWS「プライベートホストゾーンの使用」（『*プライベートホストゾーン*は、Amazon VPC サービスで作成する 1 つ以上の VPC 内のドメインとそのサブドメインへの DNS クエリに対し、Amazon Route 53 がどのように応答するかに関する情報を保持するコンテナです。』））

#### 問 aws-11-o04

- 問：プライベートホストゾーンを作って VPC に関連付けたが、EC2 から名前が引けない。VPC の設定で確かめるべきものはどれか。
- ア：VPC の enableDnsHostnames と enableDnsSupport の両方が true か
- イ：VPC にインターネットゲートウェイが付いているか
- ウ：サブネットがパブリックサブネットか
- エ：EC2 に Elastic IP が付いているか
- 正解：ア
- 解説：プライベートホストゾーンで定義した名前を使うには、VPC の enableDnsHostnames と enableDnsSupport の両方を true にする必要がある。
- アの意味：正しい。
- イの意味：プライベートホストゾーンはインターネットを通らないので関係ない。
- ウの意味：プライベートサブネットからも引ける。
- エの意味：名前の解決とは関係ない。
- 出典：オリジナル問題（根拠：AWS「VPC の DNS 属性」（『Amazon Route 53 のプライベートホストゾーンに定義されているカスタム DNS ドメイン名を使用している場合は、`enableDnsHostnames` 属性と `enableDnsSupport` 属性の両方を `true` に設定する必要があります。』））

#### 問 aws-11-o05

- 問：同じドメイン example.com で、社外の人には公開用の Web サイト、社内の VPC からは社内用のサーバーの名前を返したい。最も適したものはどれか。

- イ：加重ルーティングで社内用に 50% を送る
- ウ：同じ名前のパブリックホストゾーンとプライベートホストゾーンを作るスプリットビュー DNS
- エ：ドメインを 2 つ登録する
- 正解：ウ
- 解説：スプリットビュー DNS では、内部の使用と外部の使用で同じドメイン名を使う。VPC の中からはプライベートホストゾーンの答えが返る。
- アの意味：日本の社外の人にも社内用が返ってしまう。
- イの意味：社外の人の半分にも社内用が返る。
- ウの意味：正しい。
- エの意味：同じドメイン名で分けたいという要件に合わない。
- 出典：オリジナル問題（根拠：AWS「プライベートホストゾーンの使用」（『Route 53 を使用して、スプリットビュー DNS (別名、スプリットホライズン DNS) を設定できます。』『スプリットビュー DNS では、内部使用 (accounting.example.com) とパブリックウェブサイト (www.example.com) などの外部使用で同じドメイン名 (example.com) を使用します。』））

#### 問 aws-11-o06

- 問：来週、Web サーバーの IP アドレスを変える。変えたあと、古い IP に送られる時間をできるだけ短くしたい。前もってしておくこととして最も適したものはどれか。
- ア：レコードの TTL を長くしておく
- イ：レコードを CNAME に変える
- ウ：レコードの TTL を短くしておく
- エ：DNSSEC 署名を有効にする
- 正解：ウ
- 解説：TTL を短くすると、レコードの値を変えたあとに DNS リゾルバーが古いリソースに送る時間が短くなる。長いと変更の反映に時間がかかる。
- アの意味：キャッシュが長く残り、古い IP に送られる時間が延びる。
- イの意味：キャッシュの時間は変わらない。
- ウの意味：正しい。
- エの意味：改ざんを防ぐもので、反映の速さとは関係ない。
- 出典：オリジナル問題（根拠：AWS「Amazon Route 53 の概念」（『TTL を短くすると、www.example.com のウェブサーバーの IP アドレスを変更するなどして、レコードの値を変更した後に DNS リゾルバーが古いリソースにトラフィックをルーティングする時間を短縮できます。』））

#### 問 aws-11-o07

- 問：DNS の応答がなりすまされ、利用者が偽のサイトに誘導される攻撃を防ぎたい。DNS リゾルバーが、応答が Route 53 から来て改ざんされていないことを確かめられるようにしたい。最も適したものはどれか。

- 正解：ア

- アの意味：正しい。
- イの意味：証明書を発行してよい認証局を決めるもので、DNS の応答は守らない。
- ウの意味：VPC から外へ出るクエリを絞るもので、応答の正しさを証明するものではない。

#### 問 aws-11-o08

- 問：他社のレジストラで登録しているドメインを、Route 53 で管理したい。Route 53 について正しいものはどれか。
- ア：Route 53 は DNS だけのサービスで、ドメインの登録はできない
- イ：ドメインの登録を Route 53 に移管できるほか、登録は他社のままで DNS だけを Route 53 にすることもできる
- ウ：Route 53 に移管したドメインは、ほかのレジストラに戻せない
- エ：Route 53 の DNS を使うには、必ずドメインを Route 53 で登録しなければならない
- 正解：イ
- 解説：Route 53 はドメイン登録・DNS ルーティング・ヘルスチェックを好きな組み合わせで使える。他社からの移管も、Route 53 から他社への移管もできる。
- アの意味：Route 53 でドメインを登録できる。
- イの意味：正しい。
- ウの意味：別のレジストラに移管できる。
- エの意味：3 つの機能は好きな組み合わせで使える。
- 出典：オリジナル問題（根拠：AWS「Amazon Route 53 とは？」（『Route 53 を使用すると、ドメイン登録、DNS ルーティング、ヘルスチェックの 3 つの主要な機能を任意の組み合わせで実行できます。』）／AWS「Amazon Route 53 を使用したドメインの登録と管理」（『また、既存のドメインの登録を他のレジストラから Route 53 に移管することも、逆に、Route 53 に登録したドメインの登録を別のレジストラに移管することもできます。』））

### 11-2 ルーティングポリシー

#### 問 aws-11-o10

- 問：新しいバージョンのアプリを、まず全利用者の 5% だけで試し、問題がなければ少しずつ増やしたい。DNS で実現する最も適したポリシーはどれか。
- ア：加重ルーティング
- イ：レイテンシールーティング
- ウ：フェイルオーバールーティング
- エ：複数値回答ルーティング
- 正解：ア
- 解説：加重ルーティングは、同じ名前のレコードに重みを付け、決めた割合でトラフィックを分ける。新しいバージョンのテストに役立ち、重みを変えて少しずつ移せる。
- アの意味：正しい。
- イの意味：利用者から速いリージョンを選ぶもので、割合は決められない。
- ウの意味：プライマリが異常になったときだけセカンダリへ送る。
- エの意味：正常な値をランダムに返すだけで、割合は決められない。
- 出典：オリジナル問題（根拠：AWS「加重ルーティング」（『加重ルーティングを使用すると、複数のリソースを単一のドメイン名 (example.com) またはサブドメイン名 (acme.example.com) にリンクし、各リソースへのトラフィック量を選択できます。』『これは、ソフトウェアの新しいバージョンのロードバランシングとテストに役立ちます。』））

#### 問 aws-11-o11

- 問：加重ルーティングで、A に重み 3、B に重み 1 を付けた。B に送られるトラフィックのおよその割合はどれか。
- ア：33%
- イ：75%
- ウ：1%
- エ：25%
- 正解：エ
- 解説：割合は、そのレコードの重み ÷ グループのすべての重みの合計。B は 1 ÷（3＋1）＝ 25%。
- アの意味：1 ÷ 3 で計算しており、合計を使っていない。
- イの意味：A の割合。
- ウの意味：重みの値をそのまま割合と読んでいる。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「加重ルーティング」（『重みが 1 のリソースは、トラフィックの 1/256 (1/(1\+255)) を、他のリソースは 255/256 (255/(1\+255)) を取得します。』））

#### 問 aws-11-o14
