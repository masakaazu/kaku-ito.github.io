## 06-1 疎結合と SQS のキュー

### まとめ表

| 項目 | 標準キュー | FIFO キュー |
| :-: | :-: | :-: |
| スループット | ほぼ無制限 | 1 秒あたり 300 API コール（バッチで 3,000 メッセージ）。高スループットモードで最大 30,000 TPS |
| 配信 | 少なくとも 1 回（重複することがある） | 1 回のみの処理（5 分間の重複排除） |
| 順序 | ベストエフォート（保証しない） | メッセージグループの中で送った順 |

### 疎結合と SQS

#### 疎結合（そけつごう / loose coupling）

- 意味：部品どうしが互いの都合（同時に動いているか・処理の速さ）に直接しばられないようにつなぐこと
- ポイント：あいだにキューやトピックをはさむと、送る側は受け取る側が止まっていても送れる。片方が落ちても全体が止まりにくく、それぞれを別々にスケールできる。「弾力性に優れた（止まりにくい）アーキテクチャ」の基本
- 例：注文の受付（Web）と在庫の引き当て（バッチ）のあいだに SQS をはさむ

#### Amazon SQS（あまぞんえすきゅーえす / Amazon Simple Queue Service）

- 意味：分散したシステムや部品をつないだり切り離したりするための、フルマネージドのメッセージキュー
- ポイント：受け取る側が取りに行く（ポーリング）しくみ。メッセージは複数のサーバー・複数の AZ に保存される。1つのメッセージは基本的に1つの受け手が処理して消す（1対1）。たくさんの受け手に配るなら SNS
- 語の意味：Simple＝簡単な、Queue＝待ち行列、Service＝サービス

#### 標準キュー（ひょうじゅんきゅー / standard queue）

- 意味：ほぼ無制限のスループットを持つ、SQS のデフォルトのキュー
- ポイント：少なくとも1回の配信で、同じメッセージが2回以上届くことがある。順序はベストエフォートで保証しない。重複を処理しても困らないよう、受け手をべき等にする

#### FIFO キュー（ふぁいふぉきゅー / FIFO queue）

- 意味：送った順に、1回だけ処理されるよう設計された SQS のキュー
- ポイント：順序はメッセージグループの中で守られる。グループを分けると、各グループの順序を保ったまま並列に処理できる。5 分間の重複排除の間隔のあいだに同じメッセージを送り直しても重複は入らない。スループットは標準キューより低い
- 語の意味：FIFO＝First-In, First-Out（先に入ったものが先に出る）

#### メッセージグループ（めっせーじぐるーぷ / message group）

- 意味：FIFO キューの中で、順序を守る単位。`MessageGroupId` で指定する
- ポイント：同じグループの中は送った順、違うグループどうしは並列に処理できる。グループの数に上限はない
- 例：注文ごと（注文 ID ごと）にグループを分け、注文の中のイベントの順序だけ守る

#### べき等性（べきとうせい / idempotency）

- 意味：同じ処理を何回くり返しても、結果が1回だけ行ったときと同じになる性質
- ポイント：標準キューは同じメッセージが2回以上届くことがあるので、受け手をべき等にしておく（処理済みの ID を記録するなど）。または FIFO キューを使う

#### メッセージの保持期間とサイズ（めっせーじのほじきかんとさいず / message retention period and size）

- 意味：SQS がメッセージを残す期間（デフォルト 4 日・最小 1 分・最大 14 日）と、1つのメッセージの大きさの上限（1 MiB）
- ポイント：保持期間を過ぎたメッセージは消える。1 MiB より大きいデータは、SQS 拡張クライアントライブラリで本体を S3 に置き、SQS には参照だけを送る

## 06-2 SQS の動きを調整する

### まとめ表

| 設定 | 何を決める | 値の範囲 |
| :-: | :-: | :-: |
| 可視性タイムアウト | 受け取ったあと、ほかの受け手から隠す時間 | デフォルト 30 秒・最大 12 時間 |
| 遅延キュー | 送ってから見えるようになるまでの時間 | 0 秒～15 分 |
| メッセージの保持期間 | 消えるまでの時間 | デフォルト 4 日・1 分～14 日 |
| ロングポーリング | 空のときに待つ | 空の応答を減らしてコストを下げる |
| デッドレターキュー | 何度も失敗したメッセージの行き先 | maxReceiveCount で回数を決める |

### 受け取りと失敗

#### 可視性タイムアウト（かしせいたいむあうと / visibility timeout）

- 意味：受け手がメッセージを受け取ってから、ほかの受け手に見えなくする時間。デフォルトは 30 秒、最大 12 時間
- ポイント：この時間のうちに処理して削除しないと、メッセージはキューに戻り、別の受け手が処理する（二重処理の原因）。処理にかかる時間より長めにする。`ChangeMessageVisibility` で延ばせる
- 例：処理に 2 分かかるのに 30 秒のまま → 同じ注文が何度も処理される

#### デッドレターキュー（でっどれたーきゅー / dead-letter queue, DLQ）

- 意味：正常に処理できなかったメッセージを、元のキュー（ソースキュー）から移す先のキュー
- ポイント：`maxReceiveCount`（何回受け取られたら移すか）を再処理ポリシーで決める。毒メッセージ（何度やっても失敗するもの）を分けて、ほかのメッセージの処理を止めない。元のキューと同じアカウント・同じリージョンに置く。標準キューでは有効期限は元のキューに入った時刻から数えるので、DLQ の保持期間は元より長くする
- 例：3 回受け取られても消されなかったら DLQ へ移し、ログを調べる

#### ロングポーリング（ろんぐぽーりんぐ / long polling）

- 意味：`ReceiveMessage` がすべてのサーバーを調べ、メッセージが来るまで（待ち時間が切れるまで）待ってから応答するしくみ
- ポイント：デフォルトはショートポーリング（一部のサーバーだけ見て、すぐ返る）。ロングポーリングにすると空の応答が減り、コストが下がる。待ち時間は `WaitTimeSeconds` で決める
- 例：「空の ReceiveMessage の呼び出しが多くて費用がかさむ」→ ロングポーリング

#### 遅延キュー（ちえんきゅー / delay queue）

- 意味：キューに送ったメッセージを、決めた時間（最大 15 分）だけ受け手から見えなくするキュー
- ポイント：可視性タイムアウトに似ているが、遅延は「送ったあと最初に見えるまで」、可視性タイムアウトは「受け取ったあと」。15 分より先の予定の実行は EventBridge スケジューラなどを使う

#### キューの長さでスケールする（きゅーのながさですけーるする / scaling based on SQS）

- 意味：SQS のキューにたまったメッセージ数から「インスタンスあたりのバックログ」を計算し、それを目標値にして Auto Scaling グループを増減させること
- ポイント：`ApproximateNumberOfMessages` ÷ 動いているインスタンス数 ＝ インスタンスあたりのバックログ。目標値は「許容できる待ち時間 ÷ 1件の処理時間」から決める。CPU 使用率より、たまった仕事の量に合わせて増減できる

#### Lambda のイベントソースマッピング（らむだのいべんとそーすまっぴんぐ / Lambda event source mapping for SQS）

- 意味：Lambda が SQS のキューをポーリングし、メッセージをまとめて（バッチで）関数に渡すしくみ
- ポイント：標準キューと FIFO キューの両方に対応。バッチの一部だけ失敗したときは、部分的なバッチレスポンスで失敗したものだけを再試行させる。受け手のサーバーを持たずにキューを処理できる（#07）

## 06-3 SNS・EventBridge・Amazon MQ

### まとめ表

| サービス | 形 | 選ぶ決め手 |
| :-: | :-: | :-: |
| SQS | キュー（受け手が取りに行く・1対1） | ためておいて、受け手の都合で処理 |
| SNS | トピック（押し出す・1対多） | 同じ通知を多くの受け手に同時に配る |
| EventBridge | イベントバス＋ルール | AWS のサービスや SaaS のイベントを、条件で振り分ける |
| Amazon MQ | ActiveMQ・RabbitMQ のブローカー | 既存のブローカーからコードを書き換えずに移す |

### 配る・振り分ける

#### Amazon SNS（あまぞんえすえぬえす / Amazon Simple Notification Service）

- 意味：パブリッシャー（送る側）からサブスクライバー（受ける側）にメッセージを届けるフルマネージドのサービス
- ポイント：送る側はトピックに送るだけで、登録された複数の受け手に押し出す（プッシュ）。受け手は SQS・Lambda・HTTP/HTTPS・メール・SMS・モバイルプッシュ・Data Firehose など。アプリどうし（A2A）にも人への通知（A2P）にも使う
- 語の意味：Simple＝簡単な、Notification＝通知、Service＝サービス

#### トピック（とぴっく / topic）

- 意味：SNS で、メッセージを送り込む論理的な入口。受け手はトピックをサブスクライブする
- ポイント：送る側は受け手を知らなくてよい。受け手を増やしても送る側は変えない

#### ファンアウト（ふぁんあうと / fanout）

- 意味：1つの SNS トピックに複数の SQS キューをサブスクライブさせ、同じメッセージを複数のキューに同時に配ること
- ポイント：SNS の「押し出す・1対多」と SQS の「ためる・受け手の都合で処理」を組み合わせる。受け手のシステムごとにキューがあるので、1つが止まってもほかに影響しない
- 例：「注文確定」を1つのトピックに送り、在庫・請求・メールの3つのキューに配る

#### メッセージフィルタリング（めっせーじふぃるたりんぐ / message filtering）

- 意味：SNS のサブスクリプションにフィルターポリシー（JSON）を付け、受け手が欲しいメッセージだけを受け取ること
- ポイント：デフォルトでは受け手はトピックのすべてのメッセージを受け取る。メッセージの属性や本文で絞れる。受け手ごとにトピックを分けなくてよい

#### SNS FIFO トピック（えすえぬえすふぁいふぉとぴっく / SNS FIFO topic）

- 意味：順序と重複排除を守る SNS のトピック。SQS の FIFO キューと組み合わせて使う
- ポイント：「ファンアウトしつつ、順序も守り重複もなくしたい」→ SNS FIFO トピック＋SQS FIFO キュー

#### Amazon EventBridge（あまぞんいべんとぶりっじ / Amazon EventBridge）

- 意味：イベントを使ってアプリの部品どうしをつなぐサーバーレスのサービス。イベントの取り込み・絞り込み・変換・配信を行う
- ポイント：イベントバスは、AWS のサービス・自分のアプリ・SaaS からのイベントを受けて、ルールに合うものをターゲットに送る。デフォルトのイベントバスには AWS のサービスのイベントが自動で届く
- 例：EC2 の状態が「停止」になったら Lambda を呼ぶ

#### ルールとイベントパターン（るーるといべんとぱたーん / rules and event patterns）

- 意味：EventBridge で、どのイベントをどのターゲットに送るかを決めるもの。イベントパターンはイベントの形と値の条件
- ポイント：1つのルールで複数のターゲットに同時に送れる。条件で細かく振り分けたいときは SNS より EventBridge

#### EventBridge Pipes（いべんとぶりっじぱいぷす / Amazon EventBridge Pipes）

- 意味：1つのソースからイベントを受け、絞り込み・変換・付け足しをして、1つのターゲットに届けるポイントツーポイントのつなぎ
- ポイント：イベントバスは「多くのソースから多くのターゲットへ」、パイプは「1対1」。パイプの先をイベントバスにする組み合わせも多い

#### EventBridge スケジューラ（いべんとぶりっじすけじゅーら / Amazon EventBridge Scheduler）

- 意味：cron やレート式のくり返し、または1回限りの予定で、タスクを実行するサーバーレスのスケジューラ
- ポイント：「毎日 2 時に Lambda を実行」「3 日後に1回だけ実行」など。SQS の遅延（最大 15 分）では足りない先の予定に使う

#### Amazon MQ（あまぞんえむきゅー / Amazon MQ）

- 意味：Apache ActiveMQ Classic と RabbitMQ のための、マネージドなメッセージブローカーのサービス
- ポイント：業界標準のメッセージングのプロトコルを使う既存のブローカーから、メッセージングのコードを書き換えずに移せる。新しく作るクラウドのアプリなら SQS・SNS が第一候補
- 例：オンプレミスの RabbitMQ を使うアプリを、コードを変えずに AWS に移す

### 06-1 疎結合と SQS のキュー

#### 問 aws-06-o01

- 問：Web で受けた注文を、裏の在庫システムが処理している。在庫システムが止まると Web の注文受付もエラーになってしまう。最も効果的な改善はどれか。
- ア：在庫システムのインスタンスを大きくする
- イ：Web から在庫システムを同期で呼ぶ回数を増やす（リトライ）
- ウ：Web と在庫システムのあいだに SQS のキューを置き、在庫システムはキューから取り出して処理する
- エ：Web と在庫システムを同じ EC2 に載せる
- 正解：ウ
- 解説：キューで切り離すと、在庫システムが止まっていても注文はキューにたまり、Web は受付を続けられる。復旧したら在庫システムがためた分を処理する。
- アの意味：止まったときに受付が止まる問題は残る。
- イの意味：止まっている相手に何度呼んでも失敗する。
- ウの意味：正しい。
- エの意味：結合がさらに強くなり、片方の障害で両方が止まる。
- 出典：オリジナル問題（根拠：AWS「Amazon SNS 通知の Amazon SQS キューへのファンアウトと非同期処理」（『各コンポーネントを同時に使用可能にすることなく、送受信コンポーネントを切り離します。』））

#### 問 aws-06-o02

- 問：銀行の口座の入出金のイベントを、口座ごとに発生した順に、1回だけ処理したい。最も適した SQS の構成はどれか。
- ア：標準キューを使い、受け手で並べ替える
- イ：標準キューを2つ用意して交互に送る
- ウ：FIFO キューを使い、口座番号をメッセージグループ ID にする
- エ：FIFO キューを使い、すべてのメッセージを1つのメッセージグループにする
- 正解：ウ
- 解説：FIFO キューはメッセージグループの中で送った順に取り出し、重複を受け入れない。口座ごとにグループを分ければ、口座の中の順序を守りつつ、口座どうしは並列に処理できる。
- アの意味：標準キューは重複して届くことがあり、順序も保証しない。
- イの意味：順序も1回だけの処理も保証されない。
- ウの意味：正しい。
- エの意味：順序は守れるが、すべてが1列になり並列に処理できず遅い。
- 出典：オリジナル問題（根拠：AWS「Amazon SQS キュータイプ」（『FIFO キューでは、各メッセージグループ内のメッセージを送信した順序どおりに取り出します。』／『メッセージを複数のグループに分散することで、各グループ内の順序を維持しながら、メッセージを並列処理できます。』））

#### 問 aws-06-o03

- 問：SQS の標準キューについて正しいものはどれか。
- ア：送った順に必ず届く
- イ：少なくとも1回は配信されるが、同じメッセージが2回以上届くことがある
- ウ：1 秒あたり 300 件までしか送れない
- エ：同じメッセージは決して重複しない
- 正解：イ
- 解説：標準キューは at-least-once の配信で、再試行やネットワークの遅れで2回以上届くことがある。順序はベストエフォート。スループットはほぼ無制限。
- アの意味：順序は保証しない（ベストエフォート）。
- イの意味：正しい。
- ウの意味：これは FIFO キュー（バッチなし）の目安。
- エの意味：重複がないのは FIFO キュー。
- 出典：オリジナル問題（根拠：AWS「Amazon SQS キュータイプ」（『つまり、すべてのメッセージは少なくとも 1 回配信されますが、再試行やネットワーク遅延が原因で 2 回以上配信される場合もあります。』））

#### 問 aws-06-o04

- 問：標準キューを使う画像の変換処理で、まれに同じ画像が2回変換されることがある。キューの種類は変えたくない。受け手の設計として最も適したものはどれか。
- ア：可視性タイムアウトを 0 秒にする
- イ：処理をべき等にする（処理済みの ID を記録し、同じものは処理し直さない）
- ウ：メッセージの保持期間を 1 分にする
- エ：ロングポーリングをやめる
- 正解：イ
- 解説：標準キューは重複して届くことがあるので、同じメッセージを何度処理しても結果が変わらないよう、受け手をべき等にする。
- アの意味：受け取ってすぐ他の受け手に見えるようになり、重複がかえって増える。
- イの意味：正しい。
- ウの意味：処理しきれないメッセージが消えるだけで、重複は防げない。
