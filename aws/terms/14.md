## 14-1 Amazon EBS

### まとめ表

| ボリュームタイプ | 種類 | 向く用途 | 最大 IOPS | 最大スループット | ブート |
| :-: | :-: | :-: | :-: | :-: | :-: |
| gp3 | 汎用 SSD | ほとんどの用途・ブート・開発 | 80,000 | 2,000 MiB/秒 | できる |
| gp2 | 汎用 SSD（前の世代） | 同上（容量でベースラインが決まる） | 16,000 | 250 MiB/秒 | できる |
| io2 Block Express | プロビジョンド IOPS SSD | 重要な DB・低レイテンシー・高い耐久性 | 256,000 | 4,000 MiB/秒 | できる |
| st1 | スループット最適化 HDD | ビッグデータ・DWH・ログ処理 | 500 | 500 MiB/秒 | できない |
| sc1 | Cold HDD | アクセスの少ないデータを最も安く | 250 | 250 MiB/秒 | できない |

数字は AWS「Amazon EBS ボリュームの種類」の表による

### ボリューム

#### Amazon EBS（いーびーえす / Amazon Elastic Block Store）

- 意味：EC2 インスタンスにアタッチして、ローカルのハードドライブのように使うブロックストレージ
- ポイント：ボリュームは 1 つの AZ の中で作られ、その AZ の複数のサーバーに自動で複製される。インスタンスを止めてもデータは残る（インスタンスストアとの違い）。別の AZ で使うにはスナップショットから作り直す
- 例：EC2 のルートボリュームとデータボリュームに EBS を使う
- 語の意味：Elastic＝伸縮する、Block＝ブロック単位で読み書きする、Store＝保存する場所

#### 汎用 SSD（gp3）（はんようえすえすでぃー / General Purpose SSD gp3）

- 意味：最新世代の汎用 SSD ボリューム。EBS で最も安い SSD
- ポイント：容量にかかわらず 3,000 IOPS と 125 MiB/秒のベースラインが料金に含まれ、IOPS（最大 80,000）とスループット（最大 2,000 MiB/秒）を容量と別に追加でプロビジョニングできる。バーストは使わない。GiB あたりの料金は gp2 より 20% 低い
- 例：ブートボリューム・開発環境・中規模の DB

#### 汎用 SSD（gp2）（じーぴーつー / General Purpose SSD gp2）

- 意味：前の世代の汎用 SSD ボリューム。IOPS が容量に比例する
- ポイント：ベースラインは GiB あたり 3 IOPS（最小 100、最大 16,000）。小さいボリュームは I/O クレジットで最大 3,000 IOPS までバーストする。IOPS を増やすには容量を増やすしかない。Elastic Volumes で止めずに gp3 に移行できる
- 例：IOPS のためだけに大きくした gp2 を、gp3 に変えてコストを下げる

#### プロビジョンド IOPS SSD（io2 Block Express）（ぷろびじょんどあいおぺす / Provisioned IOPS SSD io2）

- 意味：高い IOPS・大量のスループット・低いレイテンシーが要る重要なワークロード向けの、最高性能の EBS ボリューム
- ポイント：io2 Block Express は最大 256,000 IOPS・4,000 MiB/秒・64 TiB。耐久性は 99.999%（ほかは 99.8〜99.9%）。16 KiB の I/O で平均 500 マイクロ秒未満のレイテンシー。io1・io2 はマルチアタッチに対応する
- 例：ミッションクリティカルな Oracle や SQL Server の DB

#### スループット最適化 HDD（st1）（すとりーみんぐ / Throughput Optimized HDD）

- 意味：IOPS ではなくスループットで性能を示す、低コストの HDD ボリューム。アクセスの多い大きな順次の読み書き向け
- ポイント：Amazon EMR・ETL・データウェアハウス・ログ処理に向く。ブートボリュームにはできない。ランダムな小さい I/O には向かない
- 例：毎晩大きなログファイルを順に読む ETL のデータ置き場

#### Cold HDD（sc1）（こーるどえいちでぃーでぃー / Cold HDD）

- 意味：アクセスの少ないワークロード向けの、最も安い HDD ボリューム
- ポイント：ストレージのコストを最も下げたいときに使う。ブートボリュームにはできない
- 例：たまにしか読まない古いデータのファイルサーバーのボリューム

#### EBS マルチアタッチ（まるちあたっち / EBS Multi-Attach）

- 意味：1 つのプロビジョンド IOPS SSD（io1・io2）ボリュームを、同じ AZ の複数のインスタンスにアタッチする機能
- ポイント：同じ AZ の Nitro のインスタンス最大 16 台まで。gp3・gp2・HDD では使えない。同時の書き込みを整えるクラスター対応のファイルシステムやアプリが要る。別の AZ のインスタンスとファイルを共有したいなら EFS
- 例：クラスター化したアプリの 2 台から、同じ io2 ボリュームを使う

#### Elastic Volumes（いらすてぃっくぼりゅーむ / Elastic Volumes）

- 意味：EBS ボリュームのサイズの増加・タイプの変更・性能の調整を、デタッチや再起動なしで行う機能
- ポイント：変更のあと、同じボリュームを次に変えられるまで待つ時間がある（ローリング 24 時間で最大 4 回など）。gp2 から gp3 への移行もこれで行う
- 例：ディスクが足りなくなったデータボリュームを、止めずに 500 GiB から 1 TiB に増やす

#### EBS 暗号化（いーびーえすあんごうか / Amazon EBS encryption）

- 意味：KMS キーで EBS のボリュームとスナップショットを暗号化する機能。暗号化はインスタンスのホストのサーバーで行われる
- ポイント：保存時のデータと、インスタンスとボリュームのあいだを流れるデータの両方を守る。「デフォルトでの暗号化」を有効にすると新しいボリュームが自動で暗号化される。既存のボリュームやスナップショットの KMS キーは変えられないが、スナップショットのコピーのときに別のキーで暗号化できる
- 例：暗号化されていないボリュームのスナップショットを、暗号化してコピーし、そこから新しいボリュームを作る

### スナップショットとバックアップ

#### EBS スナップショット（すなっぷしょっと / Amazon EBS snapshot）

- 意味：EBS ボリュームのある時点のバックアップ。増分で、前回から変わったブロックだけを保存する
- ポイント：S3 に（直接は見えない形で）保存され、リージョンのすべての AZ に自動で複製される。そこから別の AZ にボリュームを作れる。別のリージョンや別のアカウントにもコピーできる。AWS は EBS を自動でバックアップしないので、自分で取る
- 例：毎晩スナップショットを取り、別のリージョンにもコピーする

#### Amazon Data Lifecycle Manager（でーたらいふさいくるまねーじゃー / Amazon Data Lifecycle Manager）

- 意味：EBS スナップショットと EBS-backed AMI の作成・保持・削除を自動化するマネージドサービス
- ポイント：定期的なバックアップのスケジュールを守り、古いバックアップを消してストレージのコストを下げる。複数のサービスをまとめてバックアップするなら AWS Backup（#10）
- 例：毎日スナップショットを取り、決めた数より古いものを自動で消す（Claude が作った例）

#### 高速スナップショット復元（こうそくすなっぷしょっとふくげん / Fast Snapshot Restore, FSR）

- 意味：スナップショットから作るボリュームを、作った時点で完全に初期化された状態にする機能
- ポイント：ふつうはブロックに初めてアクセスしたときに遅れが出るが、FSR ならそれがない。スナップショットと AZ の組ごとに有効にする。有効にしている時間に料金がかかる（1 時間単位）
- 例：起動直後から全性能が要る DB のボリュームを、FSR を有効にしたスナップショットから作る
- 語の意味：FSR＝Fast Snapshot Restore

#### EBS スナップショットのアーカイブ（すなっぷしょっとあーかいぶ / Amazon EBS Snapshots Archive）

- 意味：めったに使わないスナップショットを、低コストで長く保存するための階層
- ポイント：アーカイブすると増分ではなくフルスナップショットになる。90 日以上残し、ほとんどアクセスしないスナップショットのコストを最大 75% 下げられる。使うときは標準の階層に復元する
- 例：プロジェクトの終わりに取った最後のスナップショットを、規制のために何年も残す

#### ごみ箱（ごみばこ / Recycle Bin）

- 意味：誤って削除した EBS ボリューム・EBS スナップショット・EBS-backed AMI を、決めた保持期間のあいだ復元できるようにするデータ復旧の機能
- ポイント：保持ルールで期間を決める。期間内ならいつでも戻せ、過ぎると完全に削除される。「誤って消したスナップショットを戻したい」ならごみ箱
- 例：削除されたスナップショットを 7 日間ごみ箱に残す

## 14-2 Amazon EFS

### まとめ表

| 項目 | 選べるもの |
| :-: | :-: |
| ファイルシステムタイプ | リージョン（推奨・複数 AZ）／1 ゾーン（1 つの AZ） |
| ストレージクラス | EFS 標準／EFS 低頻度アクセス（IA）／EFS アーカイブ |
| スループットモード | エラスティック（推奨・既定）／プロビジョニング／バースト |
| パフォーマンスモード | 汎用（推奨）／最大 I/O（前の世代） |

### ファイルシステム

#### Amazon EFS（いーえふえす / Amazon Elastic File System）

- 意味：サーバーレスで伸縮自在な共有のファイルストレージ。容量や性能をプロビジョニングせずに使える
- ポイント：NFSv4 で、多くの EC2・ECS・EKS・Lambda・Fargate から同時にマウントできる。ファイルを足せば自動で大きくなる。Linux 向けで、Windows の EC2 からの利用はサポートされない（Windows なら FSx for Windows File Server）
- 例：複数の AZ の Web サーバーで、アップロードされた画像を共有する
- 語の意味：Elastic＝伸縮する、File System＝ファイルシステム

#### リージョンと 1 ゾーンのファイルシステム（りーじょん / Regional and One Zone file systems）

- 意味：EFS のデータを置く範囲。リージョン＝複数の AZ に冗長に保存（推奨）、1 ゾーン＝1 つの AZ に保存
- ポイント：1 ゾーンは安いが、AZ の損失や破損でデータを失うことがある。1 ゾーンは AWS Backup で自動でバックアップされる。高い可用性が要らないデータ（開発用など）に 1 ゾーン
- 例：開発環境の共有フォルダーを 1 ゾーンで安く作る

#### マウントターゲット（まうんとたーげっと / mount target）

- 意味：EFS をマウントするための、VPC の中の NFSv4 のエンドポイント（IP アドレス）
- ポイント：AZ ごとに 1 つ作れる。インスタンスは同じ AZ のマウントターゲットにつなぐ。セキュリティグループで NFS の通信を許可する。Direct Connect や VPN 経由でオンプレミスからもマウントできる
- 例：3 つの AZ にそれぞれマウントターゲットを作る

#### EFS アクセスポイント（あくせすぽいんと / EFS access points）

- 意味：EFS へのアプリケーションごとの入口。そこを通る要求に、決まったユーザー（POSIX のユーザーやグループ）とディレクトリを当てはめる
- ポイント：別のルートディレクトリを当てはめれば、そのディレクトリの下だけを使わせられる。IAM ポリシーと組み合わせて、アプリごとに決まったアクセスポイントを使わせる。S3 のアクセスポイントとは別のもの
- 例：Lambda 関数ごとに別のアクセスポイントを作り、/app1 と /app2 に分ける

### 性能・コスト・保護

#### EFS のストレージクラスとライフサイクル管理（すとれーじくらす / EFS storage classes and lifecycle management）

- 意味：EFS 標準（SSD・頻繁）・EFS 低頻度アクセス（四半期に数回）・EFS アーカイブ（年に数回）の 3 つのクラスと、ファイルをそのあいだで自動で移すライフサイクル管理
- ポイント：新しいデータはまず EFS 標準に書かれ、ライフサイクルポリシーで、アクセスのない日数に応じて IA やアーカイブに移る。標準のファイルにアクセスするとタイマーがリセットされる
- 例：30 日読まれていないファイルを IA、90 日でアーカイブに移す

#### スループットモード（するーぷっともーど / throughput modes）

- 意味：EFS で使えるスループットを決める設定。エラスティック・プロビジョニング・バーストの 3 つ
- ポイント：エラスティック（推奨・既定）は負荷に合わせて自動で上下し、予測できない・急に増えるワークロードに向く。プロビジョニングは容量に関係なく決まったスループットを確保する。バーストは容量に比例し、クレジットを使い切ると遅くなる
- 例：保存量は小さいが高いスループットが要る → エラスティックかプロビジョニング

#### パフォーマンスモード（ぱふぉーまんすもーど / performance modes）

- 意味：EFS のレイテンシーと並列性の性格を決める設定。汎用と最大 I/O
- ポイント：汎用は Web 配信・CMS・ホームディレクトリなど、レイテンシーに敏感な用途に最適。最大 I/O は前の世代で、高いレイテンシーに耐えられる高度に並列な処理向け。最大 I/O は 1 ゾーンやエラスティックスループットでは使えない
- 例：ふつうは汎用を選ぶ

#### EFS レプリケーション（れぷりけーしょん / EFS replication）

- 意味：EFS のデータとメタデータを、別のファイルシステム（別のリージョンや AZ）に自動で同期し続ける機能
- ポイント：レプリケーション設定を作れば、同期は自動で保たれる。災害のときはコピー先のファイルシステムに切り替える
- 例：東京の EFS を大阪へレプリケートして DR に備える

## 14-3 Amazon FSx

### まとめ表

| サービス | 中身 | プロトコル | 選ぶ合図 |
| :-: | :-: | :-: | :-: |
| FSx for Windows File Server | Windows Server | SMB | Windows・Active Directory・NTFS |
| FSx for Lustre | Lustre | Lustre（POSIX） | HPC・機械学習・S3 と連携・最高速 |
| FSx for NetApp ONTAP | NetApp ONTAP | NFS・SMB・iSCSI・NVMe | マルチプロトコル・オンプレの NetApp から移行 |
| FSx for OpenZFS | OpenZFS | NFS | オンプレの ZFS・Linux のファイルサーバーから移行 |

### FSx のファイルシステム

#### Amazon FSx for Windows File Server（うぃんどうずふぁいるさーばー / Amazon FSx for Windows File Server）

- 意味：ネイティブの Windows ファイルシステムを持つ、フルマネージドの Microsoft Windows ファイルサーバー
- ポイント：SMB でアクセスし、Microsoft Active Directory と連携してユーザー認証とアクセス制御をする。Windows のアプリをコードを変えずに移せる。シングル AZ とマルチ AZ があり、本番はマルチ AZ が勧められる
- 例：社内の Windows のファイル共有（\\share）を AWS に移す

#### FSx for Windows File Server のマルチ AZ（まるちえーぜっと / Multi-AZ file systems）

- 意味：優先 AZ とスタンバイ AZ の 2 つにファイルサーバーとストレージを置き、障害やメンテナンスで自動でフェイルオーバーする配置
- ポイント：Windows Server フェイルオーバークラスタリング（WSFC）を使う。AZ 間でデータを複製するので耐久性も上がる。SQL Server の高可用性のデプロイには、マルチ AZ の継続的に使用可能な（CA）共有が要る
- 例：本番のファイル共有を、マルチ AZ で作る

#### Amazon FSx for Lustre（らすたー / Amazon FSx for Lustre）

- 意味：高性能な Lustre のファイルシステムを、フルマネージドで使うサービス。機械学習・HPC・動画処理・金融のモデリングなど、速さが重要な処理向け
- ポイント：POSIX に準拠し、Linux のアプリを変えずに使える。S3 のバケットにリンクすると、S3 のオブジェクトをファイルとして見せ、結果を S3 に書き戻せる。Windows のファイル共有には使わない
- 例：S3 にある学習データを FSx for Lustre で高速に読み、GPU のインスタンスで学習する

#### スクラッチと永続のファイルシステム（すくらっち / scratch and persistent file systems）

- 意味：FSx for Lustre のデプロイの種類。スクラッチ＝一時的で短期の処理向け、永続＝長期の保存向け
- ポイント：スクラッチはデータが複製されず、ファイルサーバーに障害が起きるとデータは残らない。永続はデータが複製され、障害のときはファイルサーバーが置き換えられる。「短期間の処理で、安く」ならスクラッチ
- 例：数時間のシミュレーションの作業領域にスクラッチを使い、結果は S3 に書き戻す

#### Amazon FSx for NetApp ONTAP（おんたっぷ / Amazon FSx for NetApp ONTAP）

- 意味：NetApp の ONTAP ファイルシステムの上に作られた、フルマネージドのファイルストレージ
- ポイント：NFS・SMB・iSCSI・NVMe でのマルチプロトコルのアクセスができ、Linux・Windows・macOS から使える。スナップショット・クローン・レプリケーション・安いストレージへの自動の階層化がある。オンプレミスで ONTAP を使っている会社が、やり方を変えずに移すのに向く
- 例：Linux と Windows の両方から同じデータを使い、さらに iSCSI のブロックストレージも欲しい

#### Amazon FSx for OpenZFS（おーぷんぜっとえふえす / Amazon FSx for OpenZFS）

- 意味：オープンソースの OpenZFS の上に作られた、フルマネージドのファイルストレージ
- ポイント：NFS（v3〜v4.2）で Linux・Windows・macOS から使える。オンプレミスの ZFS や Linux のファイルサーバーから、アプリやデータの管理方法を変えずに移すのに向く。日本語のドキュメントは無いので、英語版で確かめた
- 例：オンプレミスの ZFS のファイルサーバーを AWS に移す

## 問題演習

### 14-1 Amazon EBS

#### 問 aws-14-o01

- 問：EC2 のデータ用のボリュームに、容量は 200 GiB で十分だが 10,000 IOPS が必要。最もコストを抑えられる EBS のボリュームタイプはどれか。
- ア：gp3（IOPS を容量と別に追加でプロビジョニングする）
- イ：gp2（IOPS のために容量を増やす）
- ウ：st1
- エ：sc1
- 正解：ア
- 解説：gp3 は 3,000 IOPS のベースラインが料金に含まれ、追加料金で容量と別に IOPS をプロビジョニングできる。GiB あたりの料金も gp2 より 20% 低い。
- アの意味：正しい。
- イの意味：gp2 は GiB あたり 3 IOPS なので、10,000 IOPS には約 3,334 GiB が要り、使わない容量にも払うことになる。
- ウの意味：HDD で、IOPS ではなくスループットの性能を示すボリューム。
- エの意味：最も安い HDD で、高い IOPS は出ない。
- 出典：オリジナル問題（根拠：AWS「Amazon EBS 汎用 SSD ボリューム」（『gp3 ボリュームは、ストレージの料金に含まれている 3,000 IOPS の一貫したベースライン IOPS パフォーマンスを提供します。』『さらに、gp3 ボリュームでは、GiB あたりの料金が汎用 SSD (gp2) ボリュームよりも 20% 低くなります。』『ベースライン IOPS パフォーマンスは、最小 100 から最大 16,000 の間で、ボリュームサイズの GiB あたり 3 IOPS のレートで直線的にスケールします。』））

#### 問 aws-14-o02

#### 問 aws-14-o04

- 問：EBS について正しいものはどれか。

#### 問 aws-14-o07

- 問：EBS スナップショットについて正しいものはどれか。

### 14-2 Amazon EFS

#### 問 aws-14-o11

- 問：3 つの AZ にある Linux の Web サーバーの全台から、同じファイルを同時に読み書きしたい。容量の管理はしたくない。最も適したストレージはどれか。

#### 問 aws-14-o13

#### 問 aws-14-o14

#### 問 aws-14-o16

- 問：VPC の中の EC2 から EFS をマウントするために、VPC の中に作る必要があるものはどれか。
