## 07-1 Lambda のしくみと設定

### まとめ表

| 項目 | 値（2026-11 の Lambda クォータ） |
| :-: | :-: |
| メモリ | 128 MB〜10,240 MB（1 MB 単位）。CPU はメモリに比例 |
| タイムアウト | デフォルト 3 秒、最大 900 秒（15 分） |
| /tmp（エフェメラルストレージ） | 512 MB〜10,240 MB |
| 呼び出しのペイロード | 同期 6 MB／非同期 1 MB |
| デプロイパッケージ（.zip） | 50 MB（zip 圧縮）、解凍後 250 MB（レイヤーを含む） |
| コンテナイメージ | 10 GB（非圧縮、すべてのレイヤーを含む） |
| レイヤー | 1 関数に 5 つまで |

### 関数と実行環境

#### AWS Lambda（えーだぶりゅーえす らむだ / AWS Lambda）

- 意味：サーバーを用意・管理せずに、イベントや API コールに応じてコードを動かすサーバーレスのコンピューティングサービス
- ポイント：パッチ適用・容量の用意・スケーリングは AWS がやる。使った分（リクエスト数と実行時間）だけ払う。1 回の実行は最大 15 分なので、何時間も動かす処理には向かない（Fargate や EC2 を使う）
- 例：S3 に画像が置かれたらサムネイルを作る／API Gateway の後ろで注文を受け付ける

#### 実行環境（じっこうかんきょう / execution environment）

- 意味：Lambda 関数が動く、安全で隔離された環境。最初の呼び出しで作られ、Init（初期化）・Invoke（呼び出し）・Shutdown（終了）の段階をたどる
- ポイント：一度作られた実行環境は、次の呼び出しで使い回されることがある。だから SDK のクライアントや DB 接続はハンドラーの外で作っておくと速い。ただし必ず使い回されるとは限らないので、状態は外（DynamoDB・S3 など）に置く。Init フェーズは 10 秒まで
- 例：ハンドラーの外で `s3 = boto3.client("s3")` を作る（Claude が作った例）

#### コールドスタート（こーるどすたーと / cold start）

- 意味：新しい実行環境を作るとき、コードのダウンロードや環境の準備・初期化のぶんだけ応答が遅くなること
- ポイント：AWS によると通常は呼び出しの 1% 未満。減らす方法は、プロビジョニングされた同時実行（前もって温めておく、追加料金）と SnapStart（初期化済みのスナップショットから再開）
- 例：朝いちばんのアクセスだけ数百ミリ秒遅い

#### メモリ設定（めもりせってい / memory）

- 意味：関数に割り当てるメモリの量。128 MB〜10,240 MB を 1 MB 単位で決める
- ポイント：CPU の量を直接は指定できない。CPU はメモリに比例して割り当てられるので、CPU を多く使う処理が遅いならメモリを増やす。1,769 MB で 1 vCPU 相当
- 例：画像の変換が遅いので 512 MB → 2,048 MB にする

#### タイムアウト（たいむあうと / timeout）

- 意味：関数が 1 回に動いてよい最大の時間。デフォルト 3 秒、最大 900 秒（15 分）
- ポイント：15 分を超える処理は Lambda では動かせない。小さく分けて Step Functions でつなぐか、Fargate・EC2・AWS Batch に移す。API Gateway の後ろでは、API Gateway 側の統合のタイムアウト（29 秒）が先に来る
- 例：外部 API を呼ぶ関数を 3 秒 → 10 秒にする

#### エフェメラルストレージ（えふぇめらるすとれーじ / ephemeral storage, /tmp）

- 意味：関数の中で使える一時的なディスク（`/tmp`）。512 MB〜10,240 MB で設定でき、保管時は暗号化される
- ポイント：実行環境が消えれば中身も消える一時置き場。ほかの関数や同時に動く別の実行環境とは共有されない。複数の関数でファイルを共有したり、ずっと残したりするなら EFS をマウントするか S3 に置く
- 例：S3 から 2 GB のモデルを `/tmp` に落として推論する

#### Lambda レイヤー（らむだれいやー / Lambda layer）

- 意味：ライブラリ・カスタムランタイム・設定ファイルなどをまとめた .zip。関数のコードとは別に管理し、複数の関数で使い回す
- ポイント：1 関数に 5 つまで。解凍後 250 MB の上限は、関数のコードとレイヤーを合わせた大きさ。コンテナイメージで作った関数ではレイヤーを使わず、イメージに入れる
- 例：20 個の関数が使う共通ライブラリを 1 つのレイヤーにして、更新を 1 か所で済ませる

#### コンテナイメージの関数（こんてないめーじのかんすう / container image）

- 意味：.zip ではなく、コンテナイメージ（Amazon ECR に置く）として Lambda 関数をデプロイする方法
- ポイント：最大 10 GB（非圧縮、すべてのレイヤーを含む）。.zip の 250 MB に収まらない大きな依存関係（機械学習のライブラリなど）や、Lambda がベースイメージを用意していない言語のときに使う。動きは Lambda のまま（最大 15 分）
- 例：3 GB の推論用ライブラリを入れたイメージを ECR に置いて関数にする

### デプロイとつなぎ方

#### バージョン（ばーじょん / version）

- 意味：関数のコードと設定をその時点で固めて発行したもの。発行すると変更できない（イミュータブル）
- ポイント：まだ発行していない編集中のものが `$LATEST`。デプロイすると `$LATEST` が上書きされる。プロビジョニングされた同時実行は `$LATEST` には付けられず、バージョンかエイリアスに付ける
- 例：`my-func:3`（バージョン 3）

#### エイリアス（えいりあす / alias）

- 意味：特定のバージョンを指す、付け替えられる名前（ポインタ）
- ポイント：呼び出し側はエイリアスの ARN を使えば、新しいバージョンに切り替えても設定を変えなくてよい。2 つのバージョンにトラフィックを分けられるので、新版に少しだけ流して試せる（カナリア）
- 例：`prod` エイリアスを、バージョン 3 に 90%・バージョン 4 に 10% で向ける

#### 関数 URL（かんすうゆーあーるえる / function URL）

- 意味：Lambda 関数専用の HTTPS のエンドポイント。作ると一意の URL が自動で作られ、あとから変わらない
- ポイント：API Gateway を置かずに 1 つの関数をそのまま HTTP で呼べる。認証は IAM（AWS_IAM）か、なし（NONE）。API キー・使用量プラン・キャッシュ・リクエストの検証などがほしいなら API Gateway
- 例：Webhook を受けるだけの小さな関数

#### Lambda の VPC 接続（ぶいぴーしーせつぞく / VPC access）

- 意味：関数をプライベートサブネットに接続し、VPC の中の RDS などにアクセスさせる設定。Lambda は Hyperplane ENI というネットワークインターフェイスを作る
- ポイント：パブリックサブネットに接続しても、インターネットにもパブリック IP にもつながらない。VPC に入れた関数がインターネット（外部 API）にも出るには、プライベートサブネットから NAT ゲートウェイへのルートが要る。AWS のサービスだけなら VPC エンドポイントでもよい
- 例：プライベートサブネット 2 つ（別の AZ）に関数をつなぎ、各 AZ に NAT ゲートウェイを置く

## 07-2 呼び出しとスケーリング

### まとめ表

| 呼び出し方 | だれが結果を待つか | エラーのとき | 代表的な呼び出し元 |
| :-: | :-: | :-: | :-: |
| 同期 | 呼び出し元が待つ | Lambda は再試行しない（呼び出し元しだい） | API Gateway・関数 URL・ALB |
| 非同期 | 待たない（Lambda がキューに入れる） | 関数エラーはさらに 2 回再試行。送信先・DLQ に送れる | S3・SNS・EventBridge |
| イベントソースマッピング | Lambda のポーラーが取りに行く | キューの再試行設定（可視性タイムアウト・DLQ）やストリームのバッチ単位 | SQS・Kinesis・DynamoDB Streams・MSK |

### 呼び出し方

#### 同期呼び出し（どうきよびだし / synchronous invocation）

- 意味：Lambda が関数を実行し、終わるまで待ってレスポンスを返す呼び出し方
- ポイント：エラーのとき Lambda 自身は再試行しない。再試行するかどうかは呼び出し元（クライアントやサービス）が決める。ペイロードは 6 MB まで
- 例：API Gateway が関数を呼び、結果をそのまま利用者に返す

#### 非同期呼び出し（ひどうきよびだし / asynchronous invocation）

- 意味：Lambda がイベントをいったん内部のキューに入れてすぐ成功を返し、あとで関数を実行する呼び出し方
- ポイント：関数がエラーを返すと、デフォルトでさらに 2 回再試行する（1 回目と 2 回目の間は 1 分、2 回目と 3 回目の間は 2 分）。スロットリングなどはイベントをキューに戻し、最大 6 時間試す。同じイベントが 2 回届くこともあるので関数はべき等に。ペイロードは 1 MB まで
- 例：S3 にファイルが置かれたことを S3 が非同期で関数に伝える

#### 送信先（そうしんさき / destinations）

- 意味：非同期呼び出しの結果（成功・失敗）の記録を、別のサービスに送る設定
- ポイント：成功時と失敗時で別々に設定できる。送り先は標準 SQS キュー・標準 SNS トピック・Lambda 関数・EventBridge イベントバス・S3 バケット（失敗時のみ）。FIFO は不可。デッドレターキュー（DLQ）はイベントの中身だけを送るが、送信先はレスポンスの詳細も含めた記録を送る
- 例：失敗したイベントを、エラー内容つきで SQS に送って調べる

#### イベントソースマッピング（いべんとそーすまっぴんぐ / event source mapping）

- 意味：ストリームやキューから Lambda が自分でレコードを読み取り、バッチにまとめて関数を呼ぶしくみ
- ポイント：SQS は Lambda を「押して」呼ばない。Lambda 側のイベントポーラーがキューをポーリングする。対象は SQS・Kinesis・DynamoDB Streams・Amazon MQ・MSK・セルフマネージド Kafka・DocumentDB。バッチサイズとバッチウィンドウで、まとめる量と待ち時間を調整する
- 例：注文キュー（SQS）から 10 件ずつ取り出して処理する

### 同時実行

#### 同時実行（どうじじっこう / concurrency）

- 意味：関数が同時に処理している、まだ終わっていないリクエストの数。必要な実行環境の数と同じ
- ポイント：同時実行数＝1 秒あたりのリクエスト数 × 1 回の平均の実行時間（秒）。デフォルトではリージョン内の全関数で合わせて 1,000（引き上げを申請できる）。足りないとスロットリングされる。1 つの関数は 10 秒ごとに最大 1,000 の実行環境ずつ増やせる
- 例：毎秒 200 リクエスト × 0.5 秒＝同時実行 100（Claude が作った例）

#### 予約済み同時実行（よやくずみどうじじっこう / reserved concurrency）

- 意味：ある関数のために同時実行数を取っておく設定。その数が関数の上限にもなる
- ポイント：下限（ほかの関数に取られない）と上限（それ以上は増えない）の両方の役。重要な関数を守るときと、DB など後ろの資源に同時接続をかけすぎないよう絞るときに使う。追加料金なし。0 にすると関数が止まる
- 例：決済の関数に 100 を予約／古い DB を使う関数を 50 に絞る

#### プロビジョニングされた同時実行（ぷろびじょにんぐされたどうじじっこう / provisioned concurrency）

- 意味：前もって初期化しておく実行環境の数。コールドスタートを避け、数十ミリ秒で応答できるようにする
- ポイント：追加料金がかかる。バージョンかエイリアスに設定する（`$LATEST` は不可）。Application Auto Scaling で時間帯に合わせて増減できる。同時実行の上限を決める設定ではない（それは予約済み同時実行）
- 例：始業時の 8:30〜9:30 だけ 200 に増やす

#### Lambda SnapStart（すなっぷすたーと / Lambda SnapStart）

- 意味：初期化済みの実行環境のメモリとディスクの状態をスナップショットにしておき、新しい実行環境をそこから再開して起動を速くする機能
- ポイント：前もって実行環境を用意（プロビジョニング）しなくても起動が速くなる。対応は Java 11 以降・Python 3.12 以降・.NET 8 以降などのマネージドランタイム。もっと厳しい応答時間が要るならプロビジョニングされた同時実行。Java のマネージドランタイムなら追加コストなし（ほかはスナップショットのキャッシュなどの料金がかかる）。スナップショットから複数の環境が作られるので、乱数や一意な値の作り方に注意
- 例：Spring Boot の Java 関数の起動を速くする

## 07-3 API Gateway

### まとめ表

| 項目 | REST API | HTTP API | WebSocket API |
| :-: | :-: | :-: | :-: |
| 向いているもの | 機能が多い（API キー・使用量プラン・キャッシュ・WAF・リクエストの検証） | 低価格・最小限の機能（JWT 認可・自動デプロイ） | 双方向・ステートフル（チャット・通知） |
| エンドポイント | エッジ最適化・リージョン・プライベート | リージョンのみ | — |
| 統合のタイムアウト | 50 ミリ秒〜29 秒（リージョン・プライベートは引き上げを申請できる） | 最大 30 秒 | — |

### API の種類

#### Amazon API Gateway（えーぴーあい げーとうぇい / Amazon API Gateway）

- 意味：REST・HTTP・WebSocket の API を作り、公開・保守・監視・保護するためのマネージドサービス
- ポイント：Lambda や HTTP のバックエンド、AWS のサービスの前に置く「玄関」。認可・スロットリング・キャッシュをまとめて引き受ける。アカウントごと・リージョンごとに 10,000 リクエスト/秒（バースト 5,000）のスロットリングがかかる
- 語の意味：API＝Application Programming Interface（プログラムどうしの窓口）、Gateway＝出入口

#### REST API（れすとえーぴーあい / REST API）

- 意味：API Gateway の、機能の多い RESTful な API
- ポイント：API キーと使用量プラン（クライアントごとのレート制限）・キャッシュ・AWS WAF・リクエストの検証・Canary リリース・プライベートエンドポイント・エッジ最適化は REST API だけ。これらが要件に出たら REST API
- 例：外部の取引先ごとに API キーを配り、1 日の上限回数を決める

#### HTTP API（えいちてぃーてぃーぴーえーぴーあい / HTTP API）

- 意味：API Gateway の、最小限の機能で低価格にした RESTful な API
- ポイント：JWT のオーソライザー（Cognito や OIDC のトークン）を標準で使え、自動デプロイもある。API キー・キャッシュ・WAF・エッジ最適化・プライベートはない。「シンプルで安く、Lambda や HTTP の後ろにつなぎたい」なら HTTP API
- 例：スマホアプリの裏側の、Lambda を呼ぶだけの API

#### WebSocket API（うぇぶそけっとえーぴーあい / WebSocket API）

- 意味：クライアントとサーバーが接続をつないだまま、双方向にメッセージを送り合える（ステートフルな全二重通信）API
- ポイント：REST・HTTP API はリクエストに応答するだけ（ステートレス）。サーバー側から端末へすぐ知らせたい（チャット・リアルタイムの通知・対戦ゲーム）なら WebSocket API
- 例：チャットアプリで、だれかの発言を参加者全員にすぐ届ける

#### エンドポイントタイプ（えんどぽいんとたいぷ / endpoint type）

- 意味：REST API の公開のしかた。エッジ最適化・リージョン・プライベートの 3 つ
- ポイント：エッジ最適化＝最寄りの CloudFront の POP 経由（世界中のクライアント向け）。リージョン＝同じリージョンのクライアント向け（自分で CloudFront を前に置くときもこれ）。プライベート＝インターフェイス VPC エンドポイント経由で、VPC の中からだけ呼べる
- 例：社内システムだけが使う API はプライベート

### 守る・速くする

#### API キャッシュ（えーぴーあいきゃっしゅ / API caching）

- 意味：REST API のステージで、バックエンドからのレスポンスを一定時間（TTL）ためておき、同じリクエストにはキャッシュから返す機能
- ポイント：TTL はデフォルト 300 秒、最大 3,600 秒、0 で無効。有効にするとデフォルトでは GET メソッドだけがキャッシュされる。バックエンド（Lambda・DB）の負荷と応答時間を下げる。HTTP API にはない
- 例：商品一覧の GET を 5 分キャッシュする

#### スロットリング（API Gateway）（すろっとりんぐ / throttling）

- 意味：API へのリクエストの数を、トークンバケットのしくみで制限すること。超えると `429 Too Many Requests` を返す
- ポイント：アカウント単位（リージョンごと 10,000 リクエスト/秒・バースト 5,000）・ステージやメソッド単位・使用量プランのクライアント単位の段階がある。バックエンドを急な負荷から守る
- 例：書き込みのメソッドだけ 100 リクエスト/秒に抑える

#### 使用量プランと API キー（しようりょうぷらんとえーぴーあいきー / usage plan and API key）

- 意味：API キーで呼び出し元のクライアントを見分け、使用量プランでそのクライアントのレート制限とクォータ（1 日・1 か月の上限回数）を決めるしくみ（REST API）
- ポイント：API キーは「だれが使っているか」の識別用。AWS は、API キーを認証・認可に使わないよう勧めている（それは IAM・Cognito・Lambda オーソライザー）。使用量プランもコストの上限を守る手段にはしない
- 例：無料プランは 1 日 1,000 回、有料プランは 1 日 100,000 回

#### Lambda オーソライザー（らむだおーそらいざー / Lambda authorizer）

- 意味：Lambda 関数でアクセスの可否を判断するしくみ。発信者の ID（トークンやリクエストパラメータ）を受け取り、IAM ポリシーを返す
- ポイント：トークンベース（TOKEN、OAuth などのベアラートークン）とリクエストパラメータベース（REQUEST、ヘッダー・クエリなど）がある。独自の認証基盤やヘッダーで判断したいときに使う。結果をキャッシュすると毎回は呼ばれない。以前の名前はカスタムオーソライザー
- 例：自社の認証サーバーが発行したトークンを検証する

#### Cognito オーソライザー（こぐにーとおーそらいざー / Amazon Cognito user pool authorizer）

- 意味：Amazon Cognito のユーザープールでサインインしたユーザーのトークンを、API Gateway がそのまま検証して通すしくみ（`COGNITO_USER_POOLS` タイプ）
- ポイント：自分で認可の関数を書かなくてよい。クライアントは ID トークンかアクセストークンを Authorization ヘッダーに付けて呼ぶ。ユーザーの管理が Cognito なら Cognito オーソライザー、独自の基盤なら Lambda オーソライザー、AWS の認証情報（署名）なら IAM 認可
- 例：アプリのログイン（Cognito）と API の保護を一続きにする

#### 統合のタイムアウト（とうごうのたいむあうと / integration timeout）

- 意味：API Gateway がバックエンド（Lambda・HTTP など）の応答を待つ時間の上限。REST API は 50 ミリ秒〜29 秒、HTTP API は最大 30 秒
- ポイント：Lambda は 15 分まで動けても、API Gateway の後ろでは 29 秒で打ち切られる。長い処理は「受け付けだけ返して、処理は非同期（SQS・Step Functions など）で行い、結果はあとで取りに来てもらう」形にする。リージョン・プライベートの REST API は引き上げを申請できる
- 例：レポート作成を受け付けたらジョブ ID を返し、完了は別の API で確かめる

## 07-4 Step Functions と Fargate

### まとめ表

| 項目 | 標準ワークフロー | Express ワークフロー |
| :-: | :-: | :-: |
| 最大の実行時間 | 1 年 | 5 分 |
| 実行のされ方 | Exactly-once（ちょうど 1 回） | 非同期は At-least-once、同期は At-most-once |
| 料金 | 状態遷移の回数 | 実行の回数・時間・メモリ |
| 向いているもの | 長い・監査が要る業務（承認待ち・注文処理） | 大量で短いイベント処理（IoT・ストリーミング） |
| .sync・.waitForTaskToken | 使える | 使えない |

### ワークフロー

#### AWS Step Functions（すてっぷふぁんくしょんず / AWS Step Functions）

- 意味：複数の処理（Lambda・AWS のサービス）をつなぐワークフローを、ステートマシンとして組み立てて動かすサービス
- ポイント：順番・分岐・並列・待ち・再試行・失敗時の処理を、コードではなく定義で書ける。Lambda から次の Lambda を直接呼ぶ（結合が強い・失敗の扱いが難しい）代わりに使う。実行の様子をコンソールで図として見られる
- 例：在庫の確保 → 決済 → 発送の指示、失敗したら返金

#### ステートマシン（すてーとましん / state machine）

- 意味：Step Functions でのワークフローのこと。各ステップを「状態（ステート）」と呼び、Amazon States Language（ASL、JSON）で定義する
- ポイント：主な状態は Task（仕事をする）・Choice（分岐）・Parallel（決まった枝を並列に）・Map（配列の各要素に同じ処理）・Wait（指定の時間待つ）・Succeed・Fail。ワークフローを動かした 1 回分を「実行」と呼ぶ
- 語の意味：state＝状態、machine＝機械

#### 標準ワークフロー（ひょうじゅんわーくふろー / Standard workflow）

- 意味：最長 1 年動ける、耐久性が高く監査しやすいワークフローのタイプ
- ポイント：各ステップがちょうど 1 回実行される（Exactly-once）。料金は状態遷移の回数。人の承認待ちのように長く止まるもの、二重に実行されては困るもの（決済）に向く
- 例：経費の申請 → 上司の承認待ち（数日）→ 支払い

#### Express ワークフロー（えくすぷれすわーくふろー / Express workflow）

- 意味：最長 5 分の、大量のイベント処理向けのワークフローのタイプ
- ポイント：非同期は At-least-once（2 回以上実行されることがある）、同期は At-most-once。料金は実行の回数・時間・メモリ。.sync やタスクトークンのコールバック、分散 Map は使えない。IoT のデータの取り込みやストリーミングの変換など、短くて回数が多い処理に向く
- 例：IoT 機器からの毎秒数万件のデータを整形して保存する

#### Retry と Catch（りとらいときゃっち / Retry and Catch）

- 意味：Task・Parallel・Map の状態に書く、エラー処理の設定。Retry はやり直し、Catch はやり直してもだめなときに別の状態へ進める
- ポイント：両方あるときは Retry が先。Retry では IntervalSeconds（待ち時間）・MaxAttempts（回数）・BackoffRate（待ち時間の倍率）を決める。Catch でフォールバック（取り消し・通知）の状態へ移す
- 例：決済 API の一時的なエラーは 3 回までやり直し、だめなら「注文を取り消す」状態へ

#### Map 状態（まっぷじょうたい / Map state）

- 意味：配列や S3 のオブジェクトの一覧の各要素に、同じ処理を並列で実行する状態
- ポイント：インラインモード（デフォルト）は同時に 40 まで、実行履歴は親に入る。分散モードは各要素を子ワークフローとして最大 10,000 並列で動かし、S3 の大量のファイルや CSV の処理に向く。決まった数の違う処理を並べるのは Parallel 状態
- 例：S3 にある 100 万個のログファイルを分散 Map で並列に集計する

#### サービス統合パターン（さーびすとうごうぱたーん / service integration patterns）

- 意味：Step Functions がほかのサービスを呼ぶときの待ち方。リクエストレスポンス・ジョブの実行（.sync）・タスクトークンのコールバックまで待機（.waitForTaskToken）の 3 つ
- ポイント：リクエストレスポンス＝呼んだら応答を受けてすぐ次へ。.sync＝ジョブ（AWS Batch・ECS のタスクなど）が終わるまで待つ。.waitForTaskToken＝タスクトークンを渡して、だれかがトークンを返してくるまで待つ（人の承認・外部システム）。どちらも標準ワークフローだけ
- 例：承認者にトークン入りのリンクをメールし、押されたら SendTaskSuccess で再開する

### コンテナのサーバーレス

#### AWS Fargate（ふぁーげーと / AWS Fargate）

- 意味：EC2 インスタンスのクラスターを管理せずに、Amazon ECS（や EKS）のコンテナを動かすサーバーレスのしくみ
- ポイント：CPU とメモリを指定するだけで、サーバーの種類選び・スケール・パッチは不要。各タスクはカーネル・CPU・メモリ・ENI を他のタスクと共有しない。Lambda の 15 分を超える処理や、常に動き続けるコンテナのサービスに向く。Lambda との違いは「関数かコンテナか」と「実行時間の上限」
- 例：30 分かかる動画の変換コンテナを、ECS のタスクとして Fargate で動かす

#### Fargate Spot（ふぁーげーとすぽっと / Fargate Spot）

- 意味：AWS の予備のキャパシティを使い、Fargate より割引された料金でタスクを動かす選択肢
- ポイント：AWS がキャパシティを取り戻すときは、2 分前の警告のあとにタスクが中断される。途中で止まってもやり直せる処理（バッチ・テスト）向き。需要が多いと起動できないこともある
- 例：夜間のテストを Fargate Spot で安く回す

#### ステートレス（すてーとれす / stateless）

- 意味：処理が前回のリクエストの記憶（セッション・一時ファイル）に頼らず、どのサーバー・どの実行環境が受けても同じ結果になる作り
- ポイント：ステートレスにすると、台数を自由に増減（水平スケーリング）でき、1 台が落ちても困らない。状態は DynamoDB・ElastiCache・S3 などの外に置く。Lambda や Fargate は、実行環境が使い回される保証がないのでステートレスに作る。セッションを 1 台に持たせるのがステートフル
- 例：ログインのセッションを DynamoDB に置き、どのタスクでも続きを処理できるようにする
