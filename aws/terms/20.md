## 20-1 ストリーミングデータの取り込み

### まとめ表

| サービス | 何をするか | 選ぶ決め手 |
| :-: | :-: | :-: |
| Kinesis Data Streams | シャードにデータをためて、複数のアプリがリアルタイムに読む | 自分で処理アプリを作る・読み直し・複数のコンシューマー |
| Data Firehose | 届いたデータをバッファして宛先に自動で配信 | アプリを書かずに S3・Redshift・OpenSearch へ |
| Managed Service for Apache Flink | ストリームを SQL・Java などで処理・分析 | 時系列分析・リアルタイムのダッシュボード |
| Amazon MSK | Apache Kafka をフルマネージドで動かす | すでに Kafka を使っている |

数字や条件は AWS「Amazon Kinesis Data Streams の用語と概念」「Amazon Data Firehose とは何ですか?」による

### Kinesis Data Streams

#### Amazon Kinesis Data Streams（きねしすでーたすとりーむず / Amazon Kinesis Data Streams）

- 意味：データレコードの大量のストリームをリアルタイムで集めて処理するサービス
- ポイント：プロデューサーがデータを入れ、コンシューマー（Kinesis Data Streams アプリケーション）がリアルタイムで処理する。入れてから読めるまでの遅延は通常 1 秒未満。複数のアプリが同じストリームを独立して読める（アーカイブと処理を同時に、など）。コンシューマーには KCL・Lambda・Firehose・Flink などを使える。KMS キーで保管中のデータを暗号化できる
- 例：ウェブのクリックストリームを取り込み、集計するアプリと保存するアプリが同時に読む

#### シャード（しゃーど / Shard）

- 意味：ストリームの中の一意に識別されたデータレコードの並びで、ストリームの容量の 1 単位
- ポイント：1 シャードは、書き込みが毎秒 1,000 レコード・1 MB まで、読み取りが毎秒 5 トランザクション・2 MB まで。ストリームの容量はシャードの合計。プロビジョンドモードでは、シャードの数を増減（リシャーディング）して容量を変える
- 例：毎秒 3 MB を書き込むので、プロビジョンドモードで 3 シャード以上にする

#### パーティションキー（ぱーてぃしょんきー / Partition key）

- 意味：ストリームのデータをシャードごとにまとめるために、レコードごとに指定する値
- ポイント：パーティションキーでレコードの行き先のシャードが決まる。同じキーのレコードは同じシャードに入り、シャードの中ではシーケンス番号で順番が付く。偏ったキー（1 つの値にデータが集中する）を使うと、1 つのシャードの制限を超えて読み書きの例外が起こる
- 例：ユーザー ID をパーティションキーにして、ユーザーごとの順番を保つ

#### 容量モード（ようりょうもーど / Capacity mode: on-demand, provisioned）

- 意味：ストリームの容量の管理のしかたと課金のしかたを決めるモード
- ポイント：オンデマンドモードは、容量計画がいらず、シャードを自動で管理し、使ったスループットに課金。予測できない、変動の大きいトラフィックに向く。プロビジョンドモードは、シャードの数を自分で決め、シャードの時間料金がかかる
- 例：キャンペーンのときだけアクセスが急に増えるので、オンデマンドモードにする

#### 保持期間（ほじきかん / Retention period）

- 意味：レコードをストリームに入れたあと、読み取れる期間
- ポイント：既定は 24 時間で、最大 8,760 時間（365 日）まで延ばせる。24 時間を超えると追加料金がかかる。保持期間の中なら、同じデータを読み直せる
- 例：処理のバグを直したあと 3 日前のデータを読み直せるように、保持期間を 7 日にする

#### 拡張ファンアウト（かくちょうふぁんあうと / Enhanced fan-out）

- 意味：コンシューマーごとに、シャードあたり毎秒 2 MB の専用の読み取りスループットを割り当てる機能
- ポイント：使わない場合（共有スループット）は、同じシャードを読むすべてのコンシューマーで毎秒 2 MB を分け合い、遅延はコンシューマーが 5 つなら平均約 1,000 ミリ秒まで上がる。拡張ファンアウトなら平均 70 ミリ秒で、HTTP/2 でプッシュされる。データ取得とコンシューマー・シャード時間の料金がかかる
- 例：同じストリームを 5 つのアプリが読むので、それぞれを拡張ファンアウトのコンシューマーにする

### 配信と処理

#### Amazon Data Firehose（でーたふぁいあほーす / Amazon Data Firehose）

- 意味：ストリーミングデータを、S3・Redshift・OpenSearch Service・Splunk・HTTP エンドポイントなどの宛先にリアルタイムで配信するフルマネージドサービス
- ポイント：アプリを書いたり、リソースを管理したりしなくてよい。データを送れば宛先に自動で配信される。既存の Kinesis データストリームを読んで配信することもできる。Redshift へは、いったん S3 に置いてから COPY コマンドで読み込む。配信は最低 1 回（重複することがある）
- 例：アプリのログを Firehose に送り、S3 のデータレイクにためる
- 語の意味：Firehose＝消防用の太いホース。大量のデータを宛先に流し込むイメージ

#### バッファリングサイズとバッファリング間隔（ばっふぁりんぐ / Buffer size, Buffer interval）

- 意味：Firehose が、届いたデータをためてから宛先に送るときの大きさ（MB）と時間（秒）
- ポイント：一定の期間、一定の大きさまでためてから配信する。宛先ごとに配信の頻度が違う
- 例：S3 に小さなファイルが大量にできないよう、バッファを大きめにする

#### データ形式の変換と Lambda によるデータ変換（でーたけいしきのへんかん / Record format conversion, Data transformation）

- 意味：Firehose が S3 に保存する前に、JSON を Apache Parquet か Apache ORC に変換する機能と、Lambda 関数を呼んで届いたデータを変換する機能
- ポイント：Parquet と ORC は列指向の形式で、容量が減り、行指向の JSON よりクエリが速くなる。CSV など JSON 以外の形式は、先に Lambda で JSON に変換する。Lambda の呼び出しは最大 5 分
- 例：ログを Parquet に変換して S3 に置き、Athena のクエリを安く速くする

#### 動的パーティショニング（どうてきぱーてぃしょにんぐ / Dynamic partitioning）

- 意味：Firehose が、データの中のキー（customer_id など）でデータをまとめ、キーごとに別の S3 プレフィックスに配信する機能
- ポイント：パーティションに分けておくと、分析のクエリがスキャンするデータの量が減り、性能が上がり、コストが下がる
- 例：顧客 ID ごとのフォルダにログを分けて置く

#### Amazon Managed Service for Apache Flink（まねーじどさーびすふぉーあぱっちふりんく / Amazon Managed Service for Apache Flink）

- 意味：Java・Scala・Python・SQL で、ストリーミングデータを処理・分析できるサービス
- ポイント：オープンソースの Apache Flink を使う。時系列分析、リアルタイムのダッシュボードやメトリクスに向く。コンピューティングの用意、AZ の障害への耐性、自動スケーリング、チェックポイントなどを AWS が用意する。対話的な探索には Studio ノートブックを使う
- 例：Kinesis Data Streams のデータを 1 分ごとに集計し、異常を見つける

#### Amazon MSK（えむえすけー / Amazon Managed Streaming for Apache Kafka）

- 意味：Apache Kafka を使ってストリーミングデータを処理するアプリを、作って動かせるフルマネージドサービス
- ポイント：クラスターの作成・更新・削除などを AWS が行い、データの読み書きは Apache Kafka のふつうの操作で行う。ブローカーノードは AZ ごとに作る。容量を管理しなくてよい MSK Serverless もある。いま Kafka を使っているアプリをそのまま移すときに選ぶ
- 例：オンプレミスの Kafka クラスターを、コードを変えずに AWS へ移す
- 語の意味：MSK＝Managed Streaming for Kafka

## 20-2 データの変換とカタログ・データレイク

### まとめ表

| やりたいこと | 使うもの |
| :-: | :-: |
| S3 のデータのスキーマを自動で調べて登録 | Glue クローラー → Glue Data Catalog |
| サーバーを持たずに ETL（Spark） | Glue ETL ジョブ（Glue Studio で視覚的に作れる） |
| 前回の続きから処理 | Glue のジョブのブックマーク |
| コードを書かずにデータをきれいにする | Glue DataBrew |
| データレイクの列・行・セル単位の権限 | Lake Formation |
| Spark・Hadoop を自由に大規模に動かす | Amazon EMR |

数字や条件は AWS「AWS Glue とは」「とは AWS Lake Formation」による

### AWS Glue

#### AWS Glue（ぐるー / AWS Glue）

- 意味：複数のソースのデータを見つけて、準備し、移し、まとめられるサーバーレスのデータ統合サービス
- ポイント：70 を超えるデータソースに接続し、一元化されたデータカタログで管理する。ETL パイプラインを視覚的に作って動かせる。サーバーレスなので、管理するインフラがない
- 例：毎晩、RDS と S3 のデータをまとめてデータレイクに入れる
- 語の意味：Glue＝のり。ばらばらのデータをつなぐもの

#### AWS Glue Data Catalog（でーたかたろぐ / AWS Glue Data Catalog）

- 意味：データの場所・スキーマなどのメタデータを保存する、一元化されたリポジトリ
- ポイント：アカウントのリージョンごとに 1 つある。Apache Hive メタストアの代わりに使える。Athena・Redshift Spectrum・EMR・Lake Formation が同じメタデータを使う。IAM ポリシーや Lake Formation でテーブルへのアクセスを制御する
- 例：S3 のログを「access_logs」テーブルとして登録し、Athena からクエリする

#### クローラー（くろーらー / AWS Glue crawler）

- 意味：データソースを自動でスキャンし、スキーマを推測して、メタデータを Data Catalog に保存するもの
- ポイント：新しいデータや更新されたデータを自動で見つけてカタログに入れるので、手作業のメタデータ管理が減る。スケジュールで動かせる。テーブルを手で定義することもできる
- 例：S3 に毎日増えるフォルダを、夜にクローラーでスキャンしてパーティションを登録する

#### ETL ジョブ（いーてぃーえるじょぶ / AWS Glue ETL job）

- 意味：Glue の Apache Spark ベースのサーバーレスな ETL エンジンで、データを抽出・変換・ロードする処理
- ポイント：Data Catalog のメタデータから、Scala か PySpark のスクリプトを自動で作れる。Glue Studio のビジュアルエディタで作れる。トリガーやスケジュールで動かせる。ストリーミング ETL もある
- 例：CSV を Parquet に変換して、日付ごとのフォルダに書き出す
- 語の意味：ETL＝Extract（抽出）、Transform（変換）、Load（ロード）

#### ジョブのブックマーク（じょぶのぶっくまーく / Job bookmarks）

- 意味：前回の実行で処理したところを状態として持ち、古いデータを処理し直さないようにする Glue の機能
- ポイント：決まった間隔でジョブを動かすとき、新しいデータだけを処理できる
- 例：1 時間ごとのジョブで、前の 1 時間に増えたファイルだけを変換する

#### AWS Glue DataBrew（でーたぶるー / AWS Glue DataBrew）

- 意味：コードを書かずに、データをきれいにして正規化できるビジュアルなデータ準備ツール
- ポイント：ビジネスアナリストやデータサイエンティストが、生のデータを対話的に見て、見える化し、きれいにし、変換できる。データの品質の問題を見つけやすくする。サーバーレス
- 例：アナリストが、表の欠けた値や表記ゆれを画面の操作だけで直す

### データレイクと大規模処理

#### AWS Lake Formation（れいくふぉーめーしょん / AWS Lake Formation）

- 意味：分析と機械学習のために、データを一元管理・保護・共有できるサービス
- ポイント：S3 のデータレイクと Data Catalog のメタデータに、きめ細かなアクセス制御をかける。RDBMS のような許可と取り消しのしくみで、データベース・テーブル・列・行・セルの単位で権限を決める。Athena・Redshift Spectrum・EMR・Glue・Quick Sight で同じ権限が効く。LF タグ（タグベースのアクセス制御）で多くの権限をまとめて管理できる。ほかのアカウントとも共有できる
- 例：分析チームには個人情報の列を見せず、ほかの列だけ見せる

#### Amazon EMR（いーえむあーる / Amazon EMR）

- 意味：Apache Hadoop や Apache Spark などのビッグデータのフレームワークを動かす、マネージドなクラスターのプラットフォーム
- ポイント：SQL だけでなく、機械学習・グラフ分析・データ変換・ストリーミングなど、コードで書けるほぼすべての大規模処理に使える。カスタムのコードやアプリを動かせる柔軟さがある。EMRFS を使うと S3 をデータの層にして、コンピューティングとストレージを分けられる
- 例：独自の Spark のプログラムで、何十 TB ものログから特徴量を作る
- 語の意味：EMR＝Elastic MapReduce（以前の名前）

#### EMR のノードタイプ（のーどたいぷ / Primary node, Core node, Task node）

- 意味：EMR のクラスターを作る 3 種類のノード
- ポイント：プライマリノードはクラスターを管理する（終了するとクラスターも終了）。コアノードは HDFS にデータを持ち、タスクも動かす（止めるとデータを失うおそれ）。タスクノードは計算だけを足し、HDFS にデータを持たない。スポットインスタンスはタスクノードによく使う
- 例：プライマリとコアはオンデマンド、タスクノードはスポットにして安くする

#### 一時的なクラスター（いちじてきなくらすたー / Transient cluster）

- 意味：すべてのステップが終わったら自動で終了するように設定した EMR クラスター
- ポイント：データを S3（EMRFS）に置けば、クラスターを消してもデータは残る。処理のときだけクラスターを動かして、コストを抑える。終わったあとも使い続けるクラスターは、自分で終了するまで動く
- 例：毎晩の集計のたびにクラスターを起動し、終わったら自動で消す

## 20-3 クエリと可視化

### まとめ表

| サービス | 何をするか | 選ぶ決め手 |
| :-: | :-: | :-: |
| Athena | S3 のデータに直接 SQL | サーバーレス・アドホック・クエリの分だけ課金 |
| Redshift | データウェアハウス | 多くのソースを集めて長く持ち、高度なレポート |
| Redshift Spectrum | Redshift から S3 のデータをクエリ | ロードせずに S3 も一緒に |
| Quick Sight | ダッシュボードと BI | 見える化・SPICE |
| OpenSearch Service | 検索と分析のエンジン | ログ分析・アプリの監視・全文検索 |

数字や条件は AWS「Athena の用途」「Amazon Redshift とは」による

### Athena

#### Amazon Athena（あてな / Amazon Athena）

- 意味：標準的な SQL で、S3 の中のデータを直接分析できるインタラクティブなクエリサービス
- ポイント：サーバーレスで、インフラの用意や管理がいらず、実行したクエリにだけ課金される。CSV・JSON・Parquet・ORC などに対応。Glue Data Catalog をメタデータに使う。Apache Spark も動かせる。Quick Sight と統合できる
- 例：S3 にたまった CloudFront のログを、その場で SQL で調べる

#### パーティション（ぱーてぃしょん / Partitioning）

- 意味：データを日付や国などのキーで分けて、フォルダ（year=2026/month=11/ など）に置くこと
- ポイント：クエリの WHERE 句でパーティションを指定すると、そのパーティションのデータだけをスキャンするので、速くなりコストも下がる。クエリの単位より細かく分けすぎない。パーティションが多いときはパーティション射影で管理を簡単にし、速くできる
- 例：日ごとのクエリが多いので、日付でパーティションを分ける

#### 列指向の形式（れつしこうのけいしき / Columnar formats: Apache Parquet, ORC）

- 意味：データを列ごとにまとめて保存する、Apache Parquet や ORC などの形式
- ポイント：述語プッシュダウンで必要なブロックだけを読み、データの分割で読み取りを並列にできる。行指向の CSV・JSON より速く、スキャン量も減る。小さなファイルが大量にあると性能が落ちる
- 例：CSV のログを Parquet に変換し、Athena のスキャン量を減らす

#### CTAS（しーたす / CREATE TABLE AS SELECT）

- 意味：別のクエリの SELECT の結果から、Athena で新しいテーブルを作るクエリ
- ポイント：結果のデータファイルを S3 に作る。結果を Parquet や ORC に変換すると、クエリが速く安くなる。生のデータに何度もクエリしなくてよくなる。必要なデータだけのコピーも作れる
- 例：CSV のテーブルから、Parquet の新しいテーブルを 1 回で作る

#### フェデレーティッドクエリ（ふぇでれーてぃっどくえり / Athena federated query）

- 意味：S3 以外のリレーショナル・非リレーショナル・オブジェクト・カスタムのデータソースにあるデータに、Athena から SQL でクエリする機能
- ポイント：データソースコネクタ（多くは Lambda 関数）を使い、データを移さずにその場でクエリする。複数のデータソースを組み合わせることもできる
- 例：S3 のログと、別のデータベースの顧客表を、1 つの SQL で結合する

### Redshift

#### Amazon Redshift（れっどしふと / Amazon Redshift）

- 意味：クラウドのフルマネージドで、ペタバイト規模のデータウェアハウスサービス
- ポイント：在庫・金融・販売などのいろいろなソースのデータを共通の形にまとめ、長く保存して、履歴から高度なレポートを作るのに向く。超並列処理（MPP）で行をコンピューティングノードに分けて並列に処理し、列指向ストレージで I/O を大きく減らす。プロビジョンドクラスターと Serverless がある
- 例：全社の売上データを集め、過去 5 年の傾向を毎週レポートにする

#### Redshift Spectrum（すぺくとらむ / Amazon Redshift Spectrum）

- 意味：Redshift のテーブルにロードせずに、S3 のファイルから構造化・半構造化データを取ってクエリする機能
- ポイント：超並列処理で大きなデータでも速く実行する。Glue Data Catalog の外部テーブルを使う。Redshift の中のデータと S3 のデータを一緒に分析できる
- 例：最近 1 年分は Redshift に、古いデータは S3 に置き、両方をまとめてクエリする

#### Redshift Serverless（さーばーれす / Amazon Redshift Serverless）

- 意味：データウェアハウスの容量を用意・管理せずに、分析を実行してスケールできる Redshift の形
- ポイント：容量の用意とスケーリングを自動で行い、厳しい、予測できないワークロードでも速い。使った容量にだけ支払う
- 例：月末だけ分析が集中する部署で、Redshift Serverless を使う

#### 同時実行スケーリング（どうじじっこうすけーりんぐ / Concurrency scaling）

- 意味：クエリが増えたとき、Redshift が自動でクラスターの容量を足して、待たずに処理する機能
- ポイント：数千の同時ユーザーと同時クエリでも、速さを保つ。読み取りと書き込みの両方に対応。どちらのクラスターで実行しても最新のデータが見える。WLM キューで、どのクエリを送るかを決める
- 例：朝 9 時に全社員がダッシュボードを開いても、待たせない

### 可視化と検索

#### Amazon Quick Sight と SPICE（くいっくさいと / Amazon Quick Sight, SPICE）

- 意味：対話的なデータの可視化とビジネスインテリジェンス（BI）の機能と、それが使うインメモリの計算エンジン
- ポイント：データソースに接続してダッシュボードを作り、アプリに埋め込める。SPICE にデータを取り込むと、分析が速くなり、直接クエリを待たなくてよく、何度使っても追加のコストがかからない。もとは Amazon QuickSight
- 例：Athena のテーブルを SPICE に取り込み、経営層向けのダッシュボードを作る
- 語の意味：SPICE＝Super-fast, Parallel, In-memory Calculation Engine

#### Amazon OpenSearch Service（おーぷんさーち / Amazon OpenSearch Service）

- 意味：AWS で OpenSearch クラスターのデプロイ・運用・スケーリングを簡単にするマネージドサービス
- ポイント：OpenSearch は、ログ分析・リアルタイムのアプリ監視・クリックストリーム分析などに使う、オープンソースの検索と分析のエンジン。ドメイン（＝クラスター）を作って使い、障害のノードは自動で置き換えられる。Firehose の宛先にもなる
- 例：アプリのログを Firehose で OpenSearch Service に送り、エラーをすぐ検索する

#### 問 aws-20-o28

- 問：Redshift のダッシュボードを、毎朝 9 時に数千人の社員が一斉に開き、クエリが待たされる。ふだんの容量は足りている。この時間の集中にだけ自動で対応したい。最も適したものはどれか。

#### 問 aws-20-o29
