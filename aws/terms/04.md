## 04-1 KMS のキー

### まとめ表

| 項目 | カスタマーマネージドキー | AWS マネージドキー | AWS 所有のキー |
| :-: | :-: | :-: | :-: |
| だれが作る | 自分 | AWS のサービスが自分のアカウントに | AWS のサービス（自分のアカウントの外） |
| キーポリシー | 自分で決める | サービスが決める（見るだけ） | 見えない |
| ローテーション | 選べる（自動・オンデマンド） | 毎年自動（変えられない） | サービスが決める |
| CloudTrail で使い方を見る | できる | できる | できない |
| 料金 | 月額＋使った分 | 月額なし・使った分 | なし |

### KMS とキーの種類

#### AWS KMS（えーだぶりゅーえすけーえむえす / AWS Key Management Service）

- 意味：データの暗号化や署名に使うキーを作り、使い方を管理する AWS のマネージドサービス
- ポイント：キー（KMS キー）は FIPS 140-3 レベル 3 で検証された HSM で守られ、暗号化されないまま KMS の外に出ることはない。KMS キーはリージョンごとのもの。S3・EBS・RDS など多くのサービスと統合されている
- 語の意味：Key＝鍵、Management＝管理、Service＝サービス

#### カスタマーマネージドキー（かすたまーまねーじどきー / customer managed key）

- 意味：自分のアカウントに自分で作り、所有し、管理する KMS キー
- ポイント：キーポリシー・IAM ポリシー・グラント・有効化と無効化・ローテーション・削除の予定を自分で決められる。使い方を CloudTrail で監査できる。月額の料金がかかる。アカウントをまたいで暗号化したデータを共有するならこれ
- 例：「キーのアクセス権を自分で管理し、使用状況を監査したい」→ カスタマーマネージドキー

#### AWS マネージドキー（えーだぶりゅーえすまねーじどきー / AWS managed key）

- 意味：AWS のサービスが、自分のアカウントに代わりに作って管理・使用する KMS キー。`aws/s3` のような別名が付く
- ポイント：見ることや CloudTrail での監査はできるが、キーポリシーの変更・ローテーションの設定・削除はできない。毎年自動でローテーションされる。2021 年からは新しいサービス用には作られない古い種類
- 例：SSE-KMS でキーを指定しないと、S3 が `aws/s3` を自動で作る

#### AWS 所有のキー（えーだぶりゅーえすしょゆうのきー / AWS owned key）

- 意味：AWS のサービスが所有・管理し、複数のアカウントで使う KMS キー。自分のアカウントにはない
- ポイント：無料。キーを監査したり制御したりする必要がないなら、よい選択。CloudTrail で使い方は見られない

#### キーポリシー（きーぽりしー / key policy）

- 意味：KMS キーに付けるリソースベースのポリシー。だれがそのキーをどう使えるかを決める
- ポイント：すべての KMS キーに、ちょうど1つ必要。KMS キーへのアクセスを制御する主な方法。デフォルトのキーポリシーは、キーを持つアカウントが IAM ポリシーでアクセスを許可できるようにしている。別のアカウントにキーを使わせるときは、キーポリシー（キーを持つ側）と相手のアカウントの IAM ポリシーの両方で許可する

#### グラント（ぐらんと / grant）

- 意味：特定のプリンシパルに、条件付きで KMS キーの操作を許す仕組み
- ポイント：キーポリシーや IAM ポリシーを変えずに作って消せるので、一時的な許可によく使う。AWS のサービスが利用者の代わりにキーを使うときに多い。許可だけで、拒否はできない

### 暗号化のしくみとライフサイクル

#### エンベロープ暗号化（えんべろーぷあんごうか / envelope encryption）

- 意味：データをデータキーで暗号化し、そのデータキーを別のキー（KMS キー）で暗号化する方法
- ポイント：大きなデータは手元のデータキーで速く暗号化し、KMS には小さなデータキーの暗号化・復号だけを頼む。暗号化したデータキーはデータと一緒に保存する。S3・EBS・RDS の暗号化もこの考え方
- 語の意味：Envelope＝封筒（データを入れた封筒を、さらに鍵で封じるイメージ）

#### データキー（でーたきー / data key）

- 意味：データそのものを暗号化するために、KMS に作ってもらうキー
- ポイント：KMS はプレーンテキストのデータキー（すぐ使う）と、暗号化したデータキー（保存用）を返す。KMS キーと違って KMS の外で使うが、KMS はデータキーを保存も追跡もしない。使い終わったプレーンテキストのデータキーはメモリから消す

#### 自動キーローテーション（じどうきーろーてーしょん / automatic key rotation）

- 意味：KMS キーの暗号化マテリアル（中身の鍵）を、決まった日数ごとに自動で新しくすること
- ポイント：カスタマーマネージドキーでは選んで有効にする（デフォルトの期間は 365 日）。AWS マネージドキーは毎年自動。キー ID や ARN は変わらず、古いマテリアルも残るので、前に暗号化したデータもそのまま復号でき、アプリの変更は要らない

#### キーの削除と無効化（きーのさくじょとむこうか / deleting and disabling keys）

- 意味：KMS キーを使えなくする2つの方法。削除は 7～30 日（デフォルト 30 日）の待機期間のあとで実際に消え、元に戻せない
- ポイント：削除するとそのキーで暗号化したデータは復号できなくなる。迷ったら削除ではなく無効化（あとで有効に戻せる）。待機期間中なら削除の予定を取り消せる

#### マルチリージョンキー（まるちりーじょんきー / multi-Region key）

- 意味：異なるリージョンにあって、同じキーマテリアルとキー ID を持ち、同じキーのように使える KMS キーの組
- ポイント：あるリージョンで暗号化したデータを、再暗号化やリージョンをまたぐ呼び出しなしで別のリージョンで復号できる。災害対策やグローバルなアプリで使う。キー ID は `mrk-` で始まる。キーポリシーなどは各リージョンで別々に管理する

#### キーマテリアルのインポート（きーまてりあるのいんぽーと / imported key material）

- 意味：キーマテリアルなしで KMS キーを作り、自分で用意したキーマテリアルを取り込むこと（BYOK）
- ポイント：キーマテリアルの責任は自分に残る。有効期限を付けたり、すぐに消したりできる。「自分で作った鍵を使う決まりがある」ときの答え
- 語の意味：BYOK＝Bring Your Own Key（自分の鍵を持ち込む）

## 04-2 HSM・証明書・秘密情報

### まとめ表

| 守るもの | 使うサービス | 決め手 |
| :-: | :-: | :-: |
| データを暗号化するキー | AWS KMS | 多くのサービスと統合。マネージド |
| キーを置く専用の HSM | AWS CloudHSM | シングルテナント。自分で完全に制御 |
| SSL/TLS 証明書 | AWS Certificate Manager | 無料・自動更新（統合サービスで） |
| DB のパスワード・API キー | AWS Secrets Manager | 自動ローテーション |
| 設定値・暗号化した値 | Parameter Store | 標準階層は無料。ローテーションなし |

### HSM

#### AWS CloudHSM（えーだぶりゅーえすくらうどえいちえすえむ / AWS CloudHSM）

- 意味：AWS のクラウドに置いた、自分専用の HSM（ハードウェアセキュリティモジュール）のクラスターを使えるサービス
- ポイント：汎用のシングルテナントの HSM で、キー・アルゴリズム・ユーザー管理を自分で完全に制御できる（AWS からは見えない）。その分、責任は KMS より大きい。「シングルテナント」「HSM を自分で管理」「FIPS 140 レベル 3 を自分で制御」なら CloudHSM
- 語の意味：HSM＝Hardware Security Module（鍵を安全に保管して暗号処理をする専用の機器）

#### カスタムキーストア（かすたむきーすとあ / custom key store）

- 意味：KMS キーのキーマテリアルを、自分が所有・管理する CloudHSM のクラスターで作って保存する仕組み
- ポイント：KMS の使いやすさ（S3 などとの統合）と、CloudHSM の制御を組み合わせる。暗号の処理はクラスターの HSM の中で行われる

### 証明書

#### AWS Certificate Manager（えーだぶりゅーえすさーてぃふぃけーとまねーじゃー / AWS Certificate Manager, ACM）

- 意味：Web サイトやアプリを守る SSL/TLS 証明書を、発行・保存・更新するサービス
- ポイント：ACM で管理する証明書には追加料金がかからない。ELB や CloudFront など統合されたサービスに付けた証明書は、DNS 検証なら自動で更新される。証明書はリージョンをまたいでコピーできない
- 例：ALB に HTTPS を付ける証明書を ACM で発行する
- 語の意味：Certificate＝証明書、Manager＝管理するもの

#### CloudFront 用の証明書のリージョン（くらうどふろんとようのしょうめいしょのりーじょん / us-east-1 certificate for CloudFront）

- 意味：CloudFront で ACM の証明書を使うときは、米国東部（バージニア北部）リージョン `us-east-1` で証明書をリクエスト（またはインポート）する決まり
- ポイント：ALB の証明書は ALB と同じリージョンで取る。CloudFront だけは `us-east-1`。本番のひっかけによく出る

#### インポートした証明書（いんぽーとしたしょうめいしょ / imported certificate）

- 意味：ほかの認証局から買った証明書を ACM に取り込んだもの
- ポイント：ACM は自動で更新しない。有効期限を見張って、新しい証明書を取り込み直すのは自分の責任。期限切れが近いことは CloudWatch Events（今の EventBridge）で通知できる

### 秘密情報

#### AWS Secrets Manager（えーだぶりゅーえすしーくれっつまねーじゃー / AWS Secrets Manager）

- 意味：データベースの認証情報・API キー・OAuth トークンなどのシークレットを、保存・取得・ローテーションするサービス
- ポイント：アプリのソースコードに書き込んだ（ハードコードした）パスワードを、実行時の Secrets Manager の呼び出しに置き換えられる。自動ローテーションを設定できる。保存時は KMS で暗号化。シークレットごと・API コールごとに料金がかかる
- 例：RDS のパスワードを 30 日ごとに自動で変え、アプリは毎回 Secrets Manager から取る

#### シークレットのローテーション（しーくれっとのろーてーしょん / secret rotation）

- 意味：シークレットと、データベースやサービス側の認証情報を、定期的に新しくすること
- ポイント：長く使う秘密を短期間の秘密に置き換え、漏れたときの被害を減らす。アプリは Secrets Manager から取るので、パスワードが変わってもアプリの更新は要らない

#### Parameter Store（ぱらめーたすとあ / AWS Systems Manager Parameter Store）

- 意味：設定データやシークレットを階層の形で保存する Systems Manager の機能。`SecureString` を選ぶと KMS で暗号化して保存する
- ポイント：標準階層は追加料金なし。ただし保存したシークレットの自動ローテーションはない。AMI ID・エンドポイントの URL などの設定値向き。DB の認証情報で自動ローテーションが要るなら Secrets Manager

## 04-3 ストレージと通信の暗号化

### まとめ表

| S3 の暗号化 | キーを管理するのは | 特徴 |
| :-: | :-: | :-: |
| SSE-S3 | S3 | 全バケットのデフォルト。追加費用なし |
| SSE-KMS | KMS（AWS マネージドかカスタマーマネージド） | キーの権限と CloudTrail の監査。KMS の料金 |
| DSSE-KMS | KMS | 2層の暗号化。厳しいコンプライアンス向け |
| SSE-C | お客様（リクエストごとに渡す） | S3 はキーを保存しない。HTTPS 必須 |
| クライアント側の暗号化 | お客様 | S3 に送る前に暗号化。S3 は中身を知らない |

### S3 の暗号化

#### SSE-S3（えすえすいーえすすりー / server-side encryption with Amazon S3 managed keys）

- 意味：S3 が管理するキーでオブジェクトを暗号化するサーバー側の暗号化
- ポイント：すべての S3 バケットのデフォルトの暗号化。2023 年 1 月 5 日以降、新しいオブジェクトは追加費用なしで自動的に暗号化される。キーの権限を細かく分けたり、キーの使い方を監査したりはできない
- 語の意味：SSE＝Server-Side Encryption（サーバー側の暗号化）

#### SSE-KMS（えすえすいーけーえむえす / server-side encryption with AWS KMS keys）

- 意味：KMS のキーで S3 のオブジェクトを暗号化するサーバー側の暗号化
- ポイント：キーを使う権限で「だれが復号できるか」を分けられ、キーの使い方を CloudTrail で監査できる。キーを指定しなければ AWS マネージドキー `aws/s3`。暗号化したデータをアカウントをまたいで共有するならカスタマーマネージドキーが必要
- 例：「S3 のデータの暗号化キーの使用を監査し、ローテーションも自分で管理したい」

#### DSSE-KMS（でぃーえすえすいーけーえむえす / dual-layer server-side encryption with AWS KMS keys）

- 意味：S3 にアップロードするとき、独立した2つの AES-256 の暗号化の層をかける暗号化
- ポイント：多層の暗号化を求める厳しいコンプライアンスの基準を満たすため。「2層の暗号化が必要」と書かれていたらこれ

#### SSE-C（えすえすしー / server-side encryption with customer-provided keys）

- 意味：リクエストごとにお客様が渡したキーで、S3 が暗号化・復号するサーバー側の暗号化
- ポイント：S3 はキーを保存しないので、キーをなくすとオブジェクトも失われる。どのオブジェクトにどのキーを使ったかはお客様が管理する。HTTPS が必須（HTTP は拒否）。2026 年 4 月から、新しい汎用バケットでは SSE-C がデフォルトで無効になり、使うなら明示的に有効にする

#### クライアント側の暗号化（くらいあんとがわのあんごうか / client-side encryption）

- 意味：S3 に送る前に、お客様の側でデータを暗号化すること（Amazon S3 暗号化クライアントなど）
- ポイント：S3 はすでに暗号化されたものを受け取るだけで、暗号化・復号に関わらない。AWS をふくむ第三者に中身を見せたくないとき

#### S3 バケットキー（えすすりーばけっときー / S3 Bucket Key）

- 意味：SSE-KMS で、S3 がバケット単位の短期間のキーを使い、KMS への呼び出しを減らす仕組み
- ポイント：KMS のリクエストのコストを最大 99% 減らせる。SSE-KMS のオブジェクトが大量にあって KMS の料金が高いときの答え

#### aws:SecureTransport（えーだぶりゅーえすせきゅあとらんすぽーと / aws:SecureTransport）

- 意味：リクエストが HTTPS（TLS）で送られたかどうかを表す条件キー
- ポイント：バケットポリシーで `aws:SecureTransport` が `false` のリクエストを Deny すると、HTTPS の接続だけを許可できる（転送中の暗号化を強制）。保存時の暗号化とは別の話

### EBS と RDS の暗号化

#### EBS 暗号化（いーびーえすあんごうか / Amazon EBS encryption）

- 意味：KMS のキーで EBS ボリュームとスナップショットを暗号化する機能
- ポイント：暗号化したボリュームでは、保存データ・ボリュームとインスタンスの間を流れるデータ・そこから作るスナップショット・そのスナップショットから作るボリュームがすべて暗号化される。暗号化されていないボリュームは、スナップショットを暗号化してコピーし（または暗号化してボリュームを作り）入れ替える

#### デフォルトでの EBS 暗号化（でふぉるとでのいーびーえすあんごうか / EBS encryption by default）

- 意味：リージョンごとの設定で、そのリージョンで新しく作る EBS ボリュームとスナップショットを必ず暗号化するもの
- ポイント：リージョン固有の設定。有効にすると個々のボリュームで無効にはできない。既存のボリュームやスナップショットには影響しない

#### RDS の暗号化（あーるでぃーえすのあんごうか / Amazon RDS encryption）

- 意味：KMS のキーで DB インスタンスのストレージ・ログ・自動バックアップ・リードレプリカ・スナップショットを暗号化すること
- ポイント：DB インスタンスを作るときにだけ暗号化でき、あとからは暗号化できない。暗号化は外せない。暗号化されていない DB を暗号化するには、スナップショットを取り、コピーするときに暗号化して、そこから復元する（ブルー/グリーンデプロイでもできる）
- 例：暗号化していない本番 DB → スナップショット → 暗号化コピー → 新しい DB に復元して切り替え

#### SSL/TLS での接続（えすえすえるてぃーえるえすでのせつぞく / SSL/TLS connection）

- 意味：クライアントと DB インスタンスのあいだを流れるデータを暗号化する接続
- ポイント：転送中の暗号化。保存時の暗号化（KMS）とは別に設定する。サーバー証明書を検証すれば、相手が本物の DB かも確かめられる

## 問題演習

- 書式：「#### 問 問題ID」の下に、問・ア〜エ・正解・解説・選択肢ごとの意味・出典を書く。「###」は小分類（クイズの範囲に使う）
- 全問オリジナル問題（AWS は本番の問題を公開していない）。会社名や場面は Claude が作った例。出典には、答えの根拠にした AWS のドキュメントを書いた

### 04-1 KMS のキー

#### 問 aws-04-o01

- 問：S3 のデータを KMS で暗号化する。暗号化キーにアクセスできる人をキーポリシーで自分で決め、キーの使用状況を監査し、ローテーションの有無も自分で選びたい。使うキーはどれか。
- ア：AWS マネージドキー
- イ：カスタマーマネージドキー
- ウ：AWS 所有のキー
- エ：SSE-S3 のキー
- 正解：イ
- 解説：キーポリシー・ローテーション・削除などを自分で管理できるのはカスタマーマネージドキー。使用は CloudTrail で監査できる。
- アの意味：使用状況の監査はできるが、キーポリシーの変更やローテーションの設定はできない。
- イの意味：正しい。
- ウの意味：自分のアカウントにはなく、監査も制御もできない。
- エの意味：S3 が管理するキーで、キーの権限を自分で決めたり使い方を監査したりはできない。
- 出典：オリジナル問題（根拠：AWS「AWS KMS keys」（『カスタマーマネージドキーは、 AWS アカウント ユーザーが作成、所有、管理する の KMS キーです。』／『暗号化オペレーションでカスタマーマネージドキーを使用し、 AWS CloudTrail ログでその使用を監査できます。』））

#### 問 aws-04-o02

- 問：AWS マネージドキー（例：`aws/ebs`）について正しいものはどれか。
- ア：キーポリシーを自由に書き換えられる
- イ：不要になったら削除の予定を入れられる
- ウ：月額の料金がかかる
- エ：毎年自動でローテーションされ、そのスケジュールは変更できない
- 正解：エ
- 解説：AWS マネージドキーはサービスが代わりに管理する。毎年自動でローテーションされ、スケジュールは変えられない。キーポリシーの変更や削除もできず、月額料金はない。
- アの意味：キーポリシーはサービスが決め、利用者は見るだけ。
- イの意味：削除の予定は入れられない。
- ウの意味：月額料金はない（使用には料金がかかることがある）。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「AWS KMS keys」（『すべての AWS マネージドキー は毎年自動的にローテーションされます。このローテーションスケジュールは変更できません。』））

#### 問 aws-04-o03

- 問：KMS キーのキーポリシーについて正しいものはどれか。
- ア：IAM ポリシーがあればキーポリシーはなくてもよい
- イ：1つの KMS キーに複数のキーポリシーを付け、合わせて評価する
- ウ：キーポリシーは AWS マネージドキーにだけ付く
- エ：すべての KMS キーに、ちょうど1つのキーポリシーが必要
- 正解：エ
- 解説：キーポリシーは KMS キーのリソースポリシーで、アクセス制御の主な方法。どの KMS キーにも厳密に1つ必要。
- アの意味：IAM ポリシーやグラントも使えるが、キーポリシーは必ず要る。
- イの意味：キーポリシーは1つだけ。
- ウの意味：すべての KMS キーに付く。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「AWS KMS のキーポリシー」（『すべての KMS キーには、厳密に 1 つのキーポリシーが必要です。』））

#### 問 aws-04-o04

- 問：数 GB のファイルを KMS を使って暗号化したい。AWS のドキュメントで「エンベロープ暗号化」と呼ばれる方法はどれか。
- ア：ファイル全体を KMS に送り、KMS キーで直接暗号化する
- イ：KMS キーをダウンロードして、手元でファイルを暗号化する
- ウ：ファイルを2つの KMS キーで順に二重に暗号化する
- エ：データをデータキーで暗号化し、そのデータキーを KMS キーで暗号化して、データと一緒に保存する
- 正解：エ
- 解説：エンベロープ暗号化は、データをデータキーで暗号化し、そのデータキーを別のキーで暗号化する方法。KMS には小さなデータキーの暗号化・復号だけを頼む。
- アの意味：大きなデータを毎回 KMS に送るのは非効率で、エンベロープ暗号化ではない。
- イの意味：KMS キーは KMS の外に出せない。
- ウの意味：二重の暗号化（DSSE-KMS の考え方に近い）で、エンベロープ暗号化の定義ではない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「AWS KMS 暗号化の必須事項」（『*エンベロープ暗号化*は、データキーでプレーンテキストデータを暗号化してから、そのデータキーを別のキーで暗号化する手法です。』））

#### 問 aws-04-o05

- 問：KMS の GenerateDataKey で得たデータキーについて正しいものはどれか。
- ア：KMS はプレーンテキストのデータキーと暗号化したコピーを返すが、データキーを保存も追跡もしない
- イ：KMS がデータキーを保存し、復号のときに自動で使う
- ウ：データキーは KMS の外で使えない
- エ：データキーは KMS キーそのもので、ダウンロードできる
- 正解：ア
- 解説：KMS はデータキーを作り、暗号化・復号はするが、保存・管理・追跡はしない。暗号化したデータキーはデータと一緒に自分で保存し、復号のときに KMS に復号を頼む。
- アの意味：正しい。
- イの意味：KMS はデータキーを保存しない。
- ウの意味：データキーは KMS の外で使うためのもの。
- エの意味：KMS キーはダウンロードできない。データキーとは別物。
- 出典：オリジナル問題（根拠：AWS「データキーを生成する」（『ダウンロードできない対称 KMS キーとは異なり、データキーは AWS KMSの外部での使用のためにユーザーに返されます。』／『ただし、 AWS KMS はデータキーを保存、管理、追跡したり、データキーを使用して暗号化オペレーションを実行したりしません。』））

#### 問 aws-04-o06

- 問：カスタマーマネージドキーで自動キーローテーションを有効にした。ローテーションの前に暗号化したデータはどうなるか。
- ア：新しいキーマテリアルで再暗号化しないと復号できない
- イ：キー ID が変わるので、アプリの設定を書き換える必要がある
- ウ：ローテーションのたびに古いデータは削除される
- エ：古いキーマテリアルが残るので、アプリを変えずにそのまま復号できる
- 正解：エ
- 解説：KMS はキーのすべてのキーマテリアルを保持し、暗号化に使ったマテリアルで透過的に復号する。キー ID や ARN は変わらない。
- アの意味：再暗号化は要らない。
- イの意味：キー ID は変わらない。手動でローテーションする（新しいキーを作る）場合は、エイリアスなどの切り替えが要る。
- ウの意味：データは消えない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「ローテーション AWS KMS keys」（『暗号文の復号にローテーションされた KMS キーを使用する場合、 AWS KMS は暗号化に使用したものと同じバージョンのキーマテリアルを使用します。』／『AWS KMS キーローテーションは、透過的で使いやすいように設計されています。』））

#### 問 aws-04-o07

- 問：もう使っていないと思われるカスタマーマネージドキーがあるが、どこかのデータの暗号化に使われているかもしれない。最も安全な対応はどれか。
- ア：すぐに削除する（待機期間なし）
- イ：待機期間 7 日で削除の予定を入れ、待機期間が過ぎても戻せるので放っておく
- ウ：まず無効化して様子を見る（必要ならあとで有効に戻す）
- エ：キーポリシーを空にする
- 正解：ウ
- 解説：削除すると、そのキーで暗号化したデータは復号できなくなり、元に戻せない。迷ったら無効化する。
- アの意味：削除には必ず 7～30 日の待機期間があり、すぐには消せない。
- イの意味：待機期間中なら取り消せるが、過ぎると元に戻せない。
- ウの意味：正しい。
- エの意味：だれも管理できなくなるおそれがあり、安全な対応ではない。
- 出典：オリジナル問題（根拠：AWS「AWS KMS key を削除する」（『KMS キーを削除すると、その KMS キーで暗号化されたデータを復号できなくなります。』／『不明な場合は、削除するのではなく、[KMS キーを無効化する]ことを検討します。』））

#### 問 aws-04-o08

- 問：KMS キーの削除の待機期間として正しいものはどれか。
- ア：7～30 日の間で設定し、デフォルトは 30 日
- イ：1～7 日の間で設定し、デフォルトは 7 日

- 正解：ア
- 解説：削除は破壊的で危険なので、KMS は 7～30 日の待機期間を必須にしている。デフォルトは 30 日。
- アの意味：正しい。
- イの意味：範囲が違う。
- ウの意味：待機期間は必須。
- エの意味：範囲が違う（ローテーションの期間と混同している）。
- 出典：オリジナル問題（根拠：AWS「AWS KMS key を削除する」（『KMS キーの削除は破壊的で潜在的に危険であるため、 では 7～30 日間の待機期間を設定 AWS KMS する必要があります。』／『デフォルトの待機時間は、30 日です。』））

#### 問 aws-04-o09

- 問：東京リージョンで KMS で暗号化したデータを大阪リージョンに複製し、障害時には大阪で再暗号化せずに復号したい。最も適したものはどれか。

#### 問 aws-04-o10

- 問：AWS のサービスが利用者の代わりに一時的に KMS キーを使えるようにしたい。キーポリシーを書き換えず、用が済んだら消せる仕組みはどれか。

### 04-2 HSM・証明書・秘密情報

#### 問 aws-04-o11

- 問：規制により、暗号化キーをシングルテナントの HSM に置き、キーとユーザーの管理を自社で完全に制御する必要がある。AWS からもキーが見えないようにしたい。最も適したものはどれか。
- ア：AWS KMS のカスタマーマネージドキー
- イ：AWS Secrets Manager
- ウ：AWS CloudHSM
- エ：AWS Certificate Manager
- 正解：ウ
- 解説：CloudHSM はシングルテナントの HSM で、キー・アルゴリズム・ユーザーを自分で完全に制御でき、データプレーンは AWS には見えない。その分、責任は大きい。
- アの意味：KMS の HSM は AWS が運用するマネージドなもので、シングルテナントの HSM を自分で管理するわけではない。
- イの意味：パスワードなどのシークレットを保存するサービス。
- ウの意味：正しい。
- エの意味：SSL/TLS の証明書を管理するサービス。
- 出典：オリジナル問題（根拠：AWS「とは AWS CloudHSM」（『標準に準拠したシングルテナントで、FIPS モードのクラスターに対して FIPS 140-2 レベル 3 または FIPS 140-3 レベル 3 で検証された HSM を提供します。』／『データプレーンはエンドツーエンド (E2E) で暗号化されており、AWS には表示されないため、自身のユーザー管理 (IAM ロール外) を制御できます。』））

#### 問 aws-04-o12

- 問：S3 や EBS との統合など KMS の使いやすさは保ちつつ、KMS キーのキーマテリアルは自社が管理する CloudHSM のクラスターに置きたい。使うものはどれか。
- ア：マルチリージョンキー

- 正解：エ
- 解説：CloudHSM キーストアは CloudHSM クラスターを使うカスタムキーストアで、KMS キーのキーマテリアルを自分のクラスターで作って保存する。KMS の統合と CloudHSM の制御を組み合わせられる。
- アの意味：リージョンをまたいで同じキーを使う仕組みで、CloudHSM とは関係ない。
- イの意味：AWS のサービスが管理するキー。
- ウの意味：S3 のリクエストごとにお客様がキーを渡す暗号化で、KMS の統合は使えない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「AWS CloudHSM キーストア」（『カスタムキーストア AWS KMS key で を作成すると、 は、ユーザーが所有および管理する AWS CloudHSM クラスターに KMS キーの抽出不可能なキーマテリアル AWS KMS を生成して保存します。』））

#### 問 aws-04-o13

- 問：CloudFront のディストリビューションに独自ドメインの HTTPS を付ける。オリジンは大阪リージョンの ALB。ACM の証明書はどのリージョンでリクエストするか（CloudFront 用）。
- ア：大阪リージョン（ALB と同じ）
- イ：米国東部（バージニア北部）us-east-1

- アの意味：ALB 用の証明書ならこのリージョン。CloudFront 用ではない。
- イの意味：正しい。
- ウの意味：利用者との近さでは決まらない。
- エの意味：CloudFront は us-east-1 の証明書しか使えない。
- 出典：オリジナル問題（根拠：AWS「CloudFront で SSL/TLS 証明書を使用するための要件」（『CloudFront ディストリビューションで ACM 証明書を使用するには、米国東部 (バージニア北部) リージョン (`us-east-1`) の証明書をリクエスト (またはインポート) していることを確認します。』））

#### 問 aws-04-o14

- 問：外部の認証局から買った証明書を ACM にインポートして ALB で使っている。この証明書の更新について正しいものはどれか。
- ア：ACM が有効期限の前に自動で更新する
- イ：ALB が自動で認証局に更新を依頼する
- ウ：ACM は自動で更新しないので、有効期限を見張って新しい証明書を再インポートする

- 正解：ウ

- イの意味：そのような機能はない。
- ウの意味：正しい。
- エの意味：証明書には必ず有効期限がある。
- 出典：オリジナル問題（根拠：AWS「証明書を にインポートする AWS Certificate Manager」（『インポートした証明書の有効期限をモニタリングし、失効する前に更新する責任はお客様に帰します。』））

#### 問 aws-04-o15

- 問：ACM で発行したパブリック証明書を、東京とバージニア北部の2つのリージョンの ALB で使いたい。正しいものはどれか。
- ア：リージョンごとに証明書をリクエスト（またはインポート）する。リージョン間でコピーはできない
- イ：東京で発行した証明書をバージニア北部にコピーする
- ウ：1つの証明書がすべてのリージョンの ALB で自動的に使える
- エ：ALB には ACM の証明書は使えない
- 正解：ア
- 解説：複数のリージョンの ELB で同じドメインの証明書を使うには、リージョンごとにリクエストまたはインポートする。リージョン間でコピーはできない。
- アの意味：正しい。
- イの意味：コピーはできない。
- ウの意味：ACM の証明書はリージョンごと。CloudFront だけは us-east-1 の証明書を世界に配る。
- エの意味：ELB は ACM と統合されている。
- 出典：オリジナル問題（根拠：AWS「とは AWS Certificate Manager」（『複数の AWS リージョンで同じ完全修飾ドメイン名 (FQDN) または一連の FQDNs に対して Elastic Load Balancing で証明書を使用するには、リージョンごとに証明書をリクエストまたはインポートする必要があります。』／『リージョン間で証明書をコピーすることはできません。』））

#### 問 aws-04-o16

- 問：アプリのソースコードに RDS のパスワードが書き込まれている。パスワードをコードから外し、定期的に自動で変えたい。最も適したサービスはどれか。

- エ：AWS Secrets Manager
- 正解：エ
- 解説：Secrets Manager は DB の認証情報などを保存し、自動ローテーションを設定できる。アプリは実行時に Secrets Manager から取るので、パスワードが変わってもアプリの更新は要らない。
- アの意味：暗号化して保存はできるが、自動ローテーションの仕組みはない。
- イの意味：暗号化のキーを管理するもので、パスワードの保存やローテーションはしない。
