## 16-1 DynamoDB のしくみと容量

### まとめ表

| 項目 | オンデマンドモード | プロビジョンドモード |
| :-: | :-: | :-: |
| 容量の決め方 | 決めない（自動で即座にスケール） | 1 秒あたりの読み込み・書き込みを指定 |
| 料金 | リクエストの分だけ | プロビジョニングした時間単位の容量 |
| 向くワークロード | 予測できない・新しい・ほとんどの場合の既定 | 安定していて予測できる |
| 自動の調整 | 不要 | DynamoDB Auto Scaling |

数字は AWS「DynamoDB のスループットキャパシティ」などによる

### テーブルとキー

#### Amazon DynamoDB（だいなもでぃーびー / Amazon DynamoDB）

- 意味：サーバーレスでフルマネージドの、分散 NoSQL データベース。どんな規模でも 1 桁ミリ秒の性能を出す
- ポイント：キーと値のモデルとドキュメントのモデルに対応する。JOIN はできないので、データモデルを非正規化する。サーバーのプロビジョニングやパッチは要らず、バージョンもメンテナンスウィンドウもない。1 つの項目は 400 KB まで
- 例：ショッピングカートやゲームのセッションなど、決まったキーで速く読み書きするデータ
- 語の意味：NoSQL＝SQL のリレーショナルモデル以外のデータベース

#### パーティションキー（ぱーてぃしょんきー / Partition key）

- 意味：項目を特定するプライマリキーの 1 つ目の属性。この値で、データを置く場所（パーティション）が決まる
- ポイント：パーティションキーだけのシンプルなプライマリキーと、パーティションキー＋ソートキーの複合プライマリキーがある。値がかたよると、特定のパーティションにアクセスが集中する
- 例：ユーザーの ID をパーティションキーにする

#### ソートキー（そーときー / Sort key）

- 意味：複合プライマリキーの 2 つ目の属性。同じパーティションキーの項目を、この値の順に並べて保存する
- ポイント：同じパーティションキーの中で、範囲や順序を指定して Query できる。パーティションキーとソートキーの組で項目が一意に決まる
- 例：パーティションキー＝ユーザー ID、ソートキー＝注文日時にして、あるユーザーの最近の注文を順に取る

#### グローバルセカンダリインデックス（GSI）（じーえすあい / Global secondary index）

- 意味：テーブルと違うパーティションキーとソートキーを持てるインデックス
- ポイント：テーブルのキー以外の属性で Query できる。既存のテーブルにも作れる。強力な整合性のある読み込みはできない（結果整合性だけ）。既定のクォータはテーブルあたり 20 個
- 例：パーティションキーがユーザー ID のテーブルに、ゲーム名で引く GSI を足す

#### ローカルセカンダリインデックス（LSI）（えるえすあい / Local secondary index）

- 意味：パーティションキーはテーブルと同じで、ソートキーだけが違うインデックス
- ポイント：テーブルを作るときに作る（あとから足せない）。テーブルと同じく強力な整合性のある読み込みができる。GSI との違いは「パーティションキーが同じ」「作成時だけ」「強い整合性が使える」
- 例：フォーラム名ごとのスレッドを、最後の投稿日時の順にも取れるようにする

### 容量と整合性

#### オンデマンドモード（おんでまんどもーど / On-demand mode）

- 意味：容量を計画せずに、リクエストに合わせて自動でスケールし、使った分だけ払うスループットのモード
- ポイント：ほとんどのワークロードで勧められる既定のモード。前に到達したトラフィックまで即座に受け入れ、新しいピークにも自動で合わせる。テーブルやインデックスに最大のスループットを設定してコストを抑えることもできる
- 例：利用者がどれだけ増えるかわからない新しいアプリのテーブル

#### プロビジョンドモード（ぷろびじょんどもーど / Provisioned mode）

- 意味：1 秒あたりの読み込みと書き込みの回数（RCU・WCU）を指定し、その時間単位の容量に料金を払うモード
- ポイント：実際に使った量ではなく、プロビジョニングした量に課金されるので、コストを予測しやすい。安定して予測できるワークロード向け。DynamoDB Auto Scaling で自動調整できる。プロビジョンドからオンデマンドへは 24 時間に 4 回まで、オンデマンドからプロビジョンドへはいつでも切り替えられる
- 例：毎日ほぼ同じ量の注文を処理する、成熟したシステムのテーブル

#### 読み込みキャパシティユニット（RCU）と書き込みキャパシティユニット（WCU）（あーるしーゆー・だぶりゅしーゆー / Read and write capacity units）

- 意味：プロビジョンドモードで容量を表す単位。1 RCU は 4 KB までの項目で 1 秒に強力な整合性の読み込み 1 回（結果整合性なら 2 回）、1 WCU は 1 KB までの項目で 1 秒に書き込み 1 回
- ポイント：項目のサイズを 4 KB（読み込み）または 1 KB（書き込み）で割って切り上げる。3 KB の項目を 1 秒に 80 回、強力な整合性で読むなら 80 RCU、結果整合性なら 40 RCU
- 例：512 バイトの項目を 1 秒に 100 回書くなら 100 WCU
- 語の意味：Read/Write＝読み込み・書き込み、Capacity＝容量、Unit＝単位

#### DynamoDB Auto Scaling（おーとすけーりんぐ / DynamoDB auto scaling）

- 意味：Application Auto Scaling を使い、プロビジョンドの読み込み・書き込みキャパシティを実際のトラフィックに合わせて自動で調整する機能
- ポイント：テーブルと GSI の両方に使える。コンソールでテーブルを作ると既定で有効になる。オンデマンドモードとの違いは、容量を指定するモードのまま上下させること
- 例：昼に多く夜に少ないソーシャルアプリのテーブルで、プロビジョンドの容量を自動で上下させる

#### 結果整合性と強力な整合性（けっかせいごうせい・きょうりょくなせいごうせい / Eventually consistent and strongly consistent reads）

- 意味：結果整合性のある読み込みは、直前の書き込みが反映されていないことがある読み込み（既定）。強力な整合性のある読み込みは、成功した以前のすべての書き込みを反映した最新のデータを返す読み込み
- ポイント：結果整合性は強力な整合性の半分のコスト。強力な整合性は ConsistentRead を true にして使い、テーブルと LSI だけで使える（GSI と Streams ではできない）
- 例：書き込んだ直後の残高を確実に読むときだけ、強力な整合性で読む

#### DynamoDB トランザクション（とらんざくしょん / DynamoDB Transactions）

- 意味：複数のアクションをまとめて、オールオアナッシングで実行する機能（TransactWriteItems・TransactGetItems）
- ポイント：TransactWriteItems は最大 100 の書き込みアクションをまとめ、同じアカウント・同じリージョンの 1 つ以上のテーブルにまたがれる。どれか 1 つでも失敗すれば全部が行われない
- 例：在庫の数を減らすことと注文の項目を作ることを、1 つのトランザクションで行う

#### テーブルクラス（てーぶるくらす / Table classes）

- 意味：DynamoDB 標準と DynamoDB 標準-IA の 2 つの料金体系。標準-IA は、ストレージが主なコストになるテーブル向け
- ポイント：既定で大半のワークロードに勧められるのは標準。標準-IA は、アプリのログや古い投稿、注文履歴などアクセスの少ないデータ向け。テーブルクラスはあとから変えられ、セカンダリインデックスも同じクラスになる
- 例：何年分もの注文履歴を残すテーブルを標準-IA にする
- 語の意味：IA＝Infrequent Access（アクセスの頻度が低い）

## 16-2 DynamoDB の機能と保護

### まとめ表

| したいこと | 使う機能 |
| :-: | :-: |
| 複数のリージョンで読み書き | グローバルテーブル（マルチアクティブ） |
| 項目の変更を Lambda で処理 | DynamoDB Streams（24 時間保存） |
| 変更を Firehose・Flink に流す | Kinesis Data Streams への変更のキャプチャ |
| 古い項目を自動で消す | TTL（書き込みスループットを使わない） |
| 数分前の状態に戻す | ポイントインタイムリカバリ（最大 35 日） |
| 何年も残す | オンデマンドバックアップ |
| 分析のために S3 へ | S3 へのエクスポート（RCU を使わない） |
| マイクロ秒で読む | DAX |

### 複製と変更の通知

#### グローバルテーブル（ぐろーばるてーぶる / Global tables）

- 意味：複数のリージョン（必要なら複数のアカウント）に DynamoDB のテーブルを自動で複製する、マルチアクティブなデータベース機能
- ポイント：どのリージョンのレプリカでも読み書きでき、利用者の近くで速く読み書きできる。複製は非同期で、競合は最後の書き込みが優先される。整合性モードは、既定のマルチリージョンの結果整合性（MREC）と、マルチリージョンの強力な整合性（MRSC）がある。Aurora Global Database は書き込みが 1 つのリージョンだけ、という点が違う
- 例：東京・バージニア北部・アイルランドの利用者が、それぞれ近くのリージョンに書き込むゲームのテーブル

#### DynamoDB Streams（すとりーむず / DynamoDB Streams）

- 意味：テーブルの項目レベルの変更を時間順にとらえ、最大 24 時間ログとして保存する機能
- ポイント：変更の前と後の内容をほぼリアルタイムで読める。各レコードは 1 回だけ、変更と同じ順序で現れる。Lambda のトリガー（イベントソースマッピング）で処理するのが典型
- 例：注文の項目が作られたら、Lambda で確認のメールを送る

#### Kinesis Data Streams への変更のキャプチャ（きねしすでーたすとりーむず / Kinesis Data Streams for DynamoDB）

- 意味：テーブルの項目レベルの変更を、Kinesis Data Streams に複製する機能
- ポイント：Data Firehose や Managed Service for Apache Flink につないで、ダッシュボードやアラート、S3 への保存に使える。DynamoDB Streams との違いは、Data Firehose や Flink など Kinesis のサービスにそのままつなげること
- 例：注文の変更を Kinesis Data Streams から Data Firehose で S3 に流す

#### TTL（有効期限）（てぃーてぃーえる / Time to Live）

- 意味：項目ごとに有効期限のタイムスタンプを決め、期限が切れた項目を DynamoDB が自動で削除する機能
- ポイント：書き込みスループットを使わずに消すので、コスト効率がよい。時刻は秒単位の UNIX エポック時間の数値。削除は通常、期限から数日以内（すぐではない）。削除は Streams にサービスによる削除として流れる
- 例：ログインのセッション情報を 24 時間後に自動で消す

### 保護と高速化

#### ポイントインタイムリカバリ（PITR）（ぽいんといんたいむりかばり / Point-in-time recovery）

- 意味：テーブルを継続的に自動バックアップし、最大 35 日の間の任意の秒の時点に戻せる機能
- ポイント：復元できる最新の時刻は、通常は現在の 5 分前。復元は新しいテーブルを作る。誤った書き込みや削除から守る。S3 へのエクスポートには PITR の有効化が必要
- 例：テストのスクリプトが本番のテーブルに誤って書き込んだので、その前の時点に戻す

#### オンデマンドバックアップ（おんでまんどばっくあっぷ / On-demand backup）

- 意味：テーブル全体の完全なバックアップを、好きなときに作って残す機能
- ポイント：バックアップを作った時点の正確な状態に戻せる。長期の保存や規制への対応に使う。本番の性能や可用性に影響しない。PITR は 35 日まで、長く残すならオンデマンドバックアップ（または AWS Backup）
- 例：毎月末のテーブルを、監査のため 7 年残す

#### S3 へのエクスポート（えくすぽーと / Export to Amazon S3）

- 意味：PITR の期間の任意の時点のテーブルのデータを、S3 バケットに書き出すフルマネージドの機能
- ポイント：非同期で、RCU を消費せず、テーブルの性能に影響しない。全体と増分の両方を出せる。Athena・Glue・EMR などで分析できる。PITR の有効化が必要
- 例：前日のテーブルを S3 に書き出し、Athena で集計する

#### 保管時の暗号化（ほかんじのあんごうか / Encryption at rest）

- 意味：DynamoDB に保存されるすべてのユーザーデータを、KMS のキーで暗号化するしくみ
- ポイント：常に有効で、オフにはできない。テーブル・インデックス・ストリーム・バックアップ・DAX クラスターも対象。キーの種類（AWS 所有・AWS マネージド・カスタマーマネージド）はいつでも切り替えられる
- 例：監査のためにキーの利用を記録したいので、カスタマーマネージドキーに切り替える

#### DAX（だっくす / DynamoDB Accelerator）

- 意味：DynamoDB と互換性のある、インメモリのキャッシュサービス
- ポイント：結果整合性の読み込みの応答を、1 桁ミリ秒からマイクロ秒にする。API が互換なので、アプリの変更は最小限。読み込みの多い・急に増える負荷で RCU を節約できる。強力な整合性の読み込みはキャッシュせず DynamoDB にそのまま渡す。書き込みが多い・強い整合性が要る・同じ読み込みが少ないアプリには向かない。VPC の中で動く
- 例：同じ商品の情報を何度も読むセールのページで、DynamoDB の前に DAX を置く
- 語の意味：DynamoDB Accelerator＝DynamoDB を速くするもの

## 16-3 ElastiCache とキャッシュ戦略

### まとめ表

| 項目 | Memcached | Valkey・Redis OSS |
| :-: | :-: | :-: |
| データ型 | シンプル | 複雑（ソート済みセットなど） |
| マルチスレッド | できる | できない |
| 複製・高可用性 | なし | レプリカ・自動フェイルオーバー |
| バックアップ | サーバーレスだけ | できる |
| Pub/Sub | なし | できる |

表は AWS「Valkey、Memcached、および Redis OSS のノードベースのクラスターの比較」による

### ElastiCache の形とエンジン

#### Amazon ElastiCache（えらすてぃきゃっしゅ / Amazon ElastiCache）

- 意味：クラウドで分散インメモリのデータストアやキャッシュを作り、管理し、スケールするマネージドサービス
- ポイント：エンジンは Valkey・Memcached・Redis OSS。サーバーレスのキャッシュと、ノードベースのクラスターの 2 つの形がある。データベースの前に置き、よく読むデータをミリ秒未満で返して、DB の負荷とコストを下げる
- 例：RDS への同じクエリの結果を ElastiCache に置き、2 回目からはキャッシュから返す

#### ElastiCache サーバーレス（さーばーれす / ElastiCache Serverless）

- 意味：ノードやクラスターを設定せずに使える、ElastiCache のキャッシュ
- ポイント：可用性の高いキャッシュを 1 分未満で作れる。メモリ・コンピューティング・帯域を監視して、垂直と水平の両方に自動でスケールする。データを複数の AZ に自動で複製し、99.99% の可用性 SLA。容量の計画が要らない
- 例：負荷の読めない新しいサービスのセッションのキャッシュ

#### Valkey と Redis OSS（ばるきー・れでぃす / Valkey, Redis OSS）

- 意味：ElastiCache で使える、複雑なデータ型・複製・永続化に対応したインメモリのキーと値のエンジン
- ポイント：レプリケーション（高可用性）、自動フェイルオーバー、バックアップと復元、Pub/Sub、ソート済みセットが使える。リーダーボード・メッセージング・セッションなどに向く。クラスターモードを有効にするとデータを複数のシャードに分けられる
- 例：ゲームの順位表を、ソート済みセットで計算する

#### Memcached（めむきゃっしゅでぃー / Memcached）

- 意味：ElastiCache で使える、シンプルなインメモリのキーと値のエンジン
- ポイント：できるだけシンプルなモデル、複数のコアやスレッドを持つ大きなノード、ノードの追加・削除によるスケールアウト・インが必要なときに選ぶ。レプリケーションと自動フェイルオーバーはなく、ノードベースのクラスターではバックアップもない
- 例：失っても DB から作り直せる、HTML の断片やオブジェクトのキャッシュ

### 可用性とセキュリティ

#### レプリケーショングループとマルチ AZ（れぷりけーしょんぐるーぷ / Replication group, Multi-AZ）

- 意味：Valkey・Redis OSS で、プライマリとリードレプリカをまとめた構成と、障害のときにレプリカへ自動で切り替える設定
- ポイント：単一ノードのクラスターが止まると、すべてのデータが失われる。マルチ AZ を有効にすると、プライマリの障害でレプリカに自動でフェイルオーバーし、プライマリエンドポイントの DNS も更新されるのでアプリの変更が要らない。複製は非同期なので、少しのデータを失うことがある
- 例：プライマリ 1 台とレプリカ 2 台を別々の AZ に置き、マルチ AZ を有効にする

#### グローバルデータストア（ぐろーばるでーたすとあ / Global Datastore）

- 意味：Valkey・Redis OSS のクラスターを、リージョン間で複製する機能
- ポイント：ほかのリージョンにリードレプリカのクラスターを作り、低いレイテンシーで読める。リージョンの災害対策にも使える。ノードベースのクラスターだけで使える
- 例：東京のセッションのキャッシュを、シンガポールにも複製して読む

#### ElastiCache の認証（にんしょう / RBAC, AUTH）

- 意味：Valkey・Redis OSS で、コマンドを許す前にクライアントにパスワードを求めるしくみ。AUTH（トークン）は、ロールベースのアクセスコントロール（RBAC）に置き換えられた
- ポイント：サーバーレスでは RBAC が必須。RBAC では Secrets Manager でパスワードを自動でローテーションできる。セキュリティグループ（通信の制限）や暗号化とは別の層
- 例：アプリのユーザーには読み取りと書き込み、運用担当には管理のコマンドを許す

### キャッシュ戦略

#### 遅延読み込み（ちえんよみこみ / Lazy loading）

- 意味：必要になったとき（キャッシュミスのとき）だけ、DB から読んだデータをキャッシュに入れる戦略
- ポイント：要求されたデータだけをキャッシュするので、むだがない。ノードが壊れて空になっても、遅くなるだけで動き続ける。欠点は、キャッシュミスのとき 3 回の往復（キャッシュ・DB・キャッシュへの書き込み）がかかることと、DB が変わってもキャッシュが古いままになること
- 例：商品の詳細を、最初に見られたときにキャッシュに入れる

#### 書き込みスルー（かきこみするー / Write-through）

- 意味：DB にデータを書くたびに、キャッシュにも同じデータを書く戦略
- ポイント：キャッシュのデータが古くならない。欠点は、読まれないデータまでキャッシュに入ってむだになることと、新しいノードには DB が更新されるまでデータがないこと。書き込みのたびに 2 回の往復がかかる
- 例：ユーザーのプロフィールを更新したら、キャッシュも同時に更新する

#### キャッシュの TTL（きゃっしゅのてぃーてぃーえる / Time to live for cache keys）

- 意味：キーが期限切れになるまでの秒数を決める値。期限切れのキーは、ないものとして扱われる
- ポイント：遅延読み込みの「古いデータ」と、書き込みスルーの「むだなデータ」を、それぞれの書き込みに TTL を付けて抑える。Valkey・Redis OSS は秒かミリ秒、Memcached は秒で指定する。DynamoDB の TTL（項目を削除する機能）とは別のもの
- 例：株価のキャッシュに 60 秒の TTL を付け、古くても 1 分以内にする

### 16-3 ElastiCache とキャッシュ戦略

#### 問 aws-16-o29

- 問：ElastiCache for Redis OSS のクラスターに、別の AZ のレプリカがある。プライマリのノードが壊れたとき、アプリのエンドポイントを変えずに、自動でレプリカに切り替えたい。最も適した設定はどれか。
