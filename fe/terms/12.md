## 12-1 要件定義


### 要件のまとめ方

#### システム要件定義（System Requirements Definition）

- 意味：システムに求める機能や性能などを決めて文書にすること
- ポイント：利用者の要望を「何を作るか」に落とし込む

#### 機能要件・非機能要件（Functional / Non-functional Requirements）

- 意味：機能要件は「何ができるか」、非機能要件は性能・信頼性・セキュリティ・使いやすさなど「どれくらいうまくできるか」
- 例：応答時間3秒以内は非機能要件

#### ヒアリング（Hearing）

- 意味：利用者に話を聞いて、要望を集めること

#### ユースケース図（Use Case Diagram）

- 意味：利用者（アクタ）とシステムの機能（ユースケース）の関係を表すUMLの図
- ポイント：要件を整理するときに使う


## 12-2 設計

### まとめ表

**モジュールの良し悪し**

| 尺度 | 意味 | 望ましいのは |
| :-: | :-: | :-: |
| 結合度 | モジュールどうしの依存の強さ | 低い（弱い）ほどよい |
| 凝集度 | モジュール内の機能のまとまりの強さ | 高い（強い）ほどよい |


### 設計の手法

#### DFD（でぃーえふでぃー / Data Flow Diagram）

- 意味：データの流れに注目して、処理・データストア・外部実体のつながりを表した図
- ポイント：処理の順序や条件分岐は表さない
- 語の意味：Data＝データ／Flow＝流れ／Diagram＝図

#### E-R図（Entity Relationship Diagram）

- 意味：実体と、実体どうしの関連を表した図
- ポイント：データベースの設計に使う

#### UML（ゆーえむえる / Unified Modeling Language）

- 意味：オブジェクト指向の分析・設計で使う、図の書き方の標準
- ポイント：クラス図・ユースケース図・シーケンス図・アクティビティ図・状態マシン図など
- 語の意味：Unified＝統一された／Modeling＝モデルを描く／Language＝言語

#### クラス図（Class Diagram）

- 意味：クラスの属性・操作と、クラスどうしの関係を表すUMLの図

#### シーケンス図（Sequence Diagram）

- 意味：オブジェクトどうしのメッセージのやり取りを、時間の順に表すUMLの図

#### 状態遷移図（じょうたいせんいず / State Transition Diagram）

- 意味：状態と、状態が変わるきっかけ（イベント）を表した図
- 例：自動販売機の動き

#### 汎化・特化（はんか・とっか / Generalization, Specialization）

- 意味：汎化は複数のクラスの共通点をまとめて上位クラスを作ること、特化はその逆
- ポイント：「is-a」の関係。例: 犬は動物である

#### 集約（しゅうやく / Aggregation）

- 意味：全体と部分の関係
- ポイント：「part-of」の関係。例: 車はエンジンを持つ

#### カプセル化（Encapsulation）

- 意味：データとそれを扱う処理をまとめ、外から中身を直接さわれないようにすること

#### 継承（けいしょう / Inheritance）

- 意味：上位クラスの性質を、下位クラスが引き継ぐこと

#### ポリモーフィズム（多相性 / Polymorphism）

- 意味：同じ命令でも、受け取るオブジェクトによって違う動きをすること

#### モジュール（Module）

- 意味：プログラムを機能ごとに分けた部品

#### モジュール結合度（Module Coupling）

- 意味：モジュールどうしの依存の強さ
- ポイント：弱いほど修正の影響が広がらない。データ結合が最も弱く望ましい

#### モジュール凝集度（Module Cohesion）

- 意味：1つのモジュールの中の機能のまとまりの強さ
- ポイント：強いほどよい。機能的強度が最も強い

#### 構造化設計（Structured Design）

- 意味：システムを機能ごとに上から下へ段階的に分けていく設計
- ポイント：STS分割・TR分割・共通機能分割がある


## 12-3 実装・構築


### プログラムの作成

#### コーディング（Coding）

- 意味：設計をもとにプログラムを書くこと
- ポイント：コーディング規約で書き方をそろえる

#### コードレビュー（Code Review）

- 意味：書いたプログラムをほかの人が読んで、誤りや改善点を見つけること
- ポイント：ウォークスルー・インスペクションなどの方法がある

#### インスペクション（Inspection）

- 意味：進行役（モデレータ）を立てて、決まった手順で成果物を点検するレビュー

#### ウォークスルー（Walkthrough）

- 意味：作成者が中心になり、関係者と一緒に成果物を順にたどって誤りを探すレビュー


## 12-4 統合・テスト

### まとめ表

**テストの種類**

| テスト | 確かめること |
| :-: | :-: |
| 単体テスト | モジュール1つが正しく動くか |
| 結合テスト | モジュールどうしのつながり（データの受け渡し） |
| システムテスト | システム全体が要件どおりか |
| 運用テスト | 実際の業務で使えるか |
| 回帰テスト | 修正でほかの部分がおかしくなっていないか |


### テストの方法

#### ブラックボックステスト（Black Box Test）

- 意味：中の作りを見ずに、入力と出力が仕様どおりかを確かめるテスト
- ポイント：同値分割・限界値分析でテストデータを作る

#### ホワイトボックステスト（White Box Test）

- 意味：プログラムの中の作り（命令や分岐）を見て、通り道を確かめるテスト
- ポイント：命令網羅・判定条件網羅などの基準がある

#### 同値分割（どうちぶんかつ / Equivalence Partitioning）

- 意味：入力を、同じように処理されるグループに分け、各グループから代表の値を選ぶ方法

#### 限界値分析（げんかいちぶんせき / Boundary Value Analysis）

- 意味：グループの境目の値と、その前後の値をテストする方法
- ポイント：境目は間違いが起きやすい

#### 単体テスト（Unit Test）

- 意味：モジュールを1つずつ確かめるテスト

#### 結合テスト（Integration Test）

- 意味：モジュールを組み合わせて、データの受け渡しや呼出しを確かめるテスト
- ポイント：トップダウンテストとボトムアップテストがある

#### スタブ（Stub）

- 意味：トップダウンテストで、まだできていない下位のモジュールの代わりに使う仮のモジュール

#### ドライバ（Driver）

- 意味：ボトムアップテストで、まだできていない上位のモジュールの代わりに使う仮のモジュール

#### リグレッションテスト（回帰テスト / Regression Test）

- 意味：プログラムを直したことで、ほかの部分に新しい不具合が出ていないかを確かめるテスト

#### バグ管理図（信頼度成長曲線 / Reliability Growth Curve）

- 意味：テストの時間と、見つかったバグの累計の関係を表すグラフ
- ポイント：ゴンペルツ曲線のようにS字になり、増え方が落ち着けば品質が安定してきたとみなす


## 12-5 導入・受入れ支援


### 導入と移行

#### 受入れテスト（Acceptance Test）

- 意味：発注者（利用者）が、システムが要件どおりかを確かめて受け入れるテスト

#### 移行（Migration）

- 意味：古いシステムから新しいシステムに切り替えること
- ポイント：一斉移行・段階移行・並行運用などの方式がある

#### 利用者教育（User Training）

- 意味：新しいシステムの使い方を利用者に教えること


## 12-6 保守・廃棄


### 保守

#### ソフトウェア保守（Software Maintenance）

- 意味：運用を始めたソフトウェアを、修正や改良をして使い続けられるようにすること
- ポイント：不具合の修正・環境の変化への対応・機能の改善など

#### リバースエンジニアリング（Reverse Engineering）

- 意味：既にあるプログラムを解析して、仕様や設計を明らかにすること

#### 廃棄（Disposal）

- 意味：使わなくなったシステムを止めて処分すること
- ポイント：データを確実に消去する
