## 02-1 CodeBuild のしくみ

### まとめ表

| フェーズ | すること（例） |
| :-: | :-: |
| install | パッケージのインストール、runtime-versions |
| pre_build | ECR へのサインイン、依存関係のインストール |
| build | コンパイル、テストの実行 |
| post_build | パッケージ化、Docker イメージを ECR にプッシュ |
| （UPLOAD_ARTIFACTS） | build が失敗しても必ず試みる |

### ビルドの部品

#### AWS CodeBuild（こーどびるど / AWS CodeBuild）

- 意味：ソースコードをコンパイルし、単体テストを実行して、デプロイできるアーティファクトを作る、フルマネージドのビルドサービス
- ポイント：ビルドサーバーの用意・パッチ・スケールが要らない。使ったビルドの分数だけ課金。CodePipeline の build・test アクションとしてよく使う

#### ビルドプロジェクト（びるどぷろじぇくと / build project）

- 意味：ソースの取得先・ビルド環境・実行するコマンド・出力の置き場所など、ビルドのやり方をまとめた設定
- ポイント：CodeBuild はビルドプロジェクトからビルド環境（コンテナ）を作り、ソースをダウンロードして buildspec を実行する。ログは CloudWatch Logs に送る

#### buildspec（びるどすぺっく / build specification）

- 意味：ビルドの各フェーズで実行するコマンドや設定を書いた YAML のファイル
- ポイント：既定の名前は buildspec.yml で、ソースのルートに置く。名前や場所は変えられ（buildspec_release.yml など）、S3 にも置ける（ビルドプロジェクトと同じリージョン）。1 つのビルドプロジェクトに指定できる buildspec は 1 つ。主な項目は version・env・phases・reports・artifacts・cache
- 語の意味：buildspec＝build specification（ビルドの仕様）

#### ビルドフェーズ（びるどふぇーず / build phases）

- 意味：buildspec の phases に書く、install・pre_build・build・post_build の 4 つの段階
- ポイント：各フェーズの commands は書いた順に 1 つずつ実行する。on-failure で失敗時の動き（ABORT・CONTINUE・RETRY）を、finally で失敗しても必ず実行するコマンドを書ける。BUILD が失敗しても UPLOAD_ARTIFACTS は必ず試みる

#### ビルド環境（びるどかんきょう / build environment）

- 意味：CodeBuild がビルドを実行する OS・言語のランタイム・ツールの組み合わせ（Docker イメージ）
- ポイント：AWS が用意する標準イメージか、自分のイメージ（ECR など）を使う。コンピューティングは EC2 モード（柔軟。オンデマンドかリザーブドキャパシティ）と Lambda モード（起動が速い）。Docker イメージをビルドするなら特権（権限）モードを有効にする

#### CodeBuild サービスロール（こーどびるどさーびすろーる / CodeBuild service role）

- 意味：CodeBuild がビルドの中でほかの AWS サービス（S3・CloudWatch Logs・ECR・Parameter Store など）を使うための IAM ロール
- ポイント：CodeBuild はすべての操作をこのロールで行う。ユーザーが持つべきでない権限をロールに入れると、意図せず権限を広げてしまう。Parameter Store を読むなら ssm:GetParameters を足す

#### VPC 内のビルド（ぶいぴーしーないのびるど / CodeBuild in a VPC）

- 意味：ビルドプロジェクトに VPC・サブネット・セキュリティグループを設定し、プライベートなリソースにアクセスできるようにすること
- ポイント：ふつう CodeBuild は VPC のリソースにアクセスできない。プライベートサブネットの RDS への統合テスト、社内のアーティファクトリポジトリなどに使う。インターネットに出るにはプライベートサブネットと NAT ゲートウェイが要る。VPC ではローカルキャッシュは使えない

#### キャッシュ（CodeBuild）（きゃっしゅ / build caching）

- 意味：ビルド環境の再利用できる部分を保存し、次のビルドを速くするしくみ
- ポイント：S3 キャッシュ（複数のビルドホストで共有）とローカルキャッシュ（そのビルドホストだけ）の 2 種類。ローカルには、ソース（Git のメタデータ）・Docker レイヤー（Linux・特権モードが必要）・カスタム（buildspec で指定したディレクトリ）の 3 つのモードがある

#### バッチビルド（ばっちびるど / batch builds）

- 意味：1 つのプロジェクトで、同時のビルドや依存関係のあるビルドをまとめて実行する機能
- ポイント：ビルドグラフ（依存関係のチェーン）・ビルドリスト（並列）・ビルドマトリックス（環境の組み合わせ）など。バッチ用のサービスロールが要る

## 02-2 秘密情報と環境変数

### まとめ表

| 書き方 | 値の置き場所 | 向くもの |
| :-: | :-: | :-: |
| env/variables | buildspec に平文 | 秘密でない値（コンソールや CLI で見える） |
| env/parameter-store | SSM Parameter Store | 設定値・SecureString |
| env/secrets-manager | Secrets Manager | DB の認証情報・API キー（自動ローテーション） |
| env/exported-variables | ビルドの中で作った値 | 後ろのパイプラインのステージへ渡す |

### 秘密情報

#### 環境変数の優先順位（CodeBuild）（かんきょうへんすうのゆうせんじゅんい / environment variable precedence）

- 意味：同じ名前の環境変数がいくつかの場所で決められたときに、どの値を使うかの順番
- ポイント：ビルドを始める呼び出し（start-build）の値がいちばん強く、次にビルドプロジェクトの定義、いちばん弱いのが buildspec の値。CODEBUILD_ で始まる名前は予約されているので使わない

#### env/parameter-store（ぱらめーたーすとあ / env/parameter-store）

- 意味：buildspec で、Systems Manager Parameter Store のパラメーターを環境変数として取りこむ書き方
- ポイント：サービスロールに ssm:GetParameters が要る。Parameter Store から取った値はログでマスクされる（ただし値を変換してから表示するとマスクされない）

#### env/secrets-manager（しーくれっつまねーじゃー / env/secrets-manager）

- 意味：buildspec で、Secrets Manager のシークレットを環境変数として取りこむ書き方
- ポイント：「ローカルの変数名: シークレットの ID:JSON のキー:バージョンステージ:バージョン ID」の形。JSON のキーを省くとシークレットの全文、バージョンを省くと AWSCURRENT。ほかのアカウントのシークレットは ARN で指定する
- 例：LOCAL_SECRET_VAR: "TestSecret:MY_SECRET_VAR"

#### exported-variables（えくすぽーとさーどへんすう / exported variables）

- 意味：ビルドの中で作った環境変数を、CodePipeline の後ろのステージに渡すための指定
- ポイント：値は post_build の終わりで固まる。Parameter Store や Secrets Manager のシークレット、AWS_ で始まる変数はエクスポートできない

#### Parameter Store（ぱらめーたーすとあ / AWS Systems Manager Parameter Store）

- 意味：設定データやパスワードなどを名前付きの値（パラメーター）として一元的に保存するサービス
- ポイント：タイプは String・StringList・SecureString（KMS で暗号化）。データベースの認証情報・API キー・トークンなどのシークレットには、自動ローテーションのある Secrets Manager がすすめ

#### AWS Secrets Manager（しーくれっつまねーじゃー / AWS Secrets Manager）

- 意味：DB の認証情報・API キー・OAuth トークンなどのシークレットを、ライフサイクル全体で管理・取得・ローテーションするサービス
- ポイント：コードに認証情報を書かずに済む。自動ローテーションの予定を決められ、長期のシークレットを短期に置きかえて漏れのリスクを下げる

## 02-3 テストの自動化

### まとめ表

| ステージ | 主なテスト |
| :-: | :-: |
| ビルド | ユニットテスト（全体の約 70%）・静的コード分析・コードカバレッジ |
| ステージング | 統合・コンポーネント・システム・パフォーマンス・コンプライアンス・ユーザー受け入れテスト |
| 本番 | 小さな範囲（一部のサーバー・1 リージョン）に出して最終確認 |

### テスト

#### テストのピラミッド（てすとのぴらみっど / test pyramid）

- 意味：速くて安いユニットテストを土台に多く、遅くて高い UI・エンドツーエンドのテストを上に少なく置く、テストの量の考え方
- ポイント：ユニットテストは全体の約 70% が目安。テストはできるだけ早い段階で始める（バグを安く直せる）

#### ユニットテスト（ゆにっとてすと / unit test）

- 意味：コードの小さな部分が期待どおりに動くかを確かめるテスト
- ポイント：ビルドのステージで実行する。いちばん速く安い。CodeBuild のテストレポートとコードカバレッジで結果を見る

#### 静的コード分析（せいてきこーどぶんせき / static code analysis）

- 意味：アプリケーションを実行せずにコードを調べ、誤り・セキュリティホール・規約違反を見つけるテスト
- ポイント：ビルドとユニットテストのあとに行う。セキュリティスキャンもこの段階に入れる

#### 統合テスト（とうごうてすと / integration test）

- 意味：コンポーネントの間のインターフェイスが設計どおりに動くかを確かめるテスト
- ポイント：本番に近いステージング環境で行う。VPC のデータベースを使うなら CodeBuild を VPC で動かす

#### ユーザー受け入れテスト（ゆーざーうけいれてすと / user acceptance test）

- 意味：エンドツーエンドのビジネスの流れが要件を満たすかを、ステージング環境でエンドユーザーが確かめるテスト
- ポイント：アルファテスト・ベータテストなど。パイプラインでは手動承認と組み合わせることが多い

#### パフォーマンステスト（ぱふぉーまんすてすと / performance test）

- 意味：特定の負荷でのシステムの応答の速さと安定性を確かめるテスト
- ポイント：負荷テスト・ストレステストを含み、スケーラビリティ・信頼性・リソースの使い方も見る。本番に近い規模の環境で行う

#### テストレポート（CodeBuild）（てすとれぽーと / test reports）

- 意味：ビルドの中で実行したテストの結果を、CodeBuild のレポートグループにまとめて表示する機能
- ポイント：buildspec の reports に、結果のファイルと形式を書く。形式は JUnit XML（既定）・Cucumber JSON・NUnit・TestNG・Visual Studio TRX など。1 つのプロジェクトにレポートグループは 5 つまで

#### コードカバレッジレポート（こーどかばれっじれぽーと / code coverage report）

- 意味：テストがコードのどれだけを通ったかを示すレポート
- ポイント：ラインカバレッジ（行）とブランチカバレッジ（if・case の分かれ道）。形式は JaCoCo XML・SimpleCov JSON・Clover XML・Cobertura XML・LCOV INFO

#### ウェブフックのフィルターグループ（うぇぶふっくのふぃるたーぐるーぷ / webhook filter groups）

- 意味：GitHub などのどのイベントで CodeBuild のビルドを始めるかを決める条件の組
- ポイント：イベントは PUSH・PULL_REQUEST_CREATED・PULL_REQUEST_UPDATED・PULL_REQUEST_MERGED など。グループの中のフィルターは全部が真のとき、グループどうしはどれか 1 つが真のときにビルドする。PR を作ったときにテストを回すのに使う

### 02-1 CodeBuild のしくみ

#### 問 dop-02-o01

- 問：自前のビルドサーバーを管理せずに、ソースコードのコンパイルと単体テストを行い、デプロイできるアーティファクトを作りたい。使うサービスはどれか。
- ア：AWS CodeBuild
- イ：AWS CodeDeploy
- ウ：AWS CodeArtifact
- エ：Amazon CodeGuru Profiler
- 正解：ア
- 解説：CodeBuild はフルマネージドのビルドサービスで、ソースのコンパイル、単体テストの実行、アーティファクトの作成を行う。ビルドサーバーの用意・パッチ・スケールが要らない。
- アの意味：正しい。
- イの意味：デプロイのサービス。
- ウの意味：パッケージのリポジトリ。
- エの意味：実行中のアプリのプロファイリング。
- 出典：オリジナル問題（根拠：AWS「AWS CodeBuild ユーザーガイド」とは AWS CodeBuild（『AWS CodeBuild は、クラウド内のフルマネージド型のビルドサービスです。CodeBuild はソースコードをコンパイルし、単体テストを実行して、すぐにデプロイできるアーティファクトを生成します。』））

#### 問 dop-02-o02

- 問：同じリポジトリで、デバッグ用とリリース用に別々のビルド手順を使いたい。buildspec についての説明として正しいものはどれか。
- ア：buildspec.yml という名前でルートに置くしかない
- イ：buildspec_debug.yml・buildspec_release.yml のように名前を変え、プロジェクトごとに指定できる（1 つのプロジェクトには 1 つ）
- ウ：1 つのプロジェクトに複数の buildspec を同時に指定できる
- エ：buildspec は S3 には置けない
- 正解：イ
- 解説：既定は buildspec.yml でソースのルートだが、名前や場所は変えられ、S3（プロジェクトと同じリージョン）にも置ける。ただし 1 つのビルドプロジェクトに指定できる buildspec は 1 つ。
- アの意味：変えられる。
- イの意味：正しい。
- ウの意味：1 つだけ。
- エの意味：置ける。
- 出典：オリジナル問題（根拠：AWS「AWS CodeBuild ユーザーガイド」CodeBuild のビルド仕様に関するリファレンス（『デフォルトの buildspec ファイルの名前は buildspec.yml で、ソースディレクトリのルートに配置する必要があります。』『buildspec ファイルの名前に関係なく、ビルドプロジェクトには 1 つの buildspec しか指定できません。』））

#### 問 dop-02-o03

- 問：buildspec で、Amazon ECR へのサインインに向いているフェーズはどれか。
- ア：install
- イ：build
- ウ：pre_build
- エ：post_build
- 正解：ウ
- 解説：pre_build はビルドの前のコマンドで、ECR へのサインインや依存関係のインストールの例が挙がっている。install はパッケージのインストール用、post_build はパッケージ化やイメージのプッシュ。
- アの意味：パッケージのインストールに使う。
- イの意味：コンパイルやテストに使う。
- ウの意味：正しい。
- エの意味：ECR へのプッシュやパッケージ化に使う。
- 出典：オリジナル問題（根拠：AWS「AWS CodeBuild ユーザーガイド」CodeBuild のビルド仕様に関するリファレンス（『たとえば、このフェーズを使用して Amazon ECR にサインインするか、npm の依存関係をインストールすることができます。』））

#### 問 dop-02-o04

- 問：テストのコマンドが失敗しても、後片づけのコマンドは必ず実行したい。buildspec で使うものはどれか。
- ア：on-failure: ABORT
- イ：exported-variables
- ウ：run-as
- エ：finally ブロック
- 正解：エ
- 解説：finally ブロックのコマンドは、commands ブロックのあとに実行され、commands が失敗しても実行される。
- アの意味：ビルドを中止する。
- イの意味：変数を後ろのステージに渡す。
- ウの意味：コマンドを実行する Linux ユーザーを決める。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「AWS CodeBuild ユーザーガイド」CodeBuild のビルド仕様に関するリファレンス（『finally ブロックに指定したコマンドは、commands ブロックのコマンドが失敗した場合でも実行されます。』））

#### 問 dop-02-o05

- 問：外部の依存先への接続が一時的に失敗することがある。失敗したフェーズを自動で最大 3 回やり直したい。on-failure に書く値はどれか。
- ア：RETRY
- イ：CONTINUE
- ウ：ABORT
- エ：SKIP
- 正解：ア
- 解説：on-failure: RETRY は最大 3 回やり直す。RETRY-count で回数、RETRY-regex でエラーメッセージの条件も付けられる。CONTINUE は次のフェーズに進み、ABORT は中止する。
- アの意味：正しい。
- イの意味：次のフェーズに進む。
- ウの意味：ビルドを中止する。
- エの意味：そういう値はない。
- 出典：オリジナル問題（根拠：AWS「AWS CodeBuild ユーザーガイド」CodeBuild のビルド仕様に関するリファレンス（『RETRY - 正規表現 .* に一致するエラーメッセージを表示し、ビルドを最大 3 回再試行します。』））

#### 問 dop-02-o06

- 問：build フェーズが失敗した。CodeBuild のアーティファクトのアップロード（UPLOAD_ARTIFACTS）はどうなるか。
- ア：とばされる
- イ：ビルドを手で再実行するまで待つ
- ウ：BUILD が失敗しても必ず試みられる
- エ：アーティファクトは削除される
- 正解：ウ
- 解説：UPLOAD_ARTIFACTS フェーズは、BUILD フェーズが失敗しても必ず試みられる（ログや途中の結果を回収できる）。
- アの意味：試みられる。
- イの意味：待たない。
- ウの意味：正しい。
- エの意味：削除しない。
- 出典：オリジナル問題（根拠：AWS「AWS CodeBuild ユーザーガイド」ビルドフェーズの移行（『UPLOAD_ARTIFACTS フェーズは、BUILD フェーズが失敗した場合でも必ず試行されます。』））

#### 問 dop-02-o07

- 問：CodeBuild でプライベートサブネットの RDS に対して統合テストを行いたい。必要な設定はどれか。
- ア：RDS をパブリックにする
- イ：ビルドプロジェクトに VPC ID・サブネット・セキュリティグループを設定する
- ウ：CodeBuild のリージョンを変える
