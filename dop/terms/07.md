## 07-1 AWS CDK

### まとめ表

| コマンド | すること |
| :-: | :-: |
| cdk bootstrap | 環境（アカウント×リージョン）に S3・ECR・IAM ロールを用意 |
| cdk synth | アプリから CloudFormation テンプレート（cdk.out）を作る |
| cdk diff | デプロイ済みのスタックとの差を見る |
| cdk deploy | CloudFormation でデプロイ（--hotswap は開発用） |

### CDK の部品

#### AWS CDK（しーでぃーけー / AWS Cloud Development Kit）

- 意味：TypeScript・Python・Java などのプログラミング言語でインフラを定義し、CloudFormation でプロビジョニングするオープンソースのフレームワーク
- ポイント：最後は CloudFormation のテンプレートになってデプロイされる（ドリフト・ロールバックなどは CloudFormation と同じ）。ループや関数、型のチェック、単体テストが使える

#### コンストラクト（こんすとらくと / construct）

- 意味：CDK のアプリを組み立てる部品。1 つのリソースから、複数のリソースのまとまりまでを表す
- ポイント：L1（CFN リソース。CloudFormation のリソースそのまま、Cfn から始まる名前）、L2（よく使う。よい既定値・最小権限のポリシーを作るメソッド）、L3（パターン。複数リソースでユースケース全体を作る）の 3 レベル
- 例：L1＝CfnBucket、L2＝s3.Bucket、L3＝ecs_patterns.ApplicationLoadBalancedFargateService

#### スタックとアプリ（CDK）（すたっくとあぷり / stack・app）

- 意味：アプリは CDK のプロジェクト全体、スタックは CloudFormation のスタック 1 つにあたる単位
- ポイント：1 つのアプリに複数のスタックを書ける。環境（アカウントとリージョン）をスタックごとに指定する

#### ブートストラップ（ぶーとすとらっぷ / bootstrapping）

- 意味：CDK でデプロイする前に、環境（アカウント×リージョン）に CDK が使うリソースを用意する作業（cdk bootstrap）
- ポイント：CDKToolkit スタックが、アセット用の S3 バケット、Docker イメージ用の ECR リポジトリ、デプロイ用の IAM ロールを作る。デプロイ先の環境ごとに 1 回。CDK Pipelines で別アカウントに出すときは --trust で信頼するアカウントを指定する

#### アセット（あせっと / assets）

- 意味：CDK アプリに含めるローカルのファイル・ディレクトリ・Docker イメージ（Lambda のコード、コンテナのビルド用のディレクトリなど）
- ポイント：デプロイのときに、ブートストラップで作った S3 バケットや ECR リポジトリに自動でアップロードされる

#### コンテキスト（こんてきすと / context）

- 意味：CDK アプリに渡すキーと値。cdk.json・cdk.context.json・コマンドラインで渡す
- ポイント：合成のときに AWS アカウントから取った値（AZ の一覧・AMI の検索結果など）を cdk.context.json にキャッシュし、新しい値を受け入れるまで固定する。cdk.context.json はリポジトリにコミットして、ビルドを同じ結果にする

#### アスペクト（あすぺくと / aspects）

- 意味：あるスコープの中のすべてのコンストラクトに、まとめて操作（確認や変更）をかける仕組み
- ポイント：全リソースにタグを付ける、暗号化されていないバケットがあればエラーにする、などに使う。cdk-nag もアスペクトでルールを調べる

#### きめ細かなアサーションとスナップショットテスト（あさーしょん / fine-grained assertions・snapshot tests）

- 意味：CDK の assertions モジュールで、合成したテンプレートを調べるテスト。アサーションは特定のリソースのプロパティを、スナップショットは前に保存したテンプレート全体と比べる
- ポイント：アサーションが最もよく使う。スナップショットはリファクタリングで中身が変わっていないことを確かめるのに向く。Jest や pytest で動かす

#### cdk diff・cdk synth（しーでぃーけーでぃふ・しんせ / cdk diff・cdk synth）

- 意味：cdk synth はアプリから CloudFormation のテンプレート（クラウドアセンブリ、cdk.out）を作る。cdk diff は、デプロイ済みのスタックとの差を出す
- ポイント：パイプラインでは synth の結果をアーティファクトにする。diff でセキュリティに関わる変更（IAM・SG）を確かめる

#### ホットスワップデプロイ（ほっとすわっぷ / hotswap deployment）

- 意味：cdk deploy --hotswap で、Lambda のコードなどを CloudFormation を通さず直接更新して、デプロイを速くするオプション
- ポイント：スタックにわざとドリフトを生むので、本番では使わない。ホットスワップできない変更は無視される。開発中は cdk watch と組み合わせる

#### CDK Pipelines（しーでぃーけーぱいぷらいんず / CDK Pipelines）

- 意味：CDK アプリを CodePipeline で継続的にデプロイするための、CDK の高レベルのコンストラクト
- ポイント：自動更新（セルフミューテーション）。パイプラインの定義を変えたりステージやスタックを足したりすると、パイプラインが自分を作り直してから新しいものをデプロイする。ステージ（関連するスタックのまとまり）を別のアカウント・リージョンに出す。前後に承認やテストのステップを入れる

## 07-2 AWS SAM CLI

### まとめ表

| コマンド | すること | 使う場面 |
| :-: | :-: | :-: |
| sam build | .aws-sam に依存関係を入れてまとめる | すべての前 |
| sam local invoke／start-api | Docker で関数・API を手元で動かす | 手元のテスト |
| sam deploy --guided | 設定を聞いて samconfig.toml に保存し、変更セットでデプロイ | 初回・本番 |
| sam sync --watch | 変更をすぐにクラウドへ同期 | 開発環境だけ |

### SAM CLI のコマンド

#### sam build（さむびるど / sam build）

- 意味：サーバーレスのアプリを、ローカルのテストやデプロイに向けて準備する SAM CLI のコマンド
- ポイント：.aws-sam ディレクトリに、sam local や sam deploy が必要とする形でアプリをまとめる。--use-container でコンテナの中でビルドできる

#### sam local（さむろーかる / sam local）

- 意味：Lambda 関数や API Gateway を、Docker を使って手元で動かしてテストする SAM CLI のコマンド
- ポイント：sam local invoke（関数を 1 回呼ぶ）、sam local start-api（API をローカルで立てる）、sam local generate-event（テスト用のイベントを作る）

#### sam deploy（さむでぷろい / sam deploy）

- 意味：SAM のアプリを CloudFormation のスタックとしてデプロイする SAM CLI のコマンド
- ポイント：初回は --guided で、スタック名・リージョンなどを聞かれ、答えが samconfig.toml に保存される。内部で変更セットを作って実行する

#### sam sync（さむしんく / sam sync）

- 意味：ローカルの変更を AWS クラウドにすばやく同期する SAM CLI のコマンド（--watch で変更を見張る）
- ポイント：開発環境向け。本番は sam deploy か CI/CD パイプラインを使う。コードだけの変更は CloudFormation を通さずに直接更新する

## 07-3 AWS Service Catalog

### まとめ表

| 部品 | 役目 |
| :-: | :-: |
| 製品 | CloudFormation テンプレート（や Terraform）で作る IT サービス。バージョンがある |
| ポートフォリオ | 製品の集まり。だれが使えるかを決める |
| 起動制約 | 製品を起動するときに Service Catalog が引き受ける IAM ロール |
| テンプレート制約 | パラメータ（インスタンスタイプなど）の選択肢を絞る |
| TagOption | 起動した製品に付けるタグのひな形 |

### カタログの部品

#### AWS Service Catalog（さーびすかたろぐ / AWS Service Catalog）

- 意味：組織が承認した IT サービス（CloudFormation テンプレートなど）のカタログを作って管理し、利用者がセルフサービスで起動できるようにするサービス
- ポイント：利用者は、組織が決めた制約の中で、承認済みのものだけをすばやく作れる。管理者はテンプレート・制約・IAM ロールを用意する。「開発者に広い権限を渡さずに、決まった構成だけを作らせたい」がキーワード

#### 製品とポートフォリオ（せいひんとぽーとふぉりお / product・portfolio）

- 意味：製品は AWS にデプロイできる IT サービス（1 つ以上のリソース）、ポートフォリオは製品の集まりで、だれがどの製品をどう使えるかを決める
- ポイント：ポートフォリオに IAM のユーザー・グループ・ロールを付けて使わせる。製品にはバージョンがあり、新しいバージョンを足して配る

#### プロビジョニングされた製品（ぷろびじょにんぐされたせいひん / provisioned product）

- 意味：利用者が製品を起動してできたもの。CloudFormation の製品ならスタック
- ポイント：利用者は新しいバージョンに更新したり、終了（削除）したりできる

#### 起動制約（きどうせいやく / launch constraint）

- 意味：利用者が製品を起動・更新・終了するときに、Service Catalog が引き受ける IAM ロールを決める制約
- ポイント：利用者本人には製品のリソースを作る権限がなくても、起動ロールの権限で作れる。利用者の権限を最小限にできる。ポートフォリオの中の製品（製品とポートフォリオの組）ごとに付ける

#### テンプレート制約（てんぷれーとせいやく / template constraint）

- 意味：利用者が製品を起動するときに選べるパラメータの値を絞る制約（ルールで書く）
- ポイント：例 インスタンスタイプは t3.micro・t3.small だけ、本番の環境では暗号化を必須に。組織のコンプライアンスを守らせる

#### ポートフォリオの共有（ぽーとふぉりおのきょうゆう / portfolio sharing）

- 意味：ポートフォリオを別のアカウントや組織（AWS Organizations）に共有し、相手の管理者がインポートして自分の利用者に配れるようにする機能
- ポイント：共有されたものは元と同期した参照（リファレンス）。Organizations の共有なら OU 単位で配れる。StackSets で各アカウントにカタログを配る方法もある

#### TagOption（たぐおぷしょん / TagOption）

- 意味：Service Catalog で管理するキーと値の組。起動した製品に付ける AWS のタグのひな形
- ポイント：TagOption をポートフォリオや製品に付けると、起動時にそのタグが付く（選択肢から選ばせる）。コスト配分のタグをそろえるのに使う

- イ：CodeCommit のリポジトリ
- ウ：CloudFormation のテンプレートの中に直接
- エ：EC2 のインスタンスストア
- 正解：ア
- 解説：ローカルのファイルやディレクトリはアセットとして、ブートストラップで作った S3 バケットにアップロードされる（Docker イメージは ECR）。
- アの意味：正しい。
- イの意味：ソースの置き場所で、デプロイの成果物の置き場所ではない。
- ウの意味：テンプレートには S3 の場所が書かれる。
- エの意味：関係ない。
- 出典：オリジナル問題（根拠：AWS「AWS Cloud Development Kit (AWS CDK) v2 デベロッパーガイド」AWS CDK ブートストラップ（『Amazon Simple Storage Service (Amazon S3) バケット – AWS Lambda 関数コードやアセットなどの CDK プロジェクトファイルを保存するために使用します。』））

- 問：CDK Pipelines で、スタック間に依存関係があるとき、パイプラインへの追加の順番はどうなるか。
- ア：アルファベット順に追加される
- イ：依存関係に合わせて、正しい順番で自動で追加される
- ウ：手で順番を書かないとエラーになる
- エ：すべて同時にデプロイされる
- 正解：イ
- 解説：スタック間に依存関係がある場合、スタックは正しい順番でパイプラインに自動で追加される。
- アの意味：誤り。
- イの意味：正しい。
- ウの意味：誤り。
- エの意味：依存関係があるものは順に出る。
- 出典：オリジナル問題（根拠：AWS「AWS Cloud Development Kit (AWS CDK) v2 デベロッパーガイド」CDK Pipelines を使用した継続的インテグレーションと継続的デリバリー (CI/CD)（『スタック間に依存関係がある場合、スタックはパイプラインに自動的に正しい順序で追加されます。』））

#### 問 dop-07-o30

- 問：CDK の L1・L2・L3 のうち、最も抽象化が低く、CloudFormation のリソースにそのまま対応するものはどれか。
- ア：L3（パターン）
- イ：L2（キュレーションされたコンストラクト）
- ウ：アスペクト
- エ：L1（CFN リソース）
- 正解：エ
- 解説：L1 コンストラクトは CFN リソースとも呼ばれ、最も低いレベルで抽象化をしない。
- アの意味：最も高い。
- イの意味：中間。
- ウの意味：コンストラクトのレベルではない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「AWS Cloud Development Kit (AWS CDK) v2 デベロッパーガイド」AWS CDK コンストラクト（『L1 コンストラクトは、CFN リソース とも呼ばれ、最下位のコンストラクトであり、抽象化は行いません。』））
