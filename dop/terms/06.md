## 06-1 スタックの更新と保護

### まとめ表

| 守りたいもの | 使う機能 |
| :-: | :-: |
| 更新でなにが置き換わるか先に知りたい | 変更セット |
| 手作業で変えられていないか知りたい | ドリフト検出 |
| 本番 DB を更新・置換させたくない | スタックポリシー |
| スタックごと消されたくない | 削除保護（終了保護） |
| スタックを消してもデータを残したい | DeletionPolicy: Retain／Snapshot |
| 置換で古いリソースを残したい | UpdateReplacePolicy |
| 更新後にアラームが鳴ったら戻したい | ロールバックトリガー |

### 更新の前と後

#### 変更セット（へんこうせっと / change set）

- 意味：スタックの更新を実行する前に、どのリソースが追加・変更・置換・削除されるかを確かめるための、変更の案
- ポイント：確かめてから実行（execute）する。置換（Replacement: True）が出たら、データが消えないか確かめる。変更セットはスタックの更新の成功を保証しない（実行して失敗することもある）。パイプラインでは「変更セットを作る → 承認 → 実行する」の流れが定番

#### ドリフト検出（どりふとけんしゅつ / drift detection）

- 意味：スタックのリソースが、CloudFormation の外（コンソールや CLI）で変えられて、テンプレートの定義とずれていないかを調べる機能
- ポイント：結果は IN_SYNC・MODIFIED・DELETED・NOT_CHECKED など。ドリフトを見つけるだけで、直しはしない。AWS Config のマネージドルール（cloudformation-stack-drift-detection-check）で定期的に調べられる

#### ロールバックトリガー（ろーるばっくとりがー / rollback triggers）

- 意味：スタックの作成・更新中と、その後のモニタリング時間のあいだ、指定した CloudWatch アラームを見て、ALARM になったらスタックの操作全体をロールバックする設定
- ポイント：モニタリング時間は 0（既定）〜180 分。デプロイ直後のエラー率の上昇などで自動で戻せる

#### 更新のロールバックを続ける（こうしんのろーるばっくをつづける / continue update rollback）

- 意味：更新のロールバックが失敗して UPDATE_ROLLBACK_FAILED になったスタックを、UPDATE_ROLLBACK_COMPLETE に戻す操作
- ポイント：UPDATE_ROLLBACK_FAILED のスタックは更新できない。手で原因を直すか、ロールバックに失敗したリソースをスキップして続ける

#### リソースのインポート（りそーすのいんぽーと / resource import）

- 意味：CloudFormation の外で作った既存のリソースを、作り直さずにスタックの管理下に入れる機能
- ポイント：テンプレートにリソースを書き、識別子（バケット名など）を指定して取り込む。取り込むリソースには DeletionPolicy を書く

### 消さない・変えさせない

#### スタックポリシー（すたっくぽりしー / stack policy）

- 意味：スタックの更新のときに、どのリソースを更新してよいかを決める JSON のポリシー
- ポイント：設定すると、既定ですべてのリソースが守られ、Allow を書いたものだけ更新できる。更新のときだけ効き、IAM のようなアクセス制御ではない（失敗を防ぐ安全装置）。守られたリソースを更新するときは、その更新でだけ使う一時ポリシーで上書きする

#### 削除保護（さくじょほご / termination protection）

- 意味：スタックが誤って削除されないようにする設定（終了保護とも呼ぶ）
- ポイント：有効だと削除は失敗し、スタックは変わらない。ネストされたスタックは親（ルート）の設定に従う。リソース単位で残すのは DeletionPolicy

#### DeletionPolicy（でりーしょんぽりしー / DeletionPolicy attribute）

- 意味：スタックを削除したとき（やテンプレートからリソースを消して更新したとき）に、そのリソースを消すか、残すか、スナップショットを取ってから消すかを決める属性
- ポイント：Delete（既定）・Retain（残す。どのリソースにも使える）・Snapshot（EBS ボリューム・RDS など、スナップショットに対応するもの）・RetainExceptOnCreate。RDS の DBCluster などは既定が Snapshot
- 例：`DeletionPolicy: Snapshot` を本番の RDS に付ける

#### UpdateReplacePolicy（あっぷでーとりぷれいすぽりしー / UpdateReplacePolicy attribute）

- 意味：スタックの更新でリソースが置換されるときに、古い物理リソースを消すか、残すか、スナップショットを取るかを決める属性
- ポイント：置換では新しいリソースを先に作り、参照を付け替えてから古いものを消す（既定）。DeletionPolicy は削除のとき、UpdateReplacePolicy は置換のとき。両方を付けておくと安全

## 06-2 EC2 と Auto Scaling の構成

### まとめ表

| ヘルパースクリプト | すること |
| :-: | :-: |
| cfn-init | AWS::CloudFormation::Init のメタデータを読み、パッケージ・ファイル・サービスを設定 |
| cfn-signal | CreationPolicy や WaitCondition に成功・失敗のシグナルを送る |
| cfn-get-metadata | メタデータを取り出す |
| cfn-hup | メタデータの変更を見つけて、フック（cfn-init の再実行など）を動かす |

### ヘルパースクリプトと待ち合わせ

#### cfn-init（しーえふえぬいにっと / cfn-init）

- 意味：リソースのメタデータ（AWS::CloudFormation::Init）を読み、パッケージのインストール・ファイルの作成・サービスの起動を行うヘルパースクリプト
- ポイント：UserData に長いシェルを書くより、宣言的に書ける。configSets で順番を決められる

#### cfn-signal（しーえふえぬしぐなる / cfn-signal）

- 意味：インスタンスの準備ができたことを、CreationPolicy や WaitCondition に知らせるヘルパースクリプト
- ポイント：cfn-init の終了コードを渡して「成功／失敗」を送るのが定番。シグナルが来ないとタイムアウトで失敗し、ロールバックする

#### cfn-hup（しーえふえぬはっぷ / cfn-hup）

- 意味：メタデータの更新を見張り、変更が見つかったらフック（設定したコマンド）を動かすデーモン
- ポイント：スタックの更新でメタデータだけを変えたとき、インスタンスを作り直さずに設定を入れ直せる（cfn-init を再実行するフックを書く）

#### CreationPolicy（くりえいしょんぽりしー / CreationPolicy attribute）

- 意味：指定した数の成功シグナルが来るか、タイムアウトするまで、リソースの作成を完了にしない属性
- ポイント：EC2 インスタンス・Auto Scaling グループなどに付ける。Count（シグナルの数）と Timeout（例 PT15M）。アプリが本当に動いてから次のリソースに進める

#### 待機条件（たいきじょうけん / wait condition）

- 意味：AWS::CloudFormation::WaitCondition と WaitConditionHandle で、決まった数の成功シグナルが来るまでスタックの作成を待たせる仕組み
- ポイント：EC2・Auto Scaling には CreationPolicy がすすめられる。外部の処理の完了を待つときなどに WaitCondition を使う

#### UpdatePolicy（あっぷでーとぽりしー / UpdatePolicy attribute）

- 意味：スタックの更新で、Auto Scaling グループなどの特定のリソースをどう更新するかを決める属性
- ポイント：AutoScalingRollingUpdate＝インスタンスをバッチごとに入れ替え（MinInstancesInService・MaxBatchSize・PauseTime・WaitOnResourceSignals）。AutoScalingReplacingUpdate（WillReplace: true）＝Auto Scaling グループごと新しく作って置き換え（イミュータブル。CreationPolicy と組み合わせる）。起動テンプレートの AMI を変えたときの動きを決める

## 06-3 再利用・大規模化・ガバナンス

### まとめ表

| したいこと | 使う機能 |
| :-: | :-: |
| 多くのアカウント・リージョンに同じスタック | StackSets |
| 共通部品（VPC・ALB）を分けて使い回す | ネストされたスタック／モジュール |
| 別のスタックの値（サブネット ID）を使う | Outputs の Export と Fn::ImportValue |
| パスワードをテンプレートに書かない | 動的参照（ssm・ssm-secure・secretsmanager） |
| CloudFormation にない処理をしたい | カスタムリソース（Lambda・SNS） |
| テンプレートを前処理で書き換えたい | マクロ（Transform） |
| 作る前にルールに合うか止めたい | CloudFormation フック／CloudFormation Guard |

### 大規模なデプロイ

#### StackSets（すたっくせっつ / CloudFormation StackSets）

- 意味：1 つのテンプレートから、複数のアカウントとリージョンにスタック（スタックインスタンス）を 1 回の操作で作成・更新・削除する機能
- ポイント：管理者アカウントで StackSet を作り、ターゲットアカウントに出す。リージョンの順番・同時に出すアカウントの数（最大同時アカウント数）・失敗許容数を決める。組織全体のガードレール（Config ルール・IAM ロール・CloudTrail）を配るのによく使う

#### サービスマネージド型のアクセス許可（さーびすまねーじどがた / service-managed permissions）

- 意味：StackSets が AWS Organizations と連携し、必要な IAM ロールを AWS が作って管理するアクセス許可のモデル
- ポイント：組織の管理アカウントか委任管理者から使う。OU を指定して出し、組織に新しく加わったアカウントへの自動デプロイができる。セルフマネージド型は、管理者アカウントに AWSCloudFormationStackSetAdministrationRole、各ターゲットアカウントに AWSCloudFormationStackSetExecutionRole を自分で作る

#### ネストされたスタック（ねすとされたすたっく / nested stacks）

- 意味：AWS::CloudFormation::Stack リソースで別のテンプレートを呼び出し、スタックの中に作るスタック
- ポイント：共通の部品（ALB の設定など）を 1 つのテンプレートにして使い回す。親スタックから一緒に更新される。親子の間はパラメータと出力（GetAtt Outputs.名前）で値を渡す

#### エクスポートと ImportValue（えくすぽーと / Export・Fn::ImportValue）

- 意味：あるスタックの Outputs で Export した値を、同じアカウント・同じリージョンの別のスタックが Fn::ImportValue で使う仕組み
- ポイント：インポートされているあいだは、エクスポートした値を変更・削除できない（エクスポート元のスタックも消せない）。ライフサイクルが違うスタック（ネットワークとアプリ）の間で使う。同じライフサイクルならネストされたスタック

### テンプレートを広げる・守る

#### 動的参照（どうてきさんしょう / dynamic references）

- 意味：テンプレートに `{{resolve:サービス:参照}}` と書き、Parameter Store や Secrets Manager にある値をスタックの操作時に取り出す仕組み
- ポイント：resolve:ssm（平文の String）、resolve:ssm-secure（SecureString。使えるリソースのプロパティが限られる）、resolve:secretsmanager（シークレット）。秘密をテンプレートやパラメータに書かずに済む
- 例：`MasterUserPassword: '{{resolve:secretsmanager:prod/db:SecretString:password}}'`

#### カスタムリソース（かすたむりそーす / custom resources）

- 意味：CloudFormation にないプロビジョニングの処理を、Lambda 関数や SNS トピックで動かすリソース（AWS::CloudFormation::CustomResource や Custom::名前）
- ポイント：ServiceToken に Lambda 関数か SNS トピックの ARN を書く（スタックと同じリージョン）。作成・更新・削除のリクエストに、関数が事前署名 URL へ SUCCESS／FAILED を返す。返さないとスタックが長く止まる
- 例：AMI の ID を調べる、S3 バケットを削除前に空にする、外部の SaaS に登録する

#### マクロ（まくろ / macros・Transform）

- 意味：テンプレートを CloudFormation が処理する前に、Lambda 関数で書き換える仕組み。Transform で呼ぶ
- ポイント：AWS がホストする AWS::Serverless（SAM の構文を展開）と AWS::Include（S3 のスニペットを差し込む）がある。マクロを使うテンプレートは変更セットを作ってからデプロイする

#### CloudFormation フック（ふっく / CloudFormation Hooks）

- 意味：リソース・スタック・変更セットを作る前に、その設定が組織のセキュリティ・運用・コストのルールに合うかを調べ、合わなければ止めたり警告したりする機能
- ポイント：プロビジョニングの前に先回りして調べる（予防）。Guard のルールや Lambda で書ける。作った後に調べるのは AWS Config（発見）

#### CloudFormation Guard（がーど / AWS CloudFormation Guard）

- 意味：テンプレートなどの JSON・YAML がルールに合うかを調べる、オープンソースのポリシーアズコードのツール（cfn-guard）
- ポイント：宣言的な DSL でルールを書き、ルールのユニットテストもできる。CodeBuild でテンプレートを検査し、違反があればパイプラインを止める。cfn-lint はテンプレートの文法やプロパティの誤りを調べるツール

## 問題演習

### 06-1

#### 問 dop-06-o01

- 問：本番の CloudFormation スタックを更新する前に、RDS インスタンスが置換されないかを確かめたい。どうするか。
- ア：ドリフト検出を実行する
- イ：スタックポリシーを設定する
- ウ：スタックを削除して作り直す
- エ：変更セットを作り、各リソースの変更内容（置換の有無）を確かめてから実行する
- 正解：エ
- 解説：変更セットで、提案した変更が動いているリソースにどう影響するかを、実行の前に確かめられる。置換（Replacement）が出たら止められる。
- アの意味：テンプレートの外で変えられたかを調べるもので、これからの更新の影響は分からない。
- イの意味：更新を防げるが、影響を確かめる仕組みではない。
- ウの意味：データが消え、目的に反する。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「AWS CloudFormation ユーザーガイド」変更セットを使用して CloudFormation スタックを更新する（『変更セットは、スタックに対して提案された変更が実行中のリソースにおよぼす影響を事前に確認できるようにします。』））

#### 問 dop-06-o02

- 問：運用担当がコンソールで、CloudFormation が作ったセキュリティグループのルールを手で変えたらしい。テンプレートとのずれを見つけたい。何を使うか。
- ア：ドリフト検出
- イ：変更セット
- ウ：ロールバックトリガー
- エ：スタックポリシー
- 正解：ア
- 解説：ドリフト検出で、CloudFormation の外で設定を変えられたスタックのリソースを見つけられる。
- アの意味：正しい。
- イの意味：これから行う更新の影響を確かめるもの。
- ウの意味：更新中・後のアラームで戻すもの。
- エの意味：更新を防ぐもので、外での変更は見つけられない。
- 出典：オリジナル問題（根拠：AWS「AWS CloudFormation ユーザーガイド」ドリフト検出を使用してスタックとリソースへのアンマネージド型設定変更を検出する（『ドリフト検出を使用して、CloudFormation 管理外で構成変更がされたスタックリソースを識別できます。』））

#### 問 dop-06-o03

- 問：スタックの更新のとき、本番のデータベースだけは誤って更新・置換されないようにしたい。ほかのリソースは更新してよい。何を使うか。
- ア：IAM ポリシーで cloudformation:UpdateStack を拒否する
- イ：DeletionPolicy: Retain
- ウ：スタックポリシーで、データベースの Update:* を Deny し、他を Allow する
- エ：削除保護
- 正解：ウ
- 解説：スタックポリシーで、更新のときにどのリソースを更新してよいかを決める。設定すると既定ですべてが守られ、Allow を書いたものだけ更新できる。Deny は常に優先される。
- アの意味：スタック全体を更新できなくなる。
- イの意味：削除のときに残すもので、更新・置換は防げない。
- ウの意味：正しい。
- エの意味：スタックの削除を防ぐもので、更新は防げない。
- 出典：オリジナル問題（根拠：AWS「AWS CloudFormation ユーザーガイド」スタックのリソースが更新されないようにする（『スタックポリシーを設定すると、デフォルトでスタック内のすべてのリソースが保護されます。』））

#### 問 dop-06-o04

- 問：スタックポリシーで守っているデータベースを、計画したメンテナンスで 1 回だけ更新したい。どうするか。
- ア：スタックポリシーを削除する
- イ：スタックを更新するときに、その更新でだけ使う一時ポリシー（オーバーライドポリシー）を指定する
- ウ：データベースを手で変えて、ドリフトを無視する
- エ：IAM ユーザーに AdministratorAccess を付ける
- 正解：イ
- 解説：守られたリソースを更新するには、スタックポリシーを上書きする一時ポリシーを作り、スタックの更新のときに指定する。
- アの意味：一度付けたスタックポリシーは消せず、守りもなくなる。
- イの意味：正しい。
- ウの意味：ドリフトを生み、テンプレートと合わなくなる。
- エの意味：スタックポリシーは IAM の権限と関係なく効く。
- 出典：オリジナル問題（根拠：AWS「AWS CloudFormation ユーザーガイド」スタックのリソースが更新されないようにする（『保護されたリソースを更新するには、スタックポリシーをオーバーライドする一時ポリシーを作成し、それらのリソースでの更新を許可します。』））

#### 問 dop-06-o05

- 問：本番のスタックそのものを誤って削除されないようにしたい。何を有効にするか。
- ア：スタックの削除保護（終了保護）
- イ：スタックポリシー
- ウ：ロールバックトリガー
