## 01-1 CI/CD の考え方

### まとめ表

| 考え方 | どこまで自動か | 本番への最後の一歩 |
| :-: | :-: | :-: |
| 継続的インテグレーション（CI） | 統合のたびにビルドとテスト | ― |
| 継続的デリバリー（CD） | ビルド・テスト・ステージングまで | 人・テスト・ルールが決める（手動承認など） |
| 継続的デプロイ | 本番へのデプロイまで | 人の承認なしに自動 |

### CI/CD

#### 継続的インテグレーション（けいぞくてきいんてぐれーしょん / continuous integration, CI）

- 意味：チームのメンバーが同じ場所（main ブランチなど）に作業を頻繁にまとめ、そのたびに自動でビルドとテストをして、統合の誤りを早く見つける開発のやり方
- ポイント：CI はビルドとテストまで。本番へのリリースの自動化は CD の役目。CodePipeline ではソースとビルドのステージ（CodeBuild で単体テスト）が CI に当たる

#### 継続的デリバリー（けいぞくてきでりばりー / continuous delivery, CD）

- 意味：リリースの手順を自動化し、すべての変更を自動でビルド・テストして、いつでも本番にデプロイできる状態にする開発のやり方
- ポイント：本番に出す最後の一歩は、人・自動テスト・ビジネスのルールが決める。ステージングと本番のステージがあり、本番の前に手動承認を置くのが典型。CodePipeline は「継続的な配信サービス」

#### 継続的デプロイ（けいぞくてきでぷろい / continuous deployment）

- 意味：テストを通った変更を、人の承認なしに本番まで自動でデプロイするやり方
- ポイント：継続的デリバリーとのちがいは、本番の前に手動承認があるかどうか。テストの自動化がしっかりしていることが前提

#### SDLC（えすでぃーえるしー / software development life cycle）

- 意味：ソフトウェアを計画・開発・ビルド・テスト・リリース・運用するまでの一連の流れ
- ポイント：DOP-C02 の分野 1 は「SDLC のオートメーション」。パイプラインのステージは、ソース→ビルド→テスト→ステージング→本番のように SDLC の段階に対応させる
- 語の意味：SDLC＝Software Development Life Cycle（ソフトウェア開発のライフサイクル）

#### マルチアカウントのパイプライン（まるちあかうんとのぱいぷらいん / multi-account pipeline）

- 意味：ツール用のアカウントにパイプラインを置き、開発・ステージング・本番などの別のアカウントにデプロイする形
- ポイント：環境ごとにアカウントを分けると、権限や影響の範囲を分けられる。別のアカウントのアクションは、そのアカウントの IAM ロールを使い、アーティファクトはカスタマーマネージドの KMS キーで暗号化して共有する（01-4）

## 01-2 パイプラインの部品

### まとめ表

| 部品 | 中身 |
| :-: | :-: |
| パイプライン | ステージの並び。V1 と V2 のタイプがある |
| ステージ | アクションの集まり。1 度に 1 つの実行だけ（ロック） |
| アクション | source・build・test・deploy・approval・invoke の 6 種類 |
| トランジション | ステージの間のつなぎ。無効にすると次に進まない |
| アーティファクト | アクションの間で受けわたすファイル。S3 のアーティファクトストアに置く |
| 変数 | #{namespace.variable_key} でアクションの設定に値を渡す |

### 部品

#### AWS CodePipeline（こーどぱいぷらいん / AWS CodePipeline）

- 意味：ソフトウェアのリリースの手順をモデル化・可視化・自動化する、AWS の継続的デリバリーのサービス
- ポイント：ビルドは CodeBuild、デプロイは CodeDeploy・CloudFormation・ECS・Elastic Beanstalk・S3 など、ほかのサービスをアクションとして組み合わせる。サーバーを持たないマネージドサービス

#### ステージ（すてーじ / stage）

- 意味：パイプラインを区切る論理的な単位。中にアクションを並べ、環境を分けたり、同時に入る変更を制限したりする
- ポイント：パイプラインには少なくとも 2 つのステージが要る。ソースアクションを置けるのは最初のステージだけ。ステージは実行を処理している間ロックされ、1 度に 1 つの実行しか処理しない

#### アクション（あくしょん / action）

- 意味：ステージの中で、アーティファクトに対して行う操作
- ポイント：種類は source・build・test・deploy・approval・invoke の 6 つ。同じステージの中で直列にも並列にもできる（runOrder の値が同じなら並列）。invoke は Lambda や Step Functions を呼ぶ

#### トランジション（とらんじしょん / transition）

- 意味：パイプラインのステージとステージの間のつなぎ。実行が次のステージに進むところ
- ポイント：既定は有効。無効にすると実行がそのステージに入らない（本番に出したくない時期に使う）。手動の承認を待つのは承認アクションの役目。実行を止める前に、ステージの前のトランジションを無効にするのがすすめ

#### アーティファクト（あーてぃふぁくと / artifact）

- 意味：パイプラインのアクションが受けわたすデータ（ソースコード・ビルドしたもの・テンプレートなど）
- ポイント：前のアクションの出力アーティファクトが、次のアクションの入力アーティファクトになる。S3 のアーティファクトバケット（アーティファクトストア）に置かれ、既定では AWS マネージドの KMS キーで暗号化される。ソースに使う S3 バケットとは別物

#### 変数（CodePipeline）（へんすう / variables）

- 意味：パイプラインのアクションの設定に、実行ごとの値を渡すしくみ
- ポイント：アクションが出力する変数と、V2 タイプだけのパイプラインレベルの変数がある。名前空間をつけて #{namespace.variable_key} で参照する。codepipeline という予約済みの名前空間もある（実行 ID など）
- 例：#{SourceVariables.CommitId} でソースのコミット ID を後ろのアクションに渡す

#### 手動承認アクション（しゅどうしょうにんあくしょん / manual approval action）

- 意味：パイプラインをいったん止め、権限を持つ人が承認または却下するまで次に進ませないアクション
- ポイント：承認すると再開し、却下するか 7 日以内に応答がないと失敗と同じ扱いになる。SNS のトピックに通知でき、レビューする URL やコメントも付けられる。コードレビュー・手での品質確認・本番の前の確認に使う

#### パイプラインタイプ V1 と V2（ぱいぷらいんたいぷ / pipeline type V1 and V2）

- 意味：パイプラインが使える機能のちがいによる、2 つのタイプ
- ポイント：V2 だけの機能：パイプラインレベルの変数、QUEUED・PARALLEL の実行モード、ステージのロールバック、Git タグ・プルリクエスト・ブランチ・ファイルパスでのトリガーとフィルター、ステージ条件、失敗時の自動再試行。料金のしくみもちがう

## 01-3 実行とトリガー

### まとめ表

| 実行モード | 動き | タイプ |
| :-: | :-: | :-: |
| SUPERSEDED（既定） | 新しい実行が、待っている古い実行を追いこして置きかえる | V1・V2 |
| QUEUED | キューに入った順に 1 つずつ処理する | V2 |
| PARALLEL | 実行どうしが独立して同時に動く。ロールバック不可 | V2 |

### 実行

#### パイプラインの実行（ぱいぷらいんのじっこう / pipeline execution）

- 意味：パイプラインがリリースする一連の変更。実行ごとに一意の ID を持つ
- ポイント：パイプラインは同時に複数の実行を扱えるが、ステージは 1 度に 1 つ。止め方は「停止して待機」（進行中のアクションは終える）と「停止して中止」（進行中のアクションを捨てる）の 2 つ

#### 実行モード（じっこうもーど / execution mode）

- 意味：続けて起きた複数の実行を、パイプラインがどう扱うかの設定
- ポイント：SUPERSEDED（既定。新しい実行が待っている古い実行を置きかえる）・QUEUED（順番に 1 つずつ。V2）・PARALLEL（独立して並べて動く。V2）。すべての変更を順に本番に出したいなら QUEUED、機能ブランチごとに並べて試すなら PARALLEL

#### トリガーとフィルター（とりがーとふぃるたー / triggers and filters）

- 意味：どのイベントでパイプラインを始めるかの設定と、その絞りこみ
- ポイント：V2 では、プッシュ（ブランチ・ファイルパス・Git タグで絞る）とプルリクエスト（オープン・更新・クローズで、ブランチ・ファイルパスで絞る）を選べる。プッシュはプッシュ先（ターゲット）のブランチ、プルリクエストはプル元（ソース）のブランチのコミットを使う

#### イベントベースの変更検出（いべんとべーすのへんこうけんしゅつ / event-based change detection）

- 意味：ソースの変更をイベント（EventBridge・接続の webhook など）で知り、すぐにパイプラインを始めるやり方
- ポイント：定期的に問い合わせるポーリングより、イベントベースがすすめ。CodeCommit と S3 のソースは EventBridge（S3 はイベント通知を有効にしたバケット）。30 日以上動いていないパイプラインはポーリングが止まる

#### ステージの再試行（すてーじのさいしこう / stage retry）

- 意味：パイプラインを最初からやり直さずに、失敗したステージや失敗したアクションだけをやり直す機能
- ポイント：「ステージの再試行」はステージの最初のアクションからすべて、「失敗したアクションの再試行」は失敗したものだけをやり直す。V2 では失敗時の自動再試行も設定できる。パイプラインの構造を変えたあとは再試行できない

#### ステージのロールバック（すてーじのろーるばっく / stage rollback）

- 意味：ステージを、そのステージで以前に成功した実行の状態にもどす機能
- ポイント：失敗時に自動でもどす設定も、手動でもどすこともできる。ロールバックは新しい実行（ロールバックの実行）として始まる。ソースステージはもどせない。PARALLEL モードでは使えない。V2 だけ

#### 接続（AWS CodeConnections）（せつぞく / connections）

- 意味：CodePipeline などを、GitHub・Bitbucket・GitLab などの外部のコードリポジトリにつなぐ機能
- ポイント：以前の名前は AWS CodeStar Connections。接続の ARN をパイプラインのソースアクションやテンプレートで使えば、トークンを秘密情報として持つ必要がない

## 01-4 複数のアカウントとリージョン

### まとめ表

| | クロスアカウント | クロスリージョン |
| :-: | :-: | :-: |
| 何をするか | 別のアカウントのリソースにデプロイ | 別のリージョンでアクションを実行 |
| 必要なもの | カスタマーマネージドの KMS キー、バケットポリシー、相手のアカウントのロール | リージョンごとのアーティファクトバケット（と暗号化キー） |
| 注意 | キーはエイリアスでなく ID か ARN で指定 | アーティファクトのコピーは CodePipeline が行う |

### 広げる

#### クロスアカウントアクション（くろすあかうんとあくしょん / cross-account action）

- 意味：パイプラインのあるアカウントとは別の AWS アカウントのリソース（CodeDeploy のアプリケーションなど）を使うアクション
- ポイント：アーティファクトをカスタマーマネージドの KMS キーで暗号化し（既定の AWS マネージドキーは相手のアカウントが使えない）、キーポリシーとバケットポリシーで相手のアカウントに許可し、相手のアカウントに CodePipeline が引き受けるロールを作る。キーはエイリアスでなく、キー ID かキー ARN で指定する

#### クロスリージョンアクション（くろすりーじょんあくしょん / cross-region action）

- 意味：パイプラインとは別の AWS リージョンで実行するアクション
- ポイント：アクションを実行するリージョンごとにアーティファクトバケットが要る。バケットと暗号化キーは、アクションと同じリージョン・パイプラインと同じアカウントに作る。リージョンの間のアーティファクトのコピーは CodePipeline が行う
- 例：us-east-1 のパイプラインから、ap-northeast-1 の CloudFormation スタックをデプロイする

#### アーティファクトストアの暗号化（あーてぃふぁくとすとあのあんごうか / artifact store encryption）

- 意味：アーティファクトバケットに置くアーティファクトを KMS キーで暗号化すること
- ポイント：既定は AWS マネージドキー（aws/s3）。クロスアカウントのときはカスタマーマネージドキーに替えて、相手のアカウントに使う権限を与える

### 01-1 CI/CD の考え方

#### 問 dop-01-o01

- 問：チームの開発者が変更を 1 日に何度も main ブランチにまとめ、そのたびに自動でビルドと単体テストを行って、統合の誤りを早く見つけたい。このやり方を何というか。
- ア：継続的インテグレーション
- イ：継続的デプロイ
- ウ：ブルー/グリーンデプロイ
- エ：イミュータブルインフラストラクチャ
- 正解：ア
- 解説：作業を頻繁に同じ場所に統合し、変更ごとにビルドと検証をして統合の誤りを早く見つけるのは継続的インテグレーション（CI）。本番へのデプロイの自動化までは含まない。
- アの意味：正しい。
- イの意味：本番へのデプロイまで自動化するやり方。
- ウの意味：新旧 2 つの環境を切りかえるデプロイの方法。
- エの意味：サーバーを変更せず作り直す考え方。
- 出典：オリジナル問題（根拠：AWS「AWS CodePipeline ユーザーガイド」継続的デリバリーと継続的インテグレーション（『継続的統合 は、チームのメンバーがバージョン管理システムを使用し、頻繁にマスターブランチなどの同じ場所に作業を統合するソフトウェア開発のプラクティスです。』））

#### 問 dop-01-o02

- 問：すべての変更を自動でビルド・テストしてステージング環境まで出すが、本番へのデプロイは担当者の承認のあとに行う。このやり方として最も適切なものはどれか。
- ア：継続的インテグレーション
- イ：継続的デリバリー
- ウ：継続的デプロイ
- エ：手動デプロイ
- 正解：イ
- 解説：継続的デリバリーではリリースの手順を自動化するが、本番に出す最後の判断は人・自動テスト・ビジネスのルールが行う。本番の前の手動承認が典型。承認なしに本番まで自動で出すのは継続的デプロイ。
- アの意味：ビルドとテストまで。
- イの意味：正しい。
- ウの意味：本番まで承認なしに自動。
- エの意味：ビルドやテストも自動化されている。
- 出典：オリジナル問題（根拠：AWS「AWS CodePipeline ユーザーガイド」継続的デリバリーと継続的インテグレーション（『「継続的な配信」はリリースプロセスが自動化されるソフトウェア開発方法です。』『最終的な本番稼働に進む前に、個人、自動テスト、またはビジネスルールが最終的なプッシュがいつ行われるかを決定します。』））

#### 問 dop-01-o03

- 問：AWS CodePipeline の説明として正しいものはどれか。
- ア：コードをコンパイルしてテストを実行する、フルマネージドのビルドサービス
- イ：EC2 インスタンスにアプリケーションを配るデプロイサービス
- ウ：ソフトウェアのリリースの手順をモデル化・可視化・自動化する継続的デリバリーのサービス
- エ：パッケージを保存して共有するアーティファクトリポジトリ
- 正解：ウ
- 解説：CodePipeline はリリースの手順（ステージとアクション）を組み立てて自動化するサービス。ビルドは CodeBuild、デプロイは CodeDeploy など、ほかのサービスをアクションとして呼び出す。
- アの意味：CodeBuild。
- イの意味：CodeDeploy。
- ウの意味：正しい。
- エの意味：CodeArtifact。
- 出典：オリジナル問題（根拠：AWS「AWS CodePipeline ユーザーガイド」とは AWS CodePipeline（『AWS CodePipeline は、ソフトウェアのリリースに必要なステップをモデル化、視覚化、自動化するために使用できる継続的な配信サービスです。』））

#### 問 dop-01-o04

- 問：ツール用のアカウントにパイプラインを置き、開発・本番の別々のアカウントにデプロイする構成の利点として最も適切なものはどれか。
- ア：KMS キーが要らなくなる
- イ：アーティファクトバケットが要らなくなる
- ウ：すべての環境で同じ IAM ユーザーを共有できる
- エ：環境ごとに権限と影響の範囲を分けられる
- 正解：エ
- 解説：環境ごとにアカウントを分けると、本番への権限や、まちがいが起きたときの影響を限れる。パイプラインは相手のアカウントのロールを引き受けてデプロイし、アーティファクトはカスタマーマネージドの KMS キーで共有する。
- アの意味：クロスアカウントではカスタマーマネージドキーが必要になる。
- イの意味：アーティファクトバケットは要る。
