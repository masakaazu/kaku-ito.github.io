## 13-1 DR の目標と戦略

### まとめ表

| 戦略 | DR リージョンで動いているもの | RTO・RPO の目安 | 費用 |
| :-: | :-: | :-: | :-: |
| バックアップと復元 | バックアップだけ | 数時間 | 最も安い |
| パイロットライト | データの複製とコアの基盤（アプリは止めている） | 数十分 | 安い |
| ウォームスタンバイ | 縮小した完全な環境（動いている） | 数分 | 中 |
| マルチサイトアクティブ/アクティブ | 本番と同じ環境（トラフィックも処理） | ほぼゼロ | 最も高い |

### 目標

#### RTO（あーるてぃーおー / Recovery Time Objective：目標復旧時間）

- 意味：サービスが止まってから、復旧するまでに許される最大の時間
- ポイント：検出・通知・判断（災害の宣言）の時間も含む。短くするほど費用と複雑さが増える
- 語の意味：Recovery＝復旧、Time＝時間、Objective＝目標

#### RPO（あーるぴーおー / Recovery Point Objective：目標復旧時点）

- 意味：最後に戻せるデータの時点から、障害までに許される最大の時間。失ってよいデータの量
- ポイント：RPO 1 時間なら、少なくとも 1 時間ごとにバックアップか複製が要る。「時間」は RTO、「データ」は RPO
- 語の意味：Recovery＝復旧、Point＝時点、Objective＝目標

### 戦略

#### バックアップと復元（ばっくあっぷとふくげん / backup and restore）

- 意味：バックアップを別のリージョンなどに取っておき、災害時に環境を作り直して復元する戦略
- ポイント：最も安いが、RTO・RPO は長い（数時間）。データの破損や削除への対策としてはどの戦略でも要る。IaC で環境を素早く作り直せるようにしておく

#### パイロットライト（ぱいろっとらいと / pilot light）

- 意味：データを DR リージョンへ複製し、DB などのコアの基盤だけを常に用意しておき、アプリのサーバーは止めておく戦略
- ポイント：災害時にアプリのサーバーを起動・スケールアウトして切り替える。継続的な費用を抑えつつ、RTO を数十分に

#### ウォームスタンバイ（うぉーむすたんばい / warm standby）

- 意味：本番の完全に動く縮小コピーを DR リージョンで常に動かしておく戦略
- ポイント：すでに動いているので、災害時はスケールアップするだけ。パイロットライトとの違いは「アプリも動いていて、すぐリクエストを処理できる」こと

#### マルチサイトアクティブ/アクティブ（まるちさいと / multi-site active/active）

- 意味：複数のリージョンで同時に本番を動かし、すべてのリージョンでトラフィックを処理する戦略
- ポイント：RTO はほぼゼロだが最も高く複雑。1 つのリージョンだけで処理し、ほかを DR 専用にするのはホットスタンバイ。データの破損にはバックアップが別に要る

### 切り替えとテスト

#### DR のテスト（でぃーあーるのてすと / disaster recovery testing）

- 意味：DR リージョンへのフェイルオーバーを定期的に行い、RTO と RPO を満たすかを確かめること
- ポイント：テストしていない復旧の手順は動かないと考える。DR リージョンの容量やサービスクォータが足りるかも確かめる

#### ARC ルーティングコントロール（るーてぃんぐこんとろーる / ARC routing control）

- 意味：リージョンのレプリカの間でトラフィックを切り替える、オン/オフのスイッチ。Route 53 のヘルスチェックと組み合わせて使う
- ポイント：災害時に人がはっきり判断して切り替えるため。コントロールパネルでまとめ、安全ルールで「両方オフ」などを防ぐ

#### AWS Fault Injection Service（えふあいえす / AWS FIS）

- 意味：インスタンスの停止・AZ の障害・API のエラーなどを意図的に起こし、アプリの耐性を確かめるマネージドサービス（カオス工学）
- ポイント：停止条件（CloudWatch アラーム）で実験を自動で止められる。まず本番以外で試す

#### AWS Elastic Disaster Recovery（えらすてぃっくでぃざすたりかばり / AWS Elastic Disaster Recovery, AWS DRS）

- 意味：オンプレミスやクラウドのサーバーを AWS のステージング領域に継続的に複製し、災害時に AWS で起動するサービス
- ポイント：安いストレージと最小限のコンピューティングで待機し、秒単位の RPO・分単位の RTO を目指す。止めずにドリル（訓練）ができ、フェイルバックもできる

## 13-2 AWS Backup

### まとめ表

| やりたいこと | AWS Backup の機能 |
| :-: | :-: |
| 多くのサービスのバックアップを 1 つのルールで | バックアッププラン（頻度・保持・コピー） |
| 別のリージョン・別のアカウントにも | コピールール（クロスリージョン・クロスアカウント） |
| 誰にも消させない | ボールトロック（コンプライアンスモード） |
| 乗っ取られても別の場所で戻す | 論理エアギャップボールト |
| 戻せるか定期的に確かめる | 復元テスト |
| 組織の全アカウントに同じルール | Organizations のバックアップポリシー |
| ルールどおりかを監査 | Backup Audit Manager |

### 取る・置く・写す

#### AWS Backup（えーだぶりゅーえすばっくあっぷ / AWS Backup）

- 意味：EC2・EBS・RDS・Aurora・DynamoDB・EFS・S3 などのバックアップを、1 か所で集中管理して自動化するサービス
- ポイント：サービスごとのスクリプトや手作業をなくす。バックアップの監査とコンプライアンスにも使う

#### バックアッププラン（ばっくあっぷぷらん / backup plan）

- 意味：いつ取るか（頻度・ウィンドウ）、どれだけ残すか（保持・コールドストレージへの移行）、どこにコピーするかを決めたルールの集まり
- ポイント：リソースはタグなどで割り当てる。新しく作ったリソースもタグが合えば自動で対象になる

#### バックアップボールト（ばっくあっぷぼーると / backup vault）

- 意味：復旧ポイント（バックアップ）を入れておく入れ物。KMS キーで暗号化され、アクセスポリシーを付けられる
- ポイント：ボールトのアクセスポリシーで削除の操作を拒否できる。より強く守るならボールトロック

#### クロスリージョンコピー・クロスアカウントコピー（こぴー / cross-Region copy・cross-account copy）

- 意味：バックアップを別のリージョンや、同じ組織の別のアカウントのボールトにコピーする機能。プランのコピールールで自動にできる
- ポイント：リージョンの障害に備えるならクロスリージョン、アカウントの乗っ取りや誤操作に備えるならクロスアカウント。クロスアカウントにはカスタマーマネージドキーが要る

#### ボールトロック（ぼーるとろっく / AWS Backup Vault Lock）

- 意味：ボールトのバックアップを、保持期間が終わるまで誰も消せないようにする WORM の設定
- ポイント：ガバナンスモードは十分な権限があれば外せる。コンプライアンスモードは猶予期間が過ぎると、ルートユーザーも AWS も変更・削除できない

#### 論理エアギャップボールト（ろんりえあぎゃっぷぼーると / logically air-gapped vault）

- 意味：AWS Backup のサービスが持つアカウントにバックアップを保存し、AWS RAM で別のアカウントに共有して復元できる、特別なボールト
- ポイント：ランサムウェアなどで自分のアカウントが使えなくなっても、別のアカウントから戻せる。既定でロックされている

### 確かめる・そろえる

#### 復元テスト（ふくげんてすと / restore testing）

- 意味：決めた頻度で自動的にバックアップから復元してみて、戻せるか・どれだけ時間がかかるかを確かめる AWS Backup の機能
- ポイント：復元したリソースは検証のあと自動で消える。RTO を満たすかの証拠になる

#### バックアップポリシー（ばっくあっぷぽりしー / AWS Organizations backup policy）

- 意味：Organizations で組織や OU に付けるポリシーで、各アカウントに同じバックアッププランを自動で作る
- ポイント：全アカウントのバックアップの規則をそろえ、手作業のミスを減らす。管理アカウントか委任された管理者で設定

#### AWS Backup Audit Manager（おーでぃっとまねーじゃー / AWS Backup Audit Manager）

- 意味：バックアップの頻度・保持期間などのコントロールをフレームワークにまとめ、守られているかを監査してレポートを作る機能
- ポイント：「全部のリソースが毎日バックアップされ 35 日残っているか」を継続して確かめる。AWS Config を使う

## 13-3 サービスごとの復旧

### まとめ表

| サービス | 戻し方 | ポイント |
| :-: | :-: | :-: |
| RDS | 自動バックアップ（最大 35 日）で特定の時点へ | 新しい DB インスタンスができる |
| RDS（別リージョン） | 自動バックアップのレプリケーション・スナップショットのコピー | DR リージョンで特定の時点へ |
| Aurora MySQL | バックトラック | 同じクラスターをその場で巻き戻す |
| DynamoDB | ポイントインタイムリカバリ（最大 35 日） | 新しいテーブルに戻す |
| S3 | バージョニング・Object Lock | 削除マーカーを消せば戻る |
| EBS・AMI | Data Lifecycle Manager・高速スナップショット復元・AMI のコピー | リージョン固有なのでコピーしておく |

### データベース

#### RDS のポイントインタイムリカバリ（ぽいんとインタイムりかばり / RDS point-in-time recovery）

- 意味：自動バックアップとトランザクションログ（5 分ごとに S3 へ）から、保持期間の中の任意の時点の DB を新しい DB インスタンスとして作る機能
- ポイント：元の DB は変わらず、新しいエンドポイントができる。アプリの接続先を切り替える（または名前を入れ替える）手順が要る。保持期間は最大 35 日

#### 自動バックアップのレプリケーション（じどうばっくあっぷのれぷりけーしょん / cross-Region automated backups）

- 意味：RDS の自動バックアップ（スナップショットとトランザクションログ）を別のリージョンに複製し、そこで特定の時点に戻せるようにする機能
- ポイント：リードレプリカを常に動かさずに、DR リージョンでの復元を可能にする。マルチ AZ DB クラスターでは使えない

#### Aurora のバックトラック（ばっくとらっく / Aurora backtrack）

- 意味：Aurora MySQL で、バックアップから戻さずに、同じ DB クラスターを指定した時刻まで巻き戻す機能
- ポイント：WHERE を付け忘れた DELETE などから数分で戻せる。新しいクラスターは作らない。バックアップの代わりにはならない

#### DynamoDB のポイントインタイムリカバリ（ぴーあいてぃーあーる / DynamoDB PITR）

- 意味：DynamoDB のテーブルを、最大 35 日の間の任意の秒に戻せる機能。戻した結果は新しいテーブルになる
- ポイント：誤った書き込みや削除からの回復に。別のリージョンに戻すこともできる

### ストレージとイメージ

#### S3 バージョニング（ばーじょにんぐ / S3 Versioning）

- 意味：オブジェクトを上書き・削除しても前のバージョンを残す設定。削除すると削除マーカーが付くだけ
- ポイント：誤って消しても削除マーカーを消せば戻る。古いバージョンはライフサイクルで期限を決める。レプリケーションの前提でもある

#### S3 Object Lock（おぶじぇくとろっく / S3 Object Lock）

- 意味：オブジェクトを WORM（一度書いたら変更・削除できない）で保存する機能。保持期間とリーガルホールドがある
- ポイント：コンプライアンスモードはルートユーザーも消せない。ガバナンスモードは特別な権限があれば消せる。規制の要件に

#### Data Lifecycle Manager（でーたらいふさいくるまねーじゃー / Amazon Data Lifecycle Manager）

- 意味：EBS スナップショットと EBS-backed AMI の作成・保持・削除を、ポリシーで自動化する機能
- ポイント：別のリージョンやアカウントへのコピーも自動にできる。EBS だけなら DLM、多くのサービスをまとめるなら AWS Backup

#### 高速スナップショット復元（こうそくすなっぷしょっとふくげん / EBS fast snapshot restore, FSR）

- 意味：スナップショットから作ったボリュームを、作った時点で完全に初期化された状態にする機能
- ポイント：ふつうは最初の読み取りで S3 からデータを取ってくるので遅い。RTO が短い復元に。料金がかかる

#### AMI のコピー（えーえむあいのこぴー / AMI copy）

- 意味：AMI を別のリージョンや別のアカウントにコピーすること
- ポイント：AMI はリージョンに固有なので、DR リージョンで起動するには前もってコピーしておく。パイプラインで作った AMI を自動でコピーする

## 問題演習

### 13-1

#### 問 dop-13-o01

- 問：経営層から「受注システムが止まっても、4 時間以内には使えるようにしてほしい」と言われた。これは何を決めたことになるか。
- ア：RPO
- イ：SLA
- ウ：RTO
- エ：MTBF
- 正解：ウ
- 解説：止まってから復旧するまでの最大の時間は RTO（目標復旧時間）。
- アの意味：失ってよいデータの時間の幅。
- イの意味：提供者が約束する水準で、この要件は社内の復旧の目標。
- ウの意味：正しい。
- エの意味：故障の間の平均時間で、復旧の目標ではない。
- 出典：オリジナル問題（根拠：AWS ホワイトペーパー「でのワークロードのディザスタリカバリ AWS」事業継続計画 (BCP)（『 **目標復旧時間 (RTO)** は、サービスの中断からサービスの復旧までの最大許容遅延時間です。』））

#### 問 dop-13-o02

- 問：「障害が起きても、失ってよいのは直前 15 分のデータまで」という要件がある。これを満たすために最低限必要なことはどれか。
- ア：15 分以内の間隔でデータをバックアップするか、継続的に複製する
- イ：15 分以内にサーバーを起動できるようにする
- ウ：毎日 1 回スナップショットを取る
- エ：マルチ AZ にする
- 正解：ア
- 解説：これは RPO 15 分の要件。データを少なくとも 15 分ごとに残すか、継続的に複製する。
- アの意味：正しい。
- イの意味：復旧の時間（RTO）の話で、データの損失は減らない。
- ウの意味：最大 24 時間分のデータを失う。
- エの意味：AZ の障害には効くが、リージョンの障害やデータの破損には効かない。
- 出典：オリジナル問題（根拠：AWS ホワイトペーパー「でのワークロードのディザスタリカバリ AWS」事業継続計画 (BCP)（『 **目標復旧時点 (RPO)** は、最後のデータ復旧時点からの最大許容時間です。』））

#### 問 dop-13-o03

- 問：社内の文書管理システムは、RTO 24 時間・RPO 12 時間でよい。DR の費用はできるだけ抑えたい。どの戦略を選ぶか。
- ア：ウォームスタンバイ
- イ：バックアップと復元
- ウ：マルチサイトアクティブ/アクティブ
- エ：パイロットライト
- 正解：イ
- 解説：RTO・RPO が長くてよいなら、バックアップを別のリージョンに置き、災害時に作り直す戦略が最も安い。
- アの意味：常に環境を動かすので、この要件には高すぎる。
- イの意味：正しい。
- ウの意味：最も高く、要件に対して過剰。
- エの意味：コアの基盤を常に動かす分、費用がかかる。
- 出典：オリジナル問題（根拠：AWS ホワイトペーパー「でのワークロードのディザスタリカバリ AWS」クラウド内での災害対策オプション（『 バックアップと復元は、データの損失や破損を軽減するための適切なアプローチです。』））

#### 問 dop-13-o04

- 問：RTO 30 分・RPO 数分。DR リージョンでは DB へのデータの複製と VPC などの基盤だけを常に用意し、アプリのサーバーは止めておいて費用を抑えたい。どの戦略か。
- ア：バックアップと復元
- イ：ウォームスタンバイ
- ウ：マルチサイトアクティブ/アクティブ
- エ：パイロットライト
