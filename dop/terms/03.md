## 03-1 CodeArtifact（パッケージのリポジトリ）

### まとめ表

| 置くもの | サービス | 取り出し方 |
| :-: | :-: | :-: |
| npm・Maven・PyPI・NuGet などのパッケージ | CodeArtifact | aws codeartifact login（トークン既定 12 時間） |
| Docker・OCI のコンテナイメージ | Amazon ECR | aws ecr get-login-password（トークン 12 時間） |
| ビルドの出力（zip など） | Amazon S3 | CodePipeline のアーティファクトストア |
| AMI | EC2（Image Builder で作る） | 起動権限・配布設定 |

### CodeArtifact の部品

#### AWS CodeArtifact（こーどあーてぃふぁくと / AWS CodeArtifact）

- 意味：npm・Maven・pip・NuGet などのソフトウェアパッケージを保存・共有する、フルマネージドのアーティファクトリポジトリ
- ポイント：パッケージマネージャーの接続先（リポジトリのエンドポイント）を CodeArtifact に向けて使う。公開リポジトリのパッケージを必要なときに取ってきて保存できる。コンテナイメージは ECR、ビルドの出力ファイルは S3 と分けて覚える

#### ドメイン（どめいん / domain）

- 意味：複数のリポジトリをまとめる上位の単位。アセットとメタデータはドメインに保存される
- ポイント：同じアセットはドメインに一度だけ保存される（重複排除）。ドメインの中身は 1 つの KMS キーで暗号化（非対称キーは不可）。組織のポリシーをドメインにかけて、どのアカウントが使えるかを決める。本番用のドメインは 1 つにまとめるのがすすめ。リポジトリは別のドメインに移せない

#### リポジトリ（りぽじとり / repository）

- 意味：パッケージのバージョンを入れる入れ物。1 つのリポジトリにどの形式のパッケージも入れられる（ポリグロット）
- ポイント：npm 用・Maven 用と分けなくてよい。リポジトリは必ずどこか 1 つのドメインに属する

#### アセット（あせっと / asset）

- 意味：パッケージのバージョンにひもづく個々のファイル（npm の .tgz、Maven の POM や JAR など）
- ポイント：パッケージ＞パッケージバージョン＞アセットの順に細かくなる

#### パッケージオリジンコントロール（ぱっけーじおりじんこんとろーる / package origin controls）

- 意味：パッケージの新しいバージョンを、直接の公開（publish）やアップストリームからの取り込みで入れることを許可・ブロックする設定
- ポイント：社内パッケージと同じ名前の公開パッケージが混ざる「依存関係の置き換え」を防ぐのに使う。パッケージグループを使うと、名前のパターンで多くのパッケージにまとめて設定できる

### つなぎ方

#### アップストリームリポジトリ（あっぷすとりーむりぽじとり / upstream repository）

- 意味：あるリポジトリ（ダウンストリーム）のエンドポイントから、中のパッケージを使えるようにした別のリポジトリ
- ポイント：アップストリームにあるパッケージは、ダウンストリームからも使える。1 つのリポジトリに最大 10 個まで付けられる。同じドメインのリポジトリどうしで使う。チームのリポジトリ → 共有リポジトリ → 外部接続、のようにつなぐ

#### 外部接続（がいぶせつぞく / external connection）

- 意味：CodeArtifact のリポジトリと、npmjs.com や Maven Central などの公開リポジトリとの間の接続
- ポイント：リポジトリにまだないパッケージを頼まれると、外部接続から取ってきて保存する。1 つのリポジトリに外部接続は 1 つだけ。外部接続を持つリポジトリをドメインに 1 つ作り、他のリポジトリはそれをアップストリームにする使い方が想定されている
- 例：社内の CI から npmjs.com に直接出ずに、CodeArtifact 経由で取る（取ったものは残るので、公開側の削除や障害の影響を受けにくい）

#### 認可トークン（にんかとーくん / authorization token）

- 意味：パッケージの公開・取得のために、AWS の認証情報を使って GetAuthorizationToken で発行する一時的なトークン
- ポイント：既定で 12 時間有効（15 分〜12 時間で設定できる）。切れたら取り直す。ルートユーザーは呼べない。CodeBuild ではビルドのたびに取り直す
- 例：`aws codeartifact login --tool npm --domain my-domain --repository my-repo`

#### aws codeartifact login（こーどあーてぃふぁくと ろぐいん / aws codeartifact login）

- 意味：トークンを取って、npm・pip・twine・NuGet などのパッケージマネージャーを CodeArtifact 向けに一度に設定する CLI コマンド
- ポイント：login に対応していないツールは get-authorization-token でトークンだけ取り、自分で設定する

#### ドメインポリシー（どめいんぽりしー / domain policy）

- 意味：ドメインに付けるリソースベースのポリシー。どのアカウントがドメインのリポジトリを作成・利用できるかを決める
- ポイント：既定ではドメインを持つアカウントだけが使える。別アカウントに使わせるには、ドメインのポリシーで GetAuthorizationToken などを許可する（＋リポジトリポリシーで読み取りを許可）

#### リポジトリポリシー（CodeArtifact）（りぽじとりぽりしー / repository policy）

- 意味：リポジトリに付けるリソースベースのポリシー。だれがどの操作（読み取り・公開など）をできるかを決める
- ポイント：既定ではリポジトリの所有者だけがアクセスできる。プリンシパル・アクション・Allow／Deny を書く

## 03-2 Amazon ECR（コンテナイメージのレジストリ）

### まとめ表

| 困りごと | 使う機能 |
| :-: | :-: |
| 古い・タグなしのイメージがたまる | ライフサイクルポリシー |
| latest などのタグが上書きされる | タグのイミュータビリティ |
| イメージの脆弱性を見つけたい（OS のみ） | 基本スキャン |
| 言語パッケージも、継続的にスキャンしたい | 拡張スキャン（Amazon Inspector） |
| 別リージョン・別アカウントにも置きたい | レプリケーション |
| Docker Hub などの制限・障害を避けたい | プルスルーキャッシュ |

### レジストリとアクセス

#### Amazon ECR（いーしーあーる / Amazon Elastic Container Registry）

- 意味：コンテナイメージを保存・管理する AWS マネージドのレジストリ
- ポイント：IAM のリソースベースのアクセス許可を持つプライベートリポジトリを作れる（パブリックの ECR Public もある）。ECS・EKS・Lambda（コンテナイメージ）から取り出す
- 語の意味：Elastic＝伸び縮みする、Container＝コンテナ、Registry＝登録所

#### get-login-password（げっとろぐいんぱすわーど / get-login-password）

- 意味：ECR の認証トークンを取って docker login に渡す CLI コマンド
- ポイント：トークンは 12 時間有効で、取った IAM プリンシパルと同じ権限を持つ。CodeBuild の pre_build で実行するのが定番
- 例：`aws ecr get-login-password --region ap-northeast-1 | docker login --username AWS --password-stdin 111122223333.dkr.ecr.ap-northeast-1.amazonaws.com`

#### リポジトリポリシー（ECR）（りぽじとりぽりしー / repository policy）

- 意味：個々の ECR リポジトリへのアクセスを決める、リソースベースのポリシー
- ポイント：IAM ポリシーと合わせて判断される。別アカウントの ECS や CodeBuild にイメージを取らせるときに、そのアカウントを許可する

### イメージの管理

#### タグのイミュータビリティ（たぐのいみゅーたびりてぃ / image tag immutability）

- 意味：リポジトリに既にあるタグで別のイメージを上書きできないようにする設定
- ポイント：オンのときに同じタグでプッシュすると ImageTagAlreadyExistsException になる。「本番でどのイメージが動いているか」をタグで確実にする。latest を毎回上書きする運用とは合わないので、ビルドごとにコミット ID などで新しいタグを付ける

#### ライフサイクルポリシー（ECR）（らいふさいくるぽりしー / lifecycle policy）

- 意味：古いイメージやタグの付いていないイメージを、ルールに合わせて自動で期限切れ（削除）にするポリシー
- ポイント：ルールは優先度の数値が小さいほど強い。適用の前にプレビュー（テスト）で、消えるイメージを確かめられる。例「タグなしは 14 日で消す」「prod タグは最新 30 個だけ残す」

#### 基本スキャン（きほんすきゃん / basic scanning）

- 意味：CVE のデータベースを使って、イメージの OS の脆弱性を調べるスキャン
- ポイント：プッシュ時スキャンと手動スキャン。OS のパッケージだけで、プログラミング言語のパッケージは見ない

#### 拡張スキャン（かくちょうすきゃん / enhanced scanning）

- 意味：Amazon Inspector と連携して、OS とプログラミング言語のパッケージの脆弱性を自動で続けて調べるスキャン
- ポイント：プッシュ時スキャンと継続的スキャン。新しい脆弱性が見つかれば、古いイメージでも結果が更新される。結果は EventBridge に出るので、通知や止める処理につなげられる
- 例：npm や pip のライブラリの脆弱性まで見たい → 拡張スキャン

#### レプリケーション（ECR）（れぷりけーしょん / replication）

- 意味：レジストリの設定で、イメージを別のリージョンや別のアカウントのレジストリに自動で複製する機能
- ポイント：設定した後にプッシュ（または復元）したイメージだけが複製される。クロスアカウントでは、送信先のアカウントのレジストリのポリシーで、送信元に ecr:ReplicateImage などを許可する（送信元には特別なポリシーは要らない）
- 例：DR 用に東京から大阪へ複製する

#### プルスルーキャッシュ（ぷるするーきゃっしゅ / pull through cache）

- 意味：Docker Hub・ECR Public・Quay などのアップストリームレジストリのイメージを、自分のプライベートレジストリにキャッシュして同期する機能
- ポイント：ECR が定期的にアップストリームに問い合わせて、キャッシュを最新にする。Docker Hub など認証が要るものは、認証情報を Secrets Manager のシークレットに入れる。外部のレート制限や障害の影響を減らせる

## 03-3 EC2 Image Builder（AMI とコンテナイメージの構築）

### まとめ表

| 部品 | 決めること |
| :-: | :-: |
| レシピ | ベースイメージ＋コンポーネント（AMI＝イメージレシピ、Docker＝コンテナレシピ） |
| コンポーネント | インストール・設定・テストの手順（YAML、AWSTOE が実行） |
| インフラストラクチャ設定 | ビルド・テストに使うインスタンスのタイプ・サブネット・ロール・ログ |
| 配布設定 | 配るリージョン・アカウント・起動権限 |
| イメージパイプライン | 上をまとめ、スケジュール（cron）で自動実行 |

### Image Builder の部品

#### EC2 Image Builder（いめーじびるだー / EC2 Image Builder）

- 意味：カスタマイズした、安全で最新のサーバーイメージ（AMI・コンテナイメージ）の作成・管理・配布を自動化するフルマネージドサービス
- ポイント：作ったイメージは自分のアカウントのもの。パッチを当てたイメージを定期的に作り直す「ゴールデンイメージ」の運用に使う。手で EC2 を設定して AMI を取る方法の置き換え

#### イメージレシピ（いめーじれしぴ / image recipe）

- 意味：ベースイメージと、入れるコンポーネントを決めて、AMI を作るためのレシピ
- ポイント：レシピにはバージョンがあり、変えるときは新しいバージョンを作る。AWS Marketplace のイメージ製品も使える

#### コンテナレシピ（こんてなれしぴ / container recipe）

- 意味：ベースイメージとコンポーネントから Docker のコンテナイメージを作り、ECR のリポジトリに保存するレシピ
- ポイント：AMI ではなくコンテナイメージが欲しいときはこちら。出力先は ECR

#### コンポーネント（こんぽーねんと / component）

- 意味：レシピで使う部品。パッケージのインストール、セキュリティの強化、テストなどの手順を YAML で書いたもの
- ポイント：ビルドステージ（スナップショット前）で build・validate フェーズ、テストステージ（スナップショット後）で test フェーズを実行する。AWS 管理のコンポーネント（CIS の強化など）もある

#### AWSTOE（とー / AWS Task Orchestrator and Executor）

- 意味：Image Builder がインスタンスの上でコンポーネントを実行するのに使う、コンポーネント管理アプリケーション
- ポイント：YAML のコンポーネントでワークフローのオーケストレーション、設定の変更、テストを行う。単体でも使え、validate コマンドで YAML の文法を確かめられる
- 語の意味：Task＝作業、Orchestrator＝指揮する人、Executor＝実行する人

#### インフラストラクチャ設定（いんふらすとらくちゃせってい / infrastructure configuration）

- 意味：ビルドとテストのあいだに自分のアカウントで動かすインスタンスの細かい設定（インスタンスタイプ・サブネット・セキュリティグループ・インスタンスプロファイル・ログの S3 など）
- ポイント：インスタンスプロファイルには SSM（AmazonSSMManagedInstanceCore）と EC2InstanceProfileForImageBuilder の権限が要る。失敗時にインスタンスを残してデバッグする設定もある

#### 配布設定（はいふせってい / distribution settings）

- 意味：ビルドとテストが通ったイメージを、どのリージョン・アカウントに配るか、起動権限をどうするかを決める設定
- ポイント：ビルドしたリージョンには自動で配られ、他のリージョンを足せる。他のアカウントへの起動権限は、配ったすべてのリージョンの AMI に伝わる

#### イメージパイプライン（いめーじぱいぷらいん / image pipeline）

- 意味：レシピ・インフラストラクチャ設定・配布設定をまとめ、イメージの作成を自動で繰り返す仕組み
- ポイント：スケジュールビルダーか cron 式で定期実行（手動も可）。ベースイメージとコンポーネントの変更検出を有効にすると、変化がないときはスケジュールのビルドを飛ばす。脆弱性のスキャン（Inspector）の設定もここ
- 例：毎週日曜に、最新のパッチを当てたゴールデン AMI を作って Parameter Store に ID を書き、Auto Scaling の起動テンプレートで使う

## 問題演習

### 03-1

#### 問 dop-03-o01

- 問：社内のビルドで使う npm と Maven のパッケージを、AWS のマネージドサービスにまとめて保存・共有したい。使うサービスはどれか。
- ア：AWS CodeArtifact
- イ：Amazon ECR
- ウ：AWS CodeCommit
- エ：AWS Service Catalog
- 正解：ア
- 解説：CodeArtifact は npm・Maven・pip・NuGet などのソフトウェアパッケージを保存・共有するマネージドのアーティファクトリポジトリで、一般的なビルドツールやパッケージマネージャーから使える。
- アの意味：正しい。
- イの意味：コンテナイメージのレジストリ。npm や Maven のパッケージは置かない。
- ウの意味：Git のソースコードのリポジトリ。
- エの意味：承認済みの CloudFormation テンプレートなどを製品として配るサービス。
- 出典：オリジナル問題（根拠：AWS「AWS CodeArtifact ユーザーガイド」AWS CodeArtifact とは（『AWS CodeArtifact は、組織がアプリケーション開発用のソフトウェアパッケージを保存および共有するのに役立つ、安全でスケーラブルなマネージドアーティファクトリポジトリサービスです。』））

#### 問 dop-03-o02

- 問：CodeArtifact で、npm 用と PyPI 用のパッケージを同じ 1 つのリポジトリに入れたい。正しい説明はどれか。
- ア：リポジトリは 1 つの形式だけを入れられるので、形式ごとにリポジトリを作る
- イ：形式ごとに別のドメインを作る必要がある
- ウ：リポジトリはポリグロットなので、サポートされているどの形式のパッケージも 1 つのリポジトリに入れられる
- エ：PyPI のパッケージは CodeArtifact ではなく S3 に置く
- 正解：ウ
- 解説：CodeArtifact のリポジトリはポリグロットで、サポートされている任意の形式のパッケージを 1 つのリポジトリに入れられる。
- アの意味：誤り。形式ごとに分ける必要はない。
- イの意味：誤り。ドメインはリポジトリをまとめる単位で、形式で分けるものではない。
- ウの意味：正しい。
- エの意味：誤り。PyPI（pip・twine）も CodeArtifact が対応している。
- 出典：オリジナル問題（根拠：AWS「AWS CodeArtifact ユーザーガイド」AWS CodeArtifact とは（『リポジトリはポリグロットです-単一のリポジトリには、サポートされている任意のタイプのパッケージを含めることができます。』））

#### 問 dop-03-o03

- 問：複数のチームが別々の CodeArtifact リポジトリを使っている。同じ JAR を何チームが使っても保存を 1 回にし、組織のポリシーをまとめてかけたい。どの単位でまとめるか。
- ア：パッケージグループ
- イ：ドメイン
- ウ：アップストリームリポジトリ
- エ：外部接続
- 正解：イ
- 解説：リポジトリはドメインにまとめられ、アセットはドメインに一度だけ保存される（重複排除）。ドメインのポリシーで、どのアカウントがリポジトリを使えるかを決められる。
- アの意味：パッケージ名のパターンで、オリジンコントロールなどの設定をまとめてかける単位。保存の単位ではない。
