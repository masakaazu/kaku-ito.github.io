## 20-1 IAM のしくみとアカウントをまたぐアクセス

### まとめ表

| ポリシーの種類 | 付ける場所 | はたらき |
| :-: | :-: | :-: |
| アイデンティティベースのポリシー | ユーザー・グループ・ロール | 許可を与える |
| リソースベースのポリシー | S3・SQS・KMS キーなど | 許可を与える（他アカウントのプリンシパルも指定できる） |
| 信頼ポリシー | ロール | 誰がロールを引き受けられるか |
| アクセス許可の境界 | ユーザー・ロール | 上限（許可は与えない） |
| セッションポリシー | AssumeRole のとき渡す | そのセッションの上限 |
| SCP・RCP | 組織・OU・アカウント | アカウント全体の上限 |

### アイデンティティ

#### IAM ロール（あいえーえむろーる / IAM role）

- 意味：アクセス許可を持つ IAM のアイデンティティで、必要な人やサービスが引き受けて使う。パスワードやアクセスキーのような長期の認証情報を持たない
- ポイント：引き受けると一時的な認証情報が渡される。人もマシンもロールで AWS に入るのが基本

#### 一時的な認証情報（いちじてきなにんしょうじょうほう / temporary security credentials）

- 意味：AWS STS が発行する、有効期限つき（数分〜数時間）の認証情報。アクセスキー・シークレットキー・セッショントークンの組
- ポイント：期限が来ると使えなくなるので、ローテーションや取り消しの手間が少ない。EC2・Lambda などには自動で配られる

#### インスタンスプロファイル（いんすたんすぷろふぁいる / instance profile）

- 意味：EC2 インスタンスにロールを渡すための入れ物。1 つのロールを入れる
- ポイント：コンソールで EC2 用のロールを作ると同じ名前で自動で作られる。CLI や CloudFormation では別に作る

#### サービスにリンクされたロール（さーびすにりんくされたろーる / service-linked role）

- 意味：AWS のサービスに直接ひも付き、そのサービスが必要な権限が前もって決められたロール。サービスが作って使う
- ポイント：権限は自分で編集できない。サービスの機能を有効にすると自動で作られることが多い

#### iam:PassRole（ぱすろーる / iam:PassRole）

- 意味：EC2・Lambda・ECS などのサービスにロールを渡す（設定する）ための権限
- ポイント：「ロールを付けられない」エラーは PassRole の不足。渡してよいロールの ARN に絞って許可する

### 評価とアカウントをまたぐ

#### ポリシーの評価（ぽりしーのひょうか / policy evaluation logic）

- 意味：リクエストごとに、関係するすべてのポリシーを見て許可か拒否かを決める手順
- ポイント：どこかに明示的な拒否があれば拒否。許可がどこにもなければ暗黙的に拒否。上限（SCP・境界・セッションポリシー）の外も拒否

#### クロスアカウントのアクセス（くろすあかうんとのあくせす / cross-account access）

- 意味：別のアカウントのプリンシパルに自分のリソースを使わせること。ロールを引き受けさせる方法と、リソースベースのポリシーで直接許可する方法がある
- ポイント：ロールの場合、使わせる側のロールの信頼ポリシーと、使う側のアイデンティティのポリシー（sts:AssumeRole）の両方が要る

#### 信頼ポリシー（しんらいぽりしー / trust policy）

- 意味：ロールに付けるリソースベースのポリシーで、そのロールを引き受けられるプリンシパル（アカウント・ロール・サービス・IdP）を決める
- ポイント：アクセス許可の「半分」。引き受ける側にも sts:AssumeRole の許可が要る

#### 外部 ID（がいぶあいでぃー / external ID）

- 意味：第三者（SaaS など）に自分のアカウントのロールを引き受けさせるとき、信頼ポリシーの条件 sts:ExternalId で求める値
- ポイント：「混乱した代理」問題（他の顧客が同じ業者を使って自分のロールを引き受けさせる）を防ぐ。秘密の値としては扱われない

## 20-2 最小権限の設計と見直し

### まとめ表

| やりたいこと | 使うもの |
| :-: | :-: |
| 開発者にロールを作らせるが、上限を決める | アクセス許可の境界 |
| 1 回のセッションだけ権限を絞る | セッションポリシー |
| プロジェクトが増えてもポリシーを直さない | ABAC（タグ） |
| 重要な操作は MFA の後だけ | aws:MultiFactorAuthPresent |
| 使っていない権限を見つける | 最終アクセス情報・未使用のアクセスの検出結果 |
| 実際の操作から最小のポリシーを作る | Access Analyzer のポリシー生成 |
| 外部と共有されているものを見つける | Access Analyzer の外部アクセス |

### 上限と属性

#### アクセス許可の境界（あくせすきょかのきょうかい / permissions boundary）

- 意味：ユーザーやロールに付けて、アイデンティティベースのポリシーで与えられる許可の上限を決める管理ポリシー
- ポイント：許可は与えない。境界とアイデンティティベースのポリシーの両方で許可されたものだけ使える。開発者にロールの作成を任せるとき、iam:PermissionsBoundary の条件で境界の付与を強制する

#### セッションポリシー（せっしょんぽりしー / session policy）

- 意味：AssumeRole などで一時的な認証情報を作るときに渡すポリシー。そのセッションの許可の上限になる
- ポイント：許可は与えない。ロールの許可とセッションポリシーの重なりだけが使える

#### ABAC（えーばっく / attribute-based access control）

- 意味：プリンシパルとリソースのタグ（属性）を条件にして許可を決めるやり方
- ポイント：aws:PrincipalTag と aws:ResourceTag が一致したら許可。新しいプロジェクトやリソースが増えてもポリシーを書き換えなくてよい。RBAC（役割ごとにポリシー）は増えるたびに直す
- 語の意味：Attribute-Based＝属性にもとづく、Access Control＝アクセス制御

#### MFA の条件（えむえふえーのじょうけん / aws:MultiFactorAuthPresent）

- 意味：MFA で認証したセッションかどうかを表す条件キー
- 例：TerminateInstances は aws:MultiFactorAuthPresent が true のときだけ許可する

### 見直す道具

#### 最終アクセス情報（さいしゅうあくせすじょうほう / last accessed information）

- 意味：ユーザー・ロール・ポリシーごとに、各サービス（一部はアクション）を最後にいつ使ったかを示す情報
- ポイント：使っていないサービスの許可を外す手がかり。組織の SCP にも使える

#### IAM Access Analyzer（あくせすあならいざー / IAM Access Analyzer）

- 意味：リソースベースのポリシーなどを論理で分析し、外部（信頼ゾーンの外）と共有されているリソースを検出結果にする機能。未使用のアクセスや内部のアクセスの分析、ポリシーの検証もある
- ポイント：外部と共有された S3 バケット・ロール・KMS キーなどを見つける

#### 未使用のアクセスの検出結果（みしようのあくせす / unused access findings）

- 意味：未使用のアクセスのアナライザーが、組織やアカウントで使われていないロール・アクセスキー・パスワード・権限を続けて見つける機能
- ポイント：最終アクセス情報を手で見る代わりに、継続して見張れる

#### ポリシーの生成（ぽりしーのせいせい / policy generation）

- 意味：CloudTrail のログから、指定した期間にロールやユーザーが実際に使ったアクションを調べ、ポリシーのひな形を作る機能
- ポイント：広い権限で動かしてから、実際の操作に合わせて絞るときに使う

## 20-3 人とマシンの認証情報

### まとめ表

| だれが | どうやって AWS に入るか |
| :-: | :-: |
| 社員 | IdP でフェデレーション（IAM Identity Center・SAML）→ ロール |
| GitHub Actions などの CI | OIDC プロバイダー → ロール |
| EC2・Lambda・ECS | インスタンスプロファイル・実行ロール・タスクロール |
| EKS の Pod | EKS Pod Identity・IRSA |
| オンプレミスのサーバー | IAM Roles Anywhere（X.509 証明書） |
| アプリの DB パスワード・API キー | Secrets Manager の自動ローテーション |

### フェデレーション

#### OIDC ID プロバイダー（おーあいでぃーしー / IAM OIDC identity provider）

- 意味：OIDC に対応した IdP（GitHub・GitLab・Google など）を AWS アカウントに信頼させる設定。その IdP のトークンでロールを引き受けられる（AssumeRoleWithWebIdentity）
- ポイント：CI に長期のアクセスキーを置かずに済む。信頼ポリシーの条件でリポジトリやブランチを絞る
- 語の意味：OpenID Connect＝OAuth 2.0 の上で本人確認をする標準

#### SAML フェデレーション（さむるふぇでれーしょん / SAML 2.0 federation）

- 意味：社内の SAML 2.0 の IdP（AD FS・Okta など）で認証した人が、IAM ユーザーを作らずにロールでサインインするしくみ（AssumeRoleWithSAML）
- ポイント：複数のアカウントをまとめて扱うなら IAM Identity Center がすすめられる

#### IAM Roles Anywhere（ろーるずえにうぇあ / IAM Roles Anywhere）

- 意味：AWS の外で動くサーバーやコンテナが、自分の認証局（CA）の X.509 証明書を使って、IAM の一時的な認証情報を得るしくみ。CA をトラストアンカーとして登録する
- ポイント：オンプレミスに長期のアクセスキーを置かずに済む

### マシンの認証情報

#### 実行ロール・タスクロール（じっこうろーる / execution role and task role）

- 意味：Lambda の実行ロールは関数のコードが使う権限。ECS のタスクロールはコンテナのアプリが使う権限で、タスク実行ロールはイメージの取得やログの送信に ECS が使う権限
- ポイント：コードにアクセスキーを書かない。SDK が一時的な認証情報を自動で使う

#### EKS Pod Identity（ぽっどあいでぃんてぃてぃ / EKS Pod Identity）

- 意味：EKS の名前空間とサービスアカウントの組にロールを関連付け、Pod に一時的な認証情報を渡すしくみ。クラスターに Pod Identity エージェントを入れる
- ポイント：OIDC プロバイダーを作らなくてよい。同じロールを複数のクラスターで使いやすい

#### IRSA（あいあーるえすえー / IAM roles for service accounts）

- 意味：クラスターの OIDC プロバイダーを IAM に作り、ロールの信頼ポリシーでサービスアカウントを指定して、Pod にロールを使わせるしくみ
- ポイント：ノードのロールに全部の権限を付けると、そのノードのすべての Pod が使えてしまう。Pod ごとに分けるなら IRSA か Pod Identity

#### 認証情報レポート（にんしょうじょうほうれぽーと / credential report）

- 意味：アカウントのすべての IAM ユーザーのパスワード・アクセスキー・MFA の状態と最後に使った日を一覧にした CSV
- ポイント：監査で、古いアクセスキーや MFA のないユーザーを見つける

#### マシンの認証情報のローテーション（ろーてーしょん / automated rotation for machine identities）

- 意味：アプリが使う DB のパスワードや API キーを Secrets Manager に入れ、自動で定期的に新しくすること
- ポイント：アプリは毎回 Secrets Manager から取るので、変わっても止まらない。IAM のアクセスキーは使わずロールにするのが先

## 問題演習

### 20-1

#### 問 dop-20-o01

- 問：社員 200 人が AWS のコンソールと CLI を使う。セキュリティのベストプラクティスに合う方法はどれか。
- ア：社内の IdP でフェデレーションし、ロールの一時的な認証情報で入らせる
- イ：社員ごとに IAM ユーザーとアクセスキーを作る
- ウ：ルートユーザーを共有する
- エ：アクセスキーを Secrets Manager に保存して配る
- 正解：ア
- 解説：人が AWS に入るときは一時的な認証情報を使う。IdP からのフェデレーションでロールを引き受ける。
- アの意味：正しい。
- イの意味：長期の認証情報が増え、管理と漏えいの危険が大きい。
- ウの意味：誰が何をしたかわからず、最も危ない。
- エの意味：長期のアクセスキーであることは変わらない。
- 出典：オリジナル問題（根拠：AWS「IAM ユーザーガイド」IAM でのセキュリティのベストプラクティス（『人間のユーザーが AWS にアクセスする際は、一時的な認証情報の使用が必要です。』））

#### 問 dop-20-o02

- 問：IAM ロールについて正しいものはどれか。
- ア：特定の 1 人にだけ結び付く

- エ：AWS のサービスは引き受けられない
- 正解：ウ
- 解説：ロールは必要な人やサービスが引き受け、そのセッション用の一時的な認証情報を受け取る。
- アの意味：IAM ユーザーの特徴。
- イの意味：IAM ユーザーの特徴。
- ウの意味：正しい。
- エの意味：EC2 や Lambda などのサービスも引き受ける。
- 出典：オリジナル問題（根拠：AWS「IAM ユーザーガイド」IAM ロール（『また、ロールには標準の長期認証情報 (パスワードやアクセスキーなど) も関連付けられません。』））

#### 問 dop-20-o03

- 問：別のアカウントのアプリのロールに、自分のアカウントの SQS キューへの送信だけを許したい。相手にロールを引き受けさせる仕組みは作りたくない。どうするか。

- 解説：リソースベースのポリシーは、他のアカウントのプリンシパルを指定して直接許可できる。相手側のアイデンティティのポリシーでも送信を許可する。
- アの意味：上限を決めるもので、許可は与えない。
- イの意味：上限を決めるもので、許可は与えない。
- ウの意味：上限を決めるもので、許可は与えない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「IAM ユーザーガイド」アイデンティティベースおよびリソースベースのポリシー（『**リソースベースのポリシー**をリソースにアタッチします。』））

#### 問 dop-20-o04

- 問：ユーザーのアイデンティティベースのポリシーは s3:* を許可している。バケットポリシーでは、そのユーザーの s3:DeleteObject を拒否している。オブジェクトを消せるか。

- 正解：イ
- 解説：どこかに明示的な拒否があれば、許可があっても拒否になる。
- アの意味：許可は拒否を上書きしない。
- イの意味：正しい。
- ウの意味：付けた順は関係ない。
- エの意味：評価の決まりで決まる。
- 出典：オリジナル問題（根拠：AWS「IAM ユーザーガイド」ポリシーの評価論理（『これらのポリシーのいずれかを明示的に拒否した場合、その許可は無効になります。』））

#### 問 dop-20-o05

- 問：アカウント A の運用者に、アカウント B のロール OpsRole を引き受けさせたい。何が必要か。
- ア：OpsRole の信頼ポリシーで A を信頼するだけ
- イ：A の運用者のポリシーで sts:AssumeRole を許可するだけ
- ウ：OpsRole の信頼ポリシーで A を信頼し、A の運用者のポリシーで OpsRole への sts:AssumeRole を許可する

- 正解：ウ

- アの意味：引き受ける側の許可がない。
- イの意味：ロールが信頼していない。
- ウの意味：正しい。
- エの意味：SCP は許可を与えない。
- 出典：オリジナル問題（根拠：AWS「IAM ユーザーガイド」IAM ロール（『信頼ポリシーは、信頼するアカウントのロールにアタッチされ、アクセス許可の半分です。』））

#### 問 dop-20-o06

- 問：監視 SaaS の業者に、自分のアカウントのロールを引き受けさせる。同じ業者を使う他の会社が、自分のロールを使わせるように業者をだますのを防ぎたい。どうするか。
