## 14-1 メトリクスを集める

### まとめ表

| 集めたいもの | 方法 |
| :-: | :-: |
| EC2 のメモリ・ディスク使用率、オンプレミス | CloudWatch エージェント |
| アプリの数値を API で | PutMetricData（標準 1 分・高解像度 1 秒） |
| Lambda・コンテナからログと一緒に | 埋め込みメトリクスフォーマット（EMF） |
| ECS・EKS のコンテナ | Container Insights |
| Lambda のメモリ・コールドスタート | Lambda Insights |
| 外部のツールや S3 へほぼリアルタイムに | メトリクスストリーム（Firehose） |

### メトリクスのしくみ

#### 名前空間（なまえくうかん / namespace）

- 意味：メトリクスを入れる箱。違う名前空間のメトリクスは混ざらない
- ポイント：AWS のサービスは AWS/EC2 のような名前空間。カスタムメトリクスは自分で決める（既定はない）

#### ディメンション（でぃめんしょん / dimension）

- 意味：メトリクスを区別する名前と値の組（例 InstanceId=i-123）。メトリクスは名前・名前空間・ディメンションで一意に決まる
- ポイント：ディメンションが違えば別のメトリクス。1 メトリクスに最大 30。ディメンションを付けて送ったものは、付けずに検索しても出てこない

#### 解像度と保持期間（かいぞうど / resolution and retention）

- 意味：標準解像度は 1 分、高解像度は 1 秒単位でデータを持つ。古いデータは集約されて保持される
- ポイント：60 秒未満は 3 時間、1 分は 15 日、5 分は 63 日、1 時間は 455 日（15 か月）。メトリクスは削除できず、15 か月で期限切れ

#### 統計とパーセンタイル（とうけい / statistics and percentiles）

- 意味：期間の中のデータをまとめる方法。Average・Sum・Minimum・Maximum・SampleCount と、p99 などのパーセンタイル
- ポイント：レイテンシーは平均だと一部の遅いリクエストが隠れるので、p99 などで見る。tm99 は上位 1% の外れ値を除いた平均
- 例：p95＝95% のデータがこの値以下

#### 詳細モニタリング（しょうさいもにたりんぐ / detailed monitoring）

- 意味：EC2 のメトリクスを 1 分間隔で送る設定。既定（基本モニタリング）は 5 分間隔
- ポイント：Auto Scaling を素早く反応させたいときに有効にする。料金がかかる

### カスタムメトリクスの送り方

#### PutMetricData（ぷっとめとりくすでーた / PutMetricData）

- 意味：カスタムメトリクスを CloudWatch に送る API。標準解像度か高解像度（StorageResolution=1）を選べる
- ポイント：高解像度のメトリクスには 10 秒・30 秒の期間のアラームを付けられる。頻繁に呼ぶと料金が増える

#### 埋め込みメトリクスフォーマット（うめこみめとりくすふぉーまっと / embedded metric format, EMF）

- 意味：決まった JSON の形でログを書くと、CloudWatch がそこからカスタムメトリクスを自動で取り出す仕組み
- ポイント：API を呼ばずに非同期でメトリクスを作れるので、Lambda やコンテナのような短命なリソースに向く。元のログは Logs Insights で調べられる

#### CloudWatch エージェント（くらうどうぉっちえーじぇんと / CloudWatch agent）

- 意味：EC2・オンプレミス・コンテナから、OS のメトリクス・ログ・トレースを集めるソフトウェア
- ポイント：EC2 の標準のメトリクスにないメモリやディスクの使用率はこれで取る。StatsD・collectd のカスタムメトリクスも受けられる。設定は Parameter Store に置いて配れる

#### メトリクスストリーム（めとりくすすとりーむ / metric streams）

- 意味：CloudWatch のメトリクスを、ほぼリアルタイムに Firehose 経由で S3 やサードパーティのツールへ流し続ける機能
- ポイント：API で定期的に取りに行く（ポーリング）より速く、手間がない。JSON か OpenTelemetry の形式

#### メトリクスの数式（すうしき / metric math）

- 意味：複数のメトリクスを数式で組み合わせ、新しい時系列を作る機能。アラームにも使える
- ポイント：Errors ÷ Invocations でエラー率、などの比率でアラームを出せる

### コンテナとサーバーレス

#### Container Insights（こんてなーいんさいと / CloudWatch Container Insights）

- 意味：ECS・EKS（Fargate を含む）のクラスター・サービス・タスク・Pod のメトリクスとログを集めて要約する機能
- ポイント：データは EMF のパフォーマンスログとして集められる。コンテナの再起動の失敗などの診断も出る

#### Lambda Insights（らむだいんさいと / CloudWatch Lambda Insights）

- 意味：Lambda 拡張機能（レイヤー）を入れて、関数のメモリ・CPU・コールドスタートなどのシステムのメトリクスを集める機能
- ポイント：Lambda の標準のメトリクス（Invocations・Errors・Duration）にない、関数の中の資源の使い方が分かる

## 14-2 アラーム

### まとめ表

| やりたいこと | 設定 |
| :-: | :-: |
| 5 回のうち 3 回超えたら | 評価期間 5・アラームを実行するデータポイント 3 |
| データが来ないのは正常 | 欠落データを notBreaching |
| データが来ないのが異常（ハートビート） | 欠落データを breaching |
| アラームの嵐を 1 つにまとめる | 複合アラーム |
| 時間帯で変わる値の異常 | 異常検出 |
| EC2 のハードウェア障害から戻す | 復旧アクション（StatusCheckFailed_System） |

### 評価

#### アラームの状態（あらーむのじょうたい / alarm states）

- 意味：OK（しきい値内）・ALARM（しきい値を超えた）・INSUFFICIENT_DATA（判断できるデータがない）の 3 つ
- ポイント：アクションは状態が変わったときにだけ動く（Auto Scaling のアクションを除く）。ALARM が続いても通知は繰り返されない

#### 評価期間とアラームを実行するデータポイント（ひょうかきかん / evaluation periods and datapoints to alarm）

- 意味：直近の何個の期間を見るか（N）と、そのうち何個がしきい値を超えたら ALARM にするか（M）
- ポイント：「M out of N」。一瞬の山で鳴らないようにする

#### 欠落データの扱い（けつらくでーた / treat missing data）

- 意味：データが来なかった期間をどう見るかの設定。notBreaching（良い）・breaching（悪い）・ignore（今の状態を保つ）・missing
- ポイント：エラーのときだけ送るメトリクスなら notBreaching。ハートビートのように「来ない＝止まっている」なら breaching

### 賢く鳴らす

#### 複合アラーム（ふくごうあらーむ / composite alarm）

- 意味：ほかのアラームの状態を AND・OR・NOT で組み合わせたルールで状態を決めるアラーム
- ポイント：関連するアラームをまとめて通知の嵐を減らす。SNS・OpsItem・インシデントは出せるが、EC2 アクションや Auto Scaling のアクションは実行できない

#### 異常検出（いじょうけんしゅつ / anomaly detection）

- 意味：過去のデータ（最大 2 週間）を機械学習で学び、想定される値の帯（バンド）を作って、外れたら鳴らす機能
- ポイント：時間・日・週の周期や傾向を考える。昼と夜で普通の値が違うメトリクスに、固定のしきい値の代わりに使う

### 動かす

#### アラームアクション（あらーむあくしょん / alarm actions）

- 意味：状態が変わったときに実行する動き。SNS 通知・Lambda の呼び出し・Auto Scaling・EC2 アクション・OpsItem やインシデントの作成
- ポイント：Lambda を直接呼べる。EC2 アクションは EC2 のメトリクスのアラームだけ

#### EC2 の復旧アクション（ふっきゅうあくしょん / EC2 recover action）

- 意味：システムステータスチェックの失敗（StatusCheckFailed_System）で、インスタンスを別のハードウェアに移して戻すアラームのアクション
- ポイント：インスタンス ID・プライベート IP・Elastic IP・メタデータは同じまま。インスタンスステータスチェック（OS の問題）には使えず、再起動アクションを使う。自動復旧が既定で有効なインスタンスもある

## 14-3 見える化と代表的なメトリクス

### まとめ表

| 見たいもの | メトリクス |
| :-: | :-: |
| ALB 自身が返した 5xx（ターゲットに届かない・タイムアウト） | HTTPCode_ELB_5XX_Count |
| アプリ（ターゲット）が返した 5xx | HTTPCode_Target_5XX_Count |
| 異常なターゲット | UnHealthyHostCount |
| RDS のディスク I/O の詰まり | DiskQueueDepth |
| リードレプリカの遅れ | ReplicaLag |

### ダッシュボードと横断

#### ダッシュボード（だっしゅぼーど / CloudWatch dashboards）

- 意味：メトリクス・ログ・アラームをまとめて表示する画面。複数のリージョンのリソースを 1 つのビューに載せられる
- ポイント：チームで共有して障害時の連絡に使う。複数のアカウントはクロスアカウントオブザーバビリティで

#### クロスアカウントオブザーバビリティ（くろすあかうんと / CloudWatch cross-account observability）

- 意味：モニタリングアカウントを決めてソースアカウントをリンクし、複数のアカウントのメトリクス・ログ・トレースを 1 か所で見る機能
- ポイント：Organizations とつなげられる。共有する名前空間やロググループを絞れる

#### Synthetics の canary（かなりあ / CloudWatch Synthetics canary）

- 意味：スケジュールで動くスクリプトで、エンドポイントや API、画面の操作を外から試し、可用性とレイテンシーを測る仕組み
- ポイント：本物の利用者が来る前・少ない時間帯でも障害に気づける。スクリーンショットも残す

### 代表的なメトリクスと検査

#### ALB の 5xx メトリクス（ごーえっくすえっくす / ALB 5XX metrics）

- 意味：ロードバランサー自身が返した 5xx（HTTPCode_ELB_5XX_Count）と、ターゲットが返した 5xx（HTTPCode_Target_5XX_Count）
- ポイント：502・503・504 が ELB の側だけで増えるなら、ターゲットに届かない・健全なターゲットがない・タイムアウトなどを疑う

#### UnHealthyHostCount（あんへるしーほすとかうんと / UnHealthyHostCount）

- 意味：ALB が異常とみなしたターゲットの数
- ポイント：Minimum の統計で 0 でない状態が続いたら鳴らすのが推奨

#### RDS の主なメトリクス（あーるでぃーえす / RDS metrics）

- 意味：DiskQueueDepth（待っているディスク I/O の数）・ReplicaLag（レプリカの遅れ）・FreeStorageSpace・DatabaseConnections など
- ポイント：DiskQueueDepth が高く読み書きのレイテンシーが上がる → ストレージの I/O が足りない。FreeStorageSpace の不足はストレージの自動スケーリングで

#### Amazon Inspector（いんすぺくたー / Amazon Inspector）

- 意味：EC2・ECR のコンテナイメージ・Lambda を自動で見つけて、ソフトウェアの脆弱性や意図しないネットワークの露出を継続的にスキャンするサービス
- ポイント：組織で有効にでき、新しいアカウントにも自動で入る。結果は Security Hub や EventBridge に流せる

## 問題演習

### 14-1

#### 問 dop-14-o01

- 問：EC2 のメモリ使用率でアラームを出したいが、CloudWatch の AWS/EC2 にメモリのメトリクスがない。どうするか。
- ア：インスタンスに CloudWatch エージェントを入れ、メモリのメトリクスを送る
- イ：詳細モニタリングを有効にする
- ウ：CloudTrail を有効にする
- エ：Container Insights を有効にする
- 正解：ア
- 解説：メモリやディスクの使用率は OS の中の値なので、標準のメトリクスにはない。CloudWatch エージェントで集める。
- アの意味：正しい。
- イの意味：間隔が 1 分になるだけで、メモリは増えない。
- ウの意味：API の記録で、メトリクスではない。
- エの意味：コンテナのためのもので、EC2 のメモリそのものの答えではない。
- 出典：オリジナル問題（根拠：AWS「Amazon CloudWatch ユーザーガイド」CloudWatch エージェントにより収集されるメトリクス（『すぐにプロセスに渡すことができる使用可能なメモリの割合。』））

#### 問 dop-14-o02

- 問：取引システムの注文の処理数を 1 秒単位で見て、10 秒の山でもアラームを出したい。どうするか。
- ア：EC2 の詳細モニタリングを有効にする
- イ：標準解像度のカスタムメトリクスで 60 秒の期間のアラーム
- ウ：メトリクスストリームを作る
- エ：高解像度のカスタムメトリクス（StorageResolution=1）を送り、10 秒の期間のアラームを付ける
- 正解：エ
- 解説：高解像度のメトリクスは 1 秒単位で持て、10 秒か 30 秒の期間のアラームを付けられる。
- アの意味：EC2 のメトリクスが 1 分間隔になるだけ。
- イの意味：1 分未満の山は見えない。
- ウの意味：外へ流す仕組みで、解像度は上がらない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「Amazon CloudWatch ユーザーガイド」カスタムメトリクスを発行する (PutMetricData/EMF)（『高解像度メトリクスでアラームを設定する場合、10 秒または 30 秒の期間で高解像度アラームを指定するか、60 秒の倍数の期間で通常のアラームを設定できます。』））

#### 問 dop-14-o03

- 問：Lambda 関数から注文ごとの処理時間をカスタムメトリクスにしたい。PutMetricData を毎回呼ぶと遅くなり、スロットリングも心配。どうするか。
- ア：関数の中で SNS に送る

- アの意味：メトリクスにはならず、作り込みが要る。
- イの意味：集計を自分で作る必要がある。
- ウの意味：正しい。
- エの意味：トレースの検索用で、CloudWatch のメトリクスではない。
- 出典：オリジナル問題（根拠：AWS「Amazon CloudWatch ユーザーガイド」ログ内へのメトリクスの埋め込み（『CloudWatch 埋め込みメトリクス形式を使用すると、CloudWatch Logs に書き込まれるログの形式でカスタムメトリクスを非同期的に生成できます。』））

#### 問 dop-14-o04

- 問：カスタムメトリクスを Service と Environment のディメンション付きで送っている。ディメンションを付けずに同じメトリクス名で検索したら何も出なかった。なぜか。

#### 問 dop-14-o05

- 問：1 か月前の障害を調べようとしたら、その日のメトリクスが 1 分単位では見られず、5 分単位でしか見られなかった。なぜか。
- ア：1 分のデータポイントは 15 日間だけ使え、そのあとは 5 分に集約されるから
- イ：CloudWatch のメトリクスは 7 日で消えるから
- ウ：詳細モニタリングを無効にしたから
- エ：ダッシュボードの設定の誤り
- 正解：ア
- 解説：1 分は 15 日、5 分は 63 日、1 時間は 455 日。古いデータは長い期間に集約される。細かく残したいならログやメトリクスストリームで S3 に残す。
- アの意味：正しい。
- イの意味：消えるのは 15 か月。
- ウの意味：保持の期間とは関係しない。
- エの意味：表示ではなく、保持のしくみ。
- 出典：オリジナル問題（根拠：AWS「Amazon CloudWatch ユーザーガイド」メトリクスの概念（『+ 期間が 60 秒 (1 分) のデータポイントは、15 日間使用できます。』））

#### 問 dop-14-o06

- 問：全アカウントの CloudWatch メトリクスを、サードパーティの監視ツールにほぼリアルタイムに送りたい。API で定期的に取りに行くのはやめたい。何を使うか。
- ア：GetMetricData を 1 分ごとに呼ぶ Lambda
- イ：CloudWatch Logs のサブスクリプション
- ウ：Firehose を送信先にしたメトリクスストリーム
- エ：ダッシュボードの共有
- 正解：ウ
- 解説：メトリクスストリームはメトリクスを低いレイテンシーで流し続け、Firehose から S3 やサードパーティへ届ける。
