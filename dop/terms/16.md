## 16-1 X-Ray のトレース

### まとめ表

| やりたいこと | 使うもの |
| :-: | :-: |
| 1 件のリクエストがどのサービスで遅いかを追う | X-Ray のトレースとトレースマップ |
| ユーザー ID などで後からトレースを検索する | 注釈（インデックスされる） |
| 検索しない補足情報を残す | メタデータ |
| 記録する量を減らす・特定のパスだけ全件記録 | サンプリングルール |
| 条件に合うトレースをまとめ、障害の急増を知らせる | グループとインサイト |

### トレースのしくみ

#### AWS X-Ray（えっくすれい / AWS X-Ray）

- 意味：アプリへのリクエストが、どのサービス・データベース・外部 API をどの順に通り、どこで時間がかかったかやエラーが出たかを記録して見せる分散トレーシングのサービス
- ポイント：「API の呼び出し履歴（誰が何をしたか）」は CloudTrail。「リクエストの通り道と遅い場所」は X-Ray。サービス間のつながりはトレースマップ（旧サービスマップ）で見る

#### セグメント（せぐめんと / segment）

- 意味：1 つのサービス（コンピューティングリソース）が 1 件のリクエストで行った作業の記録。リソース名・リクエストの内容・処理時間などを持つ
- ポイント：同じリクエストのセグメントを集めたものがトレース。トレース ID でまとめる

#### サブセグメント（さぶせぐめんと / subsegment）

- 意味：セグメントの中の作業を細かく分けた記録。DynamoDB や外部 HTTP の呼び出し、自分のコードの一部の処理時間などを別に記録する
- ポイント：自分でセグメントを送らない DynamoDB などは、呼び出し側のサブセグメントからトレースマップ上に「推測セグメント」として表示される

#### トレースヘッダー（とれーすへっだー / tracing header, X-Amzn-Trace-Id）

- 意味：トレース ID とサンプリングの判断を入れた HTTP ヘッダー。最初のサービスが付け、下流のサービスへ引き継ぐことで、別々のサービスのセグメントが 1 本のトレースにつながる
- ポイント：ヘッダーを引き継がないと、下流のサービスのトレースが別物として切れてしまう

### 検索と量の調整

#### 注釈（ちゅうしゃく / annotation）

- 意味：トレースに付けるキーと値の組で、インデックスされるのでフィルタ式で検索できる
- ポイント：「後で検索したい」なら注釈。値は文字列・数値・真偽値

#### メタデータ（めたでーた / metadata）

- 意味：トレースに付けるキーと値の組で、オブジェクトやリストも入れられるが、インデックスされないので検索には使えない
- ポイント：「検索しないが、見たときに参考にしたい」詳細データを入れる。注釈との違いがよく問われる

#### サンプリングルール（さんぷりんぐるーる / sampling rule）

- 意味：どのリクエストをどれだけ記録するかを決めるルール。リザーバー（1 秒あたり必ず記録する件数）と固定レート（それを超えた分の割合）で決める
- ポイント：既定は「1 秒ごとに最初の 1 件と、それ以外の 5%」。サービス名・URL パス・HTTP メソッドなどで条件を絞れる
- 例：/health は記録しない（レート 0）、/checkout は全件記録する

#### グループ（ぐるーぷ / group）

- 意味：フィルタ式で条件を書いて、それに合うトレースをまとめたもの。グループ単位でトレースマップやメトリクスを見られる
- ポイント：グループごとにインサイトとその通知を有効にできる

#### フィルタ式（ふぃるたしき / filter expression）

- 意味：応答時間・エラーの有無・注釈の値などでトレースを絞り込む式
- 例：responsetime > 2 AND annotation.tenant = "A"

#### X-Ray インサイト（いんさいと / X-Ray Insights）

- 意味：障害の率がふだんの範囲を超えたときに自動で検出し、問題として記録して解決まで影響を追うしくみ
- ポイント：インサイトの通知は EventBridge に送れる。しきい値を自分で決めなくてよいのが特徴

### 送るしくみ

#### X-Ray デーモン（でーもん / X-Ray daemon）

- 意味：UDP ポート 2000 でアプリ（SDK）からのセグメントを受け取り、まとめて X-Ray の API に送るプログラム
- ポイント：EC2 では自分で入れて、インスタンスプロファイルに書き込み権限（AWSXRayDaemonWriteAccess）を付ける。ECS ではサイドカーのコンテナとして動かし、タスクロールに権限を付ける。Elastic Beanstalk はプラットフォームに含まれていて設定で有効にするだけ

#### Lambda のトレース（Active / PassThrough）

- 意味：Lambda の関数設定で Active トレースを有効にすると、Lambda が呼び出しのセグメントを自動で X-Ray に送る。PassThrough はトレースのコンテキストを下流に伝えるだけ
- ポイント：Lambda ではデーモンを入れる必要はない。実行ロールに X-Ray への書き込み権限が要る

#### API Gateway のトレース（えーぴーあいげーとうぇいのとれーす / API Gateway active tracing）

- 意味：API のステージで X-Ray のトレースを有効にすると、受けたリクエストをサンプリングして X-Ray に送る
- ポイント：ステージ単位の設定。サンプリングルールで記録の量を調整する

## 16-2 アプリの監視（ADOT・Application Signals・SLO・RUM）

### まとめ表

| 見たいもの | 使うもの |
| :-: | :-: |
| 一度の計装でトレースとメトリクスを複数の送り先へ | ADOT（OpenTelemetry） |
| サービスごとの呼び出し数・レイテンシー・エラーを自動で | Application Signals |
| 目標（99.9% など）を守れているか | SLO（SLI で測る） |
| 実ユーザーのブラウザでの体験 | RUM |

### 計装と自動収集

#### ADOT（えーでぃーおーてぃー / AWS Distro for OpenTelemetry）

- 意味：OpenTelemetry の AWS 版の配布物。アプリを一度計装すれば、トレースとメトリクスを CloudWatch・X-Ray・Amazon Managed Service for Prometheus など複数に送れる
- ポイント：X-Ray SDK とデーモンは 2026 年 2 月 25 日にメンテナンスモード（セキュリティ修正のみ）に移ったので、新しく計装するなら OpenTelemetry（ADOT）がすすめられる
- 語の意味：Distro＝配布物、OpenTelemetry＝トレース・メトリクス・ログを集める業界標準の仕様とツール

#### CloudWatch Application Signals（あぷりけーしょんしぐなるず / Application Signals）

- 意味：EC2・ECS・EKS・Lambda などのアプリから、メトリクスとトレースを自動で集め、呼び出し量・可用性・レイテンシー・障害・エラーを標準のダッシュボードで見せる機能
- ポイント：アプリのコードを書き換えずに APM（アプリの性能監視）ができる。SLO もここで作る

### 目標と実ユーザー

#### SLO（えすえるおー / Service Level Objective）

- 意味：サービスの品質の目標。「30 日間で可用性 99.9%」のように、SLI（測る指標）と目標値と期間で決める
- ポイント：SLA（顧客との契約）を守れているかの確認に使う。目標を下回るまでの余裕（エラーバジェット）が減ったらアラームを出せる
- 語の意味：Service Level＝サービスの水準、Objective＝目標

#### SLI（えすえるあい / Service Level Indicator）

- 意味：サービスの品質を測る指標。可用性（成功した呼び出しの割合）やレイテンシーなど
- ポイント：SLO を作るときにまず決めるもの。RTO・RPO（災害対策の目標）と混同しない
- 語の意味：Indicator＝指標

#### CloudWatch RUM（らむ / Real User Monitoring）

- 意味：実際のユーザーのブラウザから、ページのロード時間・JavaScript のエラー・操作などを集める機能。ページに小さなスクリプトを入れる
- ポイント：データは 30 日で消えるので、長く残すならアプリモニターで CloudWatch Logs にコピーを送る。人のいない時間も決まった手順で確かめるのは Synthetics（Canary）
- 語の意味：Real User＝実際の利用者、Monitoring＝監視

## 16-3 ヘルスチェックと AWS Health

### まとめ表

| どこで | 何が異常を見つけるか | そのあと |
| :-: | :-: | :-: |
| EC2 | システム／インスタンスのステータスチェック | アラームで復旧・再起動 |
| Auto Scaling | EC2 チェック＋（有効にすれば）ELB チェック | インスタンスを置き換え |
| ECS | コンテナの healthCheck | タスクを置き換え |
| EKS | liveness / readiness / startup プローブ | 再起動・振り分けから外す |
| AWS 側の障害・予定 | AWS Health | EventBridge で自動対応 |

### EC2 と Auto Scaling

#### システムステータスチェック（しすてむすてーたすちぇっく / system status check）

- 意味：インスタンスが動いている AWS 側のホストやネットワーク・電源を確かめるチェック。失敗すると StatusCheckFailed_System が増える
- ポイント：直すには AWS の関与が要る。停止して起動すれば別のホストに移る。CloudWatch アラームの「復旧（recover）」アクションで自動で移せる

#### インスタンスステータスチェック（いんすたんすすてーたすちぇっく / instance status check）

- 意味：インスタンスの OS やネットワーク設定を確かめるチェック。失敗すると StatusCheckFailed_Instance が増える
- ポイント：メモリ不足・ファイルシステムの破損・カーネルの問題など、自分で直す問題（再起動や設定の修正）

#### Auto Scaling のヘルスチェックタイプ（へるすちぇっくたいぷ / health check type）

- 意味：Auto Scaling がインスタンスを「異常」と判断する根拠。EC2 のステータスチェックは常に使われ、ELB・VPC Lattice・EBS・カスタムのヘルスチェックは有効にしたときだけ使われる
- ポイント：ロードバランサーの背後で「アプリが 500 を返しても置き換わらない」なら ELB ヘルスチェックが有効になっていない。カスタムは SetInstanceHealth で異常を知らせる

#### ヘルスチェックの猶予期間（ゆうよきかん / health check grace period）

- 意味：新しく起動したインスタンスを、ヘルスチェックに失敗しても終了しないで待つ時間。コンソールの既定は 300 秒
- ポイント：起動に時間がかかるアプリで「起動しては終了」を繰り返すなら延ばす。ライフサイクルフックで起動を待つ場合は 0 にできる

#### NLB のヘルスチェック（えぬえるびーのへるすちぇっく / Network Load Balancer health check）

- 意味：NLB がターゲットに定期的に TCP・HTTP・HTTPS で確かめ、合格したターゲットにだけ通信を送るしくみ
- ポイント：すべての AZ ですべてのターゲットが失敗すると、全部に送る（フェイルオープン）

### コンテナ

#### ECS コンテナのヘルスチェック（こんてなのへるすちぇっく / container health check）

- 意味：タスク定義の healthCheck に書いたコマンドをコンテナの中で実行して正常かを確かめる。interval（間隔）・timeout・retries（再試行回数）・startPeriod（起動中の猶予）を決める
- ポイント：タスクの正常性は「必須（essential）で、ヘルスチェックを持つコンテナ」で決まる。シェルの機能（パイプや ||）を使うなら CMD-SHELL、使わないなら CMD
- 例：CMD-SHELL, curl -f http://localhost/ || exit 1

#### startPeriod（すたーとぴりおど / start period）

- 意味：コンテナの起動直後、ヘルスチェックに失敗しても再試行回数に数えない時間
- ポイント：既定では無効。起動の遅いアプリが起動中に UNHEALTHY にされて止められる問題を防ぐ

#### Kubernetes のプローブ（ぷろーぶ / liveness, readiness, startup probe）

- 意味：liveness は動いているか（失敗したらコンテナを再起動）、readiness はリクエストを受けられるか（失敗したら Service の振り分けから外す）、startup は起動が終わったか（終わるまで他の 2 つを待たせる）
- ポイント：「プロセスは動いているのに応答しない（デッドロック）」を見つけるのは liveness

### AWS Health

#### AWS Health（へるす / AWS Health）

- 意味：AWS 側の障害・予定されたメンテナンス・アカウントへの通知などの「イベント」で、自分のリソースへの影響を知らせるサービス。AWS Health Dashboard で見られる
- ポイント：全体の障害（パブリック）と自分のアカウントのリソースに関するもの（アカウント固有）がある。EC2 の予定された再起動などもここに出る

#### AWS Health と EventBridge（いべんとぶりっじ / AWS Health events in EventBridge）

- 意味：AWS Health のイベントを EventBridge のルールで受け、Lambda・SNS・Systems Manager Automation などで自動で対応するしくみ
- ポイント：追加料金なし。ルールが受けるのは自分のアカウントの通知だけなので、組織全体なら組織ビューを使う
- 例：EC2 の予定されたメンテナンスのイベントで、Automation を動かしてインスタンスを停止・起動する

#### AWS Health の組織ビュー（そしきびゅー / organizational view）

- 意味：Organizations の全アカウントの AWS Health イベントを 1 か所に集めて見るしくみ
- ポイント：委任管理者を設定して、管理アカウントを使わずに運用チームのアカウントから見るのがベストプラクティス

## 問題演習

### 16-1

#### 問 dop-16-o01

- 問：マイクロサービスで作られた注文システムが、ときどき遅くなる。1 件のリクエストが、どのサービスやデータベースの呼び出しで時間を使っているかを追いたい。何を使うか。
- ア：AWS CloudTrail
- イ：AWS X-Ray
- ウ：VPC フローログ
- エ：AWS Config
- 正解：イ
- 解説：X-Ray は同じリクエストのセグメントをトレースにまとめ、どのサービスでどれだけ時間がかかったかを見せる。
- アの意味：AWS の API を誰がいつ呼んだかの記録。アプリの中の処理時間はわからない。
- イの意味：正しい。
- ウの意味：IP アドレスとポートの通信の記録。どの処理が遅いかはわからない。
- エの意味：リソースの設定の履歴と準拠の評価。
- 出典：オリジナル問題（根拠：AWS「AWS X-Ray デベロッパーガイド」AWS X-Ray の概念（『X-Ray は、*トレース*への共通リクエストを含むセグメントをグループ化します。』））

#### 問 dop-16-o02

- 問：遅いリクエストを、後から顧客 ID で検索して調べたい。X-Ray のトレースに顧客 ID を何として付けるか。
- ア：注釈
- イ：メタデータ
- ウ：サブセグメント
- エ：トレースヘッダー
- 正解：ア
- 解説：注釈はインデックスされるので、フィルタ式で検索できる。
- アの意味：正しい。
- イの意味：インデックスされないので検索に使えない。
- ウの意味：処理の一部の時間を分けて記録するもの。検索のキーではない。
- エの意味：トレース ID を下流に引き継ぐ HTTP ヘッダー。
- 出典：オリジナル問題（根拠：AWS「AWS X-Ray デベロッパーガイド」AWS X-Ray の概念（『**注釈**は、「フィルタ式」で使用するためにインデックス化されたシンプルなキーと値のペアです。』））

#### 問 dop-16-o03

- 問：Lambda 関数の処理時間のうち、DynamoDB の呼び出しにかかった時間を分けて見たい。X-Ray で何として記録するか。
- ア：注釈
- イ：グループ
- ウ：新しいトレース
- エ：サブセグメント
- 正解：エ
- 解説：セグメントの中の作業を細かく分けたものがサブセグメント。DynamoDB の呼び出しを 1 つのサブセグメントにする。
- アの意味：検索用のキーと値。時間の内訳ではない。
- イの意味：フィルタ式でトレースをまとめる設定。
- ウの意味：別のトレースにすると、元のリクエストとつながらない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「AWS X-Ray デベロッパーガイド」AWS X-Ray の概念（『セグメントでは、完了した作業に関するデータを**サブセグメント**に分けることができます。』））

#### 問 dop-16-o04

- 問：X-Ray SDK の既定のサンプリングはどれか。
- ア：すべてのリクエストを記録する
- イ：1% のリクエストを記録する
- ウ：1 秒ごとに最初のリクエストを記録し、それ以外のリクエストの 5% を記録する
- エ：1 秒ごとに 10 件まで記録し、それ以外は記録しない
- 正解：ウ
- 解説：既定はリザーバー 1 件と固定レート 5%。少ない量でも、毎秒少なくとも 1 件は必ず記録される。
- アの意味：量と費用が多すぎるので既定ではない。
- イの意味：割合が違い、毎秒 1 件の保証もない。
