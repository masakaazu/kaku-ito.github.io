## 11-1 トラフィックの振り分けと切り替え

### まとめ表

| やりたいこと | 使うもの |
| :-: | :-: |
| 本番が落ちたら待機側へ（アクティブ/パッシブ） | Route 53 フェイルオーバールーティング＋ヘルスチェック |
| 一部の割合だけ新しい環境へ | 加重ルーティング |
| ユーザーに近い（速い）リージョンへ | レイテンシールーティング |
| 国・地域ごとに決まった先へ | 位置情報ルーティング |
| 固定 IP で、DNS のキャッシュに左右されずに切り替え | Global Accelerator |
| CloudFront のオリジンが落ちたら別のオリジンへ | オリジンフェイルオーバー（オリジングループ） |
| 1 つの AZ だけおかしいときに外す | ARC ゾーンシフト |

### Route 53 のルーティング

#### フェイルオーバールーティング（ふぇいるおーばーるーてぃんぐ / failover routing policy）

- 意味：プライマリが正常ならプライマリへ、異常ならセカンダリへ DNS の答えを切り替えるルーティングポリシー
- ポイント：アクティブ/パッシブ構成。プライマリにヘルスチェック（またはエイリアスの Evaluate Target Health）を付けないと切り替わらない

#### 加重ルーティング（かじゅうるーてぃんぐ / weighted routing policy）

- 意味：レコードに付けた重みの比率で、複数のリソースにトラフィックを分けるルーティングポリシー
- ポイント：重み 1 と 255 なら 1/256 だけ新しい方へ。重み 0 で送るのを止める。重みが 0 より大きいレコードが全部異常なら、重み 0 のレコードが使われる
- 例：ブルー/グリーンで、新しい環境に 10% だけ流して様子を見る

#### レイテンシールーティング（れいてんしーるーてぃんぐ / latency-based routing policy）

- 意味：複数のリージョンにリソースがあるとき、ユーザーからのレイテンシーが低いリージョンを答えるルーティングポリシー
- ポイント：「近い国」ではなく「速いリージョン」。国で決めたいなら位置情報ルーティング

#### 位置情報ルーティング（いちじょうほうるーてぃんぐ / geolocation routing policy）

- 意味：ユーザーの位置（大陸・国・州）に応じて答えを変えるルーティングポリシー
- ポイント：法令や言語で「この国のユーザーはこのリージョン」と決めたいとき。どれにも当たらないユーザー用にデフォルトのレコードを作る

#### エイリアスレコード（えいりあすれこーど / alias record）

- 意味：CloudFront・ALB・S3 などの AWS リソースや、同じホストゾーンの別のレコードを指す、Route 53 独自のレコード
- ポイント：CNAME と違い、ゾーンの頂点（example.com）にも作れる。Evaluate Target Health を Yes にすると、指す先（ALB のターゲットなど）の正常性で切り替わる

### ヘルスチェック

#### Route 53 ヘルスチェック（へるすちぇっく / Route 53 health check）

- 意味：世界中のヘルスチェッカーからエンドポイントを調べ、正常か異常かを決める仕組み。DNS フェイルオーバーの元になる
- ポイント：18% を超えるチェッカーが正常と報告すれば正常。インターネットから届かないプライベートなリソースは、CloudWatch アラームを監視するヘルスチェックで代わりに見る

#### 計算されたヘルスチェック（けいさんされたへるすちぇっく / calculated health check）

- 意味：ほかのヘルスチェック（子）の結果をまとめて、「何個以上が正常なら正常」と判断する親のヘルスチェック
- ポイント：最大 255 の子を見られる。「Web と DB の両方が正常なときだけ正常」のような判断に使う

#### CloudWatch アラームのヘルスチェック（くらうどうぉっちあらーむのへるすちぇっく / health check that monitors a CloudWatch alarm）

- 意味：CloudWatch アラームのデータストリームを見て、正常か異常かを決めるヘルスチェック
- ポイント：VPC の中のリソースや、エラー率などのメトリクスで切り替えたいときに使う。同じアカウントのアラームだけ見られる

### DNS 以外の切り替え

#### Global Accelerator（ぐろーばるあくせられーた / AWS Global Accelerator）

- 意味：AWS のエッジからエニーキャストで広告される固定の IP アドレスを入り口にし、AWS のネットワークで最適なリージョンのエンドポイント（ALB・NLB・EC2・EIP）へ送るサービス
- ポイント：IP が変わらないので、取引先のファイアウォールの許可リストに載せやすい。DNS のキャッシュに左右されず、エンドポイントのヘルスで素早く切り替わる

#### オリジンフェイルオーバー（おりじんふぇいるおーばー / CloudFront origin failover）

- 意味：プライマリとセカンダリの 2 つのオリジンをオリジングループにまとめ、プライマリが使えないか決めたステータスコードを返したら、CloudFront がセカンダリに切り替える機能
- ポイント：切り替わるのは GET・HEAD・OPTIONS のリクエストだけ。POST や PUT は切り替わらない

#### ARC ゾーンシフト（ぞーんしふと / ARC zonal shift）

- 意味：Amazon Application Recovery Controller（ARC）の機能で、障害のある 1 つの AZ から、同じリージョンの正常な AZ にトラフィックを一時的に移す
- ポイント：悪いデプロイや AZ の障害からすばやく回復する。AWS が自動で行うゾーンオートシフトもある。リージョンの切り替えはルーティングコントロールとリージョン切り替え

## 11-2 計算層を複数の AZ に

### まとめ表

| 部品 | 単一障害点をなくす方法 |
| :-: | :-: |
| EC2 | Auto Scaling グループを複数の AZ に |
| ロードバランサー | 複数の AZ のサブネットを有効にする（クロスゾーン負荷分散） |
| NAT ゲートウェイ | AZ ごとに 1 つ置き、ルートテーブルも AZ ごとに |
| キャッシュ | ElastiCache のマルチ AZ（自動フェイルオーバー） |

### ロードバランサーと Auto Scaling

#### クロスゾーン負荷分散（くろすぞーんふかぶんさん / cross-zone load balancing）

- 意味：ロードバランサーの各ノードが、有効なすべての AZ のターゲットにトラフィックを分ける設定
- ポイント：AZ ごとのターゲットの数が違っても、全ターゲットに均等に配れる。ALB ではロードバランサーのレベルで常に有効（ターゲットグループで無効にはできる）

#### ターゲットのヘルスチェック（たーげっとのへるすちぇっく / target group health check）

- 意味：ロードバランサーが各ターゲットを定期的に調べ、正常なターゲットにだけリクエストを送る仕組み
- ポイント：UnhealthyThresholdCount 回続けて失敗すると外し、HealthyThresholdCount 回続けて成功すると戻す。全ターゲットが異常だと、全部に送るフェールオープンになる

#### マルチ AZ の Auto Scaling グループ（まるちえーぜっとのおーとすけーりんぐぐるーぷ / multi-AZ Auto Scaling group）

- 意味：複数の AZ のサブネットを指定し、インスタンスを AZ に分けて起動する Auto Scaling グループ
- ポイント：1 つの AZ が使えなくなると、ほかの AZ で起動して補う。ELB のヘルスチェックをグループのヘルスチェックに使うと、アプリが応答しないインスタンスも入れ替わる

### 考え方

#### 単一障害点（たんいつしょうがいてん / single point of failure, SPOF）

- 意味：そこが 1 つ壊れるだけで、システム全体が止まる部品
- ポイント：1 つの AZ にだけある NAT ゲートウェイ、シングル AZ の RDS、1 台だけの EC2 など。見つけて複数の AZ に分ける
- 語の意味：Single＝1 つの、Point＝点、Of Failure＝故障の

#### SLA（えすえるえー / Service Level Agreement）

- 意味：サービスの提供者が約束する可用性などの水準。下回るとサービスクレジットが返る
- ポイント：ビジネスの要件（例 99.99%）を、どの構成なら満たせるかに置き換える。DynamoDB は単一リージョンのテーブルで 99.99%、グローバルテーブルで 99.999%
- 語の意味：Service＝サービス、Level＝水準、Agreement＝合意

#### ElastiCache のマルチ AZ（えらすてぃきゃっしゅのまるちえーぜっと / ElastiCache Multi-AZ）

- 意味：プライマリノードの障害時に、別の AZ のリードレプリカを自動でプライマリに昇格させる設定
- ポイント：プライマリエンドポイントの DNS が新しいプライマリを指すので、アプリの接続先は変えなくてよい

## 11-3 データ層のレプリケーション

### まとめ表

| サービス | 同じリージョン（AZ をまたぐ） | 別のリージョン |
| :-: | :-: | :-: |
| RDS | マルチ AZ（同期のスタンバイ、読めない）／マルチ AZ DB クラスター（読める 2 台） | クロスリージョンリードレプリカ（非同期、昇格して使う） |
| Aurora | 3 つの AZ に 6 つのコピー、Aurora レプリカ最大 15 | Aurora Global Database（通常 1 秒未満） |
| DynamoDB | もともと複数の AZ | グローバルテーブル（マルチアクティブ） |
| S3 | もともと複数の AZ | CRR・S3 RTC・マルチリージョンアクセスポイント |

### RDS と Aurora

#### RDS マルチ AZ DB インスタンス（あーるでぃーえすまるちえーぜっと / Multi-AZ DB instance deployment）

- 意味：別の AZ に同期のスタンバイを置き、障害時に自動でフェイルオーバーする RDS の構成
- ポイント：スタンバイは読めない（読み取りのスケールではない）。フェイルオーバーは通常 60〜120 秒で、DNS がスタンバイを指すように変わる。アプリはエンドポイント名でつなぎ、DNS を長くキャッシュしない

#### RDS マルチ AZ DB クラスター（まるちえーぜっとでぃーびーくらすたー / Multi-AZ DB cluster deployment）

- 意味：3 つの AZ にライター 1 台と、読み取りもできるリーダー 2 台を置く RDS の構成
- ポイント：少なくとも 1 台のリーダーが受け取ったらコミットする（準同期）。「高可用性と読み取りの両方」がほしいとき

#### リードレプリカ（りーどれぷりか / read replica）

- 意味：プライマリの変更を非同期でコピーした、読み取り用の DB インスタンス。別のリージョンにも作れる
- ポイント：読み取りのスケールと災害対策に使う。障害時は手動でスタンドアロンに昇格させる（自動のフェイルオーバーではない）

#### Aurora Global Database（おーろらぐろーばるでーたべーす / Amazon Aurora Global Database）

- 意味：1 つのプライマリリージョンと、最大 10 の読み取り専用のセカンダリリージョンからなる Aurora の構成。専用の基盤で通常 1 秒未満で複製する
- ポイント：リージョン全体の障害から、低い RTO と少ないデータ損失で回復できる。書き込み転送でセカンダリから書き込みをプライマリに送れる

#### スイッチオーバーとフェイルオーバー（すいっちおーばー / switchover and failover）

- 意味：Aurora Global Database で、セカンダリをプライマリに昇格させる 2 つの方法。スイッチオーバーは計画した切り替え、フェイルオーバーは計画外の障害からの回復
- ポイント：スイッチオーバー（旧名「計画されたマネージドフェイルオーバー」）は全部が正常なときに使い、データを失わない。フェイルオーバーは複製の遅れの分だけデータを失いうる

### DynamoDB と S3

#### DynamoDB グローバルテーブル（ぐろーばるてーぶる / DynamoDB global tables）

- 意味：複数のリージョンにレプリカを持ち、どのレプリカでも読み書きできるマルチアクティブな DynamoDB の機能
- ポイント：既定は MREC（結果整合、通常 1 秒以内に非同期で複製）。同じ項目を同時に変えたら最終書き込み者優先。MRSC（強力な整合性）も選べる

#### S3 レプリケーション（えすすりーれぷりけーしょん / S3 Replication: CRR・SRR）

- 意味：バケットのオブジェクトを別のバケットへ自動でコピーする機能。別のリージョンへは CRR、同じリージョンへは SRR
- ポイント：コピー元とコピー先の両方でバージョニングを有効にする必要がある。設定前からある既存のオブジェクトはバッチレプリケーションでコピーする
- 語の意味：CRR＝Cross-Region Replication（リージョンをまたぐ複製）、SRR＝Same-Region Replication（同じリージョン内の複製）

#### S3 Replication Time Control（えすすりーあーるてぃーしー / S3 RTC）

- 意味：新しいオブジェクトの 99.99% を 15 分以内に複製すると SLA で約束するオプション
- ポイント：「複製の時間を約束したい・遅れを監視したい」ならこれ。15 分を超えたらイベント通知が来る。バッチレプリケーションには効かない

#### S3 マルチリージョンアクセスポイント（まるちりーじょんあくせすぽいんと / S3 Multi-Region Access Points）

- 意味：複数のリージョンのバケットに 1 つのグローバルなエンドポイントで届き、近いリージョンへ自動で送るアクセスポイント
- ポイント：アクティブ-アクティブとアクティブ/パッシブを選べ、フェイルオーバーコントロールで切り替えられる。バケットどうしの複製は S3 レプリケーションで別に設定する

## 問題演習

### 11-1

#### 問 dop-11-o01

- 問：東京リージョンが本番、大阪リージョンが待機のアクティブ/パッシブ構成にしたい。東京の ALB が異常になったら、DNS の答えを大阪に切り替える。Route 53 で何を設定するか。
- ア：加重ルーティングで東京 100・大阪 0
- イ：フェイルオーバールーティング（東京をプライマリ）と、東京へのヘルスチェック（または Evaluate Target Health）
- ウ：レイテンシールーティング
- エ：複数値回答ルーティング
- 正解：イ
- 解説：アクティブ/パッシブはフェイルオーバールーティング。プライマリの正常性をヘルスチェックか Evaluate Target Health で見ていないと切り替わらない。
- アの意味：重み 0 のレコードは、ほかが全部異常なときに使われはするが、アクティブ/パッシブを作る本来の方法ではない。
- イの意味：正しい。
- ウの意味：速い方に送るもので、平常時も大阪に流れることがある。
- エの意味：正常なレコードを最大 8 つ返すもので、待機側を決められない。
- 出典：オリジナル問題（根拠：AWS「Amazon Route 53 デベロッパーガイド」ルーティングポリシーの選択（『フェイルオーバールーティングポリシー – アクティブ/パッシブフェイルオーバーを構成する場合に使用します。』））

#### 問 dop-11-o02

- 問：新しいリージョンの環境に、まず全体の 5% だけのユーザーを DNS で送り、問題がなければ少しずつ増やしたい。どのルーティングポリシーか。
- ア：加重ルーティング
- イ：位置情報ルーティング
- ウ：フェイルオーバールーティング
- エ：シンプルルーティング
- 正解：ア
- 解説：加重ルーティングはレコードの重みの比率で送る。重みを変えるだけで割合を少しずつ変えられる。
- アの意味：正しい。
- イの意味：国や地域で決まり、割合では分けられない。
- ウの意味：正常か異常かで切り替えるだけで、割合で分けない。
- エの意味：1 つのリソースだけを答える。
- 出典：オリジナル問題（根拠：AWS「Amazon Route 53 デベロッパーガイド」加重ルーティング（『重みを変更することで、バランスを徐々に変更できます。』））

#### 問 dop-11-o03

- 問：米国・欧州・アジアのリージョンに同じアプリがある。各ユーザーを、応答が最も速いリージョンに送りたい。どのルーティングポリシーか。
- ア：位置情報ルーティング
- イ：地理的近接性ルーティング
- ウ：加重ルーティング
