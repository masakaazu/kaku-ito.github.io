## 04-1 CodeDeploy のしくみ

### まとめ表

| プラットフォーム | デプロイタイプ | デプロイ設定の例 | エージェント |
| :-: | :-: | :-: | :-: |
| EC2/オンプレミス | インプレース・Blue/Green（EC2 のみ） | AllAtOnce・HalfAtATime・OneAtATime | 要る |
| AWS Lambda | Blue/Green（トラフィックの移行） | LambdaCanary10Percent5Minutes など | 要らない |
| Amazon ECS | Blue/Green（タスクセット） | ECSLinear10PercentEvery1Minutes など | 要らない |

### CodeDeploy の部品

#### AWS CodeDeploy（こーどでぷろい / AWS CodeDeploy）

- 意味：EC2 インスタンス・オンプレミスのサーバー・Lambda 関数・ECS サービスへのアプリのデプロイを自動化するサービス
- ポイント：リビジョンは S3・GitHub・Bitbucket から取る。失敗やアラームで止めてロールバックできる。CodePipeline の deploy アクションとしてよく使う

#### アプリケーション（CodeDeploy）（あぷりけーしょん / application）

- 意味：デプロイするアプリを表す名前で、デプロイグループとリビジョンをまとめる入れ物
- ポイント：作るときにコンピューティングプラットフォーム（EC2/オンプレミス・Lambda・ECS）を選ぶ

#### デプロイグループ（でぷろいぐるーぷ / deployment group）

- 意味：デプロイ先のまとまり。EC2/オンプレミスでは、タグで選んだインスタンスや Auto Scaling グループ内のインスタンスのセット
- ポイント：デプロイ設定・ロードバランサー・アラーム・自動ロールバック・トリガー（SNS）などをデプロイグループに設定する。開発・ステージング・本番でデプロイグループを分ける

#### リビジョン（りびじょん / revision）

- 意味：デプロイするもの。EC2/オンプレミスでは AppSpec ファイルとアプリのファイル（実行ファイル・設定ファイルなど）の組み合わせ
- ポイント：S3 に zip で置くか GitHub に置く。Lambda・ECS のリビジョンは AppSpec ファイル（関数のバージョンやタスク定義を指す）

#### AppSpec ファイル（あっぷすぺっくふぁいる / application specification file）

- 意味：CodeDeploy がデプロイのやり方を読む、CodeDeploy 専用の YAML（または JSON）ファイル。EC2/オンプレミスでは appspec.yml をリビジョンのルートに置く
- ポイント：files（どこにコピーするか）・permissions・hooks（ライフサイクルイベントで動かすスクリプト）を書く。Lambda・ECS では、検証用の Lambda 関数を hooks に書く
- 語の意味：AppSpec＝application specification（アプリケーションの仕様）

#### CodeDeploy エージェント（えーじぇんと / CodeDeploy agent）

- 意味：インスタンスに入れて、CodeDeploy のデプロイで使えるようにするソフトウェア
- ポイント：EC2/オンプレミスのときだけ要る（Lambda・ECS は不要）。エージェントが CodeDeploy をポーリングし、S3・GitHub からリビジョンを取って AppSpec の手順を実行する。インスタンスには S3 を読める IAM インスタンスプロファイルを付ける（オンプレミスは IAM ユーザーかロールで登録）。Systems Manager で入れるのが楽

#### デプロイ設定（でぷろいせってい / deployment configuration）

- 意味：デプロイ中に CodeDeploy が使う規則と、成功・失敗の条件
- ポイント：EC2/オンプレミスでは「正常なホストの最小数」で速さと可用性を決める。Lambda・ECS ではトラフィックの移し方（Canary・線形・一度にすべて）を決める。自分で作るカスタムのデプロイ設定もできる

#### 正常なホストの最小数（せいじょうなほすとのさいしょうすう / minimum healthy hosts）

- 意味：デプロイ中のどの時点でも使えなければならないインスタンスの数か割合
- ポイント：AllAtOnce＝できるだけ多くに一度に（1 台でも成功すれば成功）、HalfAtATime＝最大半分ずつ（端数切り捨て）、OneAtATime＝1 台ずつ（最も安全で遅い）。アベイラビリティーゾーンごとの最小数（ゾーン設定）はカスタムで設定する
- 例：9 台で HalfAtATime → 同時に 4 台まで、5 台以上で成功ならデプロイ成功

## 04-2 フック・ロールバック・Auto Scaling

### まとめ表

| EC2/オンプレミスのフック（インプレース） | 使いみち |
| :-: | :-: |
| ApplicationStop | 今のアプリを止める（初回のデプロイでは動かない） |
| （DownloadBundle） | エージェントがリビジョンを取る（スクリプト不可） |
| BeforeInstall | 復号・今のバージョンのバックアップ |
| （Install） | ファイルをコピー（スクリプト不可） |
| AfterInstall | 設定・ファイルの権限の変更 |
| ApplicationStart | 止めたサービスを起動 |
| ValidateService | 最後。デプロイがうまくいったかを確かめる |

### ライフサイクルイベントフック

#### ライフサイクルイベントフック（らいふさいくるいべんとふっく / lifecycle event hooks）

- 意味：デプロイの決まった段階で、AppSpec の hooks に書いたスクリプトや Lambda 関数を実行する仕組み
- ポイント：EC2/オンプレミスはインスタンスの上でスクリプトを動かす。Lambda・ECS は検証用の Lambda 関数を呼び、その関数が成功・失敗を CodeDeploy に返す

#### ValidateService（ばりでーとさーびす / ValidateService）

- 意味：EC2/オンプレミスのデプロイで最後に動くフック。デプロイがうまくいったかを確かめる
- ポイント：ヘルスチェックの URL を叩くなどのテストを書く。失敗すればそのインスタンスのデプロイは失敗になり、自動ロールバックにつなげられる

#### BeforeBlockTraffic・BeforeAllowTraffic（びふぉーぶろっくとらふぃっく・びふぉーあらうとらふぃっく / BeforeBlockTraffic・BeforeAllowTraffic）

- 意味：ロードバランサーから外す前（BeforeBlockTraffic）や、ロードバランサーに登録する前（BeforeAllowTraffic）に、インスタンスでタスクを実行するフック
- ポイント：BlockTraffic・AllowTraffic そのものはエージェント用でスクリプトを書けない。Lambda・ECS にも BeforeAllowTraffic・AfterAllowTraffic があり、ECS にはテストリスナー用の AfterAllowTestTraffic もある

### 止める・戻す

#### 自動ロールバック（じどうろーるばっく / automatic rollback）

- 意味：デプロイが失敗したときや、アラームのしきい値に達したときに、最後に成功したリビジョンに自動で戻す設定
- ポイント：ロールバックは前のリビジョンを新しいデプロイ ID で再デプロイするもので、前のデプロイを復元するのではない。デプロイグループで設定し、デプロイごとに上書きもできる。SNS で通知できる

#### CloudWatch アラームによる停止（あらーむによるていし / CloudWatch alarm monitoring）

- 意味：デプロイグループにアラームを付け、メトリクスがしきい値を超えたらデプロイを止める設定
- ポイント：アラームは先に CloudWatch で作っておく。「アラームのしきい値が一致したときにロールバックする」と組み合わせる。Lambda・ECS では関数のエラーなどのアラームを使う
- 例：5XX エラーの率が上がったら、Canary の途中でも止めて戻す

#### 終了デプロイ（しゅうりょうでぷろい / termination deployment）

- 意味：Auto Scaling のスケールインでインスタンスが消える直前に、CodeDeploy が動かす特別なデプロイ
- ポイント：何もデプロイせず、BeforeBlockTraffic などのフックだけを動かす。デプロイグループで「Auto Scaling グループに終了フックを追加」をオンにすると有効になる。失敗してもインスタンスの終了は続く

#### 古いインスタンスの自動更新（ふるいいんすたんすのじどうこうしん / automatic updates to outdated instances）

- 意味：デプロイ中のスケールアウトで、前のリビジョンのまま起動したインスタンスを、デプロイの直後に追加のデプロイで最新にする動き（既定）
- ポイント：新しいインスタンスには「最後に成功したリビジョン」が入るので、デプロイ中にスケールアウトすると古いリビジョンが混ざる。1 つの Auto Scaling グループに複数のデプロイグループを付けると問題が起きやすい

## 04-3 デプロイ戦略

### まとめ表

| 方法 | 失敗の影響 | 時間 | ダウンタイムなし | ロールバック |
| :-: | :-: | :-: | :-: | :-: |
| 一括（インプレース） | ダウンタイム | 速い | × | 再デプロイ |
| ローリング | 1 バッチが止まる | 中 | ○ | 再デプロイ |
| 追加バッチによるローリング | 最初のバッチなら小さい | 中 | ○ | 再デプロイ |
| イミュータブル | 最小限 | 長い | ○ | 新しいインスタンスを消す |
| トラフィック分割（Canary） | 最小限 | 長い | ○ | トラフィックを戻す |
| ブルー/グリーン | 最小限 | 長い | ○ | 元の環境に切り戻す |

### 戦略の名前

#### インプレースデプロイ（一括）（いんぷれーすでぷろい / in-place deployment）

- 意味：今動いているインスタンスの上で、アプリを止めて新しいリビジョンを入れて起動し直す方法
- ポイント：新しいインスタンスは要らず速いが、全部に一度に入れるとダウンタイムが出る。ロールバックは前のリビジョンの再デプロイ。CodeDeploy では EC2/オンプレミスだけ（Lambda・ECS では使えない）

#### ローリングデプロイ（ろーりんぐでぷろい / rolling deployment）

- 意味：フリートをいくつかのバッチに分け、1 バッチずつ新しいバージョンにする方法
- ポイント：デプロイ中は新旧 2 つのバージョンが同じフリートで動く。バッチが外れている間は容量が減る。Elastic Beanstalk ではバッチサイズ（割合か固定数）を決める

#### 追加バッチによるローリング（ついかばっちによるろーりんぐ / rolling with additional batch）

- 意味：ローリングの前に新しいインスタンスのバッチを先に起動し、デプロイ中も総容量を保つ Elastic Beanstalk のデプロイポリシー
- ポイント：容量を落としたくないがイミュータブルほどお金や時間をかけたくないとき

#### イミュータブルデプロイ（いみゅーたぶるでぷろい / immutable deployment）

- 意味：新しいバージョンを入れた、まったく新しいインスタンスのセットを起動して入れ替える方法
- ポイント：Elastic Beanstalk はロードバランサーの後ろに 2 つ目の（一時的な）Auto Scaling グループを作る。失敗しても新しいインスタンスを消すだけで、今のインスタンスには触れない
- 語の意味：immutable＝変更できない（一度作ったサーバーは書き換えず、作り直す）

#### ブルー/グリーンデプロイ（ぶるーぐりーんでぷろい / blue/green deployment）

- 意味：今の環境（ブルー）とは別に新しい環境（グリーン）を作り、テストが通ったらトラフィックを移す方法
- ポイント：ブルーはロールバックに備えて残しておく。切り替えはロードバランサー・Route 53・Elastic Beanstalk の CNAME スワップなど。CodeDeploy の EC2 では、Auto Scaling グループをコピーして置き換え先を作り、元のインスタンスは終了か残すかを選ぶ

#### Canary（かなりあ / canary）

- 意味：まずトラフィックやサーバーのごく一部だけを新しいバージョンにし、問題がなければ残りを移す方法
- ポイント：CodeDeploy の Canary は 2 段階。例 LambdaCanary10Percent5Minutes＝10% を移し、5 分後に残り 90%。Elastic Beanstalk ではトラフィック分割のデプロイで Canary テストができる
- 語の意味：canary＝カナリア（炭鉱で危険をいち早く知らせた鳥）

#### 線形（Linear）（せんけい / linear）

- 意味：同じ割合ずつ、同じ間隔でトラフィックを移していく方法
- ポイント：例 ECSLinear10PercentEvery1Minutes＝毎分 10% ずつ、10 分で 100%。Canary より細かく少しずつ進む

#### CNAME スワップ（しーねーむすわっぷ / CNAME swap）

- 意味：Elastic Beanstalk で、新しいバージョンを別の環境に出してから、2 つの環境の CNAME（URL）を入れ替えて、すぐにトラフィックを移す方法
- ポイント：Elastic Beanstalk のブルー/グリーン。戻すときはもう一度スワップする。DNS の TTL の分だけ古い環境にアクセスが残ることがある

#### 問 dop-04-o01

- 問：CodeDeploy で EC2 インスタンスにアプリをデプロイしたい。インスタンスに必ず入れておくものはどれか。

#### 問 dop-04-o03

- 問：CodeDeploy のデプロイが、エージェントが S3 からリビジョンを取れずに失敗する。インスタンスに必要なものはどれか。
- ア：CodeDeploy のサービスロールをインスタンスに付ける

- エ：S3 を読める IAM インスタンスプロファイルを付けてインスタンスを起動する
- 正解：エ

- イの意味：公開は危険で、不要。
- ウの意味：アクセスキーを書くのは秘密情報の漏れにつながり、不要。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「AWS CodeDeploy ユーザーガイド」EC2/オンプレミスコンピューティングプラットフォームの Blue/Green デプロイ（『CodeDeploy エージェントでインスタンスの ID を検証するには、Amazon EC2 インスタンスを起動する際に IAM インスタンスプロファイルをアタッチする必要があります。』））

- 問：EC2/オンプレミスのリビジョンについて正しいものはどれか。
- ア：コンテナイメージだけを指す

- エ：デプロイ設定とデプロイグループの組み合わせ
- 正解：ウ

- ウの意味：正しい。

- 出典：オリジナル問題（根拠：AWS「AWS CodeDeploy ユーザーガイド」CodeDeploy とは（『AppSpec ファイルは CodeDeploy に固有です。』））

#### 問 dop-04-o05

- 問：本番の EC2 インスタンス 10 台に CodeDeploy でデプロイする。常に 9 台は動かしておき、1 台ずつ進めたい。どの設定を使うか。
- ア：CodeDeployDefault.OneAtATime
- イ：CodeDeployDefault.AllAtOnce
- ウ：CodeDeployDefault.HalfAtATime
- エ：CodeDeployDefault.LambdaLinear10PercentEvery1Minute
- 正解：ア
- 解説：OneAtATime は一度に 1 台だけにデプロイする。最も安全だが時間がかかる。
- アの意味：正しい。
- イの意味：できるだけ多くに一度にデプロイし、ダウンタイムが出る。
- ウの意味：最大半分ずつで、5 台が同時に外れる。
- エの意味：Lambda のトラフィックを移す設定で、EC2 には使えない。
