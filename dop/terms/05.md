## 05-1 Amazon ECS・EKS のデプロイ

### まとめ表

| ECS のデプロイ | しくみ | 失敗の検知・戻し方 |
| :-: | :-: | :-: |
| ローリング更新（ECS） | タスクを順に置き換える（minimumHealthyPercent・maximumPercent） | サーキットブレーカー・デプロイアラーム |
| ブルー/グリーン（ECS ネイティブ） | 新しいサービスリビジョンにトラフィックを移し、ベイク時間のあいだ両方を動かす | ライフサイクルフック・アラーム |
| カナリア（ECS ネイティブ） | 2 つのフェーズで移す（Canary の割合 → 残り） | 評価期間 |
| CodeDeploy のブルー/グリーン | 置き換えタスクセットと 2 つのターゲットグループ | フック・アラーム・自動ロールバック |

### ECS のデプロイ

#### ローリング更新（ECS）（ろーりんぐこうしん / rolling update）

- 意味：ECS のサービススケジューラが、動いているタスクを新しいタスクに順に置き換えるデプロイタイプ（ECS）
- ポイント：minimumHealthyPercent（動いていなければならないタスクの下限の割合）と maximumPercent（動かせるタスクの上限の割合）で速さと容量を決める。例 タスク 4 個で最小 50%・最大 200% なら、2 個まで止めてよく、8 個まで増やせる

#### minimumHealthyPercent・maximumPercent（みにまむへるしーぱーせんと・まきしまむぱーせんと / minimumHealthyPercent・maximumPercent）

- 意味：ローリング更新やドレインのあいだ、動いていて正常であるべきタスク数の下限と、動かせるタスク数の上限を、必要なタスク数に対する割合で表したもの
- ポイント：最小 100%・最大 200% → 容量を落とさず先に新しいタスクを増やす。最小 0% → 全部止めてよい（速いが止まる）。スケジューラが 1 つ以上のタスクを止めたり起動したりできる値にする

#### デプロイサーキットブレーカー（さーきっとぶれーかー / deployment circuit breaker）

- 意味：ローリング更新で、タスクが定常状態にならない（起動できない）ことを検知して、デプロイを失敗にする仕組み
- ポイント：ロールバックのオプションを付けると、COMPLETED 状態の最新のデプロイに自動で戻す。タスクが起動できないときに止めたいならこちら、アプリのメトリクスで止めたいならデプロイアラーム。両方を一緒に使える

#### デプロイアラーム（ECS）（でぷろいあらーむ / deployment alarms）

- 意味：指定した CloudWatch アラームが ALARM 状態になったら、ECS のデプロイを失敗にする設定
- ポイント：ロールバックのオプションと組み合わせて前のサービスリビジョンに戻せる。5XX エラーやレイテンシーなどアプリのメトリクスで止める

#### ECS ブルー/グリーンデプロイ（ぶるーぐりーん / Amazon ECS blue/green deployment）

- 意味：今のサービスリビジョン（ブルー）と新しいサービスリビジョン（グリーン）を両方動かし、検証してから本番のトラフィックを移す、ECS 自身のデプロイ方法
- ポイント：テストトラフィックで検証してから本番を移せる。ベイク時間（本番のトラフィックを移した後もブルーとグリーンを両方動かす期間）のあいだは、すぐにブルーに戻せる。ライフサイクルフック（Lambda 関数か一時停止）で検証を自動化できる

#### ECS カナリアデプロイ（かなりあ / Amazon ECS canary deployment）

- 意味：トラフィックを 2 つのフェーズで移し、まず一部（Canary の割合）を新しいリビジョンに流して評価期間のあいだ確かめる ECS のデプロイ方法
- ポイント：評価期間中は元と Canary の両方のタスクが動くので、リソースの使用量が増える。デプロイの時間は長くなるが、本番のトラフィックで確かめられる

#### CodeDeploy による ECS のブルー/グリーン（こーどでぷろいによる / CodeDeploy blue/green for Amazon ECS）

- 意味：CodeDeploy が新しいタスク定義で置き換えタスクセットを作り、ロードバランサーの 2 つのターゲットグループを切り替えてトラフィックを移す方法
- ポイント：ロードバランサーに 2 つのターゲットグループが要る。テストリスナーを付けるとテストトラフィックを置き換えタスクセットに流せる。Canary・線形・一度にすべてのデプロイ設定と、AppSpec のフック（AfterAllowTestTraffic など）を使う

#### イメージダイジェストの解決（いめーじだいじぇすとのかいけつ / container image resolution）

- 意味：ECS が、タスク定義のイメージのタグ（latest など）を、デプロイの最初にイメージのダイジェスト（sha256）に置き換えて使う動き（既定）
- ポイント：デプロイ中にタグが別のイメージに付け替えられても、サービスのすべてのタスクが同じイメージで動く。versionConsistency でコンテナごとに変えられる

#### imagedefinitions.json（いめーじでふぃにしょんず / imagedefinitions.json）

- 意味：CodePipeline の Amazon ECS 標準デプロイアクション（ローリング更新）が読む、コンテナ名とイメージ URI の対応を書いた JSON ファイル
- ポイント：CodeBuild の post_build で作り、出力アーティファクトに入れる。アクションはサービスのタスク定義から新しいリビジョンを作る
- 例：`[{"name":"web","imageUri":"111122223333.dkr.ecr.ap-northeast-1.amazonaws.com/web:abc123"}]`

#### imageDetail.json・taskdef.json・appspec.yaml（いめーじでぃてーる / imageDetail.json・taskdef.json・appspec.yaml）

- 意味：CodePipeline の CodeDeployToECS アクション（ECS のブルー/グリーン）が使う 3 つのファイル。イメージ URI、タスク定義、AppSpec
- ポイント：taskdef.json の IMAGE1_NAME のようなプレースホルダーに imageDetail.json のイメージ URI が入る。標準デプロイアクションの imagedefinitions.json と取り違えない

#### Amazon EKS（いーけーえす / Amazon Elastic Kubernetes Service）

- 意味：Kubernetes のクラスターの運用の手間を減らす、フルマネージドの Kubernetes サービス
- ポイント：デプロイは Kubernetes の Deployment（既定はローリングアップデート）を kubectl・Helm・Argo CD などで適用する。CodePipeline には EKS へのデプロイアクションもある。ECS と違い、Kubernetes の API と道具をそのまま使える
- 語の意味：Elastic＝伸び縮みする、Kubernetes＝コンテナのオーケストレーションのオープンソース

## 05-2 Lambda とサーバーレスのデプロイ

### まとめ表

| しくみ | 何ができるか |
| :-: | :-: |
| バージョン | 公開した時点のコードと設定を固定（$LATEST だけが変えられる） |
| エイリアス | バージョンを指す名前（prod など）。呼び出し側は ARN を変えない |
| 加重エイリアス | 2 つのバージョンにトラフィックを割合で分ける |
| SAM の DeploymentPreference | CodeDeploy で Canary・線形に移し、フックとアラームで自動ロールバック |
| API Gateway の Canary | ステージのトラフィックの一部を Canary に流し、よければ昇格 |

### Lambda のバージョン管理

#### Lambda のバージョン（ばーじょん / Lambda function version）

- 意味：関数を公開したときに作られる、その時点のコードと設定のコピー。番号（1、2、3…）で呼べる
- ポイント：公開したバージョンのコードと設定は変えられない（変えられるのは未公開の $LATEST だけ）。バージョンを指して呼べば、だれかが $LATEST を変えても影響を受けない

#### $LATEST（れいてすと / $LATEST）

- 意味：Lambda 関数の未公開のバージョン。コードをデプロイするたびに上書きされる
- ポイント：本番から $LATEST を直接呼ぶと、デプロイした瞬間に全部が変わり、戻すのも難しい。本番はエイリアス経由で公開したバージョンを呼ぶ

#### エイリアス（えいりあす / alias）

- 意味：関数の特定のバージョンを指す、付け替えられる名前（prod・staging など）
- ポイント：呼び出し側（API Gateway・イベントソース）はエイリアスの ARN を使うので、新しいバージョンを出すときはエイリアスの向き先を変えるだけ。戻すときも向き先を戻すだけ

#### 加重エイリアス（かじゅうえいりあす / weighted alias）

- 意味：1 つのエイリアスで、2 つのバージョンにトラフィックを割合で分ける設定（ルーティング設定）
- ポイント：新しいバージョンに少しだけ流して確かめ、すぐに戻せる（Canary）。トラフィックが少ないと、設定の割合と実際の割合がずれることがある。CodeDeploy の Lambda デプロイはこの割合を自動で動かしている

### SAM と API Gateway

#### AWS SAM（さむ / AWS Serverless Application Model）

- 意味：サーバーレスのリソースを短く書ける CloudFormation の拡張（SAM テンプレート）と、ビルド・テスト・デプロイ用の CLI（sam build・sam deploy など）
- ポイント：Transform: AWS::Serverless-2016-10-31 で CloudFormation に展開される。AWS::Serverless::Function・Api・SimpleTable などを使う
- 語の意味：Serverless＝サーバーを意識しない、Application Model＝アプリの書き方の型

#### AutoPublishAlias（おーとぱぶりっしゅえいりあす / AutoPublishAlias）

- 意味：SAM の関数のプロパティ。コードの変更を見つけると新しいバージョンを公開し、指定した名前のエイリアスをそのバージョンに向ける
- ポイント：DeploymentPreference を使う前提。呼び出し側がエイリアスを使うようにしておく

#### DeploymentPreference（でぷろいめんとぷりふぁれんす / DeploymentPreference）

- 意味：SAM の関数のプロパティ。CodeDeploy を使って、新しいバージョンにトラフィックを段階的に移す設定
- ポイント：Type（Canary10Percent10Minutes・Linear10PercentEvery1Minute・AllAtOnce など）、Alarms（エラーで自動ロールバック）、Hooks（PreTraffic・PostTraffic）を書く。CodeDeploy のアプリケーションとデプロイグループは SAM が自動で作る
- 例：`DeploymentPreference: { Type: Canary10Percent10Minutes, Alarms: [ !Ref ErrorsAlarm ], Hooks: { PreTraffic: !Ref PreTrafficFn } }`

#### PreTraffic・PostTraffic フック（ぷれとらふぃっく・ぽすととらふぃっく / PreTraffic・PostTraffic hooks）

- 意味：トラフィックを新しいバージョンに移し始める前（PreTraffic）と、移し終わった後（PostTraffic）に CodeDeploy が呼ぶ検証用の Lambda 関数
- ポイント：テストが失敗すると CodeDeploy がロールバックする。フック関数は結果を CodeDeploy に返す（PutLifecycleEventHookExecutionStatus）。CodeDeploy の BeforeAllowTraffic・AfterAllowTraffic にあたる

#### API Gateway の Canary リリース（えーぴーあいげーとうぇいのかなりあ / API Gateway canary release）

- 意味：API のステージのトラフィックを、決めた割合でランダムに本番のリリースと Canary のリリースに分けるデプロイ
- ポイント：Canary には少しだけ流し、Canary 用のログやメトリクスで確かめる。よければ Canary を本番に昇格し、だめなら外す。ステージ変数を Canary 用に変えて、別の Lambda エイリアスに向けることもできる

## 問題演習

### 05-1

#### 問 dop-05-o01

- 問：ECS サービスのタスクは 4 個。ローリング更新で容量を一切落とさず、先に新しいタスクを起動してから古いタスクを止めたい。設定はどれか。
- ア：minimumHealthyPercent 0%・maximumPercent 100%
- イ：minimumHealthyPercent 50%・maximumPercent 100%
- ウ：minimumHealthyPercent 100%・maximumPercent 200%
- エ：minimumHealthyPercent 100%・maximumPercent 100%
- 正解：ウ
- 解説：minimumHealthyPercent は動いていなければならないタスクの下限、maximumPercent は動かせるタスクの上限。下限 100% で 4 個を保ち、上限 200% で 8 個まで増やせるので、先に新しいタスクを起動できる。
- アの意味：全部止めてよく、ダウンタイムが出る。
- イの意味：2 個まで止まり、容量が落ちる。
- ウの意味：正しい。
- エの意味：1 つも止められず、1 つも増やせないので、デプロイが進まない。
- 出典：オリジナル問題（根拠：AWS「Amazon Elastic Container Service デベロッパーガイド」タスクを置き換えて Amazon ECS サービスをデプロイする（『maximumPercent は、ローリングデプロイメント中またはコンテナインスタンスがドレインしているときに、サービスに対して実行する必要があるタスク数の上限を、サービスに必要なタスク数の割合 (%) として表します。』））

#### 問 dop-05-o02

- 問：ECS のローリング更新で、新しいタスクが起動に失敗し続けると、デプロイがいつまでも終わらない。自動で失敗と判断して前の正常なデプロイに戻したい。何を使うか。
- ア：デプロイサーキットブレーカーとロールバックのオプション
- イ：Service Auto Scaling のターゲット追跡
- ウ：ECS Exec
- エ：タスク定義の essential パラメータ
- 正解：ア
- 解説：デプロイサーキットブレーカーは、タスクが定常状態にならないことを検知してデプロイを失敗にする。ロールバックのオプションで、COMPLETED 状態のデプロイに自動で戻す。
- アの意味：正しい。
- イの意味：負荷に合わせてタスク数を変える機能。
- ウの意味：動いているコンテナでコマンドを実行する機能。
- エの意味：そのコンテナが止まったらタスク全体を止めるかの設定で、デプロイを戻す機能ではない。
- 出典：オリジナル問題（根拠：AWS「Amazon Elastic Container Service デベロッパーガイド」Amazon ECS デプロイサーキットブレーカーが障害を検出する方法（『デプロイサーキットブレーカーには、デプロイが失敗した場合に、 COMPLETED 状態のデプロイに自動的にロールバックするオプションがあります。』））

#### 問 dop-05-o03

- 問：ECS のローリング更新で、タスクは起動するが新しいバージョンで 5XX エラーが増えることがある。アプリのメトリクスでデプロイを止めて戻したい。何を使うか。
- ア：デプロイサーキットブレーカーだけ
- イ：CloudWatch アラームをデプロイに指定し、ロールバックのオプションを付ける
- ウ：タスク定義のヘルスチェックを外す
- エ：minimumHealthyPercent を 0% にする
- 正解：イ
- 解説：ECS は、指定した CloudWatch アラームが ALARM 状態になったらデプロイを失敗にできる。アプリのメトリクスで止めたいならアラーム、タスクが起動できないときに止めたいならサーキットブレーカーを使う。
- アの意味：タスクが起動していれば検知できない。
- イの意味：正しい。
- ウの意味：異常に気づけなくなる。
- エの意味：止まってよい数が増えるだけ。
- 出典：オリジナル問題（根拠：AWS「Amazon Elastic Container Service デベロッパーガイド」CloudWatch アラームが Amazon ECS のデプロイ障害を検出する方法（『指定された CloudWatch アラームが ALARM 状態になったことを検出したとき、デプロイが失敗に設定されるように Amazon ECS を設定できます。』））

#### 問 dop-05-o04

- 問：ECS のブルー/グリーンデプロイで、本番のトラフィックをグリーンに移した後も、しばらくブルーを動かしておき、問題があればすぐ戻せるようにしたい。この期間を何と呼ぶか。
- ア：評価期間
- イ：ドレイン期間
- ウ：ヘルスチェックの猶予期間
- エ：ベイク時間
- 正解：エ
- 解説：ベイク時間は、本番のトラフィックを移した後に、ブルーとグリーンの両方のサービスリビジョンを同時に動かす期間。この間はすぐにブルーに戻せる。
- アの意味：カナリアデプロイで一部のトラフィックを流して確かめる期間。
- イの意味：ロードバランサーから外す接続を待つ期間（登録解除の遅延）。
- ウの意味：起動直後のタスクのヘルスチェックの失敗を無視する期間。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「Amazon Elastic Container Service デベロッパーガイド」Amazon ECS ブルー/グリーンデプロイ（『ベイク時間 – 本番トラフィックが移行した後に、ブルーおよびグリーンのサービスリビジョンの両方が同時に実行される期間。』））

#### 問 dop-05-o05

- 問：CodeDeploy で ECS にブルー/グリーンデプロイをする。ロードバランサーに必要なものはどれか。
- ア：2 つのターゲットグループ
- イ：2 つのロードバランサー
- ウ：1 つのターゲットグループだけ
- エ：Network Load Balancer の TLS リスナーだけ
- 正解：ア
- 解説：CodeDeploy の ECS ブルー/グリーンでは、ロードバランサーに 2 つのターゲットグループを用意し、元のタスクセットと置き換えタスクセットのあいだでトラフィックを切り替える。
- アの意味：正しい。
- イの意味：ロードバランサーは 1 つでよい。
- ウの意味：1 つはローリング更新の場合。
- エの意味：NLB も使えるが、その場合のデプロイ設定は ECSAllAtOnce だけ。ターゲットグループは 2 つ要る。
- 出典：オリジナル問題（根拠：AWS「Amazon Elastic Container Service デベロッパーガイド」Amazon ECS 用の CodeDeploy ブルー/グリーンデプロイ（『ロードバランサーに対して 2 つのターゲットグループを定義する必要があります。』））

#### 問 dop-05-o06

- 問：CodeDeploy の ECS ブルー/グリーンで、本番のトラフィックを移す前に、別のポートから新しいタスクセットにテストをかけたい。何を設定するか。
- ア：2 つ目のロードバランサー
- イ：Route 53 の加重レコード
- ウ：ロードバランサーにテストリスナーを追加する
- エ：ECS Service Connect
- 正解：ウ
