## 12-1 EC2 とコンテナのスケーリング

### まとめ表

| 負荷の形 | 選ぶポリシー |
| :-: | :-: |
| メトリクスをある値に保ちたい（CPU 50% など） | ターゲット追跡 |
| アラームの超え方で増やす量を変えたい | ステップスケーリング |
| 決まった日時に増減（毎週月曜 9 時など） | スケジュールされたスケーリング |
| 日・週の規則的なパターンがあり、起動が遅い | 予測スケーリング |
| 起動が非常に遅い | ウォームプール |
| キューの処理 | インスタンスあたりのバックログでターゲット追跡 |

### Auto Scaling のポリシー

#### ターゲット追跡スケーリング（たーげっとついせき / target tracking scaling）

- 意味：メトリクスとターゲット値を決めると、その値を保つように Auto Scaling が台数を増減するポリシー
- ポイント：サーモスタットのような動き。アラームは自動で作られる。まず選ぶポリシー
- 例：ASGAverageCPUUtilization を 50%、ALBRequestCountPerTarget を 1,000

#### ステップスケーリング（すてっぷすけーりんぐ / step scaling）

- 意味：CloudWatch アラームの超え方の大きさ（ステップ）に応じて、決めた数だけ増減するポリシー
- ポイント：シンプルスケーリングはクールダウンの間は次の動きを待つので、急な負荷に追いつかないことがある。シンプルスケーリングとクールダウンは使わないことが推奨されている

#### スケジュールされたスケーリング（すけじゅーるされたすけーりんぐ / scheduled scaling）

- 意味：決まった日時に、希望するキャパシティ・最小・最大を変えるアクション
- ポイント：予測できる負荷の変化（キャンペーンの開始時刻、毎週の締め処理）に。cron 形式で繰り返せる

#### 予測スケーリング（よそくすけーりんぐ / predictive scaling）

- 意味：負荷の履歴から日・週のパターンを見つけ、予想される負荷の前にキャパシティを増やすポリシー
- ポイント：規則的なパターンがあり、アプリの初期化に時間がかかるときに向く。動的スケーリング（ターゲット追跡など）と組み合わせる

#### ウォームプール（うぉーむぷーる / warm pool）

- 意味：Auto Scaling グループに付けた、初期化済みの EC2 インスタンスの控え。スケールアウトのときにここから出す
- ポイント：停止（Stopped）で置けば、待っている間の EC2 の料金はかからない（EBS の料金はかかる）。起動が速いアプリには要らない

#### ライフサイクルフック（らいふさいくるふっく / lifecycle hook）

- 意味：インスタンスの起動直後や終了直前に待機状態で止め、自分の処理が終わるまで待たせる仕組み（既定 1 時間）
- ポイント：起動時はソフトの導入や設定、終了時はログの退避や接続のドレインに使う。EventBridge で通知を受け、終わったら complete-lifecycle-action を呼ぶ

#### インスタンスあたりのバックログ（いんすたんすあたりのばっくろぐ / backlog per instance）

- 意味：SQS キューのメッセージ数（ApproximateNumberOfMessages）を、処理するインスタンスの数で割った値。カスタムメトリクスとして出し、ターゲット追跡に使う
- ポイント：キューの長さだけを見るより、台数に比例した正しいスケールになる。ターゲット値は「1 台が許されるレイテンシーの中で処理できる数」

#### 混合インスタンスグループ（こんごういんすたんすぐるーぷ / mixed instances group）

- 意味：1 つの Auto Scaling グループで、複数のインスタンスタイプと、オンデマンド・スポットを組み合わせて起動する構成
- ポイント：ベースはオンデマンド、増えた分はスポットにするなどで費用を下げる。スポットは中断されうるので、中断に強い処理に使う

### コンテナ

#### ECS サービスの自動スケーリング（いーしーえすさーびすのじどうすけーりんぐ / Amazon ECS service auto scaling）

- 意味：Application Auto Scaling で、ECS サービスの必要なタスク数を増減する機能。ターゲット追跡・ステップ・予測が使える
- ポイント：タスク（コンテナ）の数を増やす。EC2 起動タイプでタスクを置く場所（インスタンス）を増やすのは、キャパシティプロバイダーの役目

#### キャパシティプロバイダーのマネージドスケーリング（きゃぱしてぃぷろばいだー / capacity provider managed scaling）

- 意味：ECS の Auto Scaling グループのキャパシティプロバイダーで、タスクに必要なだけ EC2 インスタンスを自動で増減する機能
- ポイント：CapacityProviderReservation メトリクスでターゲット追跡する。タスクが PENDING のまま置き場所がないときの答え

#### Karpenter（かーぺんたー / Karpenter）

- 意味：Kubernetes の負荷の変化に応じて、ちょうどよい大きさの EC2 インスタンスを 1 分未満で起動するクラスターオートスケーラー
- ポイント：EKS Auto Mode の土台。Cluster Autoscaler（Auto Scaling グループの台数を変える）より柔軟にインスタンスタイプを選ぶ

## 12-2 サーバーレスとデータ層のスケーリング

### まとめ表

| 困りごと | 答え |
| :-: | :-: |
| ほかの関数に同時実行を取られて大事な関数が動かない | 予約済み同時実行 |
| コールドスタートの遅延 | プロビジョニングされた同時実行 |
| Lambda から RDS への接続が多すぎる | RDS Proxy |
| 同じ GET が多くバックエンドが重い | API Gateway のキャッシュ |
| 利用者ごとに上限 | 使用量プラン（スロットリング・クォータ） |
| DynamoDB の負荷が読めない | オンデマンドモード |
| Aurora の読み取りの増減 | Aurora Auto Scaling（レプリカの数） |

### Lambda と API Gateway

#### 同時実行数（どうじじっこうすう / concurrency）

- 意味：Lambda 関数が同時に処理している未完了のリクエストの数。リクエストごとに実行環境が用意される
- ポイント：リージョンのアカウント全体で既定 1,000 が上限。超えるとスロットリングされる（同期呼び出しでは 429）。引き上げは申請する

#### 予約済み同時実行（よやくずみどうじじっこう / reserved concurrency）

- 意味：関数に同時実行数を取り分けておき、同時にその関数の上限にもする設定
- ポイント：大事な関数の分を確保できる。逆に、下流（DB など）を守るために上限として使う。0 にすると関数を止められる。追加料金はない

#### プロビジョニングされた同時実行（ぷろびじょにんぐされたどうじじっこう / provisioned concurrency）

- 意味：前もって初期化した実行環境を用意しておき、コールドスタートをなくす設定
- ポイント：数十ミリ秒で応答できる。料金がかかる。Application Auto Scaling で時間帯に合わせて増減できる。初期化はハンドラーの外に書く

#### API Gateway のスロットリング（すろっとりんぐ / API Gateway throttling）

- 意味：トークンバケットでリクエストの速さ（レート）と同時の山（バースト）を制限し、超えたら 429 Too Many Requests を返す仕組み
- ポイント：アカウント・ステージ・メソッドで決められる。使用量プランと API キーで、利用者ごとのレートとクォータも決められる

#### API Gateway のキャッシュ（きゃっしゅ / API caching）

- 意味：ステージでキャッシュを有効にし、TTL の間はバックエンドを呼ばずにキャッシュから返す機能
- ポイント：TTL の既定は 300 秒、最大 3600 秒。同じ GET が多いときにバックエンドの負荷とレイテンシーを下げる

### データ層

#### RDS Proxy（あーるでぃーえすぷろきし / Amazon RDS Proxy）

- 意味：データベースの接続をプールして再利用する、RDS・Aurora 用のフルマネージドなプロキシ
- ポイント：Lambda のように短い接続が大量にできると DB の接続が足りなくなる。その答え。フェイルオーバーの時間も短くなる

#### DynamoDB のキャパシティモード（きゃぱしてぃもーど / capacity modes）

- 意味：使った読み書きの分だけ払うオンデマンドモードと、読み書きの量を決めておくプロビジョンドモード
- ポイント：負荷が読めない・急に跳ねるならオンデマンド（ほとんどのワークロードで推奨の既定）。プロビジョンドは DynamoDB Auto Scaling で増減するが、使用率がターゲットを 2 分続けて超えてから動くので、急なスパイクには遅れる

#### Aurora Auto Scaling（おーろらおーとすけーりんぐ / Aurora Auto Scaling）

- 意味：CloudWatch のメトリクスとターゲット値に応じて、Aurora レプリカ（リーダー）の数を増減する機能
- ポイント：読み取りの負荷に合わせる。書き込み（ライター）は増えない。アプリはリーダーエンドポイントにつなぐ

#### キャッシュ戦略（きゃっしゅせんりゃく / caching strategies: lazy loading・write-through）

- 意味：要るときだけキャッシュに読み込む遅延読み込みと、DB に書くたびにキャッシュも更新する書き込みスルー
- ポイント：遅延読み込みは古いデータが残りうる。書き込みスルーは常に新しいが、読まれないデータもキャッシュする。TTL を足して両方の欠点を和らげる

## 12-3 疎結合とメッセージング

### まとめ表

| やりたいこと | 使うもの |
| :-: | :-: |
| 送る側と受ける側を切り離し、山をならす | SQS |
| 処理に失敗し続けるメッセージを外す | デッドレターキュー（maxReceiveCount） |
| 1 つのイベントを複数のシステムに | SNS → 複数の SQS（ファンアウト） |
| 一部のメッセージだけ受け取る | SNS のフィルターポリシー |
| 順序どおり・重複なし | SQS FIFO キュー |
| 大量のストリームを順に処理 | Kinesis Data Streams（シャード） |
| 手順・再試行・分岐を組む | Step Functions |

### SQS

#### 可視性タイムアウト（かしせいたいむあうと / visibility timeout）

- 意味：あるコンシューマーがメッセージを受け取ってから、ほかのコンシューマーに見えなくなっている時間。既定 30 秒、最大 12 時間
- ポイント：処理がこれより長いと、削除する前にほかのコンシューマーがまた受け取り、二重に処理される。処理時間に合わせて長くする

#### デッドレターキュー（でっどれたーきゅー / dead-letter queue, DLQ）

- 意味：何度受け取っても処理できないメッセージを移す先のキュー。maxReceiveCount の回数を超えると移る
- ポイント：毒メッセージがキューを詰まらせるのを防ぎ、あとで調べて再処理（リドライブ）できる。ソースキューと同じアカウント・リージョンに置く

#### ロングポーリング（ろんぐぽーりんぐ / long polling）

- 意味：メッセージがないとき、待ち時間（最大 20 秒）の間待ってから応答する受け取り方
- ポイント：空の応答が減り、費用が下がる。ReceiveMessageWaitTimeSeconds を 0 より大きくする

#### FIFO キュー（ふぁいふぉきゅー / FIFO queue）

- 意味：送った順序を厳密に守り、重複を入れないキュー。メッセージグループごとに順序を保つ
- ポイント：順序が大事・重複が許されないとき。標準キューは順序と 1 回だけを約束しない
- 語の意味：First-In-First-Out＝先に入れたものを先に出す

#### 部分的なバッチレスポンス（ぶぶんてきなばっちれすぽんす / partial batch response）

- 意味：Lambda が SQS のバッチを処理するとき、失敗したメッセージだけを返して、それだけを再処理させる仕組み（ReportBatchItemFailures）
- ポイント：使わないと、1 件の失敗でバッチ全部が可視性タイムアウトのあとにまた届き、成功したものも二重に処理される

### SNS・Kinesis・Step Functions

#### SNS のファンアウト（ふぁんあうと / SNS fanout to SQS）

- 意味：1 つの SNS トピックに複数の SQS キューをサブスクライブさせ、1 つのメッセージを複数の処理に並行して届ける構成
- ポイント：送る側は受け手を知らなくてよく、受け手は自分のキューで自分のペースで処理できる。受け手が止まってもメッセージはキューに残る

#### フィルターポリシー（ふぃるたーぽりしー / subscription filter policy）

- 意味：サブスクリプションに付ける JSON で、メッセージの属性や本文が条件に合うものだけを届ける
- ポイント：トピックを分けたり受け手で捨てたりせずに済む。ポリシーがないサブスクリプションには全部届く

#### Kinesis のシャード（しゃーど / Kinesis shard）

- 意味：Kinesis Data Streams の容量の単位。1 シャードは書き込み 1 MB/秒・1,000 レコード/秒、読み取り 2 MB/秒
- ポイント：パーティションキーでどのシャードに入るかが決まる。キーが偏るとホットシャードになる。オンデマンドモードならシャードを自動で管理

#### Step Functions（すてっぷふぁんくしょんず / AWS Step Functions）

- 意味：ステート（手順）をつないだステートマシンで、分散アプリの処理の流れを組むサービス
- ポイント：再試行・エラー処理・分岐・並列・待機を、コードではなく定義で書ける。Lambda どうしを直接呼び合う密結合をほどく

## 問題演習

### 12-1

#### 問 dop-12-o01

- 問：Web アプリの Auto Scaling グループで、負荷が変わっても平均 CPU 使用率をおよそ 50% に保ちたい。設定と運用が最も簡単なポリシーはどれか。
- ア：シンプルスケーリング
- イ：スケジュールされたスケーリング
- ウ：ステップスケーリング
- エ：ターゲット追跡スケーリング（ASGAverageCPUUtilization = 50）
- 正解：エ
- 解説：ターゲット追跡はメトリクスとターゲット値を決めるだけで、アラームも自動で作られ、その値を保つように増減する。
- アの意味：アラームと増減の数を自分で決め、クールダウンで遅れる。
- イの意味：時刻で決めるので、負荷の変化には合わない。
- ウの意味：保てるが、アラームとステップを自分で設計する手間がある。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「Amazon EC2 Auto Scaling ユーザーガイド」ターゲットトラッキングスケーリングポリシー（『このニーズを満たすには、50% の平均 CPU 使用率をターゲットとする、ターゲット追跡スケーリングポリシーを作成します。』））

#### 問 dop-12-o02

- 問：毎週月曜の 9 時に社内の集計処理が始まり、負荷が急に上がる。8 時 50 分には台数を増やしておきたい。どれを使うか。
- ア：スケジュールされたスケーリング
- イ：ターゲット追跡だけ
- ウ：ライフサイクルフック
- エ：ウォームプールだけ
- 正解：ア
- 解説：日時が決まっている予測できる負荷は、スケジュールされたアクションで前もって希望するキャパシティを上げる。
- アの意味：正しい。
- イの意味：負荷が上がってから増えるので、始まりに間に合わない。
- ウの意味：起動・終了の途中で止める仕組みで、台数は増やさない。
- エの意味：起動を速くするだけで、増やすきっかけにはならない。
- 出典：オリジナル問題（根拠：AWS「Amazon EC2 Auto Scaling ユーザーガイド」スケジュールされたスケーリング（『スケジュールされたスケーリングでは、予測可能な負荷の変化に基づいてアプリケーションに自動スケーリングを設定できます。』））

#### 問 dop-12-o03

- 問：EC サイトのトラフィックは毎日朝と夜に山があるが、日によって時刻が少しずれる。アプリの初期化に 5 分かかり、ターゲット追跡だけでは山の始まりに遅れる。何を足すか。
- ア：シンプルスケーリング
- イ：ステップスケーリング
- ウ：予測スケーリング
- エ：最小台数を山の台数に固定する
- 正解：ウ
- 解説：予測スケーリングは履歴から日・週のパターンを見つけ、予想される負荷の前にキャパシティを増やす。初期化が長いときに向く。
- アの意味：負荷が上がってから動くので遅れる。
- イの意味：同じく反応的で遅れる。
