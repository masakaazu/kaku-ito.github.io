## 10-1 Config の記録と評価

### まとめ表

| 知りたいこと | 使うもの |
| :-: | :-: |
| このリソースの設定が、いつ・どう変わったか | 設定履歴（設定項目の集まり） |
| 今のアカウント全体の設定を丸ごと | 設定スナップショット（S3 へ配信） |
| 設定が変わるたびに知らせてほしい | 設定ストリーム（SNS トピック） |
| 誰が API を呼んだか | CloudTrail（Config ではない） |
| 設定がルールに合っているか | Config ルール（マネージド・カスタム） |

### 記録のしくみ

#### AWS Config（えーだぶりゅーえすこんふぃぐ / AWS Config）

- 意味：アカウントの AWS リソースの設定と、リソースどうしの関係を記録し続け、その変化の履歴を残し、ルールに照らして評価するサービス
- ポイント：「設定が何だったか・どう変わったか」を答える。「誰が操作したか」は CloudTrail。両方を組み合わせて、変更の中身と変更した人をたどる

#### 設定レコーダー（せっていれこーだー / configuration recorder）

- 意味：範囲に入るリソースタイプの設定変更を、設定項目として保存する部品
- ポイント：これが止まっていると何も記録されず、ルールの評価もできない。記録するリソースタイプは絞れる。組織のルールの展開も、相手のアカウントにレコーダーがないと失敗する

#### 設定項目（せっていこうもく / configuration item, CI）

- 意味：あるリソースの、ある時点の属性・関係・設定をまとめた記録
- ポイント：リソースの作成・変更・削除を検出するたびに作られる。関連するリソース（例：セキュリティグループとそれを使うインスタンス）も記録される
- 語の意味：Configuration＝設定、Item＝項目

#### 設定履歴（せっていりれき / configuration history）

- 意味：ある期間の、あるリソースの設定項目を並べたもの
- ポイント：コンソールではタイムラインで前の設定に戻って見られる。S3 には 6 時間ごとに設定履歴ファイルが届く。障害の直前の「最後に正常だった設定」を調べるのに使う

#### 設定スナップショット（せっていすなっぷしょっと / configuration snapshot）

- 意味：記録しているすべてのリソースの、ある時点の設定項目をまとめたもの
- ポイント：履歴は「1 つのリソースの時間の流れ」、スナップショットは「全リソースのある瞬間」。S3 に配信できる

#### 配信チャネル（はいしんちゃねる / delivery channel）

- 意味：設定履歴・スナップショットを送る S3 バケットと、通知を送る SNS トピックを決める設定
- ポイント：Config は S3 に置くだけで、古いファイルの削除はしない。保存期間は S3 のライフサイクルで決める

#### 設定ストリーム（せっていすとりーむ / configuration stream）

- 意味：リソースが作成・変更・削除されるたびに設定項目を追加していく、自動更新のリスト。SNS トピックで流れてくる
- ポイント：コンプライアンスの状態が変わったときも SNS に通知が来る。プログラムで処理するなら SNS の先に SQS をつなぐのがおすすめとされる

### ルールの種類

#### マネージドルール（まねーじどるーる / AWS managed rules）

- 意味：AWS が用意した、ベストプラクティスに合っているかを調べる定義済みのルール。パラメータで動きを変えられる
- ポイント：EBS ボリュームが暗号化されているか、必要なタグが付いているか、など。まずマネージドルールで足りるかを考える
- 例：encrypted-volumes、required-tags、s3-bucket-versioning-enabled

#### カスタム Lambda ルール（かすたむらむだるーる / custom Lambda rule）

- 意味：自分で書いた Lambda 関数（Java・Python など）で評価するカスタムルール。Config が設定情報を渡し、関数が評価結果を返す
- ポイント：スコープ（リソースタイプ）を決めないと、すべてのリソースの変更で関数が呼ばれる。削除されたリソースには NOT_APPLICABLE を返す処理を入れるよう推奨されている

#### カスタムポリシールール（かすたむぽりしーるーる / custom policy rule）

- 意味：CloudFormation Guard のポリシー言語で書くカスタムルール。Lambda 関数を作らなくてよい
- ポイント：「Lambda を書かずに独自のルール」なら Guard。検出評価のトリガーは設定の変更

#### トリガータイプ（とりがーたいぷ / trigger type）

- 意味：ルールの評価を始めるきっかけ。設定変更・定期的（24 時間ごとなど）・その両方（ハイブリッド）がある
- ポイント：設定変更はスコープ内のリソースが変わったとき。定期的は決まった間隔で。「変更がなくても毎日チェックしたい」は定期的

#### 評価モード（ひょうかもーど / evaluation mode）

- 意味：リソースをいつ評価するか。プロアクティブ（デプロイ前）と検出（デプロイ済み）がある
- ポイント：プロアクティブ評価は StartResourceEvaluation API でリソースのプロパティを渡して COMPLIANT か NON_COMPLIANT かを返すだけで、デプロイを止めたり直したりはしない。止めたいなら CloudFormation フックなどを組み合わせる

## 10-2 修復と組織への展開

### まとめ表

| やりたいこと | 使うもの |
| :-: | :-: |
| 非準拠を直す手順を決めておく | 修復アクション（SSM Automation ドキュメント） |
| 非準拠になったらすぐ直す | 自動修復（再試行の回数と秒数も決める） |
| ルールと修復をまとめて配る | コンフォーマンスパック（YAML テンプレート） |
| 全アカウントに同じルールを強制 | 組織のルール・組織のコンフォーマンスパック |
| 全アカウント・全リージョンの結果を一か所で見る | アグリゲータ |
| 設定を SQL で探す | 高度なクエリ |

### 直す

#### 修復アクション（しゅうふくあくしょん / remediation action）

- 意味：Config ルールで非準拠になったリソースを直すために、ルールに関連付ける Systems Manager Automation ドキュメント
- ポイント：AWS が用意したマネージドの Automation ドキュメント（例：AWS-EnableS3BucketEncryption）も、自作のものも使える。実行にはサービスロールを渡す

#### 自動修復（じどうしゅうふく / automatic remediation）

- 意味：リソースが非準拠になったら、修復アクションを自動で実行する設定
- ポイント：直したあともまだ非準拠なら再試行させられる（例：300 秒で 5 回）。古いコンプライアンスのデータを元に、準拠しているリソースでも動くことがある点に注意

#### 手動修復（しゅどうしゅうふく / manual remediation）

- 意味：修復アクションを関連付けておき、人がコンソールなどで「修復」を押したときに実行する設定
- ポイント：本番への影響を人が確かめてから直したいときに選ぶ。1 つの修復アクションは手動か自動かのどちらか

### まとめて配る

#### コンフォーマンスパック（こんふぉーまんすぱっく / conformance pack）

- 意味：Config ルールと修復アクションを YAML テンプレートにまとめ、1 つの単位として配って監視するもの
- ポイント：サンプルテンプレート（例：運用のベストプラクティス）が用意されている。テンプレートは SSM ドキュメントに保存して、その名前で配ることもできる。組織全体にも配れる

#### 組織のルール（そしきのるーる / organization Config rules）

- 意味：Organizations の管理アカウント（または委任された管理者）から、組織の全アカウントに Config ルールを一括で作成・更新・削除する機能
- ポイント：メンバーアカウントは変更できないので、ガバナンスを強制できる。API・CLI でだけ作れる。リージョンごとの操作。新しく入ったアカウントにも自動で入る

#### アグリゲータ（あぐりげーた / aggregator）

- 意味：複数のアカウント・リージョン（または組織全体）の設定とコンプライアンスのデータを、1 つのアカウントに集めて見るための Config のリソース
- ポイント：見るだけ。アグリゲータからルールを配ったり、相手のアカウントを変更したりはできない。配るのは組織のルールやコンフォーマンスパック

#### 高度なクエリ（こうどなくえり / advanced query）

- 意味：SQL の SELECT 構文の一部を使って、今のリソースの設定を検索・集計する機能
- ポイント：アグリゲータと組み合わせると、全アカウント・全リージョンをまとめて検索できる。記録していないリソースタイプは検索できない
- 例：SELECT resourceId WHERE resourceType = 'AWS::S3::Bucket' のように、バージョニングが無効なバケットを一覧する

## 10-3 AppConfig で設定を安全に配る

### まとめ表

| AppConfig の部品 | 役割 |
| :-: | :-: |
| アプリケーション | 設定をまとめる入れ物 |
| 環境 | 配り先のまとまり（Beta・Production など）。CloudWatch アラームを付ける |
| 設定プロファイル | 機能フラグかフリーフォームか、どこに保存するか、バリデータ |
| デプロイ戦略 | 線形か指数か、ステップの割合、デプロイ時間、ベイク時間 |
| エージェント・Lambda 拡張機能 | アプリの近くで設定をキャッシュし、裏で取りに行く |

### しくみ

#### AWS AppConfig（あっぷこんふぃぐ / AWS AppConfig）

- 意味：コードを再デプロイせずに、本番のアプリケーションの動き（機能のオン・オフや設定値）を安全に変えるための Systems Manager の機能
- ポイント：検証してから少しずつ配り、アラームが鳴ったら自動でロールバックする。「設定変更のデプロイ」を CodeDeploy のように安全に行う

#### 機能フラグ（きのうふらぐ / feature flag）

- 意味：アプリケーションの機能を有効・無効にするフラグと、その属性（値と制約）。AppConfig のホストされた設定ストアに保存される
- ポイント：新機能を一部のユーザーにだけ出し、問題があればフラグを無効にするだけで止められる。マルチバリアント機能フラグなら、渡したコンテキストに応じて違う値を返す

#### フリーフォーム設定（ふりーふぉーむせってい / freeform configuration）

- 意味：機能フラグ以外の自由な形の設定データ。ホストされた設定ストア・S3・Parameter Store・Secrets Manager・SSM ドキュメントなどに置ける
- ポイント：スロットリングの上限、ログのレベル、許可リスト・ブロックリストなど。できればホストされた設定ストアに置くのがおすすめとされる

#### 設定プロファイル（せっていぷろふぁいる / configuration profile）

- 意味：設定データの種類（機能フラグかフリーフォームか）と、保存場所を指す URI、バリデータをまとめたもの
- ポイント：機能フラグの URI は hosted。バリデータは最大 2 つ

#### 環境（かんきょう / environment）

- 意味：設定を配る先の論理的なまとまり（Beta・Production、Web・Mobile など）
- ポイント：環境ごとに CloudWatch アラームを登録する。デプロイ中にアラームが ALARM になるとロールバックする。そのために AppConfig がアラームを読める IAM ロールを渡す。1 つの環境には一度に 1 つの設定しかデプロイできない

### 安全に配る

#### デプロイ戦略（でぷろいせんりゃく / deployment strategy）

- 意味：設定をどう広げるかの決まり。デプロイタイプ（線形・指数）、ステップの割合（増加係数）、デプロイ時間、ベイク時間を決める
- ポイント：線形は同じ割合ずつ、指数は 2%→4%→8% のように倍々で広げる。事前定義の戦略（例：AppConfig.AllAtOnce、AppConfig.Linear50PercentEvery30Seconds、AppConfig.Canary10Percent20Minutes）もある

#### ベイク時間（べいくじかん / bake time）

- 意味：設定を 100% に配り終えてから、デプロイ完了とみなすまで CloudWatch アラームを見続ける時間
- ポイント：この間にアラームが鳴ってもロールバックされる。「全部に配った直後に出る問題も拾いたい」ならベイク時間を長くする

#### バリデータ（ばりでーた / validator）

- 意味：設定データが文法的にも意味的にも正しいかを、デプロイの前に調べる仕組み。JSON スキーマか Lambda 関数を使う
- ポイント：JSON スキーマは形（型・必須項目）を、Lambda は「値が素数か」のような中身の判断を調べる。Lambda は appconfig.amazonaws.com から呼べるように権限を付ける

#### AppConfig エージェント（あっぷこんふぃぐえーじぇんと / AWS AppConfig Agent）

- 意味：アプリの横で動き、設定データをローカルにキャッシュして、裏で AppConfig を定期的にポーリングする Amazon 製のプロセス
- ポイント：アプリは localhost:2772 に HTTP GET するだけ。API（StartConfigurationSession・GetLatestConfiguration）とトークンの管理をエージェントがやるので、呼び出しが減りコストも下がる。推奨の取り方

#### AppConfig エージェント Lambda 拡張機能（らむだかくちょうきのう / AWS AppConfig Agent Lambda extension）

- 意味：Lambda 関数のレイヤーとして追加する、AppConfig エージェントの Lambda 版
- ポイント：関数と並んで動き、設定をキャッシュする。AppConfig への API 呼び出しと関数の処理時間が減る

## 問題演習

### 10-1

#### 問 dop-10-o01

- 問：本番の RDS のパラメータが先週変わり、性能が落ちた。いつ・どのように設定が変わったか、変わる前の値は何だったかを確かめたい。最も適したものはどれか。
- ア：CloudTrail のイベント履歴だけを見る
- イ：CloudWatch のメトリクスを見る
- ウ：AWS Config の設定履歴（タイムライン）を見る
- エ：Trusted Advisor のチェックを見る
- 正解：ウ
- 解説：Config は設定項目を履歴として残すので、変更の前後の値と時刻を比べられる。誰が変えたかは CloudTrail と合わせて見る。
- アの意味：API を呼んだ人と時刻は分かるが、リソースの設定の前後の状態を並べて見るものではない。
- イの意味：性能の数値は分かるが、設定の中身は記録しない。
- ウの意味：正しい。
- エの意味：ベストプラクティスのチェックで、設定の変化の履歴は残さない。
- 出典：オリジナル問題（根拠：AWS「AWS Config デベロッパーガイド」AWS Config とは?（『また、AWS Config が提供するリソースの設定履歴を使用して、問題のトラブルシューティングを行ない、問題が発生したリソースの最後の正常であると判明している設定にアクセスできます。』））

#### 問 dop-10-o02

- 問：AWS Config を有効にしたはずなのに、新しく作った EC2 インスタンスの設定項目が 1 つも作られない。ルールも評価されない。最初に確かめるべきものはどれか。
- ア：SNS トピックのサブスクリプション
- イ：設定レコーダーが起動していて、そのリソースタイプが記録の範囲に入っているか
- ウ：アグリゲータの設定
- エ：コンフォーマンスパックのテンプレート
- 正解：イ
- 解説：設定項目を作るのは設定レコーダー。止まっているか、記録するリソースタイプから外れていると何も記録されない。
- アの意味：通知の受け取り先で、記録そのものには関係しない。
- イの意味：正しい。
- ウの意味：複数アカウントのデータを集めて見るもので、記録はしない。
- エの意味：ルールを配るもので、記録の有無は決めない。
- 出典：オリジナル問題（根拠：AWS「AWS Config デベロッパーガイド」AWS Config の用語と概念（『*設定レコーダー*は、範囲に含まれるリソースタイプの設定変更を設定項目として保存します。』））

#### 問 dop-10-o03

- 問：監査のため、ある時点でアカウント内の記録対象のすべてのリソースの設定を、まとめて S3 に出力したい。何を使うか。
- ア：設定スナップショットの配信（deliver-config-snapshot）
- イ：設定履歴ファイル
- ウ：設定ストリーム
- エ：高度なクエリ
- 正解：ア
- 解説：スナップショットは記録しているすべてのリソースの、ある時点の設定項目の集まり。CLI の deliver-config-snapshot などで S3 に送れる。
- アの意味：正しい。
- イの意味：リソースタイプ別に 6 時間ごとに届く、変更があったリソースの記録。全体の一時点ではない。
- ウの意味：変更があるたびに SNS に流れる通知で、全体の一覧ではない。
- エの意味：今の設定を検索できるが、「ある時点の全体を S3 に出す」ものではない。
- 出典：オリジナル問題（根拠：AWS「AWS Config デベロッパーガイド」AWS Config の仕組み（『設定スナップショットには、AWS アカウント で AWS Config が記録したすべてのリソースの設定詳細が含まれています。』））

#### 問 dop-10-o04

- 問：Config の設定履歴ファイルが S3 バケットにたまり続け、費用が増えている。古いファイルを 1 年で消したい。どうするか。
- ア：配信チャネルの保存期間を 365 日にする
