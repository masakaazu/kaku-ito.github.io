## 17-1 EventBridge の基本

### まとめ表

| やりたいこと | 使うもの |
| :-: | :-: |
| AWS のサービスのイベントで何かを動かす | デフォルトのイベントバス＋ルール |
| 条件に合うイベントだけ選ぶ | イベントパターン（prefix・anything-but・numeric など） |
| ターゲットに渡す形を変える | 入力トランスフォーマー |
| 外部の HTTPS の API に送る | API 送信先（接続で認証） |
| 決まった時刻・1 回だけ呼ぶ | EventBridge Scheduler |

### バスとルール

#### イベントバス（いべんとばす / event bus）

- 意味：イベントを受け取り、ルールに合うものをターゲットに配るルーター。デフォルトのイベントバス（AWS のサービスのイベントが自動で届く）・カスタムイベントバス（自分のアプリ用）・パートナーイベントバス（SaaS 用）がある
- ポイント：EC2 の状態変化や CodePipeline の失敗など AWS のイベントはデフォルトのイベントバスに届く

#### ルール（るーる / rule）

- 意味：イベントバスに届いたイベントをイベントパターンで選び、ターゲットに送る設定。スケジュールで動くルールもある
- ポイント：1 つのルールに複数のターゲットを付けると並行して送られる（1 ルールに 5 つまで）

#### イベントパターン（いべんとぱたーん / event pattern）

- 意味：どのイベントをターゲットに送るかを決める JSON。イベントと同じ形で、一致させたい値を書く
- ポイント：比較演算子で prefix（前方一致）・suffix・anything-but（〜以外）・numeric（数値の範囲）・exists（項目があるか）・equals-ignore-case を使える
- 例：{"source": ["aws.ec2"], "detail": {"state": ["stopped"]}}

#### 入力トランスフォーマー（にゅうりょくとらんすふぉーまー / input transformer）

- 意味：入力パスでイベントから値を取り出して変数にし、入力テンプレートでターゲットに渡す文字列や JSON を作る機能
- ポイント：ターゲットが決まった形の入力を求めるとき（Slack への文面、API の本文など）に使う。イベントを選ぶ機能ではない

### いろいろなターゲット

#### API 送信先（えーぴーあいそうしんさき / API destination）

- 意味：ルールやパイプのターゲットにできる外部の HTTPS エンドポイント。接続（connection）に認証方法と認証情報を持たせ、呼び出しの速さの上限も決められる
- ポイント：SaaS の Webhook などに Lambda を書かずに送れる。認証情報は Secrets Manager に保存される

#### EventBridge Scheduler（すけじゅーら / EventBridge Scheduler）

- 意味：cron 式・rate 式・1 回限りのスケジュールで、270 以上の AWS のサービスの API を呼び出すサービス。タイムゾーンを指定できる
- ポイント：フレキシブルな時間枠でターゲットへの呼び出しを分散させ、再試行の上限・DLQ も設定できる。たくさんのスケジュールを扱うならルールより Scheduler

#### スキーマレジストリ（すきーまれじすとり / schema registry）

- 意味：イベントの構造（スキーマ）を保存する場所。イベントバスのスキーマを自動で検出でき、各言語のコードバインディングをダウンロードできる
- ポイント：イベントを扱うコードを書きやすくするための機能で、イベントの配信や検証はしない

## 17-2 確実に届ける・アカウントをまたぐ

### まとめ表

| 心配 | 対策 |
| :-: | :-: |
| ターゲットが一時的に失敗 | 再試行ポリシー（既定 24 時間・185 回） |
| 再試行しても届かない | ターゲットに DLQ（標準 SQS） |
| 過去のイベントを流し直したい | アーカイブと再生 |
| 他のアカウント・リージョンへ | 受信側のバスのポリシー＋送信側のルール |
| 1 対 1 でつなぎ、絞って足して送る | EventBridge Pipes |

### 届かなかったとき

#### 再試行ポリシー（さいしこうぽりしー / retry policy）

- 意味：ターゲットへの配信に失敗したときに、どれだけの時間・回数再試行するかの設定。既定は指数バックオフとジッタで 24 時間・最大 185 回
- ポイント：再試行を使い切ったイベントは捨てられる。失いたくないなら DLQ を付ける

#### EventBridge の DLQ（でっどれたーきゅー / dead-letter queue）

- 意味：ターゲットに届けられなかったイベントを入れておく標準の SQS キュー。ルールのターゲットごとに設定する
- ポイント：SQS のキューポリシーで EventBridge からの送信を許可する。FIFO キューは使えない

#### アーカイブと再生（あーかいぶとさいせい / archive and replay）

- 意味：イベントバスに届いたイベントをアーカイブに保存し、後で期間を指定して同じバスに送り直す機能
- ポイント：既定では無期限に保存。イベントパターンで保存するイベントを絞れる。障害からの回復や新機能の確かめに使う

### つなぐ

#### クロスアカウントのイベント（くろすあかうんと / cross-account events）

- 意味：受信側のアカウントのイベントバスのアクセス許可（リソースベースポリシー）で送信元のアカウントや組織を許可し、送信側のアカウントのルールのターゲットに受信側のイベントバスを指定する
- ポイント：送信側のルールには IAM ロールが要る。組織全体を許可するなら aws:PrincipalOrgID の条件。別のリージョンのイベントバスも同じようにターゲットにできる

#### EventBridge Pipes（ぱいぷす / EventBridge Pipes）

- 意味：SQS・Kinesis・DynamoDB Streams などのソースと 1 つのターゲットを 1 対 1 でつなぐ機能。途中でフィルターとエンリッチメント（Lambda・Step Functions・API で情報を足す）を入れられる
- ポイント：イベントバスは「多くの送り元から多くのターゲットへ配る」、Pipes は「1 つのソースから 1 つのターゲットへ」。つなぐための Lambda を書かずに済む

## 17-3 イベント駆動のサービスのつなぎ方

### まとめ表

| 場面 | 使うもの |
| :-: | :-: |
| S3 のイベントをいろいろな先へ・FIFO へ | S3 で EventBridge を有効にする |
| 1 つのメッセージを複数のシステムへ | SNS → 複数の SQS（ファンアウト）＋フィルターポリシー |
| Lambda の非同期呼び出しの失敗 | 再試行（既定 2 回）→ 失敗時の送信先 |
| SQS のバッチの一部だけ失敗 | 部分的なバッチレスポンス（ReportBatchItemFailures） |
| ストリームの不良レコード | バッチの分割・最大再試行回数・失敗時の送信先 |
| 手順の再試行と失敗時の分岐 | Step Functions の Retry と Catch |

### S3・SNS・SQS

#### S3 イベント通知と EventBridge（えすすりーいべんとつうち / S3 Event Notifications）

- 意味：S3 のオブジェクトの作成・削除などを知らせる機能。送り先は SNS・SQS・Lambda。バケットで EventBridge を有効にすると、すべてのイベントが EventBridge にも送られる
- ポイント：SQS FIFO キューには S3 イベント通知で直接送れないので EventBridge を使う。EventBridge ならイベントパターンで細かく絞れ、ターゲットも多い

#### SNS のファンアウト（ふぁんあうと / SNS fan-out）

- 意味：1 つの SNS トピックに複数の SQS キューを購読させ、1 つのメッセージを複数のシステムがそれぞれのペースで処理できるようにする形
- ポイント：1 つの SQS キューを複数のシステムで共有すると、メッセージは 1 つのシステムにしか届かない

#### SNS のフィルターポリシー（ふぃるたーぽりしー / subscription filter policy）

- 意味：サブスクリプションに付ける JSON で、そのサブスクリプションが受け取るメッセージを絞る
- ポイント：範囲はメッセージ属性（既定）かメッセージ本文。トピックを分けずに、受け取り手ごとに必要なものだけ届ける

#### SQS のデッドレターキュー（でっどれたーきゅー / SQS dead-letter queue）

- 意味：何度受信しても処理できなかったメッセージを移すキュー。ソースキューの再処理ポリシー（redrive policy）の maxReceiveCount で回数を決める
- ポイント：毒のメッセージ（処理できないもの）が他を妨げるのを防ぐ。原因を直したら、デッドレターキューからソースキューに戻せる（redrive）

#### 可視性タイムアウト（かしせいたいむあうと / visibility timeout）

- 意味：あるコンシューマーが受け取ったメッセージを、他のコンシューマーから見えなくする時間
- ポイント：処理時間より短いと、処理中のメッセージが他のコンシューマーにも届いて二重に処理される。Lambda のイベントソースなら関数のタイムアウトより十分長くする

### Lambda の呼び出し方

#### Lambda の非同期呼び出し（ひどうきよびだし / asynchronous invocation）

- 意味：S3・SNS・EventBridge などからの呼び出しで、Lambda がイベントをキューに入れてすぐに応答し、別のプロセスが関数に渡す形
- ポイント：関数がエラーを返すと既定でさらに 2 回再試行する。スロットルとシステムエラーはキューに戻して既定で最大 6 時間再試行する

#### 失敗時の送信先（しっぱいじのそうしんさき / on-failure destination）

- 意味：非同期呼び出しやイベントソースマッピングで、処理に失敗したイベントの記録を送る先。SQS・SNS・Lambda・EventBridge・S3 から選ぶ。成功時の送信先も別に決められる
- ポイント：DLQ はイベントの中身だけ。送信先はエラーの内容などの詳細も含むので、こちらがすすめられる

#### イベントソースマッピング（いべんとそーすまっぴんぐ / event source mapping）

- 意味：SQS・Kinesis・DynamoDB Streams・MSK などから Lambda がレコードを読み、バッチにまとめて関数を呼ぶしくみ
- ポイント：SQS は部分的なバッチレスポンス（ReportBatchItemFailures）で失敗したメッセージだけ再処理。ストリームはバッチの分割（BisectBatchOnFunctionError）・最大再試行回数・最大レコード経過時間・失敗時の送信先で、不良レコードがシャードを止め続けるのを防ぐ

### 手順とアラーム

#### Step Functions の Retry と Catch（りとらいときゃっち / Retry and Catch）

- 意味：Task・Parallel・Map の状態に書く。Retry は指定したエラーを、間隔（IntervalSeconds）・回数（MaxAttempts）・倍率（BackoffRate）で再試行する。Catch は再試行しても失敗したとき、別の状態（通知や戻す処理）に進める
- ポイント：Standard ワークフローは最大 1 年・各手順が 1 回だけ。Express は最大 5 分・1 回以上で、件数の多い処理向け

#### アラームの状態変化イベント（あらーむのじょうたいへんかいべんと / alarm state change event）

- 意味：CloudWatch アラームの状態が変わるたびに EventBridge に送られるイベント
- ポイント：アラームのアクション（SNS・EC2・Auto Scaling・Systems Manager）にない処理は、このイベントを EventBridge のルールで受けて Lambda や Step Functions を動かす

## 問題演習

### 17-1

#### 問 dop-17-o01

- 問：EC2 インスタンスが停止したら Lambda 関数を動かしたい。EventBridge のどのイベントバスにルールを作るか。

- 正解：ウ
- 解説：AWS のサービスのイベントは、アカウントのデフォルトのイベントバスに自動で届く。

- ウの意味：正しい。
