## 19-1 デプロイの失敗を調べる

### まとめ表

| 症状 | まず見る・直す |
| :-: | :-: |
| CodeDeploy のデプロイが失敗 | インスタンスのエージェントのデプロイログ（CloudWatch Logs に集める） |
| 前のリビジョンの ApplicationStop で毎回失敗 | ApplicationStop の失敗を無視してデプロイ |
| 「ファイルが既に存在」 | 既存のファイルの扱い（上書き・保持）を指定 |
| CodeBuild で Docker が使えない | 特権モード |
| CloudFormation が失敗 | スタックイベントの最初の失敗の理由 |
| UPDATE_ROLLBACK_FAILED | ロールバックを続ける（直せないリソースはスキップ） |

### CodeDeploy

#### CodeDeploy のデプロイログ（でぷろいろぐ / CodeDeploy deployment logs）

- 意味：インスタンスで CodeDeploy エージェントが書くログ。Linux では /opt/codedeploy-agent/deployment-root/deployment-logs/codedeploy-agent-deployments.log
- ポイント：多くの失敗の原因はここでわかる。1 台ずつ見るより、CloudWatch エージェントで CloudWatch Logs に集めるのがすすめられる

#### ApplicationStop の失敗（あぷりけーしょんすとっぷのしっぱい / ApplicationStop failure）

- 意味：ApplicationStop・BeforeBlockTraffic・AfterBlockTraffic では、前回成功したリビジョンの AppSpec のスクリプトが動く。そのスクリプトが壊れていると、新しいリビジョンを直しても毎回失敗する
- ポイント：デプロイを作るときに「ApplicationStop の失敗を無視する」（ignoreApplicationStopFailures）を選んで通す

#### 既存のファイルの扱い（きそんのふぁいるのあつかい / file exists behavior）

- 意味：CodeDeploy が置くファイルがすでにインスタンスにあるとき、失敗にするか（既定）・上書きするか・残すかの設定
- ポイント：手で置いたファイルや、前回のデプロイの記録にないファイルがあると「既に存在する」で失敗する

#### タグとデプロイグループ（たぐとでぷろいぐるーぷ / tags and deployment group）

- 意味：EC2 のデプロイ先はタグや Auto Scaling グループで決める
- ポイント：タグを付けた直後は対象に入らないことがある。数分（5 分ほど）待ってからデプロイする。エージェントが動いていない・インスタンスプロファイルに S3 の読み取り権限がない、も典型的な原因

#### 残ったライフサイクルフック（のこったらいふさいくるふっく / leftover lifecycle hooks）

- 意味：CodeDeploy が Auto Scaling グループに付けたライフサイクルフックが、デプロイグループを消した後などに残ったもの
- ポイント：新しいインスタンスがハートビートタイムアウトまで待たされる。残ったフックを探して消す

### CodeBuild と CodePipeline

#### 特権モード（とっけんもーど / privileged mode）

- 意味：CodeBuild のビルド環境で Docker デーモンを使えるようにする設定
- ポイント：docker build で「Docker デーモンにつながらない」なら特権モードが無効

#### VPC 内のビルドの通信（ぶいぴーしーないのびるど / VPC builds and internet access）

- 意味：VPC につないだ CodeBuild はプライベート IP アドレスしか持たないので、外に出るにはプライベートサブネット＋NAT ゲートウェイか VPC エンドポイントが要る
- ポイント：パブリックサブネットに置いてもパブリック IP アドレスは付かないので外に出られない

#### パイプラインのアーティファクトのバケット（あーてぃふぁくとのばけっと / artifact store）

- 意味：CodePipeline がステージ間でアーティファクトを渡す S3 バケット
- ポイント：パイプラインと同じリージョンに置く。サービスロールにバケットと KMS キーの権限が要る。失敗したアクションは詳細でエラーを見て、直したらステージを再試行できる

### CloudFormation と Canary

#### スタックイベント（すたっくいべんと / stack events）

- 意味：スタックの作成・更新・削除で、リソースごとに起きたことの記録。オペレーション ID で 1 回の操作のイベントにしぼれる
- ポイント：最初に失敗したリソースの「ステータスの理由」を見る。後に続く失敗はその結果であることが多い

#### 正常にプロビジョニングされたリソースの保持（りそーすのほじ / preserve successfully provisioned resources）

- 意味：スタックの操作が失敗しても、成功したリソースをロールバックせずに残す設定（--disable-rollback・on-failure DO_NOTHING）
- ポイント：大きなスタックで、直すたびに最初から作り直す時間を省ける

#### UPDATE_ROLLBACK_FAILED（あっぷでーとろーるばっくふぇいるど / UPDATE_ROLLBACK_FAILED）

- 意味：更新に失敗して元に戻そうとしたが、戻すのにも失敗した状態。手で消したリソースなどが原因
- ポイント：この状態では変更セットも更新もできない。原因を直して「更新のロールバックを続ける」。直せないリソースはスキップする

#### Canary の失敗の調べ方（かなりーのしっぱい / troubleshooting canaries）

- 意味：CloudWatch Synthetics の Canary が失敗したとき、実行ごとのスクリーンショット・HAR ファイル・ログ・ステップのレポートで原因を調べる
- ポイント：どのステップで、どのリクエストで失敗したかがわかる

## 19-2 動いているシステムの障害を調べる

### まとめ表

| 症状 | まず見る・直す |
| :-: | :-: |
| Auto Scaling が起動できない | アクティビティ履歴のステータスとメッセージ |
| ECS のタスクがすぐ止まる | 停止したタスクの理由（1 時間だけ表示） |
| CannotPullContainerError（タイムアウト） | NAT ゲートウェイか VPC エンドポイント |
| CannotPullContainerError（権限） | タスク実行ロール |
| タスク数が増えない | サービスイベント |
| EKS のノードが参加しない | aws-auth・アクセスエントリのノード IAM ロール ARN |
| Lambda がタイムアウト | タイムアウト・メモリ・Lambda Insights |

### Auto Scaling と ECS

#### アクティビティ履歴（あくてぃびてぃりれき / activity history）

- 意味：Auto Scaling グループの起動・終了の記録。ステータスとエラーメッセージ（StatusMessage）が残る
- ポイント：起動の失敗の理由（キャパシティ不足・セキュリティグループがない・AMI がないなど）はここで見る。describe-scaling-activities でも取れる

#### 停止したタスクの理由（ていしたたすくのりゆう / stopped task reason）

- 意味：ECS のタスクが止まった理由（コンテナの終了・ヘルスチェックの失敗・イメージを取れないなど）
- ポイント：停止したタスクはコンソールに 1 時間しか出ない。長く残すなら EventBridge でタスクの状態変化を受けてログに残す

#### CannotPullContainerError（きゃのっとぷるこんてなえらー / CannotPullContainerError）

- 意味：ECS がコンテナイメージを取れずにタスクを起動できないエラー
- ポイント：タイムアウトならイメージの取得先への道（NAT ゲートウェイ、または ECR の VPC エンドポイント＋S3 のゲートウェイエンドポイント）がない。拒否なら Fargate ではタスク実行ロールに ECR の権限がない

#### ECS Exec（えくぜっく / ECS Exec）

- 意味：動いているコンテナに、SSH なしでコマンドを実行したりシェルに入ったりする機能。Session Manager のしくみを使う
- ポイント：サービスやタスクで enableExecuteCommand を有効にし、タスクロールに SSM のメッセージの権限を付ける。インターネットがないなら ssmmessages の VPC エンドポイント

#### サービスイベント（さーびすいべんと / service event messages）

- 意味：ECS のサービススケジューラが出すメッセージ。タスクを配置できない理由や、ヘルスチェックによる置き換えなどが出る
- ポイント：サービスの問題を調べるときは最初に見る

### EKS と Lambda

#### EKS のノードが参加しない（のーどがさんかしない / nodes fail to join cluster）

- 意味：ワーカーノードが EKS クラスターに Ready で現れない状態
- ポイント：aws-auth の ConfigMap やアクセスエントリに、インスタンスプロファイルではなくノード IAM ロールの ARN が入っているか確かめる。クラスターのエンドポイントへの通信も確かめる

#### kubectl の Unauthorized（あんおーそらいずど / kubectl unauthorized）

- 意味：kubectl が EKS の API サーバーで認証・認可されないエラー
- ポイント：クラスターを作った IAM プリンシパルと、kubectl が使っている IAM プリンシパルが違うことが多い。アクセスエントリで権限を与える

#### Lambda のタイムアウト（たいむあうと / Lambda timeout）

- 意味：関数の実行が設定した時間（最大 15 分）を超えて止められること。ログに Task timed out が出る
- ポイント：大きいペイロードや遅い呼び出し先が原因。タイムアウトを見直し、メモリを増やすと CPU も増える

#### Lambda Insights（らむだいんさいと / CloudWatch Lambda Insights）

- 意味：Lambda 関数の CPU 時間・メモリ・ディスク・ネットワーク・コールドスタートなどを集めて見せる機能。拡張機能（レイヤー）で入れる
- ポイント：関数の中の資源の使い方を見る。リクエストの流れは X-Ray

## 19-3 根本原因を探す道具

### まとめ表

| やりたいこと | 道具 |
| :-: | :-: |
| 複数のサービスの運用の問題を 1 か所で扱う | OpsCenter（OpsItem） |
| アラームから関係するデータと原因の仮説を集める | CloudWatch 調査 |
| つながらない理由（設定）を調べる | Reachability Analyzer |
| ネットワークがない・起動しないインスタンスに入る | EC2 シリアルコンソール |

### 道具

#### OpsCenter（おぷすせんたー / AWS Systems Manager OpsCenter）

- 意味：運用の問題（OpsItem）を集めて、関係するリソース・似た OpsItem・ランブックと合わせて調べ、解決する場所
- ポイント：CloudWatch アラームや EventBridge のルールから OpsItem を自動で作れる

#### CloudWatch 調査（ちょうさ / CloudWatch investigations）

- 意味：生成 AI でメトリクス・ログ・デプロイのイベントなどを調べ、根本原因の仮説を出すアシスタント
- ポイント：アラームなどから調査を始める。調べる範囲は始めた人の権限の中

#### Reachability Analyzer（りーちゃびりてぃあならいざー / Reachability Analyzer）

- 意味：VPC の中の 2 つのリソースの間がつながるかを、ルートテーブル・セキュリティグループ・ネットワーク ACL などの設定から調べる道具。つながらないときは止めている部品を示す
- ポイント：実際の通信を送らずに設定を調べる。実際の通信の記録はフローログ

#### EC2 シリアルコンソール（しりあるこんそーる / EC2 serial console）

- 意味：インスタンスのシリアルポートにつなぐ機能。ネットワークが使えなくても入れる
- ポイント：ネットワーク設定の誤りや起動の失敗で SSH も Session Manager も使えないときに使う

## 問題演習

### 19-1

#### 問 dop-19-o01

- 問：EC2 への CodeDeploy のデプロイが AfterInstall で失敗した。原因を調べるため、まず何を見るか。
- ア：CloudTrail のイベント履歴
- イ：インスタンスの CodeDeploy エージェントのデプロイログ
- ウ：VPC フローログ
- エ：AWS Config の設定履歴
- 正解：イ
- 解説：多くの失敗の原因は、インスタンスに残るデプロイのログでわかる。CloudWatch Logs に集めておくと見やすい。
- アの意味：API の呼び出しの記録で、スクリプトの中のエラーはわからない。
- イの意味：正しい。
- ウの意味：通信の記録で、スクリプトのエラーはわからない。
- エの意味：リソースの設定の履歴。
- 出典：オリジナル問題（根拠：AWS「AWS CodeDeploy ユーザーガイド」EC2/オンプレミスのデプロイに関する問題のトラブルシューティング（『多くのデプロイ失敗の原因は、デプロイプロセス中に作成されたログファイルを確認して特定できます。』））

#### 問 dop-19-o02

- 問：デプロイ先のタグを新しいインスタンスに付けて、すぐにデプロイしたが、そのインスタンスが対象に入らなかった。どうするか。
- ア：CodeDeploy エージェントを入れ直す
- イ：インスタンスプロファイルを付け替える
- ウ：デプロイグループを作り直す
- エ：タグを付けてから数分待ってデプロイする
- 正解：エ
- 解説：CodeDeploy がタグを読み込むまで数分かかるので、少なくとも 5 分ほど待つ。
- アの意味：対象に入らない理由ではない。
- イの意味：対象に入らない理由ではない。
- ウの意味：必要ない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：AWS「AWS CodeDeploy ユーザーガイド」インスタンスの問題のトラブルシューティング（『インスタンスにタグを付けてから、そのインスタンスへのデプロイを試みるまでに、少なくとも 5 分待つことをお勧めします。』））

#### 問 dop-19-o03

- 問：前回のリビジョンの ApplicationStop のスクリプトにバグがあり、新しいリビジョンで直してもデプロイが毎回 ApplicationStop で失敗する。どうするか。
- ア：新しいリビジョンの AppSpec の ApplicationStop をさらに直す
- イ：CodeDeploy エージェントを再起動する
- ウ：デプロイを作るときに ApplicationStop の失敗を無視するように指定する
- エ：自動ロールバックを有効にする
- 正解：ウ
- 解説：ApplicationStop は前回成功したリビジョンのスクリプトが動くので、新しいリビジョンを直しても効かない。失敗を無視して一度通す。
- アの意味：新しいリビジョンのスクリプトはこの段階では使われない。
- イの意味：同じスクリプトが動いて失敗する。
- ウの意味：正しい。
- エの意味：前のリビジョンに戻るだけで、問題は残る。
- 出典：オリジナル問題（根拠：AWS「AWS CodeDeploy ユーザーガイド」EC2/オンプレミスのデプロイに関する問題のトラブルシューティング（『デプロイ時に、CodeDeploy エージェントは ApplicationStop、BeforeBlockTraffic、および AfterBlockTraffic に対して前回の正常なデプロイで AppSpec ファイルに指定されていたスクリプトを実行します。』））

#### 問 dop-19-o04

- 問：運用者が手で置いた設定ファイルと同じ名前のファイルがリビジョンにあり、デプロイが失敗した。リビジョンの内容で置き換えたい。どうするか。
- ア：既存のファイルの扱いを「上書き」にしてデプロイする
- イ：インスタンスを作り直す
- ウ：デプロイ設定を AllAtOnce にする
- エ：エージェントのログを消す
- 正解：ア
- 解説：同じファイルがあると既定では失敗する。上書きか保持かを指定できる。
- アの意味：正しい。
- イの意味：手間がかかり、手で置く運用が続けばまた起きる。
- ウの意味：一度に配る台数の設定で、ファイルの扱いは変わらない。
- エの意味：関係ない。
- 出典：オリジナル問題（根拠：AWS「AWS CodeDeploy ユーザーガイド」EC2/オンプレミスのデプロイに関する問題のトラブルシューティング（『CodeDeploy でファイルをデプロイしようとして、指定したデプロイ先のインスタンスに同じファイルが既に存在している場合、そのインスタンスへのデプロイは失敗する場合があります。』））

#### 問 dop-19-o05

- 問：CodeDeploy のデプロイグループを消した後、Auto Scaling グループで起動したインスタンスが、ハートビートタイムアウトまで待たされるようになった。原因はどれか。
- ア：CodeDeploy エージェントが古い
- イ：ヘルスチェックの猶予期間が短い
- ウ：CodeDeploy が付けたライフサイクルフックが残っている
- エ：起動テンプレートのバージョンが古い
- 正解：ウ
- 解説：残ったフックがインスタンスを待たせる。describe-lifecycle-hooks などで探して消す。
- アの意味：待たされる理由ではない。
- イの意味：待たされる理由ではない。
- ウの意味：正しい。
- エの意味：待たされる理由ではない。
- 出典：オリジナル問題（根拠：AWS「AWS CodeDeploy ユーザーガイド」Amazon EC2 Auto Scaling の問題のトラブルシューティング（『出力に `hooksNotCleanedUp` 構造と Amazon EC2 Auto Scaling ライフサイクルフックの一覧が含まれている場合、ライフサイクルフックの残りがあります。』））

#### 問 dop-19-o06

- 問：CodeBuild の buildspec で docker build を実行すると、Docker デーモンにつながらないというエラーになる。どうするか。
- ア：サービスロールに ECR の権限を足す
- イ：ビルドプロジェクトで特権モードを有効にする
