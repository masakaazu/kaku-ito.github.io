## 03-1 TCP のしくみ

### まとめ表

| 項目 | TCP | UDP |
| :-: | :-: | :-: |
| 接続 | コネクション型（3 ウェイハンドシェイク） | コネクションレス |
| 信頼性 | 順番どおり・失ったら再送 | 再送しない（ベストエフォート） |
| 番号 | シーケンス番号・確認応答番号 | なし |
| 流れの制御 | ウィンドウ（フロー制御）・輻輳制御 | なし |
| ヘッダー | 20 バイト以上（オプションで増える） | 8 バイト |
| 向くもの | Web・SSH・ファイル転送・メール | 音声・動画（RTP）・DHCP・TFTP・SNMP |

### つなぐ・切る

#### TCP（てぃーしーぴー / Transmission Control Protocol）

- 意味：アプリに「信頼できる、順番どおりの、バイトの流れ」を届けるトランスポート層のプロトコル
- ポイント：シーケンス番号で失ったデータを見つけ、チェックサムで壊れたデータを見つけ、再送で直す（RFC 9293 2.2）。コネクション型で、両方向にデータを流せる。ポート番号でアプリを見分ける
- 語の意味：Transmission＝送ること／Control＝制御／Protocol＝通信の決まり

#### 3 ウェイハンドシェイク（すりーうぇいはんどしぇいく / three-way handshake）

- 意味：TCP のコネクションを始めるときの 3 回のやりとり。SYN → SYN＋ACK → ACK
- ポイント：①A が SYN（自分の最初の番号を知らせる）②B が SYN と ACK（自分の番号＋A の SYN を受けた）③A が ACK。これで両方が ESTABLISHED になる。UDP にはこの手順がない
- 例：A が SEQ=100 で SYN → B が SEQ=300・ACK=101 → A が ACK=301（RFC 9293 図 6）

#### FIN と RST（ふぃんとりせっと / FIN, RST flags）

- 意味：FIN は「もう送るデータはない」と知らせるフラグ。RST はコネクションをすぐに打ち切る（リセットする）フラグ
- ポイント：ふつうの終わり方は両側がそれぞれ FIN を送り、相手が ACK で受ける（片方ずつ閉じる）。RST はおかしな状態や、開いていないポートへの接続などで使う
- 語の意味：FIN＝Finish（終わり）／RST＝Reset（やり直し）／SYN＝Synchronize（番号を合わせる）／ACK＝Acknowledgment（受け取った）

### 確実に届ける

#### シーケンス番号（しーけんすばんごう / sequence number）

- 意味：送るデータの位置を、バイト単位で表す 32 ビットの番号。セグメントの最初のバイトの番号を入れる
- ポイント：受け手は番号を見て、順番を並べ直し、抜けや重複を見つける。最初の番号（ISN）は SYN で知らせ、データは ISN＋1 から始まる
- 例：SEQ=101 のセグメントに 500 バイト → 次は SEQ=601

#### 確認応答番号（かくにんおうとうばんごう / acknowledgment number, ACK）

- 意味：「次はこの番号のバイトを待っている」と相手に返す番号
- ポイント：ACK＝受け取った最後のバイト＋1。ACK が来ないデータは、時間切れ（RTO）のあとで再送する。UDP には確認応答がない
- 例：SEQ=101 から 500 バイト受けた → ACK=601

#### 再送（さいそう / retransmission）

- 意味：確認応答が返ってこないデータを、もう一度送ること
- ポイント：待つ時間（再送タイムアウト、RTO）は通信の往復時間から計算して変える（RFC 9293 3.8.1）。UDP は再送しない。再送が要るなら UDP を使うアプリが自分で作る（RFC 8085）

#### ウィンドウ（うぃんどう / window, flow control）

- 意味：受け手が「今これだけのバイト数なら受け取れる」と送り手に知らせる値。送り手はその範囲までまとめて送れる
- ポイント：受け手のバッファーに合わせて送る量を調整する（フロー制御）。ACK を 1 つずつ待たずに続けて送れるので速い（スライディングウィンドウ）。受け手が 0 を返すと送り手は止まる
- 例：TCP ヘッダーの Window 欄は 16 ビット

#### 輻輳制御（ふくそうせいぎょ / congestion control）

- 意味：ネットワークが混んでいるのを感じて、送る量を減らすしくみ
- ポイント：スロースタート、輻輳回避、高速再送、高速回復（RFC 5681）。フロー制御は「受け手」に合わせ、輻輳制御は「ネットワーク」に合わせる。UDP には輻輳制御がない（RFC 8085）

#### TCP ヘッダー（てぃーしーぴーへっだー / TCP header）

- 意味：TCP のセグメントの先頭につく情報。送信元・宛先ポート、シーケンス番号、確認応答番号、フラグ、ウィンドウ、チェックサムなど
- ポイント：長さは 32 ビット単位で Data Offset に入る。オプションがなければ 5（＝20 バイト）。UDP のヘッダー（8 バイト）より大きい
- 例：フラグ CWR・ECE・URG・ACK・PSH・RST・SYN・FIN

## 03-2 UDP のしくみ

### まとめ表

| 項目 | 中身 |
| :-: | :-: |
| ヘッダー | 送信元ポート・宛先ポート・長さ・チェックサムの 8 バイト |
| 接続 | つながない（ハンドシェイクなし） |
| 再送・順番 | しない（アプリが必要なら自分で作る） |
| 輻輳制御 | ない |
| 使う例 | DNS の問い合わせ・DHCP・TFTP・SNMP・syslog・NTP・RTP（音声・動画） |

### UDP の性質

#### UDP（ゆーでぃーぴー / User Datagram Protocol）

- 意味：最小限のしくみで、メッセージ（データグラム）を送るトランスポート層のプロトコル
- ポイント：届くことも、重ならないことも保証しない（RFC 768）。そのかわり接続の手間がなく、軽くて速い。順番どおり確実に届けたいアプリは TCP を使う
- 語の意味：User＝利用者（アプリ）／Datagram＝1 つずつ独立して送るデータ／Protocol＝通信の決まり

#### コネクションレス（こねくしょんれす / connectionless）

- 意味：送る前に相手と接続をつくらず、いきなりデータを送る方式
- ポイント：UDP は端どうしの接続をつくらないので、つなぐ・切るの手間がなく、覚えておく状態も少ない（RFC 8085）。TCP はコネクション型
- 例：DNS の問い合わせは 1 往復で終わる

#### UDP ヘッダー（ゆーでぃーぴーへっだー / UDP header）

- 意味：UDP の先頭につく 8 バイトの情報。送信元ポート・宛先ポート・長さ・チェックサムの 4 つ
- ポイント：長さはヘッダーを含むので、いちばん小さい値は 8（RFC 768）。シーケンス番号も確認応答番号もウィンドウもない
- 例：16 ビット × 4 ＝ 64 ビット ＝ 8 バイト

#### ベストエフォート（べすとえふぉーと / best-effort）

- 意味：できるだけ届けるが、届くことは保証しない送り方
- ポイント：UDP は「最小限の、信頼性のない、ベストエフォートの」トランスポート（RFC 8085）。失ったパケットを再送しない。重複や順番の入れ替わりも、アプリが自分で処理する

#### RTP（あーるてぃーぴー / Real-time Transport Protocol）

- 意味：音声や動画をリアルタイムで運ぶためのプロトコル。順番の番号や時刻の印を付ける
- ポイント：ふつう UDP の上で動き、UDP のポート番号とチェックサムを使う（RFC 3550）。音声は遅れて届いても役に立たないので、再送する TCP ではなく UDP を使う
- 語の意味：Real-time＝その場で／Transport＝運ぶ

#### チェックサム（ちぇっくさむ / checksum）

- 意味：データが途中で壊れていないかを確かめるための検査値
- ポイント：TCP にも UDP にもある。UDP では IP の送信元・宛先などの「疑似ヘッダー」も計算に入れ、まちがった宛先に届くのを防ぐ（RFC 768）。壊れていることは分かるが、UDP は直さない（再送しない）

## 03-3 ポート番号

### まとめ表

| ポート | プロトコル | トランスポート |
| :-: | :-: | :-: |
| 20・21 | FTP（データ・制御） | TCP |
| 22 | SSH | TCP |
| 23 | Telnet | TCP |
| 25 | SMTP | TCP |
| 53 | DNS | UDP と TCP |
| 67・68 | DHCP（サーバー・クライアント） | UDP |
| 69 | TFTP | UDP |
| 80・443 | HTTP・HTTPS | TCP |
| 123 | NTP | UDP |
| 161・162 | SNMP・SNMP トラップ | UDP |
| 514 | syslog | UDP |

### 番号の範囲

#### ポート番号（ぽーとばんごう / port number）

- 意味：1 台の中で、どのアプリ（サービス）あてかを見分ける 16 ビットの番号（0〜65535）
- ポイント：TCP と UDP はどちらもポート番号を使う。送信元 IP・宛先 IP・プロトコル・送信元ポート・宛先ポートで、1 つの通信が決まる。IP アドレスは「どの機器」、ポート番号は「どのアプリ」
- 例：Web サーバーは TCP 80・443 で待つ

#### ウェルノウンポート（うぇるのうんぽーと / system ports, well-known ports）

- 意味：0〜1023 番。よく使うサービスに割り当てられた番号
- ポイント：RFC 6335 の名前では System Ports。サーバー側が待ち受けに使う。HTTP 80、SSH 22、DNS 53 など
- 例：0〜1023

#### 登録済みポート（とうろくずみぽーと / user ports, registered ports）

- 意味：1024〜49151 番。IANA に登録して使う番号
- ポイント：RFC 6335 の名前では User Ports。ウェルノウンより後ろで、アプリやベンダーが登録する
- 例：1024〜49151

#### ダイナミックポート（だいなみっくぽーと / dynamic ports, ephemeral ports）

- 意味：49152〜65535 番。決まった割り当てがなく、クライアントが一時的に使う番号
- ポイント：RFC 6335 は「Private または Ephemeral Ports」とも呼び、割り当てることはない。PC がサーバーに接続するとき、送信元ポートとしてここから選ぶことが多い
- 例：PC 50123 → サーバー 443

### よく出る組み合わせ

#### TCP を使う主なアプリ（てぃーしーぴーをつかうおもなあぷり / TCP applications）

- 意味：データを欠けなく順番どおり届けたいアプリ。HTTP（80）・HTTPS（443）・SSH（22）・Telnet（23）・FTP（20・21）・SMTP（25）
- ポイント：Telnet の接続は TCP（RFC 854）、SSH は TCP の 22 番で待つ（RFC 4253）、SMTP は 25 番（RFC 5321）。ファイルやページが 1 バイトでも欠けると困るものは TCP
- 例：`ssh admin@10.1.1.1` は TCP 22 へ

#### UDP を使う主なアプリ（ゆーでぃーぴーをつかうおもなあぷり / UDP applications）

- 意味：軽さや速さが大事なアプリ。DHCP（67・68）・TFTP（69）・SNMP（161・162）・syslog（514）・NTP（123）・RTP（音声・動画）
- ポイント：DHCP は UDP で、クライアントからサーバーへは 67、サーバーからクライアントへは 68（RFC 2131）。TFTP は UDP の 69 番に最初の要求を送る（RFC 1350）。FTP（TCP）と TFTP（UDP）の取り違えに注意
- 例：IP 電話の音声は RTP／UDP

#### DNS とポート 53（でぃーえぬえすとぽーと53 / DNS over UDP and TCP）

- 意味：DNS は UDP の 53 番と TCP の 53 番の両方を使う
- ポイント：ふつうの問い合わせは UDP（512 バイト以内。長いと切り詰めて TC ビットを立てる）。ゾーン転送には UDP は使えず TCP を使う（RFC 1035 4.2）。「DNS は UDP だけ」はまちがい
- 例：ゾーン転送（AXFR）は TCP 53

## 03-4 端末の IP 設定

### まとめ表

| 設定 | 役割 | まちがえると |
| :-: | :-: | :-: |
| IP アドレス | 自分の住所 | 重なると片方がつながらない |
| サブネットマスク | どこまでが同じネットワークか | 同じ LAN の相手を外だと思う、またはその逆 |
| デフォルトゲートウェイ | 外へ出る出口のルーター | 同じ LAN の中だけ通じ、外へ出られない |
| DNS サーバー | 名前を IP アドレスに変える | IP では通じるが名前では通じない |

### 4 つの設定

#### IP アドレス（あいぴーあどれす / IP address）

- 意味：ネットワークの中で機器を見分ける番号。IPv4 は 32 ビットを 4 つの 10 進数で書く
- ポイント：DHCP で自動でもらうか、手で入れる（Apple の手順も「Using DHCP」か「Manually」）。詳しい分け方は #04
- 例：192.168.1.23

#### サブネットマスク（さぶねっとますく / subnet mask）

- 意味：IP アドレスのどこまでがネットワークの部分かを表す値
- ポイント：自分と相手が同じネットワークかどうかをこれで判断する。マスクで取り出したネットワークの部分が同じなら直接、違えばゲートウェイへ送る（RFC 1122 3.3.1.1）。詳しい計算は #04
- 例：255.255.255.0（/24）

#### デフォルトゲートウェイ（でふぉるとげーとうぇい / default gateway, router）

- 意味：自分のネットワークの外へ送るときの出口になるルーター（L3 スイッチ）の IP アドレス
- ポイント：自分と同じネットワークの中のアドレスでなければならない。まちがえると同じ LAN の中は通じるが、外へ出られない。Mac の設定画面では「Router（ルーター）」、Linux では `default via`
- 例：192.168.1.1

#### DNS サーバー（でぃーえぬえすさーばー / DNS server, name server）

- 意味：名前（www.example.com）を IP アドレスに変えてくれるサーバー
- ポイント：まちがえると「IP アドレスでは通じるのに、名前では通じない」。Linux は /etc/resolv.conf の `nameserver` 行、Windows は `ipconfig /all`、Mac は Network 設定の DNS で確かめる
- 例：nameserver 192.168.1.53

### 自動でもらう

#### DHCP と手動設定（でぃーえいちしーぴーとしゅどうせってい / DHCP vs static）

- 意味：DHCP はサーバーから IP アドレス・マスク・ゲートウェイ・DNS をまとめて自動でもらうしくみ。手動は自分で入れる
- ポイント：PC はふつう DHCP、サーバーやプリンターは手動（固定）が多い。Windows の `ipconfig /renew` は DHCP のときだけ使える。DHCP のくわしいしくみは #17
- 例：Mac の Configure IPv4 で「Using DHCP」を選ぶ

#### APIPA と 169.254（えーぴっぱ / Automatic Private IP Addressing, IPv4 link-local）

- 意味：DHCP からアドレスをもらえないとき、端末が自分で 169.254.0.0/16 の中のアドレスを付ける動き
- ポイント：169.254/16 は同じリンクの中だけで使うリンクローカルのアドレスで、ルーターの外とは通信できない（RFC 3927）。「169.254 が付いている」＝ DHCP サーバーに届いていない、と考える。Windows の `ipconfig` は、設定が DHCP・APIPA・代替構成のどれで決まったかを見るのに役立つ（Microsoft）
- 例：IPv4 Address 169.254.37.10

## 03-5 OS ごとの確かめ方

### まとめ表

| 見たいもの | Windows | macOS | Linux |
| :-: | :-: | :-: | :-: |
| IP・マスク | `ipconfig` | システム設定 › ネットワーク › 詳細 › TCP/IP | `ip address show` |
| ゲートウェイ | `ipconfig` | 同じ画面の「ルーター」、`netstat -nr` | `ip route show`（default via） |
| DNS サーバー | `ipconfig /all` | 詳細 › DNS | `/etc/resolv.conf` |
| DHCP にする・やり直す | `ipconfig /release`・`/renew` | TCP/IP の画面で Using DHCP | （ディストリビューションによる） |

### Windows

#### ipconfig（あいぴーこんふぃぐ / ipconfig）

- 意味：Windows で IP の設定を見るコマンド。何も付けないと、すべてのアダプターの IPv4・IPv6 アドレス、サブネットマスク、デフォルトゲートウェイを表示する
- ポイント：Linux の `ip`、macOS の設定画面に当たる。DNS サーバーまでは出ないので `/all` を使う
- 例：`ipconfig`

#### ipconfig /all（あいぴーこんふぃぐおーる / ipconfig /all）

- 意味：すべてのアダプターの TCP/IP の設定を、くわしく表示する
- ポイント：Physical Address（MAC アドレス）、DHCP Enabled（DHCP が有効か）、DNS Servers なども表示する（Microsoft Learn の Azure の手順にある出力例）。「DNS サーバーを確かめたい」なら `/all`
- 例：`ipconfig /all`

#### ipconfig /release と /renew（あいぴーこんふぃぐりりーすりにゅー / ipconfig /release, /renew）

- 意味：/release は DHCP サーバーに DHCPRELEASE を送って今のアドレスを手放す。/renew は DHCP の設定をもらい直す
- ポイント：どちらも DHCP（自動）のアダプターで使う。IPv6（DHCPv6）は `/release6`・`/renew6`
- 例：`ipconfig /renew "Local Area Connection"`

#### ipconfig /flushdns（あいぴーこんふぃぐふらっしゅでぃーえぬえす / ipconfig /flushdns）

- 意味：Windows の DNS クライアントのキャッシュを消す
- ポイント：名前解決の古い答え（失敗の記録も含む）が残っているときに使う。中身を見るのは `/displaydns`。IP の設定は変わらない
- 例：`ipconfig /flushdns`

### Linux と macOS

#### ip address show（あいぴーあどれすしょー / ip address show）

- 意味：Linux でインタフェースの IP アドレスを表示するコマンド（`ip addr`、`ip a` と略せる）
- ポイント：プレフィックス長（/24 など）で表示される。`ip address add` でアドレスを付ける。Windows の `ipconfig` に当たる
- 例：`inet 192.168.1.23/24 brd 192.168.1.255 scope global eth0`

#### ip route show（あいぴーるーとしょー / ip route show）

- 意味：Linux のルーティングテーブルを表示するコマンド
- ポイント：「default via 192.168.1.1」の行がデフォルトゲートウェイ。`ip route add default via 192.168.1.1 dev eth0` で設定できる（ip-route(8) の例）
- 例：`default via 192.168.1.1 dev eth0`

#### /etc/resolv.conf（りぞるぶこんふ / resolv.conf）

- 意味：Linux で、名前解決に使う DNS サーバーなどを書く設定ファイル
- ポイント：`nameserver` 行に DNS サーバーの IP アドレスを書く（いくつか書ける。上から順に問い合わせる）。`search` 行は名前の後ろに付けて探すドメイン
- 例：`nameserver 192.168.1.53`

#### macOS のネットワーク設定（まっくのねっとわーくせってい / macOS Network settings）

- 意味：macOS で IP の設定を見る・変える画面。アップルメニュー › システム設定 › ネットワーク › 接続を選んで「詳細」› TCP/IP

#### netstat -nr（ねっとすたっと / netstat）

- ポイント：`-r` でルーティングテーブル、`-n` で名前に変えず数字のまま表示。default の行の行き先がゲートウェイ。Apple は Network Utility の Netstat の説明で、ターミナルの `netstat` を案内している
- 例：`netstat -nr`

### 03-1 TCP のしくみ

#### 問 ccna-03-o01

- 問：TCP のコネクションを始める 3 ウェイハンドシェイクで、やりとりするセグメントのフラグの順番として正しいものはどれか。
- ア：SYN → SYN＋ACK → ACK
- イ：SYN → ACK → FIN
- ウ：ACK → SYN → SYN＋ACK
- エ：FIN → ACK → FIN
- 正解：ア
- 解説：始める側が SYN、受ける側が SYN と ACK、始めた側が ACK を返して、両方が ESTABLISHED になる。
- アの意味：正しい。
- イの意味：FIN は終わるときのフラグで、始めるときには使わない。
- ウの意味：最初に送るのは SYN。
- エの意味：コネクションを終えるときのやりとりに近い。
- 出典：オリジナル問題（根拠：RFC 9293 3.5 図 6（SYN-SENT --> <SEQ=100><CTL=SYN> … <-- <SEQ=300><ACK=101><CTL=SYN,ACK> … --> <SEQ=101><ACK=301><CTL=ACK>））

#### 問 ccna-03-o02

- 問：TCP で、SEQ=1001 から 500 バイトのデータを受け取った受け手が返す確認応答番号はどれか。
- ア：1501
- イ：1500
- ウ：1001
- エ：500
- 正解：ア
- 解説：確認応答番号は「次に受け取りたいバイトの番号」。1001〜1500 を受けたので、次は 1501。
- アの意味：正しい。
- イの意味：受け取った最後のバイトの番号。ACK はその次（＋1）を返す。
- ウの意味：受け取ったデータの最初の番号。
- エの意味：データの長さで、番号ではない。
- 出典：オリジナル問題（根拠：RFC 9293 3.1（Acknowledgment Number: … contains the value of the next sequence number the sender of the segment is expecting to receive／Sequence Number: The sequence number of the first data octet in this segment））

#### 問 ccna-03-o03

- 問：TCP の受け手が、今受け取れるバイト数を送り手に知らせ、送り手がその範囲までまとめて送るしくみはどれか。
- ア：ウィンドウによるフロー制御
- イ：3 ウェイハンドシェイク
- ウ：輻輳制御のスロースタート
- エ：チェックサム
- 正解：ア
- 解説：ウィンドウは受け手が受け取れるデータの量を表す。受け手のバッファーに合わせて送る量を決めるので、フロー制御と呼ぶ。
- アの意味：正しい。
- イの意味：コネクションを始める手順。
- ウの意味：ネットワークの混み具合に合わせて送る量を増減するしくみ。受け手の空きを知らせるものではない。
- エの意味：データが壊れていないかを確かめる値。
- 出典：オリジナル問題（根拠：RFC 9293 3.1（Window: The number of data octets beginning with the one indicated in the acknowledgment field that the sender of this segment is willing to accept）・3.8.6（The window … indicates the range of sequence numbers the sender of the window (the data receiver) is currently prepared to accept））

#### 問 ccna-03-o04

- 問：TCP が信頼性のある通信を実現するしくみの組み合わせとして正しいものはどれか。
- ア：シーケンス番号で抜けを見つけ、チェックサムで壊れを見つけ、再送で直す
- イ：ブロードキャストで全員に送り、いちばん早い答えを使う
- ウ：同じデータを 2 つの経路に同時に送る
- エ：送る前にアプリが暗号化し、受け手が復号する
- 正解：ア
- 解説：TCP の信頼性は、シーケンス番号でパケットの損失を見つけ、セグメントごとのチェックサムで誤りを見つけ、再送で直すことでできている。
- アの意味：正しい。
- イの意味：TCP はユニキャストで、ブロードキャストは使わない。
- ウの意味：TCP のしくみではない。
- エの意味：暗号化は TLS などの役目で、TCP 自体は暗号化しない。
- 出典：オリジナル問題（根拠：RFC 9293 2.2（TCP reliability consists of detecting packet losses (via sequence numbers) and errors (via per-segment checksums), as well as correction via retransmission／TCP supports unicast delivery of data））

#### 問 ccna-03-o05

- 問：TCP のフラグのうち、コネクションをすぐに打ち切るために使うものはどれか。
- ア：RST
- イ：FIN
- ウ：SYN
- エ：PSH
- 正解：ア
- 解説：RST はコネクションをリセットする。ふつうの終わり方は FIN で「もう送るデータはない」と知らせる。
- アの意味：正しい。
- イの意味：送るデータが終わったことを知らせ、片方ずつ閉じていく。
- ウの意味：番号を合わせる、コネクションの始まりのフラグ。
- エの意味：データをためずにアプリへ渡すよう促すフラグ。
- 出典：オリジナル問題（根拠：RFC 9293 3.1（RST: Reset the connection／SYN: Synchronize sequence numbers／FIN: No more data from sender／PSH: Push function））

#### 問 ccna-03-o06

- 問：フロー制御と輻輳制御のちがいの説明として正しいものはどれか。
- ア：フロー制御は受け手の受け取れる量に合わせ、輻輳制御はネットワークの混み具合に合わせて送る量を変える
- イ：フロー制御はネットワークの混み具合に、輻輳制御は受け手の量に合わせる
- ウ：どちらも UDP にあり、TCP にはない
- エ：どちらもコネクションを始めるときだけ働く
- 正解：ア
- 解説：ウィンドウ（フロー制御）は受け手のバッファーに合わせる。輻輳制御（スロースタート・輻輳回避など）は途中の経路が混んでいるかに合わせる。
- アの意味：正しい。
- イの意味：逆。
- ウの意味：逆。UDP にはどちらもない。
- エの意味：データを送っている間ずっと働く。
- 出典：オリジナル問題（根拠：RFC 9293 3.8.6（related to the data buffer space currently available）／RFC 5681（slow start, congestion avoidance, fast retransmit, and fast recovery）／RFC 8085（UDP … provides no inherent congestion control mechanisms））

### 03-2 UDP のしくみ

#### 問 ccna-03-o07

- 問：UDP のヘッダーの大きさと、含まれる欄の組み合わせとして正しいものはどれか。
- ア：8 バイト。送信元ポート・宛先ポート・長さ・チェックサム
- イ：20 バイト。送信元ポート・宛先ポート・シーケンス番号・確認応答番号
- ウ：8 バイト。送信元 IP・宛先 IP・TTL・プロトコル
- エ：4 バイト。宛先ポートだけ
- 正解：ア
- 解説：UDP のヘッダーは 16 ビットの欄が 4 つで 8 バイト。シーケンス番号や確認応答番号はない。
- アの意味：正しい。
- イの意味：TCP のヘッダーの説明（オプションなしで 20 バイト）。
- ウの意味：IP ヘッダーの欄。
- エの意味：送信元ポート・長さ・チェックサムもある。
- 出典：オリジナル問題（根拠：RFC 768 Format（Source Port／Destination Port／Length／Checksum）・Fields（the minimum value of the length is eight）／RFC 9293 3.1（Data Offset … size(Options) == (DOffset-5)*32））

#### 問 ccna-03-o08

- 問：IP 電話の音声を運ぶとき、TCP ではなく UDP を使う理由として最も適切なものはどれか。
- ア：失ったパケットを再送して待つより、遅れずに届くことが大事だから
- イ：UDP は届くことを保証するから
- ウ：UDP は順番を必ずそろえて届けるから
- エ：UDP には輻輳制御があり、混雑を必ず避けられるから
- 正解：ア
- 解説：音声は遅れて届いても使えないので、再送しない軽い UDP を使う。RTP はふつう UDP の上で動く。
- アの意味：正しい。
- イの意味：UDP は届くことを保証しない（ベストエフォート）。
- ウの意味：UDP は順番をそろえない。必要ならアプリ（RTP の番号など）で扱う。
- エの意味：UDP には輻輳制御がない。
- 出典：オリジナル問題（根拠：RFC 3550（Applications typically run RTP on top of UDP to make use of its multiplexing and checksum services）／RFC 8085（UDP does not provide any reliability, e.g., it does not retransmit any lost packets））

#### 問 ccna-03-o09

- 問：UDP の性質として正しいものはどれか。
- ア：端どうしの接続をつくらないので、つなぐ・切る手間がない
- イ：3 ウェイハンドシェイクで接続をつくってから送る
- ウ：重複したデータグラムを必ず取り除く
- エ：ウィンドウで受け手の量に合わせて送る
- 正解：ア
- 解説：UDP はコネクションレスで、接続をつくる・切る手間がなく、覚えておく状態も少ない。重複や順番はアプリが処理する。
- アの意味：正しい。
- イの意味：TCP の動き。
- ウの意味：UDP は重複を防がない。アプリが処理する。
- エの意味：TCP のフロー制御。
- 出典：オリジナル問題（根拠：RFC 8085 1（they do not establish end-to-end connections … UDP communication consequently does not incur connection establishment and teardown overheads）・3.3（UDP also does not protect against datagram duplication））

#### 問 ccna-03-o10

- 問：UDP のチェックサムについて正しいものはどれか。
- ア：IP の送信元・宛先なども含む疑似ヘッダーも計算に入れ、壊れたデータやまちがった宛先を見つける
- イ：壊れたデータを見つけると、自動で再送を頼む

- エ：チェックサムは送る順番を表す番号である
- 正解：ア

- アの意味：正しい。
- イの意味：UDP は再送しない。
- ウの意味：Checksum の欄がある。
- エの意味：順番の番号はシーケンス番号（TCP）。
- 出典：オリジナル問題（根拠：RFC 768（Checksum is the 16-bit one's complement … of a pseudo header of information from the IP header, the UDP header, and the data／This information gives protection against misrouted datagrams））

#### 問 ccna-03-o11

- 問：UDP を使うアプリで、データを確実に順番どおり届けたい。RFC 8085 の考え方として正しいものはどれか。

- アの意味：正しい。
- イの意味：UDP に再送の機能はない。

#### 問 ccna-03-o12
