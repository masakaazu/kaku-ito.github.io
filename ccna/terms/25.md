## 25-1 REST API のしくみ

### まとめ表

| 部品 | 中身 | 例 |
| :-: | :-: | :-: |
| メソッド（動詞） | 何をしたいか | GET・POST・PUT・PATCH・DELETE |
| URI（エンドポイント） | どのリソースに | `https://10.1.1.1/restconf/data/…` |
| ヘッダー | 付け足す情報 | Content-Type・Accept・Authorization・X-Auth-Token |
| ボディ | 送るデータ | JSON や XML |
| ステータスコード（応答） | 結果 | 200・201・401・404 など |

### REST と API

#### API（えーぴーあい / Application Programming Interface）

- 意味：プログラムどうしがやり取りするための決まった窓口。どんな要求を送れば、どんな答えが返るかが決められている
- ポイント：人が画面（GUI）や CLI で操作する代わりに、スクリプトが API を呼んで機器やコントローラーを操作する。#24 のノースバウンド API もその1つ
- 語の意味：Application＝アプリケーション／Programming＝プログラムを作ること／Interface＝つなぎ目

#### REST API（れすとえーぴーあい / REST-based API, RESTful API）

- 意味：HTTP（HTTPS）の上で、URI で示したリソースに、GET・POST などのメソッドで操作を頼む形の API
- ポイント：クライアントが要求を送り、サーバーが応答を返す（クライアントとサーバー）。サーバーは前の要求の状態を覚えておかない（ステートレス）ので、要求ごとに認証の情報などを付ける。Catalyst Center の Intent API や IOS XE の RESTCONF がこの形
- 語の意味：REST＝Representational State Transfer（リソースの表現を、状態の転送としてやり取りする）

#### ステートレス（すてーとれす / stateless）

- 意味：サーバーが、前の要求のやり取りを覚えておかないこと。1つ1つの要求が、それだけで意味が通じるように作られる
- ポイント：Cisco は RESTCONF を「ステートレスなプロトコル」と説明している。そのため、毎回の要求にトークンなどの認証の情報を付ける
- 例：Catalyst Center には、毎回の要求の X-Auth-Token ヘッダーにトークンを付ける

#### URI（ゆーあーるあい / Uniform Resource Identifier, エンドポイント）

- 意味：操作したいリソースの場所を示す文字列。API の世界では、要求を送る先の URI をエンドポイントと呼ぶ
- ポイント：「https://」（方式）、ホスト、パス、「?」のあとのクエリ（条件）でできている。RESTCONF のデータは `/restconf/data/` の下にある
- 例：`https://10.1.1.1/restconf/data/Cisco-IOS-XE-native:native/interface?depth=1`

#### Content-Type と Accept（こんてんとたいぷとあくせぷと / Content-Type and Accept headers）

- 意味：Content-Type は「送るボディのデータ形式」、Accept は「受け取りたい応答の形式」を伝える HTTP のヘッダー
- ポイント：データの形式（エンコード）を決めるのはこれら。RESTCONF では `application/yang-data+json`（JSON）か `application/yang-data+xml`（XML）を使う
- 例：`Accept: application/yang-data+json`

#### RESTCONF（れすとこんふ / RESTCONF）

- 意味：HTTPS の上で、YANG で決めたデータ（機器の設定や状態）を、GET・POST・PUT・PATCH・DELETE で読み書きするプロトコル（RFC 8040）
- ポイント：Cisco の説明では、HTTPS を使うステートレスなプロトコルで、CRUD の操作を行う。データは JSON か XML。IOS XE では `ip http secure-server` と `restconf` で有効にする。NETCONF（SSH の上、XML）と同じデータの考え方
- 例：`GET https://10.1.1.1/restconf/data/Cisco-IOS-XE-native:native/hostname`

## 25-2 CRUD と HTTP の動詞

### まとめ表

| CRUD | HTTP のメソッド | 安全 | べき等 |
| :-: | :-: | :-: | :-: |
| Create（作る） | POST（PUT でも作れる） | × | POST は × |
| Read（読む） | GET | ○ | ○ |
| Update（変える） | PUT（置き換え）・PATCH（一部を変える） | × | PUT は ○、PATCH は決まっていない |
| Delete（消す） | DELETE | × | ○ |

### 操作の種類

#### CRUD（くらっど / Create, Read, Update, Delete）

- 意味：データに対する4つの基本の操作、作る（Create）・読む（Read）・変える（Update）・消す（Delete）の頭文字
- ポイント：REST API ではそれぞれを HTTP のメソッドに当てはめる。Cisco は RESTCONF を「HTTP のメソッドで CRUD の操作を行う」と説明している
- 語の意味：Create＝作る／Read＝読む／Update＝更新する／Delete＝消す

#### GET（げっと / GET）

- 意味：リソースの今の状態を取り出す（読む）メソッド。CRUD の Read
- ポイント：RFC 9110 では「安全な」メソッドで、サーバーの状態を変えない。何度送っても結果は同じ（べき等）
- 例：Catalyst Center から機器の一覧を GET で取る

#### POST（ぽすと / POST）

- 意味：送ったデータを、リソースに決まったやり方で処理させるメソッド。新しいものを作る（Create）のによく使う
- ポイント：べき等ではない。同じ POST を2回送ると、2つ作られることがある。Catalyst Center のトークンを取るのも POST（`/dna/system/api/v1/auth/token`）
- 例：新しい VLAN を POST で作る

#### PUT（ぷっと / PUT）

- 意味：リソースを、送ったデータの内容で作る、またはまるごと置き換えるメソッド
- ポイント：べき等（同じ PUT を何度送っても同じ状態になる）。PATCH が一部だけを変えるのに対し、PUT はまるごと置き換える。RESTCONF の表では「Create or Replace」
- 例：インタフェースの設定を、送った内容にそっくり置き換える

#### PATCH（ぱっち / PATCH）

- 意味：リソースの一部だけを変えるメソッド（RFC 5789）
- ポイント：RESTCONF の表では「Update」。送らなかった部分はそのまま残る。PUT と違い、べき等とは決められていない
- 例：インタフェースの説明（description）だけを変える

#### DELETE（でりーと / DELETE）

- 意味：リソースを消すメソッド。CRUD の Delete
- ポイント：べき等。RFC 9110 では、PUT・DELETE と安全なメソッドがべき等
- 例：使わなくなった VLAN を消す

#### 安全なメソッドとべき等（あんぜんなめそっどとべきとう / safe and idempotent methods）

- 意味：安全＝サーバーの状態を変えない（GET・HEAD・OPTIONS・TRACE）。べき等＝同じ要求を何回送っても、1回送ったのと同じ結果になる（PUT・DELETE と安全なメソッド）
- ポイント：POST はどちらでもない。通信が切れて送り直すとき、べき等なメソッドなら安心して送り直せる
- 例：DELETE を2回送っても、消えた状態は同じ

## 25-3 ステータスコードと認証

### まとめ表

| コード | 意味 | よくある場面 |
| :-: | :-: | :-: |
| 200 OK | 成功 | GET でデータが返った |
| 201 Created | 成功して新しく作られた | POST で作った |
| 204 No Content | 成功、返す中身なし | DELETE・PUT のあと |
| 400 Bad Request | 要求の書き方がおかしい | JSON の文法の誤り |
| 401 Unauthorized | 認証の情報がない・正しくない | トークンの期限切れ |
| 403 Forbidden | 分かったが、断る（権限がない） | 読むだけの権限で変えようとした |
| 404 Not Found | リソースが見つからない | URI の打ち間違い |
| 500 Internal Server Error | サーバーの中で思わぬ問題 | サーバー側の不具合 |

| 認証のしかた | 送るもの | 例 |
| :-: | :-: | :-: |
| Basic 認証 | ユーザー名:パスワード を Base64 にしたもの | Catalyst Center のトークン取得 |
| トークン（Bearer など） | 先にもらったトークン | Catalyst Center の X-Auth-Token |
| API キー | 前もって発行した鍵 | Meraki の API キー |
| OAuth 2.0 | 持ち主が許可した、範囲の決まった権限 | Meraki のアプリの連携 |

### ステータスコード

#### ステータスコード（すてーたすこーど / HTTP status code）

- 意味：サーバーが応答の最初に付ける3けたの番号。1けた目で種類が分かる
- ポイント：1xx＝情報、2xx＝成功、3xx＝リダイレクト（別の場所へ）、4xx＝クライアントの誤り、5xx＝サーバーの誤り
- 例：`HTTP/1.1 200 OK`

#### 2xx（成功）（にーえっくすえっくす / 2xx Successful）

- 意味：要求がうまく受け取られ、理解され、受け入れられたことを示すコード
- ポイント：200 OK＝成功。201 Created＝成功して新しいリソースができた。204 No Content＝成功したが、返す中身がない
- 例：POST で VLAN を作ると 201

#### 401 と 403（よんまるいちとよんまるさん / 401 Unauthorized and 403 Forbidden）

- 意味：401＝正しい認証の情報がないので、要求を実行しなかった。403＝サーバーは要求を分かったが、実行を断った
- ポイント：401 は「誰か分からない（ログインし直して）」、403 は「誰かは分かるが、その権限がない」。Catalyst Center のトークンの期限が切れると 401 が返る
- 例：トークンを付け忘れて 401／読み取り専用のユーザーで DELETE して 403

#### 404 と 500（よんまるよんとごひゃく / 404 Not Found and 500 Internal Server Error）

- 意味：404＝その URI のリソースが見つからない。500＝サーバーの中で思わぬことが起きて、要求を果たせなかった
- ポイント：4xx はクライアント（要求を送った側）の誤り、5xx はサーバー側の誤り。400 Bad Request は要求の書き方そのものがおかしいとき
- 例：URI の打ち間違いで 404

### 認証

#### Basic 認証（べーしっくにんしょう / Basic authentication）

- 意味：ユーザー名とパスワードを「ユーザー名:パスワード」の形でつなぎ、Base64 で変換して Authorization ヘッダーで送る認証（RFC 7617）
- ポイント：Base64 はただの変換で暗号化ではないので、TLS（HTTPS）と組み合わせないと安全ではない。Catalyst Center では、Basic 認証で POST してトークンをもらう
- 例：`Authorization: Basic YWRtaW46…`

#### トークン認証（とーくんにんしょう / token-based authentication, bearer token）

- 意味：最初に一度だけ認証してトークン（長い文字列）をもらい、その後の要求にはトークンを付ける認証
- ポイント：パスワードを毎回送らなくてよい。Catalyst Center のトークンは X-Auth-Token ヘッダーに付け、寿命は 60 分。Bearer トークン（RFC 6750）は、持っている人なら誰でも使えるので、盗まれないように守る
- 例：`X-Auth-Token: eyJ0eXAiOi…`／`Authorization: Bearer mF_9.B5f-4.1JqM`

#### API キー（えーぴーあいきー / API key）

- 意味：API を使うために前もって発行してもらう、パスワードのような鍵の文字列
- ポイント：Meraki のダッシュボード API では、API キーは持ち主の管理者の権限で動き、Authorization ヘッダーに `Bearer` のあとに付けて送る。パスワードと同じように扱い、プログラムのソースに書かない
- 例：環境変数 MERAKI_DASHBOARD_API_KEY に入れておく

#### OAuth 2.0（おーおーす / OAuth 2.0）

- 意味：持ち主（利用者）の許可を得て、ほかのアプリケーションに、範囲を限った権限（アクセストークン）を渡すしくみ（RFC 6749）
- ポイント：アプリにパスワードそのものを渡さずにすむ。Meraki では、ほかの会社のアプリや組織全体の自動化で OAuth を使い、権限の範囲（スコープ）を決める
- 例：外部の管理アプリに、読み取りだけの権限を許可する

## 25-4 構成管理（Ansible と Terraform）

### まとめ表

| 項目 | Ansible | Terraform |
| :-: | :-: | :-: |
| 種類 | オープンソースの自動化ツール（Python で書かれている） | HashiCorp の IaC ツール |
| 書く言葉 | YAML（プレイブック） | HCL（Terraform の言語） |
| 書き方 | 望む状態を書いたタスクを順に実行 | 宣言型（できあがりの状態だけを書く） |
| 機器への入り方 | エージェントなし。SSH（ネットワーク機器は CLI over SSH・NETCONF・HTTPS の API） | プロバイダーが各サービスの API を呼ぶ |
| 今の状態の記録 | 持たない（毎回、機器を見て判断） | ステートファイルに記録 |
| よくある使い方 | 機器の設定の管理・変更 | クラウドなどの資源を作る（プロビジョニング） |

### 構成管理

#### 構成管理ツール（こうせいかんりつーる / configuration management tool）

- 意味：機器やサーバーの設定を、コード（ファイル）で書いて管理し、そのとおりの状態にそろえるツール
- ポイント：設定をファイルにするので、バージョン管理・使い回し・共有ができる。手作業のミスとばらつきを減らす（#24）。CCNA では Ansible と Terraform を見分けられればよい
- 例：100 台のスイッチの NTP の設定を、1つのプレイブックで入れる

#### IaC（あいえーしー / Infrastructure as Code）

- 意味：ネットワークやサーバーなどの基盤（インフラ）を、人が読めるコードで定義して作り・管理する考え方
- ポイント：HashiCorp は Terraform を「IaC のツール」と説明している。コードなので、同じものを何度でも同じように作れる
- 語の意味：Infrastructure＝基盤／as Code＝コードとして

#### べき等性（構成管理）（べきとうせい / idempotence）

- 意味：同じ処理を何度実行しても、結果が同じになる性質
- ポイント：Ansible は、機器がすでにプレイブックどおりの状態なら、何回実行しても何も変えない。Terraform も、変える必要がなければ plan で「変更なし」と出る
- 例：VLAN 10 がすでにあれば、もう一度実行しても作り直さない

### Ansible

#### Ansible（あんしぶる / Ansible）

- 意味：プレイブックに望む状態を書き、機器やサーバーをその状態にそろえるオープンソースの自動化ツール
- ポイント：エージェントがいらない（管理される側にソフトを入れない）。Python で書かれ、SSH で入る。ネットワーク機器の設定の管理によく使う
- 例：`ansible-playbook -i hosts vlan.yml`

#### エージェントレス（えーじぇんとれす / agentless）

- 意味：管理される機器に、専用のソフト（エージェント）を入れずに管理できること
- ポイント：Ansible の設計の柱の1つ。ネットワーク機器のモジュールは、機器の上ではなくコントロールノードで動き、CLI over SSH・XML over SSH（NETCONF）・API over HTTPS で機器と話す。最も多いのは CLI over SSH
- 例：スイッチには何も入れず、SSH でログインできれば管理できる

#### コントロールノードと管理対象ノード（こんとろーるのーどとかんりたいしょうのーど / control node and managed nodes）

- 意味：コントロールノード＝Ansible をインストールして、コマンドを実行するコンピューター。管理対象ノード＝Ansible で管理する機器（ホスト）
- ポイント：Ansible はふつう管理対象ノードには入れない。ノートパソコンやサーバーをコントロールノードにできる
- 例：管理者の Linux サーバー（コントロールノード）から、50 台のスイッチ（管理対象ノード）を設定する

#### インベントリ（いんべんとり / inventory）

- 意味：Ansible で管理する機器（管理対象ノード）の一覧。IP アドレスなどの情報や、グループ分けを書く
- ポイント：グループを作ると、プレイでまとめて選んだり、まとめて変数を決めたりできる
- 例：`[switches]` の下に sw1・sw2 を並べる

#### プレイブック（ぷれいぶっく / playbook）

- 意味：Ansible で行う作業を書いたファイル。YAML で書き、どの機器（hosts）にどのタスクを順に行うか（プレイ）を並べる
- ポイント：YAML は人が読み書きしやすい形式。プレイの中のタスクは、書いた順に実行される。1つのタスクで1つのモジュールを呼ぶ
- 例：`- name: VLAN を作る` の下に、モジュールとその値を書く

#### モジュール（もじゅーる / module）

- 意味：Ansible のタスクで実際の仕事をする部品。用途ごとに決まっている
- ポイント：ネットワーク用のモジュールには、機器の種類ごとの VLAN やインタフェースを扱うものがある。ネットワーク機器のモジュールはコントロールノードで動く
- 例：Cisco IOS のコマンドを流すモジュール、VLAN を設定するモジュール

### Terraform

#### Terraform（てらふぉーむ / Terraform）

- 意味：HashiCorp の IaC のツール。クラウドやオンプレミスの資源を、人が読める構成ファイルで定義して、作り・変え・管理する
- ポイント：構成ファイルは宣言型で、できあがりの状態だけを書く。各サービスの API をプロバイダー経由で呼んで資源を作る。Write（書く）→ Plan（計画）→ Apply（適用）の流れ
- 例：クラウドに仮想ネットワークとセキュリティグループを作る

#### HCL と宣言型（えいちしーえるとせんげんがた / HashiCorp Configuration Language, declarative）

- 意味：HCL は Terraform の構成ファイルの言語。宣言型は「どうやって作るか」の手順ではなく「どうなっていてほしいか」のゴールを書くやり方
- ポイント：Terraform はブロックの依存関係を自分で調べ、正しい順番で作る（並べた順ではない）。手続き型（手順を順に書く）と比べて覚える
- 例：`resource "aws_vpc" "main" { cidr_block = "10.0.0.0/16" }`

#### プロバイダー（ぷろばいだー / provider）

- 意味：Terraform が、クラウドやほかのサービスの API とやり取りするためのプラグイン
- ポイント：すべての資源の種類はプロバイダーで作られている。API のあるサービスなら、プロバイダーでほぼ何でも扱える。Terraform 本体とは別に配られる
- 例：AWS・Azure・Google Cloud のプロバイダー

#### plan と apply（ぷらんとあぷらい / terraform plan and terraform apply）

- 意味：plan＝今の状態と構成ファイルを比べて、何を作る・変える・消すかの実行計画を見せる。apply＝計画を承認すると、実際に変更する
- ポイント：plan だけでは何も変わらない。変える前に、思ったとおりの変更かを確かめられる
- 例：plan で「VM を 2 台足す」と出たのを見てから apply する

#### ステートファイル（すてーとふぁいる / state file）

- 意味：Terraform が、自分の作った実際の資源と構成ファイルの対応を記録しておくファイル
- ポイント：HashiCorp は、ステートを環境の「正しい情報のもと（source of truth）」と説明している。Terraform はこれを見て、何を変えればよいかを決める。Ansible にはこれにあたるものがない
- 例：terraform.tfstate

## 25-5 JSON

### まとめ表

| 種類 | 書き方 | 例 |
| :-: | :-: | :-: |
| オブジェクト | `{ }` の中に「名前: 値」を , で並べる | `{"vlan": 10}` |
| 配列 | `[ ]` の中に値を , で並べる | `[10, 20, 30]` |
| 文字列 | ダブルクォート `" "` で囲む | `"Gi1/0/1"` |
| 数値 | そのまま（引用符なし） | `10`・`1.5` |
| 真偽値 | 小文字の true・false | `true` |
| null | 小文字の null（値がない） | `null` |

### JSON の部品

#### JSON（じぇいそん / JavaScript Object Notation）

- 意味：データをテキストで表す、軽くて言語に依らない形式（RFC 8259）。REST API のやり取りでよく使う
- ポイント：4つの基本の型（文字列・数値・真偽値・null）と、2つの組み立てる型（オブジェクト・配列）でできている。空白や改行は、読みやすくするためで意味はない
- 語の意味：JavaScript＝プログラミング言語の名前／Object＝もの（データのまとまり）／Notation＝書き表し方

#### オブジェクト（おぶじぇくと / object）

- 意味：`{ }`（波かっこ）で囲んだ、「名前: 値」の組（名前と値のペア）の集まり。順番に意味はない
- ポイント：名前は必ず文字列（ダブルクォートで囲む）。名前と値の間は `:`（コロン）、組と組の間は `,`（コンマ）。1つのオブジェクトの中の名前は重ならないようにする
- 例：`{"name": "Gi1/0/1", "enabled": true}`

#### 配列（はいれつ / array）

- 意味：`[ ]`（角かっこ）で囲んだ、値を順に並べたもの。順番に意味がある
- ポイント：値と値の間は `,`。中にはオブジェクトや配列も入れられる。最後の値のあとに `,` を付けない
- 例：`"vlans": [10, 20, 30]`

#### 名前と値（なまえとあたい / name/value pair, key/value pair）

- 意味：オブジェクトの中の1つの組。名前（キーとも呼ぶ）と、その値
- ポイント：値には、文字列・数値・真偽値・null・オブジェクト・配列のどれでも入る。オブジェクトの中にオブジェクトを入れて、階層にできる
- 例：`"vlan": 10` の名前は vlan、値は 10（数値）

#### JSON の値の型（じぇいそんのあたいのかた / JSON value types）

- 意味：文字列（`" "` で囲む）・数値（引用符なし）・真偽値（true か false）・null（値がない）
- ポイント：true・false・null は小文字だけ（True や NULL は誤り）。`"10"` は文字列で、`10` は数値。数値の頭に余計な 0 は付けない
- 例：`"mtu": 1500`（数値）、`"mtu": "1500"`（文字列）

#### データの形式（でーたのけいしき / data encoding formats: JSON, XML, YAML）

- 意味：API や自動化で使う、データをテキストで書き表す形式。JSON・XML・YAML が代表
- ポイント：JSON は `{ }` と `[ ]`、XML は `<タグ>` で囲む、YAML は字下げで階層を表す（Ansible のプレイブック）。RESTCONF は JSON と XML、NETCONF は XML を使う
- 例：`<vlan>10</vlan>`（XML）、`vlan: 10`（YAML）、`"vlan": 10`（JSON）

### 25-2 CRUD と HTTP の動詞

#### 問 ccna-25-o07

- 問：CRUD の Read にあたる HTTP のメソッドはどれか。
- ア：POST
- イ：GET
- ウ：PATCH
- エ：DELETE
- 正解：イ
- 解説：読む（Read）は GET。作る（Create）は POST、変える（Update）は PUT・PATCH、消す（Delete）は DELETE。
- アの意味：Create によく使う。
- イの意味：正しい。
- ウの意味：Update（一部を変える）。
- エの意味：Delete。
- 出典：オリジナル問題（根拠：Cisco IOS XE 17.9 Programmability CG「RESTCONF Protocol」（GET Read／PATCH Update／PUT Create or Replace／POST Create or Operations／DELETE Deletes the targeted resource））

#### 問 ccna-25-o08

- 問：インタフェースの説明（description）だけを変え、ほかの設定はそのまま残したい。RESTCONF で使うのに最も合うメソッドはどれか。
- ア：PUT
- イ：GET
- ウ：PATCH
- エ：DELETE
- 正解：ウ
- 解説：PATCH は送った部分だけを変える（Update）。PUT はまるごと置き換える。
- アの意味：送った内容で置き換えるので、送らなかった部分が消えることがある。
- イの意味：読むだけ。
- ウの意味：正しい。
- エの意味：消す。
- 出典：オリジナル問題（根拠：RFC 5789 2.（The PATCH method requests that a set of changes described in the request entity be applied to the resource）／RFC 9110 9.3.4（The PUT method requests that the state of the target resource be created or replaced））

#### 問 ccna-25-o09

- 問：RFC 9110 で、べき等（同じ要求を何回送っても1回と同じ結果）とされているメソッドの組み合わせはどれか。

- イ：POST・PUT・DELETE
- ウ：GET・POST・PATCH
- エ：POST だけ
- 正解：ア
- 解説：RFC 9110 では、PUT・DELETE と安全なメソッド（GET・HEAD・OPTIONS・TRACE）がべき等。POST はべき等ではない。
- アの意味：正しい。
- イの意味：POST がべき等ではない。
- ウの意味：POST と PATCH はべき等とは決められていない。
- エの意味：逆。
- 出典：オリジナル問題（根拠：RFC 9110 9.2.2（Of the request methods defined by this specification, PUT, DELETE, and safe request methods are idempotent）／9.2.1（the GET, HEAD, OPTIONS, and TRACE methods are defined to be safe））

#### 問 ccna-25-o10

- 問：サーバーの状態を変えない「安全な」メソッドはどれか。
- ア：GET
- イ：POST
- ウ：PUT
- エ：DELETE
- 正解：ア
- 解説：GET・HEAD・OPTIONS・TRACE が安全なメソッド。読むだけで状態を変えない。
- アの意味：正しい。
- イの意味：データを処理させ、新しいものを作ることが多い。
- ウの意味：作る・置き換える。
- エの意味：消す。
- 出典：オリジナル問題（根拠：RFC 9110 9.2.1（the GET, HEAD, OPTIONS, and TRACE methods are defined to be safe））

#### 問 ccna-25-o11

- 問：同じ POST の要求を、通信が切れたと思って2回送ってしまった。起こりうることとして正しいものはどれか。
- ア：POST はべき等なので、必ず1つだけ作られる
- イ：POST はべき等ではないので、同じものが2つ作られることがある

### 25-3 ステータスコードと認証

### 25-5 JSON

#### 問 ccna-25-o25

- 問：次の JSON で、"vlans" の値の種類はどれか。
```
{
  "hostname": "SW1",
  "vlans": [10, 20, 30],
  "stp": {"mode": "rapid-pvst"}
}
```
- ア：オブジェクト
- イ：配列
- ウ：文字列
- エ：数値
- 正解：イ
- 解説：`[ ]` で囲んで値を並べたものは配列。"stp" の値は `{ }` なのでオブジェクト。
- アの意味："stp" の値の種類。
- イの意味：正しい。
- ウの意味："hostname" の値の種類。
- エの意味：配列の中の 10・20・30 は数値だが、"vlans" の値そのものは配列。
- 出典：オリジナル問題（根拠：RFC 8259 1.・5.（An array is an ordered sequence of zero or more values／begin-array = ws %x5B ws ; [ left square bracket））

#### 問 ccna-25-o26

- 問：次の JSON に含まれるオブジェクトはいくつか。
```
{
  "interface": {
    "name": "GigabitEthernet1/0/1",
    "ipv4": {"address": "10.1.1.1", "mask": "255.255.255.0"}
  }
}
```
- ア：1 個
- イ：2 個
- ウ：4 個
- エ：3 個
- 正解：エ
- 解説：`{ }` の組が3つある。いちばん外側、"interface" の値、"ipv4" の値。
- アの意味：外側しか数えていない。
- イの意味："ipv4" の値を見落としている。
- ウの意味：数えすぎ。名前と値の組（"name" など）はオブジェクトではない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：RFC 8259 4.（An object structure is represented as a pair of curly brackets surrounding zero or more name/value pairs））

#### 問 ccna-25-o27

- イ："TRUE"
- ウ：yes
- エ：true
- 正解：エ
- 解説：真偽値は小文字の true か false だけ。ダブルクォートで囲むと文字列になる。
- アの意味：大文字が入っているので誤り。
- イの意味：ダブルクォートで囲んでいるので文字列。
- ウの意味：JSON の真偽値ではない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：RFC 8259 3.（false null true … The literal names MUST be lowercase. No other literal names are allowed））

#### 問 ccna-25-o28

- 問：次の JSON は文法が誤っている。誤りの箇所として正しいものはどれか。

```
{

```

- ウ：オブジェクトを `{ }` で囲んでいる
