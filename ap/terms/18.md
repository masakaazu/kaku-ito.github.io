# システム企画 用語集（157語）

- 出典の用語リスト：[応用情報技術者試験.com #18 システム企画](https://www.ap-siken.com/keyword/18/)
- 解説は各用語ページを参照しつつ、試験向けに要点を言い換えてまとめたもの
- サイトの解説には誤りや一般論にとどまるものがあったため、その箇所は試験で使われる定義で書いている（⚠印）
- 問題演習：IPA 午前の過去問（令和3年度春期〜令和7年度秋期の10回分）から、この分野の問題25問（同じ問題を除く）を原文のまま入れ、ア〜エそれぞれの意味を解説した（2026-11-14）。小分類はシラバス Ver.7.2 の小分類名（18-1〜18-3）で分けた

## 1. システム化計画（59語）

### 1-1 システム化構想の立案

| 用語 | 英語 | 解説 |
| :-: | :-: | :-: |
| 経営課題 | Management Issues | 企業が成長・効率化のために解決すべき問題（顧客満足度の低下、人材不足など）。システム化構想の出発点 |
| 経営要求 | Management Requirements | 経営層が業務やシステムに求めること（コスト削減、業務効率向上など）。システム化構想はこれに沿って立てる |
| 事業環境 | Business Environment | 企業を取り巻く外部状況（市場動向、競合、法規制、技術、社会変化）。構想立案時に分析する |
| 業務環境 | Business Environment | 業務を行ううえでの内外の条件（組織、資源、顧客ニーズなど）。強み・弱みの把握に使う |
| 情報技術動向 | IT Trends | 最新技術とその変化の傾向。自社に適用できる技術を見極めるために調査する |
| 業務分析 | Business Analysis | 現在の業務プロセスを把握し、非効率な箇所や改善点を見つける活動 |
| 業務フロー | Business Flow | 業務の手順・流れを図で表したもの。部署間のやり取りや役割を可視化する |
| システム最適化手法 | System Optimization Method | 個別最適ではなく組織全体として最適になるようシステムを整理・改善する手法（例：EA） |
| システム化構想書 | System Concept Document | 経営課題の解決に向けて、システム化の目的・対象範囲・効果・概算費用などをまとめた文書。経営層の承認を得るためのもの |
| システム化推進体制 | System Promotion Structure | システム化を進めるための組織体制（経営層・利用部門・情報システム部門の役割分担） |
| BABOK | Business Analysis Body of Knowledge | IIBAが発行するビジネスアナリシスの知識体系ガイド。要求の引き出し・分析・管理の手法をまとめたもの |
| BPR | Business Process Reengineering | 業務プロセスを根本から見直し、抜本的に再設計すること。部分改善（業務改善）ではなく「ゼロから作り直す」点がポイント |
| SoR | System of Record | 正確な記録を目的とする基幹系システム（会計、販売管理など）。安定性・信頼性重視 |
| SoE | System of Engagement | 顧客や利用者とのつながりを目的とするシステム（SNS、ECアプリなど）。変化への対応スピード重視 |
| SoI | System of Insight | SoR・SoEのデータを分析して洞察を得るシステム（BI、データ分析基盤など） |
| Fit to Standard | Fit to Standard | パッケージやSaaSの標準機能に業務を合わせる導入方針。カスタマイズを最小限にする。対になるのが「Fit & Gap（ギャップをカスタマイズで埋める）」 |
| OOTB | Out Of The Box | 製品を買ってすぐ、カスタマイズなしで使える状態・標準機能のこと |

### 1-2 システム化計画の立案

| 用語 | 英語 | 解説 |
| :-: | :-: | :-: |
| 全体システム化計画 | Overall Systemization Plan | 組織全体の情報システムをどう整備するかの中長期計画。個別計画の上位にあたり、優先順位や全体最適を決める |
| 個別システム化計画 | Individual Systemization Plan | 全体計画に基づき、個々のシステム（案件）ごとに目的・範囲・スケジュール・費用などを定めた計画 |
| システム化計画の基本要件 | Basic Requirements | システム化計画に盛り込むべき基本事項（目的、対象範囲、スケジュール、費用、体制など） |
| システム化の目的 | Objectives of Systematization | 何のためにシステム化するか。経営課題の解決など、計画全体の判断基準になる |
| 開発範囲 | Development Scope | 実際に開発する機能・成果物の範囲。適用範囲のうち、新たに作る部分 |
| システム適用範囲 | System Scope | システムが対象とする業務・部署・データの範囲 |
| 関連する情報技術の調査 | IT Research | システム化に使える技術・製品を調査し、適切な技術を選ぶための活動 |
| 業務モデルの作成 | Business Model Creation | 対象業務をモデル（業務フロー、DFD、E-R図など）で表し、システム化する業務を明確にすること |
| システム化機能の整理 | Organizing System Functions | 業務モデルをもとに、システムで実現する機能を洗い出し整理すること |
| システム方式の策定 | System Architecture Policy | ハードウェア・ソフトウェア・ネットワーク構成など、システムの基本的な実現方式を決めること |
| サービスレベルと品質に対する基本方針 | Service Level and Quality Policy | 稼働率・応答時間などのサービスレベルや品質目標の方針を決めること（後のSLAにつながる） |
| プロジェクト推進体制 | Project Structure | プロジェクトを進めるための組織と役割分担（オーナー、PM、利用部門など） |
| プロジェクトオーナー | Project Owner | プロジェクトの最終責任者。予算や大きな意思決定の権限を持つ（通常は経営層や利用部門の責任者） |
| サブシステム分割 | Subsystem Division | 大きなシステムを、機能や業務単位の小さなサブシステムに分けること。開発・管理しやすくする |
| 優先順位付け | Prioritization | 投資効果・緊急度などから、開発するシステムや機能の順番を決めること |
| 要員 | Personnel | プロジェクトに必要な人員（人数・スキル）。計画段階で確保方針を決める |
| 納期 | Delivery Date | 成果物を引き渡す期限 |
| 費用 | Cost | 開発・運用にかかるコスト。計画段階で概算する |
| 品質 | Quality | システムが要求を満たしている度合い。納期・費用と合わせてQCDと呼ばれる |
| クリティカルパス | Critical Path | 作業工程の中で余裕（フロート）がゼロの経路。この経路の作業が遅れると全体が遅れる。アローダイアグラムの計算問題で頻出 |

### 1-3 要員教育計画

| 用語 | 英語 | 解説 |
| :-: | :-: | :-: |
| 教育・訓練の基本要件 | Basic Requirements for Training | 教育を行うために決めるべき事項（目的、対象者、内容、方法、スケジュール、体制） |
| 教育訓練体制 | Training Structure | 教育を誰が企画・実施・評価するかの体制 |
| スケジュール | Schedule | 教育・訓練をいつ実施するかの計画。システム稼働前に利用者教育を終えるよう組む |
| 対象者 | Target Person | 教育を受ける人（利用者、運用担当者、管理者など）。対象者ごとに内容を変える |

### 1-4 投資効果・費用の算定

| 用語 | 英語 | 解説 |
| :-: | :-: | :-: |
| PBP ⚠ | Pay Back Period | **回収期間法**。投資額を、毎年の利益（キャッシュフロー）で何年で回収できるかで評価する。短いほど良い。計算が簡単だが、お金の時間価値を考慮しない（サイトの「Portfolio-Based Planning」は誤り） |
| DCF法 | Discounted Cash Flow | 将来のキャッシュフローを割引率で現在価値に直して評価する方法。「今の100万円＞1年後の100万円」という時間価値を考慮する |
| NPV | Net Present Value | 正味現在価値。将来キャッシュフローの現在価値の合計から初期投資額を引いた値。**NPV＞0なら投資する価値あり**。DCF法の代表的な指標 |
| 工数の概算見積り | Effort Estimation | 開発に必要な作業量（人月など）をおおまかに見積もること。FP法、類推法などを使う |
| 開発効果の算定 | Calculating Benefits | システム化によって得られる効果（コスト削減、売上増など）を金額などで見積もること。定量効果と定性効果がある |
| 概算費用の算出 | Rough Cost Estimation | 開発費・運用費・保守費などを概算すること。投資判断の材料になる |
| ITポートフォリオ | IT Portfolio | IT投資をリスクとリターン、目的別（戦略・業務効率化・インフラなど）に分類し、投資配分を最適化する考え方 |
| 投資回収期間 | Payback Period | 投資額を回収するのにかかる期間。PBPで求める |
| システムライフサイクル | System Life Cycle | 企画→要件定義→開発→運用・保守→廃棄までの一生。費用はライフサイクル全体（TCO）で考える |

### 1-5 リスク分析

| 用語 | 英語 | 解説 |
| :-: | :-: | :-: |
| リスク分析の対象 | Risk Analysis Targets | 分析すべき対象（情報資産、業務、プロジェクトなど）を特定すること |
| リスクの発生頻度・影響・範囲 | Frequency, Impact, Scope | リスクを「どれくらい起きるか」「起きたらどれだけ大きいか」「どこまで及ぶか」で評価すること |
| リスクの種類に応じた損害内容と損害額 | Damage by Risk Type | リスクの種類ごとに、どんな損害がいくら発生するかを見積もること |
| リスク対応 | Risk Response | リスクへの対策。**回避・低減（軽減）・移転（転嫁）・受容（保有）**の4つが基本。保険加入は「移転」 |
| 財産損失 | Property Loss | 建物・設備・データなど、資産そのものが失われる・壊れる損失 |
| 賠償責任損失 | Liability Loss | 他者に損害を与え、損害賠償責任を負うことによる損失（情報漏えいによる賠償など） |
| 純収益損失 | Net Income Loss | 事故によって事業が止まるなどして、本来得られた利益が得られなくなる損失（営業停止中の逸失利益など） |
| 人的損失 | Human Loss | 従業員や経営者の死亡・けが・退職などで生じる損失 |
| リスク測定 | Risk Measurement | リスクの大きさを発生確率×影響度などで定量・定性的に評価すること |

損失の4分類（財産・賠償責任・純収益・人的）はセットで覚える。

## 2. 要件定義（43語）

### 2-1 要求分析の手順・手法

| 用語 | 英語 | 解説 |
| :-: | :-: | :-: |
| ユーザーニーズ調査 | User Needs Survey | 利用者が何を求めているかを、インタビューやアンケートで調べること |
| 現状分析 | Current State Analysis | 現在の業務やシステムの状態を調べ、問題点を洗い出すこと |
| 課題定義 | Problem Definition | 現状分析で出た問題から、解決すべき課題を明確にすること |
| 要求仕様書 | Requirements Specification | 利用者の要求をまとめ、システムに求める機能・性能などを記述した文書。開発の基準になる |
| 現状指向型アプローチ | Current-State-Oriented Approach | 現状の業務を分析し、その問題点を改善する形で要求をまとめる方法。現実的だが抜本的な改革になりにくい |
| 目的指向型アプローチ | Goal-Oriented Approach | あるべき姿（目的）から考えて要求を導く方法。現状にとらわれず改革しやすい |
| 要求工学 | Requirements Engineering | 要求の獲得・分析・仕様化・検証・管理を体系的に行う工学的手法 |
| アンケート | Questionnaire | 多数の人から効率よく意見を集める調査方法。定量的に集計しやすいが、深掘りはしにくい |
| インタビュー | Interview | 対象者に直接質問して要求を聞き出す方法。深く聞けるが手間がかかる |
| 親和図 | Affinity Diagram | 多数の意見・情報をカードに書き、内容の近いものをグループ化して整理する図（KJ法）。新QC七つ道具の一つ |
| 機能分析 | Functional Analysis | システムに必要な機能を洗い出し、階層的に分解・整理する分析 |
| 構造分析 | Structural Analysis | 対象を構成要素とその関係に分解して分析すること（構造化分析） |
| データフローモデル | Data Flow Model | データの流れと処理の関係で業務・システムを表すモデル。DFDで表現する |
| ペトリネットモデル | Petri Net Model | プレース（○）・トランジション（｜）・トークン（●）で、並行処理や同期のふるまいを表すモデル |
| E-Rモデル | Entity-Relationship Model | 実体（エンティティ）と関連（リレーションシップ）でデータ構造を表すモデル。DB設計の基本 |
| 並列プロセスモデル ⚠ | Parallel Process Model | 複数のプロセスが並行して動き、互いに通信・同期する様子を表すモデル（ペトリネットなどで表現） |
| ゴール指向要求分析 | Goal-Oriented Requirements Analysis | 最終目標（ゴール）をサブゴールへ段階的に分解し、要求を導き出す分析手法（KAOS、i*など） |
| BABOK ⚠重複 | Business Analysis Body of Knowledge | ビジネスアナリシスの知識体系（1-1参照）。要求分析の手法の参考になる |

### 2-2 要件定義の種類

| 用語 | 英語 | 解説 |
| :-: | :-: | :-: |
| 業務要件定義 | Business Requirements Definition | システム化する業務の内容・流れ・ルールを明確にすること。「業務として何をしたいか」 |
| 業務処理手順 | Business Procedure | 業務を行うための具体的な手順・ルール |
| 機能要件定義 | Functional Requirements Definition | システムが持つべき機能（何ができるか）を定義すること。例：受注入力、帳票出力 |
| 非機能要件定義 | Non-Functional Requirements Definition | 機能以外の要件（性能、信頼性、セキュリティ、運用性、移行性など）を定義すること。IPAの「非機能要求グレード」が有名 |
| 性能要件 | Performance Requirements | 応答時間、処理件数（スループット）、同時接続数など |
| セキュリティ要件 | Security Requirements | アクセス制御、認証、暗号化、ログ取得など |
| 周辺インタフェース要件 | Interface Requirements | 他システムや外部機器との接続方法・データ形式など |
| 情報・データ要件 | Data Requirements | 扱うデータの項目、量、保存期間など |
| 運用要件 | Operational Requirements | 稼働時間、バックアップ、監視、障害時対応など運用に関する要件 |
| 移行要件 | Migration Requirements | 旧システムからのデータ移行、切替方法・時期など |
| 保守要件 | Maintenance Requirements | 修正・改善のしやすさ、保守体制など |

### 2-3 要件の表現手法

| 用語 | 英語 | 解説 |
| :-: | :-: | :-: |
| プロセス仕様 | Process Specification | DFDの各プロセスの処理内容を具体的に記述したもの（構造化言語、デシジョンテーブルなどで書く）。ミニスペックとも |
| DFD | Data Flow Diagram | データの流れを「外部実体（□）・プロセス（○）・データストア（＝）・データフロー（→）」の4記号で表す図。**制御の流れ（順序・分岐）は表さない**点が頻出 |
| DD | Data Dictionary | データディクショナリ。DFDに出てくるデータの意味・構成・形式を定義した辞書 |
| デシジョンテーブル | Decision Table | 条件の組み合わせと、それに対する動作を表形式でまとめたもの。条件の漏れ防止やテストケース作成に使う |
| デシジョンツリー | Decision Tree | 条件分岐や選択肢を木の形で表した図。期待値計算による意思決定にも使う |
| UML | Unified Modeling Language | オブジェクト指向開発の標準モデリング言語。クラス図、ユースケース図、シーケンス図、アクティビティ図、状態マシン図など |
| DOA | Data Oriented Approach | データ中心アプローチ。業務で扱うデータの構造を先に定め、それを中心にシステムを設計する。処理は変わってもデータは変わりにくい、という考え方 |
| コード・ヨードン技法 | Coad-Yourdon Method | オブジェクト指向分析・設計の手法の一つ。クラス・属性・サービス（操作）などを段階的に定義する |
| シュレア・メラー技法 | Shlaer-Mellor Method | オブジェクト指向分析手法の一つ。情報モデル・状態モデル・プロセスモデルを使ってシステムを表す |

### 2-4 要件の合意・管理

| 用語 | 英語 | 解説 |
| :-: | :-: | :-: |
| ステークホルダ | Stakeholder | プロジェクトやシステムに利害関係を持つ人・組織（利用者、経営者、開発者、顧客など） |
| アカウンタビリティ | Accountability | 説明責任。自分の行動や決定について、関係者に説明し納得を得る責任 |
| トレーサビリティ | Traceability | 追跡可能性。要件→設計→プログラム→テストのつながりをたどれること。要件の漏れや変更の影響範囲を確認できる |
| 要件変更のルール | Requirements Change Rules | 要件変更の申請・影響評価・承認の手順をあらかじめ決めておくこと。無秩序な変更（スコープクリープ）を防ぐ |
| ファシリテーション | Facilitation | 会議などで中立的な立場から議論を促し、合意形成を助けること。進行役をファシリテーターという |

## 3. 調達計画・実施（55語）

### 3-1 調達の方法・形態

| 用語 | 英語 | 解説 |
| :-: | :-: | :-: |
| 内外作基準 | Make-or-Buy Criteria | 自社で作る（内製）か外部に任せる（外製・購入）かを判断する基準。コスト、技術力、機密性などで決める |
| IFB | Invitation For Bid | 入札招請書。価格を中心に入札を呼びかける文書 |
| システムインテグレーター | System Integrator | 情報システムの企画・設計・開発・運用までを一括して請け負う事業者 |
| SI事業者 | SI Provider | システムインテグレーション（SI）を行う事業者。システムインテグレーターと同じ意味で使われる |
| アウトソーシング | Outsourcing | 業務の一部または全部を外部の専門業者に委託すること |
| SaaS | Software as a Service | ソフトウェアの機能をインターネット経由でサービスとして提供する形態。利用者はアプリを使うだけ（PaaS＝実行環境、IaaS＝インフラ） |
| ASP | Application Service Provider | アプリケーションをネットワーク経由で貸し出す事業者・サービス。SaaSの前身的な形態 |
| IDC | Internet Data Center | 顧客のサーバーを預かり、電源・回線・空調・セキュリティなどを提供する施設（ハウジング・ホスティング） |
| SOAを含むWebサービス | Web Services incl. SOA | SOA（サービス指向アーキテクチャ）は、機能を「サービス」単位に部品化し組み合わせてシステムを作る考え方。Webサービスはその実現技術 |
| ソフトウェアパッケージの適用 | Applying Software Packages | 既製のパッケージソフトを導入すること。短期間・低コストだが、業務との差（ギャップ）の扱いが課題 |
| オープンソースソフトウェアの適用 | Applying OSS | ソースコードが公開され自由に利用・改変できるソフトを使うこと。ライセンス条件（GPLなど）の遵守と、サポートが自己責任になる点に注意 |
| OEM | Original Equipment Manufacturing | 他社ブランドの製品を製造すること（設計は委託元） |
| ODM | Original Design Manufacturing | 他社ブランドの製品を**設計から**製造まで行うこと。OEMとの違いは「設計もするか」 |
| ファブレス | Fabless | 自社で工場を持たず、企画・設計に特化し、製造は外部に委託する企業形態 |
| ファウンドリ | Foundry | 他社から製造を請け負う半導体製造専門の企業（例：TSMC）。ファブレスの委託先 |
| ソフトウェアのサプライチェーンマネジメント | Software Supply Chain Management | ソフトの部品（OSS、外部ライブラリなど）の調達から提供までを管理し、脆弱性やライセンス違反を防ぐこと。SBOM（部品表）の活用がポイント |
| ライセンス管理 | License Management | 保有しているソフトウェアライセンスの数・種類と使用状況を管理し、違反を防ぐこと |
| 構成管理 | Configuration Management | ハード・ソフト・ドキュメントなどの構成要素とバージョンを管理すること |

### 3-2 調達の手順・文書

| 用語 | 英語 | 解説 |
| :-: | :-: | :-: |
| RFI | Request For Information | 情報提供依頼書。ベンダーに技術・製品・実績などの情報提供を求める。**RFPの前**に行う |
| RFP | Request For Proposal | 提案依頼書。システムの要件や条件を示し、ベンダーに提案書の提出を求める文書 |
| RFQ | Request For Quotation | 見積依頼書。具体的な見積金額の提示を求める文書 |
| 企画競争入札 | Proposal-based Competition | 価格だけでなく提案内容（企画）を競わせて契約先を選ぶ方式（プロポーザル方式） |
| 一般競争入札 | Open Competitive Bidding | 条件を満たせば誰でも参加でき、原則として最も安い価格の者と契約する方式 |
| 総合評価落札方式 | Comprehensive Evaluation Method | 価格と技術（品質）の両方を点数化し、総合点が最も高い者を落札者とする方式 |
| 総合評価 | Overall Evaluation | 技術評価と価格評価を合計して判断すること |
| 価格評価 | Price Evaluation | 提示価格の安さを点数化して評価すること |
| WTO政府調達協定 | WTO Agreement on Government Procurement | 一定額以上の政府調達で、外国企業を差別せず公平に競争させることを定めた国際協定 |

流れ：RFI（情報収集）→ RFP（提案依頼）→ 提案書・見積書の評価 → ベンダー選定 → 契約

| 用語 | 英語 | 解説 |
| :-: | :-: | :-: |
| 対象範囲 | Scope | 調達する業務・システムの範囲 |
| システムモデル | System Model | 想定するシステムの構成や概要 |
| サービス要件 | Service Requirements | 求めるサービスの内容・レベル |
| 目標スケジュール | Target Schedule | 開発・導入の目標時期 |
| 契約条件 | Contract Terms | 契約形態、支払条件、検収方法、知的財産権の扱いなど |
| ベンダーの経営要件 | Vendor Business Requirements | ベンダーの経営状態（財務の安定性など）。途中で倒産されないかを見る |
| ベンダーのプロジェクト体制要件 | Vendor Project Structure Requirements | ベンダー側の体制（PMの経験、要員数、役割分担など） |

| 原価構成 | Cost Structure | 見積金額の内訳（人件費、機器費、経費など）。妥当性の確認に使う |
| 工期 | Construction Period | 作業を完了させるのに必要な期間 |

### 3-4 調達のリスク

| 用語 | 英語 | 解説 |
| :-: | :-: | :-: |
| 品質リスク | Quality Risk | 納品物が求める品質を満たさないリスク |
| 納期リスク | Delivery Risk | 期限までに納品されないリスク |
| 費用超過リスク | Cost Overrun Risk | 予算を超えてしまうリスク |
| 要員スキルに関するリスク | Personnel Skill Risk | ベンダー要員の能力不足で品質・納期に影響が出るリスク |

### 3-5 契約の種類

| 用語 | 英語 | 解説 |
| :-: | :-: | :-: |
| ソフトウェア開発委託モデル契約 | Model Contract for Software Development | 経済産業省・IPAが示したソフト開発委託契約のひな形。工程ごとに契約形態を使い分ける考え方 |
| 情報システム・モデル取引・契約書 | Model Transaction & Contract for IS | 経済産業省が公表した、情報システム開発の取引・契約のモデル。要件定義は準委任、開発は請負などの整理が示されている |
| 準委任契約 | Quasi-Mandate Contract | 作業の遂行（業務を行うこと）に対する契約。**完成責任はない**が善管注意義務がある。指揮命令権は受託者側（発注者が直接指示すると偽装請負になる） |
| 請負契約 | Contract for Work | **仕事の完成**に対して報酬を払う契約。受託者は完成責任と契約不適合責任を負う。指揮命令は受託者が行う |
| 知的財産権利用許諾契約 | IP License Agreement | 特許・著作権などの知的財産権を他者が使えるよう許諾する契約 |
| 定額契約 | Fixed-Price Contract | あらかじめ決めた金額で行う契約。コスト超過のリスクは受注者側が負う |
| 実費償還契約 | Cost-Reimbursable Contract | 実際にかかった費用に、手数料などを上乗せして支払う契約。コスト超過のリスクは発注者側が負う |
| Time＆Material契約 | Time and Material Contract | 作業時間（単価×時間）と材料費で支払う契約。定額と実費償還の中間的な形 |

### 3-6 ライセンス

| 用語 | 英語 | 解説 |
| :-: | :-: | :-: |
| ソフトウェア使用許諾契約 | Software License Agreement | ソフトを使用する条件を定めた契約（EULAなど）。所有権ではなく「使う権利」を得る |
| ライセンス契約 | License Agreement | 権利者が他者に権利の利用を許諾し、対価（ロイヤリティ）を受け取る契約 |
| ランニングロイヤリティ | Running Royalty | 販売数・売上などに応じて継続的に支払う使用料。最初に一括で払うのはイニシャル（一括）ロイヤリティ |
| レベニューシェア | Revenue Share | 初期費用を抑え、その代わりに得られた収益を発注者と受注者で分け合う契約形態 |
| サブライセンス | Sublicense | ライセンスを受けた者（ライセンシー）が、さらに第三者に再許諾すること |
| グラントバック | Grant-back | ライセンシーが改良した技術を、元の権利者（ライセンサー）に許諾・譲渡すること。独占的なグラントバックは独占禁止法上問題になりうる |

## 試験で狙われやすい比較まとめ

| 比較 | ポイント |
| :-: | :-: |
| RFI / RFP / RFQ | 情報提供 → 提案 → 見積。順番と目的の違い |
| 請負 / 準委任 | 完成責任あり / なし。どちらも指揮命令は受託者側 |
| 定額 / 実費償還 / T&M | コスト超過リスクを誰が負うか（受注者 / 発注者 / 中間） |
| OEM / ODM | 製造のみ / 設計から |
| ファブレス / ファウンドリ | 工場を持たない企業 / 製造を請け負う企業 |
| SoR / SoE / SoI | 記録 / つながり / 洞察 |
| PBP / NPV | 回収期間（時間価値なし） / 正味現在価値（時間価値あり、＞0なら採用） |
| リスク対応 | 回避・低減・移転・受容 |
| 現状指向 / 目的指向 | 現状改善型 / あるべき姿から考える |
| BPR / 業務改善 | 抜本的な再設計 / 部分的な改善 |

- 問：IT投資効果の評価方法において，キャッシュフローベースで初年度の投資によるキャッシュアウトを何年後に回収できるかという指標はどれか。

- 解説：PBP（Pay Back Period：回収期間法）は、投資で出ていったお金（キャッシュアウト）を、毎年入ってくるお金（キャッシュイン）で何年で取り戻せるかを見る指標。短いほど良い。計算が簡単だが、お金の時間価値や、回収した後の収入は考えない。

- イの意味：NPV（正味現在価値）は、将来のキャッシュフローを現在の価値に直した合計から投資額を引いた額。回収の年数は表さない。
- ウの意味：正しい。PBP（回収期間法）。投資額を何年で回収できるかを見る指標。
- エの意味：ROI（投資利益率）は、投資で得た利益を投資額で割った割合。回収の年数ではない。

#### 問 ap-18-r05h-q61

- 問：情報化投資計画において，投資効果の評価指標であるROIを説明したものはどれか。
- ア：売上増やコスト削減などによって創出された利益額を投資額で割ったもの

- 正解：ア

- エの意味：投資しない場合の競争力への影響を見るのは、定性的な評価（投資しないことのリスクの評価）。ROIのような数値の指標ではない。
