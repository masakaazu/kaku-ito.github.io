## 12-1 システム要件定義・ソフトウェア要件定義

### まとめ表

**要件を整理する図と表（R3秋 問46・R5春 問47）**

| 手法 | 何を表すか | 見分けるキーワード |
| :-: | :-: | :-: |
| DFD | データの流れ（プロセス・データストア・外部実体・データフロー） | 処理の順番や条件は書かない |
| E-R図 | 実体（エンティティ）と実体どうしの関連 | データの構造 |
| CRUDマトリクス | 機能ごとに、どのエンティティを生成・参照・更新・削除するか | Create・Read・Update・Delete |
| 決定表 | 条件の組合せと、そのとき行う動作 | Y／Nの組合せ |
| 状態遷移表 | 状態とイベントの組合せで、次の状態と動作 | 「レディ」「一時停止」などの状態 |

**要件の種類**

| 種類 | 何を決めるか | 例 |
| :-: | :-: | :-: |
| 機能要件 | システムが何をするか | 受注を登録する、請求書を印刷する |
| 非機能要件 | どれだけうまくできるか | 応答3秒以内、稼働率99.9%、利用者が1時間で習得できる |

- 決定表の読み方：上半分が条件（Y＝成り立つ、N＝成り立たない）、下半分が動作（X＝実行する）。列が「ルール」で、条件の組合せは条件の数がnなら2ⁿ通り（R5春 問47 は3条件で8列）

### 要件の種類

#### 機能要件（きのうようけん / Functional Requirements）

- 意味：システムが「何をするか」を定めた要件。業務で使う機能・入出力・処理の内容など
- ポイント：「どれだけ速く・止まらず・安全に」は非機能要件。利用者の要求を整理して、システムで実現すると決めたものが要件
- 語の意味：Functional＝機能の／Requirements＝要件

#### 非機能要件（ひきのうようけん / Non-functional Requirements）

- 意味：機能以外の、性能・信頼性・使用性・セキュリティ・運用・移行などの品質に関する要件
- ポイント：機能要件は「何をするか」、非機能要件は「どれだけうまくできるか」。IPAの非機能要求グレードは、可用性・性能・拡張性・運用保守性・移行性・セキュリティなどを段階で決める表
- 語の意味：Non-functional＝機能でない／Requirements＝要件

#### 性能要件（せいのうようけん / Performance Requirements）

- 意味：レスポンスタイムやスループットなど、どれだけ速く・多く処理できるかの要件。非機能要件の一つ
- ポイント：非機能要件の一つ。「1時間に1万件」「応答3秒以内」のように数値で決める。止まらないことは可用性要件
- 語の意味：Performance＝性能／Requirements＝要件

#### 可用性要件（かようせいようけん / Availability Requirements）

- 意味：稼働率や止めてよい時間など、システムがどれだけ止まらずに使えるかの要件。非機能要件の一つ
- ポイント：非機能要件の一つ。障害時の復旧時間（RTO）や、計画停止の時間帯もここで決める。速さは性能要件
- 語の意味：Availability＝使える状態であること／Requirements＝要件

#### 移行要件（いこうようけん / Migration Requirements）

- 意味：古いシステムから新しいシステムへ、データや業務をどう移すかについての要件
- ポイント：移す対象（プロセスとデータ）、方式（一斉・段階・並行）、スケジュール、リハーサルなどを決める。運用開始後の扱いは運用要件
- 語の意味：Migration＝移行／Requirements＝要件

#### 運用要件（うんようようけん / Operational Requirements）

- 意味：運用時間、運用形態、バックアップや監視の手順など、システムを動かし続けるための要件
- ポイント：誰がいつどう動かすかを決める。障害が起きたときの対応や、修正・変更のやり方は保守要件
- 語の意味：Operational＝運用の／Requirements＝要件

#### 保守要件（ほしゅようけん / Maintenance Requirements）

- 意味：保守の形態（オンサイト・遠隔）、保守のタイミング、問い合わせ対応の時間など、修正や変更をどう行うかの要件
- ポイント：日々動かすことは運用要件、直したり変えたりすることは保守要件
- 語の意味：Maintenance＝保守／Requirements＝要件

#### セキュリティ要件（せきゅりてぃようけん / Security Requirements）

- 意味：アクセス制御・暗号化・ログの取得など、情報セキュリティポリシーに沿ってシステムに持たせる安全のための要件。非機能要件の一つ
- ポイント：非機能要件の一つ。設計原則として、最小権限・多層防御・攻撃にさらされる面の最小化などを選ぶ
- 語の意味：Security＝安全／Requirements＝要件

### 性能を表す指標

#### レスポンスタイム（応答時間 / Response Time）

- 意味：利用者が要求を入力し終えてから、システムが最初の応答を返し始めるまでの時間
- ポイント：オンライン処理の速さの指標。結果を全部受け取り終えるまでを含めるのはターンアラウンドタイム
- 語の意味：Response＝応答／Time＝時間

#### ターンアラウンドタイム（Turnaround Time）

- 意味：処理を依頼してから、結果をすべて受け取り終えるまでの時間
- ポイント：バッチ処理の指標としてよく使う。最初の応答までならレスポンスタイム
- 語の意味：Turnaround＝折り返し・往復／Time＝時間

#### スループット（Throughput）

- 意味：単位時間あたりに処理できる仕事の量（件数・データ量など）
- ポイント：1件あたりの速さではなく「量」。レスポンスタイムが短くても、同時にさばける件数が少なければスループットは低い
- 語の意味：Throughput＝処理量

#### 非機能要求グレード（ひきのうようきゅうぐれーど / Non-functional Requirements Grade）

- 意味：IPAが公開している、非機能要件を「可用性・性能拡張性・運用保守性・移行性・セキュリティ・システム環境」の項目ごとに段階（グレード）で決めるための表
- ポイント：発注者と開発者が、非機能要件の水準を同じ物差しで合意するために使う
- 語の意味：Non-functional＝機能でない／Requirements＝要求／Grade＝等級

### 要求を集めて決める方法

#### 利害関係者要件（りがいかんけいしゃようけん / Stakeholder Requirements）

- 意味：利用者・発注者・運用者など、システムに関わる人たちのニーズを整理した要件。システム要件のもとになる
- ポイント：利用の状況と運用シナリオから、システムの境界（どこまでをシステムでやるか）を決める
- 語の意味：Stakeholder＝利害関係者／Requirements＝要件

#### 運用シナリオ（うんようしなりお / Operational Scenario）

- 意味：システムがどんな場面で、誰に、どのような手順で使われるかを、物語のように書いたもの
- ポイント：システムの境界や機能を決める材料になる。一つの目標についての利用者とシステムのやり取りを定義したものはユースケース
- 語の意味：Operational＝運用の／Scenario＝筋書き

#### 5W2H（ごだぶりゅーにえいち）

- 意味：Why・When・Where・Who・What・How・How muchの7つの観点。要件を漏れなく文書化するときに使う
- ポイント：5W1Hに費用（How much）を足したもの。シラバスでは業務・利用者の要件を明確にする観点として挙げられている
- 語の意味：Why＝なぜ／When＝いつ／Where＝どこで／Who＝誰が／What＝何を／How＝どのように／How much＝いくらで

#### ヒアリング（Hearing / Interview）

- 意味：利用者や担当者に直接話を聞いて、何が求められているかを明らかにする方法
- ポイント：事前にヒアリング計画を立て、終わったらヒアリング議事録を作って内容を確認してもらう。多くの人から決まった質問で集めるのはアンケート
- 語の意味：Hearing＝聞き取り

#### アンケート（Questionnaire）

- 意味：決めた質問を多くの人に配って回答してもらい、要求や意見を集める方法
- ポイント：広く集められるが、深く聞くことはできない。一人ずつ詳しく聞くのはヒアリング、実際の作業を見るのは観察法
- 語の意味：Questionnaire＝質問票

#### 観察法（かんさつほう / Observation）

- 意味：実際の仕事の様子をそばで見て、口に出されない要求や手順を見つける方法
- ポイント：本人が当たり前と思って言わないことが分かる。話を聞くのはヒアリング
- 語の意味：Observation＝観察

#### JAD（じゃど / Joint Application Development）

- 意味：利用者と開発者が集中的なワークショップに集まり、一緒に要件や設計を決める方法
- ポイント：関係者が一度に集まって決めるので、要件の食い違いや手戻りを減らせる。個別に話を聞くのはヒアリング
- 語の意味：Joint＝共同の／Application＝アプリケーション／Development＝開発

#### MoSCoW分析（もすこうぶんせき / MoSCoW Method）

- 意味：要件を Must（必須）・Should（すべき）・Could（できれば）・Won't（今回はしない）の4つに分けて優先順位を付ける方法
- ポイント：限られた期間や予算で、何を先に作るかを関係者で合意するために使う
- 語の意味：Must＝必ず／Should＝すべき／Could＝できれば／Won't＝しない

### 要件の評価とレビュー

#### 双方向の追跡可能性（そうほうこうのついせきかのうせい / Bidirectional Traceability）

- 意味：要件から設計・プログラム・テストへ、逆にテストやプログラムから元の要件へと、両方向にたどれること
- ポイント：要件の漏れ（実現されていない要件）と、余計なもの（要件にない機能）の両方を見つけられる。シラバスでは要件・設計・テストの評価の観点として何度も出てくる
- 語の意味：Bidirectional＝双方向の／Traceability＝追跡できること

#### トレーサビリティマトリクス（Traceability Matrix）

- 意味：要件を行、設計書やテストケースを列にして、どの要件がどこで実現・確認されたかを対応付けた表
- ポイント：双方向の追跡可能性を確かめるための道具。機能とエンティティの操作を対応付けるのはCRUDマトリクス
- 語の意味：Traceability＝追跡できること／Matrix＝行列・表

#### 一貫性（いっかんせい / Consistency）

- 意味：要件や設計の中に矛盾がなく、上位の要件とも食い違いがないこと
- ポイント：シラバスでは、上位の文書や他の成果物と食い違わない「外部一貫性」と、文書の中で矛盾しない「内部一貫性」に分けて評価する
- 語の意味：Consistency＝首尾一貫していること

#### テスト可能性（てすとかのうせい / Testability）

- 意味：要件が、テストで合否を判定できる形で書かれていること
- ポイント：「使いやすいこと」は判定できないので、「初めての利用者が1時間以内に操作を習得できること」のように数値で書く（R6秋 問48）
- 語の意味：Test＝試験／ability＝できること

#### 共同レビュー（きょうどうれびゅー / Joint Review）

- 意味：システムの取得者（発注者）と供給者（開発者）が一緒に、要件定義書や設計書などを確認するレビュー
- ポイント：要件定義・設計・テストの各工程の終わりに行い、双方の合意を取る。作成者の仲間どうしで行うのはピアレビュー
- 語の意味：Joint＝共同の／Review＝見直し

#### アシュアランスケース（Assurance Case）

- 意味：システムが安全・安心であるという主張を、根拠（証拠）と論理の筋道で示した文書
- ポイント：「この要件を満たす」と主張するだけでなく、なぜそう言えるかを第三者に説明できるようにする。シラバスでは要件の評価の用語例
- 語の意味：Assurance＝保証・確信／Case＝論証

### 利用者とその使い方を描く

#### ペルソナ（Persona）

- 意味：システムの利用者を役割ごとに、名前・年齢・目的などを持つ典型的な一人の人物として描いたもの
- ポイント：「この人なら何に困るか」を開発者全員で共有するために使う。実在の利害関係者そのものではなく仮想の人物
- 例：R7秋 問46（利用者を典型的な姿として描いた仮想の人物はペルソナ。エピック・ステークホルダ・プロダクトオーナーは誤り）
- 語の意味：Persona＝（ラテン語で）仮面・人格

#### ユーザーストーリー（User Story）

- 意味：「〈利用者〉として、〈目的〉のために、〈機能〉がほしい」の形で、利用者の視点から要件を短く書いたもの
- ポイント：アジャイル開発でよく使う。大きすぎて1回で作れないストーリーのまとまりはエピック、大きさの見積りはストーリーポイント
- 語の意味：User＝利用者／Story＝物語

#### エピック（Epic）

- 意味：1回の開発期間（スプリント）では作り切れない大きなユーザーストーリー。いくつかのストーリーに分けて作る
- ポイント：ストーリーをまとめた「大きな単位」。仮想の利用者像はペルソナ
- 例：R7秋 問46（誤りの選択肢。利用者の人物像ではない）
- 語の意味：Epic＝叙事詩（長い物語）

#### ストーリーポイント（Story Point）

- 意味：ユーザーストーリーを作る手間の大きさを、時間ではなく他のストーリーとの比較で表した相対的な数値
- ポイント：「Aの2倍くらい」のように相対で見積もる。チームが1スプリントでこなせるポイントの合計がベロシティ（13 ソフトウェア開発管理技術）
- 語の意味：Story＝物語（ユーザーストーリー）／Point＝点数

#### ユースケース（Use Case）

- 意味：一つの目標を達成するための、利用者（アクター）とシステムのやり取りを手順として書いたもの
- ポイント：ユースケース図で、アクターとユースケースのつながりを一覧にできる。外部から見たシステムの機能を表すので、内部の作りは書かない
- 語の意味：Use＝使う／Case＝場合

#### アクター（Actor）

- 意味：ユースケースで、システムの外にいてシステムとやり取りする人や外部システムの役割
- ポイント：実在の一人ではなく「役割」。一人が「受付係」と「管理者」の二つのアクターになることもある。UMLのユースケース図では人形の記号で描く
- 語の意味：Actor＝演じる者

#### UX（ゆーえっくす / User Experience）

- 意味：利用者が製品やサービスを使う前から使った後までに感じる、使いやすさ・楽しさ・満足などの体験全体
- ポイント：画面の見た目や操作（UI）だけでなく、目的を達成できたか、気持ちよく使えたかまで含む。UXデザインは、この体験をよくするように要件や画面を設計すること
- 語の意味：User＝利用者／Experience＝体験

#### 使用性（しようせい / Usability）

- 意味：利用者が目的を、効果的・効率的・満足して達成できる度合い。JIS X 25010の製品品質特性の一つ
- ポイント：副特性に習得性・運用操作性・アクセシビリティなどがある。「1時間以内に使い方を習得できる」は使用性の目標（R6秋 問48）。止まらないことは信頼性（可用性）
- 例：R6秋 問48（使用性の目標設定として適切なのは「利用者が1時間以内に習得できること」）
- 語の意味：Usability＝使いやすさ

### 試作して確かめる

#### プロトタイプ（Prototype）

- 意味：仕様を確かめるために、早い段階で作る試作品。利用者に触ってもらって仕様の漏れや食い違いを見つける
- ポイント：作って見せて意見をもらい、直して見せるを繰り返す開発をプロトタイピングという。手戻りを防ぐのが目的
- 語の意味：Prototype＝原型・試作品

#### モックアップ（Mockup）

- 意味：画面や帳票の見た目だけを再現した模型。中の処理は動かない
- ポイント：プロトタイプより手軽に作れ、画面の配置や項目を確かめるのに使う。処理まで動かして確かめるならプロトタイプ
- 語の意味：Mockup＝実物大の模型

#### 水平型プロトタイプ（すいへいがたぷろとたいぷ / Horizontal Prototype）

- 意味：システムの多くの機能を、画面などの表面だけ広く浅く作ったプロトタイプ
- ポイント：全体の画面の流れや使い勝手を確かめるのに向く。一つの機能を深く作るのは垂直型
- 語の意味：Horizontal＝水平の／Prototype＝試作品

#### 垂直型プロトタイプ（すいちょくがたぷろとたいぷ / Vertical Prototype）

- 意味：一部の機能だけを、画面からデータベースまで深く作り込んだプロトタイプ
- ポイント：性能や技術的に実現できるかを確かめるのに向く。広く浅く作るのは水平型
- 語の意味：Vertical＝垂直の／Prototype＝試作品

### データの流れを表す（DFD）

#### DFD（でぃーえふでぃー / Data Flow Diagram）

- 意味：業務やシステムの中でのデータの流れを、プロセス・データフロー・データストア・外部実体（源泉と吸収）の4つの記号で表した図
- ポイント：処理の順番・条件分岐・繰返しは表さない。機能とデータの関係が分かる（R3秋 問46 のウの説明）。データの構造はE-R図
- 例：R3秋 問46（「機能と入出力データとの関係を記述し、データの流れを明確にする」のはDFD）
- 語の意味：Data＝データ／Flow＝流れ／Diagram＝図

#### プロセス（Process）

- 意味：DFDで、入ってきたデータを加工して出力する処理。丸（円）で描く
- ポイント：プロセスには必ず入力と出力のデータフローがある。保存しておく場所はデータストア
- 語の意味：Process＝処理

#### データフロー（Data Flow）

- 意味：DFDで、データの流れを表す矢印。何のデータが流れるかを名前として書く
- ポイント：制御の流れ（いつ・どの順で）は表さない。それを表すのは流れ図やアクティビティ図
- 語の意味：Data＝データ／Flow＝流れ

#### データストア（Data Store）

- 意味：DFDで、データを一時的または永続的に保存しておく場所。ファイルやデータベースにあたり、二本線で描く
- ポイント：データストアどうしを直接つなぐことはできず、間に必ずプロセスが入る
- 語の意味：Data＝データ／Store＝保管所

#### 外部実体（がいぶじったい / External Entity）

- 意味：DFDで、システムの外にあってデータを出す（源泉）か受け取る（吸収）人や組織。四角で描く
- ポイント：「源泉と吸収」ともいう。システムの範囲の外なので、その中の処理は書かない
- 語の意味：External＝外部の／Entity＝実体

#### コンテキストダイアグラム（Context Diagram）

- 意味：システム全体を一つのプロセスとして描き、外部実体とのデータのやり取りだけを示した、いちばん上のレベルのDFD
- ポイント：システムの境界を示す。これを段階的に分けて詳しいDFDにしていく（段階的詳細化）
- 語の意味：Context＝周囲の状況／Diagram＝図

#### ミニスペック（Mini Specification）

- 意味：DFDを最下層まで分けたときの、一つのプロセスの処理内容を、文章・決定表・擬似コードなどで書いた仕様
- ポイント：DFDは流れしか表さないので、プロセスの中身はミニスペックで補う
- 語の意味：Mini＝小さな／Specification＝仕様書

#### 構造化分析法（こうぞうかぶんせきほう / Structured Analysis）

- 意味：DFDを使って業務を上位から段階的に分け、データの流れに着目して要件を分析する方法
- ポイント：トップダウンに分けていくのが特徴。データそのものに着目するのはデータ中心アプローチ（DOA）
- 語の意味：Structured＝構造化された／Analysis＝分析

### データの構造を表す（E-R図）

#### E-R図（いーあーるず / Entity-Relationship Diagram）

- 意味：業務で扱うデータを、実体（エンティティ）・関連（リレーションシップ）・属性の3つでモデル化した図
- ポイント：エンティティどうしの関係（1対多など）が分かる。データの流れを表すのはDFD（R3秋 問46 のエの説明）
- 例：R3秋 問46（「エンティティ・関連・属性の三つでモデル化」はE-R図で、CRUDマトリクスではない）
- 語の意味：Entity＝実体／Relationship＝関連／Diagram＝図

#### エンティティ（実体 / Entity）

- 意味：E-R図で、業務で管理する対象のまとまり。「顧客」「商品」「受注」など
- ポイント：データベースでは表（テーブル）になることが多い。エンティティどうしのつながりはリレーションシップ
- 語の意味：Entity＝実体

#### リレーションシップ（関連 / Relationship）

- 意味：E-R図で、エンティティどうしの関係。「顧客は受注を出す」など。1対1・1対多・多対多がある
- ポイント：多対多の関係は、間に連関エンティティを置いて1対多の二つに分けるのが普通
- 語の意味：Relationship＝関係

#### 論理データモデル（ろんりでーたもでる / Logical Data Model）

- 意味：使う製品やハードウェアに関係なく、業務で扱うデータの構造と関係を表したモデル
- ポイント：E-R図で表すことが多い。特定のDBMSに合わせて表・索引・格納方法まで決めたものが物理データモデル
- 語の意味：Logical＝論理的な／Data＝データ／Model＝模型

#### 物理データモデル（ぶつりでーたもでる / Physical Data Model）

- 意味：論理データモデルを、使うDBMSに合わせて表・列の型・索引・格納場所まで決めたモデル
- ポイント：性能を考えて、あえて正規化を崩すこともある。製品に依存しないのは論理データモデル
- 語の意味：Physical＝物理的な／Data＝データ／Model＝模型

### 条件と状態を整理する表

#### CRUDマトリクス（くらっどまとりくす / CRUD Matrix）

- 意味：機能（プロセス）を行、エンティティを列にして、各機能がどのエンティティを生成（C）・参照（R）・更新（U）・削除（D）するかを書いた表
- ポイント：どの機能からも生成されないデータや、誰も使わないデータを見つけられる。条件と動作の関係を表すのは決定表
- 例：R3秋 問46（正解のイ。アは決定表、ウはDFD、エはE-R図の説明）
- 語の意味：Create＝生成／Read＝参照／Update＝更新／Delete＝削除／Matrix＝表

#### 決定表（けっていひょう / Decision Table）

- 意味：条件の組合せ（Y／N）と、それぞれの組合せで実行する動作（X）を表にしたもの。デシジョンテーブルともいう
- ポイント：上半分の条件部と下半分の動作部からなる。複雑な条件の漏れや重なりを見つけやすく、テストケースを作るのにも使う
- 例：R5春 問47（3つの値引き条件の組合せから、値引きなし・3%・6%・9%の動作を選ぶ）
- 語の意味：Decision＝決定／Table＝表

#### 状態遷移図（じょうたいせんいず / State Transition Diagram）

- 意味：システムがとる状態を丸、状態を変えるイベントを矢印で描き、状態がどう移り変わるかを表した図。UMLのステートマシン図にあたる
- ポイント：同じ内容を表の形にしたのが状態遷移表。UMLではステートマシン図にあたる
- 語の意味：State＝状態／Transition＝移り変わり／Diagram＝図

#### 状態遷移表（じょうたいせんいひょう / State Transition Table）

- 意味：行にイベント（条件）、列に状態をとり、交わるところに動作と次の状態を書いた表
- ポイント：空欄は「状態が変わらない」を表すことが多い。図より抜けや漏れを見つけやすい
- 例：R3春 問47（レディから6つのイベントを順にたどると、最後は一時停止になる）
- 語の意味：State＝状態／Transition＝移り変わり／Table＝表

#### SysML（しすえむえる / Systems Modeling Language）

- 意味：UMLをもとに、ソフトウェアだけでなくハードウェアを含むシステム全体を表せるようにしたモデリング言語
- ポイント：要求図やパラメトリック図など、UMLにない図がある。組込みシステムや機械の設計で使う
- 語の意味：Systems＝システム／Modeling＝モデル化／Language＝言語

#### BPMN（びーぴーえむえぬ / Business Process Model and Notation）

- 意味：業務の流れを、イベント・アクティビティ・ゲートウェイなどの決められた記号で描くための表記法の標準
- ポイント：担当者ごとにレーン（帯）を分けて、誰がどの順で作業するかを表せる。データの流れに着目するのはDFD
- 語の意味：Business Process＝業務の流れ／Model＝模型／Notation＝表記法

### UMLの構造図

#### UML（ゆーえむえる / Unified Modeling Language）

- 意味：オブジェクト指向の分析・設計で使う、図の描き方の標準。OMGが定めている
- ポイント：システムの形を表す構造図（クラス図・オブジェクト図など）と、動きを表す振る舞い図（ユースケース図・アクティビティ図・シーケンス図など）に分かれる
- 語の意味：Unified＝統一された／Modeling＝モデル化／Language＝言語

#### クラス図（くらすず / Class Diagram）

- 意味：クラスの名前・属性・操作と、クラスどうしの関係（関連・汎化・集約など）を表す構造図
- ポイント：設計図としていちばん使われる。ある時点の具体的なインスタンスどうしの関係を表すのはオブジェクト図
- 例：R3秋 問48（リファクタリング「継承の分割」の前後をクラス図で比べる）
- 語の意味：Class＝分類・型／Diagram＝図

#### オブジェクト図（おぶじぇくとず / Object Diagram）

- 意味：ある時点での、具体的なインスタンス（オブジェクト）どうしの関係を表す構造図
- ポイント：クラス図の「実例」。クラス図が型の関係なら、オブジェクト図は値の入った個々のオブジェクトの関係
- 例：R7秋 問47（インスタンス間の関係を表現するのはオブジェクト図）
- 語の意味：Object＝もの・対象／Diagram＝図

#### コンポーネント図（こんぽーねんとず / Component Diagram）

- 意味：ソフトウェアを部品（コンポーネント）に分け、部品どうしのインタフェースと依存関係を表す構造図
- ポイント：実行ファイルやライブラリなどの物理的なまとまりを表す。それをどのマシンに置くかは配置図
- 例：R7秋 問47（誤りの選択肢）
- 語の意味：Component＝部品／Diagram＝図

#### パッケージ図（ぱっけーじず / Package Diagram）

- 意味：クラスなどの要素をパッケージ（名前の付いたフォルダのようなまとまり）に分け、まとまりどうしの依存関係を表す構造図
- ポイント：大きなシステムを整理するのに使う。部品の実行時のつながりはコンポーネント図
- 語の意味：Package＝包み・まとまり／Diagram＝図

#### 配置図（はいちず / Deployment Diagram）

- 意味：サーバや端末などのハードウェア（ノード）と、そこに置かれるソフトウェアの関係を表す構造図
- ポイント：「どの部品がどの機械で動くか」を表す。部品そのものの関係はコンポーネント図
- 語の意味：Deployment＝配置・展開／Diagram＝図

### UMLの振る舞い図

#### ユースケース図（ゆーすけーすず / Use Case Diagram）

- 意味：システムが外部に提供する機能（ユースケース）と、それを使うアクター（人や外部システム）の関係を表す図
- ポイント：システムの外から見た機能の一覧。処理の手順や順番は表さない
- 例：R3秋 問47（ウの「外部に提供する機能と利用者との関係」はユースケース図）
- 語の意味：Use Case＝利用の場面／Diagram＝図

#### アクティビティ図（あくてぃびてぃず / Activity Diagram）

- 意味：ある振る舞いから次の振る舞いへの、処理の流れ（制御の流れ）を表す図。分岐・合流・並行処理も描ける
- ポイント：流れ図に近い。業務の流れを担当者ごとのレーン（パーティション）に分けて描くこともできる
- 例：R3秋 問47（「ある振る舞いから次の振る舞いへの制御の流れ」はアクティビティ図）
- 語の意味：Activity＝活動／Diagram＝図

#### シーケンス図（しーけんすず / Sequence Diagram）

- 意味：オブジェクトどうしのメッセージのやり取りを、上から下への時間の順番で表す図
- ポイント：縦の点線（ライフライン）と横の矢印で描く。同じやり取りを、つながりの形で表すのがコミュニケーション図
- 例：R3秋 問47（イの「オブジェクト間の相互作用を時系列で表現」はシーケンス図）
- 語の意味：Sequence＝順序／Diagram＝図

#### コミュニケーション図（こみゅにけーしょんず / Communication Diagram）

- 意味：オブジェクトどうしのつながり（リンク）と、その上を流れるメッセージを、番号を付けて表す図
- ポイント：シーケンス図と同じ内容を、時間の順ではなく「誰と誰がつながっているか」を中心に描く
- 語の意味：Communication＝やり取り／Diagram＝図

#### ステートマシン図（すてーとましんず / State Machine Diagram）

- 意味：一つのオブジェクトの状態が、イベントの発生や時間の経過によってどう変わるかを表す図。状態遷移図のUML版
- ポイント：状態遷移図のUML版。複数のオブジェクトの間のやり取りは表さない
- 例：R3秋 問47（エの「一つのオブジェクトの状態が…どのように変化するか」はステートマシン図）
- 語の意味：State Machine＝状態機械／Diagram＝図

#### タイミング図（たいみんぐず / Timing Diagram）

- 意味：オブジェクトの状態が、時間の目盛りに沿っていつ変わるかを表す図
- ポイント：組込みシステムなど、時間の制約が大事な場面で使う。状態の移り方だけならステートマシン図
- 語の意味：Timing＝時機／Diagram＝図

### クラスどうしの関係

#### 関連（かんれん / Association）

- 意味：クラス図で、二つのクラスのインスタンスどうしにつながりがあることを表す関係。実線で描く
- ポイント：線の端に多重度（1、0..*など）やロール名を書ける。三つ以上のクラスにまたがる関連（多項関連）もある（R6春 問45 のア）
- 語の意味：Association＝つながり

#### 汎化（はんか / Generalization）

- 意味：複数のクラスの共通部分をまとめて上位のクラスを作る関係。「〇〇は△△の一種（is-a）」の関係で、白抜きの三角の矢印で描く
- ポイント：上位から下位へ分けるのが特化。下位クラスは上位クラスの属性と操作を継承する
- 語の意味：Generalization＝一般化

#### 特化（とっか / Specialization）

- 意味：上位のクラスを、より具体的な下位のクラスに分けていくこと。汎化の逆向きの見方
- ポイント：「図形」から「三角形」「四角形」を作るのが特化、「三角形」「四角形」から「図形」をまとめるのが汎化
- 語の意味：Specialization＝特殊化

#### 集約（しゅうやく / Aggregation）

- 意味：全体と部分の関係（part-of）。部分は全体がなくなっても単独で存在できる。白抜きのひし形で描く
- ポイント：全体と部分で属性や操作を共有するわけではない（R6春 問45 のエは誤り）。部分が全体と運命を共にするのはコンポジション
- 語の意味：Aggregation＝寄せ集め

#### コンポジション（Composition）

- 意味：集約のうち、部分が全体と一緒に作られ一緒に消える強い全体と部分の関係。黒く塗ったひし形で描く
- ポイント：「注文」と「注文明細」のように、全体を消すと部分も消える。部分が単独で残れるのは集約
- 語の意味：Composition＝構成

#### 多重度（たじゅうど / Multiplicity）

- 意味：関連の端に書く、相手のインスタンスがいくつ対応するかの数。1、0..1、1..*、*など
- ポイント：「顧客 1 — 0..* 注文」なら、顧客1人に注文が0件以上。E-R図のカーディナリティにあたる
- 語の意味：Multiplicity＝多数であること

#### 依存（いぞん / Dependency）

- 意味：一方のクラスが他方を一時的に使っていて、相手が変わると影響を受ける関係。点線の矢印で描く
- ポイント：引数やローカル変数として相手を使うだけの弱い関係。インスタンスを持ち続けるなら関連
- 語の意味：Dependency＝頼っていること

### オブジェクト指向の基本

#### オブジェクト指向（おぶじぇくとしこう / Object Oriented）

- 意味：データ（属性）と、それを扱う処理（操作）を一つのオブジェクトにまとめて、オブジェクトどうしのやり取りでシステムを組み立てる考え方
- ポイント：カプセル化・継承・多相性が三つの柱。処理の手順を中心に考えるのは構造化設計
- 語の意味：Object＝もの・対象／Oriented＝向きの

#### クラス（Class）

- 意味：同じ種類のオブジェクトに共通する属性と操作を定義した型（ひな形）
- ポイント：クラスから作られた一つ一つの実体がインスタンス。クラスは設計図、インスタンスは実物
- 語の意味：Class＝分類・種類

#### インスタンス（Instance）

- 意味：クラスをもとに、実際にメモリ上に作られた個々のオブジェクト
- ポイント：同じクラスのインスタンスでも、属性の値はそれぞれ違う
- 語の意味：Instance＝実例

#### 属性（ぞくせい / Attribute）

- 意味：クラスが持つデータの項目。「顧客」なら氏名・住所など
- ポイント：属性の値を直接書き換えさせず、操作（メソッド）を通して扱うのがカプセル化
- 語の意味：Attribute＝性質

#### メソッド（操作 / Method）

- 意味：クラスに定義した、属性を扱う処理。UMLでは操作（operation）と呼ぶ
- ポイント：他のオブジェクトはメッセージを送ってメソッドを呼び出す
- 語の意味：Method＝方法

#### カプセル化（かぷせるか / Encapsulation）

- 意味：属性とメソッドを一つにまとめ、内部のデータを外から直接見せずに、決めたメソッドを通してだけ使わせること
- ポイント：情報隠蔽（いんぺい）ともいう。内部を変えても使う側に影響しにくくなる
- 語の意味：Encapsulation＝カプセルに包むこと

#### 委譲（いじょう / Delegation）

- 意味：あるオブジェクトが受けた処理の一部を、自分が持っている別のオブジェクトに任せること
- ポイント：継承を使わずに機能を再利用する方法。サブクラスのインスタンスがスーパークラスの操作を実行するのは継承によるもので、委譲ではない（R6春 問45 のウは誤り）
- 語の意味：Delegation＝任せること

### 継承と多相性

#### 継承（けいしょう / Inheritance）

- 意味：上位のクラス（スーパークラス）の属性と操作を、下位のクラス（サブクラス）が引き継ぐこと
- ポイント：共通部分を一か所に書けるので再利用しやすい。継承した操作をサブクラスで書き直すのがオーバーライド
- 語の意味：Inheritance＝受け継ぐこと

#### スーパークラス（Superclass）

- 意味：継承の元になる上位のクラス。基底クラス・親クラスともいう
- ポイント：サブクラスに共通する属性と操作を持つ。汎化でまとめてできるクラス
- 語の意味：Super＝上位の／Class＝クラス

#### サブクラス（Subclass）

- 意味：スーパークラスを継承した下位のクラス。派生クラス・子クラスともいう
- ポイント：スーパークラスの操作を再定義（オーバーライド）したり、自分だけの属性を足したりできる（R6春 問45 のイが正解）
- 語の意味：Sub＝下位の／Class＝クラス

#### オーバーライド（Override）

- 意味：スーパークラスで定義された操作を、サブクラスで同じ名前・同じ引数のまま中身を書き直すこと
- ポイント：多相性を実現するしくみ。名前が同じで引数の違う操作を並べるのはオーバーロード
- 例：R6春 問45（サブクラスではスーパークラスの操作を再定義できる）
- 語の意味：Override＝上書きする

#### オーバーロード（Overload）

- 意味：同じクラスの中に、名前は同じで引数の型や数が違う操作を複数定義すること
- ポイント：呼び出すときの引数によってどれが動くかが決まる。継承した操作を書き直すのはオーバーライド
- 語の意味：Overload＝多く載せる

#### 多相性（たそうせい / Polymorphism）

- 意味：同じメッセージを送っても、受け取ったオブジェクトのクラスによって違う動きをすること。ポリモーフィズム
- ポイント：「描画せよ」というメッセージで、三角形は三角を、四角形は四角を描く。オーバーライドで実現する
- 語の意味：Poly＝多くの／morphism＝形をとること

#### 抽象クラス（ちゅうしょうくらす / Abstract Class）

- 意味：中身のない操作（抽象メソッド）を含み、それ自体からはインスタンスを作れないクラス
- ポイント：サブクラスが抽象メソッドを必ず実装する。共通の型だけを決めたいときに使う
- 語の意味：Abstract＝抽象的な／Class＝クラス

### 設計の原則（SOLID）

#### SOLID原則（そりっどげんそく / SOLID Principles）

- 意味：オブジェクト指向設計で、変更に強く分かりやすいクラスを作るための5つの原則の頭文字
- ポイント：単一責任・開放閉鎖・リスコフの置換・インタフェース分離・依存性逆転。シラバス Ver.7.2 でソフトウェア設計原則として追加された
- 語の意味：Single responsibility／Open-closed／Liskov substitution／Interface segregation／Dependency inversion の頭文字

#### 単一責任の原則（たんいつせきにんのげんそく / Single Responsibility Principle）

- 意味：一つのクラスは一つの責任だけを持ち、クラスを変更する理由は一つだけにすべきという原則
- ポイント：モジュールの機能的強度の考えに近い。いろいろな役割を一つのクラスに詰め込まない
- 語の意味：Single＝一つの／Responsibility＝責任／Principle＝原則

#### 開放閉鎖の原則（かいほうへいさのげんそく / Open-Closed Principle）

- 意味：クラスは拡張には開いていて（機能を足せる）、修正には閉じている（既存のコードを書き換えない）べきという原則
- ポイント：新しい機能はサブクラスや新しい部品を足して実現し、動いているコードはいじらない
- 語の意味：Open＝開いた／Closed＝閉じた／Principle＝原則

#### リスコフの置換原則（りすこふのちかんげんそく / Liskov Substitution Principle）

- 意味：スーパークラスを使っている所にサブクラスのインスタンスを入れても、正しく動かなければならないという原則
- ポイント：サブクラスがスーパークラスの約束を破るような継承をしない
- 語の意味：Liskov＝提唱者の名前／Substitution＝置き換え／Principle＝原則

#### インタフェース分離の原則（いんたふぇーすぶんりのげんそく / Interface Segregation Principle）

- 意味：使う側が必要としない操作まで含んだ大きなインタフェースを作らず、小さなインタフェースに分けるべきという原則
- ポイント：使わない操作の変更に、使う側が巻き込まれないようにする
- 語の意味：Interface＝接点／Segregation＝分離／Principle＝原則

#### 依存性逆転の原則（いぞんせいぎゃくてんのげんそく / Dependency Inversion Principle）

- 意味：上位のモジュールは下位のモジュールの具体的な作りに頼らず、両方とも抽象（インタフェース）に頼るべきという原則
- ポイント：業務の処理がデータベース製品などの細部に縛られないようにする。クリーンアーキテクチャの土台になる考え
- 語の意味：Dependency＝依存／Inversion＝逆転／Principle＝原則

### デザインパターン

#### デザインパターン（Design Pattern）

- 意味：オブジェクト指向設計でよく出てくる問題と、その解き方を型として名前を付けて整理したもの
- ポイント：GoFの23パターンが有名で、生成・構造・振る舞いの3種類に分かれる。システム全体の構造の型はアーキテクチャパターン（MVCなど）
- 語の意味：Design＝設計／Pattern＝型

#### GoF（ごふ / Gang of Four）

- 意味：デザインパターンの本を書いた4人の著者のこと。その本の23のパターンを「GoFのデザインパターン」と呼ぶ
- ポイント：生成に関するパターン（Singletonなど）・構造に関するパターン（Adapterなど）・振る舞いに関するパターン（Observerなど）に分かれる
- 語の意味：Gang＝仲間／of Four＝4人の

#### Singleton（しんぐるとん）

- 意味：あるクラスのインスタンスが、システムの中で一つしか作られないことを保証する、生成に関するパターン
- ポイント：設定情報の管理など、一つだけあればよいものに使う
- 語の意味：Singleton＝一つだけのもの

#### Factory Method（ふぁくとりめそっど）

- 意味：インスタンスを作る処理をサブクラスに任せて、作るクラスを使う側から切り離す、生成に関するパターン
- ポイント：使う側は「何を作るか」を知らなくてよい。インスタンスを一つに限るのはSingleton
- 語の意味：Factory＝工場／Method＝方法

#### Adapter（あだぷた）

- 意味：インタフェースの合わないクラスを、間に変換役を入れて使えるようにする、構造に関するパターン
- ポイント：既存の部品を作り直さずに使える。シラバスのレガシーラッピングも、古い仕組みを新しいインタフェースで包む考え方
- 語の意味：Adapter＝適合させるもの

#### Composite（こんぽじっと）

- 意味：部品と、部品を集めた入れ物を同じように扱えるようにして、木構造を作る構造に関するパターン
- ポイント：フォルダとファイルのように、入れ物の中に入れ物を入れられる構造に使う
- 語の意味：Composite＝合成の

#### Observer（おぶざーば）

- 意味：あるオブジェクトの状態が変わったとき、それを見ている複数のオブジェクトに自動で知らせる、振る舞いに関するパターン
- ポイント：画面の表示を、データの変化に合わせて更新するのに使う。Pub/Subの考え方に近い
- 語の意味：Observer＝観察者

#### Strategy（すとらてじ）

- 意味：処理のやり方（アルゴリズム）をクラスとして切り出し、実行中に差し替えられるようにする、振る舞いに関するパターン
- ポイント：if文で分岐する代わりに、やり方ごとのクラスを入れ替える
- 語の意味：Strategy＝戦略

#### Template Method（てんぷれーとめそっど）

- 意味：処理の大きな流れをスーパークラスで決め、細かい手順をサブクラスで実装する、振る舞いに関するパターン
- ポイント：流れは共通で、中身だけ違う処理に使う。やり方全体を差し替えるのはStrategy
- 語の意味：Template＝ひな形／Method＝方法

### アーキテクチャ

#### MVCモデル（えむぶいしーもでる / Model-View-Controller）

- 意味：アプリケーションを、データと業務処理（Model）・表示（View）・入力の受付と制御（Controller）の3つに分けるアーキテクチャパターン
- ポイント：画面を変えても業務処理に影響しにくい。シラバスでアーキテクチャパターンの代表として挙げられている
- 語の意味：Model＝模型（データと処理）／View＝見せる部分／Controller＝制御する部分

#### クリーンアーキテクチャ（Clean Architecture）

- 意味：業務のルールを中心に置き、画面・データベース・外部サービスなどの細部を外側に置いて、内側が外側に依存しないようにする設計の考え方
- ポイント：依存の向きを外から内への一方向にする（依存性逆転の原則）。データベースを変えても業務ルールを直さずに済む
- 語の意味：Clean＝きれいな／Architecture＝構造

#### マイクロサービスアーキテクチャ（Microservice Architecture）

- 意味：システムを、独立して開発・配置できる小さなサービスの集まりとして作り、サービスどうしはAPIでやり取りする方式
- ポイント：各サービスを別々に変更・リリースしやすい（R6秋 問47 の正解）。反対に、サービスごとに言語を変えられる分そろえにくく、データの整合性やサービス間の通信の負担は増える
- 例：R6秋 問47（利点は「各サービスの変更がしやすい」）
- 語の意味：Micro＝小さな／Service＝サービス／Architecture＝構造

#### モノリシックアーキテクチャ（Monolithic Architecture）

- 意味：システムの全機能を一つの大きなプログラムとして作り、まとめて配置する方式
- ポイント：作り始めは簡単だが、一部を変えるにも全体を作り直して入れ替える必要がある。小さく分けるのはマイクロサービス
- 語の意味：Monolithic＝一枚岩の／Architecture＝構造

#### サービスメッシュ（Service Mesh）

- 意味：マイクロサービスどうしの通信の制御（経路・暗号化・再試行・監視など）を、各サービスの横に置いた代理役（プロキシ）が引き受ける仕組み
- ポイント：通信のための処理をサービスの中に書かずに済む
- 語の意味：Service＝サービス／Mesh＝網の目

#### サーキットブレーカー（Circuit Breaker）

- 意味：呼び出し先のサービスが失敗を続けたとき、しばらく呼び出しを止めてすぐにエラーを返し、障害が他のサービスに広がるのを防ぐ仕組み
- ポイント：電気のブレーカーと同じく「遮断」する。一定時間たったら試しに呼び出して回復を確かめる
- 語の意味：Circuit＝回路／Breaker＝遮断器

#### サーバレスアーキテクチャ（Serverless Architecture）

- 意味：利用者がサーバの準備や管理をせず、イベントが起きたときだけクラウド上でプログラム（関数）を動かす方式
- ポイント：サーバがないわけではなく、管理をクラウド事業者に任せる。動いた分だけ料金がかかる。FaaSともいう
- 語の意味：Server＝サーバ／less＝なしの／Architecture＝構造

### ドメイン駆動設計（DDD）

#### ドメイン駆動設計（どめいんくどうせっけい / DDD: Domain-Driven Design）

- 意味：業務の領域（ドメイン）の知識をモデルにして、そのモデルをそのままソフトウェアの設計とコードに反映させる設計手法
- ポイント：業務の専門家と開発者が同じ言葉（ユビキタス言語）で話すことを重視する。シラバス Ver.7.2 で追加された
- 語の意味：Domain＝領域／Driven＝駆動された／Design＝設計

#### ドメインモデル（Domain Model）

- 意味：業務の領域で扱う概念・ルール・関係を、エンティティや値オブジェクトなどで表したモデル
- ポイント：業務のルール（ドメインロジック）をこのモデルの中に持たせる
- 語の意味：Domain＝領域／Model＝模型

#### ユビキタス言語（ゆびきたすげんご / Ubiquitous Language）

- 意味：DDDで、業務の専門家と開発者が会話・文書・コードのすべてで同じ意味で使う共通の用語
- ポイント：「受注」と「注文」のような言葉の揺れをなくし、コードのクラス名にもそのまま使う
- 語の意味：Ubiquitous＝どこにでもある／Language＝言語

#### コンテキストマップ（Context Map）

- 意味：DDDで、システムを境界づけられたコンテキスト（同じ言葉が同じ意味で通じる範囲）に分け、その間の関係を表した図
- ポイント：「顧客」という言葉が、営業と経理で違う意味を持つことがある。その範囲の境目と関係を示す
- 語の意味：Context＝文脈／Map＝地図

#### DDDのエンティティ（でぃーでぃーでぃーのえんてぃてぃ / Entity）

- 意味：DDDで、属性の値が変わっても、識別子（IDなど）で同じものとして追い続けるオブジェクト。「顧客」「注文」など
- ポイント：住所が変わっても同じ顧客。値が同じなら同じものとみなすのは値オブジェクト
- 語の意味：Entity＝実体

#### 値オブジェクト（あたいおぶじぇくと / Value Object）

- 意味：DDDで、識別子を持たず、値そのものが同じなら同じものとみなすオブジェクト。「金額」「住所」など
- ポイント：作った後は値を変えない（不変）ように作るのが普通。IDで追い続けるのはエンティティ
- 語の意味：Value＝値／Object＝もの

### 設計の進め方

#### 構造化設計（こうぞうかせっけい / Structured Design）

- 意味：システムの機能を上位から下位へ段階的に分け、階層構造のモジュールにして設計する方法
- ポイント：モジュールの強度を高く、結合度を低くするように分ける。データと処理をまとめたオブジェクトで考えるのはオブジェクト指向設計
- 語の意味：Structured＝構造化された／Design＝設計

#### プロセス中心設計（ぷろせすちゅうしんせっけい / POA: Process Oriented Approach）

- 意味：業務の処理の流れ（プロセス）に着目して、機能を先に決めてからデータを決める設計手法
- ポイント：業務の手順が変わると、データの作りまで直すことになりやすい。データを先に決めるのはデータ中心アプローチ（DOA）
- 語の意味：Process＝処理／Oriented＝向きの／Approach＝取り組み方

#### データ中心アプローチ（でーたちゅうしんあぷろーち / DOA: Data Oriented Approach）

- 意味：業務の処理より、変化しにくい業務データの構造に着目して先に設計し、その上に処理を作る方法
- ポイント：業務の手順は変わりやすいが、扱うデータは変わりにくいという考え。処理の流れを先に考えるのはプロセス中心アプローチ（POA）
- 語の意味：Data＝データ／Oriented＝向きの／Approach＝取り組み方

#### 段階的詳細化（だんかいてきしょうさいか / Stepwise Refinement）

- 意味：大きな機能を、少しずつ細かい機能に分けて、最後に実装できる大きさまで詳しくしていく方法
- ポイント：DFDでいちばん上のコンテキストダイアグラムから下へ分けていくのも段階的詳細化
- 語の意味：Stepwise＝一歩ずつの／Refinement＝細かくすること

#### 複合設計（ふくごうせっけい / Composite Design）

- 意味：データの流れに着目してプログラムをモジュールに分け、モジュールの強度と結合度で分け方のよさを評価する構造化設計の手法
- ポイント：STS分割・TR分割・共通機能分割を使う。データの構造に着目するのはジャクソン法・ワーニエ法
- 語の意味：Composite＝複合の／Design＝設計

### モジュールの分割手法

#### STS分割（えすてぃーえすぶんかつ / Source-Transform-Sink）

- 意味：データの流れに着目して、プログラムを「入力（源泉）」「変換（加工）」「出力（吸収）」の3つの部分に分ける手法
- ポイント：入力データが少しずつ形を変えて出力になる、一本道の処理に向く。入力の種類で処理が分かれるならTR分割
- 語の意味：Source＝源泉／Transform＝変換／Sink＝吸収

#### TR分割（てぃーあーるぶんかつ / Transaction分割）

- 意味：入力されるトランザクション（取引）の種類ごとに処理を分けて、それぞれを別のモジュールにする手法
- ポイント：「入金」「出金」「照会」のように、入力の種類で処理が分かれるときに使う。一本道の流れならSTS分割
- 語の意味：TR＝Transaction（取引・処理の単位）

#### 共通機能分割（きょうつうきのうぶんかつ / Common Function Decomposition）

- 意味：いくつかのモジュールで共通に使う処理を取り出して、一つのモジュールにまとめる手法
- ポイント：STS分割やTR分割で分けた後に、重なった部分を共通化するのに使う
- 語の意味：Common＝共通の／Function＝機能

#### ジャクソン法（じゃくそんほう / Jackson Structured Programming）

- 意味：入力データと出力データの構造（順次・選択・繰返し）を図に表し、その対応からプログラムの構造を決める手法
- ポイント：データ構造に着目した分割手法。データの流れに着目するのはSTS分割・TR分割
- 語の意味：Jackson＝考案者の名前

#### ワーニエ法（わーにえほう / Warnier Method）

- 意味：入力データの構造をもとに、「何回」「どの条件で」の集合の考え方でプログラムの構造を決める手法
- ポイント：ジャクソン法と同じくデータ構造に着目する。ジャクソン法は入出力の対応、ワーニエ法は主に入力の構造を使う
- 語の意味：Warnier＝考案者の名前

### 処理の手順を描く図

#### 流れ図（ながれず / Flowchart）

- 意味：処理の手順を、処理（長方形）・判断（ひし形）・端子（角丸）などの記号と矢印で表した図。フローチャート
- ポイント：テストの網羅率の問題でよく出る（R3春 問48・R4春 問47・R4秋 問48）。データの流れを表すのはDFD
- 語の意味：Flowchart＝流れの図

#### NS図（えぬえすず / Nassi-Shneiderman Diagram）

- 意味：順次・選択・繰返しの3つの基本構造だけを、矢印を使わずに四角の中に入れ子にして描く図
- ポイント：矢印がないので勝手な飛び越し（goto）が書けず、自然に構造化プログラミングになる
- 語の意味：Nassi・Shneiderman＝考案者2人の名前／Diagram＝図

#### PAD（ぱっど / Problem Analysis Diagram）

- 意味：処理の構造を、左から右へ階層が深くなる木の形で表す、日本で作られた図
- ポイント：上から下へ処理の順番、左から右へ詳しさが進む。四角の入れ子で描くのはNS図
- 語の意味：Problem＝問題／Analysis＝分析／Diagram＝図

#### HIPO（はいぽ / Hierarchy plus Input Process Output）

- 意味：機能の階層を表す図式目次と、各機能の入力・処理・出力を表すIPO図で、システムの機能を表す方法
- ポイント：「何を入れて何を出すか」を機能ごとに整理する。処理の細かい手順はNS図やPADで表す
- 語の意味：Hierarchy＝階層／Input＝入力／Process＝処理／Output＝出力

#### 構造化チャート（こうぞうかちゃーと / Structure Chart）

- 意味：モジュールの呼び出し関係を、上位から下位への木の形で表した図。モジュールの間で受け渡すデータも書く
- ポイント：構造化設計（複合設計）の結果を表す。一つのモジュールの中の手順は流れ図やNS図で表す
- 語の意味：Structure＝構造／Chart＝図表

#### 構造化プログラミング（こうぞうかぷろぐらみんぐ / Structured Programming）

- 意味：プログラムを、順次・選択・繰返しの3つの基本構造だけを組み合わせて書く方法
- ポイント：gotoで勝手な所へ飛ばないので、読みやすく直しやすい。NS図はこの3つしか描けない図
- 語の意味：Structured＝構造化された／Programming＝プログラムを作ること

### モジュールの強度

#### モジュール強度（もじゅーるきょうど / Module Strength）

- 意味：一つのモジュールの中の処理どうしの関係の強さ。結束性・凝集度ともいい、強いほど独立性が高い
- ポイント：最もよいのは機能的強度、最も悪いのは暗合的強度。モジュールどうしの関係の強さはモジュール結合度で、こちらは弱いほどよい
- 語の意味：Module＝部品／Strength＝強さ

#### 機能的強度（きのうてききょうど / Functional Strength）

- 意味：モジュールが一つの機能だけを行っている状態。最も強度が高く、望ましい
- ポイント：シラバスでは「機能的結束性」。単一責任の原則と同じ考え
- 語の意味：Functional＝機能の／Strength＝強さ

#### 情報的強度（じょうほうてききょうど / Informational Strength）

- 意味：同じデータ構造を扱う複数の機能を一つのモジュールにまとめ、機能ごとに入口を分けた状態
- ポイント：データと操作をまとめる、オブジェクト指向のクラスに近い。機能的強度の次によい
- 語の意味：Informational＝情報の／Strength＝強さ

#### 連絡的強度（れんらくてききょうど / Communicational Strength）

- 意味：決まった順番で実行する処理のうち、同じデータを受け渡しながら使う処理をまとめた状態
- ポイント：情報的強度の次によい。データでつながっているだけで、一つの機能ではない
- 語の意味：Communicational＝伝え合う／Strength＝強さ

#### 手順的強度（てじゅんてききょうど / Procedural Strength）

- 意味：決まった順番で実行するという理由だけで、関係の薄い処理をまとめた状態
- ポイント：処理の間でデータの受け渡しまであれば連絡的強度。同じ時期に実行するだけなら時間的強度
- 語の意味：Procedural＝手順の／Strength＝強さ

#### 時間的強度（じかんてききょうど / Temporal Strength）

- 意味：初期化処理や終了処理のように、同じ時期に実行する、関係の薄い処理をまとめた状態
- ポイント：「プログラムの最初にやること全部」のようなモジュール。強度は低い
- 語の意味：Temporal＝時間の／Strength＝強さ

#### 論理的強度（ろんりてききょうど / Logical Strength）

- 意味：似たような処理をいくつかまとめ、呼び出すときの引数（フラグ）でどれを実行するかを切り替える状態
- ポイント：呼び出す側が制御フラグを渡すので、制御結合になりやすい。強度は低い
- 語の意味：Logical＝論理的な／Strength＝強さ

#### 暗合的強度（あんごうてききょうど / Coincidental Strength）

- 意味：互いに関係のない処理を、たまたま一つのモジュールにまとめた状態。最も強度が低い
- ポイント：分けた理由が説明できないモジュール。直すときにどこに影響するか分からなくなる
- 語の意味：Coincidental＝偶然の／Strength＝強さ

### モジュールの結合度

#### モジュール結合度（もじゅーるけつごうど / Module Coupling）

- 意味：モジュールどうしの関係の強さ。弱い（低い）ほどモジュールの独立性が高く、望ましい
- ポイント：低い順に データ結合 → スタンプ結合 → 制御結合 → 外部結合 → 共通結合 → 内容結合。モジュールの中のまとまりはモジュール強度で、こちらは強いほどよい
- 例：R4春 問46・R5春 問46・R6春 問46（3回出た）
- 語の意味：Module＝部品／Coupling＝つなぐこと

#### データ結合（でーたけつごう / Data Coupling）

- 意味：必要なデータ項目だけを、引数として受け渡す結合。最も結合度が低く、望ましい
- ポイント：相手の内部も共通の領域も使わない。構造体を丸ごと渡すとスタンプ結合になる
- 例：R4春 問46・R5春 問46（独立性が最も高いのはデータ結合）
- 語の意味：Data＝データ／Coupling＝結合

#### スタンプ結合（すたんぷけつごう / Stamp Coupling）

- 意味：構造体やレコードなどのデータ構造を丸ごと引数で渡し、受け取った側がその一部だけを使う結合
- ポイント：データ結合より一つ悪い。渡す構造が変わると、使っていない側まで影響を受ける
- 例：R4春 問46（誤りの選択肢）
- 語の意味：Stamp＝ひとまとまりの判／Coupling＝結合

#### 制御結合（せいぎょけつごう / Control Coupling）

- 意味：相手の処理を切り替えるためのフラグ（制御パラメータ）を引数で渡し、相手の動きを決める結合
- ポイント：呼ぶ側が相手の内部の作りを知っている必要がある。R6春 問46 のイ「実行する機能や論理を決定するために引数を受け渡す」は内容結合ではなく制御結合
- 例：R5春 問46（イの「制御パラメータを引数として渡し，実行順序を制御する」は制御結合）
- 語の意味：Control＝制御／Coupling＝結合

#### 外部結合（がいぶけつごう / External Coupling）

- 意味：外部宣言した単一のデータ項目を、複数のモジュールで共有する結合
- ポイント：共有するのが「単一のデータ項目」なら外部結合、「データ構造（共通域）」なら共通結合。R6春 問46 のウ「大域的な単一のデータ項目」は制御結合ではなく外部結合
- 例：R5春 問46（エの「必要なデータを外部宣言して共有する」は外部結合）
- 語の意味：External＝外部の／Coupling＝結合

#### 共通結合（きょうつうけつごう / Common Coupling）

- 意味：共通域（グローバル領域）に置いたデータ構造を、複数のモジュールが参照・更新する結合
- ポイント：どのモジュールが値を変えたか分かりにくく、結合度が高い。内容結合の次に悪い
- 例：R6春 問46（「大域的なデータを参照するモジュール間の関係は共通結合」が正解）、R5春 問46（アの共通域のデータの参照）
- 語の意味：Common＝共通の／Coupling＝結合

#### 内容結合（ないようけつごう / Content Coupling）

- 意味：あるモジュールが、相手のモジュールの内部のデータを直接参照したり、内部へ直接ジャンプしたりする結合。最も結合度が高い
- ポイント：R6春 問46 のア「CALL命令を使わずJUMP命令で他のモジュールを呼び出す」は外部結合ではなく内容結合
- 語の意味：Content＝中身／Coupling＝結合

### ソフトウェアの品質特性

#### JIS X 25010（じすえっくすにまんごせんじゅう）

- 意味：システムとソフトウェアの品質を、製品品質（8特性）と利用時の品質（5特性）のモデルで定めた日本産業規格。国際規格ISO/IEC 25010にあたる
- ポイント：要件定義や設計のときに、どの品質特性をどこまで求めるかを決める物差しになる
- 語の意味：JIS＝Japanese Industrial Standards（日本産業規格）

#### 機能適合性（きのうてきごうせい / Functional Suitability）

- 意味：必要な機能がそろっていて、正しい結果を出し、目的に合っている度合い。製品品質特性の一つ
- ポイント：「利用者の使いたい機能が100%提供できている」は機能適合性（機能完全性）の目標で、使用性ではない（R6秋 問48 のエ）
- 語の意味：Functional＝機能の／Suitability＝適していること

#### 性能効率性（せいのうこうりつせい / Performance Efficiency）

- 意味：決められた条件で、応答時間・処理量・使う資源の量が適切である度合い。製品品質特性の一つ
- ポイント：副特性は時間効率性・資源効率性・容量満足性。速さだけでなく、メモリやCPUの使い方も含む
- 語の意味：Performance＝性能／Efficiency＝効率

#### 互換性（ごかんせい / Compatibility）

- 意味：他の製品やシステムと情報を交換したり、同じ環境で一緒に動いたりできる度合い。製品品質特性の一つ
- ポイント：副特性は共存性（同じ環境で邪魔し合わない）と相互運用性（情報をやり取りできる）。別の環境に移せるのは移植性
- 語の意味：Compatibility＝両立できること

#### 信頼性（しんらいせい / Reliability）

- 意味：決められた条件で、決められた期間、機能を正しく実行し続けられる度合い。製品品質特性の一つ
- ポイント：副特性は成熟性・可用性・障害許容性（耐故障性）・回復性。「障害発生から1時間以内に使えること」は回復性の目標で、使用性ではない（R6秋 問48 のア）
- 語の意味：Reliability＝頼れること

#### 保守性（ほしゅせい / Maintainability）

- 意味：ソフトウェアを直したり、改良したり、環境の変化に合わせたりするときの、やりやすさの度合い。製品品質特性の一つ
- ポイント：副特性はモジュール性・再利用性・解析性・修正性・試験性。R7春 問47 では「適正規模の基準を満たすプログラムの割合」が保守性の定量的な指標
- 例：R7春 問47（不具合件数÷規模は信頼性の指標、分岐の網羅率はテストの指標）
- 語の意味：Maintainability＝保守できること

#### 移植性（いしょくせい / Portability）

- 意味：ソフトウェアを、別のハードウェアやOSなどの環境へ移しやすい度合い。製品品質特性の一つ
- ポイント：副特性は適応性・設置性・置換性。他の製品と一緒に動くのは互換性
- 語の意味：Portability＝持ち運べること

### 品質の副特性

#### 可用性（かようせい / Availability）

- 意味：使いたいときに使える状態になっている度合い。信頼性の副特性
- ポイント：稼働率で表すことが多い。止まった後に元に戻る力は回復性
- 語の意味：Availability＝利用できること

#### 障害許容性（しょうがいきょようせい / Fault Tolerance）

- 意味：ハードウェアやソフトウェアに障害が起きても、決められた働きを続けられる度合い。耐故障性ともいう。信頼性の副特性
- ポイント：フォールトトレラント設計で高める。止まってから元に戻る力は回復性
- 語の意味：Fault＝障害／Tolerance＝耐えること

#### 回復性（かいふくせい / Recoverability）

- 意味：障害が起きて止まったとき、データを戻し、望む状態へ回復できる度合い。信頼性の副特性
- ポイント：止まらずに続けるのは障害許容性、止まった後に戻るのが回復性。シラバスの設計特性では復元性（レジリエンス）とも書かれる
- 語の意味：Recoverability＝回復できること

#### 習得性（しゅうとくせい / Learnability）

- 意味：利用者が、使い方を覚えやすい度合い。使用性の副特性
- ポイント：「利用者が1時間以内に使い方を習得できる」は習得性の目標（R6秋 問48）
- 語の意味：Learnability＝学びやすさ

#### 運用操作性（うんようそうさせい / Operability）

- 意味：利用者が操作しやすく、制御しやすい度合い。使用性の副特性
- ポイント：操作の手数や分かりやすさ。覚えやすさは習得性、障害のある人も使えるかはアクセシビリティ
- 語の意味：Operability＝操作できること

#### 解析性（かいせきせい / Analysability）

- 意味：障害の原因や、変更したときの影響範囲を調べやすい度合い。保守性の副特性
- ポイント：直す前に「どこを直せばよいか」を見つけやすいか。直しやすさそのものは修正性
- 語の意味：Analysability＝分析できること

#### 修正性（しゅうせいせい / Modifiability）

- 意味：欠陥を入れたり品質を下げたりせずに、効率よく修正できる度合い。保守性の副特性
- ポイント：調べやすさは解析性、修正後に試しやすいかは試験性
- 語の意味：Modifiability＝変更できること

#### 試験性（しけんせい / Testability）

- 意味：テストの基準を決めやすく、テストを実施しやすい度合い。保守性の副特性
- ポイント：要件の評価の「テスト可能性」と同じ考え方
- 語の意味：Testability＝試験できること

### 利用時の品質

#### 有効性（ゆうこうせい / Effectiveness）

- 意味：利用者が目的を、正確に完全に達成できた度合い。利用時の品質の一つ
- ポイント：「目的が果たせたか」。どれだけの手間や時間で果たせたかは効率性
- 語の意味：Effectiveness＝効果があること

#### 効率性（こうりつせい / Efficiency）

- 意味：目的を達成するのにかかった時間や手間などの資源の少なさ。利用時の品質の一つ
- ポイント：製品品質の「性能効率性」はシステムの速さ、利用時の「効率性」は利用者の手間
- 語の意味：Efficiency＝効率

#### 満足性（まんぞくせい / Satisfaction）

- 意味：利用者が使ってみて、役に立った・快適だった・信頼できたと感じる度合い。利用時の品質の一つ
- ポイント：数値で測りにくいので、アンケートなどで測る
- 語の意味：Satisfaction＝満足

#### リスク回避性（りすくかいひせい / Freedom from Risk）

- 意味：使うことで、経済・健康・安全・環境などへの悪い影響が起きにくい度合い。利用時の品質の一つ
- ポイント：システムの中の守りの強さは製品品質のセキュリティ。利用の結果として困ったことが起きないかを見るのがリスク回避性
- 語の意味：Freedom＝自由・免れていること／from Risk＝危険から

#### 利用状況網羅性（りようじょうきょうもうらせい / Context Coverage）

- 意味：最初に想定した使い方だけでなく、想定外の状況でも有効・効率的・安全に使える度合い。利用時の品質の一つ
- ポイント：「いろいろな場面で使えるか」。シラバスの用語例に挙がる5つ目の特性
- 語の意味：Context＝状況／Coverage＝範囲を覆うこと

### 保守しやすい設計の観点

#### 無矛盾性（むむじゅんせい / Consistency）

- 意味：プログラムや文書の中で、書き方や名前の付け方、処理の考え方が統一されていて食い違いがないこと
- ポイント：シラバスで、保守性を考えた設計の観点として挙げられている。自己記述性・構造性・簡潔性と並ぶ
- 語の意味：Consistency＝首尾一貫していること

#### 自己記述性（じこきじゅつせい / Self-descriptiveness）

- 意味：分かりやすい名前やコメントによって、プログラム自身を読むだけで何をしているかが分かること
- ポイント：別の文書を読まなくても理解できるので、直す人が変わっても困らない
- 語の意味：Self＝自身／descriptiveness＝説明していること

#### 構造性（こうぞうせい / Structuredness）

- 意味：プログラムが、意味のあるまとまりに分けられ、整理された構造になっていること
- ポイント：モジュールの強度を高く結合度を低くした設計で実現する
- 語の意味：Structuredness＝構造化されていること

#### 簡潔性（かんけつせい / Conciseness）

- 意味：余分な処理や重複がなく、必要なことが短く書かれていること
- ポイント：同じ処理をあちこちに書くと、直すときに直し漏れが起きやすい
- 語の意味：Conciseness＝簡潔さ

#### 拡張性（かくちょうせい / Extensibility）

- 意味：新しい機能を後から追加しやすいこと
- ポイント：開放閉鎖の原則に従って作ると拡張性が高くなる。別の環境に移しやすいのは移植性
- 語の意味：Extensibility＝広げられること

### セキュリティの設計原則

#### 最小権限の原則（さいしょうけんげんのげんそく / Principle of Least Privilege）

- 意味：利用者やプログラムには、仕事に必要な最小限の権限だけを与えるという設計原則
- ポイント：乗っ取られたときの被害を小さくできる。シラバスでは「最小限の原則」「システムサービスへのアクセス制限」として挙げられている
- 語の意味：Least＝最小の／Privilege＝特権

#### 多層防御（たそうぼうぎょ / Defense in Depth）

- 意味：入口・ネットワーク・サーバ・データなど複数の層に対策を重ね、一つが破られても次で防ぐという設計原則
- ポイント：一つの対策に頼らない。攻撃される面そのものを減らすのは攻撃対象領域の最小化
- 語の意味：Defense＝防御／in Depth＝深さをもって

#### 攻撃対象領域の最小化（こうげきたいしょうりょういきのさいしょうか / Attack Surface Reduction）

- 意味：使わないサービスやポートを止め、外部に見せる部分を減らして、攻撃にさらされる境界面を小さくする設計原則
- ポイント：攻撃される「入口」を減らす。入られた後の被害を減らすのは最小権限や多層防御
- 語の意味：Attack＝攻撃／Surface＝表面／Reduction＝減らすこと

#### フェールセーフ（Fail Safe）

- 意味：故障や誤りが起きたとき、安全な側に倒れるように作る設計。信号機が故障したら全部赤になる、など
- ポイント：止めてでも安全を優先する。故障しても機能を続けるのはフェールソフト・フォールトトレランス（04 システム構成要素）
- 語の意味：Fail＝失敗する／Safe＝安全な

### 信頼性の解析手法

#### FTA（えふてぃーえー / Fault Tree Analysis）

- 意味：起きては困る障害（頂上事象）を出発点に、その原因を中間の原因から基本の原因まで掘り下げ、ANDやORのゲートでつないだ樹形図で分析する手法
- ポイント：結果から原因へ「上から下へ」たどる。部品の故障から影響へ「下から上へ」たどるのはFMEA
- 例：R4秋 問47（FTAの説明はイ。アはFMEA、ウはなぜなぜ分析、エはODC分析）
- 語の意味：Fault＝障害／Tree＝木／Analysis＝分析

#### FMEA（えふえむいーえー / Failure Mode and Effects Analysis）

- 意味：システムを作る部品ごとに、起こりうる故障の形（故障モード）を挙げ、それがシステムにどう影響するかを評価する手法
- ポイント：部品から全体への影響を「下から上へ」たどる。障害から原因へたどるのはFTA
- 例：R4秋 問47（アの「構成品目の故障モードに着目して…影響を評価」はFMEA）
- 語の意味：Failure Mode＝故障の形／and Effects＝と影響／Analysis＝分析

#### STAMP/STPA（すたんぷ・えすてぃーぴーえー）

- 意味：事故を部品の故障ではなく、システムの構成要素どうしの制御のやり取りがうまくいかないことで起きると考えて、危険を分析する手法
- ポイント：STAMPが事故のモデル、STPAがそれを使った分析の手順。部品が壊れなくても起きる事故を見つけられる。シラバス Ver.7.2 の用語例
- 語の意味：STAMP＝System-Theoretic Accident Model and Processes／STPA＝System-Theoretic Process Analysis

#### なぜなぜ分析（なぜなぜぶんせき / Why-Why Analysis）

- 意味：起きた問題に「なぜ」を何度も繰り返して問い、根本の原因を明らかにする手法
- ポイント：起きた後の原因の深掘りに使う。論理ゲートの樹形図で表すのはFTA
- 例：R4秋 問47（ウの説明）
- 語の意味：Why＝なぜ

#### ODC分析（おーでぃーしーぶんせき / Orthogonal Defect Classification）

- 意味：互いに重ならないように決めた属性（欠陥の種類・見つけたきっかけなど）で欠陥を分類し、どこに集中しているかから開発工程の弱点を調べる手法
- ポイント：一つ一つの原因の深掘りではなく、たくさんの欠陥を分類して傾向を見る
- 例：R4秋 問47（エの説明）
- 語の意味：Orthogonal＝直交した（互いに重ならない）／Defect＝欠陥／Classification＝分類

### 入力データのチェック

#### リミットチェック（Limit Check）

- 意味：入力された値が、決められた上限と下限の範囲に入っているかを確かめるチェック
- ポイント：シラバスのインタフェース設計の用語例。数字かどうかを見るのはニューメリックチェック、形式を見るのはフォーマットチェック
- 語の意味：Limit＝限界／Check＝確認

#### フォーマットチェック（Format Check）

- 意味：入力された値の桁数や形式（日付の形など）が、決められた形になっているかを確かめるチェック
- ポイント：値の範囲を見るのはリミットチェック
- 語の意味：Format＝形式／Check＝確認

#### ニューメリックチェック（Numeric Check）

- 意味：数字だけが入るべき項目に、数字以外の文字が入っていないかを確かめるチェック
- ポイント：値が範囲内かまでは見ない。それはリミットチェック
- 語の意味：Numeric＝数の／Check＝確認

#### チェックディジット（Check Digit）

- 意味：コード番号に、他の桁から計算した1桁を付けておき、入力したときに計算し直して入力の誤りを見つける方法
- ポイント：桁の打ち間違いや入れ替えを見つけられる。商品のバーコード（JANコード）の最後の1桁がこれ
- 語の意味：Check＝確認／Digit＝桁

#### 照合チェック（しょうごうちぇっく / Matching Check）

- 意味：入力されたコードが、マスタファイルなどに登録されているかを照らし合わせて確かめるチェック
- ポイント：存在しない顧客番号や商品番号を見つける。形の正しさだけならフォーマットチェック
- 語の意味：Matching＝突き合わせ／Check＝確認

### 部品化と再利用

#### 部品化（ぶひんか / Componentization）

- 意味：何度も使う処理を部品（コンポーネント）として切り出し、別のシステムでも使えるようにすること
- ポイント：再利用すると開発期間が短くなり、品質も安定する。部品を組み合わせてソフトウェアを作るのがコンポーネントウェア
- 語の意味：Component＝部品／ization＝にすること

#### コンポーネントウェア（Componentware）

- 意味：既にある部品（コンポーネント）を組み合わせてソフトウェアを作る方法、またはそのための部品
- ポイント：部品は中が見えないブラックボックス型で使うことが多い
- 語の意味：Component＝部品／ware＝製品

#### ブラックボックス型部品（ぶらっくぼっくすがたぶひん / Black-box Component）

- 意味：中身（ソースコード）を見せず、決められたインタフェースだけを通して使う部品
- ポイント：使う側は中を変えられないが、中が変わっても影響を受けにくい。中を見て変えられるのはホワイトボックス型
- 語の意味：Black box＝中の見えない箱／Component＝部品

#### ホワイトボックス型部品（ほわいとぼっくすがたぶひん / White-box Component）

- 意味：ソースコードが公開されていて、使う側が中身を見たり、変更したり、継承して使ったりできる部品
- ポイント：自由に合わせられるが、元の部品が変わると影響を受けやすい
- 語の意味：White box＝中の見える箱／Component＝部品

#### クラスライブラリ（Class Library）

- 意味：よく使う機能を、オブジェクト指向のクラスとしてまとめた部品集
- ポイント：必要なクラスを呼び出して使う。処理の大きな流れまで用意されていて、その中に自分の処理を入れるのはフレームワーク
- 語の意味：Class＝クラス／Library＝図書館（部品集）

#### フレームワーク（Framework）

- 意味：アプリケーションの共通の骨組みと処理の流れを用意しておき、開発者は決められた所に自分の処理を書き足す部品
- ポイント：自分のコードがフレームワークから呼ばれる（制御の反転）。自分からクラスを呼び出して使うのはクラスライブラリ
- 語の意味：Frame＝骨組み／work＝作業

#### レガシーラッピング（Legacy Wrapping）

- 意味：古いシステム（レガシー）の機能を作り直さずに、新しいインタフェースで包んで、新しいシステムから部品として使えるようにすること
- ポイント：中身は変えない。デザインパターンのAdapterと同じ考え方
- 語の意味：Legacy＝遺産（古いもの）／Wrapping＝包むこと

#### COTS（こっつ / Commercial Off-The-Shelf）

- 意味：市販されていて、買ってすぐそのまま使えるソフトウェア製品やハードウェア製品
- ポイント：自分で作るより早く安いが、自社の業務に合わない部分は業務の方を合わせるか、追加開発が必要
- 語の意味：Commercial＝市販の／Off-The-Shelf＝棚から下ろしてすぐの

### レビューの方法

#### デザインレビュー（Design Review）

- 意味：設計の工程の中で、設計書などの成果物を関係者が確認し、問題点を早く見つけるレビュー
- ポイント：目的は設計工程の成果物の問題を、次の工程に進む前に発見すること（R7春 問45）。出荷の可否の判定やプロジェクト管理の問題の発見が目的ではない
- 例：R7春 問45（デザインレビューの目的は「設計工程内で、設計工程の成果物の問題点を発見する」）
- 語の意味：Design＝設計／Review＝見直し

#### ウォークスルー（Walkthrough）

- 意味：作成者を含めた複数人で、仕様書やソースコードに書かれた処理を、机の上で順にたどって（シミュレートして）問題点を見つけるレビュー（ピアレビューの一つ）
- ポイント：作成者が説明しながら進めることが多い。司会役（モデレーター）を置き、役割と手順を決めて正式に行うのはインスペクション
- 例：R4秋 問46（成果物の振る舞いを机上でシミュレートして問題点を発見する手法はウォークスルー）
- 語の意味：Walkthrough＝通しで歩くこと

#### インスペクション（Inspection）

- 意味：モデレーター（司会役）が進め、参加者の役割・手順・チェックリストを決めて正式に行うレビュー（ピアレビューの一つ）。見つけた欠陥を記録して、修正まで確認する
- ポイント：作成者は説明役にならないことが多い。作成者中心に気軽にたどるのはウォークスルー
- 語の意味：Inspection＝検査

#### モデレーター（Moderator）

- 意味：インスペクションで、会議の進行と、レビューの手順が守られているかの管理を受け持つ司会役
- ポイント：作成者とは別の人が務める。見つかった欠陥がきちんと直されたかの確認もする
- 語の意味：Moderator＝調停者・司会者

#### ピアレビュー（Peer Review）

- 意味：同じ立場の仲間（同僚の開発者など）どうしで、成果物を確認し合うレビュー。ウォークスルーやインスペクションを含む
- ポイント：上司や品質保証部門ではなく仲間で行う。ウォークスルーやインスペクションもピアレビューの一種
- 語の意味：Peer＝同等の仲間／Review＝見直し

#### コードレビュー（Code Review）

- 意味：ソースコードを他の人が読んで、コーディング標準・設計書との一致・効率・保守性などを確認すること
- ポイント：設計書を確認するのはデザインレビュー。ツールで自動的に調べるのは静的解析
- 語の意味：Code＝プログラム／Review＝見直し

#### ラウンドロビン（Round Robin）

- 意味：参加者全員が順番にレビューの責任者（進行役）を務めながら行うレビュー
- ポイント：全員が主体的に参加するようになる。資料を回覧して意見を書いてもらうのはパスアラウンド
- 語の意味：Round Robin＝順番に回すこと

#### パスアラウンド（Pass Around）

- 意味：レビューの対象をメールなどで複数の人に回し、それぞれが都合のよいときに見て意見を返すレビュー
- ポイント：集まらなくてよいので手軽だが、議論はしにくい
- 語の意味：Pass Around＝回覧する

## 12-3 実装・構築

### まとめ表

**ホワイトボックステストの網羅基準（弱い順）**

| 基準 | 満たす条件 | 例：判定「A かつ B」が一つ |
| :-: | :-: | :-: |
| 命令網羅（C0） | すべての命令を1回以上実行 | 真になるケース1つでよい場合がある |
| 判定条件網羅（C1、分岐網羅） | すべての判定で、真と偽の両方の分岐を通る | 真になるケースと偽になるケースの2つ |
| 条件網羅 | 判定の中の個々の条件（A、B）が真と偽の両方をとる | （A真・B偽）（A偽・B真）でもよい。分岐は偽ばかりでもよい |
| 判定条件／条件網羅 | 判定条件網羅と条件網羅の両方 | 分岐の真偽と、各条件の真偽をそろえる |
| 複数条件網羅 | 各判定の中の条件の真偽の組合せを全部 | 2条件なら4通り |

- 最少のテストケース数：命令網羅は「一つの判定の中で最も多い分岐の数」が目安（R3春 問48 は3分岐の命令3つずつ → 3ケース）
- 判定条件網羅は、すべての判定で真と偽の両方を通るケースを作る（R4春 問47）
- 網羅率＝通った数 ÷ 全体の数。命令が全部通っても、分岐が片方しか通らない判定があれば C1 は100%にならない（R4秋 問48 は C0 100%・C1 80%）

**ブラックボックステストの技法**

| 技法 | 考え方 | 例：1〜100が有効な入力 |
| :-: | :-: | :-: |
| 同値分割 | 同じ扱いになる値の集まり（同値クラス）から代表を1つずつ | 有効：50、無効：−5、150 |
| 限界値分析 | 同値クラスの境目とその両隣 | 0、1、100、101 |
| 原因結果グラフ | 入力（原因）と出力（結果）の関係をグラフにし、決定表に直す | 条件の組合せが多いとき |
| 実験計画法 | 直交表を使い、少ないケースで因子の組合せを調べる | 多くの設定の組合せ |

**エラー埋込み法の計算（R7秋 問48）**

| 手順 | 計算 |
| :-: | :-: |
| ① 埋め込んだエラーの発見率 | 36 ÷ 48 ＝ 0.75 |
| ② 真のエラーも同じ率で見つかると考える | 総数 ＝ 42 ÷ 0.75 ＝ 56 |
| ③ 残っている真のエラー | 56 − 42 ＝ 14 |

### コーディング

#### コーディング標準（こーでぃんぐひょうじゅん / Coding Standard）

- 意味：プログラムの書き方を統一するために、命名規則・インデント・ネストの深さ・使ってはいけない命令などを決めた取り決め
- ポイント：守らないと、人によって書き方がばらばらになり、読みにくく直しにくくなる。守っているかはコードレビューや静的解析で確かめる
- 語の意味：Coding＝プログラムを書くこと／Standard＝標準

#### 命名規則（めいめいきそく / Naming Convention）

- 意味：変数・関数・クラスなどの名前の付け方の決まり。長さ・使う文字・単語の区切り方などを決める
- ポイント：名前を見るだけで役割が分かるようにする（自己記述性）。コーディング標準の一部
- 語の意味：Naming＝名前を付けること／Convention＝慣例・決まり

#### インデンテーション（Indentation）

- 意味：プログラムの行頭を字下げして、処理の入れ子（ブロック）の深さを見た目で分かるようにすること
- ポイント：コーディング標準で字下げの幅をそろえる。エディタが自動で字下げするのはオートインデント
- 語の意味：Indentation＝字下げ

#### ネスト（Nest）

- 意味：if文やループの中に、さらにif文やループを入れる入れ子の構造
- ポイント：深くなると読みにくく、テストもしにくい。コーディング標準で深さの上限を決めることがある
- 語の意味：Nest＝入れ子（鳥の巣）

#### 使用禁止命令（しようきんしめいれい / Prohibited Statements）

- 意味：コーディング標準で、使ってはいけないと決めた命令や書き方。goto文や、危険な関数など
- ポイント：バグやセキュリティの穴を生みやすいものを最初から使わせない
- 語の意味：Prohibited＝禁止された／Statements＝命令

### コーディングを助ける機能

#### コード補完（こーどほかん / Code Completion）

- 意味：プログラムを書いている途中で、変数名や関数名の候補を出して、残りを自動で入力する機能
- ポイント：入力の手間と打ち間違いを減らす。IDE（統合開発環境）の代表的な機能
- 語の意味：Code＝プログラム／Completion＝完成させること

#### オートインデント（Auto Indent）

- 意味：改行したときなどに、プログラムの構造に合わせて自動で字下げする機能
- ポイント：インデンテーションをそろえる手間を省く。色分けで見やすくするのはシンタックスハイライト
- 語の意味：Auto＝自動の／Indent＝字下げ

#### シンタックスハイライト（Syntax Highlight）

- 意味：予約語・変数・文字列・コメントなどを、文法上の種類ごとに色や書体を変えて表示する機能
- ポイント：書き間違いや、閉じ忘れの引用符に気付きやすくなる
- 語の意味：Syntax＝文法／Highlight＝目立たせること

#### コードオーディター（Code Auditor）

- 意味：ソースコードがコーディング標準に従っているかを、自動で調べて違反を知らせるツール。静的解析の一種
- ポイント：プログラムを動かさずに調べる静的解析の一種。人が読んで確かめるのはコードレビュー
- 語の意味：Code＝プログラム／Auditor＝監査人

#### ブレークポイント（Breakpoint）

- 意味：デバッグのとき、プログラムの実行をわざと一時停止させる場所。止めた所で変数の値などを調べる
- ポイント：デバッガの基本機能。止めずに通った道筋を記録するのはトレーサー
- 語の意味：Break＝中断／Point＝地点

### デバッグとコードの解析

#### デバッガ（Debugger）

- 意味：プログラムを1行ずつ実行したり、途中で止めたりしながら、変数の値などを調べて誤りを探すツール
- ポイント：ブレークポイントやステップ実行の機能を持つ。命令の実行の順番を記録するのはトレーサー
- 語の意味：Debug＝虫（不具合）を取る／er＝道具

#### トレーサー（Tracer）

- 意味：プログラムの実行中に、通った命令の順番や変数の変化を記録して出力するツール
- ポイント：後から実行の道筋をたどれる。ある時点のメモリの内容を丸ごと書き出すのはスナップショット
- 語の意味：Tracer＝追跡するもの

#### スナップショット（Snapshot）

- 意味：プログラムの実行中の決めた時点で、メモリやレジスタの内容を書き出して記録する方法
- ポイント：その瞬間の「写真」。途中の流れを記録するのはトレーサー
- 語の意味：Snapshot＝早撮り写真

#### アサーション（Assertion）

- 意味：プログラムの中に「ここでは必ずこの条件が成り立つ」という式を書いておき、成り立たなければ止めて知らせる仕組み
- ポイント：想定外の状態をすぐに見つけられる。テストのときの判定にも使う
- 語の意味：Assertion＝断言

#### 静的解析（せいてきかいせき / Static Analysis）

- 意味：プログラムを動かさずに、ソースコードを調べて、コーディング標準違反・使われない変数・脆弱性などを見つけること
- ポイント：動かして調べるのは動的テスト。ツールで自動的に行うことが多い
- 語の意味：Static＝静的な（動かさない）／Analysis＝分析

#### 動的テスト（どうてきてすと / Dynamic Testing）

- 意味：実際にプログラムを動かして、結果が期待どおりかを確かめるテスト
- ポイント：動かさずに調べるのは静的解析やレビュー
- 語の意味：Dynamic＝動的な（動かす）／Testing＝試験

#### サイクロマティック複雑度（さいくろまてぃっくふくざつど / Cyclomatic Complexity）

- 意味：プログラムの分岐の多さから、通り道（経路）の複雑さを数値にした指標。分岐の数＋1などで求める
- ポイント：値が大きいほど複雑で、テストもしにくい。コードレビューのメトリクス計測に使う
- 語の意味：Cyclomatic＝閉じた経路の／Complexity＝複雑さ

### プログラミングの方式

#### アスペクト指向プログラミング（あすぺくとしこうぷろぐらみんぐ / Aspect-Oriented Programming）

- 意味：ログの記録やトランザクション管理など、多くの処理にまたがる関心事（アスペクト）を、本来の処理から切り離して一か所に書く方法
- ポイント：同じ処理をあちこちに書かずに済む。オブジェクト指向を補う考え方
- 語の意味：Aspect＝側面・関心事／Oriented＝向きの／Programming＝プログラムを作ること

#### 論理型プログラミング（ろんりがたぷろぐらみんぐ / Logic Programming）

- 意味：事実と規則（論理式）を書いておき、問いに対する答えをコンピュータに推論させる方法。Prologが代表
- ポイント：手順を書くのではなく「何が成り立つか」を書く
- 語の意味：Logic＝論理／Programming＝プログラムを作ること

#### 関数型プログラミング（かんすうがたぷろぐらみんぐ / Functional Programming）

- 意味：値を受け取って値を返す関数を組み合わせてプログラムを作る方法。変数の値を後から書き換えないのが基本
- ポイント：同じ入力なら必ず同じ結果になるので、テストしやすい
- 語の意味：Functional＝関数の／Programming＝プログラムを作ること

#### 並列処理プログラミング（へいれつしょりぷろぐらみんぐ / Parallel Programming）

- 意味：処理を複数のスレッドやプロセッサに分けて、同時に実行させるプログラムの作り方
- ポイント：速くなるが、同じデータを同時に書き換える競合やデッドロックに注意する
- 語の意味：Parallel＝並列の／Programming＝プログラムを作ること

### Webアプリケーションの方式

#### レスポンシブWebデザイン（Responsive Web Design）

- 意味：一つのHTML文書を、パソコン・タブレット・スマートフォンなど画面の大きさに合わせて見やすく表示する作り方
- ポイント：CSSのメディアクエリで、画面の幅ごとにレイアウトを切り替える。端末ごとに別のページを用意するのとは違う
- 例：R6秋 問50（画面の大きさに合わせて表示するために使うのはメディアクエリ）
- 語の意味：Responsive＝反応する／Web Design＝Webの設計

#### メディアクエリ（Media Queries）

- 意味：CSSで、画面の幅や向きなどの条件を書き、条件に合うときだけ適用するスタイルを決める機能
- ポイント：レスポンシブWebデザインを実現するしくみ。端末の種類を名乗る情報はUser-Agent
- 例：R6秋 問50（正解）
- 語の意味：Media＝表示媒体／Queries＝問い合わせ

#### User-Agent（ゆーざーえーじぇんと）

- 意味：Webブラウザがサーバに送る、ブラウザの種類やOSなどを名乗る情報
- ポイント：サーバ側で端末ごとに別のページを返すのに使えるが、一つのHTML文書で表示を合わせるのはメディアクエリ
- 例：R6秋 問50（誤りの選択肢）
- 語の意味：User＝利用者／Agent＝代理人

#### PWA（ぴーだぶりゅーえー / Progressive Web Apps）

- 意味：ブラウザのサービスワーカーの機能を使い、オフラインでも起動でき、裏でデータを同期するなど、スマートフォンのアプリのように使えるWebアプリケーション
- ポイント：インストールしなくてもホーム画面から起動できる。サーバでプログラムを呼び出す昔の方式はCGI
- 例：R7秋 問49（正解はエ。アはCGI、イはセマンティックWeb、ウはマッシュアップ）
- 語の意味：Progressive＝前進的な／Web＝Web／Apps＝アプリケーション

#### サービスワーカー（Service Worker）

- 意味：Webページとは別に、ブラウザの裏で動くスクリプト。通信をとりもってキャッシュから返したり、プッシュ通知を受けたりする
- ポイント：PWAでオフラインで動かすための中心のしくみ
- 語の意味：Service＝サービス／Worker＝働き手

#### CGI（しーじーあい / Common Gateway Interface）

- 意味：Webブラウザからの要求に応じて、Webサーバがサーバ上のプログラムを呼び出し、その結果をブラウザに返すしくみ
- ポイント：動的なWebページを作る古くからの方式。ブラウザ側でアプリのように動かすのはPWA
- 例：R7秋 問49（アの説明）
- 語の意味：Common＝共通の／Gateway＝出入口／Interface＝接点

#### マッシュアップ（Mashup）

- 意味：他のサービスが公開しているWeb APIの機能を組み合わせて、新しいWebサービスを作ること
- ポイント：地図のAPIと店の情報を組み合わせる、など。自分ですべて作らない
- 例：R7秋 問49・R6秋 問50（誤りの選択肢）
- 語の意味：Mashup＝混ぜ合わせ

#### セマンティックWeb（Semantic Web）

- 意味：Webページの要素に、その意味を表すメタデータを付けて、コンピュータが自動で情報を集めたり加工したりできるようにする考え方
- ポイント：人が読む見た目ではなく、機械が意味を理解できるようにする
- 例：R7秋 問49（イの説明）
- 語の意味：Semantic＝意味の／Web＝Web

### ユニットテストの準備

#### ユニットテスト（単体テスト / Unit Test）

- 意味：一つのプログラム（ソフトウェアユニット、モジュール）が仕様どおりに動くかを確かめるテスト
- ポイント：主にホワイトボックステストで行う。モジュールを組み合わせて確かめるのは結合テスト（ソフトウェア統合テスト）
- 語の意味：Unit＝単位／Test＝試験

#### テストケース（Test Case）

- 意味：テストで与える入力データ・実行の条件・期待する結果をひと組にしたもの
- ポイント：ホワイトボックスなら網羅率、ブラックボックスなら同値分割や限界値分析で作る
- 語の意味：Test＝試験／Case＝場合

#### テストオラクル（Test Oracle）

- 意味：テストの結果が正しいかどうかを判定するための、期待する結果やその求め方
- ポイント：結果を見ても正しいか分からなければテストにならない。仕様書・別のプログラム・手計算などが元になる
- 語の意味：Test＝試験／Oracle＝神のお告げ

#### テストデータジェネレーター（Test Data Generator）

- 意味：テストで使う入力データを、条件を指定して自動的に作るツール
- ポイント：大量のデータや、境目の値をまとめて作れる
- 語の意味：Test Data＝試験用データ／Generator＝作り出すもの

#### テスト自動化（てすとじどうか / Test Automation）

- 意味：テストの実行と結果の判定を、ツールやスクリプトで自動的に行うこと
- ポイント：何度も繰り返す回帰テストで特に効く。テストを先に書くテスト駆動開発（13）とも相性がよい
- 語の意味：Test＝試験／Automation＝自動化

### ホワイトボックステスト

#### ホワイトボックステスト（White-box Test）

- 意味：プログラムの中の作り（命令や分岐）に着目して、どの道筋を通ったかで確かめるテスト
- ポイント：命令網羅・判定条件網羅・条件網羅などの基準で作る。仕様に書かれていない機能の漏れは見つけにくい
- 語の意味：White box＝中の見える箱／Test＝試験

#### 命令網羅（めいれいもうら / Statement Coverage, C0）

- 意味：プログラムの中のすべての命令を、少なくとも1回は実行するようにテストケースを作る基準（ホワイトボックステストの網羅基準の一つ）
- ポイント：最も弱い基準。何もしない側の分岐（命令のない側）は通らなくてもよい
- 例：R3春 問48（3つに分かれる判定が3つ並ぶ流れ図で、最少のテストケース数は3）
- 語の意味：Statement＝命令文／Coverage＝網羅

#### 判定条件網羅（はんていじょうけんもうら / Decision Coverage, C1）

- 意味：すべての判定で、真になる分岐と偽になる分岐の両方を、少なくとも1回は通るようにする基準（ホワイトボックステストの網羅基準の一つ）。分岐網羅ともいう
- ポイント：命令網羅より強い。「AかつB」の判定でも、判定全体の真と偽だけを見て、AとBそれぞれの真偽までは問わない
- 例：R4春 問47（A=1,B=0 と A=1,B=1 の2ケースで、二つの判定の真偽をすべて通る）
- 語の意味：Decision＝判定／Coverage＝網羅

#### 条件網羅（じょうけんもうら / Condition Coverage）

- 意味：判定の中の個々の条件（「AかつB」のAとB）が、それぞれ真と偽の両方をとるようにする基準（ホワイトボックステストの網羅基準の一つ）
- ポイント：条件ごとの真偽はそろっても、判定全体が真にならない組合せもありうる。それを補うのが判定条件／条件網羅
- 語の意味：Condition＝条件／Coverage＝網羅

#### 判定条件／条件網羅（はんていじょうけん・じょうけんもうら / Decision/Condition Coverage）

- 意味：判定条件網羅と条件網羅の両方を満たすようにする基準（ホワイトボックステストの網羅基準の一つ）
- ポイント：判定全体の真偽と、中の条件それぞれの真偽の両方をそろえる
- 語の意味：Decision＝判定／Condition＝条件／Coverage＝網羅

#### 複数条件網羅（ふくすうじょうけんもうら / Multiple Condition Coverage）

- 意味：判定の中の条件の真偽の組合せを、すべて試すようにする基準（ホワイトボックステストの網羅基準の一つ）
- ポイント：判定ごとに見るので、条件が2つなら4通り、3つなら8通り。判定をまたいだ通り道の組合せ全部を試すのは経路組合せ網羅
- 語の意味：Multiple＝複数の／Condition＝条件／Coverage＝網羅

#### 経路組合せ網羅（けいろくみあわせもうら / Path Coverage）

- 意味：プログラムの入口から出口までの、すべての通り道の組合せを試す基準（ホワイトボックステストの網羅基準の一つ）
- ポイント：最も強いが、判定が増えるとケースが爆発的に増えるので、全部は現実的でないことが多い
- 語の意味：Path＝経路／Coverage＝網羅

#### 網羅率（もうらりつ / Coverage）

- 意味：テストで通った命令や分岐の数を、全体の数で割った割合。カバレージ（カバレッジ）ともいう
- ポイント：C0（命令網羅）とC1（分岐網羅）で別々に求める。R4秋 問48 では、命令は全部通るが2つの判定で片方の分岐しか通らず、C1は10分岐中8分岐で80%
- 例：R4秋 問48（C0 100%・C1 80%）
- 語の意味：Coverage＝覆っている範囲

### ブラックボックステスト

#### ブラックボックステスト（Black-box Test）

- 意味：プログラムの中の作りは見ずに、仕様書をもとに入力と出力の関係だけで確かめるテスト
- ポイント：同値分割・限界値分析・原因結果グラフなどで作る。中の作りに着目するのはホワイトボックステスト
- 語の意味：Black box＝中の見えない箱／Test＝試験

#### 同値分割（どうちぶんかつ / Equivalence Partitioning）

- 意味：入力の値を、同じ扱いになる集まり（同値クラス）に分け、各クラスから代表の値を1つずつテストする技法（ブラックボックステストの技法）
- ポイント：有効なクラス（正しく処理される値）と無効なクラス（エラーになる値）の両方から選ぶ。シラバスでは「同値分析法」
- 語の意味：Equivalence＝同等／Partitioning＝分割

#### 限界値分析（げんかいちぶんせき / Boundary Value Analysis）

- 意味：同値クラスの境目の値と、そのすぐ外側の値をテストする技法（ブラックボックステストの技法）
- ポイント：境目は誤り（＜と≦の取り違えなど）が起きやすい。1〜100が有効なら 0・1・100・101 を試す。クラスの代表だけなら同値分割
- 例：R5秋 問46（ファジングを問う問題の誤りの選択肢）
- 語の意味：Boundary＝境界／Value＝値／Analysis＝分析

#### 原因結果グラフ（げんいんけっかぐらふ / Cause-Effect Graph）

- 意味：入力の条件（原因）と出力（結果）の論理的な関係をグラフで表し、それを決定表に直してテストケースを作る技法（ブラックボックステストの技法）
- ポイント：条件の組合せが複雑なときに、漏れなくケースを作れる
- 語の意味：Cause＝原因／Effect＝結果／Graph＝図

#### 実験計画法（じっけんけいかくほう / Design of Experiments）

- 意味：直交表を使って、たくさんの因子（設定の項目）の組合せを、少ない回数で偏りなく調べる技法（ブラックボックステストの技法）
- ポイント：全部の組合せを試さずに、2つずつの組合せが一通りは出るようにする。ペアワイズ法も似た考え方
- 例：R5秋 問46（誤りの選択肢）
- 語の意味：Design＝計画／of Experiments＝実験の

#### ドメイン分析テスト（どめいんぶんせきてすと / Domain Analysis Testing）

- 意味：限界値分析を広げて、複数の入力の値がとりうる範囲（ドメイン）の境界を、組み合わせて調べるテスト技法（ブラックボックステストの技法）
- ポイント：限界値分析を、複数の変数が関係する場合に広げたもの。シラバス Ver.7.2 の用語例
- 語の意味：Domain＝領域／Analysis＝分析

### 欠陥の数を推定する

#### エラー埋込み法（えらーうめこみほう / Error Seeding）

- 意味：わざと決まった数のエラーをプログラムに埋め込んでからテストし、埋め込んだエラーの見つかった割合から、本当のエラーの総数と残りの数を推定する方法
- ポイント：真のエラーも、埋め込んだエラーと同じ割合で見つかると考える。総数＝見つかった真のエラー数 ÷ 埋め込みエラーの発見率
- 例：R7秋 問48（48個埋め込み36個発見、真のエラー42個発見 → 総数56個、残り14個）
- 語の意味：Error＝誤り／Seeding＝種をまくこと

#### ミューテーションテスト（Mutation Testing）

- 意味：プログラムを少しだけ変えた変異版（ミュータント）を作り、今のテストケースでその変化を見つけられるかで、テストの質を評価する方法
- ポイント：テストケースの「見つける力」を測る。見つけられない変異が多ければテストが弱い
- 語の意味：Mutation＝突然変異／Testing＝試験

#### バグ曲線（ばぐきょくせん / Bug Curve）

- 意味：テストの進み具合（時間やテスト項目の消化数）を横軸、見つかったバグの累積数を縦軸にした曲線。代表的なモデルにゴンペルツ曲線がある。信頼度成長曲線ともいう
- ポイント：最初はゆっくり、途中で急に増え、最後は伸びなくなるS字の形になる。伸びが止まればバグが収束したと判断する材料になる
- 語の意味：Bug＝不具合／Curve＝曲線

#### ゴンペルツ曲線（ごんぺるつきょくせん / Gompertz Curve）

- 意味：ソフトウェア信頼度成長モデルで使う、累積バグ数が初めゆっくり増え、急に増え、やがて飽和するS字形の曲線（バグ曲線の代表的なモデル）
- ポイント：伸びが止まって水平に近づくことが、テストでバグが収束したと判定する根拠の一つになる。同じS字形のロジスティック曲線もよく使う
- 例：R6春 問47（S字形のウが正解。下に凸で増え続けるもの、直線、最初から上に凸のものは誤り）
- 語の意味：Gompertz＝考案者の名前／Curve＝曲線

#### 欠陥密度（けっかんみつど / Defect Density）

- 意味：見つかった欠陥の数を、プログラムの規模（1,000行あたりなど）で割った値。バグ密度ともいう
- ポイント：多すぎても少なすぎても注意。少なすぎるのは、テストが足りない可能性もある。「運用中の不具合件数÷規模」は保守性ではなく信頼性の指標（R7春 問47 のア）
- 語の意味：Defect＝欠陥／Density＝密度

#### テスト密度（てすとみつど / Test Density）

- 意味：作ったテストケースの数を、プログラムの規模で割った値
- ポイント：テストの量が足りているかの目安。欠陥密度と組み合わせて品質を判断する
- 語の意味：Test＝試験／Density＝密度

## 12-4 統合・テスト

### まとめ表

**テストの段階（V字モデルの右側）**

| テスト | 何に照らして確かめるか | 主な担当 |
| :-: | :-: | :-: |
| ユニットテスト（単体テスト） | ソフトウェアユニット（プログラム）の仕様 | 開発者 |
| ソフトウェア統合テスト（結合テスト） | ソフトウェア設計（モジュールのつながり） | 開発者 |
| ソフトウェア検証テスト・システム検証テスト | ソフトウェア要件・システム要件 | 開発者（供給者） |
| 受入れテスト（妥当性確認テスト） | 利用者の業務で本当に使えるか | 利用者（取得者） |

**統合の順序と、代わりに使うプログラム**

| 進め方 | 先に作るもの | 足りない部分の代わり |
| :-: | :-: | :-: |
| トップダウンテスト | 上位のモジュール | スタブ（下位の代わり） |
| ボトムアップテスト | 下位のモジュール | ドライバ（上位の代わり） |
| サンドイッチテスト | 上位と下位を同時に | スタブとドライバの両方 |
| ビッグバンテスト | 全部を一度に結合 | 使わない（不具合の場所を特定しにくい） |

### 統合テストの進め方

#### ソフトウェア統合テスト（そふとうぇあとうごうてすと / Software Integration Test）

- 意味：テスト済みのモジュールを組み合わせて、モジュールどうしのインタフェースやデータの受け渡しが正しいかを確かめるテスト。結合テストともいう
- ポイント：ソフトウェア設計で決めたテスト仕様に従って行う。組み合わせる順序でトップダウン・ボトムアップなどがある
- 語の意味：Software＝ソフトウェア／Integration＝統合／Test＝試験

#### トップダウンテスト（Top-down Test）

- 意味：上位のモジュールから順に結合していくテスト。まだできていない下位のモジュールの代わりにスタブを使う
- ポイント：主要な流れを早く確かめられる。下位から積み上げるのはボトムアップテスト
- 例：R4秋 問46（誤りの選択肢。机上でシミュレートする手法ではない）
- 語の意味：Top-down＝上から下へ／Test＝試験

#### ボトムアップテスト（Bottom-up Test）

- 意味：下位のモジュールから順に結合していくテスト。まだできていない上位のモジュールの代わりにドライバを使う
- ポイント：部品を早く確実に確かめられるが、全体の流れの確認は最後になる
- 語の意味：Bottom-up＝下から上へ／Test＝試験

#### サンドイッチテスト（Sandwich Test）

- 意味：上位からのトップダウンと下位からのボトムアップを同時に進め、中間で合わせるテスト
- ポイント：スタブとドライバの両方を使う。期間を短くできる
- 例：R4秋 問46（誤りの選択肢）
- 語の意味：Sandwich＝はさむこと／Test＝試験

#### ビッグバンテスト（Big Bang Test）

- 意味：単体テストを終えたすべてのモジュールを、一度に結合してテストする方法
- ポイント：準備は少ないが、不具合が出たときにどこが原因か特定しにくい
- 語の意味：Big Bang＝大爆発（一度に全部）／Test＝試験

#### スタブ（Stub）

- 意味：結合テストで、まだできていない下位のモジュールの代わりに置く仮のプログラム。呼ばれたら決まった値を返す
- ポイント：トップダウンテストで使う。上位のモジュールの代わりに下位を呼び出すのはドライバ
- 語の意味：Stub＝切り株（残りの部分）

#### ドライバ（Driver）

- 意味：結合テストで、まだできていない上位のモジュールの代わりに置き、テストするモジュールを呼び出して引数を渡す仮のプログラム
- ポイント：ボトムアップテストで使う。下位の代わりはスタブ
- 語の意味：Driver＝動かすもの

#### テストベッド（Test Bed）

- 意味：テストを行うための、ハードウェア・ソフトウェア・データなどを整えた環境
- ポイント：本番に近い環境を作って確かめる。代わりのプログラムそのもの（スタブ・ドライバ）とは違う
- 語の意味：Test＝試験／Bed＝台・土台

### テストの種類

#### 機能テスト（きのうてすと / Functional Test）

- 意味：要件定義で決めた機能が、仕様どおりに動くかを確かめるテスト
- ポイント：何ができるか（機能要件）を確かめる。速さや負荷への強さなど非機能要件を確かめるのは性能テスト・負荷テストなど
- 語の意味：Functional＝機能の／Test＝試験

#### 性能テスト（せいのうてすと / Performance Test）

- 意味：レスポンスタイムやスループットが、性能要件を満たしているかを確かめるテスト
- ポイント：ふだんの量の処理で、決めた速さが出るか。限界を超える量をかけるのは負荷テスト
- 語の意味：Performance＝性能／Test＝試験

#### 負荷テスト（ふかてすと / Load Test）

- 意味：大量のデータや同時アクセスなどの負荷をかけて、システムが耐えられるか、どこまで処理できるかを確かめるテスト
- ポイント：限界を超える負荷をかけて、壊れ方や回復を見るのをストレステストともいう。少数のデータで速さを見るのは性能テスト
- 例：R5秋 問46（誤りの選択肢。脆弱性を見つけるテストではない）
- 語の意味：Load＝負荷／Test＝試験

#### 回帰テスト（かいきてすと / Regression Test）

- 意味：プログラムを修正・変更した後に、変更していない部分に悪い影響が出ていないかを確かめるテスト。リグレッションテスト・退行テストともいう
- ポイント：保守のときに特に大事。何度も行うので自動化することが多い
- 語の意味：Regression＝後戻り（退行）／Test＝試験

#### セキュリティテスト（Security Test）

- 意味：不正アクセスや情報漏えいなどに対して、セキュリティ要件どおりに守られているかを確かめるテスト
- ポイント：脆弱性検査やペネトレーションテスト、ファジングなどがある
- 語の意味：Security＝安全／Test＝試験

#### ファジング（Fuzzing）

- 意味：問題を起こしそうな、ありえない形のデータや大量のデータを入力して、プログラムの挙動を監視し、脆弱性を見つけるテスト手法。セキュリティテストの一つ
- ポイント：シラバスではソフトウェア検証テストの用語例。11 セキュリティでも出る（R4秋 問45・R5秋 問46 など）
- 語の意味：Fuzz＝けば立ち（でたらめなデータ）／ing＝すること

#### 探索的テスト（たんさくてきてすと / Exploratory Testing）

- 意味：あらかじめ細かいテストケースを作らず、テスト担当者が動かしながら学び、次に何を試すかをその場で考えて進めるテスト
- ポイント：仕様書から作ったケースでは見つけにくい不具合を見つけやすい。担当者の経験に左右される
- 語の意味：Exploratory＝探検の／Testing＝試験

#### カオスエンジニアリング（Chaos Engineering）

- 意味：本番環境の分散システムに、サーバの停止や通信の遅れなどの障害をわざと起こす実験をして、弱いところを見つける手法
- ポイント：5つの原則は「定常状態の振る舞いの仮説を立てる」「実世界の事象を多様化させる」「本番環境で実験を行う」「継続的に実行できるよう実験を自動化する」「影響範囲を局所化する」
- 例：R7春 問49（残りの二つの原則は「本番環境で実験を行う」「影響範囲を局所化する」）
- 語の意味：Chaos＝混沌／Engineering＝工学

### 検証と妥当性確認

#### ソフトウェア検証テスト（そふとうぇあけんしょうてすと / Software Qualification Test）

- 意味：完成したソフトウェアが、ソフトウェア要件定義で決めた要件どおりにできているかを確かめる、検証のためのテスト
- ポイント：開発者（供給者）が行う。機能テストに加え、性能テスト・負荷テスト・セキュリティテスト・回帰テストなどを含む
- 語の意味：Software＝ソフトウェア／Qualification＝適格性の確認／Test＝試験

#### システム検証テスト（しすてむけんしょうてすと / System Qualification Test）

- 意味：ソフトウェア・ハードウェア・手作業を全部統合したシステムが、システム要件定義で決めた要件どおりかを確かめる、検証のためのテスト
- ポイント：システム要件に照らして確かめる。利用者の業務で本当に役立つかを確かめるのは妥当性確認テスト・受入れテスト
- 語の意味：System＝システム／Qualification＝適格性の確認／Test＝試験

#### 検証（けんしょう / Verification）

- 意味：作ったものが、仕様や要件のとおりに正しく作られているかを確かめること
- ポイント：「正しく作ったか」。利用者が本当に必要なものを作ったかを確かめるのは妥当性確認
- 語の意味：Verification＝正しさの確認

#### 妥当性確認（だとうせいかくにん / Validation）

- 意味：作ったものが、利用者の目的や実際の使い方に照らして、本当に役に立つかを確かめること
- ポイント：「正しいものを作ったか」。仕様どおりかを確かめるのは検証。妥当性確認テストは利用者側の環境で行う
- 語の意味：Validation＝妥当であることの確認

#### 使用性テスト（しようせいてすと / Usability Test）

- 意味：実際の利用者に操作してもらい、迷う所や時間のかかる所を観察して、使いやすさを評価するテスト。妥当性確認テストの技法の一つ
- ポイント：妥当性確認テストの技法の一つ。シラバスの用語例
- 語の意味：Usability＝使いやすさ／Test＝試験

#### ベータテスト（Beta Test）

- 意味：完成に近い製品を、社外の一部の利用者に試しに使ってもらい、意見や不具合を集めるテスト。妥当性確認のための試行利用の一つ
- ポイント：開発元の中で行う試しの利用はアルファテスト。シラバスでは「ソフトウェアの試行利用」の一つ
- 語の意味：Beta＝ギリシャ文字の2番目（2段階目）／Test＝試験

## 12-5 導入・受入れ支援

### まとめ表

**移行の方式**

| 方式 | やり方 | よい点 | 弱い点 |
| :-: | :-: | :-: | :-: |
| 一斉移行 | ある日に全部を新システムへ切り替える | 期間が短く、新旧の二重管理がない | 失敗したときの影響が大きい |
| 段階移行 | 業務や拠点ごとに順に切り替える | 失敗の影響が小さい | 移行期間が長く、新旧の連携が必要 |
| 並行運用移行 | 新旧を同時に動かし、結果を比べてから切り替える | 安全で、旧に戻せる | 二重の運用で手間と費用がかかる |
| パイロット移行 | 一部の部門で先に試し、問題がなければ全体へ | 問題を小さい範囲で見つけられる | 全体への展開に時間がかかる |

**リリース・デプロイの手法（R7春 問46）**

| 手法 | やり方 | 見分けるキーワード |
| :-: | :-: | :-: |
| ブルーグリーンデプロイメント | 本番環境を2つ用意し、新版を入れた方へロードバランサーで一気に切り替える | 環境が二つ、すぐ切り戻せる |
| カナリアリリース | 新版を一部の利用者だけに先に出し、問題がなければ広げる | 一部の利用者から |
| ローリングアップデート | 複数のサーバを1台ずつ順に新版にする | 1台ずつ順番に |

### 移行の方式

#### 一斉移行（いっせいいこう / Big Bang Migration）

- 意味：決めた日に、すべての業務やデータを旧システムから新システムへ一度に切り替える移行方式
- ポイント：移行期間が短く、新旧を同時に運用する手間がないが、失敗したときの影響が大きい。移行リハーサルを十分に行う
- 語の意味：Big Bang＝一度に全部／Migration＝移行

#### 段階移行（だんかいいこう / Phased Migration）

- 意味：業務・機能・拠点などの単位に分けて、順番に新システムへ切り替える移行方式。最初の一部だけを試行にするのはパイロット移行
- ポイント：一度に移す範囲が小さいので、問題が起きても影響が小さい。その間は新旧のシステムをつなぐ仕組みが必要
- 語の意味：Phased＝段階的な／Migration＝移行

#### 並行運用（へいこううんよう / Parallel Operation）

- 意味：新旧のシステムを一定期間同時に動かし、結果を比べて問題がないことを確かめてから旧システムを止める移行方式
- ポイント：最も安全で、問題があれば旧に戻せるが、二重に入力・運用するので手間と費用が大きい。シラバスでは「並行稼働対応」
- 語の意味：Parallel＝並行の／Operation＝運用

#### パイロット移行（ぱいろっといこう / Pilot Migration）

- 意味：一部の部門や拠点だけで先に新システムを使ってみて、問題がないことを確かめてから全体に広げる移行方式（段階移行の最初を試行にした形）
- ポイント：段階移行の最初を「試し」として行う形。一部の利用者に新版を先に出すカナリアリリースと考え方が近い
- 語の意味：Pilot＝試験的な／Migration＝移行

#### 移行リハーサル（いこうりはーさる / Migration Rehearsal）

- 意味：本番の移行の前に、同じ手順でデータの移し替えや切替えを試し、時間や問題点を確かめること
- ポイント：かかる時間を測って本番の計画に生かす。うまくいかないときに元に戻す手順も確かめる
- 語の意味：Migration＝移行／Rehearsal＝予行演習

### リリースとデプロイの手法

#### ブルーグリーンデプロイメント（Blue-Green Deployment）

- 意味：本番の稼働環境を二つ用意し、一方で今のバージョンを動かしたまま他方をバージョンアップし、ロードバランサーなどで利用者の向き先を切り替える手法
- ポイント：切替えのダウンタイムが短く、不具合があればすぐ元の環境に切り戻せる
- 例：R7春 問46（正解。ホットスタンバイ・ホットスワップ・ローリングアップデートは誤り）
- 語の意味：Blue・Green＝二つの環境の呼び名／Deployment＝配置・展開

#### カナリアリリース（Canary Release）

- 意味：新しいバージョンを、まず一部の利用者だけに提供して様子を見て、問題がなければ対象を広げていく手法
- ポイント：炭鉱でカナリアを先に入れて危険を確かめた話から。環境を二つ用意して全部を切り替えるのはブルーグリーンデプロイメント
- 語の意味：Canary＝カナリア（鳥）／Release＝公開

#### ローリングアップデート（Rolling Update）

- 意味：同じ役割を持つ複数のサーバを、1台ずつ順番にサービスから外して新しいバージョンにしていく手法
- ポイント：全体は止めずに更新できるが、途中は新旧のバージョンが混ざって動く。環境を丸ごと二つ用意するのはブルーグリーンデプロイメント
- 例：R7春 問46（誤りの選択肢）
- 語の意味：Rolling＝順に転がしていく／Update＝更新

#### ホットスタンバイ（Hot Standby）

- 意味：予備の機械を、すぐに引き継げる状態で起動したまま待機させておく冗長化の方式
- ポイント：障害に備える仕組みで、バージョンアップの手法ではない（R7春 問46 の誤りの選択肢）。04 システム構成要素の用語
- 語の意味：Hot＝動いている状態の／Standby＝待機

#### ホットスワップ（Hot Swap）

- 意味：機械の電源を入れたまま、部品（ディスクなど）を取り替えられること
- ポイント：ハードウェアの交換の話で、ソフトウェアのバージョンアップの手法ではない（R7春 問46 の誤りの選択肢）
- 語の意味：Hot＝動いたままの／Swap＝取り替え

### 受入れと納品

#### 受入れテスト（うけいれてすと / Acceptance Test）

- 意味：発注者（取得者）が、納品されたシステムが要件を満たし、業務で使えるかを確かめて受け取るかどうかを決めるテスト。合格すると検収になる
- ポイント：取得者が主体で、供給者は支援する。合格すると検収になる。開発者が要件どおりかを確かめるのはシステム検証テスト
- 語の意味：Acceptance＝受け入れ／Test＝試験

#### 受入れ基準（うけいれきじゅん / Acceptance Criteria）

- 意味：受入れテストで、どうなれば合格として受け取るかを、あらかじめ決めておいた基準
- ポイント：曖昧だと、納品のときにもめる。契約のときに供給者と取得者で合意しておく
- 語の意味：Acceptance＝受け入れ／Criteria＝基準

#### 検収（けんしゅう / Inspection and Acceptance）

- 意味：納品された物が、注文どおりの内容と品質になっているかを確かめて、受け取ること（受入れテストの合格を受けた手続）
- ポイント：検収が終わると、代金の支払いや所有の移転などの手続が進むのが普通。何をもって合格とするかは検収基準で決める
- 語の意味：Inspection＝検査／Acceptance＝受け入れ

#### 運用テスト（うんようてすと / Operational Test）

- 意味：本番と同じ環境と手順で、利用者や運用担当者が実際の業務の流れに沿ってシステムを動かし、運用できるかを確かめるテスト
- ポイント：シラバスでは妥当性確認テストの「運用操作テスト」。マニュアルや運用手順の確認も含む
- 語の意味：Operational＝運用の／Test＝試験

#### 利用者マニュアル（りようしゃまにゅある / User Manual）

- 意味：利用者が業務の中でシステムを操作する手順や、運用の手順をまとめた文書。利用者用文書類
- ポイント：設計の段階で暫定版を作り、開発が進むのに合わせて更新する。チュートリアルやオンラインヘルプもその一つ
- 語の意味：User＝利用者／Manual＝手引書

### 教育訓練

#### 教育訓練計画（きょういくくんれんけいかく / Training Plan）

- 意味：新しいシステムを使う人に向けて、教育の目的・内容・対象者・時期・方法・評価のしかたを決めた計画
- ポイント：供給者が支援し、取得者が体制を整えて行う。運用開始の前だけでなく、継続的な教育も計画する
- 語の意味：Training＝訓練／Plan＝計画

#### e-Learning（いーらーにんぐ）

- 意味：パソコンやスマートフォンなどの情報機器とネットワークを使って学ぶ方法の総称（WBTなどを含む）
- ポイント：好きな時間と場所で学べ、学習の記録も残せる。Webブラウザで学ぶ形をWBTという
- 語の意味：e＝electronic（電子の）／Learning＝学習

#### WBT（だぶりゅーびーてぃー / Web Based Training）

- 意味：Webブラウザで教材を見て学ぶ形のe-Learning
- ポイント：教材をサーバで一元管理でき、更新しやすい。CD-ROMなどに入れて配るのはCBT（Computer Based Training）
- 語の意味：Web Based＝Webを使った／Training＝訓練

#### カークパトリックの4段階モデル（Kirkpatrick Model）

- 意味：教育の効果を、反応（満足したか）・学習（身に付いたか）・行動（仕事で使っているか）・結果（業績が上がったか）の4段階で評価する考え方
- ポイント：アンケートで分かるのは1段階目だけ。仕事の行動や成果まで見て効果を測る
- 語の意味：Kirkpatrick＝提唱者の名前／Model＝模型

## 12-6 保守・廃棄

### まとめ表

**保守のタイプ（JIS X 0161の分類。R4春 問48・R5秋 問48）**

| タイプ | 目的 | タイミング | 例 |
| :-: | :-: | :-: | :-: |
| 是正保守 | 見つかった問題を直す | 問題が起きた後 | 障害の原因の修正 |
| 予防保守 | 問題になる前に、潜在的な欠陥を直す | 問題が起きる前 | 不具合の芽を事前に修正 |
| 適応保守 | 環境の変化に合わせて使い続けられるようにする | 環境が変わったとき | OSの更新・法改正への対応 |
| 完全化保守 | 性能や保守性をよくする・文書を整える | 問題は起きていない | 仕様書とソースの不整合を直す |

- 是正保守と予防保守は「直す」（訂正）、適応保守と完全化保守は「よくする」（改良）。予防保守と完全化保守はどちらも問題が起きる前だが、予防保守は「欠陥」を直し、完全化保守は「品質」をよくする

### 保守のタイプ

#### 是正保守（ぜせいほしゅ / Corrective Maintenance）

- 意味：運用中に見つかった障害や問題を、原因を突き止めて直す保守。計画外で一時的に急いで行うものは緊急保守
- ポイント：問題が「起きた後」に直す。起きる前に潜在的な欠陥を直すのは予防保守
- 例：R4春 問48（誤りの選択肢。問題は発生していない）
- 語の意味：Corrective＝正す／Maintenance＝保守

#### 予防保守（よぼうほしゅ / Preventive Maintenance）

- 意味：運用中のソフトウェアの潜在的な欠陥を、問題として現れる前に見つけて直す保守
- ポイント：問題が起きる前に「欠陥」を直す。問題はないが品質をよくするのは完全化保守
- 語の意味：Preventive＝予防の／Maintenance＝保守

#### 適応保守（てきおうほしゅ / Adaptive Maintenance）

- 意味：OSの更新・ハードウェアの変更・法律や制度の改正など、まわりの環境の変化に合わせて、使い続けられるように変える保守
- ポイント：ソフトウェア自体に問題はないが、環境が変わったから変える
- 語の意味：Adaptive＝適応する／Maintenance＝保守

#### 完全化保守（かんぜんかほしゅ / Perfective Maintenance）

- 意味：問題は起きていないが、性能や保守性をよくしたり、文書を整えたりするための保守
- ポイント：リバースエンジニアリングで、ソースコードとずれた仕様書を作り直すのは完全化保守（R4春 問48・R5秋 問48）
- 例：R4春 問48・R5秋 問48（同じ問題が2回出た）
- 語の意味：Perfective＝完全にする／Maintenance＝保守

#### 緊急保守（きんきゅうほしゅ / Emergency Maintenance）

- 意味：システムの運用を続けるために、計画外で一時的に急いで行う修正（後で正式に是正保守として直す）
- ポイント：後で正式な是正保守として手順を踏んで直すのが普通
- 語の意味：Emergency＝緊急の／Maintenance＝保守

### 保守の形態

#### オンサイト保守（おんさいとほしゅ / On-site Maintenance）

- 意味：保守の担当者が、利用者のシステムが置いてある場所まで出向いて行う保守
- ポイント：ハードウェアの交換など、現地でしかできない作業に向く。通信回線を使って離れた所から行うのは遠隔保守
- 語の意味：On-site＝現地で／Maintenance＝保守

#### 遠隔保守（えんかくほしゅ / Remote Maintenance）

- 意味：保守の担当者が、通信回線を使って離れた場所から、システムの監視や修正を行う保守。リモート保守
- ポイント：すぐに対応できるが、接続口が不正アクセスの入口にならないように対策が必要
- 語の意味：Remote＝離れた／Maintenance＝保守

#### 保守契約（ほしゅけいやく / Maintenance Contract）

- 意味：保守の範囲・対応時間・費用・責任などを、利用者と保守を行う会社の間で決めた契約
- ポイント：サービスレベル（いつまでに対応するかなど）も決めておく。保守要件をもとに結ぶ
- 語の意味：Maintenance＝保守／Contract＝契約

#### 日常点検（にちじょうてんけん / Daily Inspection）

- 意味：毎日や決まった間隔で、システムやハードウェアの状態を確かめ、異常の兆しを見つける作業
- ポイント：異常を早く見つけて、大きな障害を防ぐ
- 語の意味：Daily＝毎日の／Inspection＝点検

### 保守の作業

#### リバースエンジニアリング（Reverse Engineering）

- 意味：できあがったソフトウェアのプログラムを解析して、その仕様や設計を明らかにすること
- ポイント：作る方向（設計 → プログラム）の逆。仕様書がない・古いシステムの保守で使う（R4春 問48）。他社製品の解析は、契約や法律に注意が必要
- 語の意味：Reverse＝逆の／Engineering＝工学

#### フォワードエンジニアリング（Forward Engineering）

- 意味：要件や設計から順にプログラムを作る、ふつうの方向の開発。リバースエンジニアリングで得た設計をもとに作り直すことにも使う
- ポイント：リバースで取り出した設計を直してから、フォワードで作り直すことをまとめてリエンジニアリングという
- 語の意味：Forward＝前向きの／Engineering＝工学

#### リエンジニアリング（Re-engineering）

- 意味：既存のソフトウェアを解析して（リバース）、設計を見直し、新しく作り直す（フォワード）こと
- ポイント：外から見た機能は変えずに作りを新しくするのはリファクタリングで、こちらはもっと大きな作り直し
- 語の意味：Re＝再び／Engineering＝工学

#### リファクタリング（Refactoring）

- 意味：外から見た動作（機能）は変えずに、プログラムの内部の構造を、分かりやすく直しやすい形に整理し直すこと
- ポイント：直した後は回帰テストで動作が変わっていないことを確かめる。アジャイル開発（XP）の実践の一つでもある（13）
- 例：R3秋 問48（「継承の分割」で、形状と線種を別々の継承に分けて関連でつなぐ）
- 語の意味：Re＝再び／factoring＝因数分解（整理）すること

#### 影響分析（えいきょうぶんせき / Impact Analysis）

- 意味：修正の依頼や問題報告に対して、どこを直す必要があり、直すと他のどこに影響が出るかを調べること
- ポイント：双方向の追跡可能性があると調べやすい。修正の選択肢と費用を用意して判断する
- 語の意味：Impact＝影響／Analysis＝分析

### 廃棄

#### 廃棄計画（はいきけいかく / Disposal Plan）

- 意味：不要になったシステムやソフトウェアを、いつ・どのように止めて取り除くかを決めた計画
- ポイント：利用者への通知、新旧環境の並行運用、データの保持と消去の方法などを含める
- 語の意味：Disposal＝処分／Plan＝計画

#### データ消去（でーたしょうきょ / Data Sanitization）

- 意味：廃棄する機器の記憶媒体から、データを読み出せないように消すこと。上書き・磁気消去・物理的な破壊などがある
- ポイント：ファイルの削除やフォーマットだけでは復元できることがある。残す必要のあるデータは消す前に移して保持する
- 語の意味：Data＝データ／Sanitization＝消毒（無害化）

#### 完整性（かんせいせい / Integrity）

- 意味：システムやデータが、欠けたり壊れたり不正に変えられたりせず、正しくそろった状態であること
- ポイント：シラバスでは、保守で修正したソフトウェアや、廃棄後の組織の運用が正しく保たれていることを指す用語
- 語の意味：Integrity＝完全であること

#### 移行評価（いこうひょうか / Migration Evaluation）

- 意味：移行が終わった後に、データや業務が正しく移ったか、計画どおりだったかを確かめて評価すること
- ポイント：結果を検証してから旧環境を止め、旧環境のデータは決めた期間安全に保持する
- 語の意味：Migration＝移行／Evaluation＝評価

#### 問 ap-12-o14

### 12-6 保守・廃棄

#### 問 ap-12-r04h-q48

- 問：問題は発生していないが，プログラムの仕様書と現状のソースコードとの不整合を解消するために，リバースエンジニアリングの手法を使って仕様書を作成し直す。これはソフトウェア保守のどの分類に該当するか。
- ア：完全化保守
- イ：是正保守
- ウ：適応保守
- エ：予防保守
- 正解：ア
- 解説：問題は起きていないが、保守しやすくするために文書を整えるのは完全化保守。保守の分類は「問題が起きた後か前か」と「直すのか、よくするのか」で見分ける。是正保守は起きた問題を直す、予防保守は起きる前に欠陥を直す、適応保守は環境の変化に合わせる、完全化保守は性能や保守性をよくする。
- アの意味：正しい。問題はないが保守性をよくするための保守。
- イの意味：運用中に発生した問題を直す保守。問題が発生していないので当てはまらない。
- ウの意味：OSの更新や法改正など、環境の変化に合わせる保守。環境は変わっていない。
- エの意味：問題として現れる前に、潜在的な欠陥を見つけて直す保守。仕様書の作り直しは欠陥の修正ではない。
- 出典：IPA 令和4年度春期 応用情報技術者試験 午前 問48／令和5年度秋期 午前 問48（同じ問題）

#### 問 ap-12-r07h-q47

#### 問 ap-12-r03a-q48

- 問：図は，ある図形描画ツールのクラス図の一部である。新たな形状や線種で図形を描画する機能の追加を容易にするために，リファクタリング“継承の分割”を行った。変更後のクラス図はどれか。〔クラス図〕図形を継承して三角形と四角形があり、三角形を継承して太線の三角形、四角形を継承して太線の四角形がある。
- ア：図形の下に，細線の三角形・細線の四角形・太線の三角形・太線の四角形の四つのクラスを並べて継承させる。
- イ：図形（その下に三角形・四角形）と，太線の図形（その下に太線の三角形・太線の四角形）の二つの継承の階層を作り，太線の図形から図形へ関連を引く。
- ウ：図形（その下に三角形・四角形）と，線種（その下に太線・細線）の二つの継承の階層を作り，図形から線種へ関連を引く。
- エ：図形の下に三角形・四角形，その下に太線の三角形・太線の四角形を置き，さらに二つとも太線クラスを継承させる。
- 正解：ウ
- 解説：もとのクラス図は「形状」と「線種」という二つの違う観点を一つの継承に混ぜているので、形状か線種を一つ足すたびに組合せの数だけクラスが増える。継承の分割は、観点ごとに継承の階層を分け、関連でつなぐリファクタリング。ウなら形状を足すときは図形の下に、線種を足すときは線種の下に1クラス足せばよい。
- アの意味：形状と線種の組合せを全部クラスにしており、どちらかを足すたびにクラスが掛け算で増える。
- イの意味：太線の図形の下に、また形状ごとのクラスが必要になる。線種を足すたびに形状の数だけクラスが増えるので、分割になっていない。
- ウの意味：正しい。形状と線種を別の継承に分けて関連でつないでいる。
- エの意味：多重継承で太線を足しているが、太線の三角形のような組合せのクラスが残り、形状や線種を足すたびにクラスが増える。
- 出典：IPA 令和3年度秋期 応用情報技術者試験 午前 問48
