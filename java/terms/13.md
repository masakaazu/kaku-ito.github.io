## 13-1 例外の種類とカスタム例外

### まとめ表

| クラス | 種類 | throws や catch が必要か | 例 |
| :-- | :-- | :-- | :-- |
| Error とそのサブクラス | エラー（非チェック） | 不要（ふつうは catch しない） | StackOverflowError・OutOfMemoryError |
| RuntimeException とそのサブクラス | 実行時例外（非チェック） | 不要 | NullPointerException・ArithmeticException・ArrayIndexOutOfBoundsException・ClassCastException・NumberFormatException・IllegalArgumentException・IllegalStateException |
| それ以外の Exception（と Throwable） | チェック例外 | 必要（unreported exception … must be caught or declared to be thrown） | IOException・FileNotFoundException・Exception そのもの |

### 例外クラスの分類

#### 例外（れいがい / exception）

- 意味：プログラムの実行中に起きた、ふつうの流れを続けられない出来事。Java ではオブジェクトとして作られ、throw されて、catch で受け取られるまで呼び出し元へ伝わる
- ポイント：どこでも catch されなければ、スレッド（main）が終わり、例外の名前とスタックトレースが表示される。そのあとの文は実行されない
- 例：`Exception in thread "main" java.lang.IllegalStateException: bad`

#### Throwable（すろーあぶる / java.lang.Throwable）

- 意味：すべての例外とエラーのもとになるクラス。throw できるのは Throwable とそのサブクラスのオブジェクトだけ
- ポイント：直接のサブクラスは Error と Exception。getMessage()・toString()・printStackTrace()・getSuppressed() などのメソッドを持つ
- 例：`catch (Throwable t)` はエラーも含めてすべて受け取る

#### Error（えらー / java.lang.Error）

- 意味：プログラムでは回復できない、深刻な問題を表すクラス
- ポイント：非チェック例外なので throws も catch もいらない。catch (Exception e) では受け取れない（Error は Exception のサブクラスではない）。StackOverflowError（再帰が深すぎる）や OutOfMemoryError など
- 例：`catch (Error e)` なら StackOverflowError を受け取れる

#### Exception（えくせぷしょん / java.lang.Exception）

- 意味：プログラムで受け取って対処することが考えられる問題を表すクラス
- ポイント：Exception と、RuntimeException 以外のサブクラスがチェック例外。catch (Exception e) は RuntimeException も含めて受け取る
- 例：`throw new Exception("x");`

#### RuntimeException（らんたいむえくせぷしょん / java.lang.RuntimeException）

- 意味：プログラムの誤りなどで実行中に起きる例外のもとになるクラス。Exception のサブクラス
- ポイント：RuntimeException とそのサブクラスは非チェック例外で、throws も catch もいらない（書いてもよい）
- 例：`throw new IllegalStateException("bad");`

#### チェック例外（ちぇっくれいがい / checked exception）

- 意味：コンパイラが「処理しているか」を調べる例外。Throwable のうち、RuntimeException 系と Error 系を除いたもの
- ポイント：投げる可能性があるなら、try-catch で受け取るか、メソッドに throws を書かないと unreported exception … must be caught or declared to be thrown。try で投げられないチェック例外を catch すると exception … is never thrown in body of corresponding try statement（Exception と Throwable は例外）
- 例：IOException・FileNotFoundException

#### 非チェック例外（ひちぇっくれいがい / unchecked exception）

- 意味：コンパイラが処理を強制しない例外。RuntimeException 系（実行時例外）と Error 系（エラー）
- ポイント：throws を書かなくても投げられる。catch しなければ、実行時にプログラムが止まる
- 例：NullPointerException・ArithmeticException（/ by zero）

### throw・throws とカスタム例外

#### throw（すろー / throw statement）

- 意味：例外オブジェクトを投げる文
- ポイント：`throw new 例外クラス(…)` と書く。throw の直後に文を書くと unreachable statement のコンパイルエラー
- 例：`throw new IllegalArgumentException("負の値");`

#### throws（すろーず / throws clause）

- 意味：メソッドやコンストラクタが投げる可能性のあるチェック例外を宣言する句
- ポイント：throws を書いたメソッドを呼ぶ側は、その例外を catch するか、自分も throws を書く。main に throws を書くと、例外は JVM に伝わってプログラムが止まる
- 例：`static void read() throws IOException { … }`

#### カスタム例外（かすたむれいがい / custom exception）

- 意味：自分で作った例外クラス。Exception（チェック例外にする）か RuntimeException（非チェック例外にする）を継承する
- ポイント：コンストラクタで super(msg) を呼ぶと、getMessage() でそのメッセージを取り出せる。Exception を継承すると、投げるメソッドに throws が必要
- 例：`class InsufficientFundsException extends Exception { InsufficientFundsException(String msg) { super(msg); } }`

#### getMessage と toString（げっとめっせーじととぅすとりんぐ / getMessage() and toString()）

- 意味：getMessage() は例外の詳しいメッセージを返す。toString() は「クラス名: メッセージ」の形の文字列を返す
- ポイント：メッセージなしで作ると getMessage() は null、toString() はクラス名だけ。toString() のクラス名はパッケージ付き（java.lang.Exception: x）。自分で作ったクラスはパッケージなしならクラス名だけ
- 例：`new Exception("x").toString()` → `java.lang.Exception: x`

## 13-2 try-catch-finally とマルチキャッチ

### まとめ表

| 書き方 | 結果（JDK 17） |
| :-- | :-- |
| try だけ（catch も finally もない） | 'try' without 'catch', 'finally' or resource declarations |
| catch (Exception e) のあとに catch (IOException e) | exception IOException has already been caught |
| try で投げられない IOException を catch | exception IOException is never thrown in body of corresponding try statement |
| try で何も投げなくても catch (Exception e) | OK |
| catch (FileNotFoundException \| IOException e) | Alternatives in a multi-catch statement cannot be related by subclassing |
| マルチキャッチの e に代入 | multi-catch parameter e may not be assigned |
| try で return 1、finally で return 2 | 2 が返る |

### try-catch-finally の流れ

#### try ブロック（とらいぶろっく / try block）

- 意味：例外が起きるかもしれない処理を囲むブロック
- ポイント：途中で例外が起きると、その後の文は飛ばされて catch へ移る。try のあとには catch か finally の少なくとも一方が必要（try-with-resources は除く）
- 例：`try { int x = 10 / 0; System.out.print("B"); }`（B は表示されない）

#### catch ブロック（きゃっちぶろっく / catch clause）

- 意味：try の中で投げられた例外を受け取って処理するブロック
- ポイント：上から順に調べ、最初に型が合った 1 つだけが実行される。サブクラスの catch はスーパークラスの catch より前に書く（逆だと has already been caught）。型が合わなければ受け取られず、呼び出し元へ伝わる
- 例：`catch (ArithmeticException e) { … }`

#### finally ブロック（ふぁいなりぶろっく / finally clause）

- 意味：例外が起きても起きなくても、try（と catch）のあとに必ず実行されるブロック。後片付けに使う
- ポイント：catch で受け取れなかった例外が伝わるときも、その前に実行される。try や catch で return しても、戻る前に finally が動く。finally の中で return すると、その値が返り、try の return や例外は捨てられる。System.exit() で JVM を止めたときは実行されない
- 例：`finally { System.out.print("D"); }`

#### return と finally（りたーんとふぁいなり / return with finally）

- 意味：try で return したときの、戻り値と finally の関係
- ポイント：return の値は finally の前に決まる。finally で基本データ型の変数を変えても戻り値は変わらない（x = 5 にしても 1 が返る）。参照先のオブジェクトを変えると、返ったオブジェクトに反映される（StringBuilder に append すれば見える）
- 例：`try { return x; } finally { x = 5; }` → 1 が返る

#### 例外の伝播（れいがいのでんぱ / exception propagation）

- 意味：catch されなかった例外が、メソッドの呼び出し元へ順にさかのぼって伝わること
- ポイント：途中のどこかの catch で受け取られれば、そこから処理が続く。catch の中で別の例外を投げると、その catch の finally が動いたあと、新しい例外が外へ伝わる
- 例：内側の catch で throw → 内側の finally → 外側の catch

### マルチキャッチ

#### マルチキャッチ（まるちきゃっち / multi-catch）

- 意味：1 つの catch で、`|` で区切った複数の例外の型を受け取る書き方
- ポイント：継承関係のある型は並べられない（Alternatives in a multi-catch statement cannot be related by subclassing）。例外パラメータは暗黙に final で、代入すると multi-catch parameter e may not be assigned。ふつうの catch の e には代入できる
- 例：`catch (NumberFormatException | ArithmeticException e)`

#### 到達できない catch（とうたつできないきゃっち / unreachable catch clause）

- 意味：前の catch ですでに受け取られる型を、あとの catch に書くこと。コンパイルエラーになる
- ポイント：Exception のあとに RuntimeException、IOException のあとに FileNotFoundException などは exception … has already been caught
- 例：`catch (Exception e) { } catch (RuntimeException e) { }`

## 13-3 try-with-resources

### まとめ表

| 書き方 | 結果（JDK 17） |
| :-- | :-- |
| `try (R a = …; R b = …) { … } catch … finally …` | a・b を開く → 本体 → b・a の順に close → catch → finally |
| R が AutoCloseable を実装していない | incompatible types: try-with-resources not applicable to variable type |
| close() が throws Exception で、catch も throws もない | unreported exception Exception; must be caught or declared to be thrown（exception thrown from implicit call to close() on resource variable 'r'） |
| 本体の中で `r = new R();` | auto-closeable resource r may not be assigned |
| `try (r)` の r が実質的に final でない | variable r used as a try-with-resources resource neither final nor effectively final |
| `try (R r = null)` | OK（close は呼ばれない） |

### リソースの自動クローズ

#### try-with-resources（とらいうぃずりそーしず / try-with-resources statement）

- 意味：try のあとの ( ) にリソースを書くと、ブロックが終わったときに自動で close() を呼ぶ try 文
- ポイント：catch も finally も書かなくてよい。リソースは書いた順に初期化され、逆の順に閉じられる。catch と finally は、リソースが閉じられたあとに実行される
- 例：`try (BufferedReader br = new BufferedReader(new FileReader(path))) { … }`

#### AutoCloseable（おーとくろーざぶる / java.lang.AutoCloseable）

- 意味：try-with-resources で使えるリソースが実装するインタフェース。close() メソッドを 1 つ持つ
- ポイント：AutoCloseable の close() は throws Exception なので、そのまま実装するとチェック例外の処理が必要。throws を書かずに実装すれば不要。java.io.Closeable（throws IOException）は AutoCloseable のサブインタフェース
- 例：`class R implements AutoCloseable { public void close() { … } }`

#### リソースのクローズ順（りそーすのくろーずじゅん / closing order）

- 意味：複数のリソースを書いたとき、close() が呼ばれる順番
- ポイント：開いた順の逆（あとに開いたものから閉じる）。初期化に失敗したリソースや null のリソースは閉じられない
- 例：`try (R a = …; R b = …)` → close b → close a

#### 抑制された例外（よくせいされたれいがい / suppressed exception）

- 意味：try の本体で例外が起きたあと、close() でも例外が起きたとき、あとの例外が本体の例外に「抑制された例外」として付け加えられるしくみ
- ポイント：catch で受け取るのは本体の例外。close() の例外は getSuppressed() の配列で取り出せる。close() の例外で本体の例外が消えることはない
- 例：`e.getSuppressed()[0].getMessage()` → close の例外のメッセージ

#### リソース変数（りそーすへんすう / resource variable）

- 意味：try-with-resources の ( ) で宣言した変数、または ( ) に書いた既存の変数
- ポイント：( ) で宣言した変数は暗黙に final で、代入すると auto-closeable resource r may not be assigned。Java 9 からは、final か実質的に final の既存の変数を `try (r)` と書ける
- 例：`R r = new R(); try (r) { … }`

### 13-1 例外の種類とカスタム例外

#### 問 java-13-o01

- 問：次のプログラムをコンパイルした。結果として正しいものはどれか。

  ```
  public class Main {
    static void m() {
      throw new Exception("x");
    }
    public static void main(String[] args) { m(); }
  }
  ```

- ア：コンパイルでき、実行すると Exception がスローされてプログラムが止まる
- イ：m(); の行だけで unreported exception のコンパイルエラーになる
- ウ：throw の行で unreported exception Exception; must be caught or declared to be thrown のコンパイルエラーになる
- エ：コンパイルでき、実行しても何も表示されない
- 正解：ウ
- 解説：Exception はチェック例外なので、投げるメソッドは catch するか、throws Exception を書かなければならない。m() に throws がないので throw の行でコンパイルエラー。m() に throws を書くと、今度は呼んでいる main の m(); がエラーになる。
- アの意味：チェック例外の処理はコンパイル時に調べられるので、実行までいかない。
- イの意味：m() に throws がないので、まず m() の中の throw がエラーになる。m() 自体は何も投げないと宣言している扱い。
- ウの意味：正しい。
- エの意味：コンパイルできない。
- 出典：オリジナル問題（根拠：JLS 11.2.3（It is a compile-time error if a method or constructor body can throw some exception class E when E is a checked exception class and E is not a subclass of some class declared in the throws clause of the method or constructor）／JDK 17 でのコンパイル結果）

#### 問 java-13-o02

- 問：次のプログラムを実行した。結果として正しいものはどれか。

  ```
  public class Main {
    static void m() {
      throw new IllegalStateException("bad");
    }
    public static void main(String[] args) {
      System.out.println("start");
      m();
      System.out.println("end");
    }
  }
  ```

- ア：start と end が表示される
- イ：start が表示されたあと、IllegalStateException がスローされてプログラムが止まる（end は表示されない）
- ウ：throw の行でコンパイルエラーになる（throws がない）
- エ：start、end のあとに IllegalStateException の情報が表示される
- 正解：イ
- 解説：IllegalStateException は RuntimeException のサブクラス（非チェック例外）なので、throws がなくてもコンパイルできる。実行すると m() で投げられ、どこでも catch されないので main が終わり、end は表示されない。標準エラーに Exception in thread "main" java.lang.IllegalStateException: bad と出る。
- アの意味：例外が catch されないので、m() のあとの文は実行されない。
- イの意味：正しい。
- ウの意味：非チェック例外は throws を書かなくてよい。
- エの意味：例外が起きた時点で止まるので、end は表示されない。
- 出典：オリジナル問題（根拠：Java SE 17 API RuntimeException（RuntimeException and its subclasses are unchecked exceptions. Unchecked exceptions do not need to be declared in a method or constructor's throws clause）・JLS 14.18（If no such try statement is found, then execution of the thread … that executed the throw is terminated）／JDK 17 での実行結果）

#### 問 java-13-o03

- 問：次の例外クラスのうち、チェック例外はどれか。
- ア：java.io.IOException
- イ：java.lang.NumberFormatException
- ウ：java.lang.ArithmeticException
- エ：java.lang.StackOverflowError
- 正解：ア
- 解説：チェック例外は、Exception のうち RuntimeException 系でないもの。IOException は Exception の直接のサブクラスなのでチェック例外。
- アの意味：正しい。
- イの意味：NumberFormatException は IllegalArgumentException のサブクラスで、RuntimeException 系（非チェック例外）。
- ウの意味：ArithmeticException（/ by zero など）は RuntimeException 系（非チェック例外）。
- エの意味：StackOverflowError は Error 系（非チェック）。
- 出典：オリジナル問題（根拠：JLS 11.1.1（the checked exception classes are Throwable and all its subclasses other than RuntimeException and its subclasses and Error and its subclasses）／Java SE 17 API）

#### 問 java-13-o04

- 問：main メソッドの中の次のコードを実行した。表示されるものはどれか。

  ```
  try {
    int[] a = new int[1];
    a[1] = 5;
  } catch (ArrayIndexOutOfBoundsException e) {
    System.out.println(e.getMessage());
  }
  ```

- ア：Index 1 out of bounds for length 1
- イ：ArrayIndexOutOfBoundsException
- ウ：null
- エ：何も表示されず、プログラムが止まる
- 正解：ア
- 解説：要素が 1 つの配列の添字は 0 だけなので、a[1] で ArrayIndexOutOfBoundsException が投げられ、catch で受け取られる。JDK 17 では、そのメッセージは Index 1 out of bounds for length 1。
- アの意味：正しい。
- イの意味：getMessage() はクラス名ではなく、メッセージを返す。クラス名を含むのは toString()。
- ウの意味：JDK が投げるこの例外にはメッセージが付いている。
- エの意味：catch で受け取っているので、止まらない。
- 出典：オリジナル問題（根拠：Java SE 17 API Throwable.getMessage()（Returns the detail message string of this throwable）／JDK 17 での実行結果）

#### 問 java-13-o05

- 問：次のプログラムを実行した。表示されるものはどれか。

  ```
  class InsufficientFundsException extends Exception {
    InsufficientFundsException(String msg) { super(msg); }
  }
  public class Main {
    static int balance = 100;
    static void withdraw(int amount) throws InsufficientFundsException {
      if (amount > balance) throw new InsufficientFundsException("short by " + (amount - balance));
      balance -= amount;
    }
    public static void main(String[] args) {
      try {
        withdraw(30);
        withdraw(100);
        System.out.println("done");
      } catch (InsufficientFundsException e) {
        System.out.println(e.getMessage() + " / " + balance + " / " + e);
      }
    }
  }
  ```

- ア：short by 30 / 70 / short by 30
- イ：short by 0 / 0 / InsufficientFundsException: short by 0
- ウ：short by 30 / 70 / InsufficientFundsException: short by 30
- エ：done
- 正解：ウ
- 解説：1 回目で残高は 70。2 回目は 100 > 70 なので「short by 30」の例外が投げられ、done は飛ばされる。e を文字列につなぐと toString() が使われ、「クラス名: メッセージ」になる（パッケージなしのクラスなので名前だけ）。
- アの意味：e そのものをつなぐと toString() の形になり、クラス名が付く。
- イの意味：2 回目は残高が足りないので引かれず、70 のまま。
- ウの意味：正しい。
- エの意味：2 回目の withdraw で例外が出るので、done には届かない。
- 出典：オリジナル問題（根拠：Java SE 17 API Throwable.toString()（The result is the concatenation of: the name of the class of this object ": " (a colon and a space) the result of invoking this object's getLocalizedMessage() method）・Exception(String)（Constructs a new exception with the specified detail message）／JDK 17 での実行結果）

#### 問 java-13-o06

- 問：次のプログラムをコンパイルした。結果として正しいものはどれか。

  ```
  class AppException extends Exception {
    AppException(String msg) { super(msg); }
  }
  ```

- エの意味：外側で受け取るのは catch1 の中で投げた新しい例外（2）。
- 出典：オリジナル問題（根拠：JLS 14.20.2（If the catch block completes abruptly for reason R, then the finally block is executed. Then there is a choice: If the finally block completes normally, then the try statement completes abruptly for reason R）／JDK 17 での実行結果）

### 13-3 try-with-resources

#### 問 java-13-o23

- 問：次のプログラムを実行した。表示されるものはどれか。

  ```
  class R implements AutoCloseable {
    String n;
    R(String n) { this.n = n; System.out.print("open" + n + " "); }
    public void close() { System.out.print("close" + n + " "); }
  }
  public class Main {
    public static void main(String[] args) {
      try (R a = new R("A"); R b = new R("B")) {
        System.out.print("body ");
        throw new RuntimeException("x");
      } catch (RuntimeException e) {
        System.out.print("catch ");
      } finally {
        System.out.print("finally");
      }
      System.out.println();
    }
  }
  ```

- ア：openA openB body closeA closeB catch finally
- イ：openA openB body catch closeB closeA finally
- ウ：openA openB body closeB closeA catch finally
- エ：openA openB body catch finally closeB closeA
- 正解：ウ
- 解説：リソースは書いた順（A → B）に開かれ、逆の順（B → A）に閉じられる。catch と finally は、リソースがすべて閉じられたあとに実行される。
- アの意味：閉じる順番は、開いた順の逆。
- イの意味：catch はリソースを閉じたあとに動く。
- ウの意味：正しい。
- エの意味：finally のときには、リソースはもう閉じられている。
- 出典：オリジナル問題（根拠：JLS 14.20.3（Resources are closed in the reverse order from that in which they were initialized）・14.20.3.2（all resources will have been closed (or attempted to be closed) by the time the finally block is executed）／JDK 17 での実行結果）
