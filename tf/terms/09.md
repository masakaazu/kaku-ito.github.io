## 09-1 依存関係

### まとめ表

| 種類 | 決まり方 | 使いどころ |
| :-: | :-: | :-: |
| 暗黙の依存関係 | 引数の式がほかのリソースを参照する | ふつうはこれで足りる（推奨） |
| 明示の依存関係 | depends_on = [aws_iam_role_policy.example] | 参照はしないが、相手のふるまいに頼るとき（最後の手段） |
| グラフの処理 | 依存がすべて済んだノードから並列に | 既定で 10 個まで同時（-parallelism） |
| terraform graph | DOT 言語でグラフを出力 | dot -Tpng で画像に。-type=plan などで詳しく |

### 依存関係

#### depends_on（でぃぺんずおん / depends_on meta-argument）

- 意味：Terraform が自動で見つけられない、かくれた依存関係を明示するメタ引数
- ポイント：『You only need to explicitly specify a dependency when a resource or module relies on another resource's behavior but does not access any of that resource's data in its arguments』。値は同じモジュールの中のリソースや子モジュールへの参照のリストで、任意の式は書けない（関係が決まる前に値が分かっていなければならないため）
- 例：EC2 の中のソフトが起動時に S3 を使うので、IAM ロールのポリシーができてから EC2 を作る → depends_on = [aws_iam_role_policy.example]

#### 最後の手段としての depends_on（さいごのしゅだんとしてのでぃぺんずおん / depends_on as a last resort）

- 意味：depends_on は保守的な計画を作りやすいので、できるだけ式の参照で依存を表すべきだという考え方
- ポイント：『You should only use depends_on as a last resort』。depends_on を使うと、上流の何が変わるか分からないので、値を "(known after apply)" とみなしたり、必要以上にリソースを置きかえたりしやすい。モジュールに付けると特にそうなる。式の参照なら、その値が変わらないかぎり変更を計画しない

#### depends_on を書けるブロック（でぃぺんずおんをかけるぶろっく / supported constructs）

- 意味：depends_on を書ける設定のブロック
- ポイント：resource・data・module・output・check・ephemeral。module に付けると、そのモジュールのすべてのリソースとデータソースの処理の順番に影響する。output に付けるときは、なぜ必要かをコメントに書くのがおすすめ

#### 依存グラフ（いぞんぐらふ / dependency graph）

- 意味：Terraform が設定とステートから作る、リソース・プロバイダーなどをノードにしたグラフ。計画やリフレッシュに使う
- ポイント：depends_on と式の参照から辺を作る。循環があってはならない。深さ優先でたどり、依存がすべて済んだノードから並列に処理する。同時に処理する数は既定で 10（plan・apply・destroy の -parallelism で変更。ふつうは変えない）

#### terraform graph（てらふぉーむぐらふ / terraform graph）

- 意味：設定や実行計画の依存関係を、DOT 言語のテキストで出力するコマンド
- ポイント：既定は resource と data の依存の順番だけの簡単なグラフ。-type=plan・plan-destroy・apply などでくわしいグラフ、-draw-cycles で循環に色を付ける。画像にするのは Graphviz の dot
- 例：terraform graph -type=plan | dot -Tpng >graph.png

## 09-2 lifecycle のルール

### まとめ表

| ルール | 何をするか | 書けるブロック |
| :-: | :-: | :-: |
| create_before_destroy | 置きかえのとき、新しいものを先に作ってから古いものを消す | resource |
| prevent_destroy | 消す計画をエラーにする | resource |
| ignore_changes | 指定した属性の変更を、更新の計画で無視する（all で全部） | resource |
| replace_triggered_by | 参照したリソース・属性が変わったら置きかえる | resource |
| precondition・postcondition | 前提・保証の条件（09-3） | resource・data・ephemeral（precondition は output にも） |
| destroy = false | ステートから外すだけで実物は消さない | removed |

### lifecycle

#### lifecycle ブロック（らいふさいくるぶろっく / lifecycle meta-argument）

- 意味：リソースを作る・更新する・消す・置きかえるときの Terraform のふるまいを変える、メタ引数のブロック
- ポイント：『only literal values can be used because the processing happens too early for arbitrary expression evaluation』。依存グラフを作る段階で処理されるので、値はリテラルだけ（変数や式は使えない）

#### create_before_destroy（くりえいとびふぉあですとろい / create_before_destroy）

- 意味：その場で更新できない変更のとき、既定の「消してから作る」を「新しいものを作ってから古いものを消す」に変えるルール
- ポイント：名前が一意でなければならないリソースでは、新旧が同時にあると衝突するので自分から有効にする（opt-in）。依存先にも暗黙に伝わってステートに保存され、依存先で false にはできない。destroy のときに動くプロビジョナーも動かなくなる

#### prevent_destroy（ぷりべんとですとろい / prevent_destroy）

- 意味：true にすると、そのリソースを消す計画（置きかえも含む）をエラーにするルール
- ポイント：データベースなど作り直しが高くつくものを守る。terraform destroy もできなくなる。ただし設定からリソースのブロックごと消すと、ルールも一緒に消えるので守れない。控えめに使う

#### ignore_changes（いぐのあちぇんじず / ignore_changes）

- 意味：実物の指定した属性が設定とちがっても、更新の計画を作らないようにするルール
- ポイント：作るときには設定の値を使い、更新のときだけ無視する。ほかのしくみ（管理エージェントなど）がタグを書きかえる場合などに使う。all ならすべての属性を無視（作る・消すはするが、更新はしない）。メタ引数は指定できない
- 例：ignore_changes = [tags]・ignore_changes = [tags["Name"]]

#### replace_triggered_by（りぷれいすとりがーどばい / replace_triggered_by）

- 意味：参照したリソース・インスタンス・属性に変更があったら、このリソースを置きかえるルール
- ポイント：書けるのは管理リソースの参照だけ。変数やローカル値は計画の動作をもたないので書けない（terraform_data の input に入れて、その terraform_data を参照する）。count・for_each のリソースでは count.index・each.key も使える

#### terraform_data（てらふぉーむでーた / terraform_data resource）

- 意味：ふつうのリソースのライフサイクルをもつが、それ以外は何もしない組みこみのリソース
- ポイント：プロバイダーの設定はいらない（terraform.io/builtin/terraform）。input の値が変わると変更を計画するので、replace_triggered_by に変数の変化を伝えたり、プロビジョナーを置く場所にしたりする。triggers_replace の値が変わると自分が置きかわる

#### -replace と lifecycle のちがい（りぷれいすとらいふさいくるのちがい / -replace vs. lifecycle）

- 意味：-replace は 1 回の plan・apply で特定のリソースを置きかえるオプション、lifecycle は設定に書いておき毎回効くルール
- ポイント：一度だけ作り直したいなら -replace（taint の代わり、#05）。ある変更が起きるたびに作り直したいなら replace_triggered_by

## 09-3 カスタム条件

### まとめ表

| 検証 | 書く場所 | 評価のタイミング | 失敗したとき |
| :-: | :-: | :-: | :-: |
| 変数の validation | variable | 計画を作る前（すぐ） | エラーで止まる |
| precondition | resource・data・ephemeral の lifecycle、output | 計画のあと、作る前 | エラーで止まる |
| postcondition | resource・data・ephemeral の lifecycle | 計画・適用のあと（データソースは読んだあと） | エラーで止まる（下流は進まない。済んだことは戻さない） |
| check ブロック | トップレベル | plan・apply の最後、HCP のヘルスチェックごと | 警告だけで続ける |

### 条件

#### カスタム条件（かすたむじょうけん / custom conditions）

- 意味：condition（true であるべき式）と error_message をもつ、設定に書く検証のしくみの総称。変数の validation・precondition・postcondition・check の assert
- ポイント：すべて error_message が必須。error_message には文字列になる式（テンプレートやヒアドキュメントも）を書ける。Terraform は値が分かる時点でできるだけ早く評価し、apply まで分からない値なら apply のときに評価する

#### precondition（ぷりこんでぃしょん / precondition）

- 意味：リソース・データソース・出力を作る前に確かめる「前提」の条件
- ポイント：プロバイダーが出す引数のエラーより優先して表示される。count・for_each のあとに評価するので count.index・each.key を使える。output にも書ける（ステートに保存したり外に出したりする前に確かめる）
- 例：condition = data.aws_ami.example.architecture == "x86_64"

#### postcondition（ぽすとこんでぃしょん / postcondition）

- 意味：リソースを作ったあと・データソースを読んだあとに確かめる「保証」の条件
- ポイント：self で自分の属性を参照できる。失敗すると、それに依存する下流の処理を止めるが、すでに行った変更は元に戻さない。output には書けない
- 例：condition = self.public_dns != ""

#### self（せるふ / self object）

- 意味：postcondition の中で、そのリソースやデータソース自身の属性を指すオブジェクト
- ポイント：自分自身を名前で参照すると循環になるので、self を使う。precondition では使わない（作る前なので自分の結果はまだない）

#### 前提と保証（ぜんていとほしょう / assumptions and guarantees）

- 意味：precondition と postcondition の使い分けの考え方。precondition は設定が置いている前提、postcondition は結果が満たすべき保証
- ポイント：依存先が多いリソースなら、依存先ごとに precondition を書くより、そのリソースに postcondition を 1 つ書くほうがエラーが分かりやすいこともある。モジュールがちがうなら両方書くのもよい

#### check ブロック（ちぇっくぶろっく / check block）

- 意味：リソースのライフサイクルの外で、インフラ全体がきちんと動いているかを確かめるブロック（v1.5 から）
- ポイント：plan・apply の最後に評価し、assert が false でも警告を出すだけで処理を止めない（止めない検証はこれだけ）。assert ブロックは 1 つ以上必須
- 例：check "health_check" { data "http" "terraform_io" { url = "https://www.terraform.io" } assert { condition = data.http.terraform_io.status_code == 200 … } }

#### スコープ付きデータソース（すこーぷつきでーたそーす / scoped data source）

- 意味：check ブロックの中に書く data ブロック
- ポイント：参照できるのはその check の中だけ。plan・apply の最後に読み、プロバイダーのエラーは警告にかわる。対象のリソースを参照しないまま depends_on を付けると、作られるまで known after apply を出して、うその警告を防げる

#### 継続的検証（けいぞくてきけんしょう / continuous validation）

- 意味：HCP Terraform のワークスペースでヘルスチェックを有効にすると、check ブロック・precondition・postcondition を定期的に評価するしくみ
- ポイント：証明書の期限切れなど、apply のあとで変わる状態に気づける。ドリフト検出とあわせてヘルス評価（health assessments）と呼ぶ

#### 検証の順番（けんしょうのじゅんばん / order of validation）

- 意味：Terraform がカスタム条件を評価する、おおよその順番
- ポイント：1 変数の validation（計画の前）→ 2 precondition（計画のあと、作る前）→ 3 postcondition（計画・適用のあと）→ 4 check（plan・apply の最後、HCP のヘルスチェックのたび）

### 09-1 依存関係

#### 問 tf-09-o01

- 問：aws_instance の引数 subnet_id = aws_subnet.main.id と書いた。2 つのリソースを作る順番について正しいものはどれか。
- ア：depends_on = [aws_subnet.main] を書かないと、同時に作られる
- イ：参照から暗黙の依存関係が決まり、サブネットが先に作られる
- ウ：ファイルの中で先に書いたリソースが先に作られる
- エ：リソースの名前のアルファベット順に作られる
- 正解：イ
- 解説：引数の式がほかのリソースの属性を参照していると、Terraform はそれを依存関係として扱い、参照される側を先に処理する。ふつうは depends_on はいらない。
- アの意味：参照があれば depends_on は不要。
- イの意味：正しい。
- ウの意味：書いた順番は処理の順番に関係しない。
- エの意味：名前の順番も関係しない。
- 出典：オリジナル問題（根拠：HashiCorp「Dependency Graph」（『References to resource attributes are turned into dependencies from the resource with the interpolation to the resource being referenced.』））

#### 問 tf-09-o02

- 問：depends_on を書く必要があるのはどんなときか。
- ア：別のリソースの属性を引数で参照しているとき
- イ：同じプロバイダーのリソースが 2 つ以上あるとき
- ウ：別のリソースのふるまいに頼っているが、引数ではそのリソースのデータを使っていないとき
- エ：リソースに count や for_each を付けたとき
- 正解：ウ
- 解説：depends_on は、Terraform が自動で見つけられない「かくれた依存関係」のためのもの。たとえば EC2 の中のソフトが起動時に S3 を使うので、IAM のポリシーが先にできていてほしい場合。
- アの意味：参照があれば暗黙の依存関係になるので不要。
- イの意味：プロバイダーが同じかどうかは関係ない。
- ウの意味：正しい。
- エの意味：count・for_each とは関係ない。
- 出典：オリジナル問題（根拠：HashiCorp「depends_on meta-argument reference」（『You only need to explicitly specify a dependency when a resource or module relies on another resource's behavior but does not access any of that resource's data in its arguments.』））

#### 問 tf-09-o03

- 問：depends_on の値として書けるものはどれか。
- ア：同じモジュールの中のリソースや子モジュールへの参照のリスト
- イ：任意の式（条件式や関数の呼び出しを含む）
- ウ：リソースの名前を文字列にしたリスト（["aws_s3_bucket.example"]）
- エ：変数で作ったリソースのアドレス
- 正解：ア
- 解説：depends_on の値は、Terraform がリソースの関係を知る前に分かっていなければならない。そのため、同じモジュールのリソースや子モジュールへの参照のリストだけを書ける。
- アの意味：正しい。
- イの意味：任意の式は書けない。
- ウの意味：文字列ではなく参照（引用符なし）で書く。
- エの意味：変数でアドレスを作ることはできない。
- 出典：オリジナル問題（根拠：HashiCorp「depends_on meta-argument reference」（『It requires a list of references to other resources or child modules in the same calling module. This list cannot include arbitrary expressions』））

#### 問 tf-09-o04

- 問：HashiCorp が depends_on を「最後の手段」としている理由として正しいものはどれか。
- ア：depends_on を書いたリソースは並列に処理されなくなり、すべての処理が 1 つずつになるから
- イ：depends_on はステートファイルに保存されないから
- ウ：depends_on は Terraform 2.0 でなくなる予定だから
- エ：保守的な計画になり、値を known after apply とみなしたり、必要以上に置きかえたりしやすいから
- 正解：エ
- 解説：depends_on では上流の何が変わるか分からないので、計画が保守的になる。式の参照なら、参照した値が変わらないかぎり変更を計画しないので、できるだけ参照で依存を表す。
- アの意味：全体が 1 つずつになるわけではない。依存のないものは並列に処理される。
- イの意味：保存されるかどうかは理由ではない。
- ウの意味：そういう予定は書かれていない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：HashiCorp「depends_on meta-argument reference」（『You should only use depends_on as a last resort because it can cause Terraform to create more conservative plans that replace more resources than necessary.』））

#### 問 tf-09-o05

- 問：depends_on を書けないブロックはどれか。
- ア：module
- イ：output
- ウ：variable

- 正解：ウ

- アの意味：書ける。モジュールのすべてのリソースとデータソースの順番に影響する。
- イの意味：書ける。必要な理由をコメントに書くのがおすすめ。
- ウの意味：正しい。
- エの意味：書ける。
- 出典：オリジナル問題（根拠：HashiCorp「depends_on meta-argument reference」（Supported constructs：『check blocks』『data blocks』『ephemeral blocks』『module blocks』『output blocks』『resource blocks』））

#### 問 tf-09-o06

- 問：Terraform が依存グラフをたどるときのふるまいとして正しいものはどれか。
- ア：依存がすべて済んだノードから並列に処理し、同時に処理する数は既定で 10 まで
- イ：すべてのノードを 1 つずつ、設定に書いた順に処理する
- ウ：すべてのノードを同時に処理し、エラーになったものだけをやり直す
- エ：同時に処理する数は既定で 1 で、-parallelism で増やす
- 正解：ア
- 解説：グラフの処理は並列で、ノードは依存がすべて済んだらすぐに処理される。同時に処理する数はセマフォで制限し、既定は 10。-parallelism で変えられるが、ふつうは変えない。
- アの意味：正しい。
- イの意味：1 つずつではなく並列。
- ウの意味：依存の順番を守る。
- エの意味：既定は 10。
- 出典：オリジナル問題（根拠：HashiCorp「Dependency Graph」（『a node is walked as soon as all of its dependencies are walked.』『By default, up to 10 nodes in the graph will be processed concurrently.』））

#### 問 tf-09-o07

- 解説：check の中の data に depends_on を付けると、そのリソースの処理が済むまで data を読まず、known after apply を出すのでうその警告を防げる。ただし data がそのリソースを直接参照していると、リソースが変わるたびに known after apply の警告が出るので効果がない。
- アの意味：postcondition にすると失敗で止まるようになり、目的とちがう。
- イの意味：正しい。
- ウの意味：error_message は必須で、空にしても警告は出る。
- エの意味：並列数は関係ない。
- 出典：オリジナル問題（根拠：HashiCorp「depends_on meta-argument reference」（『You can set the depends_on argument to a resource, such as the load balancer, to ensure Terraform only runs the check once the website is up.』））

#### 問 tf-09-o29

- 問：error_message について正しいものはどれか。
- ア：文字列のリテラルしか書けない
- イ：validation だけに必須で、precondition では省略できる
- ウ：文字列になる式（テンプレートやヒアドキュメント）を書け、複数行にもできる
- エ：英語で書かなければならない
- 正解：ウ
- 解説：変数の validation・precondition・postcondition・check はすべて error_message が必須。文字列になる式なら、テンプレートやヒアドキュメントも使える。Terraform 自身のエラーと同じような、完全な文で書くのがおすすめ。
- アの意味：式も書ける。
- イの意味：どれも必須。
- ウの意味：正しい。
- エの意味：言語の決まりはない。
- 出典：オリジナル問題（根拠：HashiCorp「Validate your configuration」（『Input variable validations, preconditions, postconditions, and checks all must include the error_message argument.』『The error_message argument supports any expression that evaluates to a string.』））

#### 問 tf-09-o30

- 問：EC2 インスタンスのルートボリュームの ID のように、apply してはじめて分かる値を使う postcondition は、いつ評価されるか。
- ア：apply のときまで待って評価する
- イ：plan のときに unknown のまま評価し、必ず失敗する
- ウ：評価されずにとばされる
- エ：terraform validate のときに評価する
- 正解：ア
- 解説：Terraform は値が分かる時点でできるだけ早く評価する。計画の段階で値が分かれば plan で、apply のあとでしか分からなければ apply のときに評価する。
- アの意味：正しい。
- イの意味：unknown のまま失敗にはしない。
- ウの意味：とばさずに、あとで評価する。
- エの意味：validate は設定の書き方を確かめるコマンドで、実物の値は使わない。
- 出典：オリジナル問題（根拠：HashiCorp「Validate your configuration」（『If Terraform only knows the value after applying, then Terraform delays checking that validation until the apply phase. For example, AWS assigns the root volume ID when it starts an EC2 instance』））
