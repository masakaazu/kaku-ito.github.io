## 04-1 コアワークフロー

### まとめ表

| 段階 | 一人のとき | チームのとき | HCP Terraform |
| :-: | :-: | :-: | :-: |
| Write | エディタで書き、plan をくり返す | ブランチで書く。秘密の変数が増えると CI へ | 変数とステートを中央に置き、リモートで投機的プラン |
| Plan | apply が出す計画を最後に見る | PR に投機的プランの結果を付けてレビュー | PR を作ると自動でプラン、結果を PR に表示 |
| Apply | yes で実行、リポジトリを push | マージ後、最新のステートで出た計画を確かめて実行 | 計画を承認してから実行、進み具合を共有 |

### ワークフロー

#### コアワークフロー（こあわーくふろー / core Terraform workflow）

- 意味：Terraform の基本の 3 段階。Write（コードを書く）→ Plan（適用前に変更を見る）→ Apply（くり返し同じものを作る）
- ポイント：『Write - Author infrastructure as code.』『Plan - Preview changes before applying.』『Apply - Provision reproducible infrastructure.』。1 回で終わりではなく、変更のたびにくり返すループ

#### Write（らいと / Write）

- 意味：好きなエディタで設定を書く段階。一人でもバージョン管理のリポジトリに置くのがふつう
- ポイント：書きながら plan をくり返すと、文法のまちがいを早く見つけられる（アプリのコードとテストのくり返しと同じ）。init はこの段階で、最初に 1 回実行する

#### Plan（ぷらん / Plan）

- 意味：作る・変える・消すものを、実行する前に見る段階
- ポイント：一人なら terraform apply が確認のために出す計画を最後に見る。チームでは、PR に付けた計画を見て、意図どおりか・今やってよいか（メンテナンスの時間を待つかなど）を話しあう

#### Apply（あぷらい / Apply）

- 意味：計画を承認して、実際のインフラを作る・変える段階
- ポイント：チームでは、マージしたあとに共有ブランチと最新のステートで出た計画を、もう一度確かめる。PR で見た計画とちがうことがある（マージの順番や、手作業の変更のため）

#### 投機的プラン（とうきてきぷらん / speculative plan）

- 意味：適用はせずに、変更の結果を見るためだけに出す計画。PR のレビューに使う
- ポイント：HCP Terraform では、PR を作ると自動で投機的プランが走り、変更があるかが PR の状態に表示される。投機的プランは適用できない

#### CI での実行（しーあいでのじっこう / running Terraform in CI）

- 意味：チームが大きくなり、秘密の入力変数（API キー・証明書など）が増えたとき、各自の PC ではなく共有の CI 環境で Terraform を動かすこと
- ポイント：各自が秘密の値を手元にそろえる手間と危険をなくす。HCP Terraform は、変数とステートを中央に安全に置いて、これを助ける
- 語の意味：CI＝Continuous Integration（継続的インテグレーション）

## 04-2 terraform init

### まとめ表

| init の段階 | 何をするか | 主なオプション |
| :-: | :-: | :-: |
| バックエンドの初期化 | ルートモジュールの backend 設定を読んで準備 | -reconfigure・-migrate-state・-backend-config・-backend=false |
| 子モジュールのインストール | module ブロックの source から取ってくる | -upgrade・-get=false |
| プラグインのインストール | プロバイダーを探して入れ、ロックファイルに書く | -upgrade・-plugin-dir・-lockfile=readonly |

### init

#### terraform init（てらふぉーむいにっと / terraform init）

- 意味：Terraform の設定ファイルがある作業ディレクトリを初期化するコマンド
- ポイント：新しい設定を書いたあとや、VCS からクローンしたあとに『the first command you should run』。何回実行しても安全で、設定やステートを消すことはない。設定のバックエンド・モジュール・プロバイダーを変えたら、もう一度実行する

#### 作業ディレクトリ（さぎょうでぃれくとり / working directory）

- 意味：Terraform を実行するディレクトリ。ルートモジュールの設定ファイルがあり、init で準備される
- ポイント：init のあと、.terraform サブディレクトリ（プロバイダー・モジュールのキャッシュ、バックエンドの情報）と .terraform.lock.hcl ができる。.terraform は VCS に入れず、ロックファイルは入れる。別のディレクトリで実行したいときは -chdir

#### バックエンドの初期化（ばっくえんどのしょきか / backend initialization）

- 意味：init がルートモジュールのバックエンドの設定を読み、ステートの置き場所を準備すること
- ポイント：バックエンドを変えたあとの init には、-migrate-state（今のステートを新しいバックエンドにコピー）か -reconfigure（今の設定を無視し、移さない）が必要。-backend-config は部分設定（秘密や動的な値を外から渡す）。-backend=false はバックエンドを飛ばす

#### 子モジュールのインストール（こもじゅーるのいんすとーる / child module installation）

- 意味：init が module ブロックを探し、source に書かれた場所からモジュールのコードを取ってくること
- ポイント：もう一度 init すると、新しく追加したモジュールだけを入れ、入っているものは変えない。全部を最新にするには -upgrade

#### init -upgrade（いにっとあっぷぐれーど / init -upgrade）

- 意味：モジュールとプロバイダーを、制約に合う最新に上げる init のオプション
- ポイント：プロバイダーはロックファイルの記録を無視して選び直す。ロックファイルが変わるので、レビューしてコミットする。-lockfile=readonly とはいっしょに使えない

#### -lockfile=readonly（ろっくふぁいるりーどおんりー / -lockfile=readonly）

- 意味：ロックファイルを書きかえず、記録されたチェックサムとの照合だけをする init のオプション
- ポイント：ロックファイルを別のツールで管理していて、いつ変わるかを自分で決めたいときに使う

#### -plugin-dir（ぷらぐいんでぃれくとり / -plugin-dir）

- 意味：プロバイダーを、指定したディレクトリからだけ入れる init のオプション
- ポイント：ネットにつながらない環境や、開発中のプロバイダーを試すときの一時的な方法。いつも使うなら CLI 設定の provider_installation（filesystem_mirror など）がすすめられる

## 04-3 validate と fmt

### まとめ表

| | terraform validate | terraform fmt |
| :-: | :-: | :-: |
| 見るもの | 文法と中の整合性（属性名・型） | 書式（インデント・= のそろえ方など） |
| ファイルを変える？ | 変えない | 変える（-check・-write=false なら変えない） |
| 必要なもの | init 済みのディレクトリ（-backend=false でよい） | 何もいらない（init 前でも動く） |
| 見ないもの | 変数の値・ステート・プロバイダーの API | 中身の正しさ |
| CI では | 失敗で止める | -check で失敗を返す |

### 確かめる・整える

#### terraform validate（てらふぉーむばりでーと / terraform validate）

- 意味：ディレクトリの設定ファイルが、文法として正しく、中で矛盾がないかを確かめるコマンド
- ポイント：変数の値や今のステートに関係なく確かめる。リモートのステートやプロバイダーの API は見ない。属性名と値の型は確かめるが、値がプロバイダーにとって正しいか（そのリージョンがあるかなど）は見ない。再利用するモジュールの確認に向く。エディタの保存時や CI で自動に実行しても安全

#### validate に必要な準備（ばりでーとのじゅんび / initialized working directory）

- 意味：validate には、参照するプロバイダーとモジュールが入った、init 済みの作業ディレクトリが必要
- ポイント：バックエンドにつながずに準備するには terraform init -backend=false。特定の変数やワークスペースでの確認は、validate をふくむ terraform plan を使う

#### validate -json（ばりでーとじぇいそん / validate -json）

- 意味：検証の結果を機械向けの JSON で出すオプション。エディタとの連携などに使う
- ポイント：valid（true/false）・error_count・warning_count・diagnostics を持つ。警告（warning）があっても valid は true のまま

#### terraform fmt（てらふぉーむふぉーまっと / terraform fmt）

- 意味：設定ファイルを、Terraform の標準の書式とスタイルに整えるコマンド
- ポイント：既定では今のディレクトリだけを整えて上書きする。わざと設定項目がなく（opinionated）、ちがうコードベースでも同じ書式にそろえるのが目的。Terraform を上げたら、fmt をかけ直すのがすすめられる

#### fmt -check（ふぉーまっとちぇっく / fmt -check）

- 意味：ファイルを書きかえずに、書式が整っているかだけを確かめるオプション
- ポイント：整っていれば終了コード 0、そうでなければ 0 以外で、整っていないファイル名を出す。CI で使う。-write=false がふくまれる

#### fmt -recursive（ふぉーまっとりかーしぶ / fmt -recursive）

- 意味：サブディレクトリのファイルもふくめて整えるオプション
- ポイント：既定では今の（または指定した）ディレクトリだけ。modules/ の下も整えたいときに付ける。-diff は変更の差分を表示する

#### スタイルの規則（すたいるのきそく / style conventions）

- 意味：Terraform ドキュメントがすすめる書き方。fmt はその一部を自動で行う
- ポイント：1 段ごとに 2 スペースのインデント・となりあう 1 行の引数は = をそろえる・引数を先にブロックを後に・メタ引数（count など）は最初、lifecycle などは最後。コミットの前に fmt と validate を実行する（Git の pre-commit フックなど）。組織の規則には TFLint などのリンターを使う

### 04-1 コアワークフロー

#### 問 tf-04-o01

- 問：Terraform のコアワークフローの 3 つの段階を、正しい順に並べたものはどれか。
- ア：Plan → Write → Apply
- イ：Init → Plan → Destroy
- ウ：Write → Apply → Plan
- エ：Write → Plan → Apply
- 正解：エ
- 解説：コアワークフローは Write（コードを書く）→ Plan（適用前に変更を見る）→ Apply（くり返し同じものを作る）。変更のたびにくり返すループ。
- アの意味：書く前に計画はできない。
- イの意味：init はコマンドの 1 つで、ワークフローの 3 段階ではない。
- ウの意味：Apply の前に Plan で確かめる。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：HashiCorp「Core Terraform Workflow Overview」（『Write - Author infrastructure as code.』『Plan - Preview changes before applying.』『Apply - Provision reproducible infrastructure.』））

#### 問 tf-04-o02

- 問：一人で作業しているとき、Write の段階で plan をくり返し実行する理由として正しいものはどれか。
- ア：文法のまちがいを早く見つけ、設定が思いどおりにできているかを確かめるため
- イ：plan を実行するたびにインフラが少しずつ作られるため
- ウ：plan を実行しないと設定ファイルが保存されないため
- エ：plan でプロバイダーがインストールされるため
- 正解：ア
- 解説：書きながら plan をくり返すと、文法のまちがいをあぶり出し、設定が思いどおりかを確かめられる。アプリのコードを書いてテストを回すのと同じ。
- アの意味：正しい。
- イの意味：plan はインフラを変えない。
- ウの意味：保存はエディタで行う。
- エの意味：プロバイダーは init で入る。
- 出典：オリジナル問題（根拠：HashiCorp「Core Terraform Workflow Overview」（『repeatedly running plans can help flush out syntax errors and ensure that your config is coming together as you expect.』））

#### 問 tf-04-o03

- 問：一人で作業しているときの、最後の確認と適用のしかたとして、ドキュメントで説明されているものはどれか。
- ア：terraform plan の結果をファイルに保存して、別の人に送る
- イ：terraform apply を実行し、それが表示する計画を確かめてから yes で承認する
- ウ：terraform validate を実行すると、自動で適用される
- エ：terraform fmt を実行すると、確認なしで適用される
- 正解：イ
- 解説：terraform apply は、インフラを変える前に確認のための計画を表示する。それを最後の確認として見てから yes を入力する。
- アの意味：チームでのやり方に近く、一人のときの説明ではない。
- イの意味：正しい。
- ウの意味：validate は確かめるだけ。
- エの意味：fmt は書式を整えるだけ。
- 出典：オリジナル問題（根拠：HashiCorp「Core Terraform Workflow Overview」（『Because terraform apply will display a plan for confirmation before proceeding to change any infrastructure, that's the command you run for final review.』））

#### 問 tf-04-o04

- 問：チームで作業するとき、Write の段階でまず変わることとして正しいものはどれか。
- ア：全員が同じブランチに直接コミットする

- ウの意味：正しい。

#### 問 tf-04-o05

- 問：チームが大きくなると、Terraform を各自の PC ではなく共有の CI 環境で動かすことが多くなる。その理由として正しいものはどれか。

- イの意味：CI でもステートは要る。
- ウの意味：plan は飛ばさない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：HashiCorp「Core Terraform Workflow Overview」（『To avoid the burden and the security risk of each team member arranging all sensitive inputs locally, it's common for teams to migrate to a model in which Terraform operations are executed in a shared Continuous Integration (CI) environment.』））

#### 問 tf-04-o10

- 問：terraform init を何回も実行したときの説明として正しいものはどれか。
- ア：1 回しか実行できず、2 回目はいつもエラーになる
