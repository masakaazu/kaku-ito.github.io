## 01-1 IaC とその利点

### まとめ表

| 方法 | 書くもの | 特徴 |
| :-: | :-: | :-: |
| 手作業（コンソール・スクリプト） | 手順 | 規模が大きくなると、まちがいやすく手間がかかる |
| 宣言型の IaC（Terraform） | 最後のあるべき姿 | 手順はツールが考える。バージョン管理・再利用・共有ができる |
| 構成管理ツール（Chef・Puppet） | すでにあるマシンの中のソフトの設定 | Terraform は構成管理ツールではない |

### IaC の考え方

#### IaC（あいえーしー / Infrastructure as Code）

- 意味：サーバー・ネットワーク・DNS などのインフラを、手作業ではなく、人が読める設定ファイル（コード）で定義して作ったり変えたりするやり方
- ポイント：Terraform は『an infrastructure as code tool that lets you define both cloud and on-prem resources in human-readable configuration files that you can version, reuse, and share』。ファイルなので、バージョン管理・再利用・共有ができ、同じ手順（ワークフロー）でくり返し作れる
- 語の意味：Infrastructure＝基盤／as＝〜として／Code＝コード

#### 宣言型（せんげんがた / declarative）

- 意味：「どうやって作るか」の手順ではなく、「最後にどうなっていてほしいか」を書く書き方
- ポイント：Terraform の設定ファイルは『declarative, meaning that they describe the end state of your infrastructure』。手順を書かないので、ブロックの順番やファイルの分け方は、ふつう意味を持たない。反対は、手順を書く手続き型（imperative）

#### バージョン管理（ばーじょんかんり / version control）

- 意味：設定ファイルを Git などの VCS に入れて、変更の履歴を残し、レビューしてから反映すること
- ポイント：IaC の利点の 1 つ。だれが・いつ・何を変えたかが分かり、前の状態に戻すこともできる。HCP Terraform は VCS とつないで、チームでの作業を進められる

#### 不変のインフラ（ふへんのいんふら / immutable infrastructure）

- 意味：動いているサーバーを直接いじって変えるのではなく、新しいものを作って置き換えるという考え方
- ポイント：Terraform は『takes an immutable approach to infrastructure, reducing the complexity of upgrading or modifying your services and infrastructure』。手で少しずつ変えたサーバーは、設定がばらばらになりやすい

#### 構成管理ツールとのちがい（こうせいかんりつーる / configuration management tools）

- 意味：Chef・Puppet などの構成管理ツールは、すでにあるマシンの中にソフトを入れて設定するツール
- ポイント：『Terraform is not a configuration management tool』。Terraform はデータセンターやサービスという、より上のレベルのインフラを作る。両方を組み合わせて、Terraform が作ったマシンで cloud-init から構成管理ツールを起動することもできる

## 01-2 Terraform のしくみ

### まとめ表

| 段階 | すること |
| :-: | :-: |
| Write（書く） | 設定ファイルにリソースを定義する |
| Plan（計画） | 今のインフラと設定を比べて、作る・変える・消すものの実行計画を作る |
| Apply（適用） | 承認されたら、依存関係の順に実行計画のとおりに変える |

### 構成要素

#### Terraform（てらふぉーむ / Terraform）

- 意味：HashiCorp の IaC ツール。クラウドやほかのサービスの API を通してリソースを作り、管理する
- ポイント：『Terraform creates and manages resources on cloud platforms and other services through their application programming interfaces (APIs).』。API があるものなら、プロバイダーを通して、ほぼ何でも扱える

#### プロバイダー（ぷろばいだー / provider）

- 意味：Terraform が、あるクラウドやサービスの API を使えるようにするプラグイン
- ポイント：『Providers enable Terraform to work with virtually any platform or service with an accessible API.』。AWS・Azure・GCP・Kubernetes・GitHub・Datadog など、何千もの公開されたプロバイダーが Terraform Registry にある。自分で書くこともできる

#### Terraform Registry（てらふぉーむれじすとり / Terraform Registry）

- 意味：公開されたプロバイダーとモジュールを探して使うための公式のサイト（registry.terraform.io）
- ポイント：プロバイダーもモジュールも、ここから探せる。組織の中だけで共有するなら、HCP Terraform のプライベート・レジストリを使う

#### Terraform 言語と HCL（てらふぉーむげんご / Terraform language, HCL）

- 意味：Terraform の設定を書く言語。HCL（HashiCorp Configuration Language）の文法でできていて、ブロック・引数・式の 3 つの要素で書く。ファイルの拡張子は .tf
- ポイント：『The main purpose of the Terraform language is declaring resources, which represent infrastructure objects.』。ほかの機能は、リソースの定義をもっと柔軟・便利にするためのもの
- 語の意味：HashiCorp＝会社名／Configuration＝構成／Language＝言語

#### 実行計画（じっこうけいかく / execution plan）

- 意味：terraform plan が作る、作る・変える・消すリソースの一覧
- ポイント：Terraform は計画と実行を分ける。ほかのツールは計画と実行がいっしょなので、変更の影響を頭で考えるしかないが、Terraform は前もって何が起きるかを確かめてから適用できる

#### リソースグラフ（りそーすぐらふ / resource graph）

- 意味：リソースどうしの依存関係を表した図（グラフ）。Terraform はこれで作る順番を決める
- ポイント：依存しないリソースは並列に作ったり変えたりするので効率がよい。terraform graph で図にできる

#### ステートファイル（すてーとふぁいる / state file）

- 意味：Terraform が管理している実際のインフラの情報を記録したファイル
- ポイント：『a state file, which acts as a source of truth for your environment』。Terraform はステートを使って、設定に合わせるために何を変えればよいかを決める（詳しくは #03）

#### モジュール（もじゅーる / module）

- 意味：いくつかのリソースをまとめて、設定を変えて使い回せるようにした部品
- ポイント：組織の決まり（標準）をモジュールにすると、各チームが同じやり方でインフラを作れる（セルフサービス）。Registry の公開モジュールも、自分のモジュールも使える（詳しくは #11）

## 01-3 マルチクラウドとエディション

### まとめ表

| エディション | 形 | 特徴 |
| :-: | :-: | :-: |
| Terraform Community Edition | 無料の CLI | ローカルで実行。設定・プラグイン・インフラ・ステートを管理 |
| HCP Terraform | HashiCorp の SaaS | リモート実行・ステートとシークレットの保管・RBAC・プライベート・レジストリ・Sentinel |
| Terraform Enterprise | 自社で動かす HCP Terraform | 厳しいセキュリティ・コンプライアンスの要件に向く |

### いろいろな環境

#### マルチクラウド（まるちくらうど / multi-cloud）

- 意味：AWS と Azure のように、複数のクラウドを組み合わせて使うこと
- ポイント：クラウドの障害に強くなるが、クラウドごとにツールややり方がちがうので複雑になる。Terraform は『lets you use the same workflow to manage multiple providers and handle cross-cloud dependencies』。1 つの設定に複数のプロバイダーを書ける

#### ハイブリッドクラウド（はいぶりっどくらうど / hybrid cloud）

- 意味：自社の設備（オンプレミス）とパブリッククラウドを組み合わせて使うこと
- ポイント：Terraform はクラウドとオンプレミスの両方のリソースを、同じ言語・同じワークフローで扱える（vSphere などにもプロバイダーがある）

#### サービスに依存しない（さーびすにいぞんしない / service-agnostic）

- 意味：特定のクラウドだけでなく、DNS・CDN・監視・SaaS など、API のあるいろいろなサービスを同じやり方で扱えること
- ポイント：CloudFormation は AWS だけだが、Terraform は『both cloud-agnostic and enabling multiple providers and services to be combined and composed』。たとえば AWS のサーバーと Cloudflare の CDN と DNSimple の DNS を 1 つの設定で管理できる
- 語の意味：agnostic＝特定のものに依存しない

#### 並行環境（へいこうかんきょう / parallel environments）

- 意味：開発・テスト・QA・本番のように、同じ構成の環境をいくつも作ること
- ポイント：Terraform ならすばやく作って、使い終わったら消せる。使い捨ての環境は、ずっと置いておくより費用が安い

### エディション

#### Terraform Community Edition（こみゅにてぃえでぃしょん / Terraform Community Edition）

- 意味：無料でダウンロードして、コマンドラインで使う Terraform
- ポイント：どのクラウドにもインフラを作れ、設定・プラグイン・インフラ・ステートを管理する。チームで使うときは、最新の設定を自分で pull して実行する

#### HCP Terraform（えいちしーぴーてらふぉーむ / HCP Terraform）

- 意味：HashiCorp が提供する SaaS。安定したリモートの環境で Terraform を実行し、ステートとシークレットを安全に保管する
- ポイント：画面（UI）、ロールに基づくアクセス制御、モジュールとプロバイダーのプライベート・レジストリ、VCS とのつなぎ込み、Sentinel のポリシー。小さなチームなら多くの機能が無料（以前の名前は Terraform Cloud）
- 語の意味：HCP＝HashiCorp Cloud Platform

#### Terraform Enterprise（えんたーぷらいず / Terraform Enterprise）

- 意味：HCP Terraform を、自社の環境に置いて（セルフホストで）動かす版
- ポイント：リソースの上限を変えられ、厳しいセキュリティやコンプライアンスの要件がある組織に向く

#### Sentinel（せんちねる / Sentinel）

- 意味：HashiCorp のポリシー・アズ・コード（policy as code）のしくみ。決まりをコードで書き、Terraform が変更する前に自動で確かめる
- ポイント：チケットでの人の確認は時間がかかる。Sentinel のポリシーは HCP Terraform と Terraform Enterprise で使える（例：本番に使えるリージョンを決める）

### 01-1 IaC とその利点

#### 問 tf-01-o01

- 問：IaC（Infrastructure as Code）の説明として最も適切なものはどれか。
- ア：インフラを、バージョン管理・再利用・共有ができる、人が読める設定ファイルで定義して管理する
- イ：クラウドの管理画面を操作する手順書を作り、担当者がそのとおりに操作する
- ウ：アプリケーションのソースコードの中に、サーバーの IP アドレスを直接書く
- エ：動いているサーバーに入り、設定を少しずつ手で直す
- 正解：ア
- 解説：IaC は、インフラを設定ファイル（コード）で定義し、同じワークフローでくり返し作ったり変えたりするやり方。ファイルなので VCS で管理でき、再利用・共有もできる。
- アの意味：正しい。
- イの意味：手順書による手作業で、IaC ではない。
- ウの意味：アプリの中に値を書くことで、インフラをコードで管理することではない。
- エの意味：手作業の変更で、環境ごとに設定がばらばらになりやすい。
- 出典：オリジナル問題（根拠：HashiCorp「What is Terraform?」（『HashiCorp Terraform is an infrastructure as code tool that lets you define both cloud and on-prem resources in human-readable configuration files that you can version, reuse, and share.』））

#### 問 tf-01-o02

- 問：Terraform の設定ファイルが「宣言型」であることの説明として正しいものはどれか。
- ア：リソースを作る手順を、上から順に書かなければならない
- イ：インフラの最後のあるべき姿を書き、そこにいたる手順は Terraform が考える
- ウ：設定ファイルの中のブロックの順番を変えると、作られる順番も変わる
- エ：変数を宣言しなければ、リソースを書けない
- 正解：イ
- 解説：宣言型の設定は、最後の状態だけを書く。手順を書かないので、ブロックの順番は作る順番を決めない。順番は依存関係（リソースグラフ）から Terraform が決める。
- アの意味：それは手続き型（imperative）のやり方。
- イの意味：正しい。
- ウの意味：順番は依存関係で決まり、ファイルの中の並び順ではない。
- エの意味：「宣言型」は変数の宣言のことではない。
- 出典：オリジナル問題（根拠：HashiCorp「What is Terraform?」（『Terraform configuration files are declarative, meaning that they describe the end state of your infrastructure. You do not need to write step-by-step instructions to create resources because Terraform handles the underlying logic.』）／Terraform Language Documentation（『The Terraform language is declarative, describing an intended goal rather than the steps to reach that goal.』））

#### 問 tf-01-o03

- 問：IaC の利点として、適切でないものはどれか。
- ア：設定ファイルを VCS に入れて、変更の履歴を残し、レビューできる
- イ：同じ設定から、開発・テスト・本番の環境を同じように作れる
- ウ：インフラの費用が必ず安くなり、クラウドの利用料がかからなくなる
- エ：モジュールにして、組織の標準のやり方を再利用・共有できる
- 正解：ウ
- 解説：IaC で使い捨ての環境を作って費用を下げることはできるが、クラウドの料金そのものがなくなるわけではない。
- アの意味：IaC の利点（バージョン管理）。
- イの意味：IaC の利点（くり返し同じものを作れる）。
- ウの意味：正しい（適切でない）。
- エの意味：IaC の利点（標準化・再利用）。
- 出典：オリジナル問題（根拠：HashiCorp「What is Terraform?」Why Terraform?（Standardize configurations・Collaborate）／Terraform Use Cases（Parallel Environments））

#### 問 tf-01-o04

- 問：Terraform と Chef・Puppet などの構成管理ツールの関係として、正しいものはどれか。
- ア：Terraform は構成管理ツールの一種で、マシンの中のソフトの設定を主に行う
- イ：Terraform を使うときは、構成管理ツールは使えない
- ウ：構成管理ツールは、クラウドのネットワークやロードバランサーを作るためのもの
- エ：Terraform は構成管理ツールではなく、より上のレベルのインフラを作る。作ったマシンで構成管理ツールを起動させることもできる
- 正解：エ
- 解説：構成管理ツールは、すでにあるマシンの中にソフトを入れて管理する。Terraform はデータセンターとサービスのレベルを扱い、cloud-init などで構成管理ツールを起動させて組み合わせられる。
- アの意味：Terraform は構成管理ツールではない。
- イの意味：組み合わせて使える。
- ウの意味：構成管理ツールは、すでにあるマシンの中を扱う。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：HashiCorp「Terraform vs. Chef, Puppet, etc.」（『Configuration management tools install and manage software on a machine that already exists. Terraform is not a configuration management tool』））

#### 問 tf-01-o05

- 問：Terraform がとる「不変のインフラ（immutable infrastructure）」の考え方として、正しいものはどれか。
- ア：一度作ったインフラは、二度と変えられない
- イ：動いているサーバーを直接いじらず、新しいものを作って置き換える
- ウ：ステートファイルは変更できない
- エ：設定ファイルは、作ったあと書きかえてはいけない
- 正解：イ
- 解説：不変のインフラでは、変更が必要なとき、今あるものを直すのではなく新しく作って置き換える。手で直したサーバーのように設定がばらばらにならない。
- アの意味：変えられないという意味ではなく、置き換えで変える。
- イの意味：正しい。
- ウの意味：ステートは Terraform が更新する。
- エの意味：設定ファイルは書きかえて plan・apply する。
- 出典：オリジナル問題（根拠：HashiCorp「What is Terraform?」（『Terraform takes an immutable approach to infrastructure, reducing the complexity of upgrading or modifying your services and infrastructure.』））

#### 問 tf-01-o06

- 問：手作りのスクリプトでインフラを自動化している組織が、Terraform に移る理由として最も適切なものはどれか。
- ア：手作りのツールは、新しいサービスに合わせて作り直す手間がかかり、インフラを変える速さの足かせになりやすい
- イ：手作りのスクリプトでは、クラウドの API を呼べない
- ウ：Terraform を使うと、インフラの依存関係を担当者が覚えておく必要が増える
- エ：Terraform はソースコードが公開されていないので、安全である
- 正解：ア
- 解説：手作りのツールは、すぐ必要な機能だけで作られ、広げにくく保守しにくい。Terraform は 1 つの文法でほぼどんなリソースも扱い、依存関係も自動で解決する。
- アの意味：正しい。
- イの意味：スクリプトからも API は呼べる。問題は保守の手間。
- ウの意味：逆。依存関係は Terraform が自動で解決する。
- エの意味：Terraform は source-available（ソースを読める）で、無料で使えるツール。
- 出典：オリジナル問題（根拠：HashiCorp「Terraform versus Custom Solutions」（『Because the tooling must be updated in lockstep with any new features or infrastructure, it becomes the limiting factor for how quickly the infrastructure can evolve.』『By capturing all the resources required, the dependencies between them can be resolved automatically』））

#### 問 tf-01-o07

- 問：インフラの設定ファイルを VCS（Git など）に入れて管理する利点として、適切でないものはどれか。
- ア：だれがいつ何を変えたか、履歴が残る
- イ：変更を反映する前に、ほかの人がレビューできる
- ウ：以前の設定に戻すことができる
- エ：VCS に入れるだけで、変更がインフラに自動で反映される
- 正解：エ
- 解説：VCS に入れただけではインフラは変わらない。plan・apply を実行してはじめて変わる（HCP Terraform の VCS 連携なら、変更をきっかけに実行を始められる）。
- アの意味：利点（履歴）。
- イの意味：利点（レビュー）。
- ウの意味：利点（元に戻せる）。
- エの意味：正しい（適切でない）。
- 出典：オリジナル問題（根拠：HashiCorp「Core Terraform Workflow Overview」（Write・Plan・Apply）／「What is Terraform?」Collaborate）

### 01-2 Terraform のしくみ

#### 問 tf-01-o08

- 問：Terraform が、クラウドやサービスのリソースを作ったり変えたりするしくみとして正しいものはどれか。
- ア：対象のサーバーにエージェントを入れて、その中から操作する
- イ：各クラウドの管理画面を、画面操作で自動化する
- ウ：プロバイダーを通して、クラウドやサービスの API を呼ぶ
- エ：SSH でクラウドの管理サーバーにログインして、コマンドを打つ
- 正解：ウ

- ア：設定を全部書き終えるまで、plan を実行しない
- イ：設定ファイルは VCS に入れず、自分のパソコンだけに置く
- ウ：設定を書きながらくり返し plan を実行して、文法のまちがいを見つけ、思いどおりになっているか確かめる
- エ：書いた設定は、確かめずにすぐ apply する
- 正解：ウ
- 解説：一人でも設定を VCS に入れるのがふつう。書きながら plan をくり返すと、まちがいを早く見つけられる。
- アの意味：書きながら plan をくり返すのがよい。
- イの意味：一人でも VCS に入れるのがふつう。
- ウの意味：正しい。
- エの意味：plan で確かめてから apply する。
- 出典：オリジナル問題（根拠：HashiCorp「Core Terraform Workflow Overview」Working as an Individual Practitioner（『It's common practice to store your work in a version controlled repository even when you're just operating as an individual.』『As you make progress on authoring your config, repeatedly running plans can help flush out syntax errors and ensure that your config is coming together as you expect.』））

#### 問 tf-01-o30

- 問：Terraform の Apply の段階の説明として正しいものはどれか。
- ア：承認されたら、依存関係を守って正しい順番で、計画どおりに変更を実行する
- イ：設定ファイルの文法だけを確かめる
- ウ：すべてのリソースを一度消して、作り直す
- エ：承認を待たずに、計画を作らないで変更する
- 正解：ア
- 解説：Apply では、承認された計画の操作を、リソースの依存関係を守った順番で行う。
- アの意味：正しい。
- イの意味：それは terraform validate。
- ウの意味：変える必要のあるものだけを変える。
- エの意味：計画を示して承認を求める。
- 出典：オリジナル問題（根拠：HashiCorp「What is Terraform?」（『Apply: On approval, Terraform performs the proposed operations in the correct order, respecting any resource dependencies.』））
