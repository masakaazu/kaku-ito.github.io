## 03-1 ステートの役割

### まとめ表

| 目的 | 中身 |
| :-: | :-: |
| 現実との対応づけ（Mapping） | 設定の aws_instance.foo ＝ 実物の i-abcd1234 |
| メタデータ | 依存関係（設定から消したものを消す順番）・使ったプロバイダー設定 |
| 性能（Performance） | 属性の値のキャッシュ。大きな環境では -refresh=false と組み合わせる |
| 同期（Syncing） | チームで同じステートを使う → リモートステートとロック |

### 役割

#### ステート（すてーと / state）

- 意味：Terraform が管理するインフラと設定について記録したデータ。実物のリソースを設定に対応づけ、メタデータを追い、大きなインフラでの性能を上げるのに使う
- ポイント：『State is a necessary requirement for Terraform to function.』。Terraform はステートを見て、どんな変更をするかを決める。どの操作の前にも、まず refresh でステートを実物に合わせる

#### terraform.tfstate（てらふぉーむてぃーえふすてーと / terraform.tfstate）

- 意味：既定でステートを保存する、ルートモジュールのディレクトリのローカルファイル
- ポイント：既定のバックエンドは local。チームで使うなら HCP Terraform などのリモートに置くのがすすめられる（バージョン管理・暗号化・安全な共有のため）。秘密の値も平文で入るので、Git に入れない

#### 対応づけ（たいおうづけ / mapping to the real world）

- 意味：設定のリソースインスタンスと、リモートのシステムにある実物（オブジェクト）とのひもづけ。ステートのいちばんの目的
- ポイント：『The primary purpose of Terraform state is to store bindings between objects in a remote system and resource instances declared in your configuration.』。タグで代わりにする案は、タグに対応しないリソースやクラウドがあるので採られなかった

#### 1 対 1 の対応（いったいいちのたいおう / one-to-one mapping）

- 意味：1 つの実物は、設定の 1 つのリソースインスタンスだけにひもづく、という Terraform の前提
- ポイント：Terraform 自身が作った・消したものなら守られる。import や state rm で人がひもづけを増やしたり外したりしたときは、自分で守る（同じ実物を 2 か所に import しない）

#### メタデータ（めたでーた / metadata）

- 意味：対応づけのほかにステートが持つ情報。リソースの依存関係や、最後に使ったプロバイダー設定（alias があるとき）など
- ポイント：設定から消したリソースは、設定から順番が分からない。そこで最新の依存関係をステートに残して、正しい順番で消せるようにする

#### 属性のキャッシュ（ぞくせいのきゃっしゅ / attribute cache）

- 意味：ステートに入っている、全リソースの属性の値のコピー。性能のためのもの
- ポイント：既定では plan・apply のたびに全リソースを API で確かめる（refresh）。大きな環境では遅く、API の回数制限もあるので、-refresh=false や -target を使い、キャッシュを正とみなすことがある。ステートの目的の中で『the most optional feature』

#### refresh（りふれっしゅ / refresh）

- 意味：管理しているリモートの実物の今の設定を読み、ステートをそれに合わせること
- ポイント：plan・apply では自動で行われる。実物は変えず、ステートだけを変える。単独の terraform refresh コマンドは非推奨で、terraform apply -refresh-only（確認あり）がすすめられる（くわしくは #13）

## 03-2 ステートの中身と見方

### まとめ表

| コマンド | 何をするか |
| :-: | :-: |
| terraform show | 最新のステート（またはプランファイル）を人が読める形で表示。-json で機械向け |
| terraform state list | ステートにあるリソースのアドレスを一覧 |
| terraform state show ADDR | 1 つのリソースのくわしい属性 |
| terraform output -json | ルートモジュールの出力値を JSON で |
| terraform state pull | ステートを取ってきて標準出力にそのまま出す |

### 中身と見方

#### ステートの形式（すてーとのけいしき / state format）

- 意味：ステートのスナップショットは JSON で保存される
- ポイント：新しい版はふつう古いステートを読めるが、形式は版で変わりうる。直接ファイルを編集するのはすすめられず、terraform state コマンドを使う。外部のソフトで読むなら、show -json や output -json の出力を使う

#### terraform show（てらふぉーむしょう / terraform show）

- 意味：ステートまたはプランファイルを、人が読める形で表示するコマンド。ファイルを指定しなければ最新のステートを表示する
- ポイント：-json で機械向けの JSON になる。このとき sensitive な値も平文で出るので注意

#### terraform state list（すてーとりすと / terraform state list）

- 意味：ステートにあるリソースのアドレスを一覧するコマンド
- ポイント：アドレスのパターンで絞りこめる。ルートのリソースが先、モジュールの深いものが後に並ぶ
- 例：`aws_instance.bar[0]`、`module.elb.aws_elb.main`

#### terraform state show（すてーとしょう / terraform state show）

- 意味：ステートにある 1 つのリソースの、くわしい属性を表示するコマンド
- ポイント：state list でアドレスを調べてから使う。どちらも読むだけで、インフラもステートも変えない

#### terraform state pull（すてーとぷる / terraform state pull）

- 意味：今の置き場所（リモートでもローカルでも）からステートを取ってきて、そのまま標準出力に出すコマンド
- ポイント：jq と組み合わせて値を読んだり、バックアップを取ったりするのに使う。反対の terraform state push はリモートのステートを上書きするので、とても危険

#### lineage と serial（りねーじとしりある / lineage and serial）

- 意味：lineage はステートを作ったときに付く一意な ID、serial は書きこむたびに増える番号
- ポイント：state push のとき、lineage がちがう（別のステート）か、行き先の serial のほうが大きい（そのあとに変更がある）と、Terraform は書きこみを止める。-force で押し切れるが、先に state pull でバックアップを取る

## 03-3 ステートを守る・共有する

### まとめ表

| 心配 | 対策 |
| :-: | :-: |
| 秘密の値が平文で入る | Git に入れない・リモートに置いて保存時に暗号化・アクセス制御・監査ログ |
| チームで最新のステートが分からない | リモートステート（HCP Terraform・S3・Azure Blob・GCS・Consul など） |
| 2 人が同時に実行する | ステートのロック（対応するバックエンドで自動） |
| ステートを手で直したい | 直接編集しない。terraform state コマンドを使い、バックアップを取る |

### 守る・共有する

#### ステートの機密データ（すてーとのきみつでーた / sensitive data in state）

- 意味：ステートとプランファイルには、DB の初期パスワードや API トークンなど、秘密の値もふくめた属性が入ること
- ポイント：ローカルのステートは平文のファイル。sensitive = true は CLI や UI の表示を隠すだけで、ステートには残る。ステートに残さないのは ephemeral や write-only 引数（#10）

#### リモートステート（りもーとすてーと / remote state）

- 意味：ステートをリモートのデータストアに書き、チーム全員で共有すること。バックエンドか HCP Terraform で実現する
- ポイント：ローカルのファイルだと、各自が最新を持っているか、だれかが同時に動かしていないかを気にしなければならない。リモートのバックエンドでは、エラーのとき以外はディスクにステートを残さない。出力値を、ほかの設定に読み取り専用で渡すこともできる（terraform_remote_state）

#### ステートのロック（すてーとのろっく / state locking）

- 意味：ステートに書きこむおそれのある操作の間、ほかの人がロックを取れないようにして、ステートがこわれるのを防ぐしくみ
- ポイント：対応するバックエンドなら自動で行われ、メッセージも出ない。失敗すると Terraform は先に進まない。すべてのバックエンドが対応しているわけではない（くわしくは #12）

#### ステートのセキュリティのベストプラクティス（べすとぷらくてぃす / state security best practices）

- 意味：秘密の値が入ったステートを守るために、ドキュメントがすすめる対策
- ポイント：『Store your state remotely』『Encrypt your state at rest』『Use access controls』『Use audit logs』の 4 つ。HCP Terraform は保存時に暗号化、S3 バックエンドは encrypt を有効にすると暗号化
