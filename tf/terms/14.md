## 14-1 インポート

### まとめ表

| | import ブロック | terraform import コマンド |
| :-: | :-: | :-: |
| 書く場所 | 設定（imports.tf か resource の横） | CLI |
| 確かめ方 | plan で「1 to import」を見てから apply | すぐステートに入る |
| 一度に | 複数（for_each も可） | 1 つ |
| 設定の生成 | plan -generate-config-out=新しいファイル | しない（resource を先に手で書く） |
| CI/CD | 組みこみやすい | 向かない |
| HCP Terraform | 実行の中で動く | ローカルで動く（ワークスペースの変数は見えない） |

### 取りこむ

#### インポート（いんぽーと / import）

- 意味：Terraform の外で作られた既存のインフラを、ステートに取りこみ、Terraform で管理できるようにすること
- ポイント：ステートに入れるだけでなく、残りのライフサイクルを管理するための resource ブロック（設定）も必要。設定がないと、次の計画で消そうとする。すべてのリソースがインポートできるわけではなく、できるかどうかは Registry の各リソースのページの下に書いてある

#### import ブロック（いんぽーとぶろっく / import block）

- 意味：設定に書いて、plan・apply の流れの中で既存のリソースをインポートするブロック（v1.5 から）
- ポイント：to（取りこみ先のリソースアドレス）と id（プロバイダーでの ID）が基本。id は plan のときに分かる文字列でなければならない。id の代わりに identity（属性の組）も使えるが、両方は書けない。for_each・provider も書ける。インポート後も履歴として残しておくのがすすめ
- 例：import { to = aws_s3_bucket.this  id = "example-bucket" }

#### インポートの手順（いんぽーとのてじゅん / import workflow）

- 意味：import ブロックでインポートするときの流れ
- ポイント：1 取りこみ先の resource ブロックを書く → 2 import ブロックを書く → 3 terraform plan で取りこみの計画を確かめる → 4 apply でステートを更新する。既定値でない引数は resource に書いておかないと、次の apply で既定値にもどそうとする

#### インポート ID（いんぽーとあいでぃー / import ID）

- 意味：インポートするときに指定する、クラウドでそのリソースを見分ける ID
- ポイント：形はリソースの型ごとにちがう（EC2 は i-abcd1234、Route53 のゾーンは Z12ABC4UGMOZ2N、S3 はバケット名）。プロバイダーのドキュメントで確かめる

#### 設定の生成（せっていのせいせい / generating configuration）

- 意味：import ブロックの取りこみ先の resource が設定にないとき、plan -generate-config-out でその HCL を自動で書き出す機能
- ポイント：v1.5 からの実験的な機能。まだない新しいファイルのパスを指定する（あるファイルだとエラー）。生成された HCL は「いちばんそれらしい推測」なので、見なおして不要な属性を消したり変数にしたりしてから VCS に入れる。たくさんのリソースや、設定を知らない複雑なリソースに向く
- 例：terraform plan -generate-config-out="generated.tf"

#### terraform import コマンド（てらふぉーむいんぽーとこまんど / terraform import command）

- 意味：CLI で 1 つの既存のリソースをステートの指定したアドレスに取りこむコマンド
- ポイント：terraform import [options] ADDRESS ID。先に resource ブロックを手で書いておく。ステートに入れるだけで設定は作らない。モジュールの中のアドレスにも取りこめる。HCP Terraform を使っていてもローカルで動くので、ワークスペースの変数に当たるものをローカルで設定する必要がある
- 例：terraform import aws_instance.web i-abcd1234

#### 1 つのオブジェクトに 1 つのアドレス（ひとつのおぶじぇくとにひとつのあどれす / one object, one address）

- 意味：1 つの実物は、1 つのリソースアドレスだけに結びつけるという Terraform の前提
- ポイント：同じ実物を 2 つのアドレス（や 2 つの構成）に取りこむと、思わぬ動き（片方の destroy で消えるなど）になる。インポートのときは自分で気をつける

## 14-2 state コマンド

### まとめ表

| コマンド | 何をするか | ステートを変えるか |
| :-: | :-: | :-: |
| terraform state list | ステートのリソースのアドレスを一覧 | 変えない |
| terraform state show ADDRESS | 1 つのリソースの属性を表示 | 変えない |
| terraform state pull | ステート（JSON）を標準出力に出す | 変えない |
| terraform state mv SRC DST | アドレスを変える（moved の古いやり方） | 変える（バックアップあり） |
| terraform state rm ADDRESS | 管理をやめる（実物は残る。removed の古いやり方） | 変える（バックアップあり） |
| terraform state push PATH | ローカルのステートでリモートを上書き | 変える（安全確認あり） |
| terraform state replace-provider | リソースのプロバイダーのソースを付けかえる | 変える（バックアップあり） |

### ステートを見る・直す

#### terraform state コマンド（てらふぉーむすてーとこまんど / terraform state commands）

- 意味：ステートを直接編集せずに、高度な管理をするためのサブコマンドの集まり
- ポイント：リモートステートでもローカルと同じように使える（1 回ごとにネットワークの往復がある）。ステートを変えるサブコマンドは必ずバックアップを書き、止められない。読むだけのもの（list など）は書かない。出力は grep・awk などと組み合わせやすい

#### terraform state mv（てらふぉーむすてーとむーぶ / terraform state mv）

- 意味：ステートの中で、既存の実物を新しいリソースアドレスに結びつけなおすコマンド
- ポイント：terraform state mv SOURCE DESTINATION。リソースの型は変えられず、インスタンスはインスタンスへ、モジュールはモジュールへ。チームでは、設定の変更と state mv の間にだれも変更しないよう連絡する。-dry-run で対象だけ表示。今は moved ブロックがすすめ（#13）
- 例：terraform state mv aws_instance.a aws_instance.b

#### terraform state rm（てらふぉーむすてーとあーるえむ / terraform state rm）

- 意味：実物を消さずに、ステートの記録だけを消して、Terraform の管理から外すコマンド
- ポイント：実物は残るが、設定が残っていれば次の plan で「新しく作る」計画になる（名前の衝突で失敗することも）。複数のアドレスを一度に渡せる。今は removed ブロックがすすめ（#13）

#### terraform state push（てらふぉーむすてーとぷっしゅ / terraform state push）

- 意味：ローカルのステートファイルを、今のバックエンド（リモートやローカル）にアップロードして上書きするコマンド
- ポイント：リモートのステートを手で直さなければならないときだけ使う。lineage がちがう、または serial が今より小さいと押し返す（-force で無視できるが危険）。PATH に - を書くと標準入力から読む

#### terraform state replace-provider（りぷれいすぷろばいだー / terraform state replace-provider）

- 意味：ステートの中のリソースが使うプロバイダーのソースアドレスを、別のものに付けかえるコマンド
- ポイント：プロバイダーのソースが変わった（フォークや名前空間の移動）ときに使う。バックアップは止められない
- 例：terraform state replace-provider hashicorp/aws registry.acme.corp/acme/aws

#### ステートの手での編集を避ける（すてーとのてでのへんしゅうをさける / avoid editing state directly）

- 意味：terraform.tfstate（JSON）をエディターで直接書きかえず、state コマンドや moved・removed・import のブロックを使うという原則
- ポイント：state コマンドはステートを直接いじる代わりに使うもの。ステートの形式は内部用で、手で書きかえるとこわれるおそれがある

## 14-3 ログ

### まとめ表

| 環境変数 | 役割 |
| :-: | :-: |
| TF_LOG | ログを有効にする。TRACE・DEBUG・INFO・WARN・ERROR（くわしい順）、JSON、off |
| TF_LOG_CORE | Terraform 本体のログだけ |
| TF_LOG_PROVIDER | プロバイダーのプラグインのログだけ |
| TF_LOG_PATH | ログをファイルに追記する（TF_LOG も必要） |

### くわしいログ

#### TF_LOG（てぃーえふろぐ / TF_LOG）

- 意味：Terraform のくわしいログを有効にし、標準エラー出力（stderr）に出す環境変数
- ポイント：レベルはくわしい順に TRACE・DEBUG・INFO・WARN・ERROR。どれでもない値でも有効になる。JSON にすると TRACE 以上を JSON で出す（形式は安定していない）。止めるには変数を消すか off にする
- 例：export TF_LOG=TRACE

#### TF_LOG_PATH（てぃーえふろぐぱす / TF_LOG_PATH）

- 意味：ログを指定したファイルにいつも追記させる環境変数
- ポイント：『even when TF_LOG_PATH is set, TF_LOG must be set in order for any logging to be enabled.』。TF_LOG_PATH だけではログは出ない
- 例：export TF_LOG_PATH=./terraform.log

#### TF_LOG_CORE と TF_LOG_PROVIDER（てぃーえふろぐこあとぷろばいだー / TF_LOG_CORE and TF_LOG_PROVIDER）

- 意味：Terraform 本体（コア）とプロバイダーのプラグインのログを、別々に有効にする環境変数
- ポイント：TF_LOG と同じレベルを受け取り、ログの一部だけを出す。プロバイダーの API のやりとりだけ見たいなら TF_LOG_PROVIDER

#### ログを使う場面（ろぐをつかうばめん / when to use verbose logging）

- 意味：くわしいログを有効にすべきとき
- ポイント：ふつうのエラーメッセージで原因が分からない、予期しない動きをする、プロバイダーの API のやりとりを見たい、バグを報告する（ログを gist などに付ける）とき。ログには機密が入りうるので、共有の前に確かめる

#### 問 tf-14-o01

- 問：コンソールで作った S3 バケット example-bucket を、aws_s3_bucket.this として Terraform で管理したい。import ブロックとして正しいものはどれか。
- ア：import { to = aws_s3_bucket.this  id = "example-bucket" }

- エの意味：import ブロックにラベルは付けない。
- 出典：オリジナル問題（根拠：HashiCorp「import block reference」（『The to argument specifies the instance address to import the resource into.』『The id argument specifies the cloud provider's ID for the resource you want to import.』））

#### 問 tf-14-o10

- 問：HCP Terraform のワークスペースで管理している構成に、CLI の terraform import を使うときの注意点はどれか。
- ア：import はローカルで動くので、ワークスペースの変数に当たるものをローカルで設定する必要がある
