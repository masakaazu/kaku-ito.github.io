## 16-1 プロジェクトとワークスペースの整理

### まとめ表

| 機能 | 何をするか | 覚えどころ |
| :-: | :-: | :-: |
| プロジェクト | ワークスペースをまとめ、権限の範囲を決める | 1 つのワークスペースは 1 つのプロジェクト。Default Project は消せない |
| 変数セット | 同じ変数を複数のワークスペースで使い回す | ワークスペース・プロジェクト・グローバルの範囲 |
| run trigger | 元のワークスペースの apply 成功で、自分に実行を積む | 元は 20 まで。自動 apply は別の設定 |
| リモートステートの共有 | ほかのワークスペースにステートを読ませる | 既定はだれにも共有しない。tfe_outputs がすすめ |

### 整理する

#### プロジェクト（ぷろじぇくと / project）

- 意味：HCP Terraform で、ワークスペース（と Stacks）をまとめるフォルダーのようなもの。チームの権限の範囲にもなる
- ポイント：どのワークスペースも必ず 1 つのプロジェクトに入る。何も指定しなければ Default Project（名前は変えられるが消せない）。プロジェクトの権限は組織全体より細かく、ワークスペースごとより広い。事業部・部署・チームなどで分ける。プロジェクトのタグはワークスペースに受けつがれる

#### プロジェクトの既定の実行モード（ぷろじぇくとのきていのじっこうもーど / project default execution mode）

- 意味：プロジェクトに新しく作るワークスペースが受けつぐ、実行モードの既定値
- ポイント：組織の既定（Remote か Local）を、プロジェクトで Remote・Local・Agent に上書きできる。変えたあとに作るワークスペースが受けつぐ

#### プロジェクトのベストプラクティス（ぷろじぇくとのべすとぷらくてぃす / project best practices）

- 意味：プロジェクトを使うときに HashiCorp がすすめるやり方
- ポイント：TFE プロバイダー（hashicorp/tfe）でプロジェクト・変数セット・チームの作成を自動化する、ほかを作るための「ランディングゾーン」のプロジェクトを置く、プロジェクトの管理者を少なくして最小権限にする、本番のネットワークと開発の計算資源は別のプロジェクトにする、プロジェクトの変数セットで動的な資格情報や共通のタグを配る

#### 変数セット（へんすうせっと / variable set）

- 意味：変数（Terraform の変数と環境変数）の集まりを、複数のワークスペースで使い回すしくみ
- ポイント：範囲はワークスペース単位・プロジェクト単位（今と将来のワークスペースに自動で）・グローバル（組織のすべてに自動で）。組織もプロジェクトも変数セットを持てる。プロバイダーの資格情報を 1 つのセットにして配るのが典型
- 例：AWS の資格情報のセットを、AWS を使うプロジェクトに付ける

#### 変数の優先順位（HCP）（へんすうのゆうせんじゅんい / variable precedence）

- 意味：同じキーの変数がいくつもあるとき、HCP Terraform がどれを使うかの順番
- ポイント：優先（priority）にした変数セットがいちばん強い。次に CLI の -var・-var-file、手元の TF_VAR_、ワークスペース固有の変数、範囲を絞った変数セット、グローバルな変数セット、*.auto.tfvars の順。ワークスペース固有の変数は、同じキーの変数セットの値をいつも上書きする。同じ範囲の変数セットどうしは名前の辞書順で先のものを使う

#### run trigger（らんとりがー / run trigger）

- 意味：元（source）のワークスペースの実行が apply に成功したら、自分のワークスペースに自動で実行を積むつながり
- ポイント：ほかのワークスペースの作った値やインフラに頼るワークスペース向け。1 つのワークスペースに元は 20 まで。設定にはワークスペースの管理者の権限が要る。run trigger からの実行は、ワークスペースの auto-apply とは別の「Auto-apply run triggers」を有効にしないと自動 apply しない

#### リモートステートの共有（りもーとすてーとのきょうゆう / remote state sharing）

- 意味：あるワークスペースのステートを、実行の中でほかのどのワークスペースが読めるかの設定
- ポイント：組織のすべて・同じプロジェクトのすべて・指定したワークスペースのどれか。HCP Terraform の新しいワークスペースの既定は「指定したワークスペース」で、だれも指定されていない（だれも読めない）。最小権限で、必要なものだけに許す。値の受けわたしには terraform_remote_state より tfe_outputs データソースがすすめ

## 16-2 チーム・権限・資格情報

### まとめ表

| ワークスペースの権限 | できること |
| :-: | :-: |
| Read | 実行・変数・ステートを読む |
| Plan | Read ＋ plan を始める（apply は承認が必要） |
| Write | Plan ＋ apply、変数とステートの読み書き、ロック |
| Admin | すべて ＋ 設定（run trigger など）・チームの権限・ワークスペースの削除 |

### 人とアクセス

#### チーム（ちーむ / team）

- 意味：組織の中のユーザーのグループ。ワークスペースやプロジェクトの権限をチームに与える
- ポイント：1 つでもチームに入っていれば組織のメンバー。チームは自分の組織のワークスペースにしか権限を持てないが、ユーザーは複数の組織のチームに入れる。チームごとに、特定のユーザーに結びつかない API トークンを持てる

#### owners チーム（おーなーずちーむ / owners team）

- 意味：どの組織にもある、組織の全権を持つ特別なチーム
- ポイント：組織を作った人が最初のメンバー。削除できず、空にもできない

#### ワークスペースの権限（わーくすぺーすのけんげん / workspace permissions）

- 意味：チームに与える、ワークスペースでできることのまとまり
- ポイント：Read（見るだけ）・Plan（変更を提案する人。apply は承認が必要）・Write（日々の構築。plan と apply、ステートの読み書き、ロック）・Admin（設定・権限・削除も）。細かく選ぶ custom もある。ステートは「出力だけ読む」などに絞れる

#### 動的なプロバイダーの資格情報（どうてきなしかくじょうほう / dynamic provider credentials）

- 意味：実行ごとに一時的な資格情報をクラウドから受け取り、静的な資格情報を置かずに済ませるしくみ
- ポイント：クラウドと HCP Terraform の間に信頼関係を作る。実行ごとに HCP Terraform が OIDC 準拠のワークロード ID トークンを作ってクラウドに送り、クラウドが確かめて一時的な資格情報を返す。実行が終わると捨てる。手でのローテーションが不要。ワークスペースの環境変数か変数セットで設定する（AWS・Azure・GCP・Vault など）
- 語の意味：OIDC＝OpenID Connect（ID の確認のための標準のしくみ）

## 16-3 ガバナンス

### まとめ表

| 機能 | 何をするか |
| :-: | :-: |
| ポリシー（Sentinel・OPA） | 実行ごとに plan がルールに合うか確かめる |
| ヘルス評価 | ドリフト検出と継続的な検証を定期的に |
| プライベートレジストリ | 組織の中でモジュール・プロバイダーを共有 |
| Explorer | 組織中のワークスペース・モジュール・プロバイダー・版を一覧・検索 |
| change requests | ワークスペースに「やること」を記録して担当に知らせる |

### ポリシー

#### ポリシーとしてのコード（ぽりしーとしてのこーど / policy as code）

- 意味：セキュリティやベストプラクティスのルールをコードで書き、Terraform の plan がそれに合うかを実行ごとに確かめること
- ポイント：フレームワークは Sentinel（HashiCorp のポリシー言語）・OPA（Open Policy Agent、Rego 言語）・Terraform policy（HCL）。ポリシーはポリシーセットにまとめ、組織全体・プロジェクト・ワークスペースに付ける。1 つのセットには 1 つのフレームワークだけ。ポリシーは VCS に置いて管理するのがすすめ
- 例：本番を正しいリージョンに作るか、金曜日の新しいデプロイを止めるか

#### ポリシーの強制レベル（きょうせいれべる / policy enforcement levels）

- 意味：ポリシーに合わなかったときに実行をどうするかの設定
- ポイント：Sentinel は advisory（止めずに知らせるだけ）・soft mandatory（止めるが、許された人が上書き（override）して続けられる）・hard mandatory（直すまで apply しない）の 3 つ。OPA は advisory と mandatory（上書きの権限を持つ人なら続けられる）の 2 つ

#### Sentinel（せんちねる / Sentinel）

- 意味：HashiCorp のポリシーとしてのコードのフレームワーク
- ポイント：CLI 駆動の実行では、ポリシーの結果が端末に出る（OPA の結果は CLI に出ない）。soft mandatory に失敗すると「override」と入力して続けられる（権限があれば）

#### OPA（おーぴーえー / Open Policy Agent）

- 意味：Rego という言語でポリシーを書く、オープンソースのポリシーエンジン
- ポイント：HCP Terraform では、Rego のどのルールを結果にするかを query（例 terraform.deny）で決める。強制レベルは advisory と mandatory
- 語の意味：OPA＝Open Policy Agent（オープンな・ポリシーの・代理人）

### 見守る・共有する

#### ヘルス評価（へるすひょうか / health assessments）

- 意味：HCP Terraform がワークスペースのインフラを定期的に確かめる機能。ドリフト検出と継続的な検証からなる
- ポイント：ドリフト検出は実物が設定と合っているか（構成のドリフト）を見る。継続的な検証は precondition・postcondition・check ブロックが apply のあとも通るかを見る（check ブロックがすすめ）。設定を変えるのはワークスペースの管理者。問題があると Health warning を表示する

#### 継続的な検証（けいぞくてきなけんしょう / continuous validation）

- 意味：構成のカスタムな条件が、プロビジョニングのあとも通りつづけているかを定期的に確かめるヘルス評価の 1 つ
- ポイント：例：Web サイトが 200 を返すか、証明書が有効か。check ブロックと、その中のスコープつきデータソースで書く。Terraform v1.3 以上

#### プライベートレジストリ（ぷらいべーとれじすとり / private registry）

- 意味：組織の中だけでモジュールやプロバイダーを共有する、HCP Terraform のレジストリ
- ポイント：公開の Terraform Registry と同じように、版の管理と検索ができる一覧を持つ。公開のプロバイダーやモジュールも追加できる。ソースは <ホスト>/<組織>/<名前>/<プロバイダー> の形（#11）

#### Explorer（えくすぷろーらー / explorer for workspace visibility）

- 意味：組織中のワークスペース・モジュール・プロバイダー・Terraform の版の情報を一覧し、検索できる画面
- ポイント：使える問い合わせの例：よく使われるモジュールの版、古い Terraform の版、VCS のないワークスペース、ドリフトしたワークスペース、継続的な検証に失敗したワークスペース。使うには組織の owner か「View all workspaces」以上の権限が要る

#### change requests（ちぇんじりくえすと / change requests）

- 意味：ワークスペースに「やるべきこと」を記録して、担当のチームに知らせる機能
- ポイント：管理者は Explorer の結果から、選んだワークスペースにまとめて作れる（例：非推奨のモジュールの版を上げる）。対応したらアーカイブする。チームの通知で担当に知らせられる

### 16-1 プロジェクトとワークスペースの整理

#### 問 tf-16-o01

- 問：HCP Terraform のプロジェクトの説明として正しいものはどれか。
- ア：ワークスペースをまとめ、チームのアクセス制御の範囲にもなる
- イ：1 つの Terraform の構成ファイル
- ウ：CLI のワークスペースの別名
- エ：プロバイダーの集まり
- 正解：ア
- 解説：プロジェクトはワークスペース（と Stacks）をまとめ、アクセスの範囲を決める。プロジェクトごとの権限で、チームにプロジェクト内のすべてのワークスペースへのアクセスを与えられる。
- アの意味：正しい。
- イの意味：ちがう。
- ウの意味：別物。
- エの意味：ちがう。
- 出典：オリジナル問題（根拠：HashiCorp「Projects Overview」（『Projects let you organize your workspaces and Stacks and scope access to those workspace and Stack resources.』））

#### 問 tf-16-o02

- 問：ワークスペースとプロジェクトの関係として正しいものはどれか。
- ア：ワークスペースはどのプロジェクトにも入らなくてよい
- イ：どのワークスペースも必ず 1 つのプロジェクトに入り、指定しなければ Default Project に入る
- ウ：1 つのワークスペースは複数のプロジェクトに入れる
- エ：Default Project は自由に削除できる
- 正解：イ
- 解説：ワークスペースと Stack はちょうど 1 つのプロジェクトに入る。既定は組織の Default Project で、名前は変えられるが削除できない。あとで別のプロジェクトに移せる。
- アの意味：必ず入る。
- イの意味：正しい。
- ウの意味：ちょうど 1 つ。
- エの意味：削除できない。
- 出典：オリジナル問題（根拠：HashiCorp「Projects Overview」（『Every workspace and Stack must belong to exactly one project. By default, all workspaces belong to an organization's Default Project. You can rename the default project, but you cannot delete it.』））

#### 問 tf-16-o03

- 問：あるプロジェクトのすべてのワークスペース（これから作るものも含む）に、同じ AWS の資格情報を配りたい。よい方法はどれか。
- ア：ワークスペースごとに同じ変数を手で作る
- イ：設定ファイルに資格情報を書く
- ウ：プロジェクトを範囲にした変数セットを作る
- エ：run trigger を作る
- 正解：ウ
- 解説：プロジェクトを範囲にした変数セットは、プロジェクトの今と将来のワークスペースに自動で付く。資格情報をまとめて配るのに向く（動的な資格情報の設定も配れる）。
- アの意味：手間がかかり、漏れやすい。
- イの意味：資格情報を設定に書かない。
- ウの意味：正しい。
- エの意味：実行をつなぐ機能。
- 出典：オリジナル問題（根拠：HashiCorp「Variables overview」（『Project-Scoped Variable Set』『Automatically applied and available to all current and future workspaces and Stacks within a project.』））

#### 問 tf-16-o04

- 問：変数セットの範囲（scope）にないものはどれか。
- ア：特定のワークスペース
- イ：特定のプロジェクト
- ウ：組織のすべて（グローバル）
- エ：特定の resource ブロック
- 正解：エ
- 解説：変数セットの範囲は、ワークスペース単位・プロジェクト単位・グローバル（組織のすべての今と将来のワークスペース）。resource ブロック単位ではない。
- アの意味：ある。
- イの意味：ある。
- ウの意味：ある。
- エの意味：正しい（ない）。
- 出典：オリジナル問題（根拠：HashiCorp「Variables overview」（『Global Variable Set』『Automatically applied to all current and future workspaces and Stacks within an organization.』））

#### 問 tf-16-o05

- 問：同じキーの変数が、ワークスペース固有の変数と（優先にしていない）変数セットの両方にある。どちらが使われるか。
- ア：ワークスペース固有の変数
- イ：変数セットの値
- ウ：あとで編集したほう
- エ：エラーで実行が止まる
- 正解：ア
- 解説：ワークスペース固有の変数は、同じキーを持つ変数セットの値をいつも上書きする。ただし「優先（priority）」にした変数セットは例外で、より強い。
- アの意味：正しい。
- イの意味：ワークスペース固有の変数が勝つ。
- ウの意味：編集の時刻は関係ない。
- エの意味：止まらない。
- 出典：オリジナル問題（根拠：HashiCorp「Variables overview」（『Workspace-specific variables always overwrite variables from variable sets that have the same key.』））

#### 問 tf-16-o06

- 問：同じワークスペースに付けた 2 つの変数セット A_Variable_Set と B_Variable_Set（範囲・持ち主は同じ）に、同じキーの変数がある。どちらが使われるか。
- ア：あとで編集したほう
- イ：B_Variable_Set
- ウ：A_Variable_Set（名前の辞書順で先）
- エ：両方の値をつなげたもの
- 正解：ウ
- 解説：同じ範囲の変数セットどうしがぶつかると、HCP Terraform は変数セットの名前を辞書順で比べ、先のものの値を使う。編集の時刻は関係ない。
- アの意味：関係ない。
- イの意味：辞書順で後。
- ウの意味：正しい。
- エの意味：つなげない。
- 出典：オリジナル問題（根拠：HashiCorp「Variables overview」（『if you apply A_Variable_Set and B_Variable_Set to the same workspace, HCP Terraform will use any conflicting variables from A_Variable_Set. This is the case regardless of which variable set has been edited most recently.』））

#### 問 tf-16-o07

- 問：ネットワークのワークスペースの apply が成功したら、アプリのワークスペースで自動で実行を始めたい。使う機能はどれか。
- ア：変数セット
- イ：run trigger
- ウ：ドリフト検出
- エ：スペキュラティブプラン
- 正解：イ
- 解説：run trigger は、元のワークスペースの実行が apply に成功したら、自分のワークスペースに実行を積む。ほかのワークスペースの作ったものに頼るワークスペース向け。
- アの意味：変数を使い回す機能。
- イの意味：正しい。
