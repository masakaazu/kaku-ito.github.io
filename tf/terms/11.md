## 11-1 モジュールのしくみとソース

### まとめ表

| ソース | source の書き方 | ポイント |
| :-: | :-: | :-: |
| ローカルパス | "./consul"・"../modules/vpc" | ./ か ../ で始める。インストールせずそのまま使う。version は使えない |
| 公開 Registry | "hashicorp/consul/aws" | <NAMESPACE>/<NAME>/<PROVIDER>。version が使える |
| プライベート Registry | "app.terraform.io/example-corp/k8s-cluster/azurerm" | 先頭にホスト名。HCP Terraform は app.terraform.io |
| GitHub | "github.com/hashicorp/example" | Git の別名。?ref= でタグ・ブランチ・コミット |
| 一般の Git | "git::https://example.com/vpc.git?ref=v1.2.0" | git:: を付ける。?depth=1 で浅いクローン |
| HTTP・S3・GCS | "https://example.com/vpc-module.zip" など | アーカイブを取ってくる |
| サブディレクトリ | "hashicorp/consul/aws//modules/consul-cluster" | // のあとがパッケージの中のディレクトリ |

### しくみ

#### モジュール（もじゅーる / module）

- 意味：いっしょに管理する複数のリソースをまとめた入れ物。1 つのディレクトリにある .tf ファイルの集まり
- ポイント：くり返し作る構成をモジュールにすると、標準化でき、速く同じように作れる。ただし使いすぎると分かりにくくなる。1 つのリソースを包んだだけの薄いモジュールはすすめない
- 例：VPC・サブネット・ルートテーブルをまとめた network モジュール

#### ルートモジュールと子モジュール（るーともじゅーるとこもじゅーる / root module and child module）

- 意味：作業ディレクトリ（plan・apply を実行する場所）の .tf ファイルがルートモジュール、module ブロックで呼ぶものが子モジュール
- ポイント：ルートは子を何度でも呼べ、子がさらに子（入れ子）を呼ぶこともできる。子モジュールのリソースも、ルートと同じワークスペースのステートで管理される

#### module ブロック（もじゅーるぶろっく / module block）

- 意味：子モジュールを呼び出し、そのリソースを作るように指示するブロック
- ポイント：引数は source（必須）・version・モジュール固有の入力・count・for_each（どちらか一方）・providers・depends_on。ラベルはローカル名で、出力は module.<ラベル>.<出力名> で参照する。同じ source を別のラベルで何回でも呼べる

#### source 引数（そーすひきすう / source argument）

- 意味：子モジュールのコードをどこから取るかを指定する、module ブロックの必須の引数
- ポイント：『You must specify a literal string for the source value. This argument does not support template sequences or arbitrary expressions.』。変えたら terraform init をやり直す。init がコードを作業ディレクトリの .terraform/modules にダウンロードする

#### ローカルパス（ろーかるぱす / local paths）

- 意味：./ か ../ で始まる、同じリポジトリの中のモジュールを指す source
- ポイント：インストール（コピー）せずにディスクの上のファイルをそのまま使う。呼び出し側と同じバージョンなので version は使えない。/ やドライブ文字で始まる絶対パスはローカルパスとみなされず、パッケージとしてキャッシュにコピーされる（すすめない）

#### モジュールレジストリ（もじゅーるれじすとり / module registry）

- 意味：Terraform 専用のプロトコルでモジュールを配る場所。バージョン管理を完全にサポートする
- ポイント：公開の Terraform Registry は <NAMESPACE>/<NAME>/<PROVIDER>。HCP Terraform のプライベートレジストリは app.terraform.io/<組織>/<NAME>/<PROVIDER>、Terraform Enterprise は自分のホスト名。どちらでも localterraform.com という汎用ホスト名も使える。プライベートレジストリには CLI 設定のトークンが必要

#### Git のソースと ref（ぎっとのそーすとれふ / Git sources and ref）

- 意味：git:: や github.com で Git リポジトリからモジュールを取るときに、?ref= でタグ・ブランチ・コミットを選ぶしくみ
- ポイント：ref がなければ既定のブランチ（HEAD）を使う。git clone を実行するので、ローカルの Git の資格情報や SSH 鍵を使う。HCP Terraform では SSH 鍵の認証だけ。?depth=1 の浅いクローンでは ref はブランチ名かタグ名で、コミット ID は使えない
- 例：source = "git::https://example.com/vpc.git?ref=v1.2.0"

#### パッケージのサブディレクトリ（ぱっけーじのさぶでぃれくとり / modules in package sub-directories）

- 意味：リポジトリやアーカイブ（パッケージ）の中のサブディレクトリにあるモジュールを、// で指す書き方
- ポイント：// のあとがパッケージの中のパス。?ref= などのクエリはいちばん最後に書く。パッケージ全体を取ってくるので、同じパッケージのほかのモジュールをローカルパスで参照できる
- 例：source = "git::https://example.com/network.git//modules/vpc?ref=v1.2.0"

## 11-2 値の受け渡しとスコープ

### まとめ表

| 向き | しくみ | 書き方 |
| :-: | :-: | :-: |
| 親 → 子 | 子の variable に、module ブロックの引数で渡す | module "web" { servers = 3 } |
| 子 → 親 | 子の output を、親が参照する | module.web.instance_ip |
| 子の中だけ | locals・リソース | 親からは直接見えない |
| プロバイダー | 暗黙の継承か、providers 引数で明示 | providers = { aws = aws.west } |

### スコープ

#### モジュールの入力（もじゅーるのにゅうりょく / module inputs）

- 意味：子モジュールが variable で宣言し、呼び出し側が module ブロックの引数として渡す値
- ポイント：子は親の var.・local.・リソースを直接参照できない。必要な値はすべて引数で渡す。default のない変数は呼び出し側が必ず渡す（必須の入力）

#### モジュールの出力（もじゅーるのしゅつりょく / module outputs）

- 意味：子モジュールが output で外に出し、親が module.<名前>.<出力名> で参照する値
- ポイント：『The resources defined in a module form a self-contained group of resources.』。親は子のリソースの属性を直接参照できない（module.web.aws_instance.x.id は不可）。必要な値は子で output にする
- 例：vpc_id = module.vpc.vpc_id

#### モジュールのカプセル化（もじゅーるのかぷせるか / module encapsulation）

- 意味：モジュールの中の変数・ローカル値・リソースは、そのモジュールの中だけのもので、外とは入力と出力だけでやりとりする考え方
- ポイント：関数にたとえると、variable が引数、output が戻り値、locals が関数の中の変数。名前が同じでも、親の var.region と子の var.region は別の変数

#### モジュールの中のプロバイダー（もじゅーるのなかのぷろばいだー / providers within modules）

- 意味：子モジュールのリソースが、どのプロバイダーの設定を使うかの決まり
- ポイント：プロバイダーの設定（provider ブロック）は構成全体で共有され、ルートモジュールでだけ定義する。子には暗黙に継承されるか、providers 引数で明示して渡す。ほかから呼ばれるモジュールには provider ブロックを書かない（書くと count・for_each・depends_on が使えない）。required_providers（必要なバージョン）は各モジュールが自分で宣言する

#### モジュールの構成（もじゅーるのこうせい / module composition）

- 意味：子モジュールを深く入れ子にせず、ルートで平らに並べ、式（出力 → 入力）でつなぐ書き方
- ポイント：『in most cases we strongly recommend keeping the module tree flat, with only one level of child modules』。小さなモジュールをいろいろな組み合わせで使いまわしやすくなる

#### count・for_each 付きのモジュール（かうんと・ふぉーいーちつきのもじゅーる / multiple module instances）

- 意味：1 つの module ブロックに count か for_each を付けて、同じモジュールを複数作ること
- ポイント：count と for_each はどちらか一方だけ。インスタンスは module.<名前>[0]・module.<名前>["key"] で指す。モジュールの中のリソースを作り直すときは terraform apply -replace=module.example.aws_instance.example のように完全なアドレスを書く

## 11-3 バージョンと公開

### まとめ表

| 項目 | 内容 |
| :-: | :-: |
| version 引数 | レジストリのモジュールだけ。制約に合う、インストール済みのいちばん新しいものを使う |
| 変えたあと | source・version を変えたら terraform init。上げるときは terraform init -upgrade |
| Git のモジュール | version は使えない。?ref=v1.2.0 でタグを指す |
| ~> 1.2.0 | 1.2.x だけ（1.3.0 は不可） |
| 公開の条件 | GitHub の公開リポジトリ・terraform-<PROVIDER>-<NAME>・説明・標準構造・x.y.z のタグ |
| 標準構造 | README・LICENSE・main.tf・variables.tf・outputs.tf・modules/・examples/ |

### バージョン

#### version 引数（ばーじょんひきすう / version argument）

- 意味：レジストリのモジュールについて、使ってよいバージョンを制約の文字列で決める module ブロックの引数
- ポイント：レジストリ（公開・プライベート）のモジュールだけで使える。書かなければ最新版。制約に合うインストール済みのいちばん新しいものを使い、なければ合うものの最新をダウンロードする。外部のモジュールには、予期しない更新を防ぐためバージョンを明示するのがすすめ
- 例：version = "~> 5.0"

#### バージョン制約（ばーじょんせいやく / version constraints）

- 意味：=・!=・>・>=・<・<=・~> とバージョン番号を組み合わせ、カンマでつないだ文字列
- ポイント：~> はいちばん右の数字だけ上がってよい（~> 1.0.4 は 1.0.10 可・1.1.0 不可、~> 1.1 は 1.10 可・2.0 不可）。= は 1 つだけ。プレリリース（1.2.0-beta）は = か演算子なしでだけ選べる

#### terraform init -upgrade（てらふぉーむいにっとあっぷぐれーど / terraform init -upgrade）

- 意味：インストール済みのモジュール（とプロバイダー）を、制約が許すいちばん新しいバージョンに上げるオプション
- ポイント：init だけでは、すでにインストールされているものが制約に合えばそのまま使う。version を変えたときや、新しい版を取りこみたいときに -upgrade を付ける

#### 標準モジュール構造（ひょうじゅんもじゅーるこうぞう / standard module structure）

- 意味：再利用するモジュールにすすめられる、ファイルとディレクトリの並べ方
- ポイント：必須はルートモジュール（リポジトリの直下の .tf）だけ。README・LICENSE・main.tf・variables.tf・outputs.tf をおき、入れ子のモジュールは modules/、使い方の例は examples/ に。変数と出力には description を書く。README のある入れ子モジュールは外から使ってよいもの、ないものは内部用（あくまで目安）

#### Registry へのモジュールの公開（れじすとりへのもじゅーるのこうかい / publishing modules）

- 意味：公開の Terraform Registry にモジュールを載せること
- ポイント：条件は GitHub の公開リポジトリ・名前が terraform-<PROVIDER>-<NAME>（例：terraform-aws-ec2-instance）・リポジトリの説明・標準モジュール構造・x.y.z のセマンティックバージョンのタグ（v は付けてもよい）。新しい版は正しいタグを push するだけで出せる

#### プライベートレジストリ（ぷらいべーとれじすとり / private registry）

- 意味：HCP Terraform や Terraform Enterprise にある、組織の中だけでモジュールやプロバイダーを共有するレジストリ
- ポイント：source は app.terraform.io/<組織>/<NAME>/<PROVIDER>（Enterprise は自分のホスト名、どちらでも localterraform.com 可）。GitHub の公開リポジトリという条件はいらない。CLI からはトークンで認証する

### 11-1 モジュールのしくみとソース

#### 問 tf-11-o01

- 問：terraform plan や terraform apply を実行するディレクトリにある .tf ファイルの集まりを何と呼ぶか。
- ア：子モジュール
- イ：入れ子モジュール
- ウ：公開モジュール
- エ：ルートモジュール
- 正解：エ
- 解説：作業ディレクトリの .tf ファイルがルートモジュールになる。ルートモジュールが module ブロックで呼ぶものが子モジュール。
- アの意味：module ブロックで呼ばれる側。
- イの意味：子モジュールがさらに呼ぶモジュール。
- ウの意味：Registry に公開されたモジュールのことで、階層の名前ではない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：HashiCorp「Creating Modules」（『The .tf files in your working directory when you run terraform plan or terraform apply together form the root module.』））

#### 問 tf-11-o02

- 問：同じリポジトリの modules/vpc にあるモジュールを呼ぶ source として正しいものはどれか。
- ア：source = "./modules/vpc"
- イ：source = "modules/vpc"
- ウ：source = "/modules/vpc"
- エ：source = local.vpc_path
- 正解：ア
- 解説：ローカルパスは ./ か ../ で始めて、レジストリのアドレスと区別する。
- アの意味：正しい。
- イの意味：./ がないと、レジストリのアドレスとみなされる。
- ウの意味：/ で始まる絶対パスはローカルパスとして扱われず、パッケージとしてコピーされる（すすめない）。
- エの意味：source にはリテラルの文字列しか書けない。
- 出典：オリジナル問題（根拠：HashiCorp「Module Sources」（『A local path must begin with either ./ or ../ to indicate that a local path is intended, to distinguish from a module registry address.』））

#### 問 tf-11-o03

- 問：source に変数やテンプレートを使って source = "./modules/${var.env}" と書いた。どうなるか。
- ア：var.env の値に合わせてモジュールが切りかわる
- イ：terraform init -upgrade を付ければ使える
- ウ：source はリテラルの文字列だけなので、エラーになる
- エ：既定のブランチのモジュールが使われる
- 正解：ウ
- 解説：source はモジュールのインストール（init）のときに必要なので、リテラルの文字列で書く。テンプレートや任意の式は使えない。
- アの意味：切りかえはできない。環境ごとに変えたいなら別の module ブロックや別のルートモジュールにする。
- イの意味：-upgrade とは関係ない。
- ウの意味：正しい。
- エの意味：ブランチの話ではない。
- 出典：オリジナル問題（根拠：HashiCorp「module block reference」（『You must specify a literal string for the source value. This argument does not support template sequences or arbitrary expressions.』））

#### 問 tf-11-o04

- 問：公開の Terraform Registry のモジュールを指す source の形として正しいものはどれか。
- ア：<PROVIDER>/<NAMESPACE>/<NAME>
- イ：<NAMESPACE>/<NAME>/<PROVIDER>
- ウ：registry::<NAME>
- エ：terraform-<PROVIDER>-<NAME>
- 正解：イ
- 解説：公開 Registry は <NAMESPACE>/<NAME>/<PROVIDER>（例：hashicorp/consul/aws）。ほかのレジストリなら先頭に <HOSTNAME>/ を付ける。
- アの意味：並びがちがう。
- イの意味：正しい。
- ウの意味：そういう接頭辞はない。
- エの意味：公開するときの GitHub リポジトリの名前の形。
- 出典：オリジナル問題（根拠：HashiCorp「Module Sources」（『Modules on the public Terraform Registry can be referenced using a registry source address of the form <NAMESPACE>/<NAME>/<PROVIDER>』））

#### 問 tf-11-o05

- 問：HCP Terraform（SaaS）のプライベートレジストリのモジュールを指す source として正しいものはどれか。
- ア：app.terraform.io/example-corp/k8s-cluster/azurerm
- イ：registry.terraform.io/private/k8s-cluster
- ウ：git::app.terraform.io/k8s-cluster
- エ：example-corp/k8s-cluster（ホスト名は書けない）
- 正解：ア
- 解説：ほかのレジストリのモジュールは、先頭にホスト名を付ける。HCP Terraform の SaaS 版のホスト名は app.terraform.io。
- アの意味：正しい。
- イの意味：公開 Registry のホスト名で、private という書き方もない。
- ウの意味：レジストリは Git のソースではない。
- エの意味：ホスト名を書かないと公開 Registry を探す。
- 出典：オリジナル問題（根拠：HashiCorp「Module Sources」（『If you are using the SaaS version of HCP Terraform, its private registry hostname is app.terraform.io.』））

#### 問 tf-11-o06

- 問：Git リポジトリのモジュールの v1.2.0 のタグを使いたい。正しい source はどれか。
- ア：source = "git::https://example.com/vpc.git" と version = "1.2.0"
- イ：source = "git::https://example.com/vpc.git@v1.2.0"
- ウ：source = "git::https://example.com/vpc.git#v1.2.0"
- エ：source = "git::https://example.com/vpc.git?ref=v1.2.0"
- 正解：エ
- 解説：Git のソースは ?ref= で git checkout に渡せる参照（ブランチ・タグ・SHA-1）を選ぶ。version 引数はレジストリのモジュールだけで使える。
- アの意味：Git のソースに version は使えない。
- イの意味：そういう書き方はない。
- ウの意味：そういう書き方はない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：HashiCorp「Module Sources」（『You can override this using the ref argument.』『source = "git::https://example.com/vpc.git?ref=v1.2.0"』））

#### 問 tf-11-o07

- 問：Git のソースで ?ref= を書かなかったとき、どれが使われるか。
- ア：いちばん新しいタグ
- イ：いちばん古いコミット
- ウ：既定のブランチ（HEAD が指すもの）
- エ：エラーになり、ref が必須だと表示される
- 正解：ウ
- 解説：ref がなければ、リポジトリの既定のブランチ（HEAD）をクローンして使う。いつ変わるか分からないので、本番ではタグで固定するのがよい。
- アの意味：タグを自動で選ぶことはない。
- イの意味：古いコミットは使わない。
- ウの意味：正しい。
- エの意味：ref は省略できる。
- 出典：オリジナル問題（根拠：HashiCorp「Module Sources」（『By default, Terraform will clone and use the default branch (referenced by HEAD) in the selected repository.』））

#### 問 tf-11-o08

- 問：リポジトリ network.git の modules/vpc ディレクトリにあるモジュールを、タグ v1.2.0 で使う source はどれか。
- ア：git::https://example.com/network.git/modules/vpc?ref=v1.2.0
- イ：git::https://example.com/network.git//modules/vpc?ref=v1.2.0
- ウ：git::https://example.com/network.git?ref=v1.2.0//modules/vpc
- エ：git::https://example.com/network.git?path=modules/vpc&ref=v1.2.0

- アの意味：正しい。
- イの意味：利用者が上げられなくなる。
- ウの意味：古い非互換のバージョンで動いてしまう。
- エの意味：上限だけでは意味がない。
- 出典：オリジナル問題（根拠：HashiCorp「Version constraints」（『Reusable modules should constrain only their minimum allowed versions of Terraform and providers, such as >= 0.12.0.』『Root modules should use a ~> constraint』））

#### 問 tf-11-o30

- 問：プライベートレジストリについて正しいものはどれか。
- ア：公開 Registry と同じく、GitHub の公開リポジトリでなければならない
- イ：source にホスト名を書く必要はない
- ウ：HCP Terraform や Terraform Enterprise にあり、組織の中でモジュールを共有でき、CLI からはトークンで認証する
- エ：version 引数は使えない
- 正解：ウ
- 解説：HCP Terraform と Terraform Enterprise にはプライベートレジストリがあり、組織の中だけでモジュールを共有できる。source にはホスト名を付け、CLI 設定のトークンで認証する。レジストリなので version も使える。
- アの意味：GitHub の公開リポジトリの条件は公開 Registry だけ。
- イの意味：ホスト名（app.terraform.io など）を付ける。
- ウの意味：正しい。
- エの意味：レジストリのモジュールなので使える。
- 出典：オリジナル問題（根拠：HashiCorp「Modules overview」（『HCP Terraform and Terraform Enterprise include a private module registry for sharing modules internally within your organization.』）／「Module Sources」（『you may need to configure an access token in the CLI config』））
