## 10-1 sensitive とステートの保護

### まとめ表

| しくみ | 画面（CLI・HCP の UI） | ステート・プランファイル | 使えるバージョン |
| :-: | :-: | :-: | :-: |
| sensitive = true | (sensitive value) と隠す | 平文で残る | 0.15 から |
| ephemeral = true | ― | 残さない | 1.10 から |
| sensitive と ephemeral の両方 | 隠す | 残さない | 1.10 から |
| write-only 引数（_wo） | ― | 残さない（バージョン引数だけ残る） | 1.11 から |

### 隠す・守る

#### sensitive 引数（せんしてぃぶひきすう / sensitive argument）

- 意味：variable や output に sensitive = true と書き、CLI の出力と HCP Terraform の UI でその値を (sensitive value) と隠す引数
- ポイント：その値を参照した式も自動で sensitive になる（リソースの password など）。ただし『Terraform stores values with the sensitive argument in both state and plan files』。terraform output -json・-raw では平文で出る
- 例：variable "database_password" { type = string  sensitive = true }

#### ステートの中の機密データ（すてーとのなかのきみつでーた / sensitive data in state）

- 意味：ステートファイルとプランファイルには、リソースの属性として初期パスワードや API トークンなどが入りうること
- ポイント：ローカルのステートは平文のファイル。ステートそのものを機密として扱い、Git に入れない。設定に秘密を直接書くと、ステートとプランにも残る

#### ステートを守るベストプラクティス（すてーとをまもるべすとぷらくてぃす / state security best practices）

- 意味：機密を含むステートを守るために HashiCorp がすすめる 4 つの対策
- ポイント：リモートに置く・保存時に暗号化する・アクセス制御でさわれる人を絞る・監査ログでアクセスを追う。リモートのステートは使う間だけメモリに置く。HCP Terraform は保存時に暗号化し、S3 バックエンドは encrypt を有効にすると暗号化する。暗号化のしかたはバックエンドごとにちがう

#### HCP Terraform の sensitive な変数（えいちしーぴーてらふぉーむのせんしてぃぶなへんすう / sensitive workspace variables）

- 意味：HCP Terraform のワークスペースの変数で「Sensitive」にチェックを入れたもの
- ポイント：『Marking a variable as sensitive makes it write-only』。作った本人も UI や API で値を見られない。値は変えられるが、ほかの属性を変えるには消して作り直す。資格情報は Terraform 変数より環境変数で渡すのがおすすめ

## 10-2 ephemeral と write-only 引数

### まとめ表

| しくみ | 書き方 | ポイント |
| :-: | :-: | :-: |
| ephemeral な変数 | variable { ephemeral = true } | provider ブロックなど一時的な場所でだけ使える |
| ephemeral な出力 | 子モジュールの output { ephemeral = true } | ルートモジュールの output には付けられない |
| ephemeral ブロック | ephemeral "random_password" "db" { … } | 実行の間だけある一時的なリソース。open → renew → close |
| write-only 引数 | password_wo = …・password_wo_version = 1 | 値は保存しない。更新はバージョン引数を上げる |

### 一時的な値

#### 一時的な値（いちじてきなあたい / ephemeral values）

- 意味：実行中だけ使えて、ステートファイルとプランファイルにはまったく残らない値
- ポイント：作り方は 3 つ。変数・子モジュールの出力の ephemeral 引数、ephemeral ブロック、管理リソースの write-only 引数。残らないので、とっておきたい値はほかのリソース（シークレットの保管庫など）に入れておく

#### 一時的な値を参照できる場所（いちじてきなあたいをさんしょうできるばしょ / ephemeral contexts）

- 意味：一時的な値を参照してよい、限られた場所
- ポイント：locals・ephemeral = true の variable・ephemeral = true の子モジュールの output・write-only 引数・ephemeral ブロック・provider ブロック・provisioner と connection ブロック。ふつうの引数で参照すると plan のときにエラー

#### ephemeral ブロック（いふぇめらるぶろっく / ephemeral block）

- 意味：今の Terraform の実行の間だけある、一時的なリソースを宣言するブロック（v1.10 から）
- ポイント：プロバイダーごとに用意されている（random_password・aws_secretsmanager_secret_version・vault_kv_secret_v2 など）。参照は ephemeral.<型>.<名前>.<属性>。入力に計画では分からない値があると、apply まで実行を遅らせる
- 例：ephemeral "random_password" "db_password" { length = 16 }

#### ephemeral リソースのライフサイクル（いふぇめらるりそーすのらいふさいくる / ephemeral resource lifecycle）

- 意味：ephemeral リソースに特有の、開く（open）・更新する（renew）・閉じる（close）の流れ
- ポイント：結果が必要なら開き、期限より長く使うならプロバイダーに更新を頼み、依存するプロバイダーの作業が終わったら閉じる。Vault のシークレットなら、リースを取る → リースを延長する → リースを終わらせる

#### write-only 引数（らいとおんりーひきすう / write-only arguments）

- 意味：管理リソースの引数のうち、実行中にだけプロバイダーへ渡し、ステートにもプランにも残さないもの（v1.11 から）
- ポイント：名前はふつう _wo で終わり、対になる _wo_version 引数がある。値を保存しないので plan で差分を出せない。ほかの一時的なしくみとちがい、ふつうの値（文字列のリテラルなど）も受け付けるが、ephemeral な値を渡すのがおすすめ
- 例：password_wo = ephemeral.random_password.db_password.result

#### バージョン引数（ばーじょんひきすう / version argument）

- 意味：write-only 引数と対になり、ステートに保存される番号の引数（password_wo_version など）
- ポイント：write-only の値を変えても Terraform は気づけないので、バージョン引数を 1 → 2 と上げると、変更を計画して新しい値をプロバイダーに渡す。しくみはプロバイダーごとに決まる

## 10-3 Vault と一時的な資格情報

### まとめ表

| 方法 | 何をするか | 注意 |
| :-: | :-: | :-: |
| Vault のデータソース | vault_aws_access_credentials などで、ほかのプロバイダー用の資格情報を Vault から借りる | 読んだ値はステート・プランに平文で残る |
| Vault の子トークン | Terraform は短い TTL（既定 20 分）の子トークンを作って使う | plan のあと時間がたつと apply が失敗しうる |
| Vault の ephemeral リソース | ephemeral "vault_kv_secret_v2" で読む | ステートに残さない |
| HCP の動的な資格情報 | OIDC のトークンで、実行ごとに一時的な資格情報をもらう | 実行が終わると捨てる |

### Vault

#### HashiCorp Vault（はしこーぷぼると / HashiCorp Vault）

- 意味：シークレット（パスワード・API キー・証明書など）を保管し、必要なときに一時的な資格情報を発行する HashiCorp の製品
- ポイント：Terraform からは Vault プロバイダーで使う。用途は 2 つ。① Vault そのものを設定し、シークレットを入れる ② Vault から資格情報を借りて、ほかのプロバイダーの認証に使う

#### Vault プロバイダー（ぼるとぷろばいだー / Vault provider）

- 意味：Terraform から Vault を読み書き・設定するためのプロバイダー
- ポイント：『Interacting with Vault from Terraform causes any secrets that you read and write to be persisted in both Terraform's state file and in any generated plan files』。アドレスとトークンは設定に書かず、環境変数 VAULT_ADDR・VAULT_TOKEN で渡すのがおすすめ

#### 一時的な資格情報（いちじてきなしかくじょうほう / short-lived credentials）

- 意味：Vault の AWS シークレットエンジンなどが、必要なときに発行し、期限がくると無効にする資格情報
- ポイント：Terraform を動かす人やシステムは、適切な権限の Vault トークンだけを持てばよい。長く使う静的なアクセスキーを配らずにすむ。AWS プロバイダーの認証に使う資格情報は更新（renew）できないので、Terraform が終わるまでもつリース期間にする
- 例：data "vault_aws_access_credentials" "creds" { backend = … role = … } → provider "aws" { access_key = data.vault_aws_access_credentials.creds.access_key … }

#### 子トークンと TTL（こどーくんとてぃーてぃーえる / child token and TTL）

- 意味：Vault プロバイダーが、渡されたトークンから作る、有効期間（TTL）の短い子トークン
- ポイント：既定は約 20 分（max_lease_ttl_seconds で変更）。期限がくると Vault が発行した資格情報を取り消すので、漏れたときの被害を減らせる。ただしデータソースは plan で読んでプランに書くので、時間をおいて apply すると失敗しうる。静的なシークレット（KV など）は取り消せない

#### 動的なプロバイダー資格情報（どうてきなぷろばいだーしかくじょうほう / dynamic provider credentials）

- 意味：HCP Terraform が、実行（plan・apply）ごとに新しい一時的な資格情報をクラウドからもらうしくみ
- ポイント：HCP Terraform が OIDC 準拠のワークロード ID トークンを作り、クラウドが公開鍵で確かめて一時的な資格情報を返す。実行が終わると捨てる。静的な資格情報をワークスペースに置かず、ローテーションもいらない。AWS・Azure・GCP・Vault などに対応

- 問：データベースのパスワードをステートに残さずに作って設定し、あとで取り出せるようにもしたい。最も適切な流れはどれか。
- ア：ephemeral の random_password で作り、Secrets Manager のシークレットの write-only 引数に入れ、DB の password_wo にも渡す
- イ：resource の random_password で作り、DB の password に渡す
- ウ：sensitive な変数で受け取り、output に出す
- エ：パスワードを main.tf に書き、.gitignore に main.tf を入れる
- 正解：ア
- 解説：ephemeral で作った値はステートに残らない。保管庫の write-only 引数（secret_string_wo）に入れておけば失われず、DB には write-only 引数で渡すので、どこにも Terraform の記録が残らない。
- アの意味：正しい。
- イの意味：ふつうのリソースの値も password もステートに残る。
- ウの意味：ステートに残り、output -raw で平文になる。
- エの意味：設定を VCS に入れられなくなり、本末転倒。
- 出典：オリジナル問題（根拠：HashiCorp「Ephemeral values in resources」（『secret_string_wo = ephemeral.random_password.db_password.result』『Terraform discards the password value without ever storing it.』））

#### 問 tf-10-o30

- 問：ephemeral ブロックに書けないメタ引数はどれか。
- ア：depends_on
- イ：for_each
- ウ：prevent_destroy（lifecycle）
- エ：provider
- 正解：ウ
- 解説：ephemeral ブロックでは count・for_each・depends_on・provider・lifecycle（precondition・postcondition）が使える。ステートに残らず消す計画もないので、prevent_destroy は使えない（resource ブロックだけ）。
- アの意味：書ける。
- イの意味：書ける。
- ウの意味：正しい。
- エの意味：書ける。
- 出典：オリジナル問題（根拠：HashiCorp「ephemeral block reference」（『depends_on list of references』『provider reference』『lifecycle block』）／「lifecycle meta-argument reference」（prevent_destroy：『You can use prevent_destroy in resource blocks.』））
