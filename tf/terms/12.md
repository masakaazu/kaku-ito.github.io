## 12-1 backend ブロックと local バックエンド

### まとめ表

| 決まり | 内容 |
| :-: | :-: |
| 書く場所 | terraform ブロックの中の backend "<種類>" { … }（ルートモジュール） |
| 数 | 1 つの構成に backend は 1 つだけ。cloud ブロックとは同時に書けない |
| 値 | 変数・ローカル値・データソースは参照できない（リテラルだけ） |
| 既定 | local バックエンド（terraform.tfstate） |
| 変えたら | terraform init（-migrate-state で移す・-reconfigure で移さない） |
| 資格情報 | 設定に書かず、環境変数や資格情報ファイルで |
| 部分設定 | 空の backend ＋ init -backend-config=ファイル か KEY=VALUE |

### バックエンド

#### バックエンド（ばっくえんど / backend）

- 意味：Terraform がステートのデータファイルをどこに保存するかを決めるしくみ
- ポイント：ステートをリモートに置くと、複数の人が同じステートを使ってチームで作業できる。組みこみの種類（local・s3・azurerm・gcs・consul・pg・kubernetes・http・remote など）から選び、プラグインで追加はできない。HCP Terraform を使うなら backend ではなく cloud ブロック

#### backend ブロック（ばっくえんどぶろっく / backend block）

- 意味：terraform ブロックの中に書き、バックエンドの種類（ラベル）と、その種類ごとの引数を決めるブロック
- ポイント：1 つの構成に 1 つだけ。『A backend block cannot refer to named values (like input variables, locals, or data source attributes).』。backend の中の値をほかの場所で参照することもできない。cloud ブロックがある構成には書けない
- 例：terraform { backend "s3" { bucket = "mybucket"  key = "path/to/my/key"  region = "us-east-1" } }

#### local バックエンド（ろーかるばっくえんど / local backend）

- 意味：ステートをローカルのファイルシステムに保存し、OS の API でロックし、処理もローカルで行う既定のバックエンド
- ポイント：backend を書かなければこれになる。path の既定はルートモジュールからの terraform.tfstate、workspace_dir は既定以外のワークスペースの置き場所（既定は terraform.tfstate.d）。ステートは平文なので Git には入れない
- 例：backend "local" { path = "relative/path/to/terraform.tfstate" }

#### -state・-state-out・-backup（すてーと・すてーとあうと・ばっくあっぷ / legacy local backend options）

- 意味：local バックエンドで、読むステート・書くステート・バックアップのファイル名を変える CLI のオプション
- ポイント：組みこみのリモートステートがなかったころのための古い機能で、新しいシステムでは使わない。-backup=- でバックアップを作らない。ほかのバックエンドでは効かない

#### バックエンドの移行（ばっくえんどのいこう / backend migration）

- 意味：バックエンドの種類や設定を変えたとき、terraform init で今のステートを新しいバックエンドに移すこと
- ポイント：-migrate-state は今のステートを新しいバックエンドにコピー、-reconfigure は今の設定を無視して移さない。-force-copy は確認せずに移す（-migrate-state も有効になる）。移す前に terraform.tfstate を別の場所に手でバックアップするのが強くすすめられる

#### 部分設定（ぶぶんせってい / partial configuration）

- 意味：backend ブロックに引数の一部（またはすべて）を書かず、残りを terraform init のときに渡すやり方
- ポイント：渡し方は 3 つ。-backend-config=PATH のファイル（名前は *.<バックエンド名>.tfbackend がすすめ）・-backend-config="KEY=VALUE"（シェルの履歴に残るので秘密には向かない）・対話で入力。最低でも空の backend "<種類>" {} を書いておく。まとめた設定は .terraform に平文で保存される
- 例：terraform init -backend-config="./state.config"

#### .terraform ディレクトリのバックエンド設定（どっとてらふぉーむのばっくえんどせってい / .terraform/terraform.tfstate）

- 意味：init が作る .terraform/terraform.tfstate に保存される、今の作業ディレクトリのバックエンドの設定
- ポイント：インフラのステート（バックエンドに保存される terraform.tfstate）とはまったく別のファイル。資格情報が入りうるので .terraform を Git に入れない。プランファイルにもこの設定が入り、保存したプランを apply するときはプランの中の設定を使う

## 12-2 ステートのロック

### まとめ表

| しくみ | 内容 |
| :-: | :-: |
| いつ | ステートに書きこむおそれのあるすべての操作で自動。メッセージは出ない |
| 失敗したら | 先に進まない。時間がかかればメッセージを出す |
| -lock=false | ロックしない（すすめない） |
| -lock-timeout=3s | ロックを取れるまで、その時間だけ再試行する |
| force-unlock LOCK_ID | 自分のロックが自動で外れなかったときに手で外す。インフラは変えない |
| S3 | use_lockfile = true（S3 のロックファイル）。DynamoDB のロックは非推奨 |

### ロック

#### ステートのロック（すてーとのろっく / state locking）

- 意味：バックエンドが対応していれば、ステートに書きこむおそれのある操作の間、ほかの人がロックを取れないようにして、ステートがこわれるのを防ぐしくみ
- ポイント：自動で行われ、メッセージも出ない。ロックが取れなければ Terraform は先に進まない。すべてのバックエンドが対応しているわけではない（各バックエンドのドキュメントに書いてある）。local バックエンドは OS の API でロックする

#### -lock=false（ろっくふぉるす / -lock=false）

- 意味：その操作の間、ステートのロックを取らないようにするオプション
- ポイント：『This is dangerous if others might concurrently run commands against the same workspace.』。ほとんどのコマンドで使えるが、すすめない

#### -lock-timeout（ろっくたいむあうと / -lock-timeout=DURATION）

- 意味：ロックがほかの人に取られているとき、すぐエラーにせず、指定した時間だけロックを取りなおすオプション
- ポイント：数字と単位の文字で書く（"3s" は 3 秒）。-lock=false のときは効かない。CI でほかの実行が終わるのを少し待ちたいときに使う

#### terraform force-unlock（てらふぉーむふぉーすあんろっく / terraform force-unlock）

- 意味：自動でロックが外れなかったときに、ステートのロックを手で外すコマンド
- ポイント：引数にロック ID（ロックの失敗時に表示される、一意の ID）が必須。インフラは変えない。ほかの人がロックを持っているときに外すと同時に書きこまれるおそれがあるので、自分のロックにだけ使う。-force で確認を省く。ローカルのステートのロックは、ほかのプロセスからは外せない
- 例：terraform force-unlock 6638e010-8fb0-46cf-966d-21e806602f3a

#### S3 バックエンドのロック（えすすりーばっくえんどのろっく / S3 backend locking）

- 意味：S3 バックエンドで、use_lockfile = true にして、S3 のロックファイルでステートをロックするしくみ
- ポイント：use_lockfile の既定は false。DynamoDB のテーブル（dynamodb_table、パーティションキー LockID）を使うロックは非推奨で、今後のバージョンでなくなる。バケットのバージョニングを有効にして、誤って消したときに戻せるようにするのが強くすすめられる。暗号化は encrypt

## 12-3 リモートステートの共有と CLI のワークスペース

### まとめ表

| しくみ | 何をするか | 注意 |
| :-: | :-: | :-: |
| terraform_remote_state | ほかの構成のルートモジュールの出力を読む | 使う人はステート全体を読める権限が必要 |
| tfe_outputs | HCP Terraform のワークスペースの出力を読む | HCP では terraform_remote_state よりこちら |
| 公開用の場所 | SSM パラメーター・Consul・DNS などに書いて、ほかで読む | アクセス制御を分けられる（すすめ） |
| CLI のワークスペース | 1 つの構成・1 つのバックエンドで複数のステート | 資格情報やアクセス制御を分けたい環境の分離には向かない |

### 共有と分離

#### terraform_remote_state データソース（てらふぉーむりもーとすてーとでーたそーす / terraform_remote_state data source）

- 意味：ほかの Terraform の構成のバックエンドから最新のステートを読み、そのルートモジュールの出力値を取りだすデータソース
- ポイント：組みこみのプロバイダー（terraform.io/builtin/terraform）なので設定はいらない。読めるのはルートモジュールの output だけ。ただし使う人はステート全体にアクセスできる必要があり、機密も含まれる。HCP Terraform では tfe_outputs データソースがすすめられる
- 例：data.terraform_remote_state.vpc.outputs.subnet_id

#### 公開用の場所でのデータの共有（こうかいようのばしょでのでーたのきょうゆう / sharing data explicitly）

- 意味：ほかの構成に渡したい値を、SSM パラメーターストア・Consul・S3 のオブジェクト・DNS などに書き出し、使う側はデータソースで読むやり方
- ポイント：ステートそのものを読ませずにすむので、共有する情報とステートで別のアクセス制御にできる。HashiCorp はできるだけこちらをすすめる

#### CLI のワークスペース（しーえるあいのわーくすぺーす / Terraform CLI workspaces）

- 意味：1 つの構成・1 つのバックエンドのまま、名前ごとに別のステートを持てるしくみ
- ポイント：最初は削除できない default ワークスペースだけ。terraform workspace new・select・list・show・delete で操作する。local バックエンドでは terraform.tfstate.d に保存。HCP Terraform のワークスペースとは別物。すべてのバックエンドが複数のワークスペースに対応しているわけではない（s3・azurerm・gcs・local・remote などは対応）

#### terraform.workspace（てらふぉーむわーくすぺーす / terraform.workspace）

- 意味：設定の中で、今選んでいるワークスペースの名前を表す値
- ポイント：ワークスペースによって台数を変えたり、名前やタグに入れたりする。count = terraform.workspace == "default" ? 5 : 1

#### ワークスペースが向かない使い方（わーくすぺーすがむかないつかいかた / when not to use workspaces）

- 意味：CLI のワークスペースでは分けるべきでない場合
- ポイント：『Workspaces are not appropriate for system decomposition or deployments requiring separate credentials and access controls.』。同じバックエンドを使うので、開発・本番のように資格情報やアクセス制御を分けたい環境の分離には、ルートモジュール（ディレクトリ）やバックエンドを分けるほうがよい。機能ブランチ用の一時的なコピーには向く

#### 問 tf-12-o02

- イの意味：正しい。
- ウの意味：default の有無は関係ない。

- 出典：オリジナル問題（根拠：HashiCorp「Backend block configuration overview」（『A backend block cannot refer to named values (like input variables, locals, or data source attributes).』））

#### 問 tf-12-o04

- 問：S3 バックエンドのアクセスキーの渡し方として、HashiCorp がすすめるものはどれか。

If you use -backend-config or hardcode these values directly in your configuration, Terraform will include these values in both the .terraform subdirectory and in plan files.』））

#### 問 tf-12-o05

- 問：local バックエンドから S3 バックエンドに変えて、今のステートを S3 に移したい。正しい手順はどれか。
- ア：terraform apply を実行すると自動で移る

- アの意味：バックエンドを変えたあとは、init をしないと plan・apply できない。
- イの意味：正しい。
- ウの意味：今の設定を無視し、ステートは移さない。
- エの意味：init でバックエンドを設定しないと使えない。
- 出典：オリジナル問題（根拠：HashiCorp「Backend block configuration overview」（『When you change backends, Terraform gives you the option to migrate your state to the new backend.』『we strongly recommend manually backing up your state by copying your terraform.tfstate file to another location.』）／「Command: init」（『The -migrate-state option will attempt to copy existing state to the new backend』））

- 問：新しいワークスペースで terraform plan を実行した。ほかのワークスペースで作ったリソースについて正しいものはどれか。
- ア：実物は残っているが、このワークスペースのステートにはないので、このワークスペースからは管理されない
- イ：このワークスペースにもコピーされ、変更が計画される
- ウ：自動で削除される
- エ：plan がエラーになる
- 正解：ア
- 解説：新しいワークスペースの plan は、ほかのワークスペースのリソースにアクセスしない。リソースは実在するが、管理するにはそのワークスペースに切りかえる。
- アの意味：正しい。
- イの意味：ステートは別々。
- ウの意味：削除はされない。
- エの意味：エラーにはならない（新しく作る計画になる）。
- 出典：オリジナル問題（根拠：HashiCorp「Workspaces」（『When you run terraform plan in a new workspace, Terraform does not access existing resources in other workspaces. These resources still physically exist, but you must switch workspaces to manage them.』））

#### 問 tf-12-o30

- 問：リモートステートの利点として、ドキュメントが挙げているものはどれか。
- ア：ステートが暗号化されなくなり、速くなる
- イ：plan が不要になる
- ウ：チームで共有でき、出力を読み取り専用でほかのチームに渡せる
- エ：プロバイダーがいらなくなる
- 正解：ウ
- 解説：リモートステートはチーム全員で共有でき、出力をほかの構成と共有して、インフラを小さな部品に分けられる。中核のチームが作ったものを、ほかのチームが読み取り専用で使える。
- アの意味：多くのバックエンドは保存時の暗号化に対応する。
- イの意味：関係ない。
- ウの意味：正しい。
- エの意味：関係ない。
- 出典：オリジナル問題（根拠：HashiCorp「Remote State」（『With remote state, Terraform writes the state data to a remote data store, which can then be shared between all members of a team.』『remote state also allows teams to share infrastructure resources in a read-only way』））
