## 05-1 実行計画を作って読む

### まとめ表

| 記号 | 意味 |
| :-: | :-: |
| + | 作る（create） |
| - | 消す（destroy） |
| ~ | その場で変える（update in-place） |
| -/+ | 消してから作り直す（destroy and then create replacement） |
| +/- | 作ってから古いものを消す（create_before_destroy のとき） |
| <= | データソースを読む（read） |

### 計画

#### 実行計画（じっこうけいかく / execution plan）

- 意味：Terraform がインフラに対してしようとしている変更（作る・変える・消す）の一覧。terraform plan が作る
- ポイント：plan はまず実物を読んでステートを最新にし、設定と前のステートを比べ、実物を設定に合わせるための変更を提案する。plan だけでは変更は行われない。変更がなければ『no actions need to be taken』と表示する

#### terraform plan（てらふぉーむぷらん / terraform plan）

- 意味：実行計画を作って表示するコマンド
- ポイント：適用の前に、変更が思いどおりかを確かめたり、チームでレビューしたりするのに使う。ふつうはオプションなしで使えるように設定を作る。中で validate の確認もふくむ

#### 投機的プラン（とうきてきぷらん / speculative plan）

- 意味：-out を付けずに terraform plan を実行したときの計画。結果を見るためだけで、適用するつもりはない
- ポイント：コードレビューの前に変更の効果を確かめるのに使う。その間にほかの変更があると最終の結果は変わりうるので、適用の前に最終の計画をもう一度確かめる

#### プランファイル（ぷらんふぁいる / saved plan file）

- 意味：terraform plan -out=FILE で保存した計画。あとで terraform apply FILE に渡して、そのとおりに実行する
- ポイント：主に自動化（CI）で使う 2 段階の流れ。名前は tfplan が慣例で、.tf で終わる名前はつけない（設定ファイルとして読まれてエラーになる）。中身は標準の形式ではないが、設定全体・計画した値・入力変数をふくみ、sensitive な値も平文で入る。中身は terraform show FILE で見る

#### 計画の記号（けいかくのきごう / resource action symbols）

- 意味：計画の出力で、各リソースに何をするかを表す記号
- ポイント：+ 作る、- 消す、~ その場で変える、-/+ 消してから作り直す。引数の横の「# forces replacement」は、その変更が作り直しの原因であることを示す。「(known after apply)」は適用するまで値が分からない属性（ID など）

#### -detailed-exitcode（でぃているどいぐじっとこーど / -detailed-exitcode）

- 意味：plan の終了コードで、変更があるかを返すオプション
- ポイント：0＝成功して変更なし、1＝エラー、2＝成功して変更あり。CI でドリフトや変更の有無を見分けるのに使う

## 05-2 計画のモードとオプション

### まとめ表

| 種類 | オプション | 何をするか |
| :-: | :-: | :-: |
| モード | （なし）＝ノーマル | 実物を設定に合わせる |
| モード | -destroy | 管理しているもの全部を消す計画（terraform destroy と同じ） |
| モード | -refresh-only | 外での変更に合わせて、ステートと出力値だけを更新する計画 |
| オプション | -refresh=false | 計画の前の実物の読みこみを省く（速いが外の変更を見落とす） |
| オプション | -replace=ADDR | そのインスタンスを作り直す計画にする |
| オプション | -target=ADDR | そのインスタンスと依存先だけを計画する（例外のときだけ） |
| オプション | -var・-var-file | ルートモジュールの入力変数を渡す |
| オプション | -parallelism=n | 同時に処理する数（既定 10） |

### モードとオプション

#### 計画のモード（けいかくのもーど / planning modes）

- 意味：計画が何を目ざすかを決めるもの。ノーマル・destroy・refresh-only の 3 つ
- ポイント：モードはどれか 1 つだけで、同時に 2 つは選べない。-destroy と -refresh-only は plan と apply の両方で使える

#### -refresh=false（りふれっしゅふぉるす / -refresh=false）

- 意味：計画の前に、ステートを実物に合わせる処理を省くオプション
- ポイント：API の呼び出しが減って速くなるが、外での変更を無視するので、不完全・まちがった計画になるおそれがある

#### -replace（りぷれいす / -replace=ADDRESS）

- 意味：指定したリソースインスタンスを、作り直す（replace）計画にするオプション
- ポイント：実物がこわれた・おかしくなったときに、同じ設定で作り直すのに使う（不変のインフラの考え方）。ふつうなら更新か何もしないところを作り直しにする。昔の terraform taint の代わり

#### -target（たーげっと / -target=ADDRESS）

- 意味：指定したリソースインスタンスと、それが依存するものだけに計画をしぼるオプション
- ポイント：まちがいからの復旧や Terraform の制限の回避など、例外のときだけ使う。ふだん使うとドリフトに気づかず、ステートと設定の関係が分かりにくくなる。大きな設定は、-target ではなく、小さな設定に分ける。count・for_each のときは aws_instance.example[0] のように番号まで書くとその 1 つ、番号なしなら全部

#### -var と -var-file（ばーとばーふぁいる / -var and -var-file）

- 意味：ルートモジュールの入力変数に、コマンドラインで値を渡すオプション。-var は 1 つずつ、-var-file は .tfvars ファイルからまとめて
- ポイント：シェルの引用符が面倒なので、多くの場合 -var-file がすすめられる。= の前後に空白を入れるとエラー（-var "length = 2" は×）。リストなどは Terraform の式で書く（-var 'name=["a","b"]'）

#### リソースグラフ（りそーすぐらふ / dependency graph）

- 意味：Terraform が設定から作る依存関係のグラフ。計画やステートの refresh などに使う
- ポイント：参照（式）と depends_on から辺を作る。依存がすべて済んだノードから並列に処理する。同時に処理する数は既定で 10 で、-parallelism で変えられる。循環（cycle）があるとエラー。terraform graph で DOT 形式に出して Graphviz で絵にできる

## 05-3 apply と destroy

### まとめ表

| 書き方 | 計画 | 承認 |
| :-: | :-: | :-: |
| terraform apply | その場で新しく作る（plan のモード・オプションが使える） | yes の入力（-auto-approve で省略） |
| terraform apply tfplan | 保存した計画をそのまま使う（オプションは付けられない） | 聞かれない（ファイルを渡すことが承認） |
| terraform destroy | destroy モードの計画（＝ apply -destroy） | yes の入力 |
| terraform plan -destroy | 消す計画を見るだけ | なし（実行しない） |

### 適用と削除

#### terraform apply（てらふぉーむあぷらい / terraform apply）

- 意味：実行計画の変更を実行するコマンド
- ポイント：プランファイルを渡さないと、自動で新しい計画を作り、承認を求めてから実行する（automatic plan mode）。このとき plan のモードとオプション（-destroy・-refresh-only・-replace・-var など）が使える

#### 保存した計画の適用（ほぞんしたけいかくのてきよう / saved plan mode）

- 意味：terraform apply にプランファイルを渡して、その計画どおりに実行すること
- ポイント：承認は聞かれない（ファイルを渡すことが承認とみなされる）。計画はもう決まっているので、モードやオプションを追加で指定できない。先に terraform show で中身を確かめる

#### -auto-approve（おーとあぷるーぶ / -auto-approve）

- 意味：apply・destroy で、計画の承認の入力を省くオプション
- ポイント：使うなら、Terraform の外でインフラを変えられないようにしておくのがすすめられる（ドリフトの危険を減らす）。プランファイルを渡したときは意味がない（無視される）

#### -input=false（いんぷっとふぉるす / -input=false）

- 意味：変数の入力や承認など、対話のプロンプトを全部止めるオプション
- ポイント：apply で付けると、承認も聞けないので、適用しないものとみなして失敗する。自動化では、プランファイルを使うか -auto-approve を付ける。-json は -input=false をふくむ

#### terraform destroy（てらふぉーむですとろい / terraform destroy）

- 意味：設定で管理しているすべてのリモートのオブジェクトを消すコマンド
- ポイント：terraform apply -destroy の別名。開発用の一時的な環境の片づけに便利。プランファイルは受け取らない。-target で特定のリソースと、それに依存するものだけを消せる。消す計画を見るだけなら terraform plan -destroy

#### 消す順番（けすじゅんばん / destroy order）

- 意味：Terraform は依存関係にしたがって、作るときと逆の順番で消す
- ポイント：グラフでは、作り直すリソースを「消すノード」と「作るノード」に分ける（消す順番と作る順番がちがうため）。設定から消えて、ステートにだけあるもの（orphan）も消す対象になる

### 05-1 実行計画を作って読む

#### 問 tf-05-o01

- 問：terraform plan が既定で行うこととして、ふくまれないものはどれか。
- ア：すでにある実物の今の状態を読み、ステートを最新にする
- イ：計画した変更を実物に適用する
- ウ：今の設定と前のステートを比べ、ちがいを見つける

- 正解：イ
- 解説：plan は実物を読む・設定と比べる・変更を提案するまで。提案した変更を実行はしない。
- アの意味：ふくまれる（refresh）。
- イの意味：正しい（ふくまれない）。適用は apply。
- ウの意味：ふくまれる。
- エの意味：ふくまれる。
- 出典：オリジナル問題（根拠：HashiCorp「Command: plan」（『Reads the current state of any already-existing remote objects』『Compares the current configuration to the prior state』『Proposes a set of change actions』『The plan command alone does not actually carry out the proposed changes』））
