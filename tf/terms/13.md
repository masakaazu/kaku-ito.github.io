## 13-1 ドリフトと refresh-only

### まとめ表

| やりたいこと | 方法 | 実物 | ステート |
| :-: | :-: | :-: | :-: |
| 外での変更を取り消し、設定にもどす | terraform plan → apply（ノーマルモード） | 設定に合わせて変える | 更新 |
| 外での変更を受け入れる | 設定を書きかえる（＋ apply -refresh-only） | 変えない | 更新 |
| ステートだけ実物に合わせる | terraform apply -refresh-only | 変えない | 実物に合わせる |
| 変化を見るだけ | terraform plan -refresh-only | 変えない | 変えない |
| terraform refresh（非推奨） | apply -refresh-only -auto-approve と同じ | 変えない | 確認なしで更新 |

### ドリフト

#### ドリフト（どりふと / resource drift）

- 意味：コンソールやほかのツールなど、Terraform の外で実物が変更され、実物とステート・設定がずれること
- ポイント：ふつうの plan は最初に refresh して実物を読むので、ドリフトがあると「Objects have changed outside of Terraform」と表示し、設定にもどす変更を計画する。外での変更を残したいなら、設定のほうを書きかえる

#### 構成のドリフトとステートのドリフト（こうせいのどりふととすてーとのどりふと / configuration drift and state drift）

- 意味：外での変更が設定と食いちがうのが構成のドリフト、設定とは食いちがわない（ステートだけが古い）のがステートのドリフト
- ポイント：HCP Terraform のドリフト検出が見つけるのは構成のドリフトだけ。ステートのドリフトは refresh-only で直す

#### refresh-only モード（りふれっしゅおんりーもーど / refresh-only mode）

- 意味：外での変更にあわせて、ステートとルートモジュールの出力値だけを更新する計画を作るモード
- ポイント：実物は変えない。障害対応などで意図して外から変えたものを、Terraform の記録に取りこむときに使う。plan -refresh-only は見るだけ、apply -refresh-only は確認してからステートに書く。-refresh=false とは同時に使えない
- 例：terraform apply -refresh-only

#### terraform refresh（てらふぉーむりふれっしゅ / terraform refresh）

- 意味：すべての管理リソースの実物を読み、ステートを合わせるコマンド。非推奨
- ポイント：terraform apply -refresh-only -auto-approve と同じで、確認なしにステートを書きかえる。プロバイダーの資格情報がまちがっていると、すべてのリソースが消えたと思いこんで、ステートから全部消してしまうおそれがある。代わりに apply -refresh-only で中身を確かめる

#### ドリフト検出（どりふとけんしゅつ / drift detection）

- 意味：HCP Terraform のヘルス評価のうち、実物が設定と合っているかを定期的に調べる機能
- ポイント：結果はワークスペースの Health > Drift で見る。直し方は、変更がいらなければ新しい実行で上書き、いるなら設定を書きかえて新しい構成のバージョンを push。ヘルス評価を変えたり手動で実行したりするのはワークスペースの管理者

## 13-2 moved ブロック

### まとめ表

| 変えたいこと | moved の書き方 |
| :-: | :-: |
| リソースの名前 | from = aws_instance.a　to = aws_instance.b |
| モジュールの中へ移す | from = aws_instance.a　to = module.web.aws_instance.a |
| モジュール呼び出しの名前 | from = module.a　to = module.b |
| for_each を付ける | from = aws_instance.a　to = aws_instance.a["small"] |
| count から for_each へ | from = aws_instance.a[0]　to = aws_instance.a["small"] |

### 名前を変える

#### moved ブロック（むーぶどぶろっく / moved block）

- 意味：リソースやモジュールのアドレスが変わったことを設定に書き、消して作り直さずにステートの中のアドレスを変えるブロック（v1.1 から）
- ポイント：from（前のアドレス）と to（新しいアドレス）が必須。計画を作る前に from のオブジェクトがステートにあるか確かめ、あれば to に名前を変えてから計画する。結果の計画は、最初から to で作ったかのようになる
- 例：moved { from = aws_instance.a  to = aws_instance.b }

#### アドレスを変えたときの既定のふるまい（あどれすをかえたときのきていのふるまい / default behavior on address change）

- 意味：moved を書かずに resource のラベルを変えると、Terraform は古いアドレスのものを消し、新しいアドレスで作ろうとすること
- ポイント：『By default, Terraform interprets a change as an instruction to destroy the existing resource and create a new resource at the new address.』。データベースなどでは大事故になるので、名前を変えるときは moved を書く

#### インスタンスキーの移動（いんすたんすきーのいどう / moving instance keys）

- 意味：count や for_each を付けたり外したりするときに、どの古いオブジェクトをどのキーにするかを moved で決めること
- ポイント：from か to にキー（["small"] や [0]）があると、リソース全体ではなく特定のインスタンスを指す。count を新しく付けたときは、moved がなければ自動で元のオブジェクトを [0] に移すが、読み手のために moved を書くのがすすめ

#### moved ブロックの削除（むーぶどぶろっくのさくじょ / removing moved blocks）

- 意味：役目を終えた moved ブロックを設定から消すこと
- ポイント：『Removing a moved block is a breaking change』。古いアドレスのままの利用者は、移すのではなく消す計画になる。共有モジュールでは過去の moved をすべて残すのが強くすすめられる。同じものを 2 回動かしたら、moved をつなげて（a → b、b → c）履歴を残す

#### terraform state mv（てらふぉーむすてーとむーぶ / terraform state mv）

- 意味：ステートの中のリソースのアドレスを、CLI で直接変えるコマンド
- ポイント：moved と同じことができるが、計画で確かめられず、記録も残らない。v1.1 より前や、ステートファイルの間での移動に使う古いやり方。今は moved ブロックがすすめられる（#14）

#### moved でできないこと（むーぶどでできないこと / moved limitations）

- 意味：moved ブロックでは変えられないもの
- ポイント：管理リソース（resource）をデータソース（data）に変えることはできない。ちがう型どうしの移動は、プロバイダーが対応している場合だけ

## 13-3 removed ブロックとステートの分割

### まとめ表

| やりたいこと | 方法 |
| :-: | :-: |
| 管理をやめるが、実物は残す | resource を removed { from = …  lifecycle { destroy = false } } に置きかえて apply |
| 実物も消す | resource ブロックを消して apply（または removed で destroy = true） |
| ステートから外す（古いやり方） | terraform state rm（確認できないのですすめない） |
| もう一度管理する | import する（#14） |
| 別のステートへ移す | 元で removed（destroy = false）→ 先で import（すすめ）／state mv（古い） |

### 外す・分ける

#### removed ブロック（りむーぶどぶろっく / removed block）

- 意味：実物を変えずに、リソースをステートから外すためのブロック（v1.7 から）
- ポイント：from に外すリソースのアドレスを書く（count・for_each のリソースでもインスタンスキーは書けない）。lifecycle で使えるのは destroy だけで、既定は実物も消す。destroy = false で実物を残し、管理だけをやめる。外したあとで管理したくなったら import する
- 例：removed { from = aws_instance.example  lifecycle { destroy = false } }

#### removed と state rm のちがい（りむーぶどとすてーとあーるえむのちがい / removed block vs. terraform state rm）

- 意味：どちらもステートからリソースを外すが、removed は設定で計画して確かめてから外し、state rm は CLI ですぐ外す
- ポイント：『we recommend using the removed block instead. This is because the removed block lets you preview the results of the operation, which makes it a safer way to remove resources.』

#### 管理の引きわたし（かんりのひきわたし / handing off management）

- 意味：最初に Terraform で作ったリソースを、ほかのツールやチームの管理に移すこと
- ポイント：removed の destroy = false を使う。実物は残り、Terraform はそれ以降そのリソースの変更も削除もしない

#### ステートの分割（すてーとのぶんかつ / refactoring Terraform state）

- 意味：大きくなった 1 つの構成とステートを、複数の構成・ステートに分けること
- ポイント：きっかけは apply が長い・変更の頻度がちがう・持ち主のチームがちがう・モジュールにできる部分がある。分け方の目安は変化の速さ・状態を持つか（DB とサーバーを分ける）・チームの担当。ほかのステートのリソースは、データソース・tfe_outputs・terraform_remote_state で参照する（値を直接書かない）

#### 削除してインポート（さくじょしてインポート / remove and import）

- 意味：元の構成で removed（destroy = false）で外し、移した先の構成で import ブロックで取りこむ、ステートの間の移し方
- ポイント：removed と import のブロックが設定の履歴として残るので、HashiCorp がすすめる方法（v1.7 から）。terraform state mv で直接移すのは古いやり方。状態を持たないリソースは、止めずに安くできるなら新しい構成で作り直すのがすすめ

#### 問 tf-13-o01

- 問：同僚が AWS コンソールで EC2 インスタンスのタグを書きかえた。設定は変えていない。次の terraform plan（ノーマルモード）について正しいものはどれか。

#### 問 tf-13-o11

- 問：resource "aws_instance" "a" のラベルを "b" に変えた。moved は書いていない。次の plan はどうなるか。
- ア：自動で名前だけ変わる
- イ：エラーで止まる
- ウ：aws_instance.a を消し、aws_instance.b を作る計画になる
- エ：何も変わらない
- 正解：ウ
- 解説：既定では、アドレスの変更は「古いものを消して新しいアドレスで作る」という指示とみなされる。消さずに名前だけ変えるには moved を書く。
- アの意味：moved がなければ名前の変更とはみなされない（count を付けたときの [0] への自動の移動は例外）。
- イの意味：エラーにはならない。
- ウの意味：正しい。
- エの意味：消して作る計画になる。
- 出典：オリジナル問題（根拠：HashiCorp「Refactor modules」（『By default, Terraform interprets a change as an instruction to destroy the existing resource and create a new resource at the new address. You can use a moved block to update a resource address without destroying it.』））
