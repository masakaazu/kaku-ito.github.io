## 07-1 入力変数

### まとめ表

| variable の引数 | 意味 | 既定 |
| :-: | :-: | :-: |
| type | 型の制約 | any |
| default | 既定値（あれば省略できる。リテラルだけ） | なし（なければ必須） |
| description | 使う人に向けた説明 | なし |
| validation | condition と error_message で値を確かめる | なし |
| sensitive | CLI の出力で値を隠す（ステートには残る） | false |
| nullable | null を入れてよいか | true |
| ephemeral | ステートとプランファイルに残さない | false |

### 変数

#### 入力変数（にゅうりょくへんすう / input variable）

- 意味：モジュールに外から値を渡すための引数。variable ブロックで宣言し、var.<NAME> で参照する
- ポイント：ほかの言語の関数の引数にあたる。ルートモジュールの変数は CLI・環境変数・tfvars・HCP Terraform で、子モジュールの変数は親の module ブロックの引数で値を渡す。名前に source・version・providers・count・for_each・lifecycle・depends_on・locals は使えない

#### type（たいぷ / type constraint）

- 意味：変数に入れられる値の型を決める引数
- ポイント：書かなければ any（どの型でもよい）。型を書くと、使う人に必要な値が分かり、ちがう型ならわかりやすいエラーになる。値は型に自動で変換されてから使われる（var. の値はいつも型に合う）

#### default（でふぉると / default）

- 意味：変数の既定値。値が渡されなければこれが使われる
- ポイント：default がない変数は必須で、値がなければ plan の前に入力を求められる（-input=false ならエラー）。default はリテラルで、ほかのオブジェクトを参照できない。type と両方書くと、default は型に変換できなければならない

#### description（でぃすくりぷしょん / description）

- 意味：変数の目的と期待する値の説明
- ポイント：モジュールを使う人の立場で書く。保守する人へのメモは # のコメントに書く。スタイルガイドは、すべての変数に type と description を書くことをすすめる

#### validation（ばりでーしょん / validation）

- 意味：型の制約に加えて、変数の値が満たすべき条件を書くブロック。condition と error_message が必須
- ポイント：計画を作るときに評価し、false ならエラーにして error_message を表示し、止まる
- 例：`validation { condition = contains(["dev", "staging", "prod"], var.environment)  error_message = "Environment must be dev, staging, or prod." }`

#### sensitive（せんしてぃぶ / sensitive）

- 意味：CLI の出力（plan・apply のログ）で値を隠す引数。(sensitive value) と表示される
- ポイント：その変数を使った式も sensitive になる。ステートには平文で残るので、ステートにアクセスできる人は見られる

#### nullable（ぬらぶる / nullable）

- 意味：変数に null を入れてよいかを決める引数
- ポイント：false なら null 以外の値が必要。true で default があるとき、呼ぶ側が明示的に null を渡すと default を上書きして null になる

## 07-2 値の渡し方と優先順位・出力値・ローカル値

### まとめ表

| 優先順位（上ほど強い） | 渡し方 |
| :-: | :-: |
| 1 | コマンドラインの -var・-var-file（書いた順）と HCP Terraform の変数 |
| 2 | *.auto.tfvars・*.auto.tfvars.json（名前の順） |
| 3 | terraform.tfvars.json |
| 4 | terraform.tfvars |
| 5 | 環境変数 TF_VAR_<名前> |
| 6 | variable ブロックの default |

### 渡し方と出力

#### 変数定義ファイル（へんすうていぎふぁいる / variable definition files）

- 意味：変数の値をまとめて書く .tfvars（または .tfvars.json）ファイル。`instance_type = "t3.large"` のように書く
- ポイント：terraform.tfvars・terraform.tfvars.json・*.auto.tfvars・*.auto.tfvars.json は自動で読まれる。それ以外の名前（prod.tfvars など）は -var-file で指定する。秘密の値が入るなら VCS から外す

#### TF_VAR_ 環境変数（てぃーえふばー / TF_VAR_ environment variables）

- 意味：TF_VAR_<変数名> という名前の環境変数で、変数の値を渡すしくみ
- ポイント：ファイルを作らずに値を入れたい CI/CD で便利。リストなどの複雑な型は JSON の書き方で渡す。優先順位は tfvars より低く、default より高い
- 例：`export TF_VAR_instance_type=t3.medium`

#### 変数の優先順位（へんすうのゆうせんじゅんい / variable precedence）

- 意味：同じ変数に複数の場所から値が渡されたとき、どれを使うかの順番
- ポイント：強い順に、-var・-var-file（と HCP Terraform）→ *.auto.tfvars → terraform.tfvars.json → terraform.tfvars → 環境変数 → default。default がいちばん弱い

#### output ブロック（あうとぷっとぶろっく / output block）

- 意味：インフラの情報を外に出すブロック。ほかの言語の関数の戻り値にあたる。value は必須
- ポイント：子モジュールが親に属性を渡す・ルートモジュールが CLI に表示する・terraform_remote_state でほかの設定に渡す・自動化ツールに渡す、に使う。値はステートに保存される。引数は value・description・sensitive・ephemeral・depends_on・precondition

#### terraform output（てらふぉーむあうとぷっと / terraform output）

- 意味：ステートからルートモジュールの出力値を取りだして表示するコマンド
- ポイント：名前を付けるとその値だけ。-json は JSON（jq に渡せる）、-raw は文字列をそのまま出す（文字列・数・真偽値だけ。シェルスクリプト向け）。-json と -raw では sensitive な値も平文で出る

#### ローカル値（ろーかるあたい / local values）

- 意味：式に名前を付けて、モジュールの中で何度も使えるようにするもの。locals ブロックで定義し、local.<NAME> で参照する
- ポイント：ほかの言語の関数の中の変数にあたる。外から値は渡せない（それは入力変数）。変数・リソースの属性・関数の結果・ほかのローカル値を使える。定義は locals（複数形）、参照は local（単数形）。使いすぎると読みにくくなる

## 07-3 型

### まとめ表

| 種類 | 型 | 例 |
| :-: | :-: | :-: |
| プリミティブ型 | string・number・bool | "hello"・15・true |
| コレクション型（同じ型の要素） | list(…)・map(…)・set(…) | list(string)・map(number) |
| 構造型（ちがう型の要素） | object({…})・tuple([…]) | object({ name = string, age = number })・tuple([string, number, bool]) |
| 動的 | any | まだ決まっていない型の置き場所 |

### 型

#### プリミティブ型（ぷりみてぃぶがた / primitive types）

- 意味：ほかの型からできていない単純な型。string（文字列）・number（整数も小数も）・bool（true/false）
- ポイント：number と bool は必要なら string に自動で変換され、その逆も、文字列が正しい数や真偽値を表していれば変換される（true ⇔ "true"、15 ⇔ "15"）

#### コレクション型（これくしょんがた / collection types）

- 意味：同じ 1 つの型の値をまとめた型。list（0 から番号の付いた並び）・map（文字列のキーで値を引く）・set（順番もキーもない、重複しない値の集まり）
- ポイント：要素の型は必ず 1 つ（list(string) と list(number) は別の型）。list・map だけを書くと list(any)・map(any) の省略形だが、新しいコードでは完全な形がすすめられる

#### 構造型（こうぞうがた / structural types）

- 意味：ちがう型の値をまとめた型。object（名前の付いた属性がそれぞれの型を持つ）・tuple（番号の位置ごとに型を持つ）
- ポイント：object は指定したキーが全部必要（多いキーは変換で捨てられる）。tuple は要素の数がぴったり同じでなければならない

#### optional（おぷしょなる / optional object attributes）

- 意味：object 型の属性を省略できるようにする修飾子。optional(型, 既定値)
- ポイント：既定値を書かなければ null。既定値が null でなければ、モジュールの中では null にならない（呼ぶ側が省いても、null を渡しても既定値になる）
- 例：`type = object({ a = string  b = optional(string)  c = optional(number, 127) })`

#### 型の変換（かたのへんかん / type conversion）

- 意味：渡した値が求める型とちがうとき、Terraform ができるかぎり自動で変換すること
- ポイント：map と object、list と tuple はにている。list や tuple を set にすると重複が消え、順番もなくなる。["a", 15, true] を list(string) にすると ["a", "15", "true"]。変換できないとき（文字列にリストを入れるなど）は型のエラー

#### any（えにー / any）

- 意味：まだ決まっていない型の置き場所を表す特別なキーワード。それ自体は型ではない
- ポイント：『any is very rarely the correct type constraint to use.』値の中を見ずにそのまま jsonencode などで渡すときだけ使う。list(any) では、要素がそろって変換できる 1 つの型を Terraform が選ぶ（["a", 1, "b"] → list(string)）

### 07-1 入力変数

#### 問 tf-07-o01

- 問：入力変数 instance_type の値を、resource の引数で使う書き方として正しいものはどれか。
