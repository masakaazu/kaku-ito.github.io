## 15-1 HCP Terraform とリモート実行

### まとめ表

| | ローカルの Terraform | HCP Terraform |
| :-: | :-: | :-: |
| 設定 | ディスク | つないだ VCS か、API・CLI でアップロード |
| 変数の値 | .tfvars・CLI 引数・シェル | ワークスペース |
| ステート | ディスクかリモートのバックエンド | ワークスペース |
| 資格情報・機密 | シェル・入力 | ワークスペース（sensitive な変数） |
| 実行の場所 | 手元 | HCP Terraform の使い捨ての VM（Remote が既定） |

### HCP Terraform の基本

#### HCP Terraform（えいちしーぴーてらふぉーむ / HCP Terraform）

- 意味：チームで Terraform を使うための HashiCorp のサービス。実行の環境・共有のステート・機密データ・承認・プライベートレジストリなどをまとめて提供する
- ポイント：app.terraform.io にあるホスト型。2024 年 4 月 22 日に Terraform Cloud から名前が変わった（機能は同じ）。自社で動かす版は Terraform Enterprise。小さなチームは無料で始められる
- 語の意味：HCP＝HashiCorp Cloud Platform（HashiCorp のクラウド基盤）

#### Terraform Enterprise（てらふぉーむえんたーぷらいず / Terraform Enterprise）

- 意味：HCP Terraform を自社の環境で動かせる、セルフホスト版
- ポイント：セキュリティやコンプライアンスの要件が高い組織向け。CLI 連携では cloud ブロックの hostname にそのホスト名を書く（既定は app.terraform.io）

#### ワークスペース（HCP）（わーくすぺーす / HCP Terraform workspace）

- 意味：HCP Terraform で、1 つのインフラの集まりを管理するための単位。設定・変数・ステート・実行の記録を持つ
- ポイント：ローカルの「作業ディレクトリ」と同じ役目。ワークスペースどうしは完全に別のディレクトリのように働く。HCP ではワークスペースは必須で、アクセス制御の単位にもなる。CLI のワークスペース（1 つの作業ディレクトリでステートを分けるだけ）とは別物
- 例：networking-prod・app1-prod・monitoring-prod のように、大きな構成を分けてワークスペースにする

#### ステートのバージョン（すてーとのばーじょん / state versions）

- 意味：HCP Terraform のワークスペースが残す、今と過去のステートファイルの記録
- ポイント：States タブで、どの実行・どのコミットのステートかと、前との差分が見られる。変更の追跡や問題からの回復に使える

### リモート実行

#### リモート実行（りもーとじっこう / remote operations）

- 意味：HCP Terraform が自分の使い捨ての仮想マシンで Terraform の実行（plan・apply）をすること
- ポイント：安定した実行の環境になり、Sentinel・OPA のポリシー、コストの見積もり、通知、VCS 連携などが使える。CLI から始めると、進み具合が手元の端末に流れてくる
- 例：terraform apply（cloud ブロックあり）→「Running apply in HCP Terraform. Output will stream here.」

#### 実行モード（じっこうもーど / execution mode）

- 意味：ワークスペースの Terraform をどこで動かすかの設定
- ポイント：Remote（HCP の VM で動かす、新しいワークスペースの既定）・Local（手元で動かし、HCP はステートの保存だけ。ワークスペースの変数は使われない）・Agent（社内やプライベートなネットワークの HCP Terraform エージェントで動かす）。プロジェクトの既定に従う「Project Default」もある。Local にするとポリシーなどリモート実行に頼る機能は使えない

#### 実行のキュー（じっこうのきゅー / run queue）

- 意味：ワークスペースごとに実行を順に並べ、1 つずつ処理するしくみ
- ポイント：前の実行が終わるまで、次は plan もしない（結果が変わりうるため）。例外は plan だけの実行（スペキュラティブプラン）と、保存したプランの plan の段階。実行を始めると、そのときの設定のバージョンと変数の値に固定される

#### 自動適用（じどうてきよう / auto-apply）

- 意味：成功した plan を、人の確認なしに apply するワークスペースの設定
- ポイント：既定は手動（Confirm & Apply を押す）。UI・API・VCS からの実行に効き、run trigger からの実行には別の設定がある。CLI からの実行は -auto-approve で決める。変更がない plan は apply せず「Planned and finished」で終わる

#### Terraform のバージョン（HCP）（てらふぉーむのばーじょん / workspace Terraform version）

- 意味：ワークスペースのすべての操作で使う Terraform のバージョン
- ポイント：既定はワークスペースを作ったときの最新版。決まった版でも、バージョンの制約でも書ける。上げる前に、Plan only の実行で別の版を選んでスペキュラティブプランを試せる（ワークスペースの設定は変わらない）

## 15-2 実行の 3 つのワークフロー

### まとめ表

| ワークフロー | 実行の始まり | 向くところ |
| :-: | :-: | :-: |
| UI/VCS 駆動 | ブランチへのマージ・コミット（webhook）、UI の + New run | 主なやり方。PR でスペキュラティブプラン |
| CLI 駆動 | terraform plan・apply（cloud ブロック） | CLI に慣れた人・既存の CI/CD |
| API 駆動 | Runs API などを自分のツールから | 自由度が高いが、ツールを作る必要がある |

### ワークフロー

#### UI/VCS 駆動のワークフロー（ゆーあいぶいしーえすくどう / UI/VCS-driven run workflow）

- 意味：ワークスペースを VCS のリポジトリの 1 つのブランチにつなぎ、コミットやマージで自動で実行するやり方
- ポイント：HCP Terraform の主なやり方。ワークスペースを作るときに webhook を登録する。PR を開くとスペキュラティブプランが走り、PR にリンクが付く。設定はいつも VCS の特定のコミットから来る。新しいワークスペースでは最初の実行を手で始める。フォークからの PR では（悪意のあるコードを防ぐため）プランを走らせない

#### CLI 駆動のワークフロー（しーえるあいくどう / CLI-driven run workflow）

- 意味：cloud ブロックを書いた作業ディレクトリから、ふつうの terraform plan・apply で HCP Terraform の実行を始めるやり方
- ポイント：実行は HCP Terraform で、ワークスペースの変数とポリシーを使い、ログは手元に流れる。手元の設定ファイルがアップロードされる。VCS につないだワークスペースでは terraform apply（リモートの apply）はできない（VCS が正）。terraform plan はどのワークスペースでもできる

#### API 駆動のワークフロー（えーぴーあいくどう / API-driven run workflow）

- 意味：HCP Terraform の API（設定のバージョンのアップロード・Runs API など）を自分のツールから呼んで実行するやり方
- ポイント：いちばん自由だが、ツールを作る必要がある。人の入力がいらないので、対話のない自動化（外部の CI など）ではこれがすすめ

#### スペキュラティブプラン（すぺきゅらてぃぶぷらん / speculative plan）

- 意味：変更を試すための、plan だけの実行。apply はできない
- ポイント：実物を変えないので、ほかの実行を待たずに始められる。始め方は 3 つ：VCS の PR、CLI の terraform plan、API（設定のバージョンを speculative にする）。ポリシーの結果も見られる。手元に機密の変数をコピーせずに試せる

#### 保存したプラン（HCP）（ほぞんしたぷらん / saved plan run）

- 意味：terraform plan -out と terraform apply FILE で、plan と apply を分けて行う HCP Terraform の実行
- ポイント：CLI v1.6 から。VCS につないでいないワークスペース向け。ファイルはリモートの実行への参照にすぎず、plan したのと同じワークスペースでしか apply できない。ステートが変わって古くなったプランは自動で捨てられる

#### 実行のモードとオプション（じっこうのもーどとおぷしょん / run modes and options）

- 意味：HCP Terraform の実行で選べる、CLI とほぼ同じモードとオプション
- ポイント：標準（plan と apply）・destroy・Plan only・保存したプラン・Allow empty apply（変更がなくても apply）・Refresh state（refresh-only）・-refresh=false・-replace・-target・設定の生成。UI では + New run で選ぶ

## 15-3 CLI との連携と移行

### まとめ表

| 手順 | 中身 |
| :-: | :-: |
| 1 資格情報 | terraform login（API トークンを credentials.tfrc.json に保存） |
| 2 接続の設定 | terraform ブロックに cloud ブロック（organization・workspaces） |
| 3 初期化 | terraform init（ワークスペースがなければ作る） |
| 4 ステートの移行（任意） | init のときに聞かれる。remote バックエンドは cloud に書きかえる |

### つなぐ

#### cloud ブロック（くらうどぶろっく / cloud block）

- 意味：terraform ブロックの中に書いて、作業ディレクトリを HCP Terraform のワークスペースにつなぐブロック
- ポイント：organization（組織）・workspaces（name か tags、project）・hostname（既定 app.terraform.io）・token。1 つの構成に 1 つ、backend ブロックとは同時に書けない、変数・ローカル値は参照できない。v1.1 から（それより前は remote バックエンド）。変えたら terraform init
- 例：terraform { cloud { organization = "my-org"  workspaces { name = "my-app-prod" } } }

#### workspaces の name と tags（わーくすぺーすのねーむとたぐ / workspaces name and tags）

- 意味：cloud ブロックで、つなぐワークスペースを選ぶ 2 つの方法
- ポイント：name は 1 つのワークスペースにだけつなぐ。tags はタグが全部合うワークスペースにつなぎ、terraform workspace コマンドで切りかえる。name と tags は同時に書けない。project を書くとそのプロジェクトの中で探す。環境変数 TF_CLOUD_ORGANIZATION・TF_WORKSPACE・TF_CLOUD_PROJECT・TF_CLOUD_HOSTNAME でも渡せる（両方あれば設定が優先）

#### terraform login（てらふぉーむろぐいん / terraform login）

- 意味：HCP Terraform などの API トークンを取ってきて保存するコマンド
- ポイント：ホスト名を省くと app.terraform.io。トークンは既定で credentials.tfrc.json に平文で保存する（credentials helper で別の場所にもできる）。ブラウザーを開くので対話のある場面だけ。無人の自動化では CLI 設定ファイルや環境変数で資格情報を渡す。終わったら terraform logout

#### 暗黙のワークスペースの作成（あんもくのわーくすぺーすのさくせい / implicit workspace creation）

- 意味：cloud ブロックに書いたワークスペースがまだないとき、terraform init で HCP Terraform が作ること
- ポイント：自動で作られたワークスペースは、変数がない（グローバルな変数セットを除く）・実行モードは Remote・VCS にはつながっていない・Terraform のバージョンは作ったときの最新。実行の前に UI で設定を確かめる。TF_WORKSPACE からは作らない

#### .terraformignore（どっとてらふぉーむいぐのあ / .terraformignore）

- 意味：CLI 駆動の実行でアップロードしないファイルを書く、設定のディレクトリの直下のファイル
- ポイント：書き方は .gitignore と同じ。なくても .git/ と .terraform/（.terraform/modules を除く）はアップロードしない

### 移す

#### HCP Terraform へのステートの移行（すてーとのいこう / migrate state to HCP Terraform）

- 意味：今あるインフラを消さずに、そのステートを HCP Terraform のワークスペースに移すこと
- ポイント：まず関係する Terraform の操作を全部止める。CLI なら cloud ブロックを書いて terraform init し、聞かれたら移す。ほかに API や tf-migrate でも移せる。移す先はまだ一度も実行していないワークスペースにする。CLI のワークスペースは HCP では一意の名前が必要なので、名前の変更を聞かれることがある

#### remote バックエンド（りもーとばっくえんど / remote backend）

- 意味：cloud ブロックができる前（v1.0 以前）に HCP Terraform につなぐのに使った、古いバックエンド
- ポイント：cloud ブロックに移るには、backend "remote" を cloud に書きかえる（同じワークスペースを使いつづける）。prefix は cloud にないので tags に置きかえ、ワークスペースは完全な名前で選ぶ

### 15-1 HCP Terraform とリモート実行

#### 問 tf-15-o01

- 問：HCP Terraform の説明として正しいものはどれか。
- ア：チームで Terraform を使うためのサービスで、安定した環境での実行・共有のステート・機密データ・承認のしくみなどを提供する
- イ：Terraform の新しい設定言語
- ウ：プロバイダーを自作するための SDK
- エ：自社のデータセンターにしか置けない製品
- 正解：ア
- 解説：HCP Terraform は、チームが Terraform を一緒に使うためのアプリケーション。実行の環境、共有のステートと機密データ、変更の承認、プライベートレジストリなどを提供する。自社に置く版は Terraform Enterprise。
- アの意味：正しい。
- イの意味：言語は HCL のまま。
- ウの意味：Plugin Framework などの役目。
- エの意味：それは Terraform Enterprise。HCP Terraform はホスト型。
- 出典：オリジナル問題（根拠：HashiCorp「What is HCP Terraform?」（『HCP Terraform is an application that helps teams use Terraform together.』『It manages Terraform runs in a consistent and reliable environment, and includes easy access to shared state and secret data, access controls for approving changes to infrastructure』））

#### 問 tf-15-o02

- 問：HCP Terraform のワークスペースが、ローカルで Terraform を使うときの何に当たるか。
- ア：プロバイダーのプラグイン
- イ：永続的な作業ディレクトリ（設定・ステート・変数を持つ）
- ウ：1 つの resource ブロック
- エ：.terraform.lock.hcl
- 正解：イ
- 解説：ローカルでは作業ディレクトリが設定・ステート・変数を持つ。HCP Terraform ではワークスペースがその役目をし、ワークスペースどうしは完全に別のディレクトリのように働く。
- アの意味：関係ない。
- イの意味：正しい。
- ウの意味：単位が小さすぎる。
- エの意味：プロバイダーの版を記録するファイル。
- 出典：オリジナル問題（根拠：HashiCorp「Remote operations」（『The workspace serves the same role that a persistent working directory serves when running Terraform locally: it provides the configuration, state, and variables for the run.』））

#### 問 tf-15-o03

- 問：HCP Terraform のワークスペースで、変数の値と資格情報はどこに置かれるか。
- ア：作業者の PC の .tfvars だけ
- イ：VCS のリポジトリ

- アの意味：ローカルのやり方。
- イの意味：VCS に置くのは設定。
- ウの意味：正しい。
- エの意味：ステートに置くものではない。
- 出典：オリジナル問題（根拠：HashiCorp「Workspaces」（『Credentials and secrets』『In workspace, stored as sensitive variables』））

#### 問 tf-15-o04

- 問：HCP Terraform のリモート実行（remote operations）の説明として正しいものはどれか。
- ア：作業者の PC で plan・apply を動かし、結果だけを送る

- アの意味：それはローカル実行。
- イの意味：Terraform を動かす。
- ウの意味：apply もできる。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：HashiCorp「Remote operations」（『HCP Terraform is designed as an execution platform for Terraform, and can perform Terraform runs on its own disposable virtual machines.』））

#### 問 tf-15-o05

- 問：ワークスペースの実行モードを Local にした。どうなるか。
- ア：実行は手元で行い、HCP Terraform はステートを保存するだけになる
- イ：実行は HCP Terraform の VM で行う
- ウ：社内ネットワークのエージェントで実行する
- エ：ステートも手元に置く
- 正解：ア
- 解説：Local にすると、ワークスペースはステートのリモートのバックエンドとしてだけ働き、実行は手元や CI で行う。ポリシーなどリモート実行に頼る機能は使えない。
- アの意味：正しい。
- イの意味：Remote モード。
- ウの意味：Agent モード。
- エの意味：ステートは HCP に置く。
- 出典：オリジナル問題（根拠：HashiCorp「Remote operations」（『This causes the workspace to act only as a remote backend for Terraform state, with all execution occurring on your own workstations or continuous integration workers.』））

#### 問 tf-15-o06

- 問：社内のプライベートなネットワークにあるインフラを、外からの受信を開けずに HCP Terraform で管理したい。選ぶ実行モードはどれか。
- ア：Local
- イ：Remote
- ウ：Agent
- エ：Speculative
- 正解：ウ
- 解説：Agent モードでは、社内に置いた HCP Terraform エージェントが HCP Terraform に問い合わせて、変更を社内で実行する。公開の受信を開ける必要がない（有料の機能）。
- アの意味：手元で実行する。
- イの意味：HCP の VM からは社内に届かない。
- ウの意味：正しい。
- エの意味：実行モードではない（plan だけの実行）。
- 出典：オリジナル問題（根拠：HashiCorp「Remote operations」（『The agent polls HCP Terraform or Terraform Enterprise for any changes to your configuration and executes the changes locally, so you do not need to allow public ingress traffic』））

#### 問 tf-15-o07

- 問：あるワークスペースで実行中に、新しい実行が始まった。HCP Terraform の動きとして正しいものはどれか。
- ア：2 つの実行が同時に apply される

#### 問 tf-15-o30

- 問：backend "remote" で HCP Terraform につないでいた構成を、cloud ブロックに移す。正しいものはどれか。
- ア：backend "remote" を cloud に書きかえれば、同じワークスペースを使いつづけられる

- 正解：ア

- アの意味：正しい。
- イの意味：作り直さない。
- ウの意味：prefix はない。
- エの意味：同時には書けない。
- 出典：オリジナル問題（根拠：HashiCorp「Connect to HCP Terraform」（『In the terraform block or terraform.tf file, replace backend "remote" with cloud. Terraform continues to use the same set of HCP Terraform workspaces.』『the cloud block does not support the prefix argument』））
