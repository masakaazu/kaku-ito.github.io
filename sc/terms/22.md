## 22-1 開発プロセスと設計

### まとめ表

| 設計の考え方 | 障害や誤りが起きたとき |
| :-: | :-: |
| フールプルーフ | 誤った操作や入力をさせない、受け付けない |
| フェールセーフ | 安全な側に倒して止める（信号を赤にする） |
| フェールソフト | 機能や性能を落としてでも動き続ける（縮退運転） |
| フォールトトレランス | 冗長化して、故障しても機能を止めない |
| フォールトアボイダンス | 部品の信頼性を高めて、故障そのものを減らす |

| JIS X 25010 の品質特性 | 意味 |
| :-: | :-: |
| 機能適合性 | 明示・暗黙のニーズを満たす機能を提供する度合い |
| 性能効率性 | 使う資源の量に対する性能の度合い |
| 使用性 | 利用者が有効・効率的・満足して目標を達成できる度合い |
| 信頼性 | 決められた期間・条件で機能を実行し続ける度合い |
| セキュリティ | 認可された人・システムだけがアクセスできる度合い |
| 保守性 | 修正・改良を有効・効率的にできる度合い |

### プロセスと要件

#### ソフトウェアライフサイクルプロセス（そふとうぇあらいふさいくるぷろせす / SLCP: Software Life Cycle Processes）

- 意味：ソフトウェアの構想から開発、運用、保守、廃棄までの作業を、プロセスとして定義した枠組み。国際規格 ISO/IEC/IEEE 12207 を基にした JIS X 0160、日本向けに IPA がまとめた共通フレームがある
- ポイント：発注者と受注者が同じ言葉で作業の範囲と責任を決めるのに使う。プロジェクトの事情に合わせてプロセスを修正したり新しく定義したりすることを修整（テーラリング）という（R4春 問23）

#### ペルソナ（ぺるそな / Persona）

- 意味：要件定義や設計で、ソフトウェアの利用者を役割ごとに典型的な人物像として、名前・年齢・目的・困りごとまで具体的に描いた架空の人物
- ポイント：エピックは大きなユーザーストーリー、ステークホルダは利害関係者、プロダクトオーナはスクラムで価値の最大化に責任を持つ役割（R2 問22）

### アーキテクチャと設計

#### マイクロサービスアーキテクチャ（まいくろさーびすあーきてくちゃ / Microservices Architecture）

- 意味：システムを、業務の機能ごとの小さな独立したサービスに分け、API でつないで構成する方式。サービスごとに開発・デプロイ・拡張ができる
- ポイント：サービス間の通信が増えるので、通信の暗号化と相互認証、障害の連鎖を止めるサーキットブレーカー、通信を横断的に管理するサービスメッシュが重要になる

#### サーキットブレーカー（さーきっとぶれーかー / Circuit Breaker）

- 意味：呼出し先のサービスで失敗が続いたら、しばらくの間呼出しを止めてすぐにエラーを返し、回復を確かめてから再開する仕組み。電気のブレーカーにならった名前
- ポイント：応答しないサービスを待ち続けて呼出し元まで止まる、障害の連鎖を防ぐ

#### マッシュアップ（まっしゅあっぷ / Mashup）

- 意味：公開されている複数のサービスや API（地図、天気など）を組み合わせて、新しいサービスを作ること
- ポイント：店舗案内のページに他のサイトの地図検索の結果を表示するのが例（R1秋 問23）。既存プログラムから仕様を導くのはリバースエンジニアリング

#### GoF のデザインパターン（じーおーえふのでざいんぱたーん / GoF Design Patterns）

- 意味：E. Gamma ら 4 人（Gang of Four）がまとめた、オブジェクト指向設計でよく使われる 23 の設計の型。生成（Singleton・Factory Method など）、構造（Adapter・Proxy など）、振る舞い（Observer・Strategy など）の 3 つに分類される
- ポイント：Layers・Broker などはアーキテクチャパターン（POSA）で、GoF ではない（R6秋 問22）

#### SOLID 原則（そりっどげんそく / SOLID Principles）

- 意味：オブジェクト指向設計の五つの原則の頭文字。単一責任（S）、開放閉鎖（O：拡張に開き修正に閉じる）、リスコフの置換（L）、インタフェース分離（I）、依存性逆転（D）
- ポイント：変更の影響を小さくする原則。モジュールの強度を高く（凝集度を高く）、結合度を低くするという考え方と同じ方向

#### フェールソフトとフールプルーフ（ふぇーるそふととふーるぷるーふ / Fail Soft, Fool Proof）

- 意味：フェールソフトは、障害が起きた部分を切り離し、性能や機能を落としてでも運転を続ける設計。フールプルーフは、利用者が誤った操作や入力をしてもシステムが誤動作しないようにする設計
- ポイント：構成を縮小して運転を続けるのはフェールソフト（R1秋・R3秋 問24）。無効なデータにメッセージを出して正しい入力を促すのはフールプルーフ（R4春 問22）。安全に停止させるのはフェールセーフ

#### 品質特性（ひんしつとくせい / Quality Characteristics）

- 意味：JIS X 25010 が定める、システムやソフトウェアの製品の品質を表す 8 つの特性。機能適合性・性能効率性・互換性・使用性・信頼性・セキュリティ・保守性・移植性
- ポイント：セキュリティの副特性は機密性・インテグリティ・否認防止性・責任追跡性・真正性。R3春 問22 は機能適合性の説明が正しく、ほかは信頼性・性能効率性・保守性・使用性の説明を入れ替えた誤り

## 22-2 テストとレビュー

### まとめ表

| 結合テストの方式 | 進め方 | 代わりに使う部品 |
| :-: | :-: | :-: |
| トップダウンテスト | 上位のモジュールから順に結合 | 下位の代わりのスタブ |
| ボトムアップテスト | 下位のモジュールから順に結合 | 上位の代わりのドライバ |
| サンドイッチテスト | 上下両方から進める | スタブとドライバ |
| ビッグバンテスト | 全部そろえて一度に結合 | なし |

### テストの方法

#### ファジング（ふぁじんぐ / Fuzzing）

- 意味：問題を引き起こしそうな異常なデータ（ファズ）を大量に自動生成して入力し、異常終了や想定外の応答を監視して、ソフトウェアの脆弱性を見つけるテスト
- ポイント：H31 問22 の正解。限界値分析は境界の値を選ぶテストケースの設計法、ロードテストは負荷をかけるテスト

#### 探索的テスト（たんさくてきてすと / Exploratory Testing）

- 意味：テスト担当者が、ソフトウェアを動かしてその動きを学びながら、自分の経験に基づいて次に何をテストするかをその場で決めて進めるテスト
- ポイント：前もってテストケースを全部書くのではなく、学習・設計・実行を同時に行う（R3秋 問22）。モデルベースドテストは、振る舞いのモデルからテストケースを作る

#### 判定条件網羅（はんていじょうけんもうら / Branch Coverage）

- 意味：ホワイトボックステストで、プログラムの全ての分岐（判定の真と偽）を少なくとも 1 回ずつ通るようにテストケースを選ぶ基準（分岐網羅）
- ポイント：「A＞6 or B＝0」なら、全体が真になるケースと偽になるケースを 1 つずつ選ぶ（R4秋 問22）。命令網羅は全ての命令を 1 回通る、条件網羅は個々の条件の真偽を全て通る

#### トップダウンテストとボトムアップテスト（とっぷだうんてすととぼとむあっぷてすと / Top-down, Bottom-up Integration Testing）

- 意味：トップダウンテストは上位のモジュールから結合し、未完成の下位をスタブで代える。ボトムアップテストは下位から結合し、上位の呼出し元をドライバで代える
- ポイント：上位の層の単体テストが先に終わり、下位のデバイスドライバ層が未完成ならトップダウンテスト（R7秋 問22）

### レビューと検証

#### ウォークスルー（うぉーくするー / Walkthrough）

- 意味：作成者が中心になり、複数人で仕様書やソースコードを机上で順にたどって、振る舞いをシミュレートしながら問題点を見つけるレビュー
- ポイント：R6春 問22 の正解。インスペクションは、モデレーターが進め、役割と手順を決めた公式のレビュー

#### 形式手法（けいしきしゅほう / Formal Methods）

- 意味：数学的に厳密な意味を持つ言語で仕様を記述し、満たすべき性質と仕様が整合しているかを論理的に証明・検証する手法
- ポイント：鉄道や航空、暗号のプロトコルなど、誤りが許されない分野で使う（R6春 問23）。役割を決めた複数人での検証はインスペクション、内部構造を見ないのはブラックボックステスト

#### 静的コード解析ツール（せいてきこーどかいせきつーる / Static Code Analysis Tool）

- 意味：ソースコードを実行せずに解析し、バグ、コードの重複、脆弱性につながる書き方などを自動で見つけるツール。OSS では SonarQube などがある
- ポイント：R7春 問22 の正解は SonarQube。Git はソースコード管理、Jenkins は CI のツール、Snort はネットワーク型 IDS

## 22-3 アジャイルと DevOps

### まとめ表

| スクラムの要素 | 例 |
| :-: | :-: |
| 役割（責任） | プロダクトオーナー、スクラムマスター、開発者 |
| イベント | スプリント、スプリントプランニング、デイリースクラム、スプリントレビュー、スプリントレトロスペクティブ |
| 作成物 | プロダクトバックログ、スプリントバックログ、インクリメント |

| SRE・DevOps の言葉 | 意味 |
| :-: | :-: |
| SLO | 目標とするサービスの信頼性の水準（例：月の可用性 99.9%） |
| エラーバジェット | 100% − SLO で許される失敗の量 |
| カオスエンジニアリング | 本番などで意図的に障害を起こして耐障害性を確かめる |
| オブザーバビリティ | ログ・メトリクス・トレースから内部の状態を把握できること |

### アジャイル開発

#### スクラム（すくらむ / Scrum）

- 意味：短い期間（スプリント）を繰り返して、価値のある成果物を少しずつ作り、検査と適応を行うアジャイル開発の枠組み。役割、イベント、作成物、ルールからなる
- ポイント：R5秋 問23 の正解。五つの価値とテスト駆動開発・ペアプログラミングを推奨するのは XP、推測・協調・学習のサイクルは ASD、フィーチャ単位で進めるのは FDD

#### テスト駆動開発（てすとくどうかいはつ / TDD: Test-Driven Development）

- 意味：プログラムのコードを書く前に、そのテストコードを書き、テストが通る最小限のコードを書いてから整理（リファクタリング）するという短いサイクルで開発する手法。XP のプラクティスの一つ
- ポイント：R3春・R6秋 問23 の正解は「プログラムコードを書く前にテストコードを書く」

#### レトロスペクティブ（れとろすぺくてぃぶ / Retrospective）

- 意味：イテレーション（スプリント）の最後に、チームで進め方を振り返り、次に何を改善するかを決める活動（ふりかえり）
- ポイント：各イテレーションの最後に行う（R2 問23）。KPT は Keep（続けること）、Problem（問題）、Try（次に試すこと）の三つの視点で振り返る手法（R7春 問23）

### DevOps と SRE

#### SRE とエラーバジェット（えすあーるいーとえらーばじぇっと / Site Reliability Engineering, Error Budget）

- 意味：SRE は、運用の課題をソフトウェアエンジニアリングの手法で解決し、サービスの信頼性を高める考え方と役割（Google が提唱）。エラーバジェットは、100% から SLO（信頼性の目標）を引いた、許される失敗の量
- ポイント：エラーバジェットが残っていれば新機能のリリースを進め、使い切ったら信頼性の改善を優先する。開発の速さと安定性を数字で調整する

#### カオスエンジニアリング（かおすえんじにありんぐ / Chaos Engineering）

- 意味：ステージング環境や本番環境で、意図的にサーバの停止や通信の遅延などの障害を起こし、システムの挙動を観察して問題を直すことを継続的に行い、耐障害性を高める手法
- ポイント：多数のサービスが連携する分散システムでは障害時の挙動を予測しにくいので、実際に起こして確かめる（R5秋 問22）。Netflix の Chaos Monkey が有名

#### オブザーバビリティ（おぶざーばびりてぃ / Observability）

- 意味：システムが出すログ・メトリクス・トレース（処理の経路の記録）から、内部で何が起きているかを外から把握し、未知の問題の原因も調べられる性質（可観測性）
- ポイント：決めた項目を見張るのが監視、想定していない問題も掘り下げられるのがオブザーバビリティ。マイクロサービスでは分散トレーシングが重要

#### CI/CD（しーあいしーでぃー / Continuous Integration, Continuous Delivery）

- 意味：CI（継続的インテグレーション）は、変更を頻繁に共有のリポジトリに統合し、そのたびに自動でビルドとテストを行うこと。CD（継続的デリバリー）は、いつでも本番にリリースできる状態を保つこと。継続的デプロイは本番への反映まで自動で行う
- ポイント：パイプラインに SAST・依存ライブラリの検査・IaC スキャンを組み込むのが DevSecOps。パイプラインやその認証情報が攻撃されると、本番に不正なコードが入る（#17 のサプライチェーン）

#### DevSecOps（でぶせっくおぷす / DevSecOps）

- 意味：開発（Dev）と運用（Ops）が協力して速くリリースする DevOps に、セキュリティ（Sec）を最初から組み込み、全員の責任として自動化して進める考え方
- ポイント：リリースの直前にまとめて診断するのではなく、設計・コーディング・CI の各段階で検査する（シフトレフト）

## 22-4 運用・保守と権利

### まとめ表

| 保守の種類（JIS X 0161） | きっかけ |
| :-: | :-: |
| 是正保守 | 見つかった障害（欠陥）を直す |
| 予防保守 | 障害になる前の潜在的な欠陥を直す |
| 適応保守 | 法改正や OS の更新など、環境の変化に合わせる |
| 完全化保守 | 性能や保守性を良くする |

| 解析技法 | 進め方 |
| :-: | :-: |
| FTA（故障の木解析） | 望ましくない事象から、原因を AND・OR の木で下へたどる（トップダウン） |
| FMEA（故障モード影響解析） | 部品の故障の仕方から、全体への影響を上へたどる（ボトムアップ） |

### 運用と保守

#### 保守の種類（ほしゅのしゅるい / Types of Maintenance）

- 意味：ソフトウェアの引渡し後の修正を、きっかけで分けたもの。是正保守、予防保守、適応保守、完全化保守（改良保守）がある
- ポイント：脆弱性の修正は是正保守、暗号の危殆化に合わせたアルゴリズムの変更は適応保守に当たる

#### FTA と FMEA（えふてぃーえーとえふえむいーえー / Fault Tree Analysis, Failure Mode and Effects Analysis）

- 意味：FTA は望ましくない事象（頂上事象）を出発点に、その原因を AND・OR の論理記号の木で分解する解析。FMEA は部品やプロセスの故障モードを洗い出し、システム全体への影響を評価する解析
- ポイント：結果から原因へ（トップダウン）が FTA、原因から結果へ（ボトムアップ）が FMEA。攻撃者の目標を頂上に置く攻撃木（アタックツリー）は FTA の考え方の応用

#### AIOps（えーあいおぷす / Artificial Intelligence for IT Operations）

- 意味：システムの運用で、大量のログ・メトリクス・アラートを AI（機械学習）で分析し、異常の検知、原因の推定、対応の自動化を行うこと
- ポイント：アラートの相関とノイズの削減で、運用者の負担を減らす。AI の判断の誤りに備えて、人の確認や段階的な自動化を組み合わせる

### 権利

#### 請負で開発したソフトウェアの著作権（うけおいでかいはつしたそふとうぇあのちょさくけん / Copyright of Commissioned Software）

- 意味：注文者から請け負って開発したプログラムの著作権は、契約で取り決めがなければ、実際に作った請負人（受注した企業）に帰属する
- ポイント：お金を払った注文者に自動的に移るわけではない（R7秋 問23）。注文者が著作権を得るには、契約で譲渡を定める。派遣社員が派遣先の指揮で作ったものは派遣先の職務著作になる

#### プログラムの著作権の例外（ぷろぐらむのちょさくけんのれいがい / Exceptions for Programs）

- 意味：著作権法は、プログラムの正当な所有者が自分で使うための必要な限度での複製（バックアップなど、第 47 条の 3）や、機能を調べるための解析（第 30 条の 4）などを認めている。一方で、技術的保護手段（プロテクト）を外して複製することは、私的な複製の例外の対象にならない
- ポイント：使用許諾契約で複製権がないのにプロテクトを外して複製するのは不適切（R5春 問23）。公開されたプロトコルで同等の機能を独自に作ることは問題ない

#### GPL（じーぴーえる / GNU General Public License）

- 意味：自由ソフトウェア財団（FSF）が定めた OSS のライセンス。ソフトウェアを自由に使用・複製・改変・再配布できるが、改変したものや組み込んだものを配布するときは、同じ GPL でソースコードも公開しなければならない（コピーレフト）
- ポイント：MIT・BSD・Apache などの許容型ライセンスは、ソースの公開を求めない。製品に OSS を組み込むときはライセンスの義務を確かめ、SBOM（#19）で管理する
