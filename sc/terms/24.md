## 24-1 マネジメントの事例

### まとめ表

| 事例で問われること | 見方 |
| :-: | :-: |
| 情報資産台帳の書き方 | 管理部署は「情報の中身に責任を持つ部署」。保管場所を貸している部署ではない |
| 重要度の決め方 | 台帳の説明どおりに計算する（サンプル問題では C・I・A の最大値） |
| まとめて書いてよいか | 注記の条件（管理方法や評価値が全部同じ）を一つずつ確かめる |
| 残留リスクの受容 | リスク所有者が承認する（JIS Q 27001 6.1.3） |
| 委託・再委託 | 委託元が委託先を監督する。再委託は事前承認と同等の義務 |
| 退職・異動 | 申出の時点からアクセス権を見直し、資産を返してもらう |

### 情報資産台帳

#### 情報資産台帳（じょうほうしさんだいちょう / Information Asset Inventory）

- 意味：組織が持つ情報資産を一覧にした表。名前・内容・利用部署・管理部署・機密性や完全性や可用性の評価値・重要度・保存期限などを書く
- ポイント：リスクアセスメントの出発点。資産が分からないとリスクを特定できない（サンプル問題 問1 は内部監査でこの点を指摘された会社が題材）
- 例：「作成中の決算短信」と「開示済みの決算短信」は、機密性の評価値が違うので一つの行にまとめられない

#### 管理部署（かんりぶしょ / Asset Owner）

- 意味：情報資産を管理する責任を持つ部署。JIS Q 27002 の「資産の管理責任者（オーナー）」にあたる
- ポイント：情報の中身に責任を持つ部署を書く。ファイルサーバを運用している情報システム部は、置き場所を提供しているだけで、債権管理情報の管理部署ではない（サンプル問題 問1）
- 例：債権管理情報 → 管理部署は経理部、保管するサーバの運用は情報システム部

#### 重要度（じゅうようど / Asset Importance）

- 意味：情報資産をどれだけ守るべきかを表す値。台帳で決めた計算方法で求める
- ポイント：サンプル問題では「機密性・完全性・可用性の評価値の最大値」。合計や平均、最小値と取り違えさせる選択肢に注意。問題文の説明に従う
- 例：機密性 0・完全性 1・可用性 2 → 重要度 2

#### 利用部署（りようぶしょ / User Department）

- 意味：その情報資産を利用できる部署。アクセス権を与える範囲の根拠になる
- ポイント：利用部署と管理部署は別のことがある。アクセス権の見直しは、管理部署が利用部署の一覧をもとに行う

### リスクの判断

#### リスク所有者（りすくしょゆうしゃ / Risk Owner）

- 意味：リスクを運用管理することについて、説明責任（アカウンタビリティ）と権限を持つ人（JIS Q 27000）
- ポイント：リスク対応計画と残留リスクの受容は、リスク所有者の承認を得る（JIS Q 27001 6.1.3 f）。支援士は計画づくりを助言・支援する立場で、承認する人ではない
- 例：営業部の顧客管理システムのリスク → 営業本部長がリスク所有者

#### 残留リスク（ざんりゅうりすく / Residual Risk）

- 意味：リスク対応をしたあとに、まだ残っているリスク
- ポイント：対策をしても 0 にはならない。残る大きさを示して、リスク所有者に受け入れてよいか判断してもらう。シラバスの技能 1-3 に「残留リスクと併せて説明する能力」とある

#### リスク値（りすくち / Risk Value）

- 意味：リスクの大きさを数で表したもの。組織が決めた式（例：資産の重要度 × 脅威 × 脆弱性）で求める
- ポイント：事例問題では式が問題文に書いてある。重要度がいちばん高い資産が、リスク値もいちばん高いとは限らない。掛け算を最後までする
- 例：重要度 3・脅威 2・脆弱性 2 → 12、重要度 3・脅威 2・脆弱性 1 → 6

#### リスク受容基準（りすくじゅようきじゅん / Risk Acceptance Criteria）

- 意味：どの大きさのリスクなら対策せずに受け入れてよいかを、前もって決めた基準
- ポイント：リスク評価で、分析したリスクをこの基準と比べ、対応が必要かと優先順位を決める。基準はリスクアセスメントの前に決めておく

### 委託と人

#### 委託先の監督（いたくさきのかんとく / Supervision of Contractors）

- 意味：個人データの取扱いを委託するとき、委託先で安全管理が行われるよう、委託元が必要で適切な監督をすること（個人情報保護法 第25条）
- ポイント：適切な委託先を選ぶ、契約を結ぶ、取扱状況を把握する、の三つ（ガイドライン通則編）。自己申告を受け取るだけでなく、監査や報告を求める権利を契約に入れる

#### 再委託（さいいたく / Subcontracting）

- 意味：委託先が、受けた業務をさらに別の会社に委託すること
- ポイント：委託元の事前の承諾を条件にし、再委託先にも委託先と同じ水準の義務を課す。委託元は、委託先が再委託先をきちんと監督しているかも確かめる（ガイドライン通則編）

#### 雇用の終了時の手続（こようのしゅうりょうじのてつづき / Termination Responsibilities）

- 意味：従業員が退職・異動するときに、資産を返してもらい、アクセス権を外し、退職後も続く守秘の義務を確認する手続（JIS Q 27002 5.11・5.18・6.5）
- ポイント：退職の申出から退職日までが、情報を持ち出されやすい期間。退職日を待たずにアクセス権を業務に必要な範囲まで絞り、操作の記録を確かめる（IPA「組織における内部不正防止ガイドライン」）

#### 情報セキュリティ方針の承認（じょうほうせきゅりてぃほうしんのしょうにん / Approval of Information Security Policy）

- 意味：情報セキュリティ方針（基本方針）は、トップマネジメント（経営者）が確立し、承認し、組織の中と関係する外部の人に伝える（JIS Q 27001 5.2、JIS Q 27002 5.1）
- ポイント：支援士は方針の案づくりを助言・支援する（技能 1-1）。承認するのは経営者。下位の規程や手順は、規程で決めた権限者が承認する

## 24-2 ライフサイクルとWeb診断の事例

### まとめ表

| 脆弱性 | 根本的な対策（IPA「安全なウェブサイトの作り方」） |
| :-: | :-: |
| セッションフィクセーション（1.4） | ログインに成功したら新しいセッションIDを発行し、古いものは無効にする |
| CSRF（1.6） | 処理の直前の画面で推測できないトークンを hidden に埋め込み、処理で照合する |
| メールヘッダインジェクション（1.8） | ヘッダは固定値にし、外部の入力は本文に出す。ヘッダに使うなら改行を除く |
| クリックジャッキング（1.9） | X-Frame-Options か CSP の frame-ancestors で、他サイトの枠の中に表示させない |
| 認可制御の欠落（1.11） | 処理のたびに、ログイン中の利用者がそのデータを扱ってよいかを確かめる |

| Cookie の属性 | 効き目 |
| :-: | :-: |
| HttpOnly | JavaScript から読めなくする（XSS で盗まれにくい） |
| Secure | HTTPS の通信のときだけ送る |
| SameSite | 他のサイトから始まった要求に Cookie を付けない（CSRF の緩和） |

### Web アプリの攻撃

#### セッションフィクセーション（せっしょんふぃくせーしょん / Session Fixation）

- 意味：攻撃者が手に入れたセッションIDを利用者に使わせ、利用者がログインしたあと、同じセッションIDで成りすます攻撃。セッション固定化攻撃ともいう
- ポイント：ログインの前後でセッションIDが変わらないことが原因。サンプル問題 問2 では、hidden の sessionID がログイン画面からログイン後まで同じ値だった。罠サイトから攻撃者の sessionID を付けてログイン画面へ POST させ、利用者のログイン完了を待ってから、その sessionID でアクセスする

#### CSRF（しーえすあーるえふ / Cross-Site Request Forgery）

- 意味：ログイン中の利用者に罠のページを開かせ、利用者の意図しない要求（パスワード変更、投稿など）をWebサイトへ送らせる攻撃
- ポイント：攻撃者は応答を見られない。「利用者の権限で処理を実行させる」攻撃。XSS（スクリプトを利用者のブラウザで動かす）と区別する
- 語の意味：Cross-Site＝サイトをまたいだ／Request＝要求／Forgery＝偽造

#### メールヘッダインジェクション（めーるへっだいんじぇくしょん / Mail Header Injection）

- 意味：問合せフォームなどで、メールのヘッダに使う入力に改行と別のヘッダ（Bcc: など）を混ぜ、意図しない宛先にメールを送らせる攻撃
- ポイント：迷惑メールの送信の踏み台にされる。対策はヘッダを固定値にして入力を本文に出すこと、ヘッダに使うなら改行を取り除くか、ヘッダを安全に組み立てる API を使うこと

#### クリックジャッキング（くりっくじゃっきんぐ / Clickjacking）

- 意味：罠のページの上に、標的サイトの画面を透明な iframe で重ね、利用者に気付かれないままボタンを押させる攻撃
- ポイント：対策は HTTP 応答ヘッダの X-Frame-Options（DENY / SAMEORIGIN）か、CSP の frame-ancestors。HTTP ヘッダの不備として診断報告に挙がることが多い

### セッションの守り

#### セッションIDの再発行（せっしょんあいでぃーのさいはっこう / Session ID Regeneration）

- 意味：ログインに成功したときなど、権限が変わる時点で、使っていたセッションIDを無効にして新しいセッションIDを発行すること
- ポイント：セッションフィクセーションの根本的な対策（サンプル問題 問2 設問3 の正解）。暗号化して保存する、GET や URL のパラメータに移す、では防げない

#### HttpOnly 属性（えいちてぃーてぃーぴーおんりーぞくせい / HttpOnly Attribute）

- 意味：Cookie に付ける属性で、JavaScript から Cookie を読めなくする
- ポイント：XSS で Cookie を盗まれる被害を減らす。セッションフィクセーションや CSRF は防げない

#### Secure 属性（せきゅあぞくせい / Secure Attribute）

- 意味：Cookie に付ける属性で、HTTPS の通信のときだけ Cookie を送る
- ポイント：盗聴で Cookie を盗まれるのを防ぐ。HSTS と組み合わせて HTTP への格下げも防ぐ

#### SameSite 属性（せいむさいとぞくせい / SameSite Attribute）

- 意味：Cookie に付ける属性で、他のサイトから始まった要求に Cookie を付けるかを決める（Strict / Lax / None）
- ポイント：CSRF の被害を緩和する。ただしサンプル問題 問2 の M サイトは Cookie でなく hidden の sessionID で管理していたので、Cookie の属性は対策にならない

### HTTP 応答ヘッダ

#### X-Frame-Options（えっくすふれーむおぷしょんず / X-Frame-Options）

- 意味：そのページを他のページの frame や iframe の中に表示してよいかを指示する応答ヘッダ。DENY は全部禁止、SAMEORIGIN は同じオリジンだけ許可
- ポイント：クリックジャッキングの対策。新しい方法は CSP の frame-ancestors

#### Strict-Transport-Security（すとりくとらんすぽーとせきゅりてぃ / HTTP Strict Transport Security）

- 意味：このサイトには今後 HTTPS だけでアクセスするようブラウザに指示する応答ヘッダ（HSTS）
- ポイント：HTTP への格下げや、最初の HTTP のアクセスを狙う中間者攻撃を防ぐ。クリックジャッキングとは関係がない

#### X-Content-Type-Options（えっくすこんてんつたいぷおぷしょんず / X-Content-Type-Options）

- 意味：nosniff を指定して、ブラウザが Content-Type を無視して中身から種類を推測するのをやめさせる応答ヘッダ
- ポイント：画像として上げたファイルがスクリプトとして解釈される、といった XSS を防ぐ

#### Content-Security-Policy（こんてんとせきゅりてぃぽりしー / Content Security Policy）

- 意味：ページが読み込んでよいスクリプトや画像などの出どころを、応答ヘッダで制限するしくみ（CSP）
- ポイント：XSS の被害を緩和する。frame-ancestors ディレクティブでクリックジャッキングも防げる

### 診断の計画

#### 画面遷移図（がめんせんいず / Screen Transition Diagram）

- 意味：Webアプリの画面と、ボタンなどで画面が移る流れを図にしたもの
- ポイント：事例問題では、どの遷移に CSRF 対策があるか、ログインの前後でどの遷移を通るか、を図から読み取らせる。サンプル問題 問2 では、ログインの遷移（イ）が セッションフィクセーションの検出箇所

#### 検証用サイト（けんしょうようさいと / Staging Site）

- 意味：本番と同じ構成で、テスト用の疑似データを入れた、試験や診断のための環境
- ポイント：本番の顧客データを壊したり漏らしたりせずに診断できる。本番と構成が同じことが前提。アクセス元の制限を診断のために一時的に開けたなら、終わったら戻す

#### ツール診断（つーるしんだん / Automated Scanning）

- 意味：脆弱性診断ツールで、多くの画面とパラメータに決まった検査パターンを自動で送って調べる方法
- ポイント：既知の脆弱性や、典型的な XSS・SQL インジェクションなどを広く速く見つけるのが得意。業務の意味が分からないので、認可の不備や業務ロジックの不備は見落としやすい

#### 手動診断（しゅどうしんだん / Manual Testing）

- 意味：診断員が画面と仕様を理解したうえで、手作業で要求を作って調べる方法
- ポイント：他人のIDに書き換えて情報を見られないか（認可制御の欠落）、手順を飛ばせないか、などはこちらで見つける。シラバス技能 2-6「手動テストとツールによる自動テストを組み合わせ」

## 24-3 対策の適用とログ分析の事例

### まとめ表

| ログの特徴 | 疑うもの |
| :-: | :-: |
| 1 つの端末から、決まった間隔で、同じ見慣れない宛先へ小さな通信が続く | C2 サーバへのビーコン通信 |
| 1 つのIDに、多くのパスワードで失敗が続く | ブルートフォース攻撃 |
| 多くのIDに、同じパスワードで 1〜2 回ずつ失敗 | パスワードスプレー攻撃 |
| 多くのIDに、IDごとに違うパスワードで失敗し、一部が成功 | クレデンシャルスタッフィング（漏えいした ID とパスワードの組を使う） |

### ログの読み方

#### プロキシログ（ぷろきしろぐ / Proxy Log）

- 意味：社内から外へのWebの通信を中継するプロキシサーバが残す記録。時刻、送信元、宛先 URL、メソッド、応答コード、サイズなどが残る
- ポイント：感染した端末が外の C2 サーバと通信していないかを探すのに使う。業務時間外の通信や、決まった間隔の通信に注目する

#### ビーコン通信（びーこんつうしん / Beaconing）

- 意味：マルウェアが、指令を受けるために C2 サーバへ決まった間隔で送る、小さな通信
- ポイント：人の操作と違い、間隔とサイズがそろう。宛先のドメインが最近登録されたもの、業務と関係のないもの、という特徴も手がかり

#### 認証ログ（にんしょうろぐ / Authentication Log）

- 意味：ログインの成功と失敗を、時刻・ID・接続元などとともに残す記録
- ポイント：失敗の並び方で攻撃の種類を見分ける。IDが一つか多数か、同じパスワードか違うパスワードか、接続元が一つか多数か

#### パスワードスプレー攻撃（ぱすわーどすぷれーこうげき / Password Spraying）

- 意味：よく使われるパスワードを一つ選び、多くのIDに 1〜2 回ずつ試す攻撃。IDごとの失敗回数が少ないので、アカウントロックにかかりにくい
- ポイント：パスワードを固定してIDを変える点は、リバースブルートフォース攻撃と同じ考え方。ブルートフォース攻撃は 1 つのIDでパスワードを変える。対策は多要素認証、推測しやすいパスワードの禁止、組織全体での失敗の監視

### 技術的な対策

#### 管理セグメント（かんりせぐめんと / Management Network）

- 意味：サーバやネットワーク機器の管理用の通信だけを流す、利用者の端末とは分けたネットワーク
- ポイント：一般の端末が乗っ取られても、管理画面や SSH に直接届かないようにする。管理セグメントへの入口は踏み台サーバに限る（技能 3-5 ネットワークの分割）

#### 踏み台サーバ（ふみだいさーば / Jump Server）

- 意味：管理対象のサーバへ入るときに、必ず経由させる中継のサーバ
- ポイント：入口を一つにまとめ、多要素認証と操作の記録をそこで行う。攻撃でいう「踏み台」（他の攻撃の中継に悪用される機器）とは意味が違う

#### シークレット管理（しーくれっとかんり / Secrets Management）

- 意味：API キーやパスワードなどの秘密情報を、専用のサービス（シークレット管理サービス、鍵管理サービス）に置き、プログラムは実行時に権限を確かめたうえで取り出すしくみ
- ポイント：ソースコードに鍵を書き込む（ハードコード）と、リポジトリから漏れる。漏れた鍵は、履歴から消すより先に無効化して新しい鍵に替える

#### 暗号化消去（あんごうかしょうきょ / Cryptographic Erase）

- 意味：データを暗号化して保存している媒体で、暗号の鍵を消して、残ったデータを読めなくする消去の方法
- ポイント：SSD はウェアレベリングのため、上書きしても全部の領域が消えるとは限らない。NIST SP 800-88 は SSD に、メーカーのサニタイズ命令、暗号化消去、物理破壊などを示す（技能 3-3 媒体特性に応じたデータ消去）

#### アカウントの棚卸（あかうんとのたなおろし / Account Review）

- 意味：システムのアカウントと権限の一覧を、人事の情報と突き合わせて、不要なものや多すぎる権限を見つけて直すこと
- ポイント：退職者のアカウントの消し忘れ、異動前の権限の残りを見つける。定期的に、利用部署の管理者が確認する（技能 3-8）

## 24-4 インシデント対応の事例

### まとめ表

| 段階 | すること |
| :-: | :-: |
| 検知・受付 | 事実を確かめ、整理する |
| トリアージ | 対応するかと優先順位を、影響と緊急度で決める |
| 封じ込め | 被害が広がらないよう、ネットワークから切り離すなどする（証拠は残す） |
| 根絶・復旧 | 原因を取り除き、安全を確かめて元に戻す |
| 報告・再発防止 | 根本原因を特定し、同じ原因の箇所と作り方を直す |

### 対応の流れ

#### トリアージ（とりあーじ / Triage）

- 意味：受け付けた事象について、対応するかどうかと、対応の優先順位を決めること（JPCERT/CC「インシデントハンドリングマニュアル」）
- ポイント：被害が今も広がっているか、外部の人に被害が出ているか、重要な資産か、で優先する。届いた順に処理するのではない

#### 封じ込め（ふうじこめ / Containment）

- 意味：インシデントの被害がこれ以上広がらないようにする処置。感染した端末をネットワークから切り離す、不正なアカウントを止める、など
- ポイント：ランサムウェアなどでは、LAN ケーブルを抜き無線を切るが、電源は切らない。メモリの中の証拠が消えるから

#### 根本原因（こんぽんげんいん / Root Cause）

- 意味：インシデントを起こした、いちばん元の原因。直接の原因（ある画面の SQL の組み立て方）の奥にある、作り方や管理のしくみの欠け（開発標準にない、レビューで見ていない）まで掘る
- ポイント：再発防止は、同じ作り方をしている他の箇所も直し、標準・レビュー・教育に反映すること。WAF を入れるだけは暫定の対策（技能 4-3）

#### 情報セキュリティ早期警戒パートナーシップ（じょうほうせきゅりてぃそうきけいかいぱーとなーしっぷ / Information Security Early Warning Partnership）

- 意味：ソフトウェア製品やWebサイトの脆弱性の情報を、発見者から受け付けて、開発者と調整し、公表するまでの国内のしくみ。経済産業省の告示にもとづく
- ポイント：受付機関は IPA、ソフトウェア製品の調整機関は JPCERT/CC。製品の開発者は、届いた脆弱性を直して公表する。社内では PSIRT が窓口になる

### 証拠と報告

#### 揮発性の順序（きはつせいのじゅんじょ / Order of Volatility）

- 意味：証拠を集めるときは、消えやすいものから先に集める、という順序。RFC 3227 は、レジスタとキャッシュ → ルーティング表・ARP キャッシュ・プロセス表・メモリ → 一時ファイル → ディスク → 遠隔のログ → 物理的な構成 → 保管媒体、の順を示す
- ポイント：電源を切るとメモリの内容は消える。ディスクのイメージより先にメモリを取る

#### 証拠保全（しょうこほぜん / Evidence Preservation）

- 意味：インシデントの証拠を、改ざんされていないことを示せる形で集めて保管すること。複製（イメージ）を取ってハッシュ値を記録し、誰がいつ扱ったかを残す（保管の連鎖）
- ポイント：調査は複製で行い、元の媒体には書き込まない。技能 4-4 は、保全の対象（PC、サーバ、記録媒体など）と手順を問う

#### 漏えい等報告（ろうえいとうほうこく / Breach Notification）

- 意味：個人データの漏えい・滅失・毀損（またはそのおそれ）のうち、規則で決めた事態が起きたとき、個人情報保護委員会に報告し、本人に通知する義務（個人情報保護法 第26条）
- ポイント：対象は、要配慮個人情報、財産的な被害のおそれ（クレジットカード番号など）、不正の目的によるもの、1,000 人を超えるもの（施行規則 第7条）。人数が少なくても、他の条件に当たれば報告する

#### 速報と確報（そくほうとかくほう / Preliminary Report, Final Report）

- 意味：漏えい等報告の二段階。速報は、知ったあと速やかに（ガイドラインでは おおむね 3〜5 日以内）。確報は 30 日以内、不正の目的によるおそれがある事態は 60 日以内（施行規則 第8条）
- ポイント：不正アクセスによる漏えいは「不正の目的」に当たるので確報は 60 日以内。72 時間は EU の GDPR の期限で、日本の法律の期限ではない

#### 問 sc-24-smp-q1

- イ：してはいけない／経理部／2
- ウ：してはいけない／情報システム部／2

- アの意味：開示済みと作成中では機密性の評価値が違うので、まとめてよいは誤り。
- イの意味：正しい。原文の解答群ではオ。
- ウの意味：情報システム部は保管場所のサーバを管理しているだけで、債権管理情報の中身に責任を持つ部署ではない。
- エの意味：重要度を最小値で求めている。台帳の説明は最大値。

#### 問 sc-24-o18

- 問：AA 社の CSIRT は、同じ朝に次の四つの連絡を受けた。トリアージで最も優先して対応すべきものはどれか。
- ア：従業員から「不審なメールが届いたが、開かずに削除した」との報告
- イ：外部からのポートスキャンの記録（ファイアウォールで全て遮断済み）
- ウ：退職者のアカウントが一つ残っていた（ログインの記録はない）

- 正解：エ
- 解説：トリアージでは、被害が今も広がっているか、社外の人に被害が出るか、で優先度を決める。公開サイトの改ざんは、今まさに閲覧者にマルウェアを配っているおそれがあり、最も緊急。

- イの意味：遮断済みで、被害は出ていない。
- ウの意味：対処は必要だが、悪用の記録はなく、今広がっている被害ではない。
- エの意味：正しい。
- 出典：オリジナル問題（根拠：JPCERT/CC「インシデントハンドリングマニュアル」のトリアージ、シラバス案 技能4-2「事実関係を確認し，整理する能力」）

#### 問 sc-24-o20

- 問：AC 社のサーバが不正アクセスを受けた疑いがあり、稼働中のサーバから証拠を保全する。RFC 3227 の揮発性の順序に従うと、次のうち最初に保全すべきものはどれか。

#### 問 sc-24-o21

- 問：AD 社の EC サイトが不正アクセスを受け、利用者 300 人分のクレジットカード番号を含む個人データが漏えいしたおそれがあることが分かった。個人情報保護法にもとづく個人情報保護委員会への報告について、最も適切なものはどれか。
- ア：速報を速やかに行い、確報は知った日から 60 日以内に行う
- イ：速報を速やかに行い、確報は知った日から 30 日以内に行う
- ウ：漏えいのおそれは 1,000 人以下なので、報告の必要はない
- エ：72 時間以内に一度だけ報告すれば足りる
- 正解：ア
- 解説：施行規則 第7条は、財産的な被害のおそれ（クレジットカード番号など）、不正の目的によるおそれなどの事態を報告の対象とする。人数が 1,000 人以下でも、他の条件に当たれば報告する。第8条は、確報を 30 日以内、不正の目的によるおそれがある事態は 60 日以内とする。不正アクセスは不正の目的に当たる。
- アの意味：正しい。
- イの意味：30 日は、不正の目的によるもの以外の事態の確報の期限。
- ウの意味：1,000 人を超えることは報告の条件の一つにすぎない。財産的な被害と不正の目的の条件に当たる。

- 出典：オリジナル問題（根拠：個人情報保護法 第26条、同施行規則 第7条・第8条、個人情報保護委員会「ガイドライン（通則編）」3-5-3、シラバス案 技能1-7）
