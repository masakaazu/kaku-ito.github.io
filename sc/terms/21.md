## 21-1 データベースの方式と設計

### まとめ表

| データベースの種類 | 向いているデータ |
| :-: | :-: |
| 関係データベース（RDB） | 項目が決まった表形式のデータ。結合と整合性に強い |
| ドキュメント型 | JSON など、項目の構成がデータごとに違うデータ |
| グラフ型 | 人のつながり、経路など、ノードと関係の網 |
| キーバリュー型 | キーで値を高速に読み書きするデータ（セッションなど） |

| 制約 | 守ること |
| :-: | :-: |
| 一意性制約 | 列の値が重複しない |
| 主キー制約 | 一意で NULL でない。表に一つ |
| 参照制約（外部キー） | 参照先に存在する値か NULL だけを入れられる |
| 検査制約（CHECK） | 値が条件を満たす（例：数量 ≧ 0） |

### 方式とモデル

#### 3 層スキーマアーキテクチャ（さんそうすきーまあーきてくちゃ / Three-Schema Architecture）

- 意味：データベースを、利用者やアプリケーションから見た外部スキーマ、データ全体の論理的な構造である概念スキーマ、記憶装置への格納方法である内部スキーマの 3 層に分けて定義する考え方（ANSI/SPARC）
- ポイント：層を分けることで、格納の方法を変えても概念スキーマが変わらない（物理的データ独立性）、概念スキーマを変えても外部スキーマが変わらない（論理的データ独立性）。SQL のビューは外部スキーマに当たる

#### ドキュメント指向データベース（どきゅめんとしこうでーたべーす / Document-oriented Database）

- 意味：JSON などの形式の文書（ドキュメント）を単位として、項目の構成が文書ごとに違っていてもそのまま格納・検索できるデータベース。NoSQL の一つ
- ポイント：取得元が変わり項目が予測できない商品データは、ドキュメント型で商品単位に格納する（R1秋 問21）。表の列を前もって決める RDB では項目の増減に対応しにくい

#### グラフ型データベース（ぐらふがたでーたべーす / Graph Database）

- 意味：データをノード（点）とエッジ（関係）で表し、つながりをたどる検索を得意とするデータベース
- ポイント：SNS の友人関係や不正な取引の連鎖の分析に向く。項目名と値を別のノードにするような使い方は不自然（R1秋 問21 の誤り）

### 設計とメタデータ

#### E-R 図とカーディナリティ（いーあーるずとかーでぃなりてぃ / E-R Diagram, Cardinality）

- 意味：E-R 図はデータベースの概念設計で、実体（エンティティ）とその間の関連（リレーションシップ）を図にしたもの。カーディナリティは関連の多重度（1 対 1、1 対多、多対多）
- ポイント：多対多の関連は、関係データベースでは間に連関エンティティ（中間の表）を置いて二つの 1 対多に分解する

#### 主キーと外部キー（しゅきーとがいぶきー / Primary Key, Foreign Key）

- 意味：主キーは表の行を一意に識別する列（の組）で、NULL を許さない。外部キーは、他の表（または同じ表）の候補キーを参照する列で、参照先に存在する値か NULL しか入れられない（参照制約）
- ポイント：外部キーの値は重複してよく、一つの表に複数あってもよい（R6秋 問21）。参照制約があると、参照先にない値を持つ行の追加は拒否される（R3秋 問21）

#### サロゲートキー（さろげーときー / Surrogate Key）

- 意味：業務上の意味を持たない、システムが自動で振る連番などの値を主キーにしたもの（代理キー）
- ポイント：社員番号やメールアドレスなどの業務上の値（ナチュラルキー）は変わることがあるので、変わらないサロゲートキーを使うと参照の整合性を保ちやすい。連番を URL に出すと、推測によるアクセス（IDOR、#03）を招くことがある

#### 正規化（せいきか / Normalization）

- 意味：データの重複をなくし、更新の時に矛盾（更新時異常）が起きないように表を分割すること。第 1 正規形（繰返しがない）、第 2 正規形（部分関数従属がない）、第 3 正規形（推移的関数従属がない）と進める
- ポイント：正規化すると更新の矛盾は防げるが、検索で結合が増えて遅くなることがある。性能のためにわざと冗長にするのが非正規化

#### データディクショナリ（でーたでぃくしょなり / Data Dictionary）

- 意味：DBMS が、表や列の定義、ユーザー情報、権限、索引などのデータベースの管理情報（メタデータ）を格納したもの（システムカタログ）
- ポイント：一時的なソートのデータ、バックアップの複製、読み書きの記録（ログ）はデータディクショナリではない（R5秋 問21）

#### データリネージ（でーたりねーじ / Data Lineage）

- 意味：データがどこで発生し、どのような変換・加工を経て現在の形になったかを示すメタデータ。データの生成源の特定や、障害時の影響の調査に使う
- ポイント：アクセス制御の情報、データの管理者（オーナー）の情報、データ構造の定義とは別（R4春 問21）

## 21-2 データ操作と権限

### まとめ表

| 種類 | 文の例 | 役割 |
| :-: | :-: | :-: |
| DDL（データ定義言語） | CREATE・ALTER・DROP | 表やビューを定義する |
| DML（データ操作言語） | SELECT・INSERT・UPDATE・DELETE | データを検索・更新する |
| DCL（データ制御言語） | GRANT・REVOKE・COMMIT・ROLLBACK | 権限とトランザクションを制御する |

### SQL と関係演算

#### 関係演算（かんけいえんざん / Relational Operations）

- 意味：関係（表）に対する演算。選択（条件に合う行を取り出す）、射影（列を取り出す）、結合（二つの表を共通の列で結び付ける）、商がある。和・差・共通・直積の集合演算と合わせて関係代数という
- ポイント：選択は行、射影は列を取り出す。SQL では選択が WHERE 句、射影が SELECT 句の列の指定に当たる

#### 外部結合（がいぶけつごう / Outer Join）

- 意味：結合の相手に一致する行がない行も結果に残す結合。LEFT OUTER JOIN は左の表の全ての行を残し、右の表に一致がなければ右の列を NULL にする
- ポイント：内部結合は両方に一致する行だけ。R LEFT OUTER JOIN S なら R の全ての行が出て、S にだけある行は出ない（R4秋 問21）

#### 相関副問合せと EXISTS（そうかんふくといあわせとえぐじすつ / Correlated Subquery, EXISTS）

- 意味：外側の問合せの行の値を使って、行ごとに実行される副問合せ。EXISTS は副問合せの結果が 1 行以上あれば真、NOT EXISTS は 1 行もなければ真
- ポイント：「X.従業員コード ＝ Y.上司」となる Y が存在しない X ＝ 誰の上司でもない従業員（R7春 問21）

### データベースのセキュリティ

#### GRANT と REVOKE（ぐらんととりぼーく / GRANT, REVOKE）

- 意味：GRANT は利用者に表などへの権限（SELECT・INSERT・UPDATE・DELETE など）を与える SQL の文、REVOKE は与えた権限を取り消す文
- ポイント：ALL PRIVILEGES は全ての権限、WITH GRANT OPTION を付けると、受け取った人がその権限を他人に与える権利（付与権）も得る（R5春 問21）。アプリケーションの DB アカウントには必要最小限の権限だけを与える

#### ビュー（びゅー / View）

- 意味：一つ以上の表から、SELECT 文で取り出した結果を仮想的な表として定義したもの。データは元の表にあり、ビューは問合せの定義だけを持つ
- ポイント：利用者に表そのものではなく、必要な行と列だけのビューへの権限を与えると、見せる範囲を絞れる（行・列のアクセス制御）

#### データベースの暗号化（でーたべーすのあんごうか / Database Encryption, TDE）

- 意味：データベースのファイルや列を暗号化して、記憶媒体やバックアップが盗まれても読めないようにすること。DBMS が書込み時に自動で暗号化し、読出し時に復号する方式を透過的データ暗号化（TDE）という
- ポイント：TDE はアプリケーションを変えずに使えるが、正規の SQL で読めばデータは見えるので、SQL インジェクションや権限の濫用は防げない。鍵はデータと別に管理する

#### データベースの監査ログ（でーたべーすのかんさろぐ / Database Audit Log）

- 意味：誰が、いつ、どの表に、どんな SQL を実行したかを記録するログ。特権ユーザーの操作や大量のデータの読出しを後から追跡するのに使う
- ポイント：トランザクションログ（障害回復用）とは目的が違う。監査ログは DB の管理者が消せないように、別のサーバに送って保管する

## 21-3 トランザクションと障害回復

### まとめ表

| ACID 特性 | 意味 |
| :-: | :-: |
| 原子性（Atomicity） | 全部実行されるか、全く実行されないか |
| 一貫性（Consistency） | 実行の前後で整合性の制約が守られる |
| 独立性（Isolation） | 同時に実行しても互いに影響しない |
| 耐久性（Durability） | コミットした結果は障害があっても失われない |

| 障害 | 回復の方法 |
| :-: | :-: |
| トランザクションの異常終了 | ロールバック（更新前ログで元に戻す） |
| システムの障害（電源断など） | チェックポイントから、未完了はロールバック、完了済みはロールフォワード |
| 媒体（ディスク）の障害 | バックアップを戻し、更新後ログでロールフォワード |

### 同時実行制御

#### ACID 特性（あしっどとくせい / ACID Properties）

- 意味：トランザクションが満たすべき四つの性質。原子性・一貫性・独立性・耐久性の頭文字
- ポイント：耐久性のために、DBMS はコミットの情報をログファイルに書き込んだ時点でコミット完了とする（ログ先行書込み）。データベース本体への反映は後でもよい

#### 2 相ロッキングプロトコル（にそうろっきんぐぷろとこる / Two-Phase Locking）

- 意味：トランザクションが、ロックを掛けるだけの段階（成長相）と、外すだけの段階（縮退相）を分け、一度ロックを外したら新しいロックを掛けないという規則。これを守ると、同時実行の結果が直列に実行した結果と同じになる（直列化可能性）
- ポイント：共有ロック（読取り用、他の共有ロックと両立）と専有ロック（更新用、何とも両立しない）がある。2 相ロッキングでもデッドロックは起こりうる

#### デッドロック（でっどろっく / Deadlock）

- 意味：二つ以上のトランザクションが、互いに相手がロックしている資源を待ち合って、どちらも先に進めなくなる状態
- ポイント：全ての処理でロックを掛ける順番をそろえると防げる（R3春 問21）。読むだけのレコードに専有ロックを掛けたり、大きな一つのトランザクションにしたりすると、かえって起きやすい。DBMS は検出すると一方をロールバックする

#### 2 相コミットメント（にそうこみっとめんと / Two-Phase Commit）

- 意味：分散データベースで、複数のサイトにまたがるトランザクションを全部コミットするか全部取り消すかにそろえる手順。調整役が全サイトにコミットの準備ができるかを問い合わせ（第 1 相）、全員が「可」ならコミット、一つでも「否」ならロールバックを指示する（第 2 相）
- ポイント：第 1 相で「可」と答えたサイトは、指示が来るまでコミットもロールバックもできない待ちの状態になる。調整役が故障すると止まる（ブロッキング）

### 障害回復

#### ジャーナルファイル（じゃーなるふぁいる / Journal File, Log File）

- 意味：データベースの更新の前の値（更新前ログ）と後の値（更新後ログ）、トランザクションの開始とコミットを時系列に記録したファイル。障害の回復に使う
- ポイント：コミットの完了はログファイルへのコミット情報の書込みが完了した時点で、ログバッファへの書込みの時点ではない（R2・R7秋 問21）

#### チェックポイント（ちぇっくぽいんと / Checkpoint）

- 意味：メモリ上のバッファにある更新をデータベースのファイルに書き出し、その時点を記録すること。システム障害の回復は、ログ全体ではなくチェックポイント以降を処理すればよい
- ポイント：チェックポイントの間隔が長いほど、回復で処理するログが増えて時間がかかる

#### ロールフォワードとロールバック（ろーるふぉわーどとろーるばっく / Roll Forward, Roll Back）

- 意味：ロールフォワード（フォワードリカバリ）は、バックアップや古い状態に、更新後ログを順に反映して新しい状態まで進める回復。ロールバック（バックワードリカバリ）は、更新前ログで更新を取り消して元に戻す回復
- ポイント：ディスク障害で、バックアップを戻した後に更新後ログを反映するのはロールフォワード（R3春 問24）。フルバックアップの間隔を 2 倍にすると、反映するログが約 2 倍になり、回復の時間が延びる（H31 問24）

## 21-4 分散データベース

### まとめ表

| 分け方 | 意味 |
| :-: | :-: |
| 水平分散（水平分割） | 表の行を、条件ごとに別のサーバに置く（例：地域ごと） |
| 垂直分散（垂直分割） | 表の列を、別のサーバに置く |
| シャーディング | キーの値で行を多数のサーバ（シャード）に振り分け、負荷を分散 |
| レプリケーション | 同じデータの複製を複数のサーバに置き、更新を伝える |

### 分散の方式

#### レプリケーション（れぷりけーしょん / Replication）

- 意味：データベースの複製（レプリカ）を他のサーバに作り、元のデータの更新を複製に伝えて同じ内容を保つ仕組み
- ポイント：読取りの負荷分散と、障害時の切替えに使う。更新を同期で伝えるとデータを失わないが遅く、非同期だと速いが障害時に直前の更新を失うことがある。誤った削除やランサムウェアの暗号化も複製に伝わるので、バックアップの代わりにはならない

#### シャーディング（しゃーでぃんぐ / Sharding）

- 意味：一つの大きな表の行を、キー（利用者 ID など）の値に応じて複数のデータベースサーバ（シャード）に振り分けて格納し、書込みの負荷と容量を分散する方式
- ポイント：水平分散の一つ。シャードをまたぐ結合やトランザクションが難しくなる

#### 結果整合性（けっかせいごうせい / Eventual Consistency）

- 意味：分散したデータベースで、更新の直後はサーバによって古い値が読めることがあるが、更新が止まれば時間がたつと全てのサーバの値が同じになるという、緩い整合性の考え方
- ポイント：常に最新の値を読める強い整合性より、可用性と性能を優先する。NoSQL のデータベースに多い。残高のように常に正しくなければならないデータには向かない

### 21-1 データベースの方式と設計

#### 問 sc-21-r01a-q21

- 問：JSON 形式で表現される図 1，図 2 のような商品データを複数の Web サービスから取得し，商品データベースとして蓄積する際のデータの格納方法に関する記述のうち，適切なものはどれか。ここで，商品データの取得元となる Web サービスは随時変更され，項目数や内容は予測できない。したがって，商品データベースの検索時に使用するキーにはあらかじめ制限を設けない。（図 1 は A 社 Web サービスの商品データで、"id"・"品名"・"価格"・"関連商品id" の配列などの項目、図 2 は B 社 Web サービスの商品データで、"id"・"商品名"・"生産地"・"価格"・"画像 URL" などの項目を持ち、項目の構成が違う）
- ア：階層型データベースを使用し，項目名を上位階層とし，値を下位階層とした 2 階層でデータを格納する。
- イ：グラフ型データベースを使用し，商品データの項目名の集合から成るノードと値の集合から成るノードを作り，二つのノードを関係づけたグラフとしてデータを格納する。
- ウ：ドキュメント型データベースを使用し，項目構成の違いを区別せず，商品データ単位にデータを格納する。
- エ：リレーショナルデータベースを使用し，商品データの各項目名を個別の列名とした表を定義してデータを格納する。
- 正解：ウ
- 解説：項目が予測できない JSON のデータは、ドキュメント型データベースで商品データ単位にそのまま格納する。
- アの意味：項目名と値を分けると、一つの商品のデータがばらばらになり、商品単位で扱えない。
- イの意味：項目名の集合と値の集合を結ぶだけでは、どの値がどの商品のものか分からない。
- ウの意味：正しい。
- エの意味：項目が予測できないので、列を前もって定義できない。

### 21-4 分散データベース

#### 問 sc-21-o07

- 問：利用者 ID の値に応じて、一つの大きな表の行を多数のデータベースサーバに振り分けて格納し、書込みの負荷を分散する方式はどれか。
- ア：シャーディング
- イ：レプリケーション
- ウ：垂直分散
- エ：2 相コミットメント
- 正解：ア
- 解説：シャーディングはキーで行を振り分ける水平分散で、書込みと容量を分散できる。
- アの意味：正しい。
- イの意味：同じデータの複製を置く方式で、書込みの負荷は分散しない。
- ウの意味：列を分けて置く方式。
- エの意味：分散したトランザクションの結果をそろえる手順。
- 出典：オリジナル問題（根拠：IPA「支援士試験 シラバス（案）」用語例「水平分散，垂直分散，シャーディング」）

#### 問 sc-21-o08

- 問：データベースのレプリケーションに関する記述として、適切なものはどれか。
- ア：レプリカがあれば、ランサムウェアによる暗号化からも必ず回復できる。
- イ：レプリカは読取りの負荷分散や障害時の切替えに使えるが、誤った削除なども複製に伝わるので、バックアップの代わりにはならない。
- ウ：非同期のレプリケーションでは、障害時でも直前の更新は必ず失われない。
- エ：レプリケーションをすると、全てのサーバで常に最新の値が読めることが保証される。
- 正解：イ
- 解説：レプリケーションは可用性のための仕組みで、誤操作や暗号化も伝わる。過去の時点に戻れるバックアップは別に必要。
- アの意味：暗号化された内容も複製に伝わる。
- イの意味：正しい。
- ウの意味：非同期では、複製に伝わる前の直前の更新を失うことがある。
- エの意味：非同期のレプリケーションでは、更新の直後に古い値が読めることがある（結果整合性）。
- 出典：オリジナル問題（根拠：IPA「支援士試験 シラバス（案）」用語例「レプリケーション，結果整合性」）
