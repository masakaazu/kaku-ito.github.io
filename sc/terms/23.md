## 23-1 サービスマネジメント

### まとめ表

| 管理 | 目的 |
| :-: | :-: |
| インシデント管理 | サービスをできるだけ早く元に戻す（暫定的な復旧でもよい） |
| 問題管理 | インシデントの根本原因を見つけ、恒久的な解決策を作る |
| 変更管理 | 変更の要求（RFC）を評価・承認し、リスクを抑えて変更する |
| リリース及び展開管理 | 承認された変更を、本番の環境に計画どおりに展開する |
| 構成管理 | 構成品目（CI）とその関係を正確に記録し続ける |
| サービスレベル管理 | 合意したサービスの目標を監視し、報告し、改善する |
| サービス継続管理 | 災害などでも合意したサービスを続けられるようにする |

| 可用性の計算 | 式 |
| :-: | :-: |
| サービス可用性 | （合意したサービス時間 − 停止時間）÷ 合意したサービス時間 |
| 稼働率 | MTBF ÷（MTBF ＋ MTTR） |

### サービスレベル

#### SLA・SLO・SLI（えすえるえー・えすえるおー・えすえるあい / Service Level Agreement, Objective, Indicator）

- 意味：SLI は、サービスの品質を測る指標（応答時間、可用性など）。SLO は、その指標で目標とする値。SLA は、サービスの提供者と顧客の間で、サービスの内容と目標の水準を文書で合意したもの（サービスレベル合意書）
- ポイント：SLI で測り、SLO を目標に置き、SLA で約束する。SLA を守れなかったときの返金などの取り決めを含むことがある。SRE のエラーバジェット（#22）は SLO から計算する

#### サービス可用性（さーびすかようせい / Service Availability）

- 意味：合意したサービスの提供時間のうち、実際にサービスを使えた時間の割合
- ポイント：計画停止のように「サービス提供時間に含めない」と合意した時間は、分母からも分子からも除く。提供時間の外の修復やメンテナンスの時間も入れない（R4春・R7秋・R7春 問24）
- 例：毎日 0〜24 時、4〜6 月の 91 日で 2,184 時間。合意した計画停止の 84 時間を除くと 2,100 時間。故障の停止 10 時間 → 2,090 ÷ 2,100 ＝ 99.52%

#### MTBF と MTTR（えむてぃーびーえふとえむてぃーてぃーあーる / Mean Time Between Failures, Mean Time To Repair）

- 意味：MTBF は故障から次の故障までの平均の稼働時間、MTTR は故障してから修理が終わるまでの平均の時間。稼働率は MTBF ÷（MTBF ＋ MTTR）
- ポイント：MTBF を長くするのは信頼性の向上、MTTR を短くするのは保守性の向上。どちらでも稼働率は上がる

### 運用のプロセス

#### インシデント管理と問題管理（いんしでんとかんりともんだいかんり / Incident Management, Problem Management）

- 意味：インシデント管理は、サービスの中断や品質の低下を、できるだけ早く元に戻すプロセス。問題管理は、インシデントの根本原因を特定し、恒久的な解決策を作って再発を防ぐプロセス
- ポイント：暫定的な復旧はインシデント管理、未知の根本原因を見つけて恒久策を作るのが問題管理（R5春 問24）。根本原因が分かり回避策がある状態を「既知の誤り」という

#### エスカレーション（えすかれーしょん / Escalation）

- 意味：自分で解決できないインシデントを、別の担当や上の階層に引き継いだり報告したりすること。より専門的な知識を持つ担当に回すのが機能的エスカレーション、管理者などの上位の権限者に報告して判断を求めるのが階層的エスカレーション
- ポイント：重大なインシデントは階層的エスカレーションで経営層まで早く伝える。基準を前もって決めておく

#### 変更管理（へんこうかんり / Change Management）

- 意味：サービスや構成への変更の要求（RFC）を記録し、影響とリスクを評価して承認したうえで変更を実施し、結果をレビューするプロセス
- ポイント：変更のカテゴリーには、事前に承認された手順で行う標準変更、通常の評価を経る通常の変更、すぐに行う必要がある緊急変更などがある。緊急のパッチ適用も、後から記録とレビューを行う

#### 構成管理（こうせいかんり / Configuration Management）

- 意味：サービスを構成するハードウェア・ソフトウェア・文書などの構成品目（CI）と、その関係・版を構成管理データベース（CMDB）に記録し、正確に保つプロセス
- ポイント：脆弱性が公表されたとき、影響を受ける機器をすぐ特定できる（#12 の資産インベントリ）。承認された時点の構成を構成ベースラインという

#### ビジネスインパクト分析（びじねすいんぱくとぶんせき / BIA: Business Impact Analysis）

- 意味：業務が中断したときの影響の大きさを時間の経過とともに分析し、優先して復旧すべき業務と、目標復旧時間（RTO）・目標復旧時点（RPO）などを決めること
- ポイント：サービス継続計画（事業継続計画）を作る前に行う。RTO は「いつまでに戻すか」、RPO は「どの時点のデータまで戻すか」

#### 継続的改善（けいぞくてきかいぜん / Continual Improvement）

- 意味：JIS Q 20000-1 の定義で、パフォーマンスを向上するために繰り返し行われる活動（R6秋 問24）
- ポイント：「意図した結果を得るためにインプットを使用する一連の活動」はプロセス、「サービスを中断なしに提供する能力」は可用性・継続性の考え方。SMS が要求事項に適合しているかを、あらかじめ定めた間隔で確かめるのが内部監査（R5秋 問24）

## 23-2 内部統制

### まとめ表

| 内部統制の基本的要素 | 例 |
| :-: | :-: |
| 統制環境 | 経営者の姿勢、組織の気風、倫理規程 |
| リスクの評価と対応 | リスクを識別・分析し、対応を選ぶ |
| 統制活動 | 承認、職務の分離、照合などの方針と手続 |
| 情報と伝達 | 必要な情報を正しく識別・伝える |
| モニタリング | 内部統制が働いているかを継続的に評価 |
| IT への対応 | IT 環境への対応、IT の利用及び統制 |

| IT に係る統制 | 例 |
| :-: | :-: |
| 全般統制 | システムの開発・保守の管理、運用の管理、アクセスなどの安全性の確保、外部委託の管理 |
| 業務処理統制 | 入力情報の完全性・正確性・正当性の確保、エラーの修正と再処理、マスタデータの維持管理、利用者の認証と操作の範囲の限定 |

### 内部統制の考え方

#### 内部統制（ないぶとうせい / Internal Control）

- 意味：業務の有効性と効率性、報告の信頼性、法令の遵守、資産の保全の四つの目的を達成するために、組織の全ての者が行う仕組みとプロセス。金融庁の基準では、六つの基本的要素からなる
- ポイント：内部統制には限界がある。複数の担当者の共謀、経営者による無視、想定外の事態には働かないことがあり、目的の達成を絶対ではなく合理的に保証するもの。令和 5 年の改訂でデジタルや AI のリスクの考慮が加わった

#### J-SOX（じぇいそっくす / Internal Control Reporting System）

- 意味：金融商品取引法に基づき、上場企業の経営者が財務報告に係る内部統制の有効性を評価した内部統制報告書を出し、監査法人などの監査を受ける制度（内部統制報告制度）
- ポイント：米国の SOX 法にならったので J-SOX と呼ばれる。評価と監査の方法を定めたのが、金融庁の「評価及び監査の基準」と「実施基準」

#### IT 全般統制と IT 業務処理統制（あいてぃーぜんぱんとうせいとあいてぃーぎょうむしょりとうせい / IT General Controls, IT Application Controls）

- 意味：IT 業務処理統制は、個々の業務のアプリケーションに組み込まれ、承認された取引が正しく処理・記録されることを確保する統制。IT 全般統制は、業務処理統制が有効に働く環境を保つための、システムの開発・保守、運用、安全性、外部委託の管理などの統制
- ポイント：アプリケーションに業務に応じた権限の ID とパスワードで認証する機能を設けるのは業務処理統制（R4春・R6秋 問25）。規程や方針、教育は全社的な統制。システムの開発・保守に係る管理は全般統制（R6春 問25）

#### IT の統制目標（あいてぃーのとうせいもくひょう / IT Control Objectives）

- 意味：金融庁の実施基準で、IT の統制が達成すべき目標として挙げられているもの。有効性及び効率性、準拠性、信頼性、可用性、機密性
- ポイント：「記録した取引に漏れ・重複がないこと」は、情報が正確で完全であることを求める信頼性に含まれる（R7春 問25）。準拠性は法令や規程に従っていること

## 23-3 システム監査

### まとめ表

| 監査の流れ | すること |
| :-: | :-: |
| 監査計画 | リスクに基づいて、対象・範囲・方法・時期を決める（リスクアプローチ） |
| 予備調査 | 対象の概要をつかみ、監査手続書を作る |
| 本調査 | 監査手続を実施して監査証拠を集め、評価する |
| 監査調書 | 実施した監査のプロセスと証拠、結論の根拠を記録する |
| 監査報告 | 指摘事項と改善提案を報告する |
| フォローアップ | 改善提案への対応の状況を確かめる |

### 監査の基準と形態

#### システム監査基準（しすてむかんさきじゅん / System Audit Standards）

- 意味：経済産業省が定めた、システム監査人が監査を行うときの行動の規範（監査の体制、計画、実施、報告など）。監査の判断の尺度として使うのはシステム管理基準
- ポイント：令和 5 年の改訂で、ITガバナンスの観点や、保証と助言の両方を行えることが明確になった。監査人には監査対象からの独立性と、専門的能力、正当な注意、秘密の保持が求められる

#### 保証型監査と助言型監査（ほしょうがたかんさとじょげんがたかんさ / Assurance Audit, Advisory Audit）

- 意味：保証型監査は、監査対象の管理が適切であることを監査人が一定の水準で保証する監査。助言型監査は、問題点を指摘し、改善のための助言を行う監査
- ポイント：外部に向けて信頼性を示したいときは保証型、組織の中で改善を進めたいときは助言型を使う。情報セキュリティ監査制度にも両方の型がある

#### リスクアプローチ（りすくあぷろーち / Risk-based Approach）

- 意味：情報システムに関わるリスクの大きさに応じて、監査の対象や手続、資源の配分を決め、重要なリスクに重点的に監査する考え方
- ポイント：監査リスクを完全に回避することはできず、許容できる水準に抑える。全ての対象に一律に資源を配るのは誤り。リスクは変化するので、環境が変わったら監査計画を見直す（R5春・R7秋 問25）

### 監査の実施

#### 監査証拠（かんさしょうこ / Audit Evidence）

- 意味：監査人が監査の結論を導くために集める、事実を示す資料。運用・保守の記録、アクセスログ、トランザクションログ、オーディットトレイル（監査証跡）、インタビューの記録など
- ポイント：監査証跡は、処理の過程を後から追跡できるようにした記録。証拠は十分かつ適切でなければならない

#### 監査調書（かんさちょうしょ / Audit Working Papers）

- 意味：監査人が、実施した監査のプロセス（手続、集めた証拠、判断の過程）を記録した文書。監査の結論の根拠になる
- ポイント：監査対象部門が書くものではない（H31 問25）。年度の監査計画を詳しくしたものは個別監査計画、監査対象部門の改善の計画は改善計画書

#### 統制自己評価（とうせいじこひょうか / CSA: Control Self-Assessment）

- 意味：業務の担当者や管理者が、自分たちの業務の内部統制が有効に働いているかを、ワークショップなどで自ら評価する手法
- ポイント：監査人が独立して評価するのではないので、それだけで保証にはならない。監査人は CSA の結果を参考にして監査を効率的に行える

#### 指摘事項（してきじこう / Audit Findings）

- 意味：監査で見つかった、管理の不備や基準・規程からの逸脱で、監査報告書に記載して改善を求める事項
- ポイント：アプリケーションを経由しない直接修正なのに、ログ上はアプリケーション経由の更新として記録されているのは、記録が実態と違い追跡できないので指摘事項（R5秋 問25）。承認を得て、作業後に特権 ID を無効にしているのは適切な管理

### 23-1 サービスマネジメント

#### 問 sc-23-r07a-q24

- 問：サービス提供時間帯が毎日 0 時から 24 時までの IT サービスにおいて，ある年の 4 月 1 日 0 時から 6 月 30 日 24 時までのサービス停止状況は表のとおりであった。システムバージョンアップ作業に伴う停止時間は，サービス提供時間に含めないことが顧客との間で合意されている。4 月 1 日から 6 月 30 日までの IT サービスのサービス可用性は何%か。ここで，サービス可用性（%）は小数第 3 位を四捨五入するものとする。〔サービス停止状況〕システムバージョンアップ作業に伴う停止：5 月 2 日 22 時から 5 月 6 日 10 時までの 84 時間　ハードウェア故障に伴う停止：6 月 26 日 10 時から 20 時までの 10 時間
- ア：95.52
- イ：95.70
- ウ：99.52
- エ：99.63
- 正解：ウ
- 解説：91 日 × 24 時間 ＝ 2,184 時間から、合意した 84 時間を除いて 2,100 時間。故障の 10 時間を引いて 2,090 ÷ 2,100 ＝ 99.52%。
- アの意味：（2,100 − 94）÷ 2,100 で、合意した停止も停止時間に数えてしまった値。
- イの意味：（2,184 − 94）÷ 2,184 で、合意した停止を分母に含め、停止時間にも数えた値。
- ウの意味：正しい。
- エの意味：計算の誤りによる値。
- 出典：IPA 令和7年度秋期 情報処理安全確保支援士試験 午前Ⅱ 問24（令和4年度春期 問24 とほぼ同じ。原文は表の形）

#### 問 sc-23-r07h-q24

- 問：サービス提供時間帯が毎日 6 時〜20 時のシステムにおいて，ある月の停止時間，修復時間及びシステムメンテナンス時間は次のとおりであった。この月のサービス可用性は何%か。ここで，1 か月の稼働日数は 30 日であって，サービス可用性（%）は小数第 2 位を四捨五入するものとする。〔停止時間，修復時間及びシステムメンテナンス時間〕・システム障害によるサービス提供時間内の停止時間：7 時間・システム障害への対処に要したサービス提供時間外の修復時間：3 時間・サービス提供時間外のシステムメンテナンス時間：8 時間
- ア：95.7
- イ：97.6
- ウ：98.3
- エ：99.0
- 正解：ウ
- 解説：サービス提供時間は 14 時間 × 30 日 ＝ 420 時間。提供時間内の停止 7 時間だけを引き、413 ÷ 420 ＝ 98.3%。
- アの意味：（420 − 18）÷ 420 で、提供時間外の修復とメンテナンスも引いた値。
- イの意味：（420 − 10）÷ 420 で、提供時間外の修復も引いた値。
- ウの意味：正しい。
- エの意味：計算の誤りによる値。
- 出典：IPA 令和7年度春期 情報処理安全確保支援士試験 午前Ⅱ 問24

#### 問 sc-23-r05h-q24

- 問：サービスマネジメントにおける問題管理において実施する活動はどれか。
- ア：インシデントの発生後に暫定的にサービスを復旧させ，業務を継続できるようにする。
- イ：インシデントの発生後に未知の根本原因を特定し，恒久的な解決策を策定する。
- ウ：インシデントの発生に備えて，復旧のための設計をする。
- エ：インシデントの発生を記録し，関係する部署に状況を連絡する。
- 正解：イ
- 解説：問題管理は根本原因を見つけて恒久策を作り、再発を防ぐ。
- アの意味：インシデント管理の活動。
- イの意味：正しい。
