## 17-1 セキュア開発の進め方と脆弱性への実装上の対策

### まとめ表

| 検査の方法 | 何を見るか | いつ | 得意なこと |
| :-: | :-: | :-: | :-: |
| SAST（静的検査） | ソースコード | 実装中（動かす前） | 危険な関数・入力から出力までの流れを網羅的に |
| DAST（動的検査） | 動いているアプリケーション | テスト環境で動かして | 設定の不備や実際に攻撃が通るか |
| ファジング | 異常な入力への反応 | 動かして大量に | 想定外の入力によるクラッシュ・メモリ破壊 |
| SCA（構成分析） | 使っている部品（ライブラリ） | ビルド時 | 既知の脆弱性のある部品（#19） |

| 脆弱性 | 根本的な対策 |
| :-: | :-: |
| SQL インジェクション | プレースホルダ（バインド機構）で SQL を組み立てる |
| クロスサイトスクリプティング | 出力の文脈に合ったエスケープ（出力エンコーディング） |
| CSRF | 推測できない CSRF トークンを確認する、SameSite 属性 |
| バッファオーバーフロー | 境界を確かめる関数・メモリ安全な言語、ASLR・DEP・スタックカナリア |
| パスワードの漏えい | ソルト＋ストレッチングの専用関数でハッシュ化 |

### セキュア開発の進め方

#### セキュアプログラミング（せきゅあぷろぐらみんぐ / Secure Programming）

- 意味：脆弱性を作り込まないように、設計・実装の段階から安全な書き方の決まりに沿ってプログラムを作ること
- ポイント：指針に IPA「安全なウェブサイトの作り方」「セキュア・プログラミング講座」、OWASP の ASVS、NIST SP 800-218（SSDF）などがある。後から見つけて直すより、作り込まないほうが安い（シフトレフト）

#### SAST（さすと / Static Application Security Testing）

- 意味：プログラムを動かさずに、ソースコードやバイナリを解析して脆弱性を見つける検査。ソースコード静的検査
- ポイント：外部からの入力が、無害化されないまま SQL の組立てや HTML の出力に届く流れ（テイント解析）を網羅的に見つけられる。誤検知が多く、設定の不備や実行環境の問題は見つけにくい
- 語の意味：Static＝静的な（動かさない）

#### DAST（だすと / Dynamic Application Security Testing）

- 意味：動いている Web アプリケーションに、外から攻撃を模したリクエストを送り、その応答から脆弱性を見つける検査。プログラムの動的検査
- ポイント：ソースコードがなくても検査でき、実際に攻撃が通るかが分かる。一方、通らなかった画面や処理は検査されず、原因のコードの場所は分からない
- 語の意味：Dynamic＝動的な（動かす）

#### ファジング（ふぁじんぐ / Fuzzing）

- 意味：検査対象に、わざと壊れたデータや想定外のデータ（ファズ）を大量に自動で与え、異常終了やメモリ破壊などの不具合を見つける検査
- ポイント：開発者が思いつかない入力で起きる脆弱性（バッファオーバーフローなど）が見つかる。IPA が「ファジング活用の手引き」を公開している。入力の作り方で、ランダムに作る方法と、正しい形式を少しずつ変える方法がある
- 語の意味：Fuzz＝けば、ぼやけたもの

### 脆弱性への実装上の対策

#### 出力時のエスケープ処理（しゅつりょくじのえすけーぷしょり / Output Encoding）

- 意味：外から受け取った値を HTML・JavaScript・URL などに出力するとき、その場所（文脈）で特別な意味をもつ文字を、意味をもたない形に変換すること
- ポイント：HTML の本文なら「<」を「&lt;」に、属性値なら「"」も変換し、属性値は必ず引用符で囲む。JavaScript の中や URL の中は規則が違うので、文脈に合ったエスケープが必要。入力時のチェックだけでは不十分で、出力時に行うのが基本

#### クロスサイトスクリプティング対策（くろすさいとすくりぷてぃんぐたいさく / XSS Prevention）

- 意味：攻撃者のスクリプトが、利用者のブラウザで Web サイトのものとして動かないようにする対策
- ポイント：根本的な対策は出力時のエスケープ。href 属性に「javascript:」で始まる URL を入れさせない（http・https に限る）。保険的な対策として、cookie の HttpOnly 属性、CSP がある。DOM を JavaScript で書き換えるときは innerHTML ではなく textContent を使う

#### プレースホルダ（ぷれーすほるだ / Placeholder, Bind Variable）

- 意味：SQL 文の中で値が入る場所を「?」などの記号にしておき、SQL 文の構造を確定させてから、値をデータとして別に渡す（バインドする）仕組み
- ポイント：入力値が SQL 文の構造として解釈されないので、SQL インジェクションの根本的な対策になる。文字列連結で SQL を組み立ててエスケープする方法は、漏れや文字コードの問題が起きやすい。表名や並べ替えの列名は値ではないので、許可した名前の一覧から選ぶ

#### CSRF トークン（しーさーふとーくん / Anti-CSRF Token）

- 意味：重要な処理を行うフォームに、セッションごとに推測できないランダムな値を埋め込み、送られてきた値がサーバの保持する値と一致するときだけ処理を行う仕組み
- ポイント：攻撃者の罠ページは、その値を知らないので正しいリクエストを作れない。パスワードの再入力や、cookie の SameSite 属性も対策になる。Referer の確認は補助的

#### バッファオーバーフロー対策（ばっふぁおーばーふろーたいさく / Buffer Overflow Mitigation）

- 意味：確保した領域を超えてデータを書き込ませ、戻り先のアドレスなどを書き換える攻撃を防ぐ対策
- ポイント：根本は、書き込む長さを確かめる（strcpy でなく長さを指定できる関数を使う）、メモリ安全な言語（Rust・Java など）を使うこと。OS やコンパイラの緩和策に、スタックカナリア（戻り先の手前に置いた値の改ざんを検知）、DEP・NX ビット（データ領域のコードを実行させない）、ASLR（メモリの配置をランダムにする）がある

#### ソルト（そると / Salt）

- 意味：パスワードをハッシュ化するとき、利用者ごとに異なるランダムな値を加えてからハッシュ値を計算すること。その値をソルトという
- ポイント：同じパスワードでも利用者ごとにハッシュ値が変わるので、事前に計算したハッシュ値の表（レインボーテーブル）が使えず、同じパスワードの利用者も見分けられない。ソルトは秘密にしなくてよく、ハッシュ値と一緒に保存する
- 語の意味：Salt＝塩（味付けを加える）

#### ストレッチング（すとれっちんぐ / Key Stretching）

- 意味：パスワードのハッシュ値の計算を何千回、何万回と繰り返したり、多くのメモリを使わせたりして、1回の計算に時間がかかるようにすること
- ポイント：漏えいしたハッシュ値から総当たりでパスワードを求める攻撃を遅くする。自分で SHA-256 を繰り返すのでなく、Argon2id、scrypt、bcrypt、PBKDF2 などの専用の関数を使う（OWASP は Argon2id を勧める）

## 17-2 ブラウザが備える防御機構と指示

### まとめ表

| 指示 | 書く場所 | 防ぐもの |
| :-: | :-: | :-: |
| Secure 属性 | Set-Cookie | HTTP の平文の通信での cookie の送出 |
| HttpOnly 属性 | Set-Cookie | JavaScript からの cookie の読出し（XSS での盗用） |
| SameSite 属性 | Set-Cookie | 他サイトからのリクエストでの cookie の送出（CSRF） |
| HSTS | Strict-Transport-Security ヘッダ | HTTP での接続（SSL ストリッピング） |
| CSP | Content-Security-Policy ヘッダ | 許可していないスクリプトの実行（XSS）、他サイトでの枠表示 |
| SRI | script・link タグの integrity 属性 | CDN などで改ざんされたファイルの読込み |
| CORS | Access-Control-Allow-Origin ヘッダ | （同一オリジンポリシーを、許可した相手にだけ緩める） |
| Cache-Control: no-store | 応答のヘッダ | 秘密の情報のキャッシュへの保存 |

### 同一オリジンポリシーと CORS

#### 同一オリジンポリシー（どういつおりじんぽりしー / Same Origin Policy）

- 意味：あるオリジン（スキーム・ホスト・ポート番号の組）から読み込まれた文書やスクリプトが、別のオリジンのリソースの内容を読み取れないようにする、ブラウザの基本的な制限
- ポイント：https://example.jp と http://example.jp はスキームが違うので別オリジン。ポートが違っても別。R3春 問15 の誤りの選択肢イはこの説明（HSTS ではない）

#### CORS（こーす / Cross-Origin Resource Sharing）

- 意味：サーバが Access-Control-Allow-Origin などの応答ヘッダで許可したときだけ、別オリジンのスクリプトがそのリソースを読めるようにする、同一オリジンポリシーを安全に緩める仕組み
- ポイント：許可する相手を「*」（どこでも）にしたり、要求の Origin をそのまま返したりすると、悪意のあるサイトからも読まれる。cookie などの認証情報を付けるときは「*」は使えない。CORS は読取りの制限で、CSRF の対策ではない
- 語の意味：Cross-Origin＝オリジンをまたぐ、Resource Sharing＝資源の共有

### cookie の属性

#### Secure 属性（せきゅあぞくせい / Secure Attribute）

- 意味：cookie に付けると、URL のスキームが https のとき（HTTPS 通信のとき）だけ、ブラウザがその cookie を送出する属性。サーバは Set-Cookie で「Secure」とだけ書く
- ポイント：R1秋・R3秋・R2 の正解。有効期間は Expires・Max-Age、JavaScript からの読出しの禁止は HttpOnly、パスの一致は Path 属性。HTTP で cookie が盗聴されるのを防ぐ

#### HttpOnly 属性（えいちてぃーてぃーぴーおんりーぞくせい / HttpOnly Attribute）

- 意味：cookie に付けると、JavaScript（document.cookie）からその cookie を読み出せなくする属性
- ポイント：XSS が起きても、セッション ID の cookie を盗まれにくくする保険的な対策。XSS そのものは防げない（偽の画面を出す、利用者の代わりに操作する、などはできる）

#### SameSite 属性（せいむさいとぞくせい / SameSite Attribute）

- 意味：他のサイトから始まったリクエストで cookie を送るかを指定する属性。Strict（送らない）、Lax（トップレベルの GET の移動だけ送る）、None（送る、Secure 必須）
- ポイント：罠サイトからの POST に cookie が付かなくなるので、CSRF の対策になる。主なブラウザは指定がないとき Lax として扱う。ただし CSRF トークンと組み合わせるのが確実

### 通信と読込みを守る指示

#### HSTS（えいちえすてぃーえす / HTTP Strict Transport Security）

- 意味：Web サーバが Strict-Transport-Security ヘッダで指示すると、ブラウザは以降の指定された期間（max-age）、そのサイトには全て HTTPS で接続する仕組み（RFC 6797）
- ポイント：利用者が http:// で入力しても、ブラウザが自動で https に変える。最初の接続が HTTP だと狙われる隙が残るので、ブラウザに組み込まれた HSTS プリロードリストに登録する方法がある。R3春 問15・R4春 問14・R6春 問13 の正解。EV 証明書の表示、圧縮、再ハンドシェイクは無関係

#### CSP（しーえすぴー / Content Security Policy）

- 意味：Content-Security-Policy ヘッダで、ページが読み込んで実行してよいスクリプトや画像などの読込み元を指定し、それ以外を実行・読込みさせない仕組み
- ポイント：XSS が起きても、許可していない場所のスクリプトやインラインのスクリプトは動かないので被害を減らせる（保険的な対策）。nonce を使うと、その値を付けたスクリプトだけを許可できる。frame-ancestors で他のサイトに枠表示させない（クリックジャッキング対策、X-Frame-Options の後継）

#### SRI（えすあーるあい / Subresource Integrity）

- 意味：script タグや link タグの integrity 属性に、読み込むファイルのハッシュ値を書いておき、ブラウザが読み込んだファイルのハッシュ値と一致しなければ実行しない仕組み
- ポイント：CDN など外部のサーバに置いたライブラリが改ざんされても、そのまま実行されない。ライブラリを更新したらハッシュ値も更新する
- 例：script src="https://cdn.example/lib.js" integrity="sha384-（ハッシュ値）" crossorigin="anonymous"

#### Cache-Control: no-store（きゃっしゅこんとろーるのーすとあ / Cache-Control: no-store）

- 意味：応答の内容を、ブラウザやプロキシサーバなどのキャッシュに保存させないようにする HTTP ヘッダの指定
- ポイント：R6春 問20 の正解。no-cache は「保存してよいが、使う前に必ずサーバに確かめる」で、保存はされる。private はブラウザだけに保存を許し、共有キャッシュ（プロキシ）には保存させない。個人情報の画面は no-store にする

## 17-3 ソフトウェアサプライチェーンと実行環境の保護

### まとめ表

| 対策 | 守るもの | 例 |
| :-: | :-: | :-: |
| シークレット管理 | パスワード・API キー・秘密鍵 | シークレットストア、ハードコードの排除、秘密情報のスキャン |
| 依存ライブラリの更新管理 | 使っている部品 | SCA・SBOM で把握し、更新する |
| 署名付きコミット | ソースコードの変更者 | GPG・SSH の鍵でコミットに署名 |
| 成果物の署名検証 | ビルドしたプログラム・コンテナイメージ | 署名して配布し、使う前に検証 |
| SLSA | ビルドの過程全体 | 来歴（プロヴナンス）の記録と改ざん防止のレベル |
| 要塞化（ハードニング） | 実行するサーバ・OS | 不要なサービスの停止、初期設定の変更 |

### サプライチェーンの保護

#### シークレット管理（しーくれっとかんり / Secrets Management）

- 意味：パスワード、API キー、秘密鍵などのシークレットを、ソースコードや設定ファイルに直接書かず（ハードコードの排除）、専用のシークレットストアで保管・配布・更新すること
- ポイント：ソースコードに書いたシークレットは、リポジトリの公開や履歴から漏れる。履歴に入ったものは消しても残るので、漏れたら必ず無効にして作り直す（ローテーション）。リポジトリへの秘密情報の混入を検査するツールも使う

#### 依存ライブラリの更新管理（いぞんらいぶらりのこうしんかんり / Dependency Management）

- 意味：アプリケーションが使うオープンソースなどのライブラリと、その版数を把握し、脆弱性が公表されたら速やかに更新すること
- ポイント：間接的に使うライブラリ（依存の依存）も含めて把握する（SBOM、#19）。名前の似た偽のパッケージ（タイポスクワッティング）や、乗っ取られたパッケージの更新にも注意し、版数を固定してハッシュ値で確かめる

#### 署名付きコミット（しょめいつきこみっと / Signed Commit）

- 意味：Git のコミットに、作成者の GPG や SSH の秘密鍵でデジタル署名を付け、誰が変更したかを検証できるようにすること
- ポイント：Git の作者名やメールアドレスは誰でも自由に設定できるので、署名がないとなりすましの変更を見分けられない。リポジトリの設定で、署名のないコミットを受け付けないようにできる

#### 成果物の署名検証（せいかぶつのしょめいけんしょう / Artifact Signing and Verification）

- 意味：ビルドしたプログラムやコンテナイメージに署名して配布し、使う側（デプロイの仕組みなど）が実行の前に署名を検証すること
- ポイント：配布の途中やリポジトリでのすり替えを防ぐ。コンテナイメージの署名には Sigstore の cosign などが使われる。署名鍵の管理が肝心

#### SLSA（さるさ / Supply-chain Levels for Software Artifacts）

- 意味：OpenSSF が定めた、ソフトウェアのビルドの過程の改ざんを防ぐための要求事項と段階（レベル）の枠組み。成果物が、どのソースから、どのビルド環境で、どう作られたかの来歴（プロヴナンス）を記録・検証する
- ポイント：v1.0 のビルドの段階は L1（来歴がある）、L2（ホスト型のビルド環境で署名された来歴）、L3（改ざんに強いビルド環境）。SolarWinds のようなビルド環境への攻撃（#05）を想定している

#### 要塞化（ようさいか / Hardening）

- 意味：サーバや OS、ミドルウェアから不要な機能やサービス、アカウントを取り除き、初期のパスワードや設定を安全なものに変えて、攻撃される入口を減らすこと
- ポイント：CIS Benchmarks などの基準を使う。コンテナでは、不要なツールを含まない最小のイメージを使い、root で動かさない

### 17-1 セキュア開発の進め方と脆弱性への実装上の対策

#### 問 sc-17-o01

- 問：脆弱性検査の方法のうち、プログラムを動かさずにソースコードを解析し、外部からの入力が無害化されないまま SQL の組立てに使われている箇所などを網羅的に見つけるものはどれか。
- ア：SAST
- イ：DAST
- ウ：ファジング
