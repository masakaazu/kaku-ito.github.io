## 03-1 インジェクションとサーバ側の不備

### まとめ表

| 攻撃 | 何に混ぜ込むか | ログに残る特徴 | 根本的な対策 |
| :-: | :-: | :-: | :-: |
| SQL インジェクション | SQL 文 | `' OR '1'='1`、`UNION SELECT` | プレースホルダ |
| OS コマンドインジェクション | シェルのコマンド | `;cat /etc/passwd`、パイプ記号 | シェルを起動しない |
| HTTP ヘッダインジェクション | 応答ヘッダ | `%0d%0a`（改行） | ヘッダ出力用の API を使う |
| ディレクトリトラバーサル | ファイルのパス | `../../` | ファイル名を直接受け取らない |
| SSRF | サーバが送る要求の宛先 | `http://169.254.169.254/` | 宛先の許可リスト |

### コードやコマンドに混ぜ込む

#### SQLインジェクション（えすきゅーえるいんじぇくしょん / SQL Injection）

- 意味：入力欄やパラメータに SQL の一部となる文字列を入れ、アプリケーションが組み立てる SQL 文の意味を変えて、データベースを不正に操作する攻撃
- ポイント：情報の窃取、データの改ざん・削除、認証の回避が起きる。根本的な対策は、SQL 文を静的プレースホルダ（パラメータ化クエリ）で組み立てること。保険的な対策として、エラーメッセージを画面に出さない、DB のアカウントの権限を最小にする（過去の午前Ⅱで「実装以外の対策」として問われた）
- 例：ID 欄に `' OR '1'='1' --` と入れると、パスワードの条件が無視されてログインできてしまう

#### ブラインドSQLインジェクション（ぶらいんど / Blind SQL Injection）

- 意味：SQL インジェクションの結果が画面に直接表示されない場合に、応答の違い（ページの内容が変わるか）や応答時間の差から、1文字ずつ情報を推測していく攻撃
- ポイント：エラーメッセージを隠しても、プレースホルダを使っていなければ攻撃は成り立つ。だから「エラーを出さない」は根本的な対策にならない
- 例：`AND SUBSTRING(password,1,1)='a'` が真のときだけ通常のページが返ることを利用する

#### OSコマンドインジェクション（おーえすこまんどいんじぇくしょん / OS Command Injection）

- 意味：Web アプリケーションが外部からの入力を使ってシェル経由で OS のコマンドを実行している場合に、入力に別のコマンドを混ぜ込んで、サーバ上で任意のコマンドを実行させる攻撃
- ポイント：`;`、`|`、`&&`、バッククォートなどでコマンドをつなげる。PHP の exec 関数や Perl の open 関数などが危ない。根本的な対策は、シェルを起動する関数を使わない（ライブラリの関数で処理する）こと。過去の午前Ⅱでは、ログの `?user=;cat%20/etc/passwd` から攻撃を見抜く問題が2回出た
- 例：`/cgi-bin/submit.cgi?user=;cat /etc/passwd` で、アカウントの一覧を表示させる

#### HTTPヘッダインジェクション（えいちてぃーてぃーぴーへっだいんじぇくしょん / HTTP Header Injection）

- 意味：HTTP レスポンスヘッダの出力に外部からの値を使っている場合に、値に改行コード（CR LF）を混ぜ込んで、任意のヘッダや本文を追加させる攻撃。HTTP レスポンス分割（HTTP Response Splitting）ともいう
- ポイント：偽の Set-Cookie ヘッダを追加したり、偽のページを表示させたり、キャッシュを汚染したりできる。対策は、ヘッダの出力に専用の API を使う、改行コードを許さないこと。ログには `%0d%0a` が残る
- 語の意味：Header＝（HTTP の）ヘッダ／Injection＝注入

#### メールヘッダインジェクション（めーるへっだいんじぇくしょん / Mail Header Injection）

- 意味：問い合わせフォームなどからメールを送る機能で、宛先や件名の入力に改行コードを混ぜ込み、Bcc などのヘッダを追加して、迷惑メールの送信の踏み台にする攻撃
- ポイント：HTTP ヘッダインジェクションと同じく「改行で新しいヘッダを作る」攻撃。対策は、メールのヘッダを固定値にする、送信用の API を使う、改行を取り除く

#### ディレクトリトラバーサル（でぃれくとりとらばーさる / Directory Traversal）

- 意味：ファイル名を受け取ってファイルを開く処理に、`../` などの親ディレクトリを指す文字列を入れ、公開されるはずのないファイルを読み出す攻撃。パストラバーサルともいう
- ポイント：対策は、外部からファイル名を直接受け取らない（番号などで間接的に指定する）、ファイル名からディレクトリ部分を取り除く。重要なファイルを公開ディレクトリに置かないことは保険的な対策
- 例：`download.php?file=../../../etc/passwd`

#### バッファオーバーフロー（ばっふぁおーばーふろー / Buffer Overflow）

- 意味：プログラムが確保した記憶領域（バッファ）の大きさを超えるデータを書き込ませ、隣の領域（戻り先のアドレスなど）を上書きして、プログラムを異常終了させたり、任意のコードを実行させたりする攻撃
- ポイント：C 言語のように境界の確認を自動で行わない言語で起きやすい。対策は、入力の長さの確認、安全な関数の使用。OS 側の緩和策として、データ領域でのコード実行を禁止する DEP、アドレスを毎回変える ASLR、スタックの破壊を検出するカナリアがある（#17）

#### SSRF（えすえすあーるえふ / Server-Side Request Forgery）

- 意味：外部から指定された URL にサーバが代わりにアクセスする機能を悪用し、本来は外部から届かない内部のサーバや、クラウドのインスタンスメタデータサービスにリクエストを送らせる攻撃
- ポイント：クラウドでは、メタデータサービス（169.254.169.254）から一時的な認証情報を盗まれる事故が起きた。対策は、アクセス先を許可リストで限る、内部のアドレスへの接続を拒否する、メタデータサービスにトークンを必要とする方式（AWS の IMDSv2 など）を使う（#18）。OWASP Top 10:2025 では A01 アクセス制御の不備に含まれた
- 語の意味：Server-Side＝サーバ側の／Request＝リクエスト／Forgery＝偽造

## 03-2 ブラウザを巻き込む攻撃

### まとめ表

| 攻撃 | だれのブラウザで何が起きるか | 根本的な対策 |
| :-: | :-: | :-: |
| 反射型 XSS | 罠のリンクを踏んだ人の画面でスクリプトが動く | 出力時のエスケープ |
| 格納型 XSS | 掲示板などを見た全員の画面でスクリプトが動く | 出力時のエスケープ |
| DOM 型 XSS | ブラウザ側の JavaScript の処理だけで起きる | DOM 操作の安全な API |
| CSRF | ログイン中の人に、意図しない操作を送らせる | 秘密のトークン・再認証 |
| クリックジャッキング | 透明にした本物の画面のボタンを押させる | X-Frame-Options・CSP frame-ancestors |
| オープンリダイレクト | 正規サイトの URL から罠サイトへ飛ばす | 転送先の固定・許可リスト |

### クロスサイトスクリプティング（XSS）

#### クロスサイトスクリプティング（くろすさいとすくりぷてぃんぐ / XSS: Cross-Site Scripting）

- 意味：Web ページに外部からの入力をそのまま出力している箇所を悪用し、攻撃者のスクリプトを閲覧者のブラウザで実行させる攻撃
- ポイント：そのサイトの権限でスクリプトが動くので、cookie（セッション ID）の窃取、偽の入力フォームの表示、画面の書き換えができる。根本的な対策は、HTML に出力するときにすべての値をエスケープする（`<` を `&lt;` に置き換えるなど）。cookie の HttpOnly 属性や CSP は被害を減らす保険的な対策
- 語の意味：Cross-Site＝サイトをまたいだ／Scripting＝スクリプトの実行

#### 反射型XSS（はんしゃがた / Reflected XSS）

- 意味：攻撃者が用意した罠のリンクに含まれるスクリプトが、Web サーバの応答にそのまま「反射」して返り、リンクを踏んだ人のブラウザで実行される XSS
- ポイント：スクリプトはサーバに保存されない。被害者に罠のリンクを開かせる必要がある（メールや別のサイトに置く）
- 例：検索結果のページが、入力した検索語をエスケープせずに「○○の検索結果」と表示する

#### 格納型XSS（かくのうがた / Stored XSS）

- 意味：攻撃者が掲示板の書き込みやプロフィールなどにスクリプトを投稿してサーバに保存させ、そのページを見た人のブラウザで実行させる XSS。持続型ともいう
- ポイント：罠のリンクを踏ませる必要がなく、ページを見ただけで被害を受けるので、反射型より影響が広い

#### DOM型XSS（どむがた / DOM-based XSS）

- 意味：サーバの応答には問題がなく、ブラウザ上の JavaScript が URL の一部（`location.hash` など）を取り出して、そのまま `innerHTML` などで画面に書き込むことで起きる XSS
- ポイント：サーバのログにスクリプトが残らないこともある（URL の `#` 以降はサーバに送られない）。対策は、`textContent` のように HTML として解釈しない API を使うこと

### 利用者に操作をさせる

#### CSRF（しーさーふ / Cross-Site Request Forgery）

- 意味：ログイン中の利用者に罠のページを開かせ、利用者のブラウザから、正規のサイトに意図しないリクエスト（送金、パスワード変更、書き込みなど）を送らせる攻撃。クロスサイトリクエストフォージェリ
- ポイント：ブラウザは正規サイトの cookie を自動で付けて送るので、サーバには本人の操作に見える。対策は、①フォームに推測できない秘密の値（CSRF トークン）を埋め込み、送られてきた値と照合する、②重要な操作の直前にパスワードを入力させる、③Referer で正しい遷移元か確かめる。cookie の SameSite 属性も有効。特殊文字のエスケープは XSS の対策で、CSRF には効かない（過去の午前Ⅱで3回出た）
- 語の意味：Cross-Site＝サイトをまたいだ／Request＝リクエスト／Forgery＝偽造

#### クリックジャッキング（くりっくじゃっきんぐ / Clickjacking）

- 意味：罠のページの上に、正規のサイトのページを iframe で透明にして重ね、利用者がボタンを押したつもりで、実は正規サイトの操作（設定の変更、購入など）をさせる攻撃
- ポイント：対策は、正規サイトが HTTP レスポンスヘッダに X-Frame-Options（DENY や SAMEORIGIN）や CSP の frame-ancestors を設定し、ほかのサイトのフレームに表示されないようにすること。cookie の属性や HSTS では防げない

#### オープンリダイレクトの悪用（おーぷんりだいれくと / Open Redirect）

- 意味：URL のパラメータで指定した任意の宛先に転送する機能を悪用し、正規のサイトの URL に見せかけて、利用者を罠のサイトへ誘導すること
- ポイント：リンクのドメインは本物なので、利用者が信用しやすく、フィッシングに使われる。対策は、転送先を固定するか、許可リストで限ること
- 例：`https://bank.example.jp/login?next=https://evil.example.net/`

#### ドライブバイダウンロード（どらいぶばいだうんろーど / Drive-by Download）

- 意味：Web サイトを閲覧しただけで、利用者が気付かないうちにマルウェアをダウンロード・実行させる攻撃
- ポイント：改ざんされた正規のサイトや悪意のある広告に、エクスプロイトキット（#01）への誘導が仕込まれ、ブラウザやプラグインの脆弱性がつかれる。対策は、OS・ブラウザの更新、不要なプラグインを入れないこと

## 03-3 攻撃と根本的な対策

### まとめ表

| 攻撃 | 根本的な対策 | 保険的な対策（それだけでは不十分） |
| :-: | :-: | :-: |
| SQL インジェクション | 静的プレースホルダ | エラーを出さない、DB の権限を最小に、WAF |
| OS コマンドインジェクション | シェルを起動しない | 入力の検証、実行権限を最小に |
| ディレクトリトラバーサル | ファイル名を直接受け取らない | 重要なファイルを公開領域に置かない |
| XSS | 出力時のエスケープ | HttpOnly、CSP、入力の検証 |
| CSRF | 秘密のトークン、再認証 | Referer の確認、SameSite |

### 対策の言葉

#### 静的プレースホルダ（せいてきぷれーすほるだ / Static Placeholder）

- 意味：SQL 文の値の部分を `?` などの記号（プレースホルダ）にしたまま、データベース側で SQL 文を先に解析・確定させ、あとから値だけを渡す方式。パラメータ化クエリ、プリペアドステートメントともいう
- ポイント：値は SQL 文の構造に影響しないので、SQL インジェクションを原理的に防げる。アプリケーション側のライブラリが値をエスケープして SQL 文を組み立てる「動的プレースホルダ」より安全で、IPA は静的プレースホルダを推奨している
- 例：`SELECT * FROM users WHERE id = ?` に、あとから値を渡す

#### エスケープ処理（えすけーぷしょり / Escaping）

- 意味：出力先で特別な意味をもつ文字を、意味をもたない表現に置き換えること。HTML なら `<` を `&lt;`、`>` を `&gt;`、`"` を `&quot;`、`&` を `&amp;` にする
- ポイント：出力する場所（HTML の本文、属性値、JavaScript の中、URL）によって置き換え方が違う。「入力時」ではなく「出力時」に、出力先に合わせて行うのが原則。XSS の根本的な対策だが、CSRF やクリックジャッキングには効かない

#### CSRFトークン（しーさーふとーくん / CSRF Token）

- 意味：重要な操作を行うフォームに埋め込む、推測できない秘密の値。サーバはリクエストに含まれた値が、そのセッションに発行した値と一致するかを確かめる
- ポイント：罠のページは正規のページに埋め込まれたトークンを読めない（同一オリジンポリシー、#17）ので、正しい値を付けたリクエストを作れない。値はセッションごとに推測できない乱数で作る

#### X-Frame-Options（えっくすふれーむおぷしょんず / X-Frame-Options）

- 意味：自分のページを、ほかのページの frame や iframe の中に表示してよいかをブラウザに指示する HTTP レスポンスヘッダ。DENY（どこにも表示させない）と SAMEORIGIN（同じオリジンのページだけ）がある
- ポイント：クリックジャッキングの対策。現在は CSP の frame-ancestors ディレクティブでも同じ指示ができ、より細かく指定できる

### 03-1 インジェクションとサーバ側の不備

#### 問 sc-03-r04h-q1

- 問：Web サーバのログを分析したところ，Web サーバへの攻撃と思われる HTTP リクエストヘッダが記録されていた。次の HTTP リクエストヘッダから推測できる，攻撃者が悪用しようとしていた可能性が高い脆弱性はどれか。ここで，HTTP リクエストヘッダ中の“%20”は空白を意味する。〔HTTP リクエストヘッダの一部〕`GET /cgi-bin/submit.cgi?user=;cat%20/etc/passwd HTTP/1.1`　`Accept: */*`　`Accept-Language: ja`　`UA-CPU: x86`　`Accept-Encoding: gzip, deflate`　`User-Agent: (省略)`　`Host: test.example.com`　`Connection: Keep-Alive`
- ア：HTTP ヘッダインジェクション（HTTP Response Splitting）
- イ：OS コマンドインジェクション
- ウ：SQL インジェクション
- エ：クロスサイトスクリプティング
- 正解：イ
- 解説：パラメータの値が `;` で始まり、続けて `cat /etc/passwd`（ファイルの中身を表示する OS のコマンド）が書かれている。CGI がシェル経由でコマンドを実行していれば、`;` のあとのコマンドが実行される。
- アの意味：改行コード（%0d%0a）を混ぜてヘッダを追加する攻撃。このリクエストに改行コードはない。
- イの意味：正しい。
- ウの意味：`'` や `OR`、`UNION SELECT` などの SQL の断片が混ざるはず。
- エの意味：`<script>` などの HTML・スクリプトが混ざるはず。
- 出典：IPA 令和4年度春期 情報処理安全確保支援士試験 午前Ⅱ 問1（令和2年度10月 問1 とほぼ同じ）

#### 問 sc-03-r05a-q1

- 問：Web アプリケーションソフトウェアの脆弱性を悪用する攻撃手法のうち，入力した文字列が PHP の exec 関数などに渡されることを利用し，不正にシェルスクリプトを実行させるものは，どれに分類されるか。
- ア：HTTP ヘッダインジェクション
- イ：OS コマンドインジェクション
- ウ：クロスサイトリクエストフォージェリ
- エ：セッションハイジャック
- 正解：イ
- 解説：exec 関数は OS のコマンドを実行する関数。入力がそこに渡されると、攻撃者のコマンドがサーバで実行される。
- アの意味：応答ヘッダに改行コードを混ぜる攻撃。
- イの意味：正しい。
- ウの意味：利用者のブラウザから意図しないリクエストを送らせる攻撃。
- エの意味：セッション ID を盗んでなりすます攻撃（#02）。
- 出典：IPA 令和5年度秋期 情報処理安全確保支援士試験 午前Ⅱ 問1
