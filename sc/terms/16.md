## 16-1 デジタル署名とメッセージ認証符号

### まとめ表

| 仕組み | 作る鍵 | 確かめる鍵 | 完全性 | 送信者の真正性 | 第三者への証明（否認防止） |
| :-: | :-: | :-: | :-: | :-: | :-: |
| ハッシュ値だけ | なし | なし | 偶然の誤りだけ | できない | できない |
| MAC（HMAC など） | 共通鍵 | 同じ共通鍵 | できる | 共通鍵をもつ二者の間だけ | できない |
| デジタル署名 | 送信者の秘密鍵 | 送信者の公開鍵 | できる | できる | できる |

### 署名と MAC

#### デジタル署名（でじたるしょめい / Digital Signature）

- 意味：送信者がメッセージのハッシュ値などを自分の秘密鍵で処理して署名を作り、受信者や第三者が送信者の公開鍵で検証することで、メッセージの完全性と送信者の真正性を確かめる仕組み
- ポイント：秘密鍵は送信者しかもたないので、送信者は「送っていない」と言えない（否認防止）。暗号化（受信者の公開鍵で暗号化）と鍵の使い方が逆なので注意。公開鍵が本人のものであることは証明書（PKI）で保証する

#### メッセージ認証符号（めっせーじにんしょうふごう / MAC: Message Authentication Code）

- 意味：送信者と受信者が共有する共通鍵とメッセージから作る短い値。受信者が同じ計算をして一致すれば、メッセージが改ざんされておらず、共通鍵をもつ相手から来たと分かる
- ポイント：共通鍵は送信者と受信者の二人がもつので、受信者自身も同じ MAC を作れる。だから第三者に「送信者が作った」とは証明できない（R4秋・R6春 問1・2 の正解は「受信者がメッセージの完全性を確認できる」）。MAC は公開鍵では作らない
- 語の意味：Message Authentication＝メッセージの認証、Code＝符号

#### HMAC（えいちまっく / Hash-based Message Authentication Code）

- 意味：SHA-256 などのハッシュ関数と共通鍵を決まった手順で組み合わせて作る MAC（RFC 2104）
- ポイント：単に「鍵＋メッセージ」をハッシュするだけでは、ハッシュ関数の性質を使ってメッセージを後ろに足す攻撃（伸長攻撃）を受けることがある。HMAC は鍵を内側と外側で2回使う構造でこれを防ぐ。JWT の HS256 や API の署名に使う

#### コードサイニング証明書（こーどさいにんぐしょうめいしょ / Code Signing Certificate）

- 意味：ソフトウェアの配布者が、プログラムにデジタル署名を付けるための証明書。利用者は、配布者が誰かと、配布後に改ざんされていないことを確かめられる
- ポイント：署名は「誰が作ったか」と「改ざんがないか」を示すだけで、プログラムが安全であることは保証しない。署名鍵を盗まれると、マルウェアに正規の署名を付けられる（サプライチェーン攻撃、#05）。証明書の期限が切れても検証できるよう、タイムスタンプを付ける

#### XML デジタル署名（えっくすえむえるでじたるしょめい / XML Signature）

- 意味：XML 文書の全体や任意の要素（エレメント）にデジタル署名を付けるための W3C の規格。署名そのものも XML で書く
- ポイント：署名と対象の位置関係で3種類。署名を対象の中に入れる「エンベロープ署名」、対象を署名の中に入れる「エンベローピング署名」、別々に置く「デタッチ署名」。デタッチ署名は同じ XML 文書の中の別のエレメントにも付けられる（R1秋・R5秋・R7秋 の正解）。CMS や ASN.1 を使うのは S/MIME などで、XML 署名ではない

## 16-2 PKI と証明書の運用

### まとめ表

| 機関・文書 | 役割 |
| :-: | :-: |
| CA 認証局 | 証明書にデジタル署名して発行し、失効させる |
| RA 登録局 | 本人確認を行い、発行申請の承認・却下をする |
| VA 検証局 | 証明書の失効状態の問合せに応答する（OCSP レスポンダなど） |
| CP 証明書ポリシー | 証明書をどんな用途・条件で発行するかの方針 |
| CPS 認証局運用規程 | 認証局の認証業務の運用などの詳細を定めた文書 |

| 失効の確かめ方 | しくみ | 特徴 |
| :-: | :-: | :-: |
| CRL | 認証局が失効した証明書のシリアル番号の一覧を定期的に公開 | 一覧が大きくなる、更新までの遅れ |
| OCSP | 証明書ごとに OCSP レスポンダに失効状態を問い合わせる | その時点の状態が分かる |
| OCSP ステープリング | サーバが OCSP の応答を TLS のハンドシェイクで一緒に渡す | 利用者の閲覧先が認証局に漏れない |

### PKI の仕組み

#### PKI（ぴーけーあい / Public Key Infrastructure）

- 意味：公開鍵が本人のものであることを、信頼できる第三者の認証局が証明書で保証し、その発行・配布・失効・検証を行う仕組み全体。公開鍵基盤
- ポイント：日本の政府機関の PKI を政府認証基盤（GPKI）という。Web では、ブラウザや OS に組み込まれたルート認証局の証明書を起点に信頼する

#### デジタル証明書（でじたるしょうめいしょ / Digital Certificate）

- 意味：所有者の名前（ドメイン名など）と公開鍵、有効期限、シリアル番号などを、認証局の秘密鍵でデジタル署名して結び付けたデータ。形式は ITU-T X.509
- ポイント：認証局が署名するのは申請者の「公開鍵」を含む情報で、秘密鍵ではない。署名に使うのは認証局の「秘密鍵」。TLS では鍵交換の正当性の確認と通信相手の認証に使う（R5春・R7春 問6 の正解）。X.400 はメッセージ通信の規格

#### 認証局（にんしょうきょく / CA: Certification Authority）

- 意味：デジタル証明書にデジタル署名を付与して発行し、必要に応じて失効させる機関
- ポイント：ルート認証局は自分で自分の証明書に署名し（自己署名）、下位の認証局（中間認証局）の公開鍵を含む証明書に、ルート認証局の「秘密鍵」で署名する

#### 登録局（とうろくきょく / RA: Registration Authority）

- 意味：証明書を申請した者の本人確認を行い、発行申請の承認または却下を行う機関。発行（署名）そのものは CA が行う
- ポイント：R4秋・R6春・R7秋 問2〜4 の正解は「本人確認を行い、発行申請の承認又は却下」。署名を付与するのは CA、失効状態に応答するのは VA

#### 検証局（けんしょうきょく / VA: Validation Authority）

- 意味：証明書の失効状態についての問合せに応答する機関。OCSP レスポンダとして動く
- ポイント：R1秋・R5秋 問3 の正解。属性証明書を発行するのは属性認証局（AA）

#### CP と CPS（しーぴー・しーぴーえす / Certificate Policy, Certification Practice Statement）

- 意味：CP（証明書ポリシー）は、証明書の用途や信頼の程度など、発行の方針を定めたもの。CPS（認証局運用規程）は、認証局の認証業務の運用（本人確認の方法、鍵の管理、失効の手順など）の詳細を規定した文書
- ポイント：R5秋・R7春 問9 の正解は「認証局の認証業務の運用などに関する詳細を規定した文書」。枠組みは RFC 3647 にある

#### 証明書パス検証（しょうめいしょぱすけんしょう / Certification Path Validation）

- 意味：サーバの証明書から中間認証局の証明書をたどり、信頼するルート認証局の証明書まで、各証明書の署名・有効期限・失効状態・用途の制約が正しいかを順に確かめること（RFC 5280）
- ポイント：サーバは中間証明書も一緒に送る必要がある。一つでも検証に失敗したら信頼しない。自己署名の証明書を利用者に「例外として許可」させる運用は、中間者攻撃を見抜けなくなる

### 失効と発行の管理

#### CRL（しーあーるえる / Certificate Revocation List）

- 意味：認証局が、有効期限内に失効させた証明書のシリアル番号と失効日時などを一覧にし、署名して公開するもの
- ポイント：載るのは「有効期限内に失効した証明書のシリアル番号」（H31春 問1・R6春 問6 の正解）。期限切れの証明書は載せる必要がない。公開鍵ではなくシリアル番号。ルート証明書が組み込まれていても CRL の確認は必要

#### OCSP（おーしーえすぴー / Online Certificate Status Protocol）

- 意味：証明書の失効情報を、OCSP レスポンダにその都度問い合わせるプロトコル（RFC 6960）
- ポイント：H31春・R3春 問2 の正解は「デジタル証明書の失効情報を問い合わせる」。CRL のように大きな一覧を取らなくてよい。応答には「有効・失効・不明」が返る

#### CA/Browser Forum（しーえーぶらうざふぉーらむ / CA/Browser Forum）

- 意味：認証局とブラウザの開発者が集まり、サーバ証明書の発行の基準（Baseline Requirements）などを定める業界団体
- ポイント：ブラウザがこの基準を守らない認証局を信頼しなくなるので、事実上の義務になる。サーバ証明書の最大の有効期間は 398 日で、2026 年 3 月から段階的に短くし、2029 年には 47 日にすることが決まった

#### ACME（あくみー / Automatic Certificate Management Environment）

- 意味：ドメインの管理権限の確認（チャレンジ）、証明書の発行、更新を自動で行うためのプロトコル（RFC 8555）。Let's Encrypt が使う
- ポイント：指定されたファイルを Web サーバに置く（HTTP-01）、DNS に TXT レコードを置く（DNS-01）などで、申請者がそのドメインを管理していることを示す。有効期間の短い証明書を、更新し忘れずに使える

#### CAA（しーえーえー / Certification Authority Authorization）

- 意味：ドメインの管理者が、そのドメインの証明書を発行してよい認証局を DNS の CAA レコードで指定する仕組み（RFC 8659）。認証局は発行前に CAA レコードを確認しなければならない
- ポイント：許可していない認証局による不正なサーバ証明書の発行を防ぐ（R3春・R6春 問10・15 の正解）。発行された証明書を公開ログで監視する Certificate Transparency（CT）と組み合わせる

#### 証明書の透明性（しょうめいしょのとうめいせい / CT: Certificate Transparency）

- 意味：認証局が発行したサーバ証明書を、誰でも見られる追記だけのログに登録させ、ドメインの所有者が自分のドメインに不正な証明書が発行されていないかを監視できるようにする仕組み（RFC 6962）
- ポイント：CAA は発行の「前」に防ぐ、CT は発行の「後」に見つける。ブラウザは CT に登録されていない証明書を信頼しない

## 16-3 応用的な暗号技術

### まとめ表

| 技術 | できること | 例 |
| :-: | :-: | :-: |
| 秘密分散 | 秘密を n 個に分け、k 個集めると復元、k-1 個では何も分からない | 鍵のバックアップ |
| 準同型暗号 | 暗号化したまま計算でき、結果を復号すると平文で計算した値になる | 秘匿したままの統計 |
| ゼロ知識証明 | 秘密そのものを明かさずに、秘密を知っていることを証明する | 年齢の条件だけを証明 |
| TEE | CPU の中の隔離された領域で、OS からも見えないように処理する | Intel SGX、Arm TrustZone |
| 暗号アジリティ | 暗号アルゴリズムを、システムを大きく変えずに切り替えられる | PQC への移行 |

### 秘匿と証明の技術

#### 秘密分散（ひみつぶんさん / Secret Sharing）

- 意味：秘密の情報を n 個の断片（シェア）に分け、決めた数 k 個以上を集めれば元に戻せるが、k-1 個以下では元の情報について何も分からないようにする技術。シャミアの (k, n) しきい値法が代表
- ポイント：一つの断片が盗まれても漏えいにならず、いくつか失っても復元できる。認証局のルート鍵のバックアップを複数の管理者に分けて持たせる、などに使う

#### 準同型暗号（じゅんどうけいあんごう / Homomorphic Encryption）

- 意味：暗号文のまま足し算やかけ算などの計算ができ、その結果を復号すると、平文で計算したのと同じ値になる暗号
- ポイント：クラウドにデータを預けたまま、中身を見せずに集計や分析をさせられる。任意の計算ができる完全準同型暗号（FHE）は処理がとても重い

#### ゼロ知識証明（ぜろちしきしょうめい / Zero-Knowledge Proof）

- 意味：ある主張が正しいこと（秘密を知っていること）を、その秘密自体や、正しいということ以外の情報を相手に一切与えずに証明する方法
- ポイント：「生年月日を見せずに 20 歳以上であることだけを証明する」など、プライバシーを守った認証に使う。パスワードを送らずに知っていることを示す認証にも応用される

#### TEE（てぃーいーいー / Trusted Execution Environment）

- 意味：CPU の中に、通常の OS やアプリケーションから隔離された安全な実行領域を作り、その中で鍵や秘密のデータを処理する仕組み。Intel SGX、Arm TrustZone など
- ポイント：OS が乗っ取られても、TEE の中のデータは読まれにくい。使用中のデータを守る「コンフィデンシャルコンピューティング」の基盤。TPM は鍵の保管と計測が中心の別のチップ

### 移行への備え

#### ML-KEM と ML-DSA（えむえるけむ・えむえるでぃーえすえー / ML-KEM, ML-DSA）

- 意味：NIST が 2024 年に定めた耐量子計算機暗号（PQC）。ML-KEM（FIPS 203）は格子問題による鍵カプセル化（鍵の共有）、ML-DSA（FIPS 204）は格子問題によるデジタル署名
- ポイント：ML-KEM は RSA や ECDH の鍵共有の代わり、ML-DSA は RSA や ECDSA の署名の代わり。移行期は、従来の ECDH と ML-KEM を組み合わせる「ハイブリッド鍵交換」が TLS などで使われ始めている
- 語の意味：ML＝Module-Lattice（モジュール格子）、KEM＝Key Encapsulation Mechanism（鍵カプセル化メカニズム）

#### 暗号アジリティ（あんごうあじりてぃ / Crypto Agility）

- 意味：暗号アルゴリズムが危殆化したときなどに、システムの作りを大きく変えずに、別のアルゴリズムや鍵長へ速やかに切り替えられる性質や設計
- ポイント：アルゴリズムをプログラムに直接書き込まず設定で選べるようにする、使っている暗号の一覧（暗号資産のインベントリ）を作っておく、などで実現する。PQC への移行で特に重要

### 16-1 デジタル署名とメッセージ認証符号

#### 問 sc-16-r06h-q2

- 問：送信者から受信者にメッセージ認証符号（MAC：Message Authentication Code）を付与したメッセージを送り，次に受信者が第三者に転送した。そのときの MAC に関する記述のうち，適切なものはどれか。ここで，共通鍵は送信者と受信者だけが知っており，送信者と受信者のそれぞれの公開鍵は第三者を含めた3名が知っているものとする。
- ア：MAC は，送信者がメッセージと共通鍵を用いて生成する。MAC を用いると，受信者がメッセージの完全性を確認できる。
- イ：MAC は，送信者がメッセージと共通鍵を用いて生成する。MAC を用いると，第三者が送信者の真正性を確認できる。
- ウ：MAC は，送信者がメッセージと受信者の公開鍵を用いて生成する。MAC を用いると，第三者がメッセージの完全性を確認できる。
- エ：MAC は，送信者がメッセージと送信者の公開鍵を用いて生成する。MAC を用いると，受信者が送信者の真正性を確認できる。
- 正解：ア
- 解説：MAC は共通鍵で作り、同じ共通鍵をもつ受信者が完全性を確認できる。共通鍵をもたない第三者は検証できない。
- アの意味：正しい。
- イの意味：第三者は共通鍵を知らないので検証できない。受信者も同じ MAC を作れるので、送信者が作った証明にもならない。
- ウの意味：MAC は公開鍵では作らない。
- エの意味：MAC は公開鍵では作らない。送信者の公開鍵は誰でも知っているので、誰でも作れてしまう。
- 出典：IPA 令和6年度春期 情報処理安全確保支援士試験 午前Ⅱ 問2（令和4年度秋期 問1 と同じ）

#### 問 sc-16-r07a-q6

- 問：XML デジタル署名の特徴はどれか。
- ア：XML デジタル署名の構文には，CMS（Cryptographic Message Syntax）が用いられる。
- イ：XML 文書中のエレメントに対するデタッチ署名（Detached Signature）を作成し，同じ XML 文書に含めることができる。
- ウ：エンベローピング署名（Enveloping Signature）では，一つの署名対象に複数の署名を付与する。
- エ：署名対象と署名アルゴリズムは ASN.1 によって記述する。
- 正解：イ

- イの意味：正しい。
- ウの意味：非公開の独自の暗号は第三者の評価を受けておらず、危険。
- エの意味：暗号化をやめるのは移行への備えではない。
