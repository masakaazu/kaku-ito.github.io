## 11-1 シングルサインオンと認証基盤

### まとめ表

| SSO の方式 | どこで認証するか | 対象システムの改修 | 弱点 |
| :-: | :-: | :-: | :-: |
| リバースプロキシ方式 | 手前のリバースプロキシ | 不要 | 全通信が集中し単一障害点になり得る |
| エージェント方式 | Web サーバに入れたエージェントと認証サーバ | エージェントの導入が必要 | 対象サーバごとに導入の手間 |
| 代理認証方式 | クライアントのソフトが ID・パスワードを代行入力 | 不要 | 各システムのパスワードを保管する |
| フェデレーション方式 | IdP（SAML・OpenID Connect） | 標準規格への対応が必要 | IdP が止まると全部止まる |
| Kerberos 方式 | KDC（主に社内の Windows ドメイン） | 対応が必要 | 時刻のずれに弱い |

### SSO の実装方式

#### シングルサインオン（しんぐるさいんおん / SSO: Single Sign-On）

- 意味：一度の認証で、連携する複数のシステムやサービスを、認証をやり直さずに使えるようにする仕組み
- ポイント：パスワードの使い回しやメモ書きを減らせ、退職時の停止も一か所でできる。一方で、認証の入り口が一つになるので、そこが破られると全部に入られる。だから SSO の入り口には多要素認証（#10）を組み合わせる
- 語の意味：Single＝一回の、Sign-On＝ログイン

#### リバースプロキシ方式（りばーすぷろきしほうしき / Reverse Proxy SSO）

- 意味：利用者と各 Web サーバの間にリバースプロキシを置き、そこで認証してから、認証済みの利用者の通信だけを中継する SSO の方式
- ポイント：対象の Web サーバを改修しなくてよい。その代わり、SSO を使う全ての通信がリバースプロキシに集中するので、性能の上限や単一障害点になり得る（R4秋・R6秋 問8 の正解）

#### エージェント方式（えーじぇんとほうしき / Agent SSO）

- 意味：SSO の対象の Web サーバにエージェント（プラグイン）を組み込み、エージェントが認証サーバと連携して利用者を認証する方式。認証に成功すると cookie を発行し、以後はその cookie で各サーバにアクセスする
- ポイント：エージェントは「Web サーバに」導入する。クライアント PC に入れてログイン画面に代行入力するのは代理認証方式。R4秋・R6秋 問8 はこの2つを入れ替えた誤りの選択肢を置いた

#### 代理認証方式（だいりにんしょうほうしき / Proxy Authentication SSO）

- 意味：クライアント PC のソフトが、各システムのログイン画面を検知して、保管しておいた ID とパスワードを代わりに入力する方式
- ポイント：対象システムの改修は「不要」。古い業務システムにも使える。R4秋・R6秋 問8 の「代理認証方式では対象サーバにモジュールを組み込み改修が必要」は誤り（それはエージェント方式に近い）

### 認証基盤

#### Kerberos（けるべろす / Kerberos）

- 意味：信頼できる第三者の鍵配布センター（KDC）が「チケット」を発行し、利用者はパスワードをネットワークに流さずに、チケットでサービスに認証される方式（RFC 4120）
- ポイント：Windows の Active Directory ドメインの標準の認証。チケットには有効期限と時刻が入るので、サーバと端末の時刻がずれていると失敗する（既定の許容は5分程度）。SAML のアサーションと並べて「チケットを使う」のが Kerberos と覚える
- 例：朝 PC にログインすると TGT をもらい、ファイルサーバを開くときはその TGT でファイルサーバ用のサービスチケットをもらう

#### 鍵配布センター（かぎはいふせんたー / KDC: Key Distribution Center）

- 意味：Kerberos で、利用者を認証して TGT を発行する認証サーバ（AS）と、TGT を確かめてサービスチケットを発行するチケット発行サーバ（TGS）をまとめた呼び名
- ポイント：全利用者・全サービスの鍵をもつので、KDC（Active Directory ではドメインコントローラ）が乗っ取られると、どのチケットでも偽造できる（ゴールデンチケット攻撃、#02）

#### TGT（ちけっとはっこうちけっと / Ticket Granting Ticket）

- 意味：Kerberos で、最初の認証に成功した利用者に AS が発行する「チケットをもらうためのチケット」。有効期間内は、パスワードを入れ直さずにサービスチケットをもらえる
- ポイント：TGT は TGS に見せるもの。サービス（ファイルサーバなど）に見せるのはサービスチケット。この順番が問われる
- 語の意味：Ticket Granting＝チケットを与える

#### LDAP（えるだっぷ / Lightweight Directory Access Protocol）

- 意味：利用者・グループ・組織などの情報を木構造で管理するディレクトリサービスに、問い合わせたり更新したりするためのプロトコル（RFC 4511、TCP 389。TLS で守る LDAPS は 636）
- ポイント：LDAP サーバでの認証は、利用者の DN とパスワードで「バインド」できるかで本人を確かめる。平文のバインドは盗聴されるので、LDAPS か StartTLS を使う。入力をそのまま検索フィルタに入れると LDAP インジェクション（#03）
- 語の意味：Lightweight＝軽量の、Directory＝名簿

#### IDaaS（あいだーす / Identity as a Service）

- 意味：ID の管理、認証、SSO、多要素認証、アクセスのログなどを、クラウドのサービスとして提供するもの（Microsoft Entra ID、Okta など）
- ポイント：多くのクラウドサービスに、SAML や OpenID Connect で SSO できる。利用者の追加・削除を各サービスへ自動で反映する（プロビジョニング）には SCIM を使うことが多い

#### SCIM（すきむ / System for Cross-domain Identity Management）

- 意味：異なるサービスの間で、利用者やグループのアカウント情報を作成・更新・削除するための、REST と JSON による標準（RFC 7643・7644）
- ポイント：SAML や OpenID Connect は「ログインのとき」の連携、SCIM は「アカウントの登録と削除」の連携。退職者のアカウントを各 SaaS からすぐ消す（プロビジョニングとデプロビジョニング）に使う

## 11-2 SAML によるアイデンティティ連携

### まとめ表

| 規格 | 策定 | 形式 | 主な目的 |
| :-: | :-: | :-: | :-: |
| SAML 2.0 | OASIS | XML | 組織をまたぐ認証・属性・認可情報の交換（Web SSO） |
| OAuth 2.0 | IETF（RFC 6749） | JSON ほか | 権限の委譲（認可） |
| OpenID Connect | OpenID Foundation | JSON（JWT） | OAuth 2.0 の上で認証の結果を伝える |
| XKMS | W3C | XML | 公開鍵の登録・検索を Web サービスで |
| XML Signature | W3C | XML | XML 文書へのデジタル署名 |

### ID 連携の登場人物

#### アイデンティティ連携（あいでんてぃてぃれんけい / Identity Federation）

- 意味：ある組織やサービス（IdP）で行った認証の結果や属性を、信頼関係を結んだ別の組織やサービス（SP・RP）に安全に伝え、そこでも本人として扱ってもらう仕組み
- ポイント：SP は利用者のパスワードを受け取らず、IdP が署名して発行した情報（アサーションや ID トークン）を検証する。規格に SAML と OpenID Connect がある

#### IdP（あいでぃーぴー / Identity Provider）

- 意味：ID 連携で、利用者を認証し、その結果と属性を SP に発行する側
- ポイント：SAML でも OpenID Connect でも、利用者認証を行うのは IdP（OpenID Connect では OpenID Provider＝OP とも呼ぶ）

#### SP（えすぴー / Service Provider）

- 意味：ID 連携で、IdP が発行した認証結果を検証し、利用者にサービスを提供する側（OpenID Connect では Relying Party＝RP と呼ぶ）
- ポイント：SP は認証そのものは行わず、アサーションの署名・宛先・有効期限を検証する

### SAML

#### SAML（さむる / Security Assertion Markup Language）

- 意味：標準化団体 OASIS が策定した、組織（ドメイン）をまたいで、認証・属性・認可の情報を XML で安全に交換するための規格。Web のシングルサインオンに使う
- ポイント：過去問の定番は「OASIS」「異なるドメイン間」「XML ベース」「認証・属性・認可」。SOAP（XML のメッセージ交換）、XKMS（鍵管理）、XML Signature（署名）と並べて出る
- 語の意味：Assertion＝表明、Markup Language＝タグで印を付ける言語

#### アサーション（あさーしょん / Assertion）

- 意味：SAML で、IdP が「この利用者を、この時刻に、この方法で認証した」「この利用者の属性はこう」と表明し、署名して SP に渡す XML の文書
- ポイント：SP は IdP の公開鍵で署名を検証し、宛先（Audience）・有効期限・応答先が自分と合うかを確かめる。署名の検証が不十分だと、署名済みの部分を残して中身をすり替える XML 署名ラッピング攻撃を受ける

#### SP-initiated と IdP-initiated（えすぴーいにしえーてっど / SP-initiated SSO）

- 意味：SAML の SSO の始まり方。SP-initiated は、利用者がまず SP にアクセスし、SP が認証要求を作って IdP へリダイレクトする。IdP-initiated は、利用者がまず IdP のポータルにログインし、そこから SP へアサーションを送る
- ポイント：SP-initiated では、SP が送った認証要求の ID とアサーションの応答先（InResponseTo）を照合でき、送り付けの偽アサーションを防ぎやすい

#### XML 署名（えっくすえむえるしょめい / XML Signature）

- 意味：XML 文書の全体や一部に付けるデジタル署名の W3C 勧告。SAML のアサーションの署名に使う
- ポイント：XML Signature そのものは署名の書式で、認証情報を交換する規格ではない。R6春 問4 の誤りの選択肢

## 11-3 OAuth 2.0 と OpenID Connect

### まとめ表

| トークン | 規格 | だれに見せる | 何を表す |
| :-: | :-: | :-: | :-: |
| 認可コード | OAuth 2.0 | クライアントが認可サーバへ | 利用者が許可した、という一回限りの引換券 |
| アクセストークン | OAuth 2.0 | クライアントがリソースサーバへ | 決められた範囲（スコープ）の操作の許可 |
| リフレッシュトークン | OAuth 2.0 | クライアントが認可サーバへ | 新しいアクセストークンをもらう権利 |
| ID トークン | OpenID Connect | IdP（OP）がクライアント（RP）へ | だれが、いつ、どう認証されたか |

### OAuth 2.0 の登場人物と流れ

#### OAuth 2.0（おーおーす / OAuth 2.0 Authorization Framework）

- 意味：利用者（リソースオーナー）の許可のもとで、サービス（クライアント）に、利用者のリソースへの限定されたアクセス権を与えるための「認可」のプロトコル（RFC 6749）
- ポイント：パスワードを渡さずに、アクセストークンという限定された権限を渡す。OAuth は「認可」であり、利用者がだれかを確かめる「認証」ではない。認証の結果がほしいときは OpenID Connect を使う（R5秋・R7春 問14・16 の正解）
- 語の意味：OAuth＝Open Authorization（開かれた認可）

#### リソースオーナーとクライアント（りそーすおーなー / Resource Owner, Client）

- 意味：OAuth 2.0 の4つの役割のうちの2つ。リソースオーナーはリソース（写真・予定など）の持ち主の利用者。クライアントは、利用者の許可を得てリソースを使いたいアプリやサービス
- ポイント：残りの2つは、アクセストークンを発行する認可サーバと、リソースを保管しトークンを確かめて応じるリソースサーバ。R6秋 問16 では「Web サービス C」が認可サーバ兼リソースサーバ、「Web サービス D」がクライアント

#### 認可サーバ（にんかさーば / Authorization Server）

- 意味：OAuth 2.0 で、リソースオーナーを認証して許可（同意）を得たうえで、クライアントにアクセストークンを発行するサーバ
- ポイント：アクセストークンを発行するのは認可サーバ。クライアント（D）ではない。デジタル証明書を送り合う手順も OAuth にはない

#### 認可コードグラント（にんかこーどぐらんと / Authorization Code Grant）

- 意味：OAuth 2.0 の代表的な流れ。利用者をブラウザで認可サーバへ送り、同意後に一回限りの認可コードをクライアントに返し、クライアントがそれを裏側の通信でアクセストークンと交換する
- ポイント：トークンをブラウザの URL に載せないので安全。トークンを直接 URL で返すインプリシットグラントや、利用者のパスワードをクライアントに渡す方式は、RFC 9700（2025年）で使わないよう求められている

#### スコープ（すこーぷ / Scope）

- 意味：OAuth 2.0 で、アクセストークンに許す操作の範囲（「予定の読取りだけ」など）
- ポイント：最小特権（#10）のために、必要なスコープだけを要求する。同意画面で利用者に範囲が示される。偽アプリに広いスコープを許可させる攻撃を同意フィッシング（OAuth フィッシング）と呼ぶ

### トークンと PKCE

#### アクセストークン（あくせすとーくん / Access Token）

- 意味：OAuth 2.0 で、クライアントがリソースサーバにアクセスするときに見せる、権限（スコープ）と有効期限の付いた証
- ポイント：多くは Bearer トークン（RFC 6750）で、持っている者が使えるので、盗まれるとそのまま使われる。だから有効期限を短くし、TLS で守り、ログや URL に残さない
- 語の意味：Bearer＝持参人

#### リフレッシュトークン（りふれっしゅとーくん / Refresh Token）

- 意味：アクセストークンの期限が切れたとき、利用者に同意をやり直させずに新しいアクセストークンをもらうためのトークン。認可サーバにだけ見せ、リソースサーバには見せない
- ポイント：寿命が長いので、漏れたときの影響が大きい。使うたびに新しいものに替える（ローテーション）と、盗まれた古いトークンの再利用を見つけられる

#### PKCE（ぴくしー / Proof Key for Code Exchange）

- 意味：認可コードグラントで、クライアントがランダムな値（code_verifier）を作り、そのハッシュ値（code_challenge）を最初の要求に付け、コードとトークンを交換するときに元の値を見せることで、横取りされた認可コードを他人が使えないようにする仕組み（RFC 7636）
- ポイント：スマホアプリなど秘密の鍵を安全にもてないクライアント（パブリッククライアント）向けに作られたが、RFC 9700 では全てのクライアントで使うよう勧めている。ハッシュは S256（SHA-256）を使う
- 語の意味：Proof Key＝証明の鍵、Code Exchange＝コードの交換

### OpenID Connect と JWT

#### OpenID Connect（おーぷんあいでぃーこねくと / OpenID Connect）

- 意味：OAuth 2.0 の上に「認証」の層を加え、IdP（OpenID Provider）が利用者を認証した結果を ID トークンで RP に伝える規格（OpenID Foundation「OpenID Connect Core 1.0」）
- ポイント：OAuth 2.0＝認可、OpenID Connect＝認証。「ログインに OAuth 2.0 のアクセストークンだけを使う」と、別のアプリ用に発行されたトークンで他人になりすませる危険がある。R5秋 問8 の「URL や XRI を利用者 ID にする」は、古い OpenID 2.0 の説明

#### ID トークン（あいでぃーとーくん / ID Token）

- 意味：OpenID Connect で、IdP が発行する、認証の結果を表す署名付きの JWT。発行者（iss）、利用者の識別子（sub）、宛先（aud）、有効期限（exp）、発行時刻（iat）、nonce などを含む
- ポイント：RP は、署名・iss・aud（自分宛てか）・exp・nonce（自分の要求への応答か）を必ず確かめる。aud を確かめないと、他のサービス宛ての ID トークンを使い回される

#### JWT（じょっと / JSON Web Token）

- 意味：「ヘッダ．ペイロード．署名」の3つを Base64URL で符号化し、ピリオドでつないだ、主張（クレーム）を安全に渡すためのトークンの形式（RFC 7519）
- ポイント：署名（JWS）なら改ざんは見つけられるが、中身は Base64URL で読めるので、秘密の情報を入れない。暗号化したいときは JWE を使う。ヘッダの alg を "none" にした JWT を受け入れてしまう実装の脆弱性が有名で、受け入れるアルゴリズムはサーバ側で固定する
- 語の意味：JSON＝JavaScript Object Notation（データの書式）

#### JWS と JWE（じぇーだぶりゅーえす / JSON Web Signature, JSON Web Encryption）

- 意味：JWS は JSON の内容にデジタル署名か MAC を付ける形式（RFC 7515）、JWE は内容を暗号化する形式（RFC 7516）
- ポイント：JWS は改ざんの検出（完全性）、JWE は秘匿（機密性）。普通の ID トークンは JWS で、中身はだれでも読める

### 11-1 シングルサインオンと認証基盤

#### 問 sc-11-r06a-q8

- 問：シングルサインオン（SSO）に関する記述のうち，適切なものはどれか。
- ア：SAML 方式では，URL 形式の1人一つの利用者 ID を IdP（Identity Provider）で自動生成することによって，インターネット上の複数の Web サイトにおける SSO を実現する。
- イ：エージェント方式では，クライアント PC に導入したエージェントが SSO の対象システムのログイン画面を監視し，ログイン画面が表示されたら認証情報を代行入力する。
- ウ：代理認証方式では，SSO の対象サーバに SSO のモジュールを組み込む必要があり，システムの改修が必要となる。

#### 問 sc-11-o10

- 問：JWT を検証する Web API で、ヘッダの alg を "none" に書き換え、署名を空にした JWT を受け入れてしまう脆弱性への対策として、最も適切なものはどれか。
- ア：JWT のペイロードを Base64URL ではなく Base64 で符号化する。
- イ：サーバ側で受け入れる署名アルゴリズムを固定し、それ以外のアルゴリズムや署名のない JWT を拒否する。
- ウ：JWT の有効期限（exp）を長くする。
- エ：JWT を cookie ではなく URL のクエリ文字列で送る。
- 正解：イ
- 解説：トークンのヘッダが示す alg をそのまま信じると、署名なしの偽トークンを通してしまう。検証側で許すアルゴリズムを決めておく。
- アの意味：符号化の方式を変えても、署名の検証の欠陥はなくならない。
- イの意味：正しい。
- ウの意味：有効期限を長くすると、盗まれたときの被害が広がる。
- エの意味：URL に載せるとログや Referer で漏れやすく、かえって危ない。
- 出典：オリジナル問題（根拠：RFC 8725 JSON Web Token Best Current Practices 3.1・3.2／RFC 7519）
