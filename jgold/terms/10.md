## 10-1 モジュールのしくみ

### まとめ表

| 用語 | 中身 |
| :-: | :-: |
| モジュール | パッケージのまとまり＋module-info.class |
| 読む（read） | requires で、ほかのモジュールを使えるようにすること |
| 公開（exports） | パッケージの public 型を、ほかのモジュールから使えるようにすること |
| 強いカプセル化 | exports していないパッケージは、public クラスでも外から使えない |
| java.base | すべてのモジュールが自動で読む（requires java.base mandated） |

### 基本

#### モジュール（もじゅーる / module）

- 意味：関係のあるパッケージとリソースをまとめ、名前・依存するモジュール・公開するパッケージを module-info.java で宣言したもの（Java 9〜）
- ポイント：モジュールの中のクラスは、必ずどこかのパッケージに入れる（無名パッケージは「unnamed package is not allowed in named modules」）。1 つのパッケージを 2 つのモジュールに置くこと（分割パッケージ）はできない

#### module-info.java（もじゅーるいんふぉ / module declaration）

- 意味：モジュールの名前と、requires・exports・opens・uses・provides などのディレクティブを書くファイル。モジュールのソースの一番上のディレクトリに置く
- ポイント：コンパイルすると module-info.class になる。ファイル名は module-info.java で固定（ハイフンを含むので、ふつうのクラス名にはならない）

#### モジュール名（もじゅーるめい / module name）

- 意味：モジュールを区別する名前。パッケージ名と同じく、ドットで区切った識別子
- ポイント：ハイフンは使えない（module my-mod は「'{' expected」）。逆ドメイン名（com.example.app）が推奨。最後が数字だと javac が警告（module name component m3 should avoid terminal digits）を出すが、エラーではない

#### 強いカプセル化（つよいかぷせるか / strong encapsulation）

- 意味：exports していないパッケージは、public クラスであっても、ほかのモジュールからコンパイル時にも実行時にも使えないというしくみ
- ポイント：コンパイルでは「package com.lib.internal is not visible（package com.lib.internal is declared in module com.lib, which does not export it）」。リフレクションでも setAccessible が InaccessibleObjectException になる（opens していない場合）

#### 読みやすさ（よみやすさ / readability）

- 意味：モジュール A が requires でモジュール B を指定したとき、「A は B を読む（reads）」という。A は B が exports したパッケージを使える
- ポイント：requires がないと「package java.sql is not visible（… but module m4 does not read it）」。読むことと、公開されていることの両方がそろって初めて使える（アクセス可能性 accessibility）

#### モジュール型 JDK（もじゅーるがたじぇーでぃーけー / modular JDK）

- 意味：Java 9 から、JDK 自体が java.base・java.sql・java.logging などのモジュールに分けられていること
- ポイント：java.base（java.lang・java.util・java.io など）はすべてのモジュールが自動で読む。java --list-modules で一覧が出る（JDK 17 の Temurin では 70 個）

## 10-2 module-info.java のディレクティブ

### まとめ表

| ディレクティブ | 意味 |
| :-: | :-: |
| requires M | M を読む（コンパイル時も実行時も必要） |
| requires transitive M | M を読み、自分を読むモジュールにも M を読ませる |
| requires static M | コンパイル時だけ必要（実行時はなくてもよい） |
| exports P | P の public 型をすべてのモジュールに公開 |
| exports P to M1, M2 | M1・M2 にだけ公開（限定公開） |
| opens P | 実行時のリフレクション（private も）を許す |
| opens P to M | M にだけリフレクションを許す |
| open module | すべてのパッケージを opens する |
| uses・provides … with | サービスの利用・提供（#11） |

### 依存

#### requires（りくわいあず / requires）

- 意味：自分のモジュールが、指定したモジュールを読むことを宣言するディレクティブ
- ポイント：同じモジュールを 2 回書くと「duplicate requires: java.sql」。モジュールどうしの循環（A が B を、B が A を requires）は「cyclic dependence involving com.lib」。実行時にモジュールが見つからないと「java.lang.module.FindException: Module a.core not found, required by b.api」
- 語の意味：require＝必要とする

#### requires transitive（りくわいあずとらんじてぃぶ / requires transitive）

- 意味：指定したモジュールを読み、さらに自分を requires するモジュールにも、そのモジュールを読ませる（暗黙の読み取り implied readability）ディレクティブ
- ポイント：b.api が `requires transitive a.core` なら、`requires b.api` だけの c.app も a.core のパッケージを使える。transitive がなければ「package a.core is not visible（… but module c.app does not read it）」。java.sql は java.logging・java.xml・java.transaction.xa を requires transitive している
- 語の意味：transitive＝推移的な（次へ受け渡す）

#### requires static（りくわいあずすたてぃっく / requires static）

- 意味：コンパイル時には必要だが、実行時にはなくてもよい（任意の）依存を宣言するディレクティブ
- ポイント：実行時に、そのモジュールは自動では読み込まれない。モジュール・パスにあっても、ほかに requires するものがなければ解決されない（--add-modules で加えれば使える）。ないまま使うと NoClassDefFoundError

#### java.base（じゃばべーす / java.base）

- 意味：java.lang・java.util・java.io などの基本のパッケージを持つ、JDK の土台のモジュール
- ポイント：すべてのモジュールが自動で読む（--describe-module で「requires java.base mandated」）。`requires java.base;` と書いてもエラーにはならない

### 公開

#### exports（えくすぽーつ / exports）

- 意味：パッケージを、ほかのモジュールから使えるように公開するディレクティブ
- ポイント：指定するのはパッケージ名で、クラス名やモジュール名ではない。存在しないパッケージ（クラス名を書いたときも）は「package is empty or does not exist: com.lib.api.Greeter」。サブパッケージは含まれない（com.lib を exports しても com.lib.api は公開されない）

#### 限定公開（げんていこうかい / qualified export）

- 意味：`exports パッケージ to モジュール1, モジュール2;` の形で、指定したモジュールにだけパッケージを公開すること
- ポイント：指定されたモジュールからは、ふつうの exports と同じように使える。ほかのモジュールからは見えない

#### opens（おーぷんず / opens）

- 意味：パッケージを、実行時のリフレクション（深いリフレクション：private メンバーへの setAccessible(true)）に開くディレクティブ
- ポイント：exports はコンパイル時と実行時の public へのアクセス、opens は実行時のリフレクションだけ。opens だけではコンパイル時にそのパッケージを使えない。opens していないパッケージの private フィールドに setAccessible(true) すると InaccessibleObjectException。`opens P to M` で限定もできる

#### open module（おーぷんもじゅーる / open module）

- 意味：`open module 名前 { … }` と宣言し、モジュールのすべてのパッケージを opens したことにするモジュール
- ポイント：open module の中に opens は書けない（'opens' only allowed in strong modules）。exports はふつうに書ける

## 10-3 コンパイルと実行のコマンド

### まとめ表

| コマンド | 意味 |
| :-: | :-: |
| javac -d out --module-source-path src -m com.app | src/com.app などのモジュールを out/com.app などにコンパイル |
| javac -d out/com.app -p libs ...java | 1 つのモジュールをコンパイル（依存はモジュール・パスから） |
| java -p out -m com.app/com.app.Main | モジュールのメインクラスを実行 |
| java -p jars -m com.app | jar の main-class で実行 |
| java --list-modules | 使えるモジュールの一覧 |
| java -p out --describe-module com.lib（-d） | モジュールの中身を表示 |
| jar --create --file app.jar --main-class com.app.Main -C dir . | モジュール jar を作る |
| jar --describe-module --file app.jar | jar のモジュールの中身 |
| jlink --module-path … --add-modules … --output … | 必要なモジュールだけのランタイムを作る |

### オプション

#### モジュール・パス（もじゅーるぱす / module path）

- 意味：モジュール（展開したディレクトリやモジュール jar）を探す場所。--module-path または -p で指定する
- ポイント：クラスパス（-cp）とは別物。モジュールをクラスパスに置くと、無名モジュールのふつうの jar として扱われる（#11）

#### --module（もじゅーる / --module, -m）

- 意味：java コマンドで、実行するモジュールとメインクラスを `モジュール名/クラスの完全修飾名` の形で指定するオプション。短い形は -m
- ポイント：jar に main-class が入っていれば `-m com.app` だけでよい。入っていないモジュールで `/クラス名` を省くと「module com.app does not have a ModuleMainClass attribute, use -m <module>/<main-class>」。javac の -m は「コンパイルするモジュール」の指定で、意味が違う

#### --module-source-path（もじゅーるそーすぱす / --module-source-path）

- 意味：javac で、モジュールごとのソースのディレクトリ（src/モジュール名/…）をまとめて指定するオプション
- ポイント：-d で指定したディレクトリの下に、モジュール名のディレクトリができる（out/com.app/com/app/Main.class・out/com.app/module-info.class）

#### --describe-module（でぃすくらいぶもじゅーる / --describe-module, -d）

- 意味：java コマンドで、モジュールの exports・requires・contains（公開していないパッケージ）などを表示するオプション。短い形は -d
- ポイント：java の -d は --describe-module。javac の -d は出力先のディレクトリ。jar では `jar --describe-module --file x.jar`（main-class も表示される）

#### --list-modules（りすともじゅーるず / --list-modules）

- 意味：java コマンドで、使えるモジュールの一覧（名前@バージョン）を表示するオプション
- ポイント：-p を付けると、そのパスのモジュールも一覧に入る

#### --add-modules（あっどもじゅーるず / --add-modules）

- 意味：最初に解決するモジュール（ルート）を追加するオプション
- ポイント：requires static だけで参照されているモジュールを、実行時に使えるようにしたいときなどに使う

#### --show-module-resolution（しょうもじゅーるりぞりゅーしょん / --show-module-resolution）

- 意味：起動時に、どのモジュールがどのモジュールを requires して解決されたかを表示するオプション
- ポイント：「root c.app …」「c.app requires b.api …」のように表示される

#### jlink（じぇいりんく / jlink）

- 意味：アプリに必要なモジュールだけを集めて、小さな Java ランタイムを作るツール
- ポイント：`jlink --module-path … --add-modules com.app --output myjre`。自動モジュール（#11）は jlink に入れられない

### 10-1 モジュールのしくみ

#### 問 jgold-10-o01

- 問：モジュール com.lib に次の module-info.java がある。com.lib には com.lib.api と com.lib.internal の 2 つのパッケージがあり、どちらにも public クラスがある。正しいものはどれか。

  ```
  module com.lib {
    exports com.lib.api;
  }
  ```

- ア：com.lib.internal の public クラスも、ほかのモジュールから使える
- イ：com.lib.internal の public クラスは、ほかのモジュールからはコンパイル時に使えない
- ウ：com.lib.internal を使うには、ほかのモジュールで requires com.lib.internal と書けばよい
- エ：com.lib の中の com.lib.api のクラスも、com.lib.internal のクラスを使えない
- 正解：イ
- 解説：exports していないパッケージは、public クラスでも外のモジュールからは使えない（強いカプセル化）。コンパイル済みの com.lib を使う側で import すると「package com.lib.internal is not visible（package com.lib.internal is declared in module com.lib, which does not export it）」。
- アの意味：Java 8 までのクラスパスなら使えたが、モジュールでは exports が必要。
- イの意味：正しい。
- ウの意味：requires に書くのはモジュール名で、パッケージ名ではない。
- エの意味：同じモジュールの中なら、exports に関係なく使える。
- 出典：オリジナル問題（根拠：JLS 7.7.2 Exported and Opened Packages、JEP 261／JDK 17 でのコンパイル結果）

#### 問 jgold-10-o02

- 問：モジュール m4 の module-info.java が `module m4 { exports p; }` で、p.A の中で java.sql.Connection と java.util.logging.Logger を使っている。コンパイルの結果として正しいものはどれか。

### 10-2 module-info.java のディレクティブ

#### 問 jgold-10-o07

- 問：3 つのモジュールが次のように宣言されている。c.app の Main で a.core.Core を使ったとき、正しいものはどれか。

  ```
  module a.core { exports a.core; }
  module b.api { requires transitive a.core; exports b.api; }
  module c.app { requires b.api; }
  ```

- ア：c.app は a.core を requires していないので、コンパイルエラーになる
- イ：c.app は b.api を通して a.core を読むので、a.core.Core を使える
- ウ：コンパイルはできるが、実行時に IllegalAccessError になる
- エ：b.api が a.core を exports していないので使えない
- 正解：イ
- 解説：requires transitive により、b.api を読むモジュール（c.app）も a.core を読む（暗黙の読み取り）。JDK 17 で実行すると問題なく動いた。
- アの意味：transitive がなければそうなる（package a.core is not visible）。
