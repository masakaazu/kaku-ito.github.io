## 11-1 3 種類のモジュール

### まとめ表

| | 名前付きモジュール | 自動モジュール | 無名モジュール |
| :-: | :-: | :-: | :-: |
| 置く場所 | モジュール・パス | モジュール・パス | クラスパス |
| module-info | ある | ない | ない（あっても無視） |
| 名前 | module-info の名前 | jar のファイル名かマニフェストから | なし |
| 公開するパッケージ | exports したものだけ | すべて | すべて |
| 読むモジュール | requires したものだけ | すべて（無名モジュールも） | すべて |
| 名前付きモジュールから requires | できる | できる | できない |

### 種類

#### 名前付きモジュール（なまえつきもじゅーる / named module）

- 意味：module-info.class を持ち、モジュール・パスに置かれたモジュール（明示的モジュール explicit module とも）
- ポイント：requires したモジュールだけを読み、exports したパッケージだけを公開する。無名モジュール（クラスパス）は読めない

#### 自動モジュール（じどうもじゅーる / automatic module）

- 意味：module-info を持たないふつうの jar を、モジュール・パスに置いたときにできるモジュール
- ポイント：jar の中のすべてのパッケージを exports（と opens）し、ほかのすべてのモジュール（無名モジュールを含む）を読む。名前付きモジュールから requires できるので、古いライブラリをそのまま使う「橋渡し」になる。jlink には入れられない

#### 自動モジュールの名前（じどうもじゅーるのなまえ / automatic module name）

- 意味：マニフェストに Automatic-Module-Name があればその名前、なければ jar のファイル名から作られる名前
- ポイント：ファイル名からは「.jar を取る → 末尾の -数字… をバージョンとして外す → 英数字以外をドットに → ドットの連続を 1 つに、前後のドットを取る」。commons-lang3-3.12.0.jar は commons.lang3、my_util-2.0-SNAPSHOT.jar は my.util、x--y-1.jar は x.y

#### 無名モジュール（むめいもじゅーる / unnamed module）

- 意味：クラスパスに置いたクラスや jar がすべて入る、名前のないモジュール
- ポイント：すべてのパッケージを公開し、すべてのモジュールを読む。ただし名前がないので、名前付きモジュールからは requires できない（クラスパスのパッケージは「package legacy.util does not exist」）。getModule() の toString は「unnamed module @…」、isNamed() は false

#### 分割パッケージ（ぶんかつぱっけーじ / split package）

- 意味：同じ名前のパッケージが、2 つ以上のモジュールに入っていること
- ポイント：モジュール・パスでは許されない。同じパッケージを持つ 2 つの jar を自動モジュールにすると「module com.app reads package legacy.util from both my.util and commons.lang3」

## 11-2 移行と jdeps

### まとめ表

| 移行の方法 | 進め方 |
| :-: | :-: |
| ボトムアップ | 依存されている側（下の層）から順に module-info を足して名前付きモジュールにする。まだのものはクラスパス（無名）に残す |
| トップダウン | アプリ（上の層）を先に名前付きモジュールにし、まだのライブラリはモジュール・パスに置いて自動モジュールとして requires する |

### 移行

#### ボトムアップ移行（ぼとむあっぷいこう / bottom-up migration）

- 意味：ほかに依存しない（依存される側の）jar から順に、名前付きモジュールにしていく移行の方法
- ポイント：モジュールにしたものはモジュール・パスへ、まだのものはクラスパスに残す。名前付きモジュールは無名モジュールを読めないので、下から順に進める

#### トップダウン移行（とっぷだうんいこう / top-down migration）

- 意味：アプリ側から先に名前付きモジュールにし、まだモジュールになっていない依存先の jar は、モジュール・パスに置いて自動モジュールとして使う移行の方法
- ポイント：アプリの module-info には、自動モジュールの名前（jar のファイル名から作った名前など）を requires で書く。自分で管理していないライブラリがあるときに使う

#### jdeps（じぇいでっぷす / jdeps）

- 意味：クラス・jar・モジュールが、どのパッケージやモジュールに依存しているかを調べるツール
- ポイント：-s（-summary）でモジュール（jar）単位の依存だけを表示（「my-util.jar -> java.base」）。--jdk-internals で JDK 内部 API（sun.misc.Unsafe など）の利用と代替を表示。--generate-module-info で module-info.java のひな形を作る。--module-path でモジュールを探す場所を指定

#### JDK 内部 API（じぇーでぃーけーないぶえーぴーあい / JDK internal API）

- 意味：sun.misc.Unsafe や sun.* などの、JDK の実装用で公開を約束していない API
- ポイント：将来なくなったり変わったりする。jdeps --jdk-internals で「JDK internal API (jdk.unsupported)」のように見つけられる。javac も「internal proprietary API and may be removed in a future release」と警告する

## 11-3 サービス

### まとめ表

| 役割 | module-info の書き方 |
| :-: | :-: |
| サービス・インタフェース（API）のモジュール | exports svc.api; |
| サービス・プロバイダ（実装）のモジュール | requires svc.api; provides svc.api.Greeter with svc.impl.Polite, svc.impl.Casual; |
| サービスを使うモジュール | requires svc.api; uses svc.api.Greeter; |

### しくみ

#### サービス（さーびす / service）

- 意味：インタフェース（または抽象クラス）を決めておき、その実装を別のモジュールが提供し、使う側は実装を知らずに ServiceLoader で取り出すしくみ
- ポイント：使う側は実装のモジュールを requires しない。実装のパッケージを exports する必要もない（provides で十分）。実装を入れ替えるとき、使う側を直さなくてよい（疎結合）

#### サービス・プロバイダ・インタフェース（さーびすぷろばいだいんたふぇーす / service provider interface, SPI）

- 意味：サービスとして提供する機能を表すインタフェース。使う側と提供する側の両方が依存する
- ポイント：SPI のモジュールは、そのパッケージを exports する

#### サービス・プロバイダ（さーびすぷろばいだ / service provider）

- 意味：サービス・インタフェースを実装し、`provides インタフェース with 実装クラス;` で宣言したもの
- ポイント：実装クラスは、public の引数なしコンストラクタを持つか、`public static 実装 provider()` メソッドを持つ必要がある（ないと「the no arguments constructor of the service implementation is not public」）。インタフェースを実装していないと「the service implementation type must be a subtype of the service interface type, or have a public static no-args method named "provider" …」

#### uses（ゆーずず / uses）

- 意味：自分のモジュールがサービスを使う（ServiceLoader で取り出す）ことを宣言するディレクティブ
- ポイント：uses を書かずに ServiceLoader.load を呼ぶと、実行時に「java.util.ServiceConfigurationError: svc.api.Greeter: module svc.app does not declare `uses`」

#### provides … with（ぷろばいずうぃず / provides ... with）

- 意味：自分のモジュールが、サービス・インタフェースの実装を提供することを宣言するディレクティブ
- ポイント：with の後ろに実装クラスを複数並べられる（カンマ区切り）。--describe-module では「provides svc.api.Greeter with svc.impl.Polite svc.impl.Casual」と表示される

#### ServiceLoader（さーびすろーだ / ServiceLoader）

- 意味：サービスの実装を探して取り出すクラス。ServiceLoader.load(インタフェース.class) で作る
- ポイント：Iterable なので for 文で実装のインスタンスを順に取り出せる。findFirst() は Optional を返し、実装がなければ Optional.empty（例外にならない）。stream() は ServiceLoader.Provider の Stream を返し、Provider.type() はクラスを返すだけでインスタンスを作らない、Provider.get() で作る

#### サービス・ロケータ（さーびすろけーた / service locator）

- 意味：サービスの実装を探して返す役目のクラス。ServiceLoader を包んで、使う側に実装を渡す
- ポイント：ロケータのモジュールに uses を書く。使う側はロケータを呼ぶだけで、ServiceLoader を直接使わなくてよい

### 11-2 移行と jdeps

#### 問 jgold-11-o11
